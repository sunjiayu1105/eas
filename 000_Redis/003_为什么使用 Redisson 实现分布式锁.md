## 4 面试口述版本

口述内容字符数：752

如果项目已经使用 Redis，又需要让多个 Java 应用实例协调同一资源，我会优先考虑 Redisson。它提供了现成的分布式锁，应用可以直接调用，少维护一套锁的持有者校验、等待重试和续期机制。业务仍要确定锁的适用范围和参数，并保护锁失效后的写入。

### 4.1 为什么需要分布式锁

多个应用实例可能同时处理同一个订单，而 Java 的本地锁只能协调同一个进程内的线程。使用 Redis 锁时，这些实例访问同一套 Redis，竞争同一资源对应的锁键，只有明确获取成功的请求才进入受保护的业务。这个协调过程就是分布式锁的作用；锁失效后仍可能有旧请求继续执行。

### 4.2 手写 Redis 锁需要解决什么问题

加锁时，用一条命令完成“锁键不存在才写入、记录本次持有者、设置过期时间”，避免写入锁键后还没设置过期时间就崩溃。解锁时，要在 Redis 中一次完成比较和删除。只有锁中保存的值与本次获取时写入的唯一值一致，才删除锁键。这样旧请求即使在自己的锁到期后才解锁，也不会误删新请求取得的锁。[手写锁命令、示例与返回结果（第 57 行）](<D:/000/sources/eas/000_Redis/004_为什么使用 Redisson 实现分布式锁_手写 Redis 锁的加锁与解锁.md:57>)

### 4.3 为什么选择 Redisson

Redisson 提供 RLock 接口，业务直接调用它完成加锁和解锁。普通 RLock 支持可重入，也就是同一个持有者可以多次获取并逐次释放。遇到竞争时可以等待解锁通知再重试，使用未指定固定租期的 tryLock 调用并且获取成功后，Redisson 还会安排看门狗自动续期。应用因此少维护一套通用锁机制，仍需管理客户端依赖、连接配置、等待时间、租期和异常处理。[选型收益与代价（第 43 行）](<D:/000/sources/eas/000_Redis/003_为什么使用 Redisson 实现分布式锁.md:43>)

### 4.4 锁失效后还有哪些责任

锁到期或故障切换后，旧请求可能继续写入，而新请求也可能已经拿到锁。安全解锁保护的是新持有者的锁键，写入端还要按业务要求校验，例如更新时检查数据版本有没有改变。[锁失效与业务写入保护（第 39 行）](<D:/000/sources/eas/000_Redis/005_为什么使用 Redisson 实现分布式锁_锁失效后的业务写入保护.md:39>)

## 5 详细方案

### 5.1 选择 Redisson 的理由与代价

Java 本地线程锁的协调范围在同一进程内；部署多个应用实例时，若要协调同一资源，需要共同的协调机制。手写 Redis 锁与 Redisson 都通过 Redis 协调不同进程对资源的访问，都必须考虑持有者、有效期和失锁后的业务保护。比较的重点是锁机制由谁实现和维护。

**手写字符串锁：** 应用使用 `SET NX PX` 和 Lua 释放脚本实现基础互斥。基础字符串锁不提供重入；若业务还需要等待重试和续期，需要另外实现对应机制，并验证异常和并发边界。

**Redisson：** 应用使用现成的 `RLock` 接口。3.17.7 普通锁用客户端标识和线程 ID 标识持有者，在 Hash 中记录重入计数，由 Lua 原子处理获取、续期和释放；它还实现了解锁通知订阅和等待重试。收益是减少应用自行实现这些通用机制的工作，而不是免除业务验证。代价是增加客户端依赖、配置和版本维护，并需要理解等待、固定租期与看门狗的差异。

具体参数及内部处理见 [看门狗与等待机制（第 132 行）](<D:/000/sources/eas/000_Redis/006_Java 中如何使用 Redisson 实现分布式锁.md:132>)。依据：[RedissonLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonLock.java)、[RedissonBaseLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonBaseLock.java)、[Config 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/config/Config.java)。

手写锁的实现细节见 [手写 Redis 锁的加锁与解锁](<D:/000/sources/eas/000_Redis/004_为什么使用 Redisson 实现分布式锁_手写 Redis 锁的加锁与解锁.md>)。

### 5.2 选型成立的条件和安全边界

选择 Redisson 的前提是业务需要基于 Redis 协调多个进程，并愿意承担客户端接入和维护成本。它提供的续期可以降低固定过期时间到期而失锁的风险，但不能保证续期永不失败，也不能终止失去锁的旧请求。

原子解锁只保护锁键，不能阻止旧请求修改数据库。严格的数据约束仍需写入端校验；条件更新、唯一约束和 fencing token 各有用途，完整解释见 [锁失效后的写入保护（第 45 行）](<D:/000/sources/eas/000_Redis/005_为什么使用 Redisson 实现分布式锁_锁失效后的业务写入保护.md:45>)。Redis 异步复制下的故障切换也可能丢失锁记录，因此部署拓扑和故障行为必须验证。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。本项目的版本基线已确认，但实际部署、依赖兼容性和故障行为尚未验证。

## 8 异议与分析

1. 旧总述“用 Redisson 封装这些机制”未准确表达能力归属，且可能让读者把普通字符串锁与 Redisson 的实现等同。Redisson 已提供基于 Hash 和 Lua 的锁实现，应用调用其接口；总述和口述现已明确这一区别。

2. 原材料用“有看门狗续期和等待队列”概括 Redisson，容易省略租期条件并混淆公平性。依据 3.17.7 源码，正数固定租期不启用该看门狗路径，普通 `RLock` 的通知和重试也不保证先到先得；正文已补充这些边界。
