## 2 问题

为什么在 Java 中选择 Redisson 实现分布式锁，而不是自己组合 Redis 命令实现？Redisson 解决了哪些问题，又有哪些问题仍需业务处理？

## 3 高级 Java 面试核心考点

1. 分布式锁协调多个进程，本地线程锁无法直接完成跨进程互斥。
2. 手写锁必须原子加锁、设置过期时间，并原子校验持有者后释放。
3. Redisson 提供锁接口、持有者校验、可重入、等待重试和有条件的续期，减少自行实现和维护这些机制的工作。
4. Redisson 仍有依赖、参数和故障处理成本，不保证锁失效后业务数据绝对安全。

## 4 面试口述版本

口述内容字符数：2392

我选择 Redisson，主要是因为分布式锁不只是创建一个 Redis 键。还需要正确处理原子加锁、持有者校验、过期时间、等待重试和续期。Redisson 已经实现了这些机制，业务可以直接调用它提供的锁接口，减少自行编写和维护锁实现的工作。但使用它以后，仍要正确设置参数、处理异常，并保护锁失效后的业务写入。

### 4.1 先明确为什么需要跨进程的锁

多个应用实例可能同时处理同一个订单，而 Java 的本地锁只能协调同一个进程内的线程。使用 Redis 锁时，这些实例访问同一套 Redis，竞争同一资源对应的锁键，只有明确获取成功的请求才进入受保护的业务。这个协调过程就是分布式锁的作用；锁失效后仍可能有旧请求继续执行。

### 4.2 手写锁首先要保证原子加锁

**准备锁键和持有者标识**

Redis 的通用写入格式是 `SET key value`。在锁场景中，`key` 是锁的名称，`value` 是锁键保存的值，用来标识本次锁的持有者。每次获取锁都应生成新的唯一值，例如 UUID（通用唯一标识符）；不能让所有请求都写固定值 `1`，否则无法区分不同持有者。这个标识用于解锁时判断锁是否仍属于当前请求。

**用一条命令完成加锁**

加锁使用 `SET key value NX PX ttl`。`SET` 是写入字符串值的命令。`NX` 通常理解为 Not eXists，意思是“键不存在”，表示只有键不存在时才写入；键已经存在，就不修改。`PX` 是按毫秒设置过期时长的选项，`ttl` 是具体时长，必须是正整数。`EX` 则按秒设置过期时长，可以用 EXpire（过期）帮助记忆。`PX` 可以联想 Precise（精细的）＋ eXpire（过期），但这只是助记法，不是已核实的官方英文全称。

例如，`SET lock:order:1001 request-a-unique-value NX PX 30000`，表示订单 `1001` 的锁不存在时，创建这个锁，把本次持有者标识写入 value，并设置 30000 毫秒，也就是 30 秒后过期。这里的持有者标识和 30 秒都是示例；实际每次生成新的唯一值，过期时长要根据业务耗时确定，不能直接照搬 30 秒。设置过期时间是为了让持有者崩溃后，锁不会永久占用。

**为什么不能分两条命令**

这条命令把“判断键不存在、写入值、设置过期时间”一起原子执行，也就是其他客户端命令不能插入这些步骤之间。不能分开执行 `SETNX`（键不存在时写入）和 `EXPIRE`（设置过期时间），否则两条命令之间进程崩溃，可能留下没有过期时间的锁。锁到期只会使键失效，不会停止正在执行的业务线程。

**根据结果决定是否执行业务**

收到 `OK` 表示命令执行时成功获得锁，才能继续业务；返回空值表示锁键已存在，本次没有获得锁，也不会刷新原锁的过期时间。如果请求超时或连接异常，可能是命令没有执行，也可能是执行成功但响应丢失，不能据此认定获得了锁。

这些步骤都需要自己实现和核对，不能只看到 `SET` 成功就忽略过期和异常分支。[手写锁的原子加锁（第 80 行）](<D:/000/sources/eas/000_Redis/003_为什么使用 Redisson 实现分布式锁.md:80>)

### 4.3 手写锁还要避免误删别人的锁

安全释放是分布式锁使用完后的解锁步骤，要求一个请求只能删除自己仍持有的锁。Redis 中的锁键表示资源被占用；业务结束后，在 `finally` 中主动释放自己仍持有的锁，让其他应用实例可以继续竞争，不必一直等到锁过期。

不能直接用 `DEL` 删除锁键。例如，请求 A 获得锁，写入 `value-A`；A 执行太久，锁过期，请求 B 随后获得同一个锁，写入 `value-B`。如果 A 恢复后直接删除锁键，就会删掉 B 的锁。请求 C 看到锁键不存在，又能获得锁，这时 B 和 C 可能同时处理同一资源，破坏互斥，也就是不能再保证它们不会同时进入受保护的业务。

因此，释放时要用 Lua 脚本在 Redis 中原子比较锁键保存的 value 与自己加锁时写入的值，一致才删除。上例中，A 保存的 `value-A` 与 Redis 当前的 `value-B` 不一致，就不能删除 B 的锁。也不能先 `GET` 读取并比较，再单独 `DEL` 删除，因为这两条命令之间仍可能发生锁过期和其他请求重新加锁。

原子加锁负责竞争锁，安全释放负责归还自己仍持有的锁。安全释放只防止误删别人的锁，不会阻止已经失去锁的旧线程继续执行业务。

这也是选择锁框架的理由：应用需要的是安全解锁能力，而不仅是一条删除命令。[原子校验后释放（第 98 行）](<D:/000/sources/eas/000_Redis/003_为什么使用 Redisson 实现分布式锁.md:98>)

### 4.4 Redisson 提供哪些现成能力

Redisson 提供 `RLock` 锁接口，应用调用它来获取和释放锁。普通 `RLock` 使用 Redis Hash（哈希结构）保存持有者和重入计数，通过 Lua 脚本原子加锁及校验后解锁，不是直接执行前面的字符串锁示例。同一持有者可以重复获取锁，也就是可重入；获取几次，需要对应释放几次。

竞争失败时，Redisson 可以等待解锁通知并重试，应用不必自行实现这套等待机制。不过普通 `RLock` 不保证先到先得。未指定固定租期时，它还提供看门狗，也就是自动续期：3.17.7 默认超时为 30 秒，按约 10 秒的间隔调度续期。显式指定正数租期时不启用这个续期机制。

因此，相比手写锁，我看重的是这些机制已有实现，可以把业务代码集中在“获取成功后执行、结束后释放”的流程上。选用 Redisson 并不代表没有接入成本，还要维护客户端依赖、连接配置、等待时间、租期和异常处理。[Redisson 的收益与代价（第 118 行）](<D:/000/sources/eas/000_Redis/003_为什么使用 Redisson 实现分布式锁.md:118>)

### 4.5 选择 Redisson 不等于消除失锁风险

例如 A 获取锁后长时间暂停，锁过期，B 获取同一把锁并开始业务；A 恢复后仍可能继续写入，这时两者可能同时处理同一资源。安全解锁只防止 A 删除 B 的锁，不会停止 A 的业务。看门狗也可能因长时间暂停或网络故障续期失败；主节点上的锁记录尚未复制到副本就故障时，副本接管后也可能允许其他请求加锁。

所以，还要按业务约束保护写入。例如，数据库条件更新只允许版本仍与读取时一致的数据被修改；版本已变化，就拒绝旧写入。Redisson 负责锁协调，业务写入校验负责拒绝不合法的数据操作，不能把用了锁当成数据绝对安全的证明。[选型条件与安全边界（第 128 行）](<D:/000/sources/eas/000_Redis/003_为什么使用 Redisson 实现分布式锁.md:128>)

## 5 详细方案

### 5.1 手写字符串锁：原子加锁与过期设置

锁键要与受保护的资源对应。例如，订单处理示例可以使用 `lock:order:1001`；竞争同一订单的所有进程必须使用相同键，并访问同一套 Redis。每次独立获取锁生成新的随机 value，例如 UUID，避免把固定值或仅线程 ID 当作跨进程、跨次获取都唯一的持有者标识。

```text
SET lock:order:1001 <本次生成的唯一value> NX PX 30000
```

`NX` 表示键不存在时才设置，`PX` 表示过期时间单位为毫秒。这里的 `30000` 毫秒是演示用的 30 秒租期，沿用 Redis 官方锁示例的量级，不是项目确认值，也不证明能覆盖实际业务耗时。`EX 30` 使用秒作为单位，表达同样的示例租期。

Redis 6.2.14 在同一条 `SET` 命令中判断键是否存在、写入值并设置过期时间，其他客户端命令不会插入这些步骤之间；这不等于故障切换后该写入绝不丢失。分开的 `SETNX` 与 `EXPIRE` 即使放进流水线，也不具备同样的原子性。

调用方只在收到 `OK` 时执行业务。键已存在时表示竞争失败；连接断开或请求超时可能意味着命令未执行，也可能意味着执行成功但响应丢失，不能按“已拿到锁”继续业务，更不能直接删除该键。原请求结果未知时，可依赖租期兜底，并结合业务结果核查决定是否重试。

固定租期需要根据临界区执行耗时、暂停时间和网络延迟的测量结果留出余量；本文没有实际测量数据，因此项目租期仍待确认。这个简单字符串锁不提供重入能力：同一线程再次执行 `SET NX` 也会因键已存在而失败。

依据：[Redis 6.2.14 的 SET 源码](https://github.com/redis/redis/blob/6.2.14/src/t_string.c) 中的 `setGenericCommand`，以及 [Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 的单实例实现。官方当前页面还介绍了较新版本的命令，本文仅采用 Redis 6.2.14 支持的 `SET` 和 Lua 方案。

### 5.2 手写字符串锁：原子校验后释放

以下脚本由 Redis 执行，`KEYS[1]` 为锁键，`ARGV[1]` 为本次加锁时写入的 value：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

返回 `1` 表示删除了本次持有的锁，`0` 表示锁已不存在或不属于当前请求。客户端应将比较和删除作为同一次脚本调用发送，不能拆成客户端侧两次命令。

例如，A 的锁过期后，B 使用新的 value 获取同一个键。A 恢复执行时直接 `DEL` 会删掉 B 的锁；即使先 `GET` 看到了自己加锁时写入的 value，也可能在 `GET` 与 `DEL` 之间发生过期和重新加锁。Lua 让校验与删除一起执行，避免这一竞态。

释放调用应在业务代码的 `finally` 中执行，但仅限已经明确获取成功的请求。释放失败不能被当作释放成功；业务是否成功和锁是否释放是两个结果，实际实现应保留业务异常及释放异常，不能因解锁失败就盲目重复业务。此脚本只适用于上面的字符串锁，不能直接操作 Redisson 使用的锁数据。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 中对唯一值及 Lua 解锁的说明。

### 5.3 选择 Redisson 的理由与代价

Java 本地线程锁的协调范围在同一进程内；部署多个应用实例时，若要协调同一资源，需要共同的协调机制。手写 Redis 锁与 Redisson 都通过 Redis 协调不同进程对资源的访问，都必须考虑持有者、有效期和失锁后的业务保护。比较的重点是锁机制由谁实现和维护。

**手写字符串锁：** 应用使用 `SET NX PX` 和 Lua 释放脚本实现基础互斥。上面的简单实现不提供重入；若业务还需要等待重试和续期，需要另外实现对应机制，并验证异常和并发边界。

**Redisson：** 应用使用现成的 `RLock` 接口。3.17.7 普通锁用客户端标识和线程 ID 标识持有者，在 Hash 中记录重入计数，由 Lua 原子处理获取、续期和释放；它还实现了解锁通知订阅和等待重试。收益是减少应用自行实现这些通用机制的工作，而不是免除业务验证。代价是增加客户端依赖、配置和版本维护，并需要理解等待、固定租期与看门狗的差异。

具体参数及内部处理见 [看门狗与等待机制（第 132 行）](<D:/000/sources/eas/000_Redis/004_Java 中如何使用 Redisson 实现分布式锁.md:132>)。依据：[RedissonLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonLock.java)、[RedissonBaseLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonBaseLock.java)、[Config 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/config/Config.java)。

### 5.4 选型成立的条件和安全边界

选择 Redisson 的前提是业务需要基于 Redis 协调多个进程，并愿意承担客户端接入和维护成本。它提供的续期可以降低固定过期时间到期而失锁的风险，但不能保证续期永不失败，也不能终止失去锁的旧请求。

原子解锁只保护锁键，不能阻止旧请求修改数据库。严格的数据约束仍需写入端校验；条件更新、唯一约束和 fencing token 各有用途，完整解释见 [失锁后的写入保护（第 144 行）](<D:/000/sources/eas/000_Redis/004_Java 中如何使用 Redisson 实现分布式锁.md:144>)。Redis 异步复制下的故障切换也可能丢失锁记录，因此部署拓扑和故障行为必须验证。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。本项目的版本基线已确认，但实际部署、依赖兼容性和故障行为尚未验证。
