A 拿锁后停顿，锁过期时 B 拿到了同一把锁。假如 A 恢复后直接删除锁键，C 就可能拿到锁，与 B 同时执行业务。先读再删也有同样的时间窗口。所以解锁时让 Redis 执行一段 Lua 脚本，把锁值与自己加锁时写入的唯一值一起比较，匹配时才删除。明确拿过锁的请求在 `finally` 中尝试释放。这个检查能避免误删锁，旧请求的业务写入仍需另行保护。[详细说明（第 28 行）](<D:/000/sources/eas/000_Redis/005_手写Redis锁如何安全解锁.md:28>)

## 5 详细方案

### 5.1 旧持有者误删新锁的后果

以下脚本由 Redis 执行，`KEYS[1]` 为锁键，`ARGV[1]` 为本次加锁时写入的 value：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

返回 `1` 表示删除了本次持有的锁，`0` 表示锁已不存在或不属于当前请求。客户端应将比较和删除作为同一次脚本调用发送，不能拆成客户端侧两次命令。

例如，A 的锁过期后，B 使用新的 value 获取同一个键。A 恢复执行时直接 `DEL` 会删掉 B 的锁；即使先 `GET` 看到了自己加锁时写入的 value，也可能在 `GET` 与 `DEL` 之间发生过期和重新加锁。Lua 让校验与删除一起执行，避免这一竞态。

释放调用应在业务代码的 `finally` 中执行，但仅限已经明确获取成功的请求。释放失败不能被当作释放成功；业务是否成功和锁是否释放是两个结果，实际实现应保留业务异常及释放异常，不能因解锁失败就盲目重复业务。此脚本只适用于使用唯一值的字符串锁，不能直接操作 Redisson 使用的锁数据。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 中对唯一值及 Lua 解锁的说明。
