**先说明原则：** 我会按业务资源设置锁键，例如同一订单共用一把锁；加锁与过期设置要原子完成，释放时只删除自己的锁。在同一个 Redis 实例上竞争锁时，可以使用 `SET key value NX EX seconds`：`NX` 表示只有键不存在时才设置，`EX` 设置以秒为单位的过期时间，这两个动作由一次命令完成。`value` 要使用每次请求都不同的唯一值，例如 UUID（随机生成的唯一标识），不能只写固定字符串。[加锁原理](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:31)

**释放锁：** 释放时不能直接 `DEL key`，因为当前线程可能已经执行超时，锁过期后被其他线程重新获得，直接删除就会误删其他线程的锁。因此要用 Lua 脚本先比较 `value`，只有值仍然属于自己时才删除，而且比较和删除要在同一个脚本中完成。[安全释放](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:41)

**执行时间较长时：** 固定过期时间只能覆盖预估的执行时长，不能保证业务执行期间锁一直有效。生产环境可以使用 Redisson 的 `RLock`，它支持同一线程重复获取同一把锁，也支持等待解锁通知后重试；获取锁时设置有限等待时间，超时未获得锁就不执行业务；不传固定 `leaseTime`（租约时长）时由看门狗定期续期，业务完成后再由持锁线程 `unlock`。如果进程宕机，看门狗停止，锁会在租约到期后释放。普通锁不保证先到先得；固定租约则不自动续期。[Redisson 用法](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:52)

**锁失效的边界：** 网络中断或 JVM 长时间暂停仍可能让续期失败，锁过期不会停止旧线程的业务；采用异步主从复制时，故障切换也可能丢失尚未复制的锁记录。因此还要用数据库条件更新、唯一约束等保护最终写入，不能只靠锁保证业务正确。当前版本选型已确认，但项目运行效果尚未验证。[失效边界](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:106)

## 4 详细方案

### 4.1 直接使用 Redis 命令加锁

```text
SET lock:order:{orderId} {requestId} NX EX 30
```

`lock:order:{orderId}` 是按业务资源划分的锁键；`{requestId}` 是本次加锁请求生成的唯一值；`30` 是示例租约秒数，不是当前项目确认的配置值。只有返回 `OK` 才表示获得锁，返回空值表示未获得锁。

`SETNX` 与 `EXPIRE` 分成两条命令时，进程可能在两条命令之间崩溃，留下没有过期时间的键。使用带 `NX` 和 `EX` 的一次 `SET`，可以避免这个间隙。过期时间仍然是兜底机制，不能替代释放时的所有权校验。

### 4.2 使用 Lua 脚本安全释放

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

调用脚本时传入锁键和本次请求的 `requestId`。脚本返回 `1` 表示删除了自己持有的锁，返回 `0` 表示键不存在或值已经不是自己的值。比较和删除必须放在同一个脚本中，避免比较完成后锁状态被其他请求改变。

### 4.3 Redisson 实现

当前项目已确认使用 `org.redisson:redisson-spring-boot-starter:3.17.7`。典型调用方式如下，代码是说明用示例，不代表项目中已经存在这段实现：

```java
import java.util.concurrent.TimeUnit;
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;

public final class ResourceLockExecutor {
    private final RedissonClient redissonClient;

    // 由调用方传入 Starter 自动配置的客户端。
    public ResourceLockExecutor(RedissonClient redissonClient) {
        this.redissonClient = redissonClient;
    }

    public boolean execute(String resourceId, Runnable action)
            throws InterruptedException {
        RLock lock = redissonClient.getLock("lock:example:" + resourceId);
        // 3 秒是竞争锁的示例等待时间；不传固定租约，使用看门狗。
        if (!lock.tryLock(3, TimeUnit.SECONDS)) {
            return false; // 未获取锁，不执行业务，由调用方决定重试或拒绝。
        }
        Throwable failure = null;
        try {
            // 必须同步执行；数据库事务应在 action 返回前完成提交。
            action.run();
            return true;
        } catch (RuntimeException | Error e) {
            failure = e;
            throw e;
        } finally {
            try {
                // unlock 本身原子校验所有权；失锁时异常不能当作成功忽略。
                lock.unlock();
            } catch (RuntimeException unlockFailure) {
                if (failure != null) {
                    failure.addSuppressed(unlockFailure);
                } else {
                    throw unlockFailure;
                }
            }
        }
    }
}
```

Redisson 的锁记录线程所有权和重入次数，解锁时会校验当前线程是否持有该锁。`tryLock(waitTime, unit)` 首次竞争失败后在等待预算内重试；网络命令超时也可能影响实际耗时；等待时间不是锁租约时间。未指定固定 `leaseTime` 时，Redisson 3.17.7 会使用看门狗续期；指定正数 `leaseTime` 后，锁按该租约到期，不会启用这条自动续期路径。等待锁时使用发布订阅通知配合剩余租约等待和重试，普通 `RLock` 不保证公平性，不能把它笼统描述成按到达顺序排队。

示例将 `InterruptedException` 交给调用方处理；调用方如捕获而不继续抛出，应恢复中断标记并终止当前尝试。业务异常与解锁异常同时发生时，保留业务异常并附加解锁异常。解锁异常可能发生在业务已提交之后，重试前仍需核对结果并确保幂等。不要在另一个线程执行 `action` 后提前返回，也不要让外层事务在解锁之后才提交。示例等待时间不是项目参数；实际等待时间和 Redis 连接参数待业务接入时确认。

Redisson 底层使用 Hash 保存客户端标识、线程标识和重入计数，通过 Lua 完成加锁、续期和解锁；前面的字符串 `SET` 示例仅用于说明基本原理，不是 Redisson 内部实现。重复获取的次数必须对应释放。以上锁机制已核对第 4.5 节链接的 3.17.7 源码，示例尚未编译或运行。

### 4.4 必须说明的边界

- 锁键应对应实际竞争资源，例如订单号或用户号；锁粒度过大降低并发，过小可能无法保护完整业务操作。
- 加锁成功后，业务执行时间超过固定租约，锁可能在业务结束前过期；其他线程随后可能获得同一把锁。应根据业务耗时评估租约；即便启用看门狗，网络故障或 JVM 长暂停也可能让锁过期。安全解锁只能防止误删新锁，不能阻止旧线程继续写数据。
- 如果部署采用异步主从复制，主节点可能在锁记录复制前故障，提升后的从节点没有该锁，另一请求便可能再次加锁。这是条件性故障场景，本文不据此断言项目采用了主从部署。
- 最终写入应结合业务条件更新、唯一约束、事务和幂等设计；幂等只能限制重复效果，不能自动拒绝旧持锁者的过时写入。更严格的场景可采用 fencing token（每次授权递增的隔离令牌），由被保护资源原子拒绝较旧令牌；随机 UUID 不能替代递增令牌，普通 `RLock` 也不会自动提供这项业务保护。具体方案仍须结合业务确认。
- Redis 服务端 6.2.14、Redisson 3.17.7 与项目依赖的实际连接和加解锁行为尚未验证，不能把版本基线写成运行结果。

以上故障切换与租约限制参见已核对的 [Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。
