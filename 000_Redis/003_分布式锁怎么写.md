## 4 面试口述版本

分布式锁用于协调多个进程对同一资源的并发操作。基于 Redis 实现时，我会围绕原子加锁、安全释放和过期处理来设计；Java 中可以直接使用 Redisson 提供的分布式锁，但仍要处理锁失效后旧请求继续执行的问题。

### 4.1 原子加锁

原子加锁是实现分布式锁的关键步骤。多个应用实例同时处理同一个订单时，都访问同一套 Redis，尝试创建同一个锁键。谁先成功创建这个键，谁就获得锁；在键未被释放或过期期间，其他请求无法通过同样的命令获得锁。只有获得锁的请求才进入受保护的业务，这样才能协调不同进程对同一资源的并发操作。

Redis 的通用写入格式是 `SET key value`。在锁场景中，`key` 是锁的名称，`value` 是锁键保存的值，用来标识本次锁的持有者。每次获取锁都应生成新的唯一值，例如 UUID；不能让所有请求都写固定值 `1`，否则无法区分不同持有者。释放时，要原子比较 Redis 保存的值是否与自己获取锁时写入的值一致，一致才删除。

加锁使用 `SET key value NX PX ttl`。`SET` 是写入字符串值的命令。`NX` 通常理解为 Not eXists，意思是“键不存在”，表示只有键不存在时才写入；键已经存在，就不修改。`PX` 是按毫秒设置过期时长的选项，`ttl` 是具体时长，必须是正整数。`EX` 则按秒设置过期时长，可以用 EXpire（过期）帮助记忆。`PX` 可以联想 Precise（精细的）＋ eXpire（过期），但这只是助记法，不是已核实的官方英文全称。

例如，`SET lock:order:1001 request-a-unique-value NX PX 30000`，表示订单 `1001` 的锁不存在时，创建这个锁，把本次持有者标识写入 value，并设置 30000 毫秒，也就是 30 秒后过期。这里的持有者标识和 30 秒都是示例；实际每次生成新的唯一值，过期时长要根据业务耗时确定，不能直接照搬 30 秒。设置过期时间是为了让持有者崩溃后，锁不会永久占用。

收到 `OK` 表示命令执行时成功获得锁，才能继续业务；返回空值表示锁键已存在，本次没有获得锁，也不会刷新原锁的过期时间。如果请求超时或连接异常，可能是命令没有执行，也可能是执行成功但响应丢失，不能据此认定获得了锁。

这条命令把“判断键不存在、写入值、设置过期时间”一起原子执行，也就是其他客户端命令不能插入这些步骤之间。不能分开执行 `SETNX`（键不存在时写入）和 `EXPIRE`（设置过期时间），否则两条命令之间进程崩溃，可能留下没有过期时间的锁。锁到期只会使键失效，不会停止正在执行的业务线程。[原子加锁（第 52 行）](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:52)

### 4.2 安全释放

业务结束后在 `finally` 中释放锁。释放时用 Lua 脚本原子比较锁键保存的 value 与自己加锁时写入的值，一致才删除，不能直接 `DEL`，也不能先 `GET` 再 `DEL`。因为旧请求的锁可能已经过期、新请求又拿到了锁，旧请求恢复后只能释放自己的锁，不能删掉新请求的锁。[安全释放（第 70 行）](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:70)

### 4.3 Redisson 的使用与续期

前两节说明的是手写字符串锁的做法。Redisson 已提供分布式锁实现，业务代码可以调用 `RLock.tryLock` 获取锁，成功后执行同步业务，再由持锁线程在 `finally` 中解锁。等待时间决定愿意等多久，租期决定锁多久后过期。未指定固定租期时可启用看门狗自动续期；3.17.7 的默认超时是 30 秒，按约 10 秒的间隔调度续期，但不保证每次都及时成功。显式指定正数租期时不启用该续期机制。普通 `RLock` 支持等待重试，不保证先到先得。[Redisson 实现（第 90 行）](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:90)

### 4.4 锁失效后的边界

过期只能让锁重新可用，不会停止旧线程。长时间暂停或网络故障可能使续期失败，旧线程恢复后仍可能与新持有者同时修改数据；Redis 异步复制下的故障切换也不能简单视为锁绝不丢失。严格要求数据正确时，还需要数据库条件更新、唯一约束或由存储端校验的递增令牌等保护，具体取决于要防止哪种错误。[失效边界（第 153 行）](D:/000/sources/eas/000_Redis/003_分布式锁怎么写.md:153)

## 5 详细方案

### 5.1 原子加锁：锁键、持有者和过期时间

锁键要与受保护的资源对应。例如，订单处理示例可以使用 `lock:order:1001`；竞争同一订单的所有进程必须使用相同键，并访问同一套 Redis。每次独立获取锁生成新的随机 value，例如 UUID，避免把固定值或仅线程 ID 当作跨进程、跨次获取都唯一的持有者标识。

```text
SET lock:order:1001 <本次生成的唯一value> NX PX 30000
```

`NX` 表示键不存在时才设置，`PX` 表示过期时间单位为毫秒。这里的 `30000` 毫秒是演示用的 30 秒租期，沿用 Redis 官方锁示例的量级，不是项目确认值，也不证明能覆盖实际业务耗时。`EX 30` 使用秒作为单位，表达同样的示例租期。

Redis 6.2.14 在同一条 `SET` 命令中判断键是否存在、写入值并设置过期时间，其他客户端命令不会插入这些步骤之间；这不等于故障切换后该写入绝不丢失。分开的 `SETNX` 与 `EXPIRE` 即使放进流水线，也不具备同样的原子性。

调用方只在收到 `OK` 时执行业务。键已存在时表示竞争失败；连接断开或请求超时可能意味着命令未执行，也可能意味着执行成功但响应丢失，不能按“已拿到锁”继续业务，更不能直接删除该键。原请求结果未知时，可依赖租期兜底，并结合业务结果核查决定是否重试。

固定租期需要根据临界区执行耗时、暂停时间和网络延迟的测量结果留出余量；本文没有实际测量数据，因此项目租期仍待确认。这个简单字符串锁不提供重入能力：同一线程再次执行 `SET NX` 也会因键已存在而失败。

依据：[Redis 6.2.14 的 SET 源码](https://github.com/redis/redis/blob/6.2.14/src/t_string.c) 中的 `setGenericCommand`，以及 [Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 的单实例实现。官方当前页面还介绍了较新版本的命令，本文仅采用 Redis 6.2.14 支持的 `SET` 和 Lua 方案。

### 5.2 安全释放：原子校验持有者后删除

以下脚本由 Redis 执行，`KEYS[1]` 为锁键，`ARGV[1]` 为本次加锁时写入的 value：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

返回 `1` 表示删除了本次持有的锁，`0` 表示锁已不存在或不属于当前请求。客户端应将比较和删除作为同一次脚本调用发送，不能拆成客户端侧两次命令。

例如，A 的锁过期后，B 使用新的 value 获取同一个键。A 恢复执行时直接 `DEL` 会删掉 B 的锁；即使先 `GET` 看到了自己加锁时写入的 value，也可能在 `GET` 与 `DEL` 之间发生过期和重新加锁。Lua 让校验与删除一起执行，避免这一竞态。

释放调用应在业务代码的 `finally` 中执行，但仅限已经明确获取成功的请求。释放失败不能被当作释放成功；业务是否成功和锁是否释放是两个结果，实际实现应保留业务异常及释放异常，不能因解锁失败就盲目重复业务。此脚本只适用于上面的字符串锁，不能直接操作 Redisson 使用的锁数据。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 中对唯一值及 Lua 解锁的说明。

### 5.3 Redisson：获取、执行业务与释放

#### 5.3.1 核心 Java 示例

当前版本使用 `redisson-spring-boot-starter` 3.17.7，通过 Spring Boot 的 `spring.redis.*` 配置连接，业务类注入自动配置的 `RedissonClient`。下面是教学示例，展示同步调用的锁边界，不代表项目已经实现或运行验证。`Runnable` 中的业务必须在当前线程完成，不能只提交异步任务后立即返回，否则会在任务结束前释放锁。若保护数据库事务，应让事务在 `action.run()` 返回前完成提交或回滚；锁的外层存在尚未结束的事务时，可能出现先解锁、后提交的问题。

```java
import java.util.concurrent.TimeUnit;
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;

public final class LockedExecutor {
    private final RedissonClient redissonClient;

    public LockedExecutor(RedissonClient redissonClient) {
        this.redissonClient = redissonClient;
    }

    public boolean execute(String resourceId, Runnable action)
            throws InterruptedException {
        RLock lock = redissonClient.getLock("lock:demo:" + resourceId);
        // 示例：竞争锁的等待预算为 3 秒；不指定固定租期，使用看门狗续期。
        if (!lock.tryLock(3, TimeUnit.SECONDS)) {
            return false; // 未确认获取成功，不执行 action。
        }
        Throwable failure = null;
        try {
            action.run(); // 业务需自行实现数据库条件校验等必要保护。
            return true;
        } catch (RuntimeException | Error ex) {
            failure = ex;
            throw ex;
        } finally {
            try {
                lock.unlock(); // 必须由当前持锁线程释放。
            } catch (RuntimeException | Error unlockFailure) {
                if (failure != null) {
                    failure.addSuppressed(unlockFailure);
                } else {
                    throw unlockFailure;
                }
            }
        }
    }
}
```

竞争锁的等待预算 `3` 秒仅为演示可中断的有限等待，依据是展示“成功、竞争失败、异常”三个分支，不是生产建议值；实际应结合接口超时预算和锁竞争情况确认。该参数不是整个调用的严格耗时上限，Redis 命令执行、网络超时及重试还受客户端配置影响。`InterruptedException` 向调用方传播，由上层决定取消策略；如果上层捕获但不继续抛出，应恢复线程中断标记。加锁命令异常可能向上抛出；3.17.7 的订阅等待分支还会将部分异常处理为获取失败。因此，只有 `tryLock` 明确返回 `true` 才执行业务，不能把返回 `false` 一律解释为其他线程正常持锁。

示例没有先调用 `isLocked()`：键存在不能证明当前线程持有锁。`isHeldByCurrentThread()` 也只是一次检查，检查后仍可能过期，不能替代解锁脚本的原子校验。直接调用 `unlock()` 时，Redisson 会检查持有者；若已失去锁，会报告 `IllegalMonitorStateException`。示例保留这类失败，不能因为 `action.run()` 返回就把整个操作报告为正常完成。

#### 5.3.2 看门狗、重入与等待机制

Redisson 3.17.7 的普通 `RLock` 使用 Redis Hash 保存客户端标识与线程 ID 对应的重入计数。Lua 原子判断持有者并更新计数和过期时间；同一持有者可重入，获取几次就需要对应释放几次，计数归零后才删除锁并发布通知。

`tryLock(waitTime, unit)` 未提供固定租期，获取成功后会安排看门狗续期。`lockWatchdogTimeout` 默认是 `30000` 毫秒，即 30 秒；源码按内部租期的三分之一安排续期任务，默认约 10 秒调度一次。续期脚本确认持有者仍存在后，将过期时间重新设置为租期长度，并继续安排下一次任务。调度延迟和通信失败都可能使续期赶不上过期，不能承诺“业务没结束，锁就绝不会过期”。

使用 `tryLock(waitTime, leaseTime, unit)` 并指定正数 `leaseTime` 时，租期到期后锁会失效，不启用上述看门狗续期。因此不能把固定租期与自动续期当成默认同时存在的保障。续期可以降低业务执行期间因固定过期时间到期而失锁的风险，但如果业务线程一直卡住而客户端仍能续期，也可能长期占用锁，仍需业务超时和取消机制配合。

普通 `RLock` 在竞争失败后可订阅解锁消息，并结合剩余等待时间、锁的剩余存活时间等待和重试；通知到达不等于已获得锁，还要重新竞争。它不是公平锁，不保证请求按到达顺序获得锁。不能把原材料的“等待队列”概括理解为普通锁具备先到先得的保证。

依据：[RedissonLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonLock.java) 的获取、订阅和解锁实现；[RedissonBaseLock 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/RedissonBaseLock.java) 的续期调度及解锁异常；[Config 3.17.7](https://github.com/redisson/redisson/blob/redisson-3.17.7/redisson/src/main/java/org/redisson/config/Config.java) 的默认超时及适用条件。

### 5.4 锁失效后，业务仍需保护

租期只控制 Redis 键的有效时间，不控制业务线程或数据库请求是否停止。例如 A 因长时间暂停而丢失锁，B 随后获得锁并写入新结果；A 恢复后仍可能用旧状态覆盖 B 的结果。安全解锁只防止 A 删掉 B 的锁，不会阻止 A 执行已经发出的业务写入。

Redis 官方说明给出的另一类风险是异步复制：主节点确认加锁后，锁数据尚未复制就故障，副本提升后可能接受第二次加锁。不能仅凭存在副本、启用了 Redisson 或配置了续期，就宣称任何故障下均具备严格互斥；具体拓扑、复制确认和故障行为需要另外核验。

保护方式取决于业务约束。数据库条件更新可以要求“状态仍为预期值或版本未变化”才允许写入，并检查影响行数；唯一约束可阻止同一业务标识的重复记录，但不会阻止任意旧值覆盖。若需要拒绝失去锁的旧持有者，可采用 fencing token：每次获取锁取得可靠的单调递增令牌，由受保护的存储系统原子拒绝比已接受令牌更旧的写入；仅生成令牌而不在写入端校验没有作用。这些是通用设计选项，不代表本项目全部采用。

依据：[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) 关于异步复制、锁有效期与 fencing token 的说明。
