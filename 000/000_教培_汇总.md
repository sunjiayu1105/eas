# 一、监管账户白名单-新增
## 1.1 功能描述
只有在白名单中的监管账户，才可以去执行资金划拨操作。

核心需要同步新增白名单账户。资金划拨时，核心会去校验监管账户是否由 E 账通渠道维护：

1. 如果是 E 账通渠道维护的监管账户，才允许交易。
2. 如果不在白名单中，则不允许执行资金划拨。

### 核心新增白名单后的处理结果
1. 核心新增成功
    - 本地表新增记录。
2. 核心新增失败
    - 本地表不新增记录。
    - 流水表操作状态为失败。
    - 返回新增失败。
3. 核心新增异常
    - 本地表不新增记录。
    - 流水表操作状态为异常。
    - 返回新增异常。
    - 如果实际结果是核心新增失败，不影响下次业务再次新增。
    - 如果实际结果是核心新增成功，下次调用核心新增接口时，会返回白名单已新增，EAS 在本地新增记录即可。

## 1.2 账户状态
监管账户白名单账户状态包括：

1. 正常
    - 如果需要签约动账通知，则只有满足“核心新增成功 + 本地新增成功 + 签约动账通知成功”后，账户状态才是正常。
2. 失效
3. 签约失败
    - 核心新增成功，但签约核心动账通知失败。

# 九、资金划拨
## 9.1 功能描述
将资金从教育机构的监管账户划拨到教育机构的对公户。

## 9.2 监管账户 vs 对公户
### 9.2.1 监管账户
1. 收取客户的课程费用。
2. 收款账号需要被监管。
3. 客户支付的课程费用先进入监管账户。
4. 教育机构不能直接从监管账户中取款。
5. 只有客户完成消课等业务条件后，资金才会从监管账户划拨到教育机构对公户。

### 9.2.2 对公户
1. 资金从监管账户划拨到对公户后，钱才真正到达教育机构。
2. 监管账户一般是本行账户。
3. 教育机构对公户可以是任意银行账户。

2. 如果交易结果为终态，则更新 `SF_DXPAYMENT_FLOW` 的交易状态。
3. 如果上一步查询结果非终态，则调用统一支付的交易结果回查接口。

# 十一、批量资金划拨
## 11.1 功能描述
有的商户需要 EAS 支持批量资金划拨操作。

对于批量操作，一般处理方式是：

1. 先把数据记录下来。
2. 后面再异步处理。
3. 异步通知商户交易结果。

## 11.2 表设计
包括：

1. 主订单表
2. 子订单表

## 11.3 技术方案
1. 先将请求参数存入主订单表、子订单表中。
2. 异步执行批量资金划拨。
3. 根据主订单表 ID 查询所有子订单。
4. 对每个子订单执行资金划拨操作。
5. 异步通知商户交易结果。

### 11.3.1 通知规则
1. 如果交易结果为终态，通知商户。
2. 如果交易结果非终态，不通知商户。
3. 对于交易异常的数据，会有异常回查批次。
4. 异常数据回查后，如果结果为终态，再通知商户。

# 十三、解析并处理核心下发的结息动账通知文件
## 13.1 功能描述
核心会定期给监管账户进行利息结算。

处理背景：

1. 利息会转入监管账户。
2. 教育机构不能直接从监管账户中取款。
3. 必须先从监管账户转账到教育机构对公户。
4. 教育机构才能从对公户中取款。

因此，需要定时处理核心下发的结息动账通知文件，将利息从监管账户转账到对公户。

## 13.2 文件下发规则
1. 核心每天都会下发结息动账通知文件。
2. 不是所有账户都会收到结息动账通知文件。
3. 只有在调用核心新增监管账户白名单时，入参指定需要结息通知，核心才会推送该监管账户的结息动账通知文件。
4. 核心的“结息动账通知文件”和普通“动账通知文件”是分开的。
5. 推送结息动账通知文件，不需要签约核心动账通知。

## 13.3 代码清单
`eAccountManage | coreYxpEduAccountInterestNotice`

含义：核心银校培教育专户结息动账通知。

## 13.4 技术方案
### 13.4.1 处理步骤
1. 解析核心推送过来的结息动账通知文件。
2. 将解析数据写入表中。
3. 如果解析过程出错，后续需要再次解析。
4. 如果直接把数据写入业务表，会导致重复写入。
5. 解决方案：创建一张临时表，先把每个文件中的数据写入临时表。

### 13.4.2 批量处理方式
不是每解析一条数据就写表、执行转账操作，而是批量读取表中的数据来转账。

批量处理逻辑：

1. 每次处理所有待处理 / 异常的数据，而不是指定条数。
2. 先查询待处理 / 处理异常的记录总数。
3. 每次处理 5000 条数据。
4. 根据总数计算需要循环处理的次数。
5. 循环处理待处理数据。
6. 调用资金划拨接口执行转账操作。
7. 根据转账结果更新结息记录处理状态。

### 13.4.3 批次执行频率
1. 每天执行一次。
2. 每次处理所有待解析 / 解析异常的文件。

### 13.6.1 为什么会存在文件已经处理成功，但是还是再次扫出文件的情况？
可能原因是文件移除失败。

因为文件移除结果和文件解析结果是分开的：

1. 先更新文件解析成功。
2. 后面再移除文件。
3. 后面可能移除文件失败。

### 13.6.2 处理结息记录时，为什么要先计算循环次数？而不是每次都查询 5000 条记录，只要还有待处理 / 处理异常的记录，就一直循环？
原因是避免无限循环和任务阻塞。

如果资金划拨接口一直有问题，那么上一轮结息记录处理结果都是异常，就会一直循环。

如果系统中的批次都是这个处理逻辑，那就会导致机器资源不够用，最后整个服务器挂掉，影响该机器上所有功能。

# 十四、根据退票文件通知商户交易结果
## 14.1 功能描述
场景：将监管账户中的资金划拨到教育机构对公户时，如果对公户是他行账户，可能出现资金已经转到对方银行，但入账客户账号失败的情况。

此时：

1. 本地资金划拨交易结果可能是成功。
2. 对于这种交易，对方银行会退票 / 退款。
3. 统一支付会处理退票记录。
4. 统一支付通过退票文件推送给 E 账通。
5. 如果退票文件中包含监管账户相关记录，则需要更新对应的资金划拨交易结果为失败。
6. 同时将交易结果通知给商户。

## 14.2 代码清单
文档仅列出标题，未展开具体代码清单。

## 14.3 技术方案
1. 统一支付推送过来的退票文件包含多种交易，不仅仅是教育监管账户的资金划拨。
2. 解析统一支付推送过来的退票文件，并逐条解析每笔交易。
3. 根据渠道查询出来教育监管账户的退票交易，包括：
    - 待处理交易；
    - 处理异常交易。
4. 根据交易流水更新资金划拨交易结果为失败。
5. 通知商户交易结果为失败。
6. 更新资金划拨交易结果，并通知商户：
    - 如果全程处理成功，则更新退票记录处理状态为成功。
    - 否则更新为处理失败 / 异常。

# 十九、核心业务链路总结
## 1. 白名单管理链路
1. 新增监管账户白名单。
2. 核心同步新增。
3. 本地记录账户信息。
4. 视渠道要求签约动账通知。
5. 账户状态更新为正常、失效或签约失败。
6. 删除时需要同步本地和核心账户状态。
7. 如果签约过动账通知，删除时还应取消动账通知。

## 2. 资金划拨链路
1. 客户资金进入监管账户。
2. 满足业务条件后，教育机构发起资金划拨。
3. EAS 将资金从监管账户划拨到教育机构对公户。
4. 交易结果如果终态，直接通知商户。
5. 交易结果如果异常，则通过异常回查获取最终结果。
6. 如果发生他行入账失败，则通过退票文件修正交易结果并通知商户。

## 3. 结息处理链路
1. 核心定期给监管账户结息。
2. 结息金额进入监管账户。
3. EAS 解析核心下发的结息动账通知文件。
4. 将结息数据入临时表，避免重复写入。
5. 批量处理待处理 / 异常记录。
6. 调用资金划拨接口将利息从监管账户划拨到教育机构对公户。
7. 根据划拨结果更新结息记录状态。

## 4. 交易明细推送链路
1. 维护监管账户白名单时签约核心动账通知。
2. 核心产生出入账动账通知。
3. E 账通订阅并处理消息。
4. 本地记录动账通知数据。
5. 根据动账通知记录生成前一天交易明细。
6. 推送给第三方商户。

## 5. 异常处理链路
1. 资金划拨异常：通过回查接口逐层回查，直到交易结果终态。
2. 通知异常：再次通知商户，超过 5 次不再通知。
3. 退票异常：根据退票文件更新资金划拨结果为失败，并通知商户。
4. 结息文件重复扫描：可能由文件移除失败导致。
5. 结息记录批量处理：需要控制循环次数，防止异常数据导致任务无限循环。
