# E 账通功能介绍梳理
资料来源：《E账通功能介绍_汇总.md》。

## 一、系统定位
E 账通可以理解为银行互联网账户与交易中台，核心围绕电子账户、虚账户、代收代付、消费、基金理财、闪付扫码、保险出单、商户代付、动账通知等业务展开。

从银行系统分工看，E 账通不是最终记账系统，也不是单纯支付通道系统，而是处在渠道、账户、交易、核心账务和外部支付通道之间的业务处理层。

整体定位可以概括为：

```latex
渠道 / 商户 / APP
        ↓
E 账通
        ↓
核心 / 统一支付 / 卡交换 / 直销通 / 银保通
```

E 账通主要承担三类职责：

1. **账户管理**  
负责客户信息、虚账户、电子账户、渠道账户关系、绑卡签约等管理。
2. **交易处理**  
负责代收、代付、消费、基金申购赎回、闪付、扫码付、保险出单等业务交易编排。
3. **账务与异常支撑**  
负责虚账户台账、交易流水、异常回查、冲正、补账、对账、清算、动账通知处理。

## 二、账户体系
### 1. 电子账户
电子账户是客户真实资金的承载账户，一般对应银行核心中的二类户、三类户等账户。

在 E 账通中，客户真正可用余额、出入账、扣款、入账等资金变化，最终都要落到电子账户和核心账务上。

可以理解为：

```latex
电子账户 = 客户真实资金账户
```

### 2. 虚账户
虚账户主要用于区分渠道和业务场景，不一定直接承载真实资金。

每个客户在不同渠道下可以有不同虚账户，用于管理客户在该渠道下的账户关系、交易关系和台账关系。

可以理解为：

```latex
虚账户 = 渠道维度的账户关系 / 台账载体
```

### 3. 虚账户和电子账户的关系
302 号文改版后，账户体系的核心变化是：

```latex
客户维度：电子账户承载真实资金
渠道维度：虚账户区分业务场景
台账维度：部分渠道记录虚账户余额变化
```

也就是说，虚账户不再简单对应一个虚账户内部户，客户资金最终还是映射到客户本人的电子账户。

### 4. 台账
台账用于记录虚账户维度的余额变化，不是所有渠道都记台账。

是否记台账，取决于渠道配置：

```latex
记台账渠道：写 EA_ACCOUNTING_INF
不记台账渠道：不写 EA_ACCOUNTING_INF
```

自营渠道、京东白条等场景可能不记台账，直接展示电子账户余额；人寿电商、合作商户等场景仍可能保留虚账户台账。

## 三、核心账务处理原则
E 账通的账务逻辑必须区分“核心真实账务”和“虚账户台账”。

### 1. 入账原则
电子账户入账一般是：

```latex
先核心入账
再加虚账户台账
```

原因是核心才是银行真实账务系统，只有核心入账成功后，本地台账才有依据增加。

### 2. 出账原则
电子账户出账一般是：

```latex
先扣虚账户台账
再调核心出账
```

如果核心出账失败，需要通过异常任务补回台账。

这个设计是为了避免虚账户可用余额和真实资金状态不一致。

### 3. 多借多贷交易
多借多贷交易一般不记录虚账户台账，主要依赖核心账务分录处理。

### 4. 原子性要求
涉及第三方系统、核心、直销通、统一支付的交易，E 账通通常无法在一个本地事务中保证全链路原子性，所以必须依赖：

```latex
交易流水
状态机
异常回查
冲正补偿
对账清算
```

来保证最终一致性。

## 四、调用核心还是统一支付的判断逻辑
### 1. 核心系统负责什么
核心系统负责银行内部账户的真实账务处理。

只要资金在广发银行内部账户之间流转，通常调用核心。

典型场景：

```latex
电子账户 → 商户过渡户
电子账户 → 本行对公户
本行对公户 → 电子账户
监管账户 → 本行对公户
内部科目户 → 电子账户
```

### 2. 统一支付负责什么
统一支付主要负责外部支付通道能力，例如：

```latex
银联
网联
UPOP
超级网银
大小额
跨行代收
跨行代付
```

只要资金链路涉及他行卡、他行账户、跨行清算或外部支付网络，一般需要统一支付参与。

### 3. 典型判断方式
| 资金链路 | 处理方式 |
| --- | --- |
| 广发电子账户 → 广发对公户 | 核心 |
| 广发电子账户 → 广发内部户 | 核心 |
| 他行绑定卡 → 广发电子账户 | 统一支付代收 + 核心入账 |
| 广发电子账户 → 他行绑定卡 | 核心出账 + 统一支付代付 |
| 广发监管账户 → 他行对公户 | 核心出账 + 统一支付 / 大小额代付 |
| 绑定卡消费 | 通常走统一支付 |
| 电子账户余额消费 | 通常走核心 |


### 4. 不能只看账户归属行
实际判断时，不仅看付款账户和收款账户是否为本行账户，还要看：

```latex
支付方式
交易类型
渠道配置
通道优先级
是否需要跨行清算
是否由统一支付统一承接
```

所以更准确的总结是：

```latex
核心负责本行内部账户账务；
统一支付负责跨行和外部支付通道；
复杂交易通常由核心和统一支付配合完成。
```

## 五、注册开户流程
注册开户是 E 账通最基础的账户能力，涉及客户建档、认证、开虚账户、开电子账户、绑卡签约等步骤。

整体流程可以理解为：

```latex
客户注册
  ↓
公安认证
  ↓
银联 / 核心认证
  ↓
开通虚账户
  ↓
开通电子账户
  ↓
绑定卡签约
  ↓
更新虚账户签约信息
```

### 1. 客户注册
建立客户基础信息，写入客户信息表。

一个客户在一个渠道下通常对应一条客户记录。

### 2. 公安认证
公安认证用于校验客户身份信息。

文档中提到公安认证支持异步处理，但存在认证结果长期有效的问题，后续建议调整为当天有效。

### 3. 验密
如果客户已有自营电子账户，并且设置过密码，其他自营渠道复用该电子账户时，需要验证原电子账户密码。

### 4. 银联认证 / 核心认证
根据银行卡类型、渠道、是否本行卡选择认证方式：

| 卡类型 | 认证方式 |
| --- | --- |
| 本行借记卡 | 核心认证 |
| 他行借记卡 | UPOP 四要素认证 |
| 本行信用卡 | 信用卡核心认证 |
| 非本行信用卡 | UPOP 六要素认证 |


这里的核心问题是认证通道存在较多特例，后续应尽量统一到统一支付或统一认证体系。

### 5. 开通虚账户
虚账户用于建立客户在某渠道下的账户关系。

当前一般不支持一个渠道下开多个虚账户，除非使用子账户体系。

### 6. 一类户认证
一类户认证主要用于三类户开户校验。

认证方式包括：

```latex
人行认证
打款认证
```

文档中提到，人行认证和打款认证耗时较长，影响开户性能，后续可以考虑异步化。

### 7. 开通电子账户
电子账户是真实资金账户。

开户时需要根据公安认证结果判断账户状态：

```latex
公安认证成功：开正常电子账户
公安认证处理中：开冻结 / 暂禁电子账户
公安认证失败：拒绝开户
```

### 8. 绑定卡签约
绑定卡签约用于建立电子账户和银行卡之间的关系。

签约成功后，需要同步核心绑定关系，并更新本地签约信息。

## 六、代收交易
### 1. 代收定义
代收就是帮业务系统从用户账户收钱。

资金方向是：

```latex
用户银行卡 / 绑定卡
        ↓
电子账户 / 商户账户 / 业务收款账户
```

常见场景：

```latex
充值
消费扣款
理财购买
保证金存入
缴费
```

### 2. 代收基本流程
```latex
参数校验
  ↓
账户状态校验
  ↓
签约状态校验
  ↓
代收通道选择
  ↓
核心预处理
  ↓
发起渠道代收
  ↓
代收成功后入账
  ↓
记录流水
  ↓
异常回查
```

### 3. 代收通道选择
代收通道选择通常考虑：

```latex
渠道支持哪些通道
银行卡支持哪些通道
单笔限额
累计限额
手续费
通知优先级
```

主要通道包括：

```latex
中国银联
广州银联
上海银联
本行卡
民生代收
借记转账
UPOP
```

### 4. 代收入账逻辑
代收成功后，资金如何入账取决于渠道和通道。

有些场景直接入本行卡或指定科目，有些场景入电子账户并增加台账，有些场景由统一支付或中间业务负责账务，E 账通只负责流水和状态。

### 5. 代收异常处理
代收异常主要通过自动任务回查。

常见异常包括：

```latex
代收结果处理中
代收成功但入账异常
本地状态和通道状态不一致
对账发现差异
```

处理方式一般是：

```latex
回查通道结果
  ↓
确认代收最终状态
  ↓
成功则补入账
失败则更新失败
异常则继续回查
```

## 七、代付交易
### 1. 代付定义
代付就是帮业务系统把钱付出去。

资金方向是：

```latex
电子账户 / 商户账户 / 业务付款账户
        ↓
用户银行卡 / 他行账户 / 对公账户
```

常见场景：

```latex
提现
退款
资金划拨
商户付款
```

### 2. 代付基本流程
```latex
判断是否 T+1 提现
  ↓
校验签约信息 / 影像信息
  ↓
选择代付通道
  ↓
核心黑名单校验
  ↓
核心出账
  ↓
发起代付
  ↓
失败则冲正出账
  ↓
异常任务回查
```

### 3. 代付通道选择
代付通道选择通常考虑：

```latex
银行卡是否在黑名单
渠道支持哪些通道
超级网银支持哪些银行
当前时间段是否支持
通道优先级
```

### 4. 代付失败处理
代付失败时，必须重点处理资金一致性。

典型逻辑：

```latex
核心已出账
  ↓
代付失败
  ↓
冲正核心出账
  ↓
恢复本地交易状态
```

如果代付结果未知，则进入异常回查。

## 八、代收对账与清算
### 1. 代收对账
不同通道对账方式不同：

| 通道 | 对账方式 |
| --- | --- |
| 中国银联 | 下载银联文件，解析对账文件和差错文件 |
| 广州银联 | 下载对账文件并与本地流水比对 |
| 上海银联 | 通过电子支付通知对账文件处理 |
| 民生代收 | 通过文鼎下载对账文件并对账 |


对账的核心是比较：

```latex
本地流水
通道流水
核心流水
金额
状态
交易日期
渠道流水号
```

### 2. 对账差异
常见差异包括：

```latex
本地成功，通道无记录
本地失败，通道成功
本地处理中，通道成功 / 失败
金额不一致
重复交易
```

文档中提到，“本地成功，银联无”的差异会在 T+2 后进入丢失报表。

### 3. 清算
代收清算和通道相关。

例如：

```latex
广州银联 / 上海银联：银联按商户号直接打款
中国银联：涉及银行大额清算科目、商统打款、内管补平
```

中国银联清算依赖汇总报表，如果汇总数据异常，可能导致清算资金不准确。

## 九、虚账户台账处理
虚账户台账是 E 账通的重要账务辅助能力。

### 1. 台账操作类型
主要包括：

```latex
虚账户加台账
虚账户减台账
虚账户冻结台账
虚账户解冻台账
台账冲正
```

### 2. 核心出入账接口逻辑
文档中提到 EA06228 是核心的虚账户出入账通用能力。

其逻辑可以概括为：

```latex
入账：先核心入账，成功后加台账
出账：先扣台账，再核心出账
出账失败：自动任务补加台账
```

### 3. 幂等风险
文档明确提到 EA_BUSINESS_INF 缺少唯一索引，如果前端没有控制幂等，可能导致重复交易。

从银行交易系统角度看，这里应该增加：

```latex
渠道流水号唯一约束
业务订单号唯一约束
幂等状态判断
重复请求直接返回原结果
```

## 十、APP 内消费交易
APP 内消费是 E 账通重要的联机交易能力。

### 1. 主要交易
```latex
消费
消费撤销
消费退货
批量消费
批量退货
交易回查
```

### 2. 消费主流程
```latex
基础校验
  ↓
账户状态校验
  ↓
商户校验
  ↓
订单号校验
  ↓
限额 / 白名单校验
  ↓
查询交易类型配置
  ↓
查询账务类型配置
  ↓
按支付方式处理资金
  ↓
更新消费明细和订单状态
```

### 3. 支付方式
| 支付方式 | 处理逻辑 |
| --- | --- |
| 余额消费 | 调核心 / 虚账户出账 |
| 基金赎回消费 | 先基金赎回，再余额消费 |
| 商户授信消费 | 先商户授权，再转账 |
| 卡代收消费 | 调统一支付 UPOP 消费 |


### 4. 撤销和退货
撤销一般用于当日交易冲正，退货一般用于交易完成后的退款。

撤销重点校验：

```latex
原交易是否存在
原交易是否成功
是否允许撤销
是否已清算
```

退货重点校验：

```latex
原交易是否存在
退款金额是否超过可退金额
是否支持部分退货
是否已发生过退款
原交易支付方式
```

### 5. 消费清算
APP 内消费清算批次的核心公式是：

```latex
清算金额 = 消费总金额 - 撤销总金额 - 退货总金额
```

清算前需要检查 T-1 日是否存在异常交易，避免异常交易进入清算导致资金不一致。

## 十一、基金申购与赎回
基金业务在文档中分为两套体系：

```latex
虚账户体系
电子账户体系
```

### 1. 基金申购：虚账户体系
核心逻辑：

```latex
校验账户 / 客户 / 公安 / 影像 / 年龄 / 产品
  ↓
判断是否需要基金开户
  ↓
如需代收，先调用资金往来代收
  ↓
如使用抵用券，调用抵用券接口
  ↓
扣虚账户台账
  ↓
调用直销通完成基金申购和电子账户扣款
  ↓
申购失败则冲正台账
```

这里的重点是：基金真实申购由直销通完成，E 账通主要负责编排交易、处理台账、记录流水和异常补偿。

### 2. 基金赎回：虚账户体系
基金赎回分为 T+0 和 T+1。

T+0 赎回：

```latex
调用直销通赎回
  ↓
赎回成功后加虚账户台账
  ↓
如需要提现，调用资金往来提现
```

T+1 赎回：

```latex
联机阶段只做赎回
  ↓
插入预提现表
  ↓
直销通推送赎回入账文件
  ↓
E 账通解析批次文件
  ↓
批量加虚账户台账
  ↓
后续执行 T+1 赎回提现
```

### 3. 基金电子账户体系的问题
文档中提到电子账户体系存在问题：

```latex
没有记录订单信息
缺少异常处理机制
使用抵用券时申购异常可能造成资金损失
```

从系统设计角度看，基金业务后续应统一交易模型，补充订单、流水、异常回查和补偿机制。

## 十二、闪付和扫码付
### 1. 业务场景
闪付、扫码付主要包括：

```latex
京东白条闪付
通用闪付
通用扫码付
自营扫码付
人寿扫码付
```

### 2. 支付方式
常见支付方式包括：

```latex
余额支付
基金消费
卡代收消费
商户授权支付
```

### 3. 异常处理
闪付和扫码付交易链路复杂，涉及核心、银联、商户授权、冲正、额度恢复等流程，所以通常会有：

```latex
子订单异常回查
核心子订单异常回查
总订单异常处理
冲正异常处理
额度恢复任务
```

### 4. 对账和清算
闪付、扫码付批次主要包括：

```latex
核心对账
银联对账
银联差错处理
授权补平清算
商户文件生成
历史数据迁移
```

核心对账关注核心流水和本地流水是否一致；银联对账关注银联交易文件和本地订单是否一致。

## 十三、保险出单
保险业务主要包括：

```latex
保单投保
保单出单
退保记录
```

### 1. 核保流程
```latex
发送核保信息到银保通
  ↓
银保通返回核保结果
  ↓
E 账通记录核保流水
```

### 2. 出单流程
支付方式包括：

```latex
卡代收出单
余额出单
```

卡代收出单比余额出单多一步代收：

```latex
先代收到电子账户
  ↓
再扣减虚账户台账
  ↓
调用保险出单
  ↓
出单失败则冲正虚账户台账
```

### 3. 退保
退保在内管手工处理，E 账通主要记录订单，具体资金操作由保险公司处理。

## 十四、商户代付
商户代付主要面向非 E 账通客户体系，提供代付能力。

### 1. 业务流程
```latex
校验商户
  ↓
判断行内 / 行外
  ↓
行外商户校验付款账号和白名单
  ↓
选择代付通道
  ↓
发起超级网银 / 中国银联代付
  ↓
代付失败冲正出账
```

### 2. 业务边界
文档中明确提到，商户代付后续应逐步上收给统一支付管理，后续新增商户不建议继续在 E 账通维护。

这符合银行系统演进逻辑：支付通道能力应由统一支付集中承接，E 账通更聚焦账户和交易编排。

## 十五、动账通知
### 1. 业务背景
动账通知主要解决：

```latex
电子账户在非 E 账通系统发生交易后，
E 账通无法感知，
导致电子账户余额和虚账户台账不一致的问题。
```

例如，人寿渠道电子账户发生闪付交易，交易直接通过卡交换和核心完成扣款，E 账通本地原本不知道这笔交易。

这时核心通过动账通知告诉 E 账通，E 账通再根据电子账户找到虚账户，并调整虚账户台账。

### 2. 动账通知触发条件
需要满足：

```latex
电子账户已在核心签约动账通知
交易不是 E 账通发起
核心识别到账户发生金融交易
核心发送通知给 E 账通
```

### 3. 核心判断因素
核心主要根据：

```latex
发送渠道
发送系统
核心接口
摘要码
```

判断是否需要通知 E 账通。

如果交易发送渠道是 E 账通自身渠道，核心一般不会再通知 E 账通，避免重复记账。

## 十六、批次、对账、清算的整体逻辑
E 账通大量业务都依赖批次任务保证最终一致性。

### 1. 批次任务的主要类型
```latex
异常回查批次
对账文件解析批次
商户文件生成批次
清算批次
补账 / 冲正批次
历史数据迁移批次
通知重试批次
```

### 2. 异常回查
异常回查用于处理联机交易中状态不明确的问题。

典型状态：

```latex
成功
失败
处理中
异常
超时
```

处理逻辑：

```latex
查询本地订单
  ↓
查询子流水
  ↓
回查核心 / 统一支付 / 直销通
  ↓
根据最终结果修正本地状态
  ↓
必要时冲正、补账、恢复额度、通知商户
```

### 3. 对账
对账用于发现本地系统和外部系统之间的数据差异。

对账对象包括：

```latex
核心
银联
统一支付
商户
直销通
```

对账发现差异后，需要进入差错处理、补账或人工处理流程。

### 4. 清算
清算用于把交易资金在银行、商户、通道之间进行最终结算。

清算前必须确保交易状态可靠，尤其是消费、撤销、退货、代收、代付等交易不能有未决异常。

## 十七、文档中反映出的主要问题
### 1. 幂等控制不足
文档中提到 EA_BUSINESS_INF 缺少唯一索引，如果前端没有控制幂等，可能导致重复请求。

从银行交易系统角度看，应增加：

```latex
渠道流水号唯一校验
业务订单号唯一校验
交易处理中拦截
重复请求返回原结果
```

### 2. 认证链路复杂
公安认证、人行认证、打款认证、银联认证存在同步耗时和通道特例问题。

后续方向应是：

```latex
认证能力统一
耗时认证异步化
通道配置标准化
```

### 3. 配置分散
例如 APP 消费中，交易行所配置在一个表，清算行所配置在另一个表，容易导致交易和清算不一致。

应尽量统一配置来源，避免同一业务参数多处维护。

### 4. 基金体系不统一
基金存在虚账户体系和电子账户体系两套逻辑，电子账户体系又缺少订单和异常处理机制。

后续应统一交易模型，补齐：

```latex
订单表
流水表
状态机
异常回查
抵用券补偿
```

### 5. 清算流程需要收敛
代收、代付、商户代付、批量提现等能力后续都倾向统一支付承接。

这说明 E 账通后续应减少对底层通道的直接处理，把更多精力放在账户、业务订单、流水、状态和异常补偿上。

---

## 十八、整体业务主线总结
E 账通的业务主线可以概括为：

```latex
客户 / 渠道
    ↓
虚账户关系
    ↓
电子账户
    ↓
核心真实账务
    ↓
统一支付 / 银联 / 网联 / 直销通 / 银保通
    ↓
消费、代收、代付、基金、闪付、扫码、保险
    ↓
异常回查、冲正、对账、清算、通知
```

核心设计思想是：

1. **电子账户承载真实资金。**
2. **虚账户区分渠道和业务场景。**
3. **台账记录虚账户维度的资金变化。**
4. **核心负责银行内部真实账务。**
5. **统一支付负责跨行和外部支付通道。**
6. **E 账通负责交易编排、流水状态、异常补偿和对账清算。**
7. **所有非实时确定结果都依靠状态机、回查、冲正和批次任务保证最终一致性。**

用一句话概括：

> E 账通是围绕电子账户建设的银行互联网交易中台，向上承接渠道和商户业务，向下编排核心、统一支付、直销通、银保通等系统，通过账户、流水、台账、状态机、异常回查和对账清算机制，保证线上资金交易可追踪、可恢复、可对账。
>
