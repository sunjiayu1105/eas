# 000_账户信息表垂直分表

## 1 问题

为什么要对账户信息表做垂直分表，如何划分主表与扩展表，以及为什么可能改善高频账户查询的性能？

## 2 高级 Java 面试核心考点

- 按字段属性、访问频率和存储占用划分主表与扩展表。
- 通过行宽、数据页和 Buffer Pool 理解查询性能变化。
- 区分优化收益的成立条件、实际验证结果与拆分后的访问成本。

## 3 面试口述精炼版本

口述内容字符数：494

**先看高频查询需要什么**

账户信息表是基础表，消费、理财、保证金等业务经常根据账户账号、状态和等级判断是否允许交易。但原表还放了 OCR 影像、银联认证、公安认证等低频信息。如果这些字段让主表行内记录较宽，查询大量不同账户时，就可能需要访问更多数据页，增加缓存和磁盘读取压力。

**按字段用途和频率拆分**

拆分时结合字段用途、访问频率和实际存储占用。主表保留账户账号、状态、等级、渠道号、客户号等高频核心字段，低频字段按业务属性放到扩展表，例如 OCR 影像信息表。交易校验只查主表，需要低频信息时再查询扩展表，并通过关联键找到同一账户的数据；具体关联键仍需核对表结构。

**说明收益和代价**

拆分后，如果主表行内记录变小，同样大小的数据页通常能放下更多记录，Buffer Pool（缓存数据页的内存区域）也能容纳更多账户数据，有助于减少页面读取和缓存淘汰。但命中率、磁盘 I/O 和耗时是否改善，还取决于查询方式与实际负载，不能仅凭拆表就下结论。同时，读取完整账户资料可能需要关联或额外查询，跨表更新也需要保证一致性。

## 4 详细方案

### 4.1 原表的问题与拆分依据

原项目材料描述：消费、理财、保证金等业务在高并发交易、批量处理和异常补跑时，需要持续查询大量不同账户。高频校验主要关注账户是否存在、状态是否正常，以及账户等级是否允许交易。

原表同时保存 OCR 影像、银联认证和公安认证等低频字段。OCR 指光学字符识别，本文沿用原材料的“OCR 影像相关字段”说法；这些字段究竟保存影像内容、地址还是识别结果，原材料没有说明。

拆分时结合三个维度判断：字段属于哪类业务、是否经常一起访问，以及实际占用多少存储空间。字段多不一定意味着记录很宽，也不能仅凭字段名称判断其占用。

例如，假设交易校验只需要账户状态和等级，而影像信息主要在资料审核时使用，两者访问频率和用途不同，适合分开存储。此处资料审核只是解释访问差异的示例，并非已核实的项目流程。具体请求占比和字段大小仍需从实际 SQL、表结构及数据分布核对。

项目材料依据：[面试题汇总中的账户表拆分背景](D:/000/sources/eas/999_EAS/999_面试题_汇总.md:105)。该材料支持拆分动机与维度，不构成性能测试证据。

### 4.2 主表与扩展表分别保存什么

垂直分表是把同一业务实体的不同字段拆到多张表中，不是按账户范围或取模把不同账户行分散到多张表，也不等于已经分库。

按原材料中的方案：

- 账户主表保留账户账号、账户状态、账户等级、渠道号和客户号等高频核心字段。
- 低频字段按属性类别进入对应扩展表，例如 OCR 影像信息表保存 OCR 影像相关字段。
- 银联认证、公安认证也是原文列出的低频信息，但具体扩展表名称和结构尚未给出，不能补写为已经落地的表。

主表与扩展表需要通过能够标识同一账户的关联键对应。不能直接把客户号当作账户唯一标识，也不能未经核对就认定账户账号一定是主键。若某类扩展信息每个账户最多一条，可通过关联键的唯一约束保证这一关系；若保存多次认证记录，则需要按实际业务设计一对多关系。这些是设计约束，尚不是已核实的项目结构。

高频交易校验只读取主表所需字段；确实需要低频资料的业务请求，再按关联键查询扩展表。如果所有高频请求仍无差别关联全部扩展表，拆分预期收益就可能被额外访问抵消。

### 4.3 行变窄为什么可能减少读取成本

InnoDB 通过聚簇索引保存行数据，并以页为单位管理缓存和读取。Buffer Pool 是缓存表和索引页面的内存区域，命中缓存时可以减少从磁盘读取页面的需要。

在页大小、填充情况等条件接近时，主表行内记录变小，一个数据页通常能容纳更多账户记录。访问一批不同账户可能涉及更少的主表页面；同样大小的 Buffer Pool 也可能缓存更多账户，从而减轻页面淘汰和磁盘读取压力。这是可能产生收益的机制，不是仅凭拆表就能保证的结果。

InnoDB 页大小的默认值为 `16 KiB`（16,384 字节）；实际值需核对 `innodb_page_size`，不能默认项目一定未修改配置。依据：[InnoDB Startup Configuration](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-init-startup-configuration.html)。

还需要区分两种情况：

- 大字段不一定完整放在主表页面中。以 DYNAMIC 行格式为例，较长的变长字段可以存到溢出页，行内保留指针。因此不能把影像文件的全部大小直接算作主表行内宽度，也不能认为不查询影像就必然读取影像内容。
- 如果高频查询已经由覆盖索引满足，即索引包含查询所需全部字段、不需要回到聚簇索引读取记录，那么移走非索引低频列，未必明显缩小该查询访问的索引。应先看执行计划，而不是笼统认为所有查询都会变快。

依据：[InnoDB Row Formats](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-row-format.html) 说明行格式与页外存储；[Buffer Pool](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-buffer-pool.html) 说明按页缓存及页面淘汰；[Clustered and Secondary Indexes](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-index-types.html) 说明行数据与二级索引的存储关系。

### 4.4 如何评价收益与拆分代价

收益要通过相同业务负载下的前后对比确认，保持数据规模、SQL 语义、并发、硬件和缓存预热条件尽量一致。主要观察查询执行计划、扫描与访问页面情况、Buffer Pool 的逻辑读取和物理读取、磁盘 I/O，以及接口耗时和吞吐量。

例如，拆分后主表查询耗时降低，但读取完整账户资料需要额外查询，仍应检查整个业务请求的耗时；不能只比较其中一条 SQL。实例整体缓存命中率也会受到其他业务影响，不能单独证明账户表优化有效。

拆分会增加关联查询、表维护和跨表写入的成本。需要原子更新主表和扩展表时，若它们位于同一 MySQL 实例且均为 InnoDB，应纳入同一有效事务；是否跨库、事务如何配置及失败如何恢复，需核对实际实现，本文不假定已有分布式事务方案。

目前没有前后测试数据，适合表述为“目标是通过缩小高频主表，降低其页面占用和读取压力”，不应写成“缓存命中率已提高、磁盘 I/O 已下降”，也不能编造提升比例。
