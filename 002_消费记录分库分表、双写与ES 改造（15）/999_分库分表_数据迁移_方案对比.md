# 999_分库分表_数据迁移_方案对比

## 1 参考文章的双写迁移方案

参考文章：[999_分库分表_数据迁移_参考文章](999_分库分表_数据迁移_参考文章.md)。

参考文章采用业务代码双写，目的是在不停机的情况下完成从旧表到新分库分表集群的平滑迁移。迁移期间，旧表继续承接线上业务，新表同步接收业务变更；历史数据迁移完成并通过一致性校验后，再逐步切换查询和写入流量，最后下线旧表双写逻辑。

参考文章强调不停机，是因为停机迁移需要暂停全部线上流量，数据量越大，迁移耗时越不可控；如果数据达到 TB 级别，迁移可能持续数小时甚至更久，业务无法承受长时间中断。双写让旧表继续承接业务请求，同时让新表持续接收增量变更，配合历史数据迁移、一致性校验和灰度切换，最终完成迁移而不影响用户使用。这里的“不停机”针对的是持续运行且不能接受长时间中断的业务，并不表示所有规模较小的系统都绝对不能选择停机迁移。

### 1.1 服务升级，开启双写

所有涉及数据变更的 INSERT、UPDATE、DELETE 操作，都需要在写入旧表的同时尝试写入新表。旧表写入是强依赖，旧表写入失败时主业务不能继续；新表写入是弱依赖，新表写入失败不能直接阻断主业务，但必须记录日志、告警并进入补偿队列重试。

双写范围应覆盖所有实际写入入口，包括接口、Job、批处理和脚本。新表写入需要按照分片键计算目标库和物理表，并保证幂等。

### 1.2 历史数据迁移

双写开启后，新表只能接收到增量数据，旧表中的历史数据还需要通过迁移工具分批导入新表。迁移工具应支持限流、断点续传、幂等和按更新时间判断新旧，避免用历史数据覆盖双写产生的新数据。

### 1.3 一致性校验和差异修复

历史数据迁移完成后，需要执行多轮全量、抽样和增量校验。校验发现差异时，应以旧表为当前业务基准，先定位差异原因，再修复代码、配置或迁移逻辑并验证；确认写入链路没有问题后，才可以手工订正新表，并再次校验，不能直接用补数掩盖写入缺陷。

### 1.4 查询和写入灰度切换

校验通过后，先按功能或流量灰度切换查询，观察错误率、延迟、慢查询和业务结果。查询稳定后，再灰度切换写入流量到新表。每个阶段都应保留回滚开关，确认全部流量稳定切换后，才下线旧表双写逻辑并停止旧表写入。

### 2.1 004 业务双写

- 明确双写目的：在不停机的情况下完成旧表到新表的平滑迁移，为旧表依赖、查询切换和最终收口提供过渡期。
- 盘点并改造所有旧表写入入口，覆盖接口、Job、批处理和脚本，不能只改已知接口。
- 明确写入顺序和失败边界：旧表写入是主流程强依赖；新表写入失败时记录日志、告警并进入补偿流程。
- 覆盖所有业务变更语义，包括新增、更新、删除、撤销和退货；撤销 `BS0013`、退货 `BS0024` 按独立记录处理。
- 固化新表分片路由和幂等规则：根据 `merchantNo` 计算目标分片，以 `serialNo` 关联新旧记录，避免重复新增、撤销和退货。
- 明确新表 `version` 的生成和更新规则，保证 ES 使用正确版本，避免旧数据覆盖新数据。
- 增加双写失败补偿、重试上限、告警和人工处理入口，并记录失败原因和处理结果。
- 保留旧表查询，按功能或流量逐步切换到新表；查询稳定且全部依赖完成后，关闭旧表写入，改为新表单写。

### 2.2 005 旧表与新表一致性校验

- 校验范围覆盖历史数据、双写增量、INSERT、UPDATE、DELETE、撤销和退货记录。
- 增加独立抽样或全量校验，避免只依赖变更事件，漏掉启动前差异、事件丢失、位点断档或任务漏建。
- 固化比较字段清单和规范化规则，明确 `NULL`、金额、时间、枚举和删除状态的比较口径。
- 建立校验任务去重、积压告警、重试上限和失败恢复机制。
- 差异处理必须遵循：定位根因 → 修复代码或配置 → 验证写入链路 → 手工订正新表 → 再次校验。
- 代码或配置问题未修复并验证前，不得直接修改新表数据。
- 记录校验批次、数据范围、差异数量、根因、修复结果和复核结果，形成可追溯验收证据。
- 连续观察并满足项目已确认的无差异周期后，才停止旧表与新表校验并进入最终收口。

### 2.3 待确认的项目实现信息

- 所有旧表写入入口及其负责人是否已形成清单。
- 新表写入失败后的补偿队列、重试和告警组件是否已确定。
- 撤销、退货及物理删除操作实际对应的 SQL 类型和删除前字段是否已确认。
- 新表 `version` 在新增、并发更新和人工修复场景下的具体实现是否已验证。
- 查询灰度比例、观察指标、回滚条件和最终切换窗口是否已确定。
