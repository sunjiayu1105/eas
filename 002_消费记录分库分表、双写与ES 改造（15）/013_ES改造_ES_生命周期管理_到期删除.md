# 013_ES改造_ES_生命周期管理_到期删除

## 1 已确认规则

- 以下内容按照当前项目 AGENTS.md 规定的技术栈版本编写：Java 8、Spring Boot 2.7.18、MySQL 8.0.33、Elasticsearch 7.17.15、RocketMQ Spring 2.3.0、RocketMQ Client 5.2.0、Canal Server 1.1.7。
- 采用整索引删除方案：MySQL 到期 DELETE 不调用 ES Delete API，ES 由 ILM 删除整个过期月份索引。
- MySQL 只清理原始 create_time 超过五年的消费记录；撤销等业务删除不等同于保留期清理。
- 查询和校验限制在最近五年，超期数据可以暂时保留，但不能被查询、校验或补偿流程重新写入。
- ES 按不可变的原始 create_time 定位自然月索引 records-yyyy.MM，业务时区为 UTC+08:00，不使用 rollover。
- 生命周期起点是所属月份下个月 1 日 00:00；正式策略的 cold min_age 为 366d，delete min_age 为 1830d，均从该起点计算。ILM 可以延后执行，不能提前删除保留范围内的数据。
- MySQL 与 ES 独立清理，不要求先后顺序；历史回放、修复和补偿不向 ES 写入五年范围外的数据。
- 历史回放期间使用只有 hot 阶段的临时策略，历史同步、校验和观察验收通过后才切换正式策略。

## 2 面试口述精炼版本

**先划分清理职责**

业务只需要查询最近五年的数据，所以 MySQL 按原始创建时间清理源记录；这类到期 DELETE 不触发 ES 逐文档删除。ES 由 ILM 按月份索引统一管理，避免大量文档删除带来的段合并和冷节点压力。

**再统一查询和校验范围**

查询、增量校验和补偿都先按 UTC+08:00 计算最近五年的范围。范围外的数据可以暂时存在 ES，但不应被查询、比较或重新补偿；范围内的数据才继续执行一致性处理。

**最后按索引年龄整月删除**

每个月份索引的生命周期起点设为所属月份下个月 1 日零点。起点满 366 天后具备进入 cold 的资格，满 1830 天后具备删除资格。切换正式策略前必须完成历史同步、校验和观察验收，实际 ILM 执行仍要以集群状态为准。

## 3 详细方案

### 3.1 MySQL、消费服务与 ILM 的职责

| 环节 | 责任 |
| --- | --- |
| MySQL 清理任务 | 清理原始 create_time 超过五年的源记录 |
| Canal 与 RocketMQ | 继续传递变更，DELETE 保留必要的删除前信息 |
| ES 消费服务 | 跳过消费记录表的保留期 DELETE；范围内 INSERT、UPDATE 正常写入 |
| 查询服务 | 校验请求范围，并把最近五年的条件下推到 ES |
| 增量校验与补偿 | 只处理范围内且当前仍存在于 MySQL 的记录 |
| ILM | 按月份索引执行冷热迁移和整索引删除 |

MySQL 和 ES 的清理任务相互独立。不能把 MySQL 已删除推导成 ES 已删除，也不能因为 ES 暂时保留超期文档就把它当作范围内差异。

### 3.2 消费端的范围判断

消费服务先精确匹配消费记录表。对该表的 DELETE，不调用 ES Delete API，保留必要消息信息后继续处理同一消息的其他事件。对 INSERT、UPDATE，必须取得原始 create_time 并计算当前保留下界；创建时间缺失或格式错误属于异常，不能直接当作超期跳过。

建议用“当天日期按 UTC+08:00 减五个自然年，再取当天零点”得到下界 L。采用 create_time >= L 作为保留范围、create_time < L 作为超期范围；实际日期包含关系和闰日处理必须在实现中统一。

重试时要重新计算当前下界，不能复用首次失败时的判断。范围内事件按原始月份索引、业务版本和既有幂等规则处理；范围外事件记录跳过原因，不能重新写入 ES。

### 3.3 查询、校验和补偿范围

后端必须校验前端时间条件，并在 ES 查询中加入 create_time >= L。用户指定的日期范围与最近五年范围取交集；列表、总数和聚合使用相同边界。

增量校验使用 [015_ES改造_ES_新表与 ES 增量校验_整体实现](<./015_ES改造_ES_新表与 ES 增量校验_整体实现.md>) 的 update_time 扫描入口。扫描当前仍存在于 MySQL 的记录后，再按 create_time 判断是否在保留范围内：

- 超期记录标记为范围排除，不作为内容差异补偿；
- 范围内记录继续比较 MySQL 与 ES，缺失或不一致才进入补偿；
- ES 查询失败、索引缺失或结果不明时保留未完成状态，不能判定为一致；
- MySQL 当前不存在的记录按已确认的到期清理规则结束，不创建 ES 删除差异。

校验扫描窗口、比较、补偿和恢复由 043—049 维护，本篇只定义保留期边界。

### 3.4 ILM 的月份计龄和删除阶段

每个月份索引分别设置 `index.lifecycle.origination_date`。例如 `records-2021.10` 的计龄起点为 2021-11-01 00:00:00+08:00，不能用索引创建时间或统一固定时间代替。

正式策略的核心阶段如下：

```http
PUT /_ilm/policy/consume-normal
{
  "policy": {
    "phases": {
      "hot": { "actions": {} },
      "cold": {
        "min_age": "366d",
        "actions": { "migrate": { "enabled": true } }
      },
      "delete": {
        "min_age": "1830d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

`1830d` 是覆盖五个自然年的保守时长，不等于任意日期简单减去 1825 天。ILM 按索引年龄执行整索引删除，不逐条检查每个文档的日期；因此不提前删除的前提是原始 create_time、月份路由和计龄起点都正确。

删除阶段配置与冷热分离配置需要统一维护，见 [012_ES改造_ES_生命周期管理_冷热分离](<./012_ES改造_ES_生命周期管理_冷热分离.md>)。两者不是需要依次覆盖同一个策略的独立脚本。

### 3.5 历史回放和过期消息防护

历史回放期间先使用只有 hot 阶段的临时策略。同步、校验和观察验收通过后，切换正式策略前检查已过期索引清单，因为某些索引可能切换后很快获得删除资格。

普通 Index 请求的自动创建限制、索引创建权限和消费者不创建索引的规则必须同时生效，防止过期消息或补偿请求在 ILM 删除后重建旧月份索引。索引缺失进入统一失败处理并保留重试能力；仅过滤 DELETE 不能解决旧 INSERT、UPDATE 重放问题。
