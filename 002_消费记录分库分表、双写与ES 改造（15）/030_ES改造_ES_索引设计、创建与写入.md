## 2 面试口述精炼版本

**消息字段支撑定位和写入**

按项目设计，消息中的主键标识记录，操作类型区分增删改，业务版本 `version` 判断新增和更新的新旧；消费服务按原始 `create_time` 所属月份确定索引。新增、更新携带变更后的完整数据。MySQL DELETE 事件只保留删除前的主键和创建时间，用于消息契约、对账或状态判断，不同步调用 ES Delete；ES 文档由 ILM 按索引保留策略删除。详见 3.1。

**事件身份识别同一次变更**

主键只能识别记录；可在主键范围明确、同版本只对应同一次操作和内容时，用“主键 + 业务版本”识别变更。拆分、重试和重投须保持版本、操作、数据和来源身份不变。独立 `eventId` 尚未确定，RocketMQ 消息 ID 或 `keys` 不能单独作为稳定事件身份。详见 3.2。

## 3 详细方案

### 3.1 消息字段各自解决什么问题

以下是内部事件的逻辑要求，不代表 Canal 原生消息已经完整提供这些字段。

| 信息 | 用途 | 保持条件 |
|---|---|---|
| 业务主键及必要库表信息 | 识别业务记录及来源；项目以 `consumeId` 作为 ES 文档 `_id` | 明确主键唯一性范围，拆分重试不改变 |
| 操作类型 | 区分新增、更新和删除 | 同一事件重投不能改变操作 |
| 业务 `version` | 比较新增、更新的同一记录的新旧 | 新增、更新取同次变更的行后值；MySQL DELETE 不要求为 ES 逐条删除生成专用删除版本 |
| 原始 `create_time` | 保留业务记录最初创建的时间，供 05 确定所属月份索引 | 更新、拆分、重试和重投不改变；不能用事件发生时间或消息处理时间替换 |
| 行后业务数据 | 组装新增、更新的完整文档 | 是否包含所需字段须验证 |
| 删除前信息 | 保留 `consumeId`、原始 `create_time` 等定位数据 | 删除事件不存在可直接套用的“删除后行数据” |
| 必要来源信息、可选 `eventId` | 追踪来源或标识同一次变更 | 跨重新分批、重投和回放仍稳定 |

新增、更新必须把同一次变更的业务数据与 `version` 一起传递，不能重试时重新查询当前数据，却继续沿用旧事件版本。这里的“行后数据”指该次新增或更新完成后的行数据；它是否包含组装 ES 完整文档所需的字段，仍须核对实际消息及转换逻辑。

消息携带 `version` 只是提供判断新旧的依据，不代表已经完成防旧写。项目设计由消费服务把业务版本作为外部版本随写入请求提交，交给 ES 在同一物理索引、同一 `_id` 内比较；不是仅靠消费端先查后比来保证并发安全。具体请求和保护边界见 [05 新增、更新与外部版本请求](<030_ES改造_ES_索引设计、创建与写入.md>)。

MySQL DELETE 没有删除后行数据，因此保留删除前的 `consumeId` 和原始 `create_time`，用于消息契约、对账或状态判断。项目不把该事件转换为 ES 逐条 Delete；ES 按自然月物理索引由 ILM 统一执行保留期删除，具体见 [07 索引保留期与删除](<032_ES改造_ES_生命周期管理_到期删除.md>)。

### 3.2 可选事件身份与去重边界

业务主键回答“是哪条记录”，业务版本用于比较同一记录不同变更的新旧，事件身份回答“是否为同一次源数据变更”。例如，同一记录发生两次更新，主键相同，但应能区分两次变更；其中一次更新被重新投递，仍应识别为原来那次变更。这是概念示例，不是运行验证结果。

“业务主键 + 业务版本”只有在主键范围明确、同版本对应同一次操作和同一内容时，才可作为新增或更新事件识别的候选依据。若主键只在某个库表内唯一，识别键就必须包含区分该范围的信息；主键复用或版本重置可能让不同事件得到同一个识别键。MySQL DELETE 不进入 ES 逐条删除分支，其事件身份主要服务于消息契约、对账或状态判断。以上是候选方案的成立条件，不代表事件识别方案已经选定或实现。

采用来源实例与 binlog 行坐标生成 `eventId` 也是候选方案。这里的坐标指源 binlog 文件、事件位置和事件内原始行序号，用来定位某一次行变更；重新分批后的行下标不能代替原始行序号。关联 Server 文档记录了原生 JSON 缺少完整坐标、二进制按键拆行缺少原行序号等边界，不能直接假设拿到消息就能构造稳定事件 ID。采用该方案前，须在拆分导致信息丢失之前补齐来源身份及行级坐标，并验证重放稳定性；本次未独立复核 Canal 源码或实际消息，这些格式边界仍以关联文档记录为依据。

RocketMQ 消息 ID 标识的是消息：一条消息可能包含多个事件，同一事件也可能被重新发布为另一条消息，因此不能单独用它标识源数据中的某次变更。`keys` 是消息查询用的业务键，不自动保证每个源事件都有唯一且稳定的值；例如按业务主键设置时，同一记录的多次变更会使用相同的键。批次 ID 和分批下标依赖本次分批结果，重新分批后也不能保证不变。这里不假定每次消费重试都会改变消息 ID，而是要求身份方案同时覆盖重新发布和重新分批。

独立事件 ID 也不等于已经实现幂等，即同一事件重复处理仍得到正确结果。还需要核对处理状态和执行结果，具体见 [09 重复消息幂等](<030_ES改造_ES_索引设计、创建与写入.md>)。事件身份也不能替代业务版本比较新旧。

## 3 详细方案

### 3.3 源库删除与旧消息保护

MySQL DELETE 消息保留删除前的 `consumeId` 与原始 `create_time`，用于消息契约、对账或状态判断；它不要求为 ES 逐条删除生成专用版本，也不触发 ES Delete API。ES 删除由 ILM 按自然月物理索引的保留策略统一执行。

下面是条件示例，不是测试结果：同一物理索引、同一 `_id` 下，更新版本为 5，后续版本为 6 的更新先写入，晚到的版本 5 更新在使用外部版本控制时会被拒绝。这里的保护对象是新增或更新请求；MySQL DELETE 不通过 ES Delete API 建立删除版本屏障。

正常新增、更新、重试以及仍在保留范围内的历史回放和补偿，继续遵守原始索引定位、业务版本和 ES 外部版本规则。由于 MySQL DELETE 不同步为 ES 删除事件，且删除发生在业务稳定五年之后，本方案不再单独设计“旧 DELETE 覆盖新写入”或“ILM 删除后旧 DELETE 重建文档”的保护。其他写入请求的保护边界由 [08 旧写保护](<030_ES改造_ES_索引设计、创建与写入.md>)、[10 失败恢复](<033_ES改造_ES_写入失败、重试与恢复.md>) 展开。

## 2 面试口述精炼版本

**按原始创建月份组织索引**

我们把记录的原始创建时间按 UTC+08:00 换算成所属年月，写入对应的 `records-yyyy.MM` 索引。原始创建时间不变，所以跨月更新仍写入原来的月份索引；跨月查询通过别名 `records-read` 访问多个索引。这个别名仅用于查询，项目不使用 rollover（索引滚动切换）。详见 3.1。

**提前创建月份索引**

**创建时还要衔接生命周期配置**

创建任务按目标月份设置 ILM（索引生命周期管理）策略和索引年龄的计算起点：按 UTC+08:00，从所属月份下个月 1 日零点起算。历史数据所属的月份索引可能已达到迁移或删除期限，所以在历史数据同步和验收期间，先使用不执行迁移和删除的临时策略。确认历史数据已同步并校验通过，且增量同步和数据一致性的观察验收通过后，再切换正式策略。任务实现及未来起点的集群行为仍待验证。详见 3.4。

**消费者只写入并统一处理失败**

消费者通过单条 Index 请求写入，不负责创建索引，也不增加索引缺失的专门恢复分支。所有写入失败进入统一失败处理并保留重试能力，不能当作消费成功。目标月份索引限制普通 Index 请求自动创建，避免绕过初始化流程。详见 3.3。

## 3 详细方案

### 3.1 索引组织与职责交接

记录按不可变的原始创建时间，以 UTC+08:00 确定所属年月，写入对应的 `records-yyyy.MM` 索引。例如，原始创建时间为 `2026-10-15 10:00:00+08:00` 的记录归入 `records-2026.10`，11 月更新时仍操作该索引。此处为规则示例，不是运行结果。

模板定义新索引的字段结构、公共配置和 `records-read` 别名。创建月份索引时，如果预期模板生效且别名配置成功，新索引就会关联到 `records-read`；查询通过该别名访问已关联的月份索引，写入直接使用目标物理索引名。实际字段 Mapping 另见 [013 ES Mapping 设计](<999_ES Mapping 设计.md>)，本文保留创建所需的最小示例。

[05 物理索引定位与增删改](<030_ES改造_ES_索引设计、创建与写入.md>) 使用这些规则计算目标索引并执行操作；创建机制不决定过期事件是否应该被接收。过期消息重建已删除月份索引的防护要求见 [07 保留期与删除](<032_ES改造_ES_生命周期管理_到期删除.md>)，对应机制仍待实现验证。

### 3.2 模板与创建配置

模板匹配 `records-*`，统一核心 Mapping、索引配置和 `records-read` 别名。模板在创建索引时应用；多个可组合索引模板匹配时，使用优先级最高的模板，不能认为所有匹配模板会自动叠加。实际生效模板及其优先级须结合部署配置核验。

公共配置例如 `index.number_of_shards`（主分片数量）和 `index.number_of_replicas`（每个主分片的副本数量），此处不指定项目取值。每月不同的 `origination_date` 由创建任务单独设置。

以下是未执行的结构示例，只用 `create_time` 和 `version` 演示字段声明，不代表项目完整字段契约，也不能直接用于完整业务文档写入：

```http
PUT /_index_template/records-template
{
  "index_patterns": ["records-*"],
  "template": {
    "settings": {},
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "create_time": { "type": "date" },
        "version": { "type": "long" }
      }
    },
    "aliases": { "records-read": {} }
  }
}
```

`dynamic: "strict"` 与 [013 ES Mapping 设计](<999_ES Mapping 设计.md>) 的既定字段策略一致：文档出现未声明字段时，拒绝该文档写入。例如，若实际 Mapping 只有示例中的两个字段，写入带 `consumeId` 的业务文档就会被拒绝。因此，实际使用前必须对齐完整业务字段及类型；这里的拒绝结果是按配置规则推导的示例，未执行请求验证。

用于应用定位索引的 `create_time` 不代表已确认要写入 ES 文档正文，正文中的业务 `version` 字段也不等同于请求中的外部版本参数。此处两个字段仅用于演示，不能据此替代 013 的字段契约核对。

ILM 负责整个月份索引的保留期删除；普通 Index 请求的自动创建限制由 3.3 说明。上述模板只展示公共结构，ILM 策略绑定和每月不同的 `origination_date` 由创建任务显式设置，见 3.4；模板示例本身不是完整建索引请求。

[来源：索引模板](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/index-templates.html)说明模板的应用时机与优先级；[dynamic](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/dynamic.html)说明严格模式拒绝未声明字段。本次已查阅上述官方文档，未验证项目实际模板。

### 3.3 提前创建、失败恢复与权限

自动任务在上一个月显式创建下个月的月份索引；历史导入所需月份索引在导入前单独准备。准备流程须在对应月份数据写入前完成，消费者不调用创建索引接口。

首次创建失败后再重试 3 次，仍失败则告警。后台管理系统提供手动启动入口，排查后可重新执行；如果自动任务代码存在问题，由运维手动创建索引。重复执行时，若索引已存在，应核对实际 Mapping、公共配置、读别名、ILM 策略及 `origination_date` 是否符合目标月份要求，不能只凭同名索引存在就判定完成。配置不符时不认定准备完成，具体修复方式仍需结合差异确定。

以索引创建成功且配置核对通过作为准备完成条件；请求超时或重复创建返回的结果不能替代实际配置核对。上述流程为已确认设计，任务调度、重试、告警及人工入口尚未验证。

目标月份索引需限制普通 Index 请求自动创建，可通过 `action.auto_create_index` 控制相应索引名称范围；具体配置及生效行为仍待核验。ES 支持自动创建这一技术能力不变，但本项目正常流程采用提前显式创建，避免写入请求绕过月份初始化。

启用安全功能时，显式创建需要 `create_index` 或 `manage` 索引权限；带别名的创建还涉及目标索引和别名名称的 `manage` 授权要求。消费者的 Index 写入权限与创建任务、模板管理权限分开核对；不能仅因消费者不主动创建，就认为自动创建已被限制。

消费者通过单条 Index 请求写入，不增加针对 `index_not_found_exception` 的专门恢复分支；包括索引缺失在内的所有写入失败进入统一失败处理，保留重试能力，不能将失败当作消费成功。请求构造及响应处理见 [05 物理索引定位与增删改](<030_ES改造_ES_索引设计、创建与写入.md>)。

依据：[Create index API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/indices-create-index.html)、[Index API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)及[权限列表](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/security-privileges.html)。本轮未联网复核这些来源，具体授权和自动创建限制未进行集群验证。

### 3.4 创建与生命周期的交接

`index.lifecycle.name` 指定生命周期策略，`index.lifecycle.origination_date` 以毫秒时间戳指定索引年龄的计算起点。通用模板不能为所有月份复用一个固定起点。本项目按 UTC+08:00，将起点设为所属月份下个月 1 日零点；这是项目设计取值，不是 ES 自动从 `records-yyyy.MM` 推导的结果。[来源：ILM 设置](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/ilm-settings.html)，本次已查阅参数定义，未验证按月配置流程。

历史数据所属的月份索引创建时可能已经达到正式策略的迁移或删除期限，因此在历史数据同步和验收期间，先绑定只有 hot（热阶段）、不配置迁移、只读或删除动作的临时策略。确认历史数据已同步并校验通过，且增量同步和数据一致性的观察验收通过后，再切换正式策略；观察期长度仍待确认。具体期限、策略和示例由 [06 历史回放与 ILM](<031_ES改造_ES_生命周期管理_冷热分离.md>)、[07 保留期与删除](<032_ES改造_ES_生命周期管理_到期删除.md>) 维护。

创建任务根据目标索引所属年月，计算该月份下个月 1 日 00:00:00（UTC+08:00）对应的毫秒时间戳，在显式创建请求中设置 `index.lifecycle.origination_date`，并绑定适用的 `index.lifecycle.name`；不能按任务执行月份直接取值，也不能对所有月份复用固定时间戳。历史月份的创建示例见 06 第 3.2 节。提前创建时起点可能位于未来，ES 7.17.15 对该配置的接受和阶段年龄计算仍须验证。此处为已确认设计，不代表任务或配置已部署。

## 3 详细方案

### 3.1 根据原始创建时间定位索引

同一条记录即使次月更新、重试或补偿，也继续操作原始创建时间所属的物理索引，不能使用当前处理时间重新计算月份。

```java
import java.time.Instant;
import java.time.ZoneOffset;
import java.time.format.DateTimeFormatter;

// 示意：已完成源字段转换的原始创建时刻；不得使用消息处理时间。
Instant originalCreateTime = Instant.parse("2026-10-15T02:00:00Z");
ZoneOffset businessZone = ZoneOffset.ofHours(8);
String indexName = "records-" + originalCreateTime.atZone(businessZone)
        .format(DateTimeFormatter.ofPattern("yyyy.MM"));
```

历史导入、Canal、RocketMQ 和补偿链路必须保持同一个原始创建时间。业务时区已确定为 UTC+08:00，源字段类型及读取转换链路仍需核对。若源字段是无时区的 MySQL `DATETIME`，应按已确认业务时区解释其本地时间；不能直接当成 UTC 时刻。字段为 `TIMESTAMP` 时，还需检查数据库会话和连接器的时区转换，避免重复偏移。示例使用 Java 8 时间 API，未在项目中执行。

[来源：Java 8 Instant](https://docs.oracle.com/javase/8/docs/api/java/time/Instant.html)说明时刻及其时区转换；[MySQL 日期与时间类型](https://dev.mysql.com/doc/refman/8.0/en/datetime.html)说明 DATETIME 与 TIMESTAMP 的时区处理差异。

### 3.2 校验定位结果与处理范围

正常路径直接计算目标索引，不先跨月搜索；`records-read` 是查询入口，不作为写入目标。创建时间缺失或非法时进入受控修复，不能退化为当前月份；修复时如发现同一记录出现在多个索引，也应单独核对，不能把搜索作为日常定位前提。

模板、Mapping 和提前创建流程统一见 [04 索引设计与创建](<030_ES改造_ES_索引设计、创建与写入.md>)。消费者不创建索引，目标月份限制普通 Index 请求自动创建；过期事件处理依赖 [07 保留期与删除](<032_ES改造_ES_生命周期管理_到期删除.md>) 的边界。自动创建限制及过期事件处理仍待实现验证。

参考文章使用 `orders` 写别名。rollover 后，写别名只指向当前 write index，不会根据文档 ID 自动定位历史索引，所以不能直接套用到跨月更新与回放。沿用原文参考：[Aliases — Write index](https://www.elastic.co/docs/manage-data/data-store/aliases#write-index)，本次未联网复核此页面的版本适用性。

### 3.3 新增、更新与外部版本请求

项目与参考文章采用相同的调用方式：遍历一条消息中的记录，每条记录单独构造 Index 请求，同步等待该次调用返回，再处理下一条记录。一次消息包含多条记录，不等于使用 Bulk API（一个请求包含多项操作的批量接口）；不同消息之间仍可并发消费。

参考文章的新增代码在 `orderList` 循环中调用 `esClient.index(request)`，更新代码也逐条调用 `esClient.index(indexRequest)`。项目沿用这一调用方式，但月份索引定位和业务外部版本控制遵守项目规则，不能据此认为两者实现完全一致。

[来源：参考文章新增示例](<./999_使用 Canal + RocketMQ + Elasticsearch8 探索索引冷热节点部署方案.md:1086>)及[更新示例](<./999_使用 Canal + RocketMQ + Elasticsearch8 探索索引冷热节点部署方案.md:1119>)支持逐条同步调用的结论；消息并发、失败重试与确认边界见 [009 消费服务处理逻辑](<./027_ES改造_自定义消费服务_自定义 ES 消费服务处理逻辑.md>)。以上属于已确认设计和示例代码静态核对，不代表项目已完成运行验证。

更新先于新增到达时，应用仍按原始创建时间定位索引，并使用 Index API 写入完整文档。较新的版本先写入后，较旧版本在同一索引和 `_id` 下由 `version_type=external` 拒绝；各写入方须遵守同一版本规则，版本随业务变更递增，同版本对应同操作和同内容。ES 保留当前版本时，相同或更低版本会发生冲突，需要区分重复、过期和异常；索引删除重建后不能依赖旧索引中的版本信息。

```http
PUT /records-2026.10/_doc/1001?version=1&version_type=external
{
  "create_time": "2026-10-15T02:00:00Z",
  "version": 1
}
```

请求 URL 中的 `version=1&version_type=external` 才启用外部版本比较；文档正文中的 `version` 是业务字段，仅保存这个字段不会自动启用版本保护。

版本条件不满足时，Index API 返回 HTTP `409 Conflict`，错误类型为 `version_conflict_engine_exception`。具体 Java 客户端如何报告异常仍需按实际依赖确认，不能直接指定项目尚未确认的异常类。

冲突只说明本次写入未被版本条件接受；具体分类和后续处理见 3.5。

如使用 Update API，文档存在时更新 `doc`；文档不存在且配置 `upsert` 时按 `upsert` 创建；既未配置 `upsert` 也未启用 `doc_as_upsert` 等创建机制时，普通 `doc` 更新会因文档不存在而失败。当前项目主链路仍使用 Index API，Update API 不能直接套用 Index API 的外部版本参数。

[来源：Index API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)说明完整文档写入及外部版本；[Update API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-update.html)说明 doc、upsert 和 doc_as_upsert。业务版本契约见 [01 消息契约](<./030_ES改造_ES_索引设计、创建与写入.md>)。

### 3.4 删除事件的处理边界

此前文档曾描述“取删除前创建时间，定位同一月份索引，再调用 Delete API”，这与当前规则不一致。项目按保留期清理，ES 文档由 ILM 删除整个月份索引；MySQL DELETE 消息不进入 ES 逐条删除分支。

因此，本文不再保留逐条 Delete 作为项目候选路径。新增、更新、重试和补偿仍须使用原始 `create_time` 定位索引并遵守业务版本；ILM 删除索引后，历史回放或补偿若需重建文档，必须另行核对恢复窗口和旧消息保护，不能把 ILM 删除当作版本判断。

### 3.5 请求结果与后续处理

包括 `index_not_found_exception` 在内的写入失败均进入统一失败处理流程，保留重试能力；消费者不调用创建接口，也不新增索引缺失专用恢复分支。索引准备由 04 的自动任务、后台手动启动及运维兜底完成。以下版本冲突分类仍属于统一结果处理，未经核实不得将失败直接确认成功。

写入成功不等于立即可搜索，搜索可见性取决于 refresh（搜索刷新）。是否等待可见由接口要求及刷新策略决定。依据：[Index API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)；本次未进行集群验证。

同版本、同操作、同内容且已成功处理，才有依据判断重复；低版本晚到需核对为过期；同版本内容不同等情况属于异常。409 响应本身不足以完成这些分类，未核实的冲突不能直接确认成功。

- 旧写及超时在途请求的保护见 [06 旧数据覆盖与 Redis 锁](<030_ES改造_ES_索引设计、创建与写入.md>)。
