# 3.4.1.4 ES 如何定位、写入和检索文档？

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 已确认规则

- 本次文件维护仅按用户确认的新名称重命名文档，并同步名称标识及关联引用；不调整正文技术结论。新建的 MySQL、Canal Server、自定义消费服务文档为空白占位文件。

- **自然月索引（已确认设计，待实现验证）**：新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。业务 ID 作为 `_id`，`records-read` 作为跨月读别名。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后进入 cold。删除事件须携带删除前的创建时间，索引模板统一 Mapping、配置和读别名；首次 Index 写入自动建索引以配置和权限允许为前提。
- INSERT/UPDATE 的来源版本取自新表业务 `version`，不再由 binlog 坐标编码；MQ 重试保持原消息数据与版本。该设计尚待实现验证，字段维护及新旧表比较规则见 005。
- 当前由自定义 MQ 消费服务写入 ES，不再采用 009 的旧 Adapter SQL 映射。
- consumeId 同时用于 `_id` 和普通排序字段；稳定 `_id` 只保证同一物理索引内唯一。增删改及重试均按原始创建时间计算同一月份索引，缺少创建时间时进入受控补偿流程。
- 当前完整文档写入候选方案按 005、008 使用 Index API，新增、更新携带新表业务 `version` 并设置 `version_type=external`；删除使用 Delete API，携带与业务 `version` 一致的外部版本规则；外部版本只在同一物理索引、同一 `_id` 范围内比较。版本冲突须区分重复、过期与异常，通用 API 说明不作为其他请求方式已经采用的依据；方案仍待实现验证。
- 业务版本传递、删除标记和字段转换仍是待实现验证的机制，不表述为已上线能力。物理删除使用 Delete API 携带与业务 `version` 一致的版本规则；`index.gc_deletes` 设计值为 `3h`，每半小时自动校验与兜底补偿并在异常时补偿，任务失败或延迟须告警。

## 面试口述精炼版本

**用索引和 `_id` 定位文档**：本方案用新表 `consumeId` 作为 ES `_id`（具体索引内的文档标识）。新增、更新、删除及重试均按原始 `create_time` 和统一业务时区计算同一月份索引；同一索引同一时刻不能存两篇相同 `_id` 的文档。新增、更新调用 Index API，将完整文档连同业务 `version` 一次性写入，由 ES 原子比较版本，决定是否接受这次写入；删除调用 Delete API，携带同一业务版本规则。外部版本不跨索引比较，版本冲突须区分重复、过期与异常，实施仍待验证。

**写入成功后仍要等待搜索可见**：ES 按 Mapping 处理写入并返回结果；相关分片 refresh 后新状态才对搜索可见。ES 响应既不负责 Canal 消费确认，也不能替代新表与 ES 的独立数据比较。

## 详细方案

**以具体索引和 `_id` 定位文档**

`_id` 是 ES 在具体索引内唯一标识文档的元数据，用于按 ID 获取、写入、更新和删除。本方案用新表 `consumeId` 的值作 `_id`；它与 `_source` 中的业务字段 `consumeId` 不是同一字段，项目要求自定义服务显式写入两者，使其表达同一业务标识。`_id` 不能跨月份索引全局定位。同一具体索引内同一时刻不能有两篇不同文档共用 `_id`，但重复提交是否报错取决于请求类型。

**字段转换：** 009 的自定义服务从行事件提取主键设置 `_id`，同时把 consumeId 作为普通字段写入文档，不需要新增 esDocId Mapping 字段或生成 32 份 Adapter 映射。真实新表列名、字段类型、时间和金额转换仍需对齐；验收检查 `_id` 与 `_source.consumeId` 一致，不把设计要求写成已完成事实。

**按请求类型处理重复 ID**

以下是通用 API 语义，不代表当前项目同时采用这些请求方式。未设置版本条件时，`index` 写入完整文档，不存在则创建，存在则替换，不因重复 `_id` 报错；携带 `version_type=external` 时，还要满足来源版本更高的条件，相同或更低版本会返回 `409`。`create` 只在不存在时创建，重复时返回 `409` 冲突。Index API 的 `op_type=create` 与 `create` 语义相同，Bulk 请求则使用 `create` 操作。`update` 更新已有文档，不存在时在未配置 upsert 的情况下通常返回 `404`；`delete` 删除对应文档，不存在时通常返回未找到结果。`_bulk` 整体请求可能返回 `200`，但单项仍可能失败，须检查每项结果。

**按 Mapping 写入，refresh 后提供搜索**

**当前请求对应关系：** 增删改均按原始创建时间计算月份索引；新增、更新组装完整文档，通过 Index API 携带业务 `version` 和 `version_type=external` 写入。DELETE 对原始创建时间确定的具体月份索引通过 Delete API 携带同一业务版本规则执行；删除状态和版本进度仍须可靠保存。ES 7.17 Update API 不支持这套外部版本参数，不能直接套用；默认缺文档时返回 404，配置 upsert 可创建，改用它需重新确定防旧写机制，当前不采用该路径。具体客户端、版本传递和恢复实现仍待验证，不能把旧 Adapter 的默认 upsert 和回查行为当成当前自定义服务配置。详见 009。

**缺字段与 Upsert 边界：** 局部 Update 只修改提交的字段，不会自动补齐历史缺字段；开启 upsert 可能以不完整字段创建缺失文档，也不能解决跨索引定位。是否需要修复历史字段须先检查真实文档和完整字段契约，本次不把历史问题或补数结果写成已验证事实。

**超时与旧写边界：** 应用侧检查不能取消已发出的 ES 请求。写入时的业务版本条件须与新表状态衔接；物理删除后，Index API 可创建缺失文档，ES 删除版本保护时间由 `index.gc_deletes=3h` 设计值限制。独立删除日志不能直接阻止在途旧写让文档复活；每半小时自动校验与兜底补偿可发现并补偿异常，但属于事后修复，不能保证整个半小时内始终不复活。候选条件写入、删除隔离和验收范围见 009，均未实现验证。

ES 按目标具体索引的 Mapping 检查字段、保存文档并建立查询结构。当前 Mapping 设计为 `dynamic: "strict"`，未声明字段会导致对应写入失败；现有 17 字段不能视作新表全字段。成功写入或删除不等于立即搜索可见，相关分片 refresh 后变更才对搜索可见。字段契约和查询约束见[013_ES Mapping 设计.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/013_ES Mapping 设计.md:5>)。

**跨月仍操作创建月份的索引**

新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。例如 10 月创建的记录，11 月修改或删除仍操作 `records-2026.10`；读别名 `records-read` 仅用于跨月检索。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后进入 cold，冷热迁移不改变索引名。模板须提前配置，首次 Index 写入自动建索引以配置和权限允许为前提；历史删除消息须保留创建时间。方案与模板仍待实现验证，生命周期及容量边界见 017、018。
