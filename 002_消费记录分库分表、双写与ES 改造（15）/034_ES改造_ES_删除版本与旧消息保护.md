# 034_ES改造_ES_删除版本与旧消息保护

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 已确认规则

- MySQL DELETE 事件保留删除前的 `consumeId` 与原始 `create_time`，但不触发 ES 逐条 Delete；ES 文档由 ILM 按自然月索引保留策略统一删除。
- 自动校验与兜底补偿任务每半小时执行一次，按当前数据库状态和原始索引规则处理新增、更新及历史回放差异，任务失败或延迟须告警。

## 2 面试口述精炼版本

项目不把 MySQL DELETE 同步为 ES 逐条 Delete，因为 ES 的到期数据由 ILM 按自然月整索引删除。删除发生在五年保留期之后，而业务数据通常在三个月内就已确定，不会出现旧 DELETE 与新写入并发覆盖的问题。因此不需要设计旧 DELETE 覆盖新写入的保护；业务版本和 ES 外部版本控制仍负责防止正常新增、更新和重试消息乱序，历史回放、索引重建及补偿仍按原始索引定位。详见 3.3。

## 3 详细方案

### 3.3 源库删除与旧消息保护

MySQL DELETE 消息保留删除前的 `consumeId` 与原始 `create_time`，用于消息契约、对账或状态判断；它不要求为 ES 逐条删除生成专用版本，也不触发 ES Delete API。ES 删除由 ILM 按自然月物理索引的保留策略统一执行。

下面是条件示例，不是测试结果：同一物理索引、同一 `_id` 下，更新版本为 5，后续版本为 6 的更新先写入，晚到的版本 5 更新在使用外部版本控制时会被拒绝。这里的保护对象是新增或更新请求；MySQL DELETE 不通过 ES Delete API 建立删除版本屏障。

正常新增、更新、重试以及仍在保留范围内的历史回放和补偿，继续遵守原始索引定位、业务版本和 ES 外部版本规则。由于 MySQL DELETE 不同步为 ES 删除事件，且删除发生在业务稳定五年之后，本方案不再单独设计“旧 DELETE 覆盖新写入”或“ILM 删除后旧 DELETE 重建文档”的保护。其他写入请求的保护边界由 [08 旧写保护](<039_ES改造_ES_旧数据覆盖与 Redis 锁.md>)、[10 失败恢复](<041_ES改造_ES_ES 写入失败、重试与恢复.md>) 展开。

依据：[07 索引保留期与删除](<038_ES改造_ES_索引保留期与删除.md>)记录的 ILM 整索引删除规则，以及上述项目文档中的业务版本和旧写保护边界。本次未执行 ES 集群实验。

删除前信息的消息契约不代表源库 DELETE 要逐条删除 ES 文档。[07 索引保留期与删除](<038_ES改造_ES_索引保留期与删除.md>)负责说明 ILM 整索引删除；[05 物理索引定位与增删改](<036_ES改造_ES_物理索引定位与增删改.md>)只保留新增、更新、重试和补偿的索引定位规则。

## 4 待确认或待验证事项

- MySQL DELETE 事件中的删除前信息是否完整传递？
- ILM 按自然月索引删除的实际策略、执行时点和 cold 阶段访问边界是否已验证？

## 5 异议与分析

- **ES 不同步执行 MySQL DELETE。** 原文若讨论删除版本和逐条 Delete，容易让人误以为消费端要写入已进入 cold 的月份索引。当前规则是由 ILM 负责整个月份索引的保留期删除，DELETE 事件不触发 ES Delete。
- **旧写保护的范围。** 这里的旧写保护只针对新增、更新、重试以及仍在保留范围内的历史回放和补偿的版本乱序；不再扩展为旧 DELETE 或五年后删除索引的重建保护。
