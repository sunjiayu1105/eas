# 3.11.1 为什么要引入 ES

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。版本：Java 8、Spring Boot 2.7.18、Elasticsearch 服务端 7.17.15、MySQL 8.0.33。

引入 Elasticsearch（ES）不是为了替换 MySQL，而是为了解决消费记录分库分表后，跨分片、多条件列表查询的性能和复杂度问题。

**分库分表后，跨分片查询需要归并**

分库分表前，消费记录、客户和商户信息可以通过单库中的一条 SQL 完成关联、排序和分页。

分库分表后，原来的单库多表 JOIN 不再适合按原方式直接使用。系统需要先查询消费记录，再根据当前页的标识批量查询 MySQL 客户信息表和 MySQL 商户信息表，最后由应用层组装结果。

在查询消费记录阶段，不带 `merchantNo` 的跨商户查询需要访问全部 32 个分片。带有 `ORDER BY` 时，各分片先过滤并按排序条件返回有序结果，再由 ShardingSphere-JDBC 做全局有序归并和分页，查询链路及资源开销都会增加，深分页时更加明显。

**多条件组合使单一索引难以覆盖**

消费记录列表涉及交易时间、交易状态、渠道、支付方式、金额、错误码等多维组合条件。MySQL 联合索引受最左前缀原则影响，难以覆盖所有条件组合；如果为各种组合建立索引，索引数量和维护成本都会增加。

**让 ES 承担过滤、排序和连续翻页**

因此，系统建立统一的消费交易索引，由 ES 完成跨商户过滤、排序和分页，并使用 `search_after` 降低深分页开销。同时，ES 承担运营和客服的查询流量，降低复杂列表查询对 MySQL 实时交易写入的影响。

**边界：搜索副本不替代交易权威数据**

ES 是消费记录的查询副本，数据同步可能存在短暂延迟。MySQL 仍是交易权威数据源；单笔详情、资金确认和最终状态判断必须回查 MySQL。
