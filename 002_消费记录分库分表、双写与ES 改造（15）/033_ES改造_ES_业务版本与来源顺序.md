# 033_ES改造_ES_业务版本与来源顺序

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 已确认规则

- 仅新分库分表的消费表增加业务 `version`，旧表不增加；历史导入初始化为 1，更新与业务字段在同一 SQL 中递增版本。
- 项目采用并发消费，同一记录的消息可能乱序完成；重试和重新投递沿用原消息版本。
- ES 版本比较请求由 03 文档维护，本文只定义业务版本来源、稳定性和来源顺序。

## 2 面试口述精炼版本

项目采用并发消费，同一记录的消息可能乱序完成，所以不能按消息到达时间判断新旧，而要使用业务 `version`。重试、拆分和重新投递都必须沿用原消息的版本、操作和定位信息。该版本规则只适用于新增和更新；MySQL DELETE 不同步为 ES Delete，不生成 ES 删除版本。

## 3 详细方案

### 3.2 业务版本与来源顺序

新增、更新从行后数据读取业务 `version`。版本随业务修改递增，重试不重新生成；业务键复用时如何衔接版本仍待确认。ES 的版本比较请求由 03 说明，这里只定义版本的来源及稳定性。

来源顺序描述数据库变更发生的先后；并发处理完成顺序不能代替它。项目不再由 binlog 坐标编码 ES 版本，也不承诺两个独立 MySQL 实例之间的全局顺序。来源坐标可以用于追踪，但不能直接当作跨实例可比较的业务版本。

依据：Canal Server 原总览（原文档已删除，依据待补充）及 [自定义消费服务](<025_ES改造_自定义消费服务_自定义 ES 消费服务处理逻辑.md>) 中的来源范围、并发与业务版本设计；本次为项目文档静态核对。
