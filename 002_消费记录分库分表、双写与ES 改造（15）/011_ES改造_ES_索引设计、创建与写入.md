# 011_ES改造_ES_索引设计、创建与写入

## 1 已确认规则

- 以下内容按照当前项目 AGENTS.md 规定的技术栈版本编写：Java 8、Spring Boot 2.7.18、MySQL 8.0.33、Elasticsearch 7.17.15、RocketMQ Spring 2.3.0、RocketMQ Client 5.2.0、Canal Server 1.1.7。
- ES 按月创建物理索引，命名规范为 `records-yyyy.MM`，不使用 rollover；`records-read` 只用于跨月查询，新增、更新和重投直接写入计算出的物理索引。
- 索引定位使用不可变的原始 `create_time`，按统一业务时区计算所属月份。不能使用消息时间、`update_time` 或当前月份替代它。
- 新分库分表的消费表使用业务 `version` 控制来源顺序：历史导入初始化为 1，后续更新在同一条 SQL 中修改业务字段并执行 `version = version + 1`；导入重跑不重置已有版本，消息重投沿用原消息中的数据和版本。
- 新增、更新使用 Index API，并在同一物理索引、同一 `_id` 范围内携带业务版本和 `version_type=external`，由 ES 原子比较新旧版本。MySQL DELETE 不调用 ES Delete API，索引删除由 ILM 管理。
- 消费者不负责创建索引。历史回放所需索引和日常月份索引由索引准备流程提前创建；首次 Index 自动创建仅是配置和权限允许时的兜底能力，不能代替按月份准备索引。
- 写入异常或必要状态保存异常时，抛出异常让 RocketMQ 重投整条消息；已成功的操作不自动回滚。具体重试次数、退避、死信和恢复流程仍待验证。

## 2 面试口述精炼版本

**先准备月份索引**

我先按月份准备物理索引，命名统一使用 `records-yyyy.MM`。索引模板负责统一 Mapping、公共配置和 `records-read` 读别名，历史回放和日常月份索引都由准备流程提前创建。消费者只负责定位索引和写入，不能在消费失败时临时创建索引；首次 Index 自动创建只能作为配置和权限允许时的兜底。

**再确定记录要写入的索引**

处理消息时，我使用业务主键生成稳定的 ES `_id`，使用原始且不可变的 `create_time` 计算所属月份，确定目标物理索引。这样记录即使跨月更新，仍然写回创建月份的索引，不能因为 `update_time` 变化就切换到当前月份。跨月查询使用 `records-read`，这个别名不能作为增删改入口。

**最后按版本写入**

确定索引和文档身份后，新增或更新使用 Index API 写入完整文档，并携带业务 `version` 和 `version_type=external`。ES 在同一物理索引、同一 `_id` 内比较版本，避免乱序消息用旧数据覆盖新数据。消息重投仍使用原索引、原 `_id`、原版本和原数据。

**异常按整条消息重投**

已确认的重复或过期事件按幂等规则处理；索引缺失、权限错误、网络超时、未解决的 ES 异常或必要状态保存失败，都向外抛出异常，让 RocketMQ 重投整条原消息。之前已经成功的操作不会自动回滚。MySQL DELETE 不调用 ES Delete API，整个月份索引的删除由 ILM 管理。

## 3 详细方案

### 3.1 先准备索引：模板、月份和创建职责

索引模板匹配 `records-*`，集中定义 Mapping、公共 settings、生命周期引用和 `records-read` 相关配置。模板只约束新创建的索引；具体字段类型、`dynamic: strict`、别名和权限仍需在实际环境核对，本文的请求和配置只作为设计示例，不表示已经部署。

ES 按月创建物理索引，索引名使用 `records-yyyy.MM`。不使用 rollover，也不把 `records-read` 当作写入索引。历史回放前，按目标月份逐个准备所需索引；日常索引由提前创建任务准备。创建成功后，需要核对模板、Mapping、别名和生命周期设置，核对通过才算准备完成。

索引创建由索引准备流程负责，消费者不在写入失败时临时创建索引。索引不存在、权限不足或模板不匹配时，应按写入失败处理并保留重试能力，不能通过切换到当前月份索引掩盖路由错误。配置和权限允许时，首次 Index 自动创建可以作为兜底能力，但不能替代按月份提前准备索引。

索引创建、冷热策略和到期删除分别由 [012_ES改造_ES_生命周期管理_冷热分离](<./012_ES改造_ES_生命周期管理_冷热分离.md>) 与 [013_ES改造_ES_生命周期管理_到期删除](<./013_ES改造_ES_生命周期管理_到期删除.md>) 维护。

### 3.2 再定位索引：原始 create_time 决定月份

处理顺序固定为“读取消息 → 确认业务主键和来源版本 → 取得原始 `create_time` → 计算月份索引 → 组装文档 → 执行带版本的 Index 请求”。

消息中的 `create_time` 必须来自原始业务记录。INSERT、UPDATE 从完整行的后值取得；DELETE 从删除前信息取得。实际列名、字段类型、时区转换，以及 Canal、RocketMQ 是否完整传递这些字段，仍需按实际消息核验。

例如，业务主键为 `consumeId=1001`，原始创建时间属于 2024 年 1 月，则目标索引是 `records-2024.01`，文档 ID 是稳定的 `1001`。这条记录在 2 月发生更新时，仍写回 `records-2024.01`，不能因为更新时间变成 2 月就改写到 `records-2024.02`。

索引定位不使用消息时间、`update_time` 或当前月份，也不在正常路径先查询 ES 后猜测索引。只要原始 `create_time` 缺失或无法确认，就不能自行用当前时间补齐，应进入受控修复或失败处理。

### 3.3 确定文档身份和来源版本

业务主键生成稳定的 ES `_id`。业务 `version` 表示来源顺序，不是 ES 内部版本，也不是 binlog 位点。历史导入从 1 开始；后续更新在数据库修改业务字段时同步递增。导入重跑不重置已有版本，消息重投和补偿沿用原始业务数据与版本，不能在重试时重新生成版本。

外部版本只在同一物理索引、同一 `_id` 范围内比较。索引月份由 `create_time` 决定，版本新旧由业务 `version` 决定，两者职责不同，不能互换。

### 3.4 使用 Index API 写入

新增或更新使用完整文档的 Index API，携带外部版本参数。概念请求如下，具体 Java 客户端写法仍需按实际依赖核对：

```http
PUT /records-2024.01/_doc/1001?version=12&version_type=external
{
  "consume_id": 1001,
  "create_time": "2024-01-20T10:00:00+08:00",
  "version": 12
}
```

同一物理索引和 `_id` 下，版本更高的请求可以覆盖旧版本；相同或更低版本会产生版本冲突。冲突不能直接等同于成功，需要结合原始事件、版本和实际处理状态，区分重复、过期和异常。不能在冲突后改用无版本写入，也不能把 Update API 的 `doc` 语义直接当作当前 Index API 方案。

跨月查询使用 `records-read`，新增、更新和消息重投直接写入计算出的物理索引。查询别名和写入索引的职责必须分开。

### 3.5 DELETE、重投与结果交接

MySQL DELETE 事件不生成 ES Delete 请求。消息仍需保留删除前的 `create_time`，用于消息契约、对账或恢复判断；整个月份索引的删除由 ILM 按保留策略执行。删除、历史回放和迟到消息之间的恢复边界见 032 及 033，不能在本节额外假设逐条删除已经完成。

单条消息内逐条同步处理 ES 请求。已核实的重复或过期事件按幂等规则处理；未解决的 ES 异常、索引缺失、权限错误、网络超时或必要状态保存异常，向外抛出异常，让 RocketMQ 重投整条原消息。此前成功的操作不会回滚，重投仍使用原物理索引、原 `_id`、原版本和原数据。

消费者处理完消息内全部事件及必要状态保存后才能正常返回，不能因为部分操作成功就提前确认。完整的失败、重试、死信与恢复流程见 [014_ES改造_ES_写入失败、重试与恢复](<./014_ES改造_ES_写入失败、重试与恢复.md>)。

## 4 待确认或待验证事项

本文确认的是索引划分、索引创建职责、索引定位规则、版本写入方式和失败边界；它不等同于功能已经实现或集群已经验证。以下事项仍需在实际环境核对：

- `create_time` 的真实列名、类型、时区语义，以及 DELETE 前信息是否完整传递；
- 索引模板、`dynamic: strict`、自动创建限制、创建权限和 `records-read` 别名；
- 实际 Java 客户端是否正确发送 `version_type=external`，以及版本冲突的返回和分类；
- 索引不存在、超时在途、重试、死信、补偿和 ILM 删除后的历史回放行为；
- 写入成功后的搜索可见性、并发容量和端到端一致性。

本次未连接 MySQL、Canal、RocketMQ 或 Elasticsearch，未执行代码编译、集群配置、联调、压测和故障演练。
