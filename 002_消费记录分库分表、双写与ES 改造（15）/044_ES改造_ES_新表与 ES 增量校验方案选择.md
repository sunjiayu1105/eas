# 044_ES改造_ES_新表与 ES 增量校验方案选择

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 主题边界

本文比较 Binlog 定位和 `update_time` 扫描两种校验入口，并说明为什么当前选择 `update_time` 扫描。Binlog、Canal 和 RocketMQ 仍用于 ES 正常同步，但不作为校验任务入口。

## 2 已确认规则

- 当前校验入口选择按 `update_time` 扫描 MySQL 当前仍存在的最新记录。
- 每轮扫描设置 `scan_end_time = 当前时间 - 5 分钟`，并使用 `update_time + consume_id` 复合游标。
- 扫描保留重叠窗口，允许重复扫描，由任务幂等和 ES 版本控制保证安全。
- Binlog 定位不再用于创建校验任务。

## 3 面试口述精炼版本

我选择用 `update_time` 扫描作为校验入口，而不是按 Binlog 的每条历史变更创建任务。因为同一条记录可能在短时间内连续更新，Binlog 会产生大量历史变更，而校验真正关心的是 MySQL 当前状态是否已经正确反映到 ES。扫描时把截止时间设置为当前时间减 5 分钟，避免 ES 还没来得及同步就开始比较；同时使用 `update_time + consume_id` 复合游标和重叠窗口，降低晚提交和分页边界导致的漏查风险。

## 4 方案比较

| 对比项 | Binlog 定位 | `update_time` 扫描 |
|---|---|---|
| 校验对象 | 每条已提交变更事件 | 扫描窗口内当前仍存在的记录 |
| 任务数量 | 同一记录多次变更可能生成多个任务 | 多次变更可合并为当前记录的一次校验 |
| 主要依赖 | 日志连续、过滤正确、位点可靠 | 所有写入路径维护 `update_time`，游标和窗口可靠 |
| 主要风险 | 历史积压造成大量无效任务 | 晚提交、时间字段漏维护或窗口不足导致漏查 |
| 当前职责 | ES 正常同步链路 | MySQL 与 ES 当前状态校验 |

## 5 扫描边界与执行规则

每轮扫描先固定 `scan_end_time`，查询：

```sql
WHERE update_time > :last_update_time - :overlap_window
  AND update_time <= :scan_end_time
ORDER BY update_time, consume_id
LIMIT :batch_size
```

扫描到记录后，先在数据库事务中保存任务和本轮游标；保存成功后才推进扫描进度。重叠窗口会产生重复任务，因此不能依赖严格去重，必须保证任务执行和 ES 补偿幂等。

## 6 选择结论与成立条件

选择 `update_time` 扫描，是为了减少历史变更造成的校验任务数量，并直接检查当前状态。该方案成立的前提是所有写入路径可靠维护 `update_time`，扫描截止时间能够覆盖 ES 同步延迟，重叠窗口能够覆盖晚提交和调度延迟，并且保留低频对账或重建能力发现扫描遗漏。

## 7 待确认或待验证事项

- `update_time` 的维护路径、精度和索引是否已核实？
- 5 分钟安全延迟和重叠窗口的实际参数如何确定？
- 扫描游标保存与任务保存是否具备事务一致性？
- 扫描遗漏和历史差异是否有对账或重建兜底？

## 8 执行记录

- 本轮将校验入口从 Binlog 定位调整为 `update_time` 扫描。
- 未运行 Canal、RocketMQ、MySQL 或 ES 服务。
