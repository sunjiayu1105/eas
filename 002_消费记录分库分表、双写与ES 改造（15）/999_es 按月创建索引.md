## 设计状态

本方案已确认采用，尚未实施验证。所属自然月结束后满 180 天进入 cold；业务时区、7 天修改窗口及历史删除范围仍待确认。

建议采用 **“按自然月分索引，应用根据文档原始创建时间定位索引”** 的方案，解决跨月更新、删除时需要先查询索引位置的问题。以下是前面讨论的方案汇总，尚未实施验证。

|项目|方案|
|---|---|
|索引命名|`records-2026.10`、`records-2026.11`|
|定位规则|根据不可变的 `create_time` 计算年月，各环节统一时区|
|文档 ID|使用业务 ID 作为 ES `_id`|
|新增|直接写入创建月份对应的索引|
|更新、删除|根据原始创建时间定位同一个索引，再按 `_id` 操作|
|跨月查询|通过覆盖各月份索引的读别名 `records-read`|
|索引创建|ES 7.17.15 支持首次 Index API 写入触发自动创建；前提是 `action.auto_create_index`、`create_index` 权限和模板匹配均满足|
|索引模板|提前配置，统一各月份索引的字段映射、配置和读别名|

例如，10 月 31 日创建的文档写入 `records-2026.10`，11 月 3 日修改或删除时，仍然操作 `records-2026.10`，**不需要先搜索，也不需要额外保存“业务 ID → 索引名”的映射**。

应用需要实现月份索引名的计算，并保证**新增、更新、删除都能获取原始创建时间**。如果通过消息同步，删除消息尤其需要携带删除前的创建时间。缺少创建时间时，仍然需要查询或维护映射。

ES 7.17.15 支持首次 Index API 写入自动创建不存在的索引并应用匹配模板；实际受 `action.auto_create_index`、`create_index` 权限和模板匹配影响。它不会每月主动创建索引，Delete 请求也不能依赖自动创建。这套方案不使用 rollover。之前讨论的 `max_age: 30d` 是按索引年龄滚动，并不等于自然月切换。

旧索引可以持续保留查询能力。如果采用“创建后 7 天内可修改”的规则，上月索引应在月末后继续保持至少 **7 天加延迟重试缓冲**的可写时间，再考虑设置只读。**若历史文档随时可能删除，就不能直接按这个窗口永久设为只读。**

落地前还需要确认：业务时区、7 天修改窗口是否为硬性限制、历史删除范围，以及消息重试和乱序处理方式。
