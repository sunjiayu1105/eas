# 006_05 索引设计、rollover 与创建

## 1 已确认规则

1. **自然月索引（已确认设计，待实现验证）**：新增、更新、正常业务删除、重试和补偿根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`；这里的“正常业务删除”不包含 MySQL 五年保留期清理产生的删除事件；`records-read` 只用于跨月查询。不使用 rollover；所属自然月结束后满 180 天进入 cold。模板统一 Mapping、配置和读别名，首次 Index 写入自动建索引以配置和权限允许为前提；业务版本在同一物理索引、同一 `_id` 范围内比较；更新先到时允许 Index API 先创建索引和完整文档，后到的旧版本由外部版本比较拒绝；过期月份重放不得无条件重建索引。
2. **业务删除边界**：MySQL 物理删除仅用于清理创建时间超过 5 年的数据，边界精确到日；不存在业务提前物理删除。撤销通过新增撤销记录表达，业务类型为 `BS0013`，并更新相关交易状态。撤销订单和类型依据见文末参考来源；物理删除范围以用户明确说明为依据。
3. **查询边界（已确认设计，待实现验证）**：前端查询必须携带时间范围；后端按统一业务时区将查询起止日期限制在最近 5 年内，单次最大跨度为 1 个月，其他筛选条件非必填；使用 `search_after` 分页，每页最多 100 条。保留一个月作为初始设计上限，不因月增约 600 万条直接收紧到 7 天，实际性能须压测验证。读别名本身不提供时间过滤。

## 2 面试口述精炼版本

### 2.1 索引划分与定位

参考文章用 rollover，也就是达到条件后滚动到下一代索引；项目按自然月分索引，不使用 rollover。应用根据不可变的原始创建时间和统一业务时区计算月份，所以同一条记录跨月更新或重试时，仍然写入原来的物理索引；跨月查询使用 `records-read` 读别名。

### 2.2 模板与写入

确定索引划分后，先配置匹配 `records-*` 的模板，统一字段映射、索引配置和读别名。应用再向计算出的月份索引发送 Index 请求：索引不存在时，在自动创建配置和权限允许的前提下，ES 创建索引并应用模板，然后写入文档；索引已存在时直接写入。请求携带业务版本，避免旧版本覆盖新版本。写入成功不等于立即可搜索；文档要等相关分片完成 refresh（刷新）后才对搜索可见，是否同步等待由刷新策略决定。

### 2.3 冷层迁移

已确认的 cold（冷层）目标是所属自然月结束后满 180 天，不能简单从建索引的时间算起。ILM（索引生命周期管理）的实际起算基准和调度仍待实现验证。

历史回放期间，校验任务负责对比新库新表与 ES 并执行兜底补偿，但一次校验通过不代表该月份已经停止写入。暂定在月份封存后执行最终一致性检查，确认没有未完成补偿和新增写入，再授予 ILM 迁移资格；满足自然月结束后 180 天且取得迁移资格后，才由 ILM 执行 cold 迁移。该流程及封存、并发控制仍待确认和验证。

### 2.4 保留期删除

索引保留五年，到期后按索引所属数据时间范围删除整个自然月索引，不逐条校验文档的 `create_time`。MySQL 现有五年清理规则继续保留。查询端限定最近五年，屏蔽暂时多保留的数据。删除过滤位置、是否需要等待 MySQL 实际清理完成、ILM 配置和执行验证仍待落实；ILM 无法自行感知 MySQL 的清理进度。

### 2.5 查询与验证

查询只允许最近五年的数据，单次最多一个月，其他条件可不填；使用 `search_after` 连续翻页，每页最多 100 条。时间范围主要控制检索范围，每页大小主要控制文档读取和返回成本，`search_after` 主要降低深分页成本。按每天约 20 万条估算，30 天约 600 万条，这是范围内记录量，不代表每次扫描全部记录，也不能认为每页只处理 100 条。一个月保留为初始设计上限，具体日数口径待确认，实际性能须通过仅填时间的首屏、翻页和并发压测验证。

## 3 参考文章与项目的索引方案有什么不同？

**结论**：文章按条件 rollover，项目按自然月分索引。

### 3.1 参考文章：按文档数滚动

rollover 是达到设定条件后创建下一代物理索引，并切换写入目标。文章基于 Elasticsearch 8.4.2 配置 ILM（索引生命周期管理）和 rollover 别名，以 `max_docs=5` 触发下一代物理索引，并用秒级或很短的时间演示 warm、cold、delete。这些是演示参数，不能作为当前项目的容量或保留期结论。

### 3.2 项目：按自然月划分

项目以 Elasticsearch 7.17.15 为基线，使用 `records-yyyy.MM`，不使用 rollover。月份决定数据归属；模板决定新索引的字段和配置；生命周期决定索引何时迁移或删除。

## 4 同一条记录跨月更新时，如何定位原来的索引？

**结论**：应用根据不可变的原始 `create_time`，按统一业务时区计算所属月份。新增、更新、重试和补偿均使用该月份的物理索引，`records-read` 只用于跨月查询。

例如，一条记录属于 2026 年 10 月，即使到 11 月才更新或重试，也仍然操作 `records-2026.10`。不能使用当前处理时间计算月份，否则同一记录可能写进不同索引，且外部版本不能跨索引保护旧写入。

原始创建时间必须在历史导入、Canal、MQ 与补偿链路中保持一致，字段类型仍待核验。

## 5 如何配置模板、计算索引并完成首次写入？

**结论**：先配置匹配 `records-*` 的模板，再根据不可变的原始 `create_time` 和统一业务时区计算目标月份索引，最后使用 Index API 写入完整文档。目标索引不存在时，只有自动创建配置、模板匹配和账号权限均满足，ES 才会自动创建索引并应用模板；写入请求携带业务版本，避免旧版本覆盖新版本。更新消息先到时也遵循这条流程，后到的旧版本由外部版本比较拒绝。[来源 8](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)

下面给出模板配置、月份计算、首次写入和权限校验的实现示例；示例尚未在项目环境执行。
### 5.1 项目实现示例（尚未执行）

以下示例按“配置模板→计算月份索引→写入文档”展开，尚未执行，不代表完整生产 Mapping 或已部署配置，也未配置冷层迁移策略。

#### 5.1.1 第一步：提前配置模板

可以使用 **Kibana** 配置 Elasticsearch 索引模板，主要有两种方式：

- **图形界面**：进入 `Stack Management → Index Management → Index Templates`，填写模板名称、匹配规则、字段映射、索引配置和别名。
- **开发控制台**：进入 `Dev Tools → Console`，粘贴下面的 `PUT` 请求和完整 JSON 后执行。

项目使用 Elasticsearch 7.17.15，建议搭配同版本 Kibana；此处是版本搭配建议，不代表项目已部署 Kibana。

模板匹配 `records-*`，新建索引时应用 Mapping（字段映射）、索引配置和读别名：

```http
PUT /_index_template/records-template
{
  "index_patterns": ["records-*"],
  "template": {
    "settings": {
      "index.gc_deletes": "3h"
    },
    "mappings": {
      "properties": {
        "create_time": { "type": "date" },
        "version": { "type": "long" }
      }
    },
    "aliases": {
      "records-read": {}
    }
  }
}
```

`index.gc_deletes=3h` 不控制 ILM 整索引删除，也不能防止已删除索引被旧写重建。这里只展示核心字段，实际 Mapping 需要补齐业务字段，并与项目既定映射一致；采用 `dynamic: strict` 时，写入字段必须全部符合 Mapping。生产环境仍需核对模板优先级及最终生效 Mapping。

保存模板不会立即创建月份索引，也不会修改已有索引。后续需要显式创建索引，或在配置和权限允许时由首次写入自动创建。

#### 5.1.2 第二步：根据原始创建时间计算索引名

下面采用 Java 8 的时间 API，假设 `originalCreateTime` 为 `Instant`，`businessZone` 为项目统一的 `ZoneId`；实际业务时区及源字段类型仍待确认。

```java
import java.time.Instant;
import java.time.ZoneId;
import java.time.format.DateTimeFormatter;

// originalCreateTime 为不可变的原始创建时间，businessZone 为统一业务时区。
String indexName = "records-" +
        originalCreateTime.atZone(businessZone)
                .format(DateTimeFormatter.ofPattern("yyyy.MM"));
```

历史导入、更新、重试和补偿都使用同一原始创建时间，不能用当前处理时间替代。若源字段是无时区的 MySQL DATETIME，须先明确业务时区。

#### 5.1.3 第三步：直接写入目标月份索引
##### 5.1.3.1 更新消息先于新增消息到达时如何处理？

如果更新操作比新增操作先到达 ES，当前方案仍可处理，前提是更新使用 Index API 写入完整文档，并且自动创建配置、模板和权限均满足要求。ES 不按消息在 MySQL 中属于 INSERT 还是 UPDATE 决定是否建索引，而是按实际写入请求处理。

处理顺序如下：

1. 应用根据不可变的原始 `create_time` 定位月份索引。
2. 月份索引不存在时，ES 在允许自动创建的前提下创建索引并应用模板；索引存在但文档不存在时，Index API 直接创建该文档。
3. 更新消息携带较新的业务版本，例如版本 `2`，先写入完整文档。
4. 新增消息随后携带较旧版本，例如版本 `1`，在同一物理索引、同一 `_id` 下会被 `version_type=external` 拒绝，消费服务应将其识别为过期消息，不能把所有版本冲突都当作成功。

如果使用 [Update API](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-update.html) 做局部更新：

- 文档存在时，更新 `doc` 中的字段；
- 文档不存在且配置了 `upsert` 时，使用 `upsert` 内容创建文档；
- 未配置 `upsert` 时，更新失败。

示例：

```json
{
  "doc": {
    "version": 2
  },
  "upsert": {
    "consumeId": "1001",
    "version": 2
  }
}
```

当前项目主链路使用 Index API 写入完整文档，`upsert` 只是 Update API 的补充方案。若月份索引已经因保留期清理而删除，过期消息也可能触发重建，因此写入前仍需检查月份是否允许重建。

##### 5.1.3.2 写入请求

向计算出的月份索引发送 Index 请求。请求参数中的 `version` 用于外部版本比较，文档字段中的 `version` 保存同一业务版本：

```http
PUT /records-2026.10/_doc/1001?version=1&version_type=external
{
  "create_time": "2026-10-15T02:00:00Z",
  "version": 1
}
```

##### 5.1.3.3 自动创建需要哪些前提？

目标月份索引不存在时，需满足以下条件：

1. **自动创建配置**：`action.auto_create_index` 的有效规则允许该索引名，例如允许 `records-*`。
2. **账号权限**：写入账号具备自动创建索引和写入文档所需权限；模板包含读别名时，还须核对创建过程中附带别名所需的权限。
3. **模板与字段**：提前配置的模板正确匹配且最终生效，文档字段符合 Mapping。

满足上述条件后，ES 创建索引，应用模板中的 Mapping、索引配置和 `records-read` 别名，再写入文档。

##### 5.1.3.4 写入后如何判断版本和搜索可见性？

请求参数中的 `version` 与文档字段中的业务版本应保持一致。`version_type=external` 在同一物理索引、同一 `_id` 内只接受更高版本；重复或过期请求可能返回版本冲突，须按消费服务的幂等规则处理，不能无条件当成成功。

文档经过 refresh（刷新）后才对搜索可见；写入成功不等于立即可搜索，是否同步等待刷新由请求策略决定。[来源 8](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)

##### 5.1.3.5 应用账号权限

应用账号至少需要创建索引和写文档权限；带别名自动创建时还需核对别名授权：

```json
{
  "indices": [
    {
      "names": ["records-*"],
      "privileges": [
        "create_index",
        "create",
        "index"
      ]
    }
  ]
}
```

模板会附带 `records-read` 别名，使用 `create_index` 创建带别名索引时，还需核对新索引与别名上的 `manage` 权限要求；若不希望应用持有该管理权限，可评估由部署账号预建索引，具体授权方式待验证。[来源 7](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/security-privileges.html#privileges-list-indices)、[来源 8](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)

上述示例按不执行文档级删除的索引级删除方案省略 `delete` 权限，ILM 整索引删除权限需另行核验。如果消费服务还需要查询数据，再增加 `read` 权限。索引模板管理权限应单独交给部署或运维账号，不建议直接授予应用账号。

## 6 月份索引何时进入 cold，历史回放期间如何处理？

**结论**：已确认的时间目标是所属自然月结束后满 180 天，冷热迁移不改变物理索引名。时间条件与历史写入是否结束是两个不同问题，实际 ILM 年龄基准和执行衔接仍待实现验证。

7 天修改窗口尚未确认为硬限制，不能据此把旧索引永久设置为只读。以下封存和迁移资格流程仍是暂定方案，不能当作已确认业务限制或 ILM 自动提供的能力。

### 6.1 历史回放期间，如何衔接校验与迁移？（暂定方案）

历史回放与校验补偿可能并发进行，因此“当前数据一致”不代表该月份已停止写入，不能直接作为迁移依据。

暂定采用以下流程：

1. **持续校验与补偿**：校验任务按既定范围对比新库新表与 ES，发现缺失或字段差异时执行兜底补偿，并按原始 `create_time` 定位月份索引。
2. **月份封存**：由历史回放或业务协调流程明确该自然月不再继续写入；封存前不得授予 ILM 迁移资格。封存的具体状态、触发时点和禁止写入方式尚待确认。
3. **封存后最终一致性检查**：封存后再执行一次最终校验；只有新库新表与 ES 一致、未完成补偿已处理且没有新的写入时，才记录“可迁移”资格。该检查点和并发控制方案尚待实现验证。
4. **ILM 执行迁移**：同时满足“自然月结束后满 180 天”和“已取得可迁移资格”后，才允许 ILM 将索引迁移到 cold；业务任务不直接执行迁移动作。
5. **异常与重放保护**：校验失败、补偿未完成或封存后又发现差异时，撤销或暂停迁移资格；过期月份重放须先检查索引生命周期和月份状态，防止误建或误写已清理索引。

该流程尚待确认与验证，重点是回放结束的权威信号、封存与补偿的并发控制，以及迁移资格和 ILM 的衔接。

## 7 为什么采用整索引删除，什么时候可以删除？

### 7.1 业务前提：区分撤销与保留期清理

MySQL 仅清理创建时间超过 5 年的数据，清理边界精确到日，项目不存在业务提前物理删除；本文沿用原文已经确认的物理删除范围和按日保留期限。撤销通过新增撤销记录表达，业务类型为“撤销”（`BS0013`）。项目材料明确说明校验通过后生成撤销订单，成功后更新原交易状态和撤销订单状态，因此撤销仍可能产生新增和更新事件。[来源 1](</D:/000/sources/eas/000/000_E账通_项目介绍.md:180>)、[来源 2](</D:/000/sources/eas/000/000_消费_原内容.md:1096>)

### 7.2 哪些变更继续同步，哪些数据由整索引删除？

基于上述业务规则，已确认采用以下方案：

- 新增、更新：继续通过 Canal、RocketMQ 同步到 ES。
- 保留期清理产生的 DELETE：消费链路识别后跳过 ES 文档级删除。
- ES 历史数据：由索引生命周期管理机制按索引所属数据时间范围删除整个自然月索引，不逐条校验文档的 `create_time`。

这样可以减少对 cold 层历史索引的逐条删除操作。DELETE 在哪一层过滤、是否等待 MySQL 实际清理完成，以及 ILM 如何协调执行仍需落实；如果在消费服务过滤，仍须完成同一消息中其他事件及必要状态的处理，才能确认整条消息。

### 7.3 为什么必须等整个月份过期？

MySQL 按天清理，ES 按月分索引，因此不能直接使用相同的删除粒度。以下假设 MySQL 当天清理的是“当天零点减 5 年”之前的数据，日期边界均按统一业务时区计算：

| 日期 | MySQL 清理边界 | ES 对 `records-2021.10` 的处理 |
|---|---|---|
| 2026-10-15 | 清理 2021-10-15 零点之前的数据 | 保留，月内还有未过期数据 |
| 2026-11-01 | 清理 2021-11-01 零点之前的数据 | 整个月份达到删除条件 |

ES 可以暂时多保留过期数据，但不能提前删除保留范围内的数据。后端查询条件负责屏蔽多保留的数据，`records-read` 读别名本身不会自动过滤最近 5 年。

## 8 ES 删除是否需要等待 MySQL 实际清理完成？

**结论**：整个月份过期是删除资格的时间条件，但是否还要等待 MySQL 实际清理完成，尚待确认。

“ES 删除范围不能比 MySQL 大”需要明确比较依据：

- 以保留期限为准：该月份所有数据均满足 MySQL 删除条件，ES 即可删除。
- 以实际清理进度为准：必须确认 MySQL 已完成该月份清理，ES 才能删除。

ILM 无法感知 MySQL 清理任务是否失败或延迟。若采用第二种保证，需要增加清理完成状态检查，由协调任务确认后允许 ES 删除，不能只依赖固定时间配置。

## 9 如何把生命周期目标转换为 ILM 时间配置？

项目使用自然月索引，不使用 rollover。原有 cold 目标是“所属自然月结束后满 180 天”，与“索引创建后 180 天”不同；月末边界取统一业务时区下次月 1 日零点。

ILM 的 `min_age` 使用固定时长，`d` 表示天，`m` 表示分钟；不能用 `6M`、`5y` 直接表达自然月、自然年。[来源 3](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/common-options.html#time-units)

无 rollover 时，ILM 年龄通常从索引创建时间计算，也可以通过 `index.lifecycle.origination_date` 指定起算时间。各阶段的 `min_age` 相对于该年龄基准，不是进入上一阶段后重新计时。[来源 4](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/ilm-settings.html)

cold 和 delete 必须一起核对起算时间。历史月份补建索引时，不能直接把补建时间当成数据所属月份的时间。

## 10 按月分索引后，查询范围和分页如何控制？

**结论**：时间范围限制检索范围，每页大小限制返回成本，`search_after` 降低深分页成本；读别名不会自动过滤最近五年。

### 10.1 查询范围与分页方案

前端查询必须携带时间范围，后端按统一业务时区，将查询起止日期限制在最近 5 年内，且**单次最大查询跨度为 1 个月**。除时间范围外，其他筛选条件非必填。分页采用 `search_after`，每页最多返回 100 条。这些查询约束沿用本文已确认设计；“最多 31 个自然日”的具体计算口径仍待确认。

一个月作为初始设计上限，不因月增约 600 万条就直接收紧到 7 天。该上限是已确认的设计决策，实际性能尚需压测验证。“一个月”的具体计算口径仍待确认；建议采用“最多 31 个自然日，起止日期均计入”，例如 3 月 1 日至 3 月 31 日允许，3 月 1 日至 4 月 1 日不允许，但该口径目前不能作为已确定的校验规则。

### 10.2 限制查询跨度：控制检索范围

限制查询跨度的作用，按重要程度从高到低排列：

1. 控制可能参与检索的数据范围，约束宽范围查询的资源开销。
2. 在能按时间定位索引或跳过无关分片时，减少分片查询、通信与结果合并成本。
3. 减少资源争用，帮助稳定并发查询的响应时间。

例如，按日均新增约 20 万条估算，包含消费、撤销和退货，30 天约有 600 万条。**这是时间范围内的记录量，不代表每次查询必须扫描全部 600 万条。**

时间字段有可用于范围查询的索引时，可以帮助排除范围外的数据；范围内仍需处理多少候选记录，取决于查询条件、排序优化、分片布局和总数统计等因素。仅有字段索引，不能保证每次只处理 100 条，也不等于已经配置了 Elasticsearch 的索引排序（写入时按指定字段组织文档）。[来源 10](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/index-modules-index-sorting.html)

当前 [013 Mapping 设计](<013_ES Mapping 设计.md>) 使用 `tradeTime` 做时间范围查询和主排序，`consumeId` 配置为 `index: false`、`doc_values: true`，通过 Doc Values（按文档存储的列式字段值）支持次排序，并非检索索引。原始 `create_time` 用于月份定位，与查询时间字段的对应关系及实际部署配置仍待核验。

### 10.3 限制每页大小：控制单次返回成本

每页最多返回 100 条的作用，按重要程度从高到低排列：

1. 控制单次完整文档读取、响应组装和网络传输成本。
2. 控制排序候选结果的维护与合并成本。
3. 控制前端渲染量。

举一个假设性示例：10 个分片参与普通排序查询，且匹配记录充足。每页 100 条时，各分片通常最多提供 100 条候选，协调节点再从最多约 1,000 条候选中选出全局前 100 条。候选主要包含排序值和文档标识，并非全部完整文档；选出结果后，再读取需要返回的文档内容。

这里的候选数量不代表各分片只需检查 100 条记录，查询阶段的实际工作量仍取决于执行条件。

### 10.4 `search_after`：降低深分页成本

`search_after` 使用上一页末条记录的排序值作为下一页的起点，避免像较大的 `from + size` 那样，维护并合并大量前序结果。[来源 9](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/paginate-search-results.html)

例如，第一页返回前 100 条；第二页保持查询条件和排序不变，使用上一页末条记录的完整排序值获取后续 100 条。只看三页最多返回 300 条，但每页仍需执行查询。

当前方案按 `tradeTime DESC, consumeId DESC` 排序，要求 `consumeId` 单值、非空且全局唯一，以唯一确定记录顺序。按 [019 查询验收文档](<019_ES 验收与查询切换.md>)，当前方案不使用 PIT（时间点一致性视图），翻页期间数据变化可能造成重复或遗漏。

### 10.5 性能验证：覆盖最宽松的查询条件

上线前重点压测“只填时间、不填其他条件”的一个月范围查询，覆盖首屏、后续翻页和预期并发场景。结合响应时间、资源占用及总数统计方式，验证一个月上限是否满足要求。本文未核验线上索引配置或执行压测。

同目录历史整合稿 `999_003_原内容_修订版.md` 与 `999_003_原内容_修订版_v2.md` 中的“暂定最多 7 天”是旧口径；本次查询上限以本文一个月的已确认设计为准，不将其与尚待确认的“7 天修改窗口”混淆。

## 11 方案落地前，还需要确认和验证什么？

### 11.1 待确认前提与验证范围

- 确认业务时区、`create_time` 列名与类型、按日清理边界及 5 年日期计算规则；验证原始创建时间经过历史导入、Canal 和 MQ 后仍保持一致。
- 7 天修改窗口尚未确认为硬限制，最大积压、重试、恢复和补偿时间仍待核验，不能据此永久设置旧索引只读。
- cold 按所属自然月结束后满 180 天计算；ILM 年龄基准和调度尚待验证，历史月份补建不能直接按补建时间重新计时。
- 历史数据写入与一致性校验可能并发进行；“新表与 ES 一致”不等同于该月份已停止写入。暂定采用“月份封存→封存后最终一致性检查→授予 ILM 迁移资格→由 ILM 执行迁移”的流程，具体封存时点、资格状态和并发控制待确认并验证。

- 明确 DELETE 过滤位置、MySQL 清理进度与 ES 删除的协调方式；并发版本、重试及过期消息重放仍待验证。
- 一个月的计算口径待确认；“最多 31 个自然日，起止日期均计入”只是建议。核对创建时间与查询时间字段的对应关系、实际 Mapping 和排序配置；压测仅填时间的一个月首屏、后续翻页及预期并发。

### 11.2 配置落实顺序与关联文档边界
