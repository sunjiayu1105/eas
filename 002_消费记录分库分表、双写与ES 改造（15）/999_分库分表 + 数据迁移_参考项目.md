**最值得先看：FlockDB + Gizzard**

Gizzard 的 README 明确描述了这种迁移方式：

1. 旧分片 A 正常提供服务。
2. 增加新分片 A′，先设置为只接收写入，不承担查询。
3. 通过复制路由，将业务写操作发送到两边。
4. 后台把旧分片的历史数据复制到新分片。
5. 新分片数据未补齐期间，查询仍由旧分片承担。

参考：[Gizzard：Winged migrations](https://github.com/twitter-archive/gizzard#winged-migrations)。

FlockDB 则提供了具体的后台比较、修复代码：

- [Copy.scala，第 64～79 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/jobs/Copy.scala#L64-L79)：分批读取多个分片。
- [第 99～110 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/jobs/Copy.scala#L99-L110)：比较同一条记录的 `updatedAt`，选择较新的记录，收集缺失或较旧的数据。
- [第 116～122 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/jobs/Copy.scala#L116-L122)：写入差异记录，继续处理后续批次。

例如，两个分片都有记录 S1，A 的更新时间为 100，A′ 为 90，任务会选择 A 的记录补到 A′。**它依据更新时间挑选较新记录，并不是无条件以旧库为准。**

还要注意：它要求写操作具备幂等性和可交换性，并使用失败队列重试，因此不能直接替代你当前“不重试失败业务写入、交给下轮校验修正”的方案。
