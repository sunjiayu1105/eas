# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

项目已确认采用“应用层双写＋在线历史迁移”总体顺序，最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**阅读说明**

各小点按业务处理顺序排列，并保留重要程度标识；分别列出参考文章方案、参考文章方案存在的问题、已确认方案和待确认方案。版本逻辑集中在 1.1，缺失记录处理在 1.4，迁移扫描在第 2 部分，校验修数在第 3 部分。本文的故障和并发示例均为分析推演，未经运行验证。

## 1. 业务双写

### 1.1 高：双写、失败补偿与历史迁移的版本维护

#### 1.1.1 参考文章方案

**通过更新时间判断数据新旧**：参考文章使用 `gmt_modified` 等更新时间字段判断迁移数据的新旧，没有明确要求为旧表新增 `version` 字段，也没有展开系统内所有写入口的统一改造。参考来源定位：[更新时间比较（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

#### 1.1.2 参考文章方案存在的问题

更新时间精度不足时，可能无法区分同一条记录的多次变更。以下保留两种不同判断条件的风险，不能合并为同一场景。

**时间戳相同不能判断数据新旧**：文章允许较晚或相等的更新时间覆盖，但没有说明时间精度不足、不同变更具有相同时间戳时如何排序。以下假设时间只保存到秒，不代表已核实当前项目字段精度。参考来源定位：[更新时间覆盖规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**允许相等时间覆盖，可能覆盖新数据**：

1. `10:00:00.100`：旧表插入金额 **100**，双写新表成功。
2. `10:00:00.200`：迁移任务读取旧表金额 **100**，尚未写入新表。
3. `10:00:00.300`：业务将旧表金额更新为 **200**，双写新表成功。
4. `10:00:00.400`：迁移任务准备将金额 **100** 的旧快照写入新表。
5. 由于时间只保存到秒，旧快照和新表记录的更新时间都是 `10:00:00`。
6. 如果允许时间相等时覆盖，迁移就会把新表金额从 **200** 改回 **100**。

这是对文章允许相等时间覆盖规则的风险推演。参考来源定位：[允许相等时间覆盖（第 89 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

**改用严格大于，又可能拒绝同步真实变更**：

1. 同一秒内先插入金额 100，双写成功。
2. 旧表金额更新为 200，但新表更新失败。
3. 两边时间都保存为同一秒，金额却不同。
4. 校验发现差异，但若只允许严格较晚的来源时间覆盖，就会拒绝修复。

严格大于是对比用的假设方案，不是文章采用的规则；不能仅以时间相等认定内容一致。参考来源定位：[文章的时间比较规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

#### 1.1.3 已确认方案

**按四个场景维护版本**：旧表新增 `version` 字段，并排查业务代码、定时任务、批处理和脚本等写入口。以下是项目自行决定的版本维护方案，参考文章没有直接给出这些版本规则；所有示例均为时序推演，未经数据库运行验证。

**双写旧表：业务更新时递增**

旧表历史记录及新增记录的 `version` 初始化为 `1`。业务更新时，业务字段与 `version = version + 1` 在同一条 SQL 中执行；事务回滚时一起回滚。这样才能让旧表版本随业务变更推进，而不是仅依赖更新时间区分变更。

**技术实现：单条 SQL 原子更新**

以下按 MySQL 8.0.33、InnoDB 事务表说明。表名和字段名为示意，命名参数由应用绑定；实际事务边界以项目实现为准，示例未经运行验证。

```sql
-- 旧表业务字段和版本一起更新，避免两次独立提交只完成一部分。
UPDATE consume_record_source
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no;
```

InnoDB 执行 UPDATE 时会对命中的记录加排他锁，协调并发写入；字段修改与版本递增在事务中一起提交或回滚。由数据库执行自增，也避免应用先读版本再把“旧版本加一”写回时丢失版本递增。但这条 SQL 没有检查调用方读取的版本，不能阻止应用基于过期业务数据覆盖当前金额，不能仅因为有 `version + 1` 就称为乐观锁。

**解决的问题一：业务字段已提交，版本却没有更新**

1. 旧表金额为 **100**、版本 **1**，假设应用把金额更新和版本递增拆成两次独立提交。
2. 第一条 SQL 将金额改为 **200**，提交成功。
3. 第二条 SQL 执行前应用退出，版本仍为 **1**，无法用版本识别这次金额变更。
4. 改为同一条 SQL 后，金额与版本一起提交；事务回滚时二者一起回滚，不会留下这类部分提交状态。

这里的前提是“两次独立提交”。两条 SQL 如果放在同一个事务中，并在失败时整体回滚，也能保证一起提交或回滚；单条 SQL 让这两个动作直接绑定。

**解决的问题二：应用计算版本后写回，可能丢失一次递增**

1. 请求 A、B 都读取旧表版本 **1**，各自在应用中计算得到 **2**。
2. A 将业务字段和固定版本 **2** 写入并提交。
3. B 也将业务字段和固定版本 **2** 写入并提交；两次更新成功，版本却只增加了 **1**。
4. 若两次更新都由数据库执行 `version = version + 1`，B 等待 A 提交后基于当前版本 **2** 递增到 **3**。

该方式解决的是丢失版本递增，不保证业务字段没有被过期请求覆盖；业务字段的冲突保护见下方乐观锁示例。

**技术对比：乐观锁还需要预期版本条件**

乐观锁是在写入时检查数据是否仍是读取时的版本，版本相同才更新。以下仅用于解释机制，旧表是否增加该条件尚未确认；后文新表业务更新已采用这一方式。

```sql
-- expected_version 来自本次读取的同一条旧表记录，而不是新表版本。
UPDATE consume_record_source
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

**解决的问题：拒绝基于过期业务数据的覆盖**

1. 请求 A、B 都读取金额 **100**、版本 **1**，分别准备将金额改为 **200**、**300**。
2. A 使用 `expected_version = 1` 更新成功，金额变为 **200**、版本变为 **2**。
3. 若 B 不检查版本，就会直接将金额覆盖为 **300**，无法发现自己基于过期状态操作；加上版本条件后，B 的版本 **1** 不再匹配，更新影响 **0 行**。
4. 应用需要区分记录不存在与版本冲突；如何重读、重算或返回冲突由业务规则决定，不能直接把旧请求的预期版本改成 **2** 后继续覆盖。

乐观锁的版本检查和写入在同一条 SQL 中执行，但数据库内部仍会加锁，不代表 UPDATE 完全不使用锁。它只保护对应记录的条件更新，不会让旧表和新表的两次写入成为同一个原子操作。

**旧表版本变化示例**

1. 旧表金额为 **100**、版本 **1**。
2. 业务将金额更新为 **200**，同时将版本递增为 **2**。
3. 事务提交后，旧表为金额 **200**、版本 **2**；若事务回滚，仍为金额 **100**、版本 **1**。
4. 旧表事务提交成功后，再尝试写新表。

**双写新表：检查新表预期版本，再递增**

更新已有新表记录前，读取其当前版本作为 `expected_version`，在同一条 SQL 中检查版本、修改业务字段并递增版本。这样可以复用最终切换后的新表业务更新逻辑，并拒绝基于过期新表版本执行的更新。以下表名及金额字段为示意，命名参数由应用绑定；实际执行前按 `merchantNo` 路由到目标分片。

```sql
UPDATE consume_record_target
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

1. 新表金额为 **100**、版本 **5**，本次读取到预期版本 **5**。
2. 更新 SQL 检查 `version = 5`。
3. 条件满足，金额改为 **200**，版本递增为 **6**。
4. 如果其他请求已改变版本，本次更新不生效，不能直接覆盖。

历史记录尚未迁入时，不在双写链路立即补建，等待迁移回填。本段 SQL 只用于已有记录的业务更新。

**新表更新失败补偿：沿用原预期版本**

补偿保留原业务数据及首次更新新表时使用的 `expected_version`，执行相同的条件更新；不能重新读取最新版本，将同一次操作当作新更新。不是所有重试都不递增，而是只有原更新尚未成功且条件仍满足时，重试才完成那一次递增。

**第一次没有提交**

1. 首次更新使用预期版本 **5**，但事务未提交。
2. 新表仍为版本 **5**，期间也没有其他更新。
3. 补偿仍使用预期版本 **5**，成功后递增为 **6**。

**第一次已提交，只是响应丢失**

1. 首次更新已成功，新表版本变为 **6**。
2. 补偿仍使用原预期版本 **5**。
3. 条件不成立，不会再次递增为 **7**。

这可以阻止同一预期版本的重复更新，前提是版本没有被重置或重复使用。影响 0 行也可能由其他并发修改造成，不能直接认定为补偿成功，具体复核和失败处理仍待确认。新增、删除的补偿不能直接套用这条 UPDATE SQL。

**历史迁移：沿用旧表快照版本，不额外递增**

迁移读取同一次旧表快照中的业务数据和 `version`，一起写入新表。新表不存在记录时，插入来源数据及版本；已有记录时，按当前约定使用 `version <= :incoming_version` 条件更新，成功后保存来源版本，不执行 `version + 1`。迁移只是复制业务状态，不应额外产生一次业务版本。

1. 迁移读取旧表金额 **300**、版本 **3**。
2. 新表不存在对应记录。
3. 迁移按新表规则生成 `consumeId`，插入金额 **300**、版本 **3**。
4. 不把版本重新设为 **1**，也不因迁移将版本递增为 **4**。

**解决的问题：避免把旧业务数据配上新版本**

1. 假设迁移通过两次不共享同一快照的查询分别读取金额和版本：第一次读到旧表金额 **100**，当时版本为 **1**。
2. 业务随后将旧表更新为金额 **200**、版本 **2**。
3. 迁移第二次单独读取版本，得到 **2**，可能错误地组装出“金额 **100**、版本 **2**”。
4. 若将金额和版本从同一次记录快照中读取，就会得到“100、1”或“200、2”，不会拼接出上述不存在的业务状态。

同一快照只保证来源数据与版本配对正确；读取后又发生业务修改的问题，仍受本节后面的跨表版本比较及并发修复边界限制。

**SQL 示例：直接按来源版本条件更新**：以下按照项目 MySQL 8.0.33 说明，表名 `consume_record_target` 和字段 `amount` 为示意名称；实际执行前按 `merchantNo` 路由到目标分片。`:参数名` 表示应用绑定参数，不是可以直接在 MySQL 客户端执行的脚本。应用无需先查询新表版本，数据库在同一条 SQL 中完成版本判断和写入。

```sql
-- incoming_amount 与 incoming_version 必须来自同一次旧表记录快照。
-- 仅更新已有记录，不修改已有 consume_id，也不在此处补建缺失记录。
UPDATE consume_record_target
SET amount = :incoming_amount,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version <= :incoming_version;
```

**版本判断：按版本数值决定是否更新**：新表版本小于或等于待写入版本时允许更新，并保存来源版本；新表版本更大时不更新。相同版本允许重复写入，前提是同一业务记录的同一来源版本对应同一份业务数据。

**使用 `<=` 的原因：允许修复同版本的数据差异**

例如：

1. 旧表为金额 **200**、`version = 6`。
2. 同步代码因字段映射错误，将新表写成金额 **100**、`version = 6`。
3. 修复代码后，校验发现两边版本相同，但金额不同。
4. 若使用 `<`，由于 `6 < 6` 不成立，无法修正。
5. 使用 `<=`，允许按旧表数据将新表金额修正为 **200**，版本仍为 **6**。

同版本不同内容属于异常，需要记录差异并排查原因。该例为故障推演，未经实践验证。来源版本更新返回 0 行时，还需区分记录缺失、版本条件不满足，以及驱动按实际变更行数返回的内容未变化，不能仅凭行数判断修复成功。

**异议与分析：场景划分不等于跨表版本可比较**

以上四个场景的设计选择已确认，但新表独立递增后，版本不一定与旧表业务版本一一对应。例如：

1. 新旧表最初都是金额 **100**、版本 **1**。
2. 旧表更新为金额 **200**、版本 **2**，迁移读取这份快照；本次新表双写失败。
3. 旧表再次更新为金额 **300**、版本 **3**。
4. 本次新表双写读取自身版本 **1**，检查后更新为金额 **300**、版本 **2**。
5. 迁移随后写入金额 **200**、来源版本 **2**，`2 <= 2` 成立，仍可能覆盖新表中较新的业务数据。

因此，不能把跨表 `<=` 条件描述为已保证不发生旧数据覆盖；校验兜底的并发修复及最终收敛仍需验证。本节记录已确认的处理方式和已知风险，不将其视为完整正确性已经得到证明。

**已确认处理：保留 `<=`，由一致性校验修正旧快照覆盖**

迁移和校验更新已有新表记录时，继续使用 `version <= :incoming_version`。项目接受上述旧快照覆盖造成的暂时不一致，在旧表仍为可信数据源的阶段，由一致性校验比较业务字段、发现差异并按旧表数据修正，而不是仅凭版本相同认定数据一致。

接续上述例子，假设本次修复期间没有新的业务变更：

1. 迁移覆盖后，新表为金额 **200**、版本 **2**；旧表为金额 **300**、版本 **3**。
2. 校验读取旧表金额 **300**、版本 **3**，比较业务字段后发现金额不同。
3. 新表满足 `2 <= 3`，校验将其修正为金额 **300**、版本 **3**。
4. 修复后再次校验，确认本条记录一致；若期间又发生业务变更，则继续复核和处理差异。

该方案以最终一致为目标，不保证差异即时消失。上述示例仅说明当前时序下的修复路径，不证明所有并发场景都能收敛；校验覆盖、修复失败处理及切换条件仍按相关待确认项细化。本处理由项目自行决定，没有直接参考来源，也没有实践验证。

### 1.2 高：上线顺序与双写开关

#### 1.2.1 参考文章方案

**先双写、再迁移和校验，最后灰度切换**：先升级服务开启应用层双写，再迁移历史数据；迁移和一致性校验完成后，先灰度切查询，再灰度切写入；新库稳定运行后关闭旧库双写。参考来源定位：[服务升级与双写（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)、[历史数据迁移（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)、[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[流量切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

#### 1.2.2 参考文章方案存在的问题

文章给出了总体顺序，但没有把每个阶段的进入条件、完成条件和失败处置定义清楚。例如，迁移任务已经跑完一遍但仍有失败消息未重试，或者校验刚完成后又出现双写失败，此时直接进入灰度切读可能把未追平的新表暴露给查询。

#### 1.2.3 已确认方案

**先双写、后迁移，再校验与切换**：开启应用层双写 → 双写稳定后迁移历史数据 → 一致性校验 → 灰度切查询 → 灰度切写入 → 稳定且满足收尾条件后停止旧表写入。双写异常处理见 [1.3](#13-高旧表主写与新表失败处理)，迁移完成判定见 [2.4](#24-高增量补齐与迁移完成判定)，切换及回退见第 4 部分。

**解决的问题：避免先迁移、后双写留下变更缺口**

1. 假设尚未开启双写，迁移已经把流水 S1 的金额 **100** 写入新表。
2. 业务随后把旧表 S1 改为 **200**；此时没有双写，新表仍为 **100**。
3. 之后才开启双写，并不会自动补发此前这次变更。
4. 先开启双写，能让迁移期间的业务变更进入新表写入及失败处理流程；它不保证每次都成功，剩余差异仍需补偿和校验处理。

#### 1.2.4 待确认方案

- 各阶段尚未细化的进入条件；
- 各阶段的观察指标；
- 各阶段的失败处置。迁移完成、校验验收及切换回退的具体事项分别在对应章节确认。

### 1.3 高：旧表主写与新表失败处理

#### 1.3.1 参考文章方案

**旧库主写、新库补偿**：旧库写入是主流程；新库失败不阻断业务，记录、告警并补偿。参考来源定位：[应用层双写伪代码与失败处理（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

#### 1.3.2 参考文章方案存在的问题

文章没有明确补偿消息的可靠投递、重复消费和最终失败处理。例如，旧表提交成功后新表写入超时，补偿消息又因生产确认丢失，最终旧表有数据、新表没有数据；即使消息成功投递，重复重试也可能重复插入。文章只说明需要补偿，没有给出这些边界的处理规则。

#### 1.3.3 已确认方案

先确认旧表事务提交成功，再尝试写新表；新表写入失败不影响接口成功，但必须打印错误日志并发送告警，同时将失败数据放入消息队列等待重试。双写出现严重异常时暂停迁移，继续由旧表承接业务。重试仍失败时，由人工排查并修复双写代码、配置或运行问题；数据本身不由人工直接修改，最终仍由一致性校验任务发现差异并修正。

**解决的问题：隔离新表故障，并为失败写入保留后续处理路径**

1. 旧表已成功提交流水 S1，新表写入因连接故障失败。
2. 若把新表失败直接作为接口失败返回，调用方会收到失败，但旧表中的业务实际上已经完成。
3. 当前方案按旧表提交结果返回，记录新表失败并告警；在失败消息可靠入队的前提下，后续由补偿重试处理。
4. 若补偿仍未修复差异，则由校验发现并修正，人工排查故障原因。消息可靠投递等未定边界仍不能视为已解决。

**人工直接修数的并发风险**

1. 旧表写入成功，新表 INSERT 失败。
2. 人工读取旧表金额 100，准备修数。
3. 业务把旧表金额更新为 200。
4. 人工脚本仍把金额 100 写入新表，产生差异。

因此人工负责修复原因，数据交给程序校验修正；程序修数本身的并发边界见 3.1。

#### 1.3.4 待确认方案

- 消息队列的重试次数；
- 消息队列的重试间隔；
- 失败状态记录方式；
- 告警升级规则；
- 人工介入时机；
- 重试最终失败后由一致性校验任务修正数据的具体衔接方式。

### 1.4 高：历史数据未迁入时的双写处理与一致性修正

#### 1.4.1 参考文章方案

#### 1.4.2 参考文章方案存在的问题

文章没有说明历史迁移尚未回填某条记录时，`UPDATE` 或 `DELETE` 影响 0 行后是否立即补建、重试或等待迁移。例如，旧表更新成功而新表尚无记录，业务更新返回成功；如果后续迁移只写入旧快照，就会把更新前数据带入新表。

#### 1.4.3 已确认方案

**缺失记录等待历史迁移回填**：历史迁移尚未回填某条记录时，业务仍以旧表为准。新表 `UPDATE`、`DELETE` 影响 0 行不阻断旧表业务，也不在双写链路中立即补建；由历史迁移任务按既定流程回填新表。新表可以暂时缺失记录或保留旧快照，后续由一致性校验任务发现并修正。迁移完成并通过一致性校验前，新表不能作为最终可信数据源。

以下两个例子均假设新表记录尚未迁入，是并发时序推演，未进行运行验证。

**更新前快照写入新表**

1. 迁移任务读取旧表，得到金额 **100**，暂未写入新表。
2. 业务将旧表金额更新为 **200**，提交成功。
3. 业务尝试更新新表，但记录尚未迁入，`UPDATE` 影响 **0 行**。
4. 迁移任务将之前读取的金额 **100** 插入新表。
5. 此时旧表金额为 **200**，新表金额为 **100**，由一致性校验任务发现差异并修正。

**删除前快照重新插入新表**

1. 迁移任务读取旧表中的流水 **S1**，暂未写入新表。
2. 业务删除旧表中的 **S1**，提交成功。
3. 业务尝试删除新表中的 **S1**，但记录尚未迁入，`DELETE` 影响 **0 行**。
4. 迁移任务将之前读取的 **S1** 插入新表。
5. 此时旧表已无 **S1**，新表却存在 **S1**，由一致性校验任务发现多余记录并删除。

#### 1.4.4 待确认方案

- 本点核心处理已确认；校验修数期间的重读、重试和失败处理见 [3.1](#31-高新旧表差异校验与修复)。

### 1.5 中：双写记录的身份关联

### 3.1 高：新旧表差异校验与修复

#### 3.1.1 参考文章方案

2. 业务将旧表和新表都更新为 300。

#### 3.1.3 已确认方案

**程序修数并保留排查记录**：校验发现差异后，先记录差异和修数前快照，再由程序按照旧表最新数据修正新表；对已有记录的更新采用 [1.1](#11-高双写失败补偿与历史迁移的版本维护) 中的来源版本条件；单条记录的插入、更新或删除在新表事务中完成。该事务及 UPDATE 条件不能单独证明跨库读写、缺失记录和删除修复的并发安全。无论修数成功还是失败，都记录修数原因、执行结果、重试次数和最终状态；修数完成后再次校验。该方案由项目自行决定，没有直接参考来源，也没有实践验证。

**解决的问题：避免修数掩盖写入缺陷，并确认修复结果**

1. 字段映射错误使旧表金额为 **200**、新表为 **100**，两边版本都是 **6**。
2. 程序修正后两边暂时一致；如果没有保留修数前差异，只看当前数据可能无法追查写入缺陷。
3. 记录原值、差异原因及执行结果，可以为人工定位映射问题保留依据；具体修数条件见 [1.1](#11-高双写失败补偿与历史迁移的版本维护) 的同版本修复示例。
4. 修数后业务又产生一次写入，如果缺陷未修好，差异可能再次出现；重新校验用于发现仍存在或新产生的差异，不能把一次修数成功当作写入链路已验证正确。

### 3.2 中：历史迁移数据的 ES 覆盖校验

#### 3.2.1 参考文章方案

**切换前校验新旧库**：文章要求切换前进行全量或多轮新旧库校验，没有讨论 ES 历史覆盖；本点是项目扩展。参考来源定位：[数据一致性校验与切换前置条件（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

#### 3.2.2 参考文章方案存在的问题

新旧库校验不能证明项目的 ES 校验已覆盖历史导入。例如，先推进新表到 ES 校验的 `update_time` 游标，再导入更新时间早于游标的历史记录，该校验可能扫不到这条记录。这里说的是更新时间扫描校验，不是 Binlog 正常同步；日志同步起点另见 4.3。

#### 3.2.3 已确认方案

暂不确认历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖，只保留风险记录。

#### 3.2.4 待确认方案

- 历史 `update_time` 早于已推进游标时的全量复核、游标调整或其他覆盖方式。

## 4. 流量切换与回滚预案

### 4.1 高：查询和写入切换

#### 4.1.1 参考文章方案

**先读后写、逐步灰度**：先灰度切读，再灰度切写，稳定后关闭双写。参考来源定位：[流量灰度切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

#### 4.1.2 参考文章方案存在的问题

文章没有明确切写期间请求如何路由及旧表、新表双写何时停止。例如，部分请求已经写入新表，仍有旧服务只写旧表；此时读流量继续扩大，可能出现同一业务记录在两套库中的结果不一致。

#### 4.1.3 已确认方案

采用 1.2 节的整体流程：先灰度切查询，稳定后再逐步切写入；全部流量切换并稳定、满足收尾条件后停止旧表写入，改为新表单写。

**解决的问题：降低一次性切换暴露全部流量的风险**

1. 假设新表数据校验通过，但查询链路在某类请求上存在慢查询。
2. 若一次切换全部读流量，这类请求会同时暴露给新查询链路，影响范围可能迅速扩大。
3. 先切部分查询，可在扩大流量前观察到慢查询，暂停后续扩大并排查原因；此时还没有同时推进写入切换，较容易区分读链路与切写问题。
4. 小流量正常不代表全量一定正常；仍需分阶段观察，具体阈值及回退方式按待确认项继续细化。

#### 4.1.4 待确认方案

- 灰度比例；
- 观察指标阈值；
- 灰度切写期间的实际写入方式；
- 旧表依赖完成的具体检查步骤；
- 收尾条件的具体检查步骤。

### 4.2 高：回滚预案

#### 4.2.1 参考文章方案

**各阶段保留旧库回退**：各灰度阶段通过配置中心保留切回旧库的方案；文章没有展开停写旧库后的回补机制。参考来源定位：[灰度阶段回滚预案（第 123 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:123>)。

#### 4.2.2 参考文章方案存在的问题

文章没有明确写流量已经切到新库后，旧库是否仍保持可回退状态，以及回退时如何处理两边新增变更。例如，新库已接收一段时间的写入后直接切回旧库，若没有回补这段时间的新数据，旧库会缺少回退期间产生的记录。

#### 4.2.3 已确认方案

暂不确认最终停止旧表写入后的回退边界。

#### 4.2.4 待确认方案

- 查询切换期间的回退方式；
- 写入切换后的回退方式；
- 数据回补要求；
- 回退截止点。

### 4.3 中：ES 同步起点与日志保留

#### 4.3.1 参考文章方案

**监控双写并多轮校验**：文章检查清单要求监控双写成功率、新库延迟并执行多轮校验，未给出 ES、Binlog 起点或日志保留方案；这些属于项目扩展。参考来源定位：[执行检查清单（第 143 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:143>)。

#### 4.3.2 参考文章方案存在的问题

文章没有明确同步起点、日志保留下限和恢复后的追赶方式。例如，迁移期间同步日志保留不足，消费者故障恢复时起点已经过期，历史写入无法重新读取，即使新表已有数据，ES 仍可能缺少对应数据。

#### 4.3.3 已确认方案

旧表到新表不采用 Binlog 同步路线；新表到 ES 的既有 Binlog、Canal 和 RocketMQ 链路保留。
