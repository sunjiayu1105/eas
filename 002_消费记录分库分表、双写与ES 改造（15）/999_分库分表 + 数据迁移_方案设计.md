# 999_分库分表 + 数据迁移_方案设计

## 1 参考文章方案总结

### 1.1 双写迁移方案

参考文章的双写迁移方案是：旧表继续承接线上业务，业务变更同时写入旧表和新表；历史数据再通过迁移程序分批导入新表；迁移完成后执行一致性校验，再按功能或流量逐步切换查询和写入，最后停止旧表写入并下线双写逻辑。

这种方案适合不能长时间停机的系统，但会增加业务写入入口改造、双写失败补偿、历史迁移与实时写入并发处理以及一致性校验的复杂度。

### 1.2 基于 Binlog 的同步双写方案

基于 Binlog 的方案以旧表作为业务写入来源，业务代码不直接写新表。系统通过 Binlog 捕获旧表的 INSERT、UPDATE、DELETE 等变更，由 Canal、消息队列和同步服务将变更应用到新库新表；历史数据仍由迁移程序分批回填。

完整流程是：记录 Binlog 起始位点，启动订阅和消费链路，分批回填历史数据，同时持续消费增量变更；回填过程中按版本或 `update_time` 合并历史数据和实时变更，处理消息重复、乱序、积压、失败重试和删除事件；待历史回填完成且增量追平后，执行新旧表校验，再灰度切换查询和写入。

Binlog 方案不能替代历史数据回填，也不能自动保证一致性。项目仍需验证 Canal 位点恢复、消息顺序、目标库分片路由、删除事件、失败重试和补偿能力。

## 2 推荐方案

### 2.1 推荐理由

项目约有 `7,000 万 × 5 年 ≈ 3.5 亿条`历史数据。停服后一次性迁移虽然实现简单，但实际停机时间取决于数据量、单行大小、索引维护、数据库负载和校验时间，可能需要数小时。项目还存在旧表依赖，查询和写入不能一次性全部切换到新表。

相比业务代码双写，Binlog 方案可以让旧表继续作为唯一业务写入入口，避免把“新表记录不存在时如何处理”等迁移特殊逻辑散落到业务代码中。项目已经使用 Canal 和 RocketMQ 技术栈，具备评估 Binlog 增量同步方案的基础。

因此，项目优先采用 Binlog 增量同步方案更合适，但这不是无条件确定的生产结论。正式实施前仍需通过接近生产规模的迁移演练，确认实际吞吐量、消息积压、失败恢复和可接受的切换窗口。

### 2.2 推荐方案

推荐采用：**旧表单写 + 历史数据分批回填 + Binlog 增量同步 + 增量追平 + 一致性校验 + 灰度切换**。

1. 业务继续只写旧表，旧表作为迁移期间的业务基准。
2. 记录迁移开始时的 Binlog 位点，启动 Canal 订阅、消息投递和新表同步服务。
3. 由独立 Java 迁移程序分批读取旧表历史数据，按新表分片规则写入目标库和目标表；迁移程序支持限流、断点、幂等、失败重试和暂停恢复。
4. Binlog 同步服务持续处理旧表的新增、更新、删除、撤销和退货变更。同步时按 `serialNo` 定位记录，并根据 `version` 或 `update_time` 防止旧的历史回填覆盖实时变更。
5. 对重复消息、乱序消息、消费失败、消息积压和删除事件建立明确的重试、补偿和告警机制；删除事件需要保留足以阻止历史回填重新插入的数据状态。
6. 历史回填完成后继续消费 Binlog，直到积压清零并完成增量追平。
7. 执行新旧表的数量、主键、业务字段、删除状态和版本校验。发现差异时先定位根因、修复代码或配置并验证，再订正新表数据。
8. 校验通过后按功能或流量灰度切换查询，观察结果、错误率、延迟和慢查询；查询稳定后再切换写入，最后停止旧表写入并下线旧表相关逻辑。

该方案的关键前提是：Binlog 链路、历史回填程序和新表写入服务必须具备可恢复、可追踪和幂等能力；实际迁移速度、消息处理能力和失败恢复效果仍需通过演练确认。
