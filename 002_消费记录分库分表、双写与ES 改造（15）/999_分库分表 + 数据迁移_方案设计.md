# 999_分库分表 + 数据迁移_方案设计

## 1 方案概述

项目采用“分批历史回填、短暂停服追平、校验后上线双写、Canal 同步 ES”的迁移方案。

迁移期间先不在业务代码中执行旧表到新表的双写，避免历史数据尚未完成回填时，业务更新链路出现新表缺失记录的特殊处理。历史数据基本迁移完成后，利用短暂停服窗口追平最后变更，确认新表数据完整后再上线业务双写。

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准：Java 8、Spring Boot 2.7.18、MySQL 8.0.33、Elasticsearch 7.17.15、Alibaba Canal Server 1.1.7 和 RocketMQ 5.2.0。

## 2 分批回填历史数据

### 2.1 迁移程序和执行方式

历史数据迁移可以使用存储过程分批导入，也可以使用独立 Java 迁移程序。存储过程适用于新旧表在同一 MySQL 实例或具备直接访问能力、迁移逻辑简单且能够控制批量提交的场景；如果新库是独立 MySQL 实例，或者需要复杂的断点、限流、告警和失败恢复，使用独立 Java 迁移程序。

迁移任务需要支持启动、暂停、恢复和终止，并持久化记录迁移范围、当前游标、已完成批次、成功数量、失败数量、最近错误和任务状态。不能只使用内存变量记录进度。

### 2.2 分批读取和游标

迁移程序按 `update_time + 主键` 组合游标读取旧表数据：

```sql
SELECT ...
FROM old_table
WHERE update_time > :lastUpdateTime
   OR (update_time = :lastUpdateTime AND id > :lastId)
ORDER BY update_time, id
LIMIT :batchSize;
```

每批大小和并发度通过接近生产规模的演练确定。组合游标可以避免仅按时间分页时因相同时间数据过多而漏数或重复处理。每批全部成功后才推进断点；批次中途失败时，从上一个安全断点重新执行，依靠幂等逻辑处理已写入的数据。

### 2.3 写入新库新表

每条数据写入新库新表时：

1. 根据 `merchantNo` 计算目标库和目标表；
2. 根据 `serialNo` 关联新旧记录；
3. 新表不存在时插入；
4. 新表已有较新数据时不能被旧迁移数据覆盖；
5. 重复执行同一批次时结果必须幂等。

迁移程序需要比较 `update_time` 或项目确定的版本字段，避免迁移过程覆盖其他来源写入的新数据。每批独立提交，控制旧表读取压力、新库写入压力、数据库连接数和整体迁移速度。

## 3 短暂停服追平最后变更

当历史数据基本回填完成后，执行短暂停服追平：

1. 停止接口、Job、批处理和脚本的写入；
2. 确认旧表不再发生业务变更，并记录停服时间 `T1`；
3. 扫描迁移开始时间 `T0` 到 `T1` 期间发生过更新的数据；
4. 将这些最新数据补齐到新库新表；
5. 处理新增、更新、撤销、退货和删除记录；
6. 完成数量、主键和关键业务字段校验。

如果旧表存在物理删除，仅依靠 `update_time` 无法发现被删除的数据，必须提前保留删除日志、删除事件或 Binlog 记录。没有删除依据时，不能声称历史数据已经完整追平。

## 4 上线业务双写

历史回填和停服追平完成并通过校验后，再上线旧表和新表业务双写：

- 旧表写入继续作为主业务流程；
- 新表写入失败时记录日志、告警并进入持久化补偿流程；
- 双写覆盖新增、更新、删除、撤销和退货；
- 新表写入按照分片规则和幂等规则执行；
- 新表 `version` 或项目确定的版本字段必须按统一规则生成和更新。

此时新表已经具备完整历史数据，正常业务写入不需要再判断“新表记录是否因历史迁移尚未完成而缺失”。

## 5 新旧表增量校验

双写上线后，持续校验旧表和新表的增量数据，覆盖 INSERT、UPDATE、DELETE、撤销和退货记录。校验内容包括数量、主键、业务字段、删除状态和版本信息。

发现差异时，必须遵循：定位根因 → 修复代码、配置或迁移逻辑 → 验证写入链路 → 手工订正新表 → 再次校验。代码或配置问题没有修复并验证前，不得直接修改新表数据。

校验任务需要记录数据范围、差异数量、根因、修复结果和复核结果，并支持失败重试、积压告警和人工补偿。

## 6 Canal 同步新表到 ES

新表业务双写稳定后，由 Canal 监听新表对应的 MySQL Binlog，将新表的新增、更新和删除事件投递到 RocketMQ，再由消费服务写入 ES。Canal 消费配置必须明确过滤范围，避免同时消费旧表和新表事件造成重复同步。

同步服务需要处理消息重复、乱序、消费失败、积压和位点恢复，并按照新表 `version` 控制 ES 写入顺序，避免旧事件覆盖新数据。撤销、退货和删除事件必须映射为明确的 ES 更新或删除动作。

如果历史回填产生的 INSERT 不会被现有 Canal 链路消费，还需要单独执行 ES 历史数据回放；不能仅凭 Canal 已启动就认为历史数据已经进入 ES。

## 7 新表与 ES 增量校验

Canal 同步稳定后，持续校验新表和 ES 的增量数据，至少检查记录数量、业务主键、关键字段、版本和删除状态。发现不一致时，先区分新表数据问题、Binlog 消费问题、消息处理问题和 ES 写入问题，再修复对应链路并执行补偿。

新表与 ES 连续达到项目确认的无差异观察周期后，才能逐步扩大 ES 查询流量。查询稳定后，再关闭旧表查询和旧表写入，完成最终切换。

## 8 迁移完成条件和待确认事项

只有同时满足以下条件，才能认为迁移完成：

- 历史数据已全部回填；
- 停服期间的最后变更已追平；
- 新旧表校验无未处理差异；
- 业务双写稳定运行；
- Canal 位点、消息积压、失败重试和 ES 同步均正常；
- 新表与 ES 达到确认的无差异观察周期；
- 查询和写入灰度切换完成并通过回归验证。

仍需通过演练确认：存储过程或 Java 迁移程序的实际吞吐量、每批数据量、并发度、`update_time` 索引、物理删除记录方式、Canal 对历史回填数据的消费行为、ES 历史数据回放方式以及失败恢复时间。
