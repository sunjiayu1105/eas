# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

如果采用文章中的“应用层双写＋在线历史迁移”主方案，项目最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**一、按重要程度组织的改造点**

以下改造点均围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)整理。重要程度表示该问题对业务连续性、数据正确性和上线门禁的影响，不表示实现工作量。

### 一、高：业务连续性与双写主链路

#### 1.1 高：上线顺序

**参考文章方案**：先升级服务开启应用层双写，再迁移历史数据；完成一致性校验后灰度切读、灰度切写，稳定后关闭双写。

**已确认方案**：采用“先升级服务开启应用层双写 → 在线迁移历史数据 → 完成一致性校验 → 灰度切换查询和写入 → 稳定后关闭双写”。

**待确认方案**：各阶段的进入条件、完成条件、观察指标、失败处置和回退边界。

#### 1.2 高：旧表优先与新表失败处理

**参考文章方案**：旧库写入是主流程；新库写入失败不阻断业务，但需要记录、告警和补偿。

**已确认方案**：业务请求先写旧表，确认旧表事务提交成功后再尝试写新表；新表失败不影响接口成功，由一致性校验发现差异。暂不引入自动补偿队列，先定位原因，修复代码或配置并验证，再由人工或独立流程修正数据。

**待确认方案**：重试任务、重试状态、告警和自动修复机制。

#### 1.3 高：新表缺失时的更新和删除

**参考文章方案**：文章说明业务层同时改造 `Insert`、`Update`、`Delete`，但没有明确新表记录不存在时 `UPDATE` 或 `DELETE` 影响 0 行的处理。

**已确认方案**：新表 `UPDATE`、`DELETE` 影响 0 行时暂不阻断旧表业务；由后续同步或迁移流程补齐，并由一致性校验发现和修正差异。

**待确认方案**：新表缺失时是否立即补建完整记录，以及业务双写与迁移任务之间的原子并发保护。

#### 1.4 高：短暂不一致与数据修正

**参考文章方案**：允许新库暂时落后，通过补偿和多轮校验收敛。

**已确认方案**：允许新表暂时缺失或出现旧快照；迁移任务读取更新前或删除前快照并写入新表造成的脏数据，交由一致性校验发现并修正。校验完成并确认差异修复前，新表不能作为最终可信数据源。

**待确认方案**：差异修复时限、告警阈值和修复责任分工。

### 二、高：历史迁移与数据身份

#### 2.1 高：在线历史迁移

**参考文章方案**：迁移工具分批扫描旧库，按主键或时间切片，支持幂等重跑；通过后续校验处理并发更新、删除和遗漏。

**已确认方案**：历史迁移从旧表读取记录，按 `merchantNo` 计算新表目标分片，使用全局唯一的 `serialNo` 关联新旧记录，按新表规则重新生成 `consumeId`，不复用旧表 `id`，历史迁移的 `version` 初始化为 `1`。

**待确认方案**：扫描范围、断点续传、限速、重跑的具体幂等写入方式、异常恢复和并发防护。

#### 2.2 高：主键、业务关联和路由

**参考文章方案**：根据业务主键或分片键确定新库目标位置，确保重复迁移和双写不会产生错误身份。

**已确认方案**：旧表和新表使用各自独立的主键；新表 `consumeId` 按 `003_分库分表.md` 规则生成。`serialNo` 是新旧表之间的全局业务关联标识；业务双写首次创建新表记录时生成 `consumeId`，后续更新、同步和重试通过 `serialNo` 定位并沿用已有的 `consumeId`；`merchantNo` 用于计算固定分片。

**待确认方案**：额外映射表、来源顺序字段和其他唯一约束。

#### 2.3 高：`version` 维护

**参考文章方案**：文章强调按更新时间判断新旧，但没有给出当前项目的 `version` 规则。

**已确认方案**：只有新表增加 `version`。历史迁移初始化为 `1`；新表更新时在同一条 SQL 中修改业务字段并执行 `version = version + 1`。数据库更新 SQL 失败时重试相同 SQL，成功执行时才递增版本；同步消息重试沿用原消息数据和版本，不再次修改新表 `version`。

**待确认方案**：日常新增记录的 `version` 初始值、字段类型和取值范围；迁移重跑的完整幂等规则。

### 三、高：一致性校验与切换门禁

#### 3.1 高：旧表与新表一致性校验

**参考文章方案**：分片并行生成指纹或逐行比对，多轮修复后再次校验，通常以旧库为修复依据。

**已确认方案**：一致性校验作为查询和写入切换的核心门禁，必须发现新表缺失、旧快照、错误新增和删除差异；发现差异后先定位原因并修复，再重新校验。

**待确认方案**：历史扫描与增量采集的具体衔接、字段比较清单、延迟复核和最终验收范围。

#### 3.2 高：历史迁移数据到 ES 的覆盖

**参考文章方案**：迁移完成后进行全量或多轮校验，确认历史数据进入新链路后再切换流量。

**已确认方案**：暂不确认历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖，只保留风险记录。

**待确认方案**：历史 `update_time` 早于已推进游标时的覆盖方式，包括全量复核、调整游标或其他机制。

#### 3.3 高：查询、写入切换与回退

**参考文章方案**：先灰度切读，再灰度切写，稳定后关闭双写并保留回滚预案。

**已确认方案**：暂不确认查询灰度、停止旧表写入、切换新表单写以及最终回退边界。

**待确认方案**：切换顺序、观察指标、旧表依赖完成条件和停止旧表写入后的回退方式。

### 四、中：同步链路与 ES

#### 4.1 中：ES 同步起点与日志保留

**参考文章方案**：双写和历史迁移产生的数据都进入后续同步链路，并关注同步延迟和日志保留，避免起点过晚漏数。

**已确认方案**：旧表到新表不采用 Binlog 同步路线；新表到 ES 的既有 Binlog、Canal 和 RocketMQ 链路保留。

**待确认方案**：ES 同步起点是否覆盖最早双写和历史导入、在线迁移期间的 binlog 保留量、追赶能力和恢复边界。

### 五、低：补充设计项

#### 5.1 低：自动补偿与运维细节

**参考文章方案**：失败进入补偿队列，自动重试并告警。

**已确认方案**：暂不引入自动补偿队列；失败先由一致性校验发现，再定位、修复和独立修正。

**待确认方案**：重试任务、状态记录、告警阈值、自动修复和责任分工。

#### 5.2 低：额外身份辅助字段

**参考文章方案**：文章未明确要求额外映射表或来源顺序字段。

**已确认方案**：暂不增加额外映射表、来源顺序字段或其他辅助身份字段。

**待确认方案**：后续是否因幂等、并发或审计需要增加这些字段。

**本文后续补齐项**：本文已排除旧表到新表的 Binlog 同步路线；后续需将应用层双写、在线历史迁移、校验、切换和恢复的具体规则补齐，形成完整方案。

**二、哪些既定规则不应因采用文章而直接改变**

现有的 **2 个实例、32 个分片、按 `merchantNo` 路由、`consumeId` 主键、`serialNo` 关联**可以继续作为设计基础；文章本身不构成修改这些规则的依据。

“切查询前连续 1 个月无差异”“全部旧表依赖切换后再次连续 3 个月无差异”的条件，也不能直接替换成文章中的 24 小时、两三轮或一周。ES 月份索引、生命周期管理及当前 DELETE 校验边界同样不能顺带改变。

**核对结果与边界**

本次完成了参考文章、现行迁移和双写方案、两类校验、同步起点及切换文档的静态对照，并按 self-check 复核了上述清单。还发现部分旧资料仍将新表与 ES 校验描述为 Binlog 任务，而当前 015 已明确采用更新时间扫描，后续整理时需要统一。

本次将旧表到新表的 Binlog 同步路线明确为不采用，并将改造内容按重要程度分组；每个小改造点均包含“参考文章方案、已确认方案、待确认方案”。已核对新表到 ES 同步及独立校验的既有职责不变。未运行数据库、消息同步或迁移测试；此前检索未找到可用于确认业务实现的 Java 源码、项目构建文件及对应配置，因此上述仍是**方案和功能模块层面的修改清单，尚不能落实到具体业务类、方法和已完成状态**。

**已确认规则**

- 旧表到新表不采用 Binlog 同步路线，删除该候选路线的修改清单。
- 业务双写采用旧表优先；旧表提交成功后尝试写新表，新表失败暂不影响接口成功；失败补偿机制暂不确认，先通过一致性校验发现差异，再定位原因并修复。
- 新表 `UPDATE` 影响 0 行时暂不视为接口失败；业务双写与迁移读取旧快照并发时可能产生脏数据，该问题依赖一致性校验发现并修正；迁移任务具体并发防护方式暂不确认。该处理没有直接参考来源，也没有实践验证。
- 旧表删除成功后尝试删除新表，新表 `DELETE` 影响 0 行时暂不视为接口失败；迁移任务将删除前快照写回新表的问题依赖一致性校验发现并修正；项目不采用删除时间点或删除标记机制。该处理没有直接参考来源，也没有实践验证。
- 业务双写允许新表暂时缺失或出现旧快照；一致性校验完成并确认差异已修复前，新表不能作为最终可信数据源。该方案允许短暂不一致，没有直接参考来源，也没有实践验证。
- 新表写入失败后暂不引入自动补偿队列；由一致性校验发现差异，定位原因并修复代码或配置后，再人工或独立流程修正数据；重试任务、重试状态、告警和自动修复机制暂不确认。
- 历史迁移按 `merchantNo` 路由，重新生成新表 `consumeId`，历史迁移的 `version` 初始化为 `1`；迁移重跑不能随意重置已有 `version`，具体幂等写入方式仍需验证。
- 旧表和新表使用各自独立的主键；`serialNo` 用于关联新旧记录，业务双写首次创建新表记录时按新表规则生成 `consumeId`，后续通过 `serialNo` 定位并沿用已有 `consumeId`。
- 新表更新时业务字段和 `version = version + 1` 在同一条 SQL 中执行；数据库更新 SQL 失败时重试相同 SQL，成功执行时才递增 `version`；同步消息重试沿用原消息数据和版本，不再次修改新表 `version`。
- 一致性校验是查询和写入切换的核心门禁；校验发现差异后必须先定位原因、修复并重新校验，校验未完成或差异未修复前不得将新表作为最终可信数据源。
- 历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖暂不确认；历史 `update_time` 早于已推进游标而造成漏同步或漏校验的风险需要保留。
- 查询灰度、停止旧表写入、切换新表单写以及停止旧表写入后的回退边界暂不确认。
- 本次不操作数据库及运行环境。
- 每个改造点的“项目已确认方案”放在“项目需要修改的地方”之后；未确认的内容留空。
