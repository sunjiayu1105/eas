# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

如果采用文章中的“应用层双写＋在线历史迁移”主方案，项目最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**一、需要修改的核心位置：参考文章方案与项目调整**

以下每个改造点均先概括[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)的做法，再说明项目需要修改的内容。参考文章是通用方案来源，不等于当前项目已经实现或确认的规则。

### 1. 上线顺序与阶段门禁

**参考文章方案**：先升级服务开启应用层双写，再迁移历史数据；完成多轮一致性校验后，先灰度切读、再灰度切写，稳定后关闭双写。

**项目需要修改的地方**：`002_改造计划`不能继续采用“停写迁移完成后再开启双写”的顺序，应调整为本节项目已确认的在线迁移顺序，并补充每个阶段的进入条件、完成条件、观察指标、失败处置和回退边界。

**项目已确认方案**：采用与参考文章相同的方案，即“先升级服务开启应用层双写 → 在线迁移历史数据 → 完成一致性校验 → 灰度切换查询和写入 → 稳定后关闭双写”。

### 2. 业务双写

**参考文章方案**：旧库写入是主流程；新库写入失败不阻断业务，但必须记录日志、告警并进入补偿处理，双写通过开关控制。

**项目需要修改的地方**：`004_分库分表_业务双写`保留“旧表提交成功后尝试新表”的规则，补充历史尚未导入时的更新、删除处理，以及业务双写与迁移任务同时处理同一记录时的并发规则。文章中的补偿队列只能作为待评估方案，不能直接写成已实现能力。

**项目已确认方案**：旧表优先，旧表提交成功后尝试写新表；新表写入失败暂不影响接口成功。新表 `UPDATE` 影响 0 行时暂不视为接口失败，后续依赖旧表到新表的同步或迁移流程补齐；如果迁移任务读取了更新前的旧快照并将其写入新表，依赖下一步数据一致性校验发现并修正。该处理没有直接参考来源，也没有实践验证；失败补偿机制仍暂不确认。

### 3. 在线历史迁移

**参考文章方案**：使用迁移工具分批扫描旧库，按主键或时间切片，支持幂等重跑；写入前比较更新时间，避免旧数据覆盖新数据，并通过后续校验处理删除和遗漏。

**项目需要修改的地方**：`999_历史迁移与数据库验收`需要从停写导入手册调整为在线迁移流程，补充扫描范围、分批导入、断点续传、限速、重跑、异常恢复、并发更新和删除防回插规则，并重新明确 DBA 执行职责与开发提供规则的边界。

**项目已确认方案**：

### 4. 记录身份、路由与并发写入

**参考文章方案**：迁移和双写根据业务主键或分片键确定目标库表，确保同一条业务在新库中具有稳定身份和路由。

**项目需要修改的地方**：`003_分库分表`和 `999_数据模型`继续使用 `serialNo` 关联新旧记录，确保同一业务复用同一个 `consumeId`，防止迁移入口和双写入口分别生成主键。唯一约束、映射记录或来源顺序字段是否增加，仍需单独设计。

**项目已确认方案**：

### 5. 新旧表一致性校验

**参考文章方案**：按分片并行生成数据指纹，逐行或按范围比对，多轮修复后再次校验，通常以旧库数据为修复依据。

**项目需要修改的地方**：`005_分库分表_新旧表一致性校验`需要重新设计历史扫描与增量采集的衔接，明确迁移期间全部变更的覆盖方式、暂未导入记录的处理和最终复核边界。抽样、总数或校验和一致不能单独作为全量通过依据。

**项目已确认方案**：

### 6. ES 同步起点与日志保留

**参考文章方案**：双写和历史迁移产生的数据都必须进入后续同步链路，迁移期间持续关注同步延迟和日志保留，避免起点过晚造成漏数。

**项目需要修改的地方**：`007_MySQL binlog 相关配置及 Canal 起点、恢复文档`需要保证 ES 同步起点覆盖最早双写和历史导入，并重新评估在线迁移期间的 binlog 日志量、保留范围和追赶能力。旧表到新表不采用文章中的 Binlog 同步路线；新表到 ES 的既有 Binlog 链路继续保留。

**项目已确认方案**：

### 7. 新表与 ES 的历史覆盖校验

**参考文章方案**：迁移完成后进行全量或多轮一致性校验，确认历史数据已进入新链路，再进入流量切换。

**项目需要修改的地方**：`015_新表与 ES 增量校验及扫描窗口文档`需要补充在线回填期间的历史覆盖保障。若后导入数据保留较早的 `update_time`，可能落在已推进游标的回看范围之外；需要增加迁移结束后的完整历史复核，或设计可证明覆盖全部回填记录的机制。

**项目已确认方案**：

### 8. 查询、写入切换与回滚

**参考文章方案**：先按比例灰度切读，观察稳定后再灰度切写；全部切换完成并稳定后关闭双写，同时保留配置开关和回滚预案。

**项目需要修改的地方**：`999_ES 验收与查询切换`需要分别定义业务查询切到新表、后台列表切到 ES、最终写入切到新表的条件、观察指标和回退边界。文章中的“24 小时观察”和“任何阶段一键回滚”不能直接替换项目已经确认的 1 个月、3 个月校验条件；写切换后旧表是否可回退也必须明确。

**项目已确认方案**：

**本文后续补齐项**：本文已排除旧表到新表的 Binlog 同步路线；后续需将应用层双写、在线历史迁移、校验、切换和恢复的具体规则补齐，形成完整方案。

**二、实现上最需要补齐的六个问题**

1. **新表还没有历史记录，业务更新怎么办？**  
    项目已确认新表 `UPDATE` 影响 0 行时暂不视为接口失败，后续依赖旧表到新表的同步或迁移流程补齐。若迁移任务读取了更新前的旧快照并将其写入新表，依赖下一步数据一致性校验发现并修正。参考文章没有直接给出这种处理方式，该方案也没有实践验证。
    
2. **历史数据和实时更新怎样避免相互覆盖？**  
    文章提出比较更新时间，但“先查询、再比较、再写入”存在并发窗口。判断条件需要在数据库写入时原子生效，并明确时间精度相同、请求乱序和重复执行时怎么办。项目现有新表 `version` 主要服务于 ES 同步，**仅递增它，并不能证明写进新表的业务内容就是最新状态**。
    
3. **如何防止迁移任务把已删除记录重新插回来？**  
    例如迁移任务刚读取旧记录，业务就删除了新旧两边，随后迁移任务再次插入新表。需要补充删除记录留存、变更重放或独立复核等机制。具体选择待确认，不能直接照搬文章中较模糊的“软删除时间点”。
    
4. **双写失败如何可靠恢复？**  
    当前 004 主要依赖独立校验发现差异，再定位原因和修复。若要采用文章的失败队列自动重试，需要增加任务可靠保存、幂等、重试状态、告警和恢复流程，并覆盖“旧表已提交、进程却在写新表或保存失败任务前退出”的缺口。自动修复还涉及已有“先定位原因，再手工订正”规则，不能直接替换。
    
5. **在线校验如何得出可信的完成结论？**  
    业务持续写入时，两次查询可能读到不同时间的状态。需要明确分批范围、延迟复核、变更覆盖和最终验收边界。指纹可以减少比对成本，但必须规范字段编码、空值、金额和时间；**抽样或校验和一致，不能单独证明全部记录完全一致**。
    
6. **切到新表写入后，还能否回旧表？**  
    只保留旧代码和查询开关不够。一旦旧表不再更新，它就会落后。如果要求写切换后仍可回退，必须设计新变更回补旧表及回退前校验；如果不提供这项能力，就要明确回退截止阶段。不能直接承诺文章所说的“任何阶段一键回滚”。
    

**三、哪些既定规则不应因采用文章而直接改变**

现有的 **2 个实例、32 个分片、按 `merchantNo` 路由、`consumeId` 主键、`serialNo` 关联**可以继续作为设计基础；文章本身不构成修改这些规则的依据。

“切查询前连续 1 个月无差异”“全部旧表依赖切换后再次连续 3 个月无差异”的条件，也不能直接替换成文章中的 24 小时、两三轮或一周。ES 月份索引、生命周期管理及当前 DELETE 校验边界同样不能顺带改变。

**核对结果与边界**

本次完成了参考文章、现行迁移和双写方案、两类校验、同步起点及切换文档的静态对照，并按 self-check 复核了上述清单。还发现部分旧资料仍将新表与 ES 校验描述为 Binlog 任务，而当前 015 已明确采用更新时间扫描，后续整理时需要统一。

本次将旧表到新表的 Binlog 同步路线明确为不采用，并为每个改造点新增“项目已确认方案”字段；已确认采用参考文章相同方案的第 1 项已填写，其余尚未确认的方案暂留空，且该字段均放在“项目需要修改的地方”之后。已核对新表到 ES 同步及独立校验的既有职责不变。未运行数据库、消息同步或迁移测试；此前检索未找到可用于确认业务实现的 Java 源码、项目构建文件及对应配置，因此上述仍是**方案和功能模块层面的修改清单，尚不能落实到具体业务类、方法和已完成状态**。

**已确认规则**

- 旧表到新表不采用 Binlog 同步路线，删除该候选路线的修改清单。
- 业务双写采用旧表优先；旧表提交成功后尝试写新表，新表失败暂不影响接口成功；失败补偿机制暂不确认，先通过一致性校验发现差异，再定位原因并修复。
- 新表 `UPDATE` 影响 0 行时暂不视为接口失败，后续依赖旧表到新表的同步或迁移流程补齐；更新前快照写入新表造成的脏数据依赖一致性校验发现并修正，该处理没有直接参考来源，也没有实践验证。
- 本次不操作数据库及运行环境。
- 每个改造点的“项目已确认方案”放在“项目需要修改的地方”之后；未确认的内容留空。
