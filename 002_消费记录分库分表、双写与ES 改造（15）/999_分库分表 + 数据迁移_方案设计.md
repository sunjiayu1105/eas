# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

项目采用“应用层双写＋在线历史迁移”：先完成旧表版本及全部写入口改造，再开启双写并启动历史迁移，两者并行运行，校验验收后逐步切换流量。双写必须先明确确认旧表提交成功，再尝试新表；新表失败由补偿和校验处理。切换为新表主写时，无需修改新表写入链路代码。完整上线顺序见 [004 2.1](<./004_分库分表_业务双写.md#21-高上线顺序与双写开关>)。

当前记录的是设计选择，尚不能保证所有差异都能自动收敛：新表版本超过旧表时的修复、删除差异覆盖、任务收尾及回退边界仍需确认。具体修改点按下方四个主题展开。

本文以[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)为参考，区分文章方案、项目已确认选择和待确认事项；方案确认不代表已实现或经过运行验证。

**阅读说明**

四个主题按业务处理顺序排列，各修改点保留重要程度和四项栏目；版本规则集中在 004 的 2.1，其余章节说明各阶段的执行流程和异常处理。每个场景先明确适用前提，再说明做法、示例及边界，跨节通过链接引用。本文示例均为分析推演，未经运行验证。

业务双写详细方案及关联规则已整合至 [004_分库分表_业务双写](<./004_分库分表_业务双写.md>)，本节只保留衔接概述与导航。

### 1.1 分期改造与不停机迁移的容量依据

003 的容量规划要求按完整年度新增量和历史 CAGR 预测保留窗口，当前保留窗口按 2022—2026 年逐年求和，不能用上一年度约 7,300 万条直接乘以 5 年。由于 2022—2025 年完整年度数据和已确认的历史 CAGR 尚未补齐，当前只能确认数据规模为数亿级，不能把估算写成实时数据库条数。

停机全量迁移的耗时取决于有效迁移吞吐，还要加上转换、校验、失败重试和故障排查时间。示例：假设待迁移 3 亿条、有效吞吐为每秒 1,000 条，仅读取和写入就约需 83 小时，约 3.5 天，尚未计算校验和重试；这个数字是假设示例，不是项目实测时长。停机期间业务不可用，任何批次失败都会继续延长维护窗口，因此不能承诺在固定窗口内完成。

采用在线双写后，旧表继续承接业务，历史迁移与线上写入并行进行；迁移耗时不占用停机窗口，待新表数据、一致性校验和链路验证完成后再切换流量。该安排解决的是数亿级数据迁移导致停机时间不可控的问题，具体双写、迁移和校验规则分别见本章后续章节。

完成旧表版本字段和全部写入口改造后开启双写；双写生效后即可迁移，两者并行。旧表提交成功后尝试新表，新表失败进入补偿，剩余差异交校验处理。历史记录尚未迁入时不在双写中立即补建。切换为新表主写时复用原新表写入链路。

## 3. 新旧表数据一致性校验

### 3.1 高：新旧表差异校验与修复

#### 3.1.1 参考文章方案

**分片并行比对并多轮复核**：分片并行生成指纹或逐行比对，多轮修复后再次校验。参考来源定位：[数据一致性校验工具（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[校验性能建议（第 131 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:131>)。

#### 3.1.2 参考文章方案存在的问题

文章没有明确校验字段范围、差异修正的并发条件和修数失败后的状态管理。

1. 校验读取旧表金额 200。
2. 业务将旧表和新表都更新为 300。
3. 修数脚本若仍无条件写回 200，就会再次制造差异。

#### 3.1.3 已确认方案

##### 3.1.3.1 校验范围与人工职责

**适用前提**：旧表仍为可信数据源。校验比较业务字段及版本，发现新表缺失、旧快照、错误新增和删除差异。程序负责修数，人工排查代码或配置，修数不必等待人工排查完成；切换验收前必须完成原因处理和复核，不能用修数成功代替写入链路正确性的验证。

**人工直接修数的并发风险**：

1. 旧表写入成功，新表 INSERT 失败。
2. 人工读取旧表金额 **100**，准备补建新表记录。
3. 业务将旧表金额更新为 **200**。
4. 人工仍按旧快照插入金额 **100**，再次产生差异。

程序修数便于统一留痕和复核，但也可能读到过期快照，不能仅因自动执行就认定并发安全。

##### 3.1.3.2 修复流程与结果留痕

1. 记录差异、修数原因及修数前快照，保留排查写入缺陷的依据。
2. 读取旧表同一快照中的业务数据与版本，在新表事务内插入、更新或删除单条记录。当前校验流程见 [008 一致性校验](<./008_分库分表_不停机数据迁移_新旧表一致性校验.md#21-校验范围数据指纹与差异修复>) 执行。
3. 记录执行结果、重试次数和最终状态。
4. 再次校验，确认差异是否消失；失败和并发变化的处理规则见本节待确认项。

这是项目自行决定的具体流程，没有直接参考来源，也没有实践验证；新表事务不能保证跨库读写或删除修复的并发安全。

##### 3.1.3.3 使用 `<=` 修复同版本差异

例如：

1. 旧表为金额 **200**、`version = 6`。
2. 同步代码因字段映射错误，将新表写成金额 **100**、`version = 6`。
3. 修复代码后，校验发现两边版本相同，但金额不同，记录修数前的金额和版本。
4. 若使用 `<`，由于 `6 < 6` 不成立，无法修正。
5. 使用 `<=`，允许按旧表数据将新表金额修正为 **200**，版本仍为 **6**。
6. 保留修复结果并再次校验；若后续写入又造成同类差异，就继续排查写入缺陷，不能因本次修数成功而判定链路正确。

同版本不同内容属于异常，需要记录差异并排查原因。该例为故障推演，未经实践验证。来源版本更新返回 0 行时，还需区分记录缺失、版本条件不满足，以及驱动按实际变更行数返回的内容未变化，不能仅凭行数判断修复成功。

##### 3.1.3.4 异议与分析：新表版本更大时无法按当前条件修复

以下假设两个请求在旧表按 A、B 顺序提交，但新表调用发生延迟；示例为未运行验证的时序推演。

1. 新旧表最初都是金额 **100**、版本 **1**。
2. 请求 A 将旧表更新为金额 **200**、版本 **2**，尚未执行新表更新。
3. 请求 B 将旧表更新为金额 **300**、版本 **3**，本次新表双写失败。
4. 迁移读取旧表当前快照，将新表更新为金额 **300**、版本 **3**。
5. A 恢复执行，读取新表自身版本 **3**，按原业务数据将金额更新为 **200**，版本递增到 **4**。
6. 校验发现旧表“300、3”与新表“200、4”不同，但 `4 <= 3` 不成立，无法按当前 SQL 修正。
7. 如果之后不再发生业务变更，继续执行同一校验和修复 SQL 仍会失败，不能认为重试即可自然收敛。

该例说明新表乐观锁只检查读取之后版本是否变化，不能识别延迟业务请求在旧表中的先后。保留 `<=` 的决定不变，但这一类差异需要另行确认处理方式，不能擅自删除版本条件或降低新表版本。

#### 3.1.4 待确认方案

- 字段比较清单；
- 最终验收范围。

**并发修复与复核**

- 校验读取旧表后发生业务变更时的重读规则；
- 版本变化后的重试与失败处理；
- 新表版本大于旧表且业务字段不同时，如何修复并避免覆盖并发业务更新；
- 延迟复核方式。

**失败处理与运行参数**

- 修数失败后的重试上限；
- 人工介入条件；
- 日志保存周期。

### 3.2 中：历史迁移数据的 ES 覆盖校验

#### 3.2.1 参考文章方案

**切换前校验新旧库**：文章要求切换前进行全量或多轮新旧库校验，没有讨论 ES 历史覆盖；本点是项目扩展。参考来源定位：[数据一致性校验与切换前置条件（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

#### 3.2.2 参考文章方案存在的问题

新旧库校验不能证明项目的 ES 校验已覆盖历史导入。例如，先推进新表到 ES 校验的 `update_time` 游标，再导入更新时间早于游标的历史记录，该校验可能扫不到这条记录。这里说的是更新时间扫描校验，不是 Binlog 正常同步；日志同步起点另见 4.3。

#### 3.2.3 已确认方案

历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖仍待确认；以下区分已存在的 ES 设计与本次迁移尚未验证的衔接。

**异议与分析：MySQL 同版本修数不能只依靠正常 ES 同步**

1. 新表错误金额 **100**、版本 **6**，已同步到 ES。
2. 新旧表校验按旧表将新表金额修正为 **200**，版本仍为 **6**。
3. 即使修复事件到达正常 ES 同步链路，`version_type=external` 也不会接受相同版本覆盖；ES 可能仍为金额 **100**。
4. 既有 ES 校验方案已规定同版本字段差异采用 `external_gte` 补偿，但前提是该校验实际扫描到修复后的记录。若修数未推进 `update_time`，记录又早于扫描窗口，就可能漏校验。

正常同步的版本规则见 [015 的外部版本写入（第 25 行）](<./015_ES改造_ES_索引设计、创建与写入.md:25>)；独立校验的同版本补偿见 [ES 自动补偿规则（第 19 行）](<./999_ES改造_ES_新表与 ES 增量校验_自动补偿、并发与恢复.md:19>)。这些是项目文档中的设计，不是参考文章 01_1 的方案，也不是运行证据。

#### 3.2.4 待确认方案

- 历史 `update_time` 早于已推进游标时的全量复核、游标调整或其他覆盖方式。
- 新旧表修数是否推进新表 `update_time`；
- 同版本修复如何被 ES 校验完整覆盖并验证。

## 4. 流量切换与回滚预案

### 4.1 高：查询和写入切换

#### 4.1.1 参考文章方案

**先读后写、逐步灰度**：先灰度切读，再灰度切写，稳定后关闭双写。参考来源定位：[流量灰度切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

#### 4.1.2 参考文章方案存在的问题

文章没有明确切写期间请求如何路由及旧表、新表双写何时停止。例如，部分请求已经写入新表，仍有旧服务只写旧表；此时读流量继续扩大，可能出现同一业务记录在两套库中的结果不一致。

#### 4.1.3 已确认方案

**查询切换**：旧表与新表、新表与 ES 的校验连续 1 个月无差异后，逐步切换查询；查询稳定后再逐步切写入。

**停止旧表写入**：全部旧表依赖切换完成后，两项校验再次连续 3 个月无差异，再停止旧表写入，改为新表单写。观察期间校验须持续覆盖应检查范围，不能将任务停滞当作无差异。项目依据：[004 双写收尾条件](<./004_分库分表_业务双写.md#5-业务双写边界与复核结果>)。这两个窗口是项目既定规则，不采用参考文章的示例时长替代。

双写阶段需复用最终的新表业务写入链路，切换为新表主写时无需修改该链路代码；切换控制方式及验收证据仍需细化。

**解决的问题：降低一次性切换暴露全部流量的风险**

1. 假设新表数据校验通过，但查询链路在某类请求上存在慢查询。
2. 若一次切换全部读流量，这类请求会同时暴露给新查询链路，影响范围可能迅速扩大。
3. 先切部分查询，可在扩大流量前观察到慢查询，暂停后续扩大并排查原因；此时还没有同时推进写入切换，较容易区分读链路与切写问题。
4. 小流量正常不代表全量一定正常；仍需分阶段观察，具体阈值及回退方式按待确认项继续细化。

#### 4.1.4 待确认方案

- 灰度比例；
- 观察指标阈值；
- 灰度切写期间的实际写入方式；
- 旧表依赖完成的具体检查步骤；
- 收尾条件的具体检查步骤。
- 旧表不再作为可信数据源前，如何停止旧表到新表的迁移、补偿与修数任务，并处理在途写入。
