# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

项目已确认采用“应用层双写＋在线历史迁移”总体顺序，最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**一、按四个主题组织的改造点**

各小点按业务处理顺序排列，并保留重要程度标识；分别列出参考文章方案、参考文章方案存在的问题、已确认方案和待确认方案。版本逻辑集中在 1.1，缺失记录处理在 1.4，迁移扫描在第 2 部分，校验修数在第 3 部分。本文的故障和并发示例均为分析推演，未经运行验证。

### 1. 业务双写

#### 1.1 高：双写、失败补偿与历史迁移的版本维护

**参考文章方案：通过更新时间判断数据新旧**：参考文章使用 `gmt_modified` 等更新时间字段判断迁移数据的新旧，没有明确要求为旧表新增 `version` 字段，也没有展开系统内所有写入口的统一改造。参考来源定位：[更新时间比较（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**参考文章方案存在的问题**：更新时间精度不足时，可能无法区分同一条记录的多次变更。以下保留两种不同判断条件的风险，不能合并为同一场景。

**时间戳相同不能判断数据新旧**：文章允许较晚或相等的更新时间覆盖，但没有说明时间精度不足、不同变更具有相同时间戳时如何排序。以下假设时间只保存到秒，不代表已核实当前项目字段精度。参考来源定位：[更新时间覆盖规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**允许相等时间覆盖，可能覆盖新数据**：

1. 10:00:00.100 插入金额 100，双写成功。
2. 10:00:00.200 迁移读取这条记录。
3. 10:00:00.300 业务把金额改为 200，双写也成功。
4. 10:00:00.400 迁移才写入旧快照。
5. 两份数据的时间都保存到秒，按相等时间允许覆盖，旧快照把新表金额从 200 改回 100。

这是对文章允许相等时间覆盖规则的风险推演。参考来源定位：[允许相等时间覆盖（第 89 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

**改用严格大于，又可能拒绝同步真实变更**：

1. 同一秒内先插入金额 100，双写成功。
2. 旧表金额更新为 200，但新表更新失败。
3. 两边时间都保存为同一秒，金额却不同。
4. 校验发现差异，但若只允许严格较晚的来源时间覆盖，就会拒绝修复。

严格大于是对比用的假设方案，不是文章采用的规则；不能仅以时间相等认定内容一致。参考来源定位：[文章的时间比较规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**已确认方案：按四个场景维护版本**：旧表新增 `version` 字段，并排查业务代码、定时任务、批处理和脚本等写入口。以下是项目自行决定的版本维护方案，参考文章没有直接给出这些版本规则；所有示例均为时序推演，未经数据库运行验证。

**双写旧表：业务更新时递增**

旧表历史记录及新增记录的 `version` 初始化为 `1`。业务更新时，业务字段与 `version = version + 1` 在同一条 SQL 中执行；事务回滚时一起回滚。这样才能让旧表版本随业务变更推进，而不是仅依赖更新时间区分变更。

1. 旧表金额为 **100**、版本 **1**。
2. 业务将金额更新为 **200**，同时将版本递增为 **2**。
3. 事务提交后，旧表为金额 **200**、版本 **2**；若事务回滚，仍为金额 **100**、版本 **1**。
4. 旧表事务提交成功后，再尝试写新表。

**双写新表：检查新表预期版本，再递增**

更新已有新表记录前，读取其当前版本作为 `expected_version`，在同一条 SQL 中检查版本、修改业务字段并递增版本。这样可以复用最终切换后的新表业务更新逻辑，并拒绝基于过期新表版本执行的更新。以下表名及金额字段为示意，命名参数由应用绑定；实际执行前按 `merchantNo` 路由到目标分片。

```sql
UPDATE consume_record_target
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

1. 新表金额为 **100**、版本 **5**，本次读取到预期版本 **5**。
2. 更新 SQL 检查 `version = 5`。
3. 条件满足，金额改为 **200**，版本递增为 **6**。
4. 如果其他请求已改变版本，本次更新不生效，不能直接覆盖。

历史记录尚未迁入时，不在双写链路立即补建，等待迁移回填。本段 SQL 只用于已有记录的业务更新。

**新表更新失败补偿：沿用原预期版本**

补偿保留原业务数据及首次更新新表时使用的 `expected_version`，执行相同的条件更新；不能重新读取最新版本，将同一次操作当作新更新。不是所有重试都不递增，而是只有原更新尚未成功且条件仍满足时，重试才完成那一次递增。

第一次没有提交：

1. 首次更新使用预期版本 **5**，但事务未提交。
2. 新表仍为版本 **5**，期间也没有其他更新。
3. 补偿仍使用预期版本 **5**，成功后递增为 **6**。

第一次已提交，只是响应丢失：

1. 首次更新已成功，新表版本变为 **6**。
2. 补偿仍使用原预期版本 **5**。
3. 条件不成立，不会再次递增为 **7**。

这可以阻止同一预期版本的重复更新，前提是版本没有被重置或重复使用。影响 0 行也可能由其他并发修改造成，不能直接认定为补偿成功，具体复核和失败处理仍待确认。新增、删除的补偿不能直接套用这条 UPDATE SQL。

**历史迁移：沿用旧表快照版本，不额外递增**

迁移读取同一次旧表快照中的业务数据和 `version`，一起写入新表。新表不存在记录时，插入来源数据及版本；已有记录时，按当前约定使用 `version <= :incoming_version` 条件更新，成功后保存来源版本，不执行 `version + 1`。迁移只是复制业务状态，不应额外产生一次业务版本。

1. 迁移读取旧表金额 **300**、版本 **3**。
2. 新表不存在对应记录。
3. 迁移按新表规则生成 `consumeId`，插入金额 **300**、版本 **3**。
4. 不把版本重新设为 **1**，也不因迁移将版本递增为 **4**。

**SQL 示例：直接按来源版本条件更新**：以下按照项目 MySQL 8.0.33 说明，表名 `consume_record_target` 和字段 `amount` 为示意名称；实际执行前按 `merchantNo` 路由到目标分片。`:参数名` 表示应用绑定参数，不是可以直接在 MySQL 客户端执行的脚本。应用无需先查询新表版本，数据库在同一条 SQL 中完成版本判断和写入。

```sql
-- incoming_amount 与 incoming_version 必须来自同一次旧表记录快照。
-- 仅更新已有记录，不修改已有 consume_id，也不在此处补建缺失记录。
UPDATE consume_record_target
SET amount = :incoming_amount,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version <= :incoming_version;
```

**版本判断：按版本数值决定是否更新**：新表版本小于或等于待写入版本时允许更新，并保存来源版本；新表版本更大时不更新。相同版本允许重复写入，前提是同一业务记录的同一来源版本对应同一份业务数据。

**使用 `<=` 的原因：允许修复同版本的数据差异**

例如：

1. 旧表为金额 **200**、`version = 6`。
2. 同步代码因字段映射错误，将新表写成金额 **100**、`version = 6`。
3. 修复代码后，校验发现两边版本相同，但金额不同。
4. 若使用 `<`，由于 `6 < 6` 不成立，无法修正。
5. 使用 `<=`，允许按旧表数据将新表金额修正为 **200**，版本仍为 **6**。

同版本不同内容属于异常，需要记录差异并排查原因。该例为故障推演，未经实践验证。来源版本更新返回 0 行时，还需区分记录缺失、版本条件不满足，以及驱动按实际变更行数返回的内容未变化，不能仅凭行数判断修复成功。

**异议与分析：场景划分不等于跨表版本可比较**

以上四个场景的设计选择已确认，但新表独立递增后，版本不一定与旧表业务版本一一对应。例如：

1. 新旧表最初都是金额 **100**、版本 **1**。
2. 旧表更新为金额 **200**、版本 **2**，迁移读取这份快照；本次新表双写失败。
3. 旧表再次更新为金额 **300**、版本 **3**。
4. 本次新表双写读取自身版本 **1**，检查后更新为金额 **300**、版本 **2**。
5. 迁移随后写入金额 **200**、来源版本 **2**，`2 <= 2` 成立，仍可能覆盖新表中较新的业务数据。

因此，不能把跨表 `<=` 条件描述为已保证不发生旧数据覆盖；校验兜底的并发修复及最终收敛仍需验证。本节记录已确认的处理方式和已知风险，不将其视为完整正确性已经得到证明。

**待确认方案**：

- `version` 字段的数据类型；
- `version` 字段的默认值和非空约束；
- 历史数据初始化和应用发布的先后步骤；
- 漏改写入口的排查清单及上线验收方式。

#### 1.2 高：上线顺序与双写开关

**参考文章方案：先双写、再迁移和校验，最后灰度切换**：先升级服务开启应用层双写，再迁移历史数据；迁移和一致性校验完成后，先灰度切查询，再灰度切写入；新库稳定运行后关闭旧库双写。参考来源定位：[服务升级与双写（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)、[历史数据迁移（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)、[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[流量切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

**参考文章方案存在的问题**：文章给出了总体顺序，但没有把每个阶段的进入条件、完成条件和失败处置定义清楚。例如，迁移任务已经跑完一遍但仍有失败消息未重试，或者校验刚完成后又出现双写失败，此时直接进入灰度切读可能把未追平的新表暴露给查询。

**已确认方案：先双写、后迁移，再校验与切换**：开启应用层双写 → 双写稳定后迁移历史数据 → 一致性校验 → 灰度切查询 → 灰度切写入 → 稳定且满足收尾条件后停止旧表写入。双写异常处理见 [1.3](#13-高旧表主写与新表失败处理)，迁移完成判定见 [2.4](#24-高增量补齐与迁移完成判定)，切换及回退见第 4 部分。

**待确认方案**：

- 各阶段尚未细化的进入条件；
- 各阶段的观察指标；
- 各阶段的失败处置。迁移完成、校验验收及切换回退的具体事项分别在对应章节确认。

#### 1.3 高：旧表主写与新表失败处理

**参考文章方案：旧库主写、新库补偿**：旧库写入是主流程；新库失败不阻断业务，记录、告警并补偿。参考来源定位：[应用层双写伪代码与失败处理（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**参考文章方案存在的问题**：文章没有明确补偿消息的可靠投递、重复消费和最终失败处理。例如，旧表提交成功后新表写入超时，补偿消息又因生产确认丢失，最终旧表有数据、新表没有数据；即使消息成功投递，重复重试也可能重复插入。文章只说明需要补偿，没有给出这些边界的处理规则。

**已确认方案**：先确认旧表事务提交成功，再尝试写新表；新表写入失败不影响接口成功，但必须打印错误日志并发送告警，同时将失败数据放入消息队列等待重试。双写出现严重异常时暂停迁移，继续由旧表承接业务。重试仍失败时，由人工排查并修复双写代码、配置或运行问题；数据本身不由人工直接修改，最终仍由一致性校验任务发现差异并修正。

人工直接修数的并发风险：

1. 旧表写入成功，新表 INSERT 失败。
2. 人工读取旧表金额 100，准备修数。
3. 业务把旧表金额更新为 200。
4. 人工脚本仍把金额 100 写入新表，产生差异。

因此人工负责修复原因，数据交给程序校验修正；程序修数本身的并发边界见 3.1。

**待确认方案**：

- 消息队列的重试次数；
- 消息队列的重试间隔；
- 失败状态记录方式；
- 告警升级规则；
- 人工介入时机；
- 重试最终失败后由一致性校验任务修正数据的具体衔接方式。

#### 1.4 高：历史数据未迁入时的双写处理与一致性修正

**参考文章方案：同步改造增删改**：改造 `Insert`、`Update`、`Delete`，但未明确新表记录不存在时影响 0 行的处理。参考来源定位：[业务写操作改造（第 16 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:16>)、[迁移并发问题说明（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)。

**参考文章方案存在的问题**：文章没有说明历史迁移尚未回填某条记录时，`UPDATE` 或 `DELETE` 影响 0 行后是否立即补建、重试或等待迁移。例如，旧表更新成功而新表尚无记录，业务更新返回成功；如果后续迁移只写入旧快照，就会把更新前数据带入新表。

**已确认方案：缺失记录等待历史迁移回填**：历史迁移尚未回填某条记录时，业务仍以旧表为准。新表 `UPDATE`、`DELETE` 影响 0 行不阻断旧表业务，也不在双写链路中立即补建；由历史迁移任务按既定流程回填新表。新表可以暂时缺失记录或保留旧快照，后续由一致性校验任务发现并修正。迁移完成并通过一致性校验前，新表不能作为最终可信数据源。

以下两个例子均假设新表记录尚未迁入，是并发时序推演，未进行运行验证。

**更新前快照写入新表**

1. 迁移任务读取旧表，得到金额 **100**，暂未写入新表。
2. 业务将旧表金额更新为 **200**，提交成功。
3. 业务尝试更新新表，但记录尚未迁入，`UPDATE` 影响 **0 行**。
4. 迁移任务将之前读取的金额 **100** 插入新表。
5. 此时旧表金额为 **200**，新表金额为 **100**，由一致性校验任务发现差异并修正。

**删除前快照重新插入新表**

1. 迁移任务读取旧表中的流水 **S1**，暂未写入新表。
2. 业务删除旧表中的 **S1**，提交成功。
3. 业务尝试删除新表中的 **S1**，但记录尚未迁入，`DELETE` 影响 **0 行**。
4. 迁移任务将之前读取的 **S1** 插入新表。
5. 此时旧表已无 **S1**，新表却存在 **S1**，由一致性校验任务发现多余记录并删除。

**待确认方案**：

- 本点核心处理已确认；校验修数期间的重读、重试和失败处理见 [3.1](#31-高新旧表差异校验与修复)。

#### 1.5 中：双写记录的身份关联

**参考文章方案：按业务键和分片键定位新库**：按业务主键或分片键写入新库；文章未定义当前项目的 `consumeId` 和 `version` 规则。参考来源定位：[应用层双写和分片路由（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**参考文章方案存在的问题**：文章没有说明旧表和新表主键规则不一致时如何稳定关联同一业务记录。例如，同一 `serialNo` 的双写消息第一次生成一个新表 `consumeId`，重试时又重新生成另一个 ID，可能在新表形成两条业务记录。

**已确认方案**：新旧表使用各自主键，以全局唯一的 `serialNo` 关联同一交易。首次创建新表记录时按 `003_分库分表.md` 规则生成 `consumeId`，后续沿用已有 `consumeId`。业务更新和补偿的版本规则见 [1.1](#11-高双写失败补偿与历史迁移的版本维护)。

**待确认方案**：

- 首次写入发生并发或结果不确定时，如何可靠定位并复用已有 `consumeId`。

### 2. 历史数据迁移

#### 2.1 中：迁移身份与版本重跑

**参考文章方案：重跑保持幂等**：重复迁移应保持幂等，不能因重跑生成错误身份或覆盖更新数据。参考来源定位：[可重入、幂等的迁移工具（第 83 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:83>)。

**参考文章方案存在的问题**：文章提出“可重入、幂等”，但没有定义幂等键、冲突处理和身份沿用规则。例如，任务写入新表成功后尚未保存进度就退出，重跑再次生成新表主键；若没有按业务唯一标识去重，就会插入重复记录。

**已确认方案**：历史迁移首次创建新表记录时生成新表 `consumeId`，不复用旧表 `id`；重跑通过 `serialNo` 定位已有记录，沿用其身份。版本赋值规则见 [1.1](#11-高双写失败补偿与历史迁移的版本维护)。

**待确认方案**：

- 完整幂等写入条件；
- 重复记录处理方式；
- 异常恢复方式。

#### 2.2 高：历史数据在线回填

**参考文章方案：分批扫描、幂等回填**：分批扫描旧库，按主键或时间切片，支持幂等重跑，并通过校验处理并发更新、删除和遗漏。参考来源定位：[历史数据迁移工具（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)。

**参考文章方案存在的问题**：文章没有明确扫描边界、游标保存和失败批次如何继续。例如，迁移扫描到第 10 批时进程退出，如果游标已前移但第 10 批部分写入失败，重启后可能跳过未写入的记录；如果游标未保存，又可能重复处理已写入记录。

**已确认方案：双写稳定后在线回填历史数据**：双写链路稳定后启动迁移；旧表继续承接业务，迁移任务分批读取旧表并按 `merchantNo` 路由到目标分片。记录身份和重跑见 [2.1](#21-中迁移身份与版本重跑)，快照版本赋值及条件 SQL 见 [1.1](#11-高双写失败补偿与历史迁移的版本维护)，并发差异处理见 [2.3](#23-高迁移快照与删除回插)。

**待确认方案**：

- 扫描范围；
- 断点续传方式；
- 限速策略；
- 异常恢复方式；

#### 2.3 高：迁移快照与删除回插

**参考文章方案：比较更新时间并依赖校验处理删除回插**：比较更新时间，并通过软删除时间点或后续校验处理删除回插；文章没有展开并发保证。参考来源定位：[迁移期间并发更新（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)、[更新时间比较与删除处理（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**参考文章方案存在的问题**：迁移可能将删除前快照回插，完整时序见 [1.4](#14-高历史数据未迁入时的双写处理与一致性修正) 的流水 S1 示例。此时旧表已无 S1；如果校验只遍历旧表，就不会发现新表多出的记录。文章未展开多余记录的发现方式。参考来源定位：[删除处理（第 90 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:90>)、[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

**已确认方案**：迁移任务读取更新前或删除前快照并写入新表造成的差异，交由一致性校验发现并修正；不采用文章中未展开的删除时间点或删除标记机制。

**待确认方案**：

- 迁移任务采用来源版本条件更新时，版本冲突后的处理规则；
- 删除回插已决定由校验修正；如何完整发现新表多余记录见 [3.1](#31-高新旧表差异校验与修复)。

#### 2.4 高：增量补齐与迁移完成判定

**参考文章方案：扫描后多轮校验**：文章提出双写失败补偿、分批扫描和后续校验；“跑完一遍”仅是理论一致，切换前还需反复校验。参考来源定位：[扫描结束说明（第 92 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:92>)、[差异修复（第 109 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:109>)。

**参考文章方案存在的问题**：缺少扫描、补偿和校验衔接的完整结束条件。

**双写遗漏后的增量补齐路径未展开**：例如，迁移已经扫描过流水 S2，随后业务更新旧表成功、新表失败；如果后续扫描只向后推进，就不会自动重新读到 S2。文章提出双写失败补偿和后续校验，但没有给出迁移扫描、补偿与校验之间完整的衔接和完成判定。文章未说明迁移任务独立读取全部增量；这不意味着必须增加独立增量采集，也不能把分批扫描理解为已实现增量重扫。参考来源定位：[双写失败处理（第 72 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:72>)、[分批扫描（第 85 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:85>)。

**迁移完成判定没有展开**：例如，扫描游标已到最后一批，但某个分片的写入失败仍未处理；或扫描结束后，又有一笔双写失败尚待补齐。此时“扫描跑完”不等于“数据追平”。文章未明确扫描范围、失败批次、增量补齐和最终校验各自的完成条件。参考来源定位：[跑完一遍后的说明（第 92 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:92>)。

**已确认方案**：历史迁移完成并通过一致性校验后，才能进入查询切换；具体完成判定尚未确认，不能把扫描游标到末尾直接当作全部数据追平。

**待确认方案**：

- 历史扫描范围的结束边界；
- 失败批次的处理完成条件；
- 扫描期间增量变更、失败补偿与后续校验的衔接；
- 迁移完成与校验验收结果如何共同作为切换依据。

### 3. 新旧表数据一致性校验

#### 3.1 高：新旧表差异校验与修复

**参考文章方案：分片并行比对并多轮复核**：分片并行生成指纹或逐行比对，多轮修复后再次校验。参考来源定位：[数据一致性校验工具（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[校验性能建议（第 131 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:131>)。

**参考文章方案存在的问题**：文章没有明确校验字段范围、差异修正的并发条件和修数失败后的状态管理。

1. 校验读取旧表金额 200。
2. 业务将旧表和新表都更新为 300。
3. 修数脚本若仍无条件写回 200，就会再次制造差异。

**已确认方案**：校验必须发现新表缺失、旧快照、错误新增和删除差异；发现差异后先定位原因并修复，再重新校验。校验是查询和写入切换的核心门禁。

**程序修数并保留排查记录**：校验发现差异后，先记录差异和修数前快照，再由程序按照旧表最新数据修正新表；对已有记录的更新采用 [1.1](#11-高双写失败补偿与历史迁移的版本维护) 中的来源版本条件；单条记录的插入、更新或删除在新表事务中完成。该事务及 UPDATE 条件不能单独证明跨库读写、缺失记录和删除修复的并发安全。无论修数成功还是失败，都记录修数原因、执行结果、重试次数和最终状态；修数完成后再次校验。该方案由项目自行决定，没有直接参考来源，也没有实践验证。

**待确认方案**：

- 新表多余记录及删除差异的完整发现方式；
- 字段比较清单；
- 校验读取旧表后发生业务变更时的重读规则；
- 版本变化后的重试与失败处理；
- 延迟复核方式；
- 最终验收范围；
- 修数失败后的重试上限；
- 人工介入条件；
- 日志保存周期。

#### 3.2 中：历史迁移数据的 ES 覆盖校验

**参考文章方案：切换前校验新旧库**：文章要求切换前进行全量或多轮新旧库校验，没有讨论 ES 历史覆盖；本点是项目扩展。参考来源定位：[数据一致性校验与切换前置条件（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

**参考文章方案存在的问题**：新旧库校验不能证明项目的 ES 校验已覆盖历史导入。例如，先推进新表到 ES 校验的 `update_time` 游标，再导入更新时间早于游标的历史记录，该校验可能扫不到这条记录。这里说的是更新时间扫描校验，不是 Binlog 正常同步；日志同步起点另见 4.3。

**已确认方案**：暂不确认历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖，只保留风险记录。

**待确认方案**：

- 历史 `update_time` 早于已推进游标时的全量复核、游标调整或其他覆盖方式。

### 4. 流量切换与回滚预案

#### 4.1 高：查询和写入切换

**参考文章方案：先读后写、逐步灰度**：先灰度切读，再灰度切写，稳定后关闭双写。参考来源定位：[流量灰度切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

**参考文章方案存在的问题**：文章没有明确切写期间请求如何路由及旧表、新表双写何时停止。例如，部分请求已经写入新表，仍有旧服务只写旧表；此时读流量继续扩大，可能出现同一业务记录在两套库中的结果不一致。

**已确认方案**：采用 1.2 节的整体流程：先灰度切查询，稳定后再逐步切写入；全部流量切换并稳定、满足收尾条件后停止旧表写入，改为新表单写。

**待确认方案**：

- 灰度比例；
- 观察指标阈值；
- 灰度切写期间的实际写入方式；
- 旧表依赖完成的具体检查步骤；
- 收尾条件的具体检查步骤。

#### 4.2 高：回滚预案

**参考文章方案：各阶段保留旧库回退**：各灰度阶段通过配置中心保留切回旧库的方案；文章没有展开停写旧库后的回补机制。参考来源定位：[灰度阶段回滚预案（第 123 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:123>)。

**参考文章方案存在的问题**：文章没有明确写流量已经切到新库后，旧库是否仍保持可回退状态，以及回退时如何处理两边新增变更。例如，新库已接收一段时间的写入后直接切回旧库，若没有回补这段时间的新数据，旧库会缺少回退期间产生的记录。

**已确认方案**：暂不确认最终停止旧表写入后的回退边界。

**待确认方案**：

- 查询切换期间的回退方式；
- 写入切换后的回退方式；
- 数据回补要求；
- 回退截止点。

#### 4.3 中：ES 同步起点与日志保留

**参考文章方案：监控双写并多轮校验**：文章检查清单要求监控双写成功率、新库延迟并执行多轮校验，未给出 ES、Binlog 起点或日志保留方案；这些属于项目扩展。参考来源定位：[执行检查清单（第 143 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:143>)。

**参考文章方案存在的问题**：文章没有明确同步起点、日志保留下限和恢复后的追赶方式。例如，迁移期间同步日志保留不足，消费者故障恢复时起点已经过期，历史写入无法重新读取，即使新表已有数据，ES 仍可能缺少对应数据。

**已确认方案**：旧表到新表不采用 Binlog 同步路线；新表到 ES 的既有 Binlog、Canal 和 RocketMQ 链路保留。

**待确认方案**：

- 追赶能力；
- 恢复边界。

**已确认规则**
