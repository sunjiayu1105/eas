# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

如果采用文章中的“应用层双写＋在线历史迁移”主方案，项目最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**一、按四个主题组织的改造点**

以下改造点均围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)整理。每个小改造点均区分参考文章方案、项目已确认方案和待确认方案。

### 1. 业务双写

#### 1.1 高：上线顺序与双写开关

**参考文章方案：先双写、后迁移，再灰度切换**

**先开启双写**：升级服务，改造所有新增、更新和删除入口，使业务变更同时尝试写入旧库和新库。

**再迁移历史数据**：双写开启后，使用迁移工具把旧库历史数据分批导入新库。

**先读后写灰度切换**：迁移和多轮一致性校验完成后，先灰度切读；读流量可按 `5% → 20% → 50% → 100%` 逐步扩大，并观察新库负载、慢查询和错误率。读流量稳定一段时间（例如 24 小时）后，再逐步切换写流量。

**稳定后关闭双写**：全部流量切到新库并稳定运行后，关闭旧库双写。

**各阶段保留回滚**：每个灰度阶段都通过配置中心保留切回旧库的回滚方案。

**检查清单中的观察建议**：开启双写后至少观察一个业务高峰周期（如 24 小时），数据校验连续 2～3 轮一致，切换后持续监控至少一周，并保留旧库数据一段时间（如一个月）。这些是文章示例，不是当前项目已确认的阈值。

**参考来源定位**：[服务升级与双写](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)、[历史数据迁移](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)、[一致性校验](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[灰度切换与回滚](<./999_分库分表 + 数据迁移_参考文章_01_1.md:113>)、[执行检查清单](<./999_分库分表 + 数据迁移_参考文章_01_1.md:135>)。

**已确认方案**：采用“先升级服务开启应用层双写 → 在线迁移历史数据 → 完成一致性校验 → 灰度切换查询和写入 → 稳定后关闭双写”。

**待确认方案**：各阶段进入条件、完成条件、观察指标、失败处置和回退边界。

#### 1.2 高：旧表主写与新表失败处理

**参考文章方案：旧库主写、新库补偿**：旧库写入是主流程；新库失败不阻断业务，记录、告警并补偿。

**参考来源定位**：[应用层双写伪代码与失败处理](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**已确认方案**：先确认旧表事务提交成功，再尝试写新表；新表失败不影响接口成功，由一致性校验发现差异。暂不引入自动补偿队列，先定位原因、修复代码或配置并验证，再人工或独立修正。

**待确认方案**：重试任务、状态、告警和自动修复机制。

#### 1.3 高：新表缺失记录的更新、删除与短暂不一致

**参考文章方案：同步改造增删改**：改造 `Insert`、`Update`、`Delete`，但未明确新表记录不存在时影响 0 行的处理。

**参考来源定位**：[业务写操作改造](<./999_分库分表 + 数据迁移_参考文章_01_1.md:16>)、[迁移并发问题说明](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)。

**已确认方案**：新表 `UPDATE`、`DELETE` 影响 0 行不阻断旧表业务；允许新表暂时缺失或出现旧快照，由一致性校验发现并修正。迁移读取更新前或删除前快照造成的脏数据也交由校验修正；校验完成前新表不能作为最终可信数据源。

**待确认方案**：新表缺失时是否立即补建完整记录，以及双写与迁移之间的原子并发保护。

#### 1.4 中：双写记录的身份和版本维护

**参考文章方案：按业务键和分片键定位新库**：按业务主键或分片键写入新库；文章未定义当前项目的 `consumeId` 和 `version` 规则。

**参考来源定位**：[应用层双写和分片路由](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**已确认方案**：旧表和新表使用各自主键；业务双写首次创建新表记录时按 `003_分库分表.md` 规则生成 `consumeId`，后续通过全局唯一的 `serialNo` 定位并沿用已有 `consumeId`。新表更新时业务字段和 `version = version + 1` 在同一条 SQL 中执行；数据库 SQL 失败时重试相同 SQL，消息重试沿用原消息数据和版本，不再次修改新表 `version`。

**待确认方案**：日常新增 `version` 初始值、字段类型和取值范围。

### 2. 历史数据迁移

#### 2.1 高：历史数据在线回填

**参考文章方案：分批扫描、幂等回填**：分批扫描旧库，按主键或时间切片，支持幂等重跑，并通过校验处理并发更新、删除和遗漏。

**参考来源定位**：[历史数据迁移工具](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)。

**已确认方案**：从旧表读取记录，按 `merchantNo` 计算目标分片，使用全局唯一 `serialNo` 关联新旧记录，按新表规则重新生成 `consumeId`，不复用旧表 `id`，历史迁移的 `version` 初始化为 `1`。

**待确认方案**：扫描范围、断点续传、限速、重跑幂等写入、异常恢复和迁移并发防护。

#### 2.2 高：迁移快照与删除回插

**参考文章方案：比较更新时间并依赖校验处理删除回插**：比较更新时间，并通过软删除时间点或后续校验处理删除回插；文章没有展开并发保证。

**参考来源定位**：[迁移期间并发更新](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)、[更新时间比较与删除处理](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**已确认方案**：迁移任务读取更新前或删除前快照并写入新表造成的差异，交由一致性校验发现并修正；不采用文章中未展开的删除时间点或删除标记机制。

**待确认方案**：迁移任务如何原子防止旧快照覆盖新数据，以及如何防止删除记录回插。

#### 2.3 中：迁移身份与版本重跑

**参考文章方案：重跑保持幂等**：重复迁移应保持幂等，不能因重跑生成错误身份或覆盖更新数据。

**参考来源定位**：[可重入、幂等的迁移工具](<./999_分库分表 + 数据迁移_参考文章_01_1.md:83>)。

**已确认方案**：历史迁移重新生成新表 `consumeId`，不复用旧表 `id`；已有新表记录的 `version` 不能随意重置，迁移重跑沿用 `serialNo` 关联记录。

**待确认方案**：完整幂等写入条件、重复记录处理和异常恢复方式。

### 3. 新旧表数据一致性校验

#### 3.1 高：新旧表差异校验与修复

**参考文章方案：分片并行比对并多轮复核**：分片并行生成指纹或逐行比对，多轮修复后再次校验。

**参考来源定位**：[数据一致性校验工具](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[校验性能建议](<./999_分库分表 + 数据迁移_参考文章_01_1.md:130>)。

**已确认方案**：校验必须发现新表缺失、旧快照、错误新增和删除差异；发现差异后先定位原因并修复，再重新校验。校验是查询和写入切换的核心门禁。

**待确认方案**：历史扫描与增量采集衔接、字段比较清单、延迟复核和最终验收范围。

#### 3.2 中：历史迁移数据的 ES 覆盖校验

**参考文章方案：迁移后确认历史数据进入新链路**：迁移完成后进行全量或多轮校验，确认历史数据进入新链路后再切换流量。

**参考来源定位**：[数据一致性校验与切换前置条件](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

**已确认方案**：暂不确认历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖，只保留风险记录。

**待确认方案**：历史 `update_time` 早于已推进游标时的全量复核、游标调整或其他覆盖方式。

### 4. 流量切换与回滚预案

#### 4.1 高：查询和写入切换

**参考文章方案：先读后写、逐步灰度**：先灰度切读，再灰度切写，稳定后关闭双写。

**参考来源定位**：[流量灰度切换](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

**已确认方案**：暂不确认查询灰度、停止旧表写入和切换新表单写的具体方案。

**待确认方案**：切换顺序、观察指标、校验门禁、旧表依赖完成条件和停止旧表写入条件。

#### 4.2 高：回滚预案

**参考文章方案：各阶段保留旧库回退**：各灰度阶段保留切回旧库的方案，必要时关闭双写并回补数据。

**参考来源定位**：[灰度阶段回滚预案](<./999_分库分表 + 数据迁移_参考文章_01_1.md:123>)。

**已确认方案**：暂不确认最终停止旧表写入后的回退边界。

**待确认方案**：查询切换期间和写入切换后的回退方式、数据回补要求及回退截止点。

#### 4.3 中：ES 同步起点与日志保留

**参考文章方案：同步链路覆盖迁移数据**：双写和历史迁移产生的数据都进入后续同步链路，并关注同步延迟和日志保留，避免起点过晚漏数。

**参考来源定位**：[双写迁移期间的同步与校验清单](<./999_分库分表 + 数据迁移_参考文章_01_1.md:143>)。

**已确认方案**：旧表到新表不采用 Binlog 同步路线；新表到 ES 的既有 Binlog、Canal 和 RocketMQ 链路保留。

**待确认方案**：ES 同步起点是否覆盖最早双写和历史导入、在线迁移期间的 binlog 保留量、追赶能力和恢复边界。

**本文后续补齐项**：本文已排除旧表到新表的 Binlog 同步路线；后续需将应用层双写、在线历史迁移、校验、切换和恢复的具体规则补齐，形成完整方案。

**二、既定规则与本文边界**

现有的 **2 个实例、32 个分片、按 `merchantNo` 路由、`consumeId` 主键、`serialNo` 关联**可以继续作为设计基础；文章本身不构成修改这些规则的依据。

“切查询前连续 1 个月无差异”“全部旧表依赖切换后再次连续 3 个月无差异”的条件，也不能直接替换成文章中的 24 小时、两三轮或一周。ES 月份索引、生命周期管理及当前 DELETE 校验边界同样不能顺带改变。

**已确认规则**

- 旧表到新表不采用 Binlog 同步路线，删除该候选路线的修改清单。
- 业务双写采用旧表优先；旧表提交成功后尝试写新表，新表失败暂不影响接口成功；失败补偿机制暂不确认，先通过一致性校验发现差异，再定位原因并修复。
- 新表 `UPDATE` 影响 0 行时暂不视为接口失败；业务双写与迁移读取旧快照并发时可能产生脏数据，该问题依赖一致性校验发现并修正；迁移任务具体并发防护方式暂不确认。该处理没有直接参考来源，也没有实践验证。
- 旧表删除成功后尝试删除新表，新表 `DELETE` 影响 0 行时暂不视为接口失败；迁移任务将删除前快照写回新表的问题依赖一致性校验发现并修正；项目不采用删除时间点或删除标记机制。该处理没有直接参考来源，也没有实践验证。
- 业务双写允许新表暂时缺失或出现旧快照；一致性校验完成并确认差异已修复前，新表不能作为最终可信数据源。该方案允许短暂不一致，没有直接参考来源，也没有实践验证。
- 新表写入失败后暂不引入自动补偿队列；由一致性校验发现差异，定位原因并修复代码或配置后，再人工或独立流程修正数据；重试任务、重试状态、告警和自动修复机制暂不确认。
- 历史迁移按 `merchantNo` 路由，重新生成新表 `consumeId`，历史迁移的 `version` 初始化为 `1`；迁移重跑不能随意重置已有 `version`，具体幂等写入方式仍需验证。
- 旧表和新表使用各自独立的主键；`serialNo` 用于关联新旧记录，业务双写首次创建新表记录时按新表规则生成 `consumeId`，后续通过 `serialNo` 定位并沿用已有 `consumeId`。
- 新表更新时业务字段和 `version = version + 1` 在同一条 SQL 中执行；数据库更新 SQL 失败时重试相同 SQL，成功执行时才递增 `version`；同步消息重试沿用原消息数据和版本，不再次修改新表 `version`。
- 一致性校验是查询和写入切换的核心门禁；校验发现差异后必须先定位原因、修复并重新校验，校验未完成或差异未修复前不得将新表作为最终可信数据源。
- 历史迁移数据如何被新表到 ES 的同步和校验链路完整覆盖暂不确认；历史 `update_time` 早于已推进游标而造成漏同步或漏校验的风险需要保留。
