# 999_分库分表 + 数据迁移_方案设计

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

**核心结论**

如果采用文章中的“应用层双写＋在线历史迁移”主方案，项目最主要的变化是：**把“停写迁移完成后开启双写”，调整为“先开启双写，再一边承接业务、一边迁移历史数据”。** 因此，需要修改的不只是双写文档，还包括迁移工具、并发保护、校验起点、ES 历史覆盖和切换流程。

本文围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)中的“应用层双写＋在线历史迁移”主方案列出修改点。旧表到新表不采用 Binlog 同步路线；新表到 ES 的现有 Binlog 同步链路保留。以下仍是修改点分析，不代表在线迁移的具体实现和全部规则已经确认。

**一、按四个主题组织的改造点**

以下改造点均围绕[参考文章 01_1](<./999_分库分表 + 数据迁移_参考文章_01_1.md>)整理。每个小改造点均区分参考文章方案、项目已确认方案和待确认方案。

### 1. 业务双写

#### 1.1 高：旧表版本字段与写入入口改造

**参考文章方案：通过更新时间判断数据新旧**：参考文章使用 `gmt_modified` 等更新时间字段判断迁移数据的新旧，没有明确要求为旧表新增 `version` 字段，也没有展开系统内所有写入口的统一改造。参考来源定位：[更新时间比较（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**已确认方案：旧表新增版本并统一递增**：旧表消费记录表新增 `version` 字段，现有历史记录初始化为 `1`；排查所有新增、更新消费记录表的业务代码、定时任务、批处理和脚本。新增记录的 `version` 初始化为 `1`，每次修改消费记录时，业务字段与 `version = version + 1` 必须在同一次更新操作中完成，双写新表时携带这次变更对应的版本。例如，记录初始金额为 100、`version = 1`，更新为 200 后旧表必须变为金额 200、`version = 2`，新表校验时可以据此识别新旧数据是否处于同一版本。该旧表字段改造和全量写入口排查是项目自行决定的方案，没有直接参考来源，也没有实践验证。

**待确认方案**：`version` 字段的数据类型、默认值和非空约束；历史数据初始化和应用发布的先后步骤；漏改写入口的排查清单及上线验收方式。

#### 1.2 高：上线顺序与双写开关

**参考文章方案：先双写、再迁移和校验，最后灰度切换**：先升级服务开启应用层双写，再迁移历史数据；迁移和一致性校验完成后，先灰度切查询，再灰度切写入；新库稳定运行后关闭旧库双写。参考来源定位：[服务升级与双写（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)、[历史数据迁移（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)、[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[流量切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

**已确认方案：项目采用相同上线顺序**：开启应用层双写 → 迁移历史数据 → 执行一致性校验 → 灰度切查询 → 灰度切写入 → 稳定后停止旧表写入并改为新表单写。各阶段的具体处理分别在业务双写、历史数据迁移、一致性校验和流量切换章节展开。

**待确认方案：顺序对应的阶段门禁**：各阶段的进入条件、完成条件、观察指标、失败处置和回退边界；具体灰度参数和切写细节见第 4 部分。

#### 1.3 高：旧表主写与新表失败处理

**参考文章方案：旧库主写、新库补偿**：旧库写入是主流程；新库失败不阻断业务，记录、告警并补偿。参考来源定位：[应用层双写伪代码与失败处理（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**已确认方案**：先确认旧表事务提交成功，再尝试写新表；新表写入失败不影响接口成功，但必须打印错误日志并发送告警，同时将失败数据放入消息队列等待重试。重试仍失败时，由人工排查并修复双写代码、配置或运行问题；数据本身不由人工直接修改，最终仍由一致性校验任务发现差异并修正。例如，旧表写入成功、新表 `INSERT` 失败后，人工如果直接把旧表当时读到的数据复制到新表，业务可能同时把旧表从金额 100 更新为 200，人工脚本却把金额 100 写回新表，造成新的脏数据；因此人工只负责排查和修复原因，数据修正交给校验任务按当前数据和版本或更新时间条件处理。

**待确认方案**：消息队列的重试次数、重试间隔、失败状态记录、告警升级和人工介入时机；重试最终失败后由一致性校验任务修正数据的具体衔接方式。

#### 1.4 高：新表缺失记录的更新、删除与短暂不一致

**参考文章方案：同步改造增删改**：改造 `Insert`、`Update`、`Delete`，但未明确新表记录不存在时影响 0 行的处理。参考来源定位：[业务写操作改造（第 16 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:16>)、[迁移并发问题说明（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)。

**已确认方案**：新表 `UPDATE`、`DELETE` 影响 0 行不阻断旧表业务；允许新表暂时缺失或出现旧快照，由一致性校验发现并修正。迁移读取更新前或删除前快照造成的脏数据也交由校验修正；校验完成前新表不能作为最终可信数据源。

以下两个例子均假设新表记录尚未迁入，是并发时序推演，未进行运行验证。

**更新前快照写入新表**

1. 迁移任务读取旧表，得到金额 **100**，暂未写入新表。
2. 业务将旧表金额更新为 **200**，提交成功。
3. 业务尝试更新新表，但记录尚未迁入，`UPDATE` 影响 **0 行**。
4. 迁移任务将之前读取的金额 **100** 插入新表。
5. 此时旧表金额为 **200**，新表金额为 **100**，由一致性校验任务发现差异并修正。

**删除前快照重新插入新表**

1. 迁移任务读取旧表中的流水 **S1**，暂未写入新表。
2. 业务删除旧表中的 **S1**，提交成功。
3. 业务尝试删除新表中的 **S1**，但记录尚未迁入，`DELETE` 影响 **0 行**。
4. 迁移任务将之前读取的 **S1** 插入新表。
5. 此时旧表已无 **S1**，新表却存在 **S1**，由一致性校验任务发现多余记录并删除。

**待确认方案**：新表缺失时是否立即补建完整记录，以及双写与迁移之间的原子并发保护。

#### 1.5 中：双写记录的身份和版本维护

**参考文章方案：按业务键和分片键定位新库**：按业务主键或分片键写入新库；文章未定义当前项目的 `consumeId` 和 `version` 规则。参考来源定位：[应用层双写和分片路由（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

**已确认方案**：旧表和新表使用各自主键；业务双写首次创建新表记录时按 `003_分库分表.md` 规则生成 `consumeId`，后续通过全局唯一的 `serialNo` 定位并沿用已有 `consumeId`。新表更新时业务字段和 `version = version + 1` 在同一条 SQL 中执行；数据库 SQL 失败时重试相同 SQL，消息重试沿用原消息数据和版本，不再次修改新表 `version`。

**待确认方案**：新旧表版本值在迁移、校验修数和消息重试之间的具体传递及冲突处理规则。

### 2. 历史数据迁移

#### 2.1 中：迁移身份与版本重跑

**参考文章方案：重跑保持幂等**：重复迁移应保持幂等，不能因重跑生成错误身份或覆盖更新数据。参考来源定位：[可重入、幂等的迁移工具（第 83 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:83>)。

**已确认方案**：历史迁移重新生成新表 `consumeId`，不复用旧表 `id`；已有新表记录的 `version` 不能随意重置，迁移重跑沿用 `serialNo` 关联记录。

**待确认方案**：完整幂等写入条件、重复记录处理和异常恢复方式。

#### 2.2 高：历史数据在线回填

**参考文章方案：分批扫描、幂等回填**：分批扫描旧库，按主键或时间切片，支持幂等重跑，并通过校验处理并发更新、删除和遗漏。参考来源定位：[历史数据迁移工具（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)。

**已确认方案**：从旧表读取记录，按 `merchantNo` 计算目标分片，使用全局唯一 `serialNo` 关联新旧记录，按新表规则重新生成 `consumeId`，不复用旧表 `id`，历史迁移的 `version` 初始化为 `1`。

**待确认方案**：扫描范围、断点续传、限速、重跑幂等写入、异常恢复和迁移并发防护。

#### 2.3 高：迁移快照与删除回插

**参考文章方案：比较更新时间并依赖校验处理删除回插**：比较更新时间，并通过软删除时间点或后续校验处理删除回插；文章没有展开并发保证。参考来源定位：[迁移期间并发更新（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)、[更新时间比较与删除处理（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**已确认方案**：迁移任务读取更新前或删除前快照并写入新表造成的差异，交由一致性校验发现并修正；不采用文章中未展开的删除时间点或删除标记机制。

**待确认方案**：迁移任务如何原子防止旧快照覆盖新数据，以及如何防止删除记录回插。

#### 2.4 高：参考文章方案存在的问题

**参考文章方案存在的问题**：参考文章 01_1 给出了分批扫描、按更新时间比较和依赖一致性校验的总体思路，但没有完整说明迁移期间的并发保护和最终收敛条件。以下例子均为分析时构造的时序或故障示例，不是文章中的实践案例，也未经实践验证。

**新表记录不存在时可能漏掉更新**：文章没有展开双写 `UPDATE` 影响 0 行时如何补齐变更。例如，迁移先读取金额 100；业务随后将旧表金额改为 200，但新表尚无记录，更新影响 0 行；迁移最后插入金额 100 的旧快照。旧表保留 200，新表仍是 100。参考来源定位：[迁移并发与写入判断（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)。

**时间戳相同不能判断数据新旧**：文章允许较晚或相等的更新时间覆盖，但没有说明时间精度不足、不同变更具有相同时间戳时如何排序。以下假设时间只保存到秒，不代表已核实当前项目字段精度。参考来源定位：[更新时间覆盖规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**允许相等时间覆盖，可能覆盖新数据**：例如，10:00:00.100 插入金额 100，双写成功；10:00:00.200 迁移读取这条记录；10:00:00.300 业务把金额改为 200，双写也成功；10:00:00.400 迁移才写入旧快照。迁移快照与新表都保存 `10:00:00`，若按 `>=` 判断，旧快照会把新表金额从 200 改回 100。这是对文章允许相等时间覆盖规则的风险推演。参考来源定位：[允许相等时间覆盖（第 89 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

**改用严格大于，又可能拒绝同步真实变更**：例如，同一秒内先插入金额 100，双写成功，再把旧表金额更新为 200，但新表更新失败。两边时间都为 `10:00:00`；即使校验通过业务字段发现差异，若修数只在旧表时间 `>` 新表时间时执行，也会拒绝修复。严格大于是对比用的假设方案，不是文章采用的规则；不能仅以时间相等认定内容一致。参考来源定位：[文章的时间比较规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**删除回插和多余记录的发现方式未展开**：例如，迁移读取流水 S1 后，业务删除旧表记录，新表删除影响 0 行；迁移随后又插入 S1，新表便多出一条记录。如果校验仅遍历旧表，再查新表，旧表已经不存在的 S1 就不会被检查。文章提到删除时间点和后续校验，但没有展开如何完整发现这类记录。参考来源定位：[删除处理（第 90 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:90>)、[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。

**双写遗漏后的增量补齐路径未展开**：例如，迁移已经扫描过流水 S2，随后业务更新旧表成功、新表失败；如果后续扫描只向后推进，就不会自动重新读到 S2。文章提出双写失败补偿和后续校验，但没有给出迁移扫描、补偿与校验之间完整的衔接和完成判定。文章未说明迁移任务独立读取全部增量；这不意味着必须增加独立增量采集，也不能把分批扫描理解为已实现增量重扫。参考来源定位：[双写失败处理（第 72 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:72>)、[分批扫描（第 85 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:85>)。

**幂等重跑规则没有展开**：文章要求可重入、幂等，但未展开具体实现。应用到本项目，例如流水 S3 已写入新表、进度尚未保存时任务退出；重跑若再次生成不同的 `consumeId`，且没有按 `serialNo` 去重的可靠约束或冲突处理，就可能插入重复业务记录。若存在唯一约束，也仍需明确冲突后如何沿用已有身份并恢复进度。这是结合项目主键规则提出的适配问题，不是文章定义了 `consumeId`。参考来源定位：[可重入与幂等（第 83 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:83>)。

**修复期间的并发保护没有展开**：例如，校验读取旧表金额 200 并生成修复脚本；执行前，业务把新旧表金额都更新为 300；如果脚本无并发条件地写回 200，就会重新造成差异。文章要求以旧库为准修复并重新校验，但没有展开读取与写入之间的并发保护。参考来源定位：[差异修复与复核（第 109 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:109>)。

**迁移完成判定没有展开**：例如，扫描游标已到最后一批，但某个分片的写入失败仍未处理；或扫描结束后，又有一笔双写失败尚待补齐。此时“扫描跑完”不等于“数据追平”。文章未明确扫描范围、失败批次、增量补齐和最终校验各自的完成条件。参考来源定位：[跑完一遍后的说明（第 92 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:92>)。

以上为参考文章的设计缺口与项目适配风险分析，不是已确认的解决方案。时间戳精度、版本设计、并发保护、删除差异发现、增量补齐、幂等重跑和完成判定仍需继续确认；本节不将“旧表新增 version”定为项目方案。

### 3. 新旧表数据一致性校验

#### 3.1 高：新旧表差异校验与修复

**参考文章方案：分片并行比对并多轮复核**：分片并行生成指纹或逐行比对，多轮修复后再次校验。参考来源定位：[数据一致性校验工具（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[校验性能建议（第 130 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:130>)。

**已确认方案**：校验必须发现新表缺失、旧快照、错误新增和删除差异；发现差异后先定位原因并修复，再重新校验。校验是查询和写入切换的核心门禁。

**程序修数并保留排查记录**：校验发现差异后，先记录差异和修数前快照，再由程序按照旧表最新数据修正新表；修数过程使用版本或更新时间条件，避免旧快照覆盖新变更，并在新表事务中完成单条记录的插入、更新或删除。无论修数成功还是失败，都记录修数原因、执行结果、重试次数和最终状态；修数完成后再次校验。该方案由项目自行决定，没有直接参考来源，也没有实践验证。

**待确认方案**：历史扫描与增量采集衔接、字段比较清单、延迟复核和最终验收范围；修数失败后的重试上限、人工介入条件和日志保存周期。

#### 3.2 中：历史迁移数据的 ES 覆盖校验

**参考文章方案：迁移后确认历史数据进入新链路**：迁移完成后进行全量或多轮校验，确认历史数据进入新链路后再切换流量。参考来源定位：[数据一致性校验与切换前置条件（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)。
