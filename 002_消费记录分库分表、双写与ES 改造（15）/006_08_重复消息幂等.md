## 已确认规则

4. **业务版本与并发消费**：采用 `CONCURRENTLY` 并发消费；仅新分库分表的消费表增加业务 `version`，旧表不增加。历史导入初始化为 `1`，后续更新在同一条 SQL 中修改业务字段并执行 `version = version + 1`；导入重跑不重置已有版本，MQ 重试沿用消息中的版本与数据。以上是已确认、待实现验证的设计决策。

5. **自然月索引（已确认设计，待实现验证）**：新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；`records-read` 只用于跨月查询。按自然月分索引，不使用 rollover；所属自然月结束后满 180 天进入 cold。删除事件须携带删除前的创建时间，索引模板统一 Mapping、配置和读别名；首次 Index 写入自动建索引以配置和权限允许为前提。新增、更新调用 Index API，删除调用 Delete API，业务版本在同一物理索引、同一 `_id` 范围内比较。

6. **消费确认、重试与校验**：不同消息并发处理，每次回调内逐条同步调用 ES；操作或必要状态保存异常时，中断当前消息并向外抛出运行时异常，由 RocketMQ 重投整条原消息。消息内全部事件处理及必要状态保存完成后，监听方法才能正常返回。自动校验任务每小时执行一次，发现差异后按数据库当前状态补偿；任务失败或延迟须告警。具体重试次数、退避、死信和恢复仍待核验。

### 自然月方案的待确认与待验证项

- 确认业务时区、`create_time` 实际列名及类型；验证历史导入保留原始创建时间，INSERT/UPDATE 行数据及 DELETE 前镜像经过 Canal、MQ 后仍完整传递。
- 7 天修改窗口尚未确认为硬限制，历史删除范围与最大积压、重试、恢复和补偿时间待确认；不能据此永久设置旧索引只读。
- 冷层时间已确认按所属自然月结束后满 180 天计算；实际调度或 ILM 年龄基准配置待实现验证，历史月份补建不能按建索引时间重新计时。
- Elasticsearch 7.17.15 支持首次 Index API 写入不存在索引时自动创建；仍需验证 `action.auto_create_index`、`create_index` 权限、索引模板匹配以及 `dynamic: strict` Mapping 是否接受文档字段。自动创建不会按月份主动建索引，Delete 请求也不能依赖它。
- 并发消费和业务版本方向已确认，具体重试参数、乱序恢复、删除版本生成及删除后旧写保护仍待实现验证。

## 面试口述精炼版本

8. **幂等处理**：同一事件重复请求时，要使用同一索引、同一 `_id`、同一来源版本和同一内容；冲突后区分重复、过期和异常。ES 文档幂等不等于所有外部副作用都只执行一次。

## 参考文章与项目方案对比

#### 参考文章以及项目中如何保证重复消息幂等？二者之间是否存在差异？

**当前结论**：幂等是同一变更重复处理后仍得到正确状态。文章主要比较业务版本并使用 Redis 锁，但没有稳定事件 ID 和持久化处理状态；项目通过同一物理索引、同一 `_id`、同一来源版本和同一内容控制重复结果，事件级去重按需采用。

文章 INSERT 使用 `create`，重复创建返回 409 时直接抛异常；版本判断中的 `continue`、锁获取失败和通过当前写别名写入等边界，不能证明重复事件已经被正确识别和处理。

项目允许重复请求 ES，但要求相同版本始终对应相同操作和内容。版本冲突后要结合实际索引、业务版本和状态区分重复、过期与异常；已核实的重复或过期事件按幂等规则处理，异常冲突仍进入失败流程。ES 文档幂等不保证数据库或其他外部副作用只执行一次。

如果需要事件级去重，可用“业务主键 + 来源版本”或稳定 `eventId` 保存处理状态；处理中或结果不明时必须核对后恢复。整条重投消息仍须处理其余事件，不能因为一个事件已经完成就确认整条消息。
