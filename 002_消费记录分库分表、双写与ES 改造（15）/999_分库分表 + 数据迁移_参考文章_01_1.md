# 999_分库分表 + 数据迁移_参考文章_01_1
### 1\. 从“停机大法”到“平滑过渡”：为什么我们需要双写迁移？

大家好，我是老张，在互联网公司摸爬滚打十几年，经手过好几次核心业务的数据架构升级。每次提到要把一个运行了好几年的单库单表系统，改造成分库分表，团队里最头疼的不是怎么写分库分表的代码，而是怎么把数据“搬过去”还不影响用户。想象一下，你正在一个热闹的商场里，现在要把整个商场的所有店铺、商品、顾客信息，原封不动地搬到一个新建的、结构更复杂的大型购物中心里去，而且要求商场不能关门，顾客的购物体验不能有一丝中断。这听起来是不是有点“不可能的任务”？

最开始，我们用的就是最原始也最“暴力”的方法—— **停机迁移** 。这活儿通常得在凌晨干，先挂公告说系统要维护几个小时，然后掐断所有流量。接着，写个脚本，把老数据库的数据一股脑儿读出来，再按照新的分库分表规则写进去。数据导完了，改改配置，重启服务，祈祷一切正常，最后看着凌晨四点的城市夜景回家。这种方法简单直接，谁都能想到，但它有个致命的缺点： **停机时间不可控** 。数据量小还好，要是碰上TB级别的大表，导个数据可能从天黑导到天亮，业务就得跟着停摆这么久，现在的互联网业务，哪还能承受这种级别的中断？用户可不会等你。

所以，我们迫切需要一种更“优雅”的方案，这就是 **双写迁移** 。它的核心思想就像它的名字一样：在迁移期间，任何对数据的修改操作，我们都不只写入老的数据库，同时也写入新的分库分表集群。这样一来，老库和新库就像一对双胞胎，在迁移过程中同步成长。等我们通过工具把历史数据也搬运过去，再经过严格的数据一致性校验后，就可以毫无感知地把流量切换到新库上。整个过程业务无感，用户体验零中断，这才是支撑高可用系统的迁移方案该有的样子。接下来，我就结合自己踩过的坑和积累的经验，带你一步步拆解这个方案到底怎么落地。

### 2\. 双写迁移方案全景图：四步走实现平滑切换

双写迁移不是一个单点技术，而是一套组合拳。我把它总结为四个核心步骤，每一步都环环相扣，缺一不可。你可以把它想象成一次精密的“心脏移植手术”，双写是建立体外循环，数据迁移是输送血液，数据校验是确保血管接通无误，最后才是切换心脏。

#### 2.1 第一步：服务升级，开启双写

这是整个迁移过程的起点，也是最关键的业务改造点。目标很明确：在业务代码中，对所有写入数据库的操作（ Insert 、Update、Delete）进行改造，让它们在写入旧库的同时，也尝试写入新的分库分表库。

**具体怎么操作呢？** 我通常会在代码里抽象一个数据访问层（DAO层）的代理。比如，原本有一个 `saveUser(User user)` 的方法，只操作旧库。现在，我会把它改造成这样：

```java
// 伪代码示例

public boolean saveUser(User user) {

    // 1. 先写旧库（必须成功）

    boolean oldWriteSuccess = oldUserDao.insert(user);

    if (!oldWriteSuccess) {

        // 旧库写入失败，直接返回失败，业务逻辑回滚

        return false;

    }

    

    // 2. 异步或同步写新库

    try {

        // 根据分片键（如user_id）计算新库和新表

        String dbName = calculateDbName(user.getId());

        String tableName = calculateTableName(user.getId());

        newUserDao.insertToSpecificDbTable(dbName, tableName, user);

    } catch (Exception e) {

        // 新库写入失败，不能影响主流程，但必须记录日志和告警！

        log.error("双写新库失败，userId: {}", user.getId(), e);

        // 可以将失败任务放入补偿队列，后续重试

        compensateQueue.add(user);

    }

    return true;

}
java运行
```

这里有几个 **实战要点** ：

1. **写旧库是“强依赖”** ：必须确保旧库写入成功，业务才能继续。因为此时线上流量依然全部走旧库，旧库的数据是唯一的真理。
2. **写新库是“弱依赖”** ：新库写入失败，不能影响主业务流程的返回。但一定要有完善的监控和补偿机制，比如记录详细日志、发送告警、将失败数据放入消息队列等待重试。否则，新库的数据就会慢慢落后于旧库，为后续的数据一致性问题埋下巨坑。
3. **双写范围要精准** ：通常只针对核心的、有写操作的表进行双写。一些只读的配置表、历史日志表，可以在后续阶段直接一次性迁移。

这个阶段上线后，系统就进入了“双写状态”。新库开始逐渐积累数据，但由于没有历史数据，还不能提供服务。不过别担心，这只是热身。

#### 2.2 第二步：历史数据迁移工具

双写开启后，新库只有增量数据，老库里的“陈年旧账”还得搬过去。这就需要开发一个 **数据迁移工具** （也叫导数工具）。这个工具的任务是把旧库中的存量数据，按照新的分库分表规则，搬运到新库中。

听起来简单，但做起来坑不少。最核心的问题是： **在迁移过程中，数据被修改了怎么办？** 比如，工具刚把用户A的数据读出来，还没写入新库，业务代码就因为用户A更新了头像，而对新旧库进行了一次双写Update。如果处理不好，要么旧库的新更新被覆盖，要么产生脏数据。

我的经验是，工具需要实现 **可重入的、幂等的、基于时间戳的增量迁移** 。具体流程如下：

1. **分批分段扫描** ：不要一次性 `SELECT *` ，而是按照主键ID范围或者时间范围，分批查询旧库数据。比如每次只取1万条。
2. **判断数据新旧** ：每条数据读取时，必须带上最后更新时间戳字段（如 `gmt_modified` ）。在写入新库前，先检查新库是否已存在该条数据（根据主键）。
	- 如果新库不存在，直接插入。
		- 如果新库已存在，则比较新旧两条数据的 `gmt_modified` 。
		- **只允许用更晚（或相等）时间戳的数据去覆盖较早的数据** ，坚决防止用老数据覆盖新数据。
3. **处理删除操作** ：这是一个难点。如果旧库中的某条数据在迁移前被删除了，我们的工具可能已经把它读出来准备插入了。一个常见的做法是，在迁移工具中记录一个“软删除”标记的逻辑时间点。对于在迁移后段才被删除的数据，工具可能感知不到。这就需要依赖下一步的 **数据校验** 来最终修正。

这个工具可以白天晚上慢慢跑，对线上服务几乎没有压力。跑完一遍后，理论上新库的数据应该和旧库在双写开启后的某个时间点是一致的。

#### 2.3 第三步：数据一致性校验工具

“理论上一致”可不行，我们必须用事实说话。在切换流量之前，必须进行一次甚至多次全量的数据一致性校验。这个校验工具的工作，就是像会计对账一样，比对两个数据库的每一分钱。

校验不能简单地 `SELECT COUNT(*)` ，那样只能知道总数对不对，不知道具体哪条不对。我们需要的是 **逐行比对** 。但全表扫描对比性能压力太大，我通常采用分库分表并行校验+抽样校验结合的方式：

1. **生成数据指纹** ：对于要校验的每一行数据，不是直接对比所有字段（特别是大文本字段），而是计算一个“指纹”，比如对所有关键字段拼接后计算MD5或CRC32校验码。
	```sql
	-- 示例：在查询时直接计算校验和
	SELECT id, CONCAT(name, email, ...) as combined_field, 
	       CRC32(CONCAT(name, email, ...)) as data_checksum 
	FROM user_table WHERE id BETWEEN ? AND ?
	sql
	```
2. **分片并行校验** ：利用新库本身就是分片的特性，启动多个校验任务，每个任务负责一个分片的数据范围，并行执行比对，大幅缩短时间。
3. **处理不一致数据** ：比对结果一定会发现不一致（尤其是在双写和数据迁移并行期）。发现不一致时，校验工具的策略必须是 **“以旧库为准”** 。自动或半自动地生成修复脚本，将旧库中的数据同步到新库。修复后，需要再次对修复过的数据范围进行校验，直到完全一致。

这个步骤可能需要反复进行几轮，特别是在数据量巨大、写操作频繁的场景下。耐心是关键，确保数据100%一致是切换前最后的，也是最重要的安全阀。

#### 2.4 第四步：流量切换与回滚预案

当前三步都稳稳落地后，终于来到了最激动人心也最紧张的环节—— **流量切换** 。这一步的目标是将所有读写流量从旧库无缝导向新库。

**千万不要用“改配置、重启服务”这种硬切换的方式！** 对于高可用系统，我们应该采用更柔和的 **灰度切换** 策略：

1. **先切读流量** ：修改配置中心的路由规则，将一部分（比如5%）的读请求引流到新库。观察新库的负载、慢查询、错误率是否正常。这个过程可以逐步放大比例，比如5% -> 20% -> 50% -> 100%。读流量全部切到新库后，旧库依然承担所有写流量，此时系统处于“读写分离”状态，风险可控。
2. **再切写流量** ：当读流量在新库上稳定运行一段时间（例如24小时）后，开始切换写流量。同样采用灰度策略，先切少量非核心业务的写操作，再逐步扩大范围，直到所有写操作都指向新库。
3. **关闭旧库双写** ：当确认100%的流量都已成功切换到新库，并且运行稳定后，就可以下线代码中的双写逻辑，移除对旧库的写入操作。至此，迁移大功告成。

**但是，一定要有回滚预案！** 在切换的每一个灰度阶段，都要准备好一键切回旧库的方案。这个方案通常依赖于配置中心的实时推送能力。一旦在新库上发现任何无法快速解决的问题（如性能不达标、出现未知 Bug ），立即将流量路由回旧库，保障业务不受损。有了这个“安全绳”，我们操作起来才能心里有底。

### 3\. 进阶实战：基于Binlog的同步双写方案

上面介绍的是在应用层代码实现双写，这对代码侵入性较强，而且需要改造所有写操作。在实际 项目 中，特别是面对遗留系统或微服务架构时，还有一种更解耦、更通用的方案—— **基于数据库Binlog的同步双写** 。这个方案我最近一次重构中就用到了，感觉非常“香”。

它的核心思想是： **不直接修改业务代码，而是通过监听旧库的二进制日志（Binlog），实时解析出数据变更事件，然后由一个独立的数据同步服务，将这些变更按照新规则写入新库。**

整个架构通常依赖阿里巴巴开源的Canal或者Debezium这样的 中间件 。我来画一下这个流程：

1. **部署Canal服务** ：它伪装成MySQL的一个从库，向旧库的主库请求Binlog。
2. **解析与转换** ：Canal解析Binlog流，将其转化为结构化的数据变更消息（包含表名、操作类型、变更前后的数据等），发送到消息队列（如Kafka/RocketMQ）。
3. **同步服务消费** ：我们编写一个“数据同步服务”消费这些消息。这个服务的核心职责是：根据消息中的数据和新的分库分表规则（比如根据订单ID哈希），计算出这条数据应该写入哪个新库的哪个表，然后执行写入。
4. **历史数据迁移** ：同样需要一个离线工具来迁移存量数据，流程和之前类似。
5. **数据校验与切换** ：校验和切换流程与应用层双写方案完全一致。

**这个方案的优势非常明显：**

- **对业务代码零侵入** ：业务团队完全感知不到迁移过程，他们依然像往常一样读写旧库。
- **解耦** ：数据同步成了一个独立的、可运维的基础服务，与业务逻辑分离。
- **通用性强** ：一套同步服务可以适配多个需要迁移的业务库。

**当然，挑战也不少：**

- **时序性问题** ：Binlog是顺序流，但消息队列消费可能存在轻微乱序。对于同一条数据的多次更新，必须保证执行顺序，否则会导致最终数据错误。这通常需要在同步服务中设计基于主键的本地队列来保证顺序。
- **数据转换更复杂** ：如果新老表结构有差异（比如字段拆分、合并、类型变更），同步服务里需要做复杂的ETL逻辑。
- **运维复杂度高** ：需要维护Canal、消息队列、同步服务这一整套链路的稳定性和监控。

选择哪种方案，取决于你的团队技术栈、业务系统现状和对风险的容忍度。应用层双写更直接可控，Binlog同步更解耦灵活。

### 4\. 避坑指南：那些年我踩过的“坑”与最佳实践

讲了这么多理论，最后分享一些实实在在的“血泪教训”和总结出的最佳实践，希望能帮你少走弯路。

**第一个大坑：双写不一致的雪崩。** 早期我们只关注了双写“写”的逻辑，忽略了异常处理。有一次，新库因为网络抖动偶尔写入超时，我们只是打了条错误日志。结果迁移后期一校验，发现大量数据缺失。原因是双写失败没有重试补偿，导致新库数据严重滞后。 **教训** ：必须建立强大的双写失败补偿机制，结合消息队列做异步重试，并配置严格的监控告警，任何一次双写失败都必须被追踪直到解决。

**第二个坑：数据校验的性能黑洞。** 第一次做全量校验时，直接 `SELECT *` 对比，几个亿的大表直接把数据库和校验程序都拖垮了。 **教训** ：务必采用“分片+指纹+并行”的策略。将大表按主键范围切成多个小任务，每个任务只计算和对比数据的校验和（Checksum），而不是对比完整数据行。同时，控制好校验任务对数据库的查询压力，避免影响线上业务。

**第三个坑：切换过程中的“幽灵写”。** 在灰度切换写流量时，我们遇到了一个诡异的问题：部分更新请求在新旧库都成功了，但数据却不一样。排查后发现，是因为一个冷门功能调用了一个老旧的服务，该服务配置未同步更新，依然在写旧库，导致了双写源混乱。 **教训** ：切换前，必须进行全面的依赖梳理和配置审计，确保所有可能写入该数据库的服务、Job、脚本都被纳入双写和切换的范围。

**基于这些经验，我梳理了一份高可用数据迁移的 checklist：**

- **事前准备阶段：**
	- \[ \] 明确迁移范围：所有涉及的表、字段、关联关系。
		- \[ \] 设计并测试新的分库分表规则（路由算法）。
		- \[ \] 评估并准备足够的数据库资源（新集群的CPU、内存、磁盘IOPS）。
		- \[ \] 制定详细的、分钟级的迁移操作手册和回滚手册。
		- \[ \] 准备数据比对工具和校验脚本，并提前在测试环境进行全流程演练。
- **事中执行阶段：**
	- \[ \] 开启双写后，至少观察一个完整的业务高峰周期（如24小时），监控双写成功率、新库延迟。
		- \[ \] 历史数据迁移工具必须支持断点续传和限流，避免拖垮旧库。
		- \[ \] 数据校验要执行多轮，直到连续2-3轮比对完全一致。
		- \[ \] 流量切换务必灰度，从非核心业务、只读操作开始，每推进一个阶段都要有足够的观察期。
		- \[ \] 切换期间，核心研发、运维、DBA必须全程在线，随时准备处理异常。
- **事后收尾阶段：**
	- \[ \] 确认所有流量切换完成后，持续监控新库性能指标和业务指标至少一周。
		- \[ \] 下线旧库的双写代码逻辑，清理相关配置和补偿队列。
		- \[ \] 保留旧库数据一段时间（例如一个月），作为灾备回滚的最后屏障，之后再根据计划归档或销毁。

数据迁移，尤其是分库分表这种大刀阔斧的改造，从来都不是一个纯技术活，它更像一个需要精心策划和严密执行的“运维+开发”联合项目。技术方案决定了下限，而细致的流程、严格的校验和充分的预案，才决定了上限。希望我分享的这些实战经验和踩坑记录，能让你在下次面对数据迁移这座大山时，手里能有一份更靠谱的地图，心里多一份从容。记住，慢就是快，稳就是赢。
