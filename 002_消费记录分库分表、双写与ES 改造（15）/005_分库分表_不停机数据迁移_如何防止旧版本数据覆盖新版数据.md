# 005_分库分表_不停机数据迁移_如何防止旧版本数据覆盖新版数据

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

本文比较双写、同步消息写新表失败重试、历史迁移和一致性校验修正执行 UPDATE 时，使用 update_time 还是 version 判断数据新旧。本文同时记录用户已确认的切写前后 version 维护及停写交接方案；设计确认不代表已有代码完成改造或上线效果经过验证。

## 1 面试口述精炼版本

**推荐 version：需要判断同一记录的修改先后**

update_time 记录修改时间，version 记录同一条记录第几次修改。时间能区分先后时，比较 update_time 可以拦住旧数据；但同一记录可能在同一秒内修改多次，如果保存的时间相同，就无法仅凭时间判断谁更新。version 每次业务修改递增，可以明确区分这两次修改。详见 [2.1](#21-update_time-能解决什么不能解决什么)、[2.2](#22-示例同时间戳的旧补偿为什么可能覆盖新数据)。

**切写前：旧表生成版本，新表比较并保存版本**

旧表主写期间，业务数据修改、version 递增和本地消息记录在同一个旧库事务中提交，后台定时扫描消息写新表。双写、消息重试、迁移和校验修复都携带对应的数据与版本，新表只接受更大的 version，并保存传入版本，不自行加一。这样较新数据先到，就拒绝后到的旧数据；较旧数据先到，后续较新数据仍能更新。详见 [2.3](#23-双写阶段旧表与消息同事务提交后台写新表)、[2.4](#24-同步消息写新表失败重试历史迁移与校验修复阶段)。

**切写时：先停旧写、清理旧方向任务，再开放新写**

采用短暂停写交接：暂停旧表所有业务写入口，等待在途事务结束，处理完本地消息中的未完成任务，结束历史迁移和修复任务，再完成最终一致性核对。确认旧方向不会再写新表后，才开放新表业务写入；任一步未完成都不能继续切写。这样避免两边同时生成版本或旧任务干扰新表业务状态。切读期间仍持续双写，停写只发生在最终写入交接窗口，时长需演练评估。详见 [2.5](#25-切写交接阶段先停旧写并清理旧方向任务)。

**切写后：新表业务更新自行递增版本**

新表接管业务主写后，在同一事务中修改业务字段并递增自身 version，从已有版本继续增加，不重置；旧表停止写入和同步。例如切写时新表 version=8，下一次成功业务更新后为 9。因为新业务状态由新表产生，版本也必须由新表维护。详见 [2.6](#26-切写后阶段新表业务更新自行递增-version)。

**版本防覆盖，重试和校验负责追平**

version 解决的是已有记录更新时的新旧顺序，不能自动补上漏写。还需要可靠保留失败任务、重试补写、迁移覆盖完整范围，以及校验发现差异后修复并复核。相同版本但字段不同、物理删除等情况不能仅靠比较版本解决。详见 [2.7](#27-version-的作用边界防覆盖不等于最终一致已完成)。

## 2 详细方案

### 2.1 update_time 能解决什么，不能解决什么

**共同点：都需要在实际 UPDATE 中比较**

不论使用时间还是版本，都不能只在 Java 查询后判断，再执行无条件 UPDATE。查询与更新之间，新表可能已被其他任务修改；条件必须在实际写入时生效，数据也必须携带与它对应的时间或版本。

**update_time：来源时间更晚时容易判断，相等时无法区分**

例如旧任务携带“异常、10:00”，新表已经是“成功、10:06”，条件更新能拒绝旧任务。这个场景不必为了处理并发就一定引入 version。

真正的缺口是：不同内容可能保存相同更新时间。

- 允许相等时间覆盖，迟到的旧数据可能覆盖较新内容。
- 只允许时间严格更晚，能拒绝相等时间的旧数据，也可能拒绝相等时间的较新数据。

所以，简单把 `<=` 改成 `<`，没有解决“如何辨认相等时间下的数据先后”。

**version：用修改序号区分同一条记录的不同状态**

例如某条记录先是 version=2，后来业务修改为 version=3。即使两次 update_time 相同，也能知道 version=3 更新。版本只比较同一条记录，不要求不同交易之间的 version 可比较。

参考文章 01_1 在[第 86～89 行](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:86>)采用更新时间、更晚或相等覆盖。参考文章 04 在[第 163 行](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_04.md:163>)提出 update_time 或 version 两种标识，但后续 SQL 使用时间戳，没有给出完整的 version 维护方案。本文的版本流程是结合项目目标提出的设计建议。

### 2.2 示例：同时间戳的旧补偿为什么可能覆盖新数据

**前提：两份内容不同，但保存的时间完全相同**

新表已有 S1。示例假设实际时间精度使两次修改都保存为 10:00:00；本地消息保存本次业务修改的数据，且后台 UPDATE 会写入核心流水号字段。这些实现前提尚未核验。

1. 消费过程中，旧表修改部分字段，形成数据 A，此时核心流水号为空，update_time=10:00:00。同事务记录携带 A 的消息；后台写新表失败，消息保留待重试。

2. 同一秒内，核心系统返回流水号，旧表补上该字段，形成数据 B，update_time 仍为 10:00:00，并在同事务中记录 B 的消息。

3. B 双写成功，新表已有核心流水号。

4. 消费流程结束后，补偿重试 A。如果允许相等时间更新，就可能把新表中的核心流水号覆盖回空值。

这不要求整个消费流程在一秒内结束，只要求其中两次字段修改保存了相同时间戳。若两次保存的时间实际不同，该具体例子便不成立。

**改用 version：两种到达顺序都能保留较新内容**

假设 A 对应 version=2，B 对应 version=3，数据和版本一起传递。

1. B 先写入新表，新表保存核心流水号及 version=3。

2. A 补偿随后到达，尝试用 version=2 更新。

3. 数据库判断 `新表 version < 来源 version`，即 `3 < 2` 不成立，拒绝 A。

4. 如果顺序相反，A 先到、B 后到，B 执行时 `2 < 3` 成立，仍能将新表推进到 version=3。

相同时间戳不再影响判断。相反，只采用严格时间比较时，A 如果先到，B 会因时间相等而被跳过，新表可能一直缺少流水号。

### 2.3 双写阶段：旧表与消息同事务提交，后台写新表

本节及 2.4 均适用于旧表主写阶段。双写流程以 [007 的本地消息表与重试机制](<./007_分库分表_不停机数据迁移_业务双写.md#22-本地消息表与重试机制>)为依据，来源为参考文章_03；本文的切写前后 version 维护已获用户确认，具体代码与发布步骤仍待验证，不据此声称 007 已实现版本控制。旧表新增记录的版本初始化及发布步骤仍需落实。

#### 2.3.1 旧表处理：修改业务数据、递增版本并记录消息

业务更新旧表时，在同一个旧库本地事务中完成业务字段修改、version 递增和本地消息记录插入。消息保存本次修改对应的数据与新版本，不能拿旧字段拼上后来查询到的版本。消息插入失败时，业务修改与版本递增一起回滚。

以下为旧表 UPDATE 核心示例，需与消息插入放在同一本地事务中：

```sql
-- expected_version 来自本次修改前读取的旧表记录。
-- 未命中时重新读取并判断业务状态，不为未成功的更新生成同步消息。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
-- 确认更新成功后，在当前事务内插入本次数据和新版本的消息记录，再提交。
```

这样旧表提交成功时，同步任务也已持久化。例如旧表由 version=2 更新为 version=3，消息同时记录 version=3 对应的数据；应用随后崩溃，恢复后仍能扫描该消息。

#### 2.3.2 新表处理：后台读取消息，比较并保存版本

后台任务扫描已提交的待处理消息，按 merchantNo 路由、serialNo 定位新表记录。对已有记录，只接受更大的 version，业务字段与传入版本一起更新，不自行加一。

```sql
-- source_version 来自消息中与数据对应的旧表版本，不是新增字段。
-- 示例仅展示部分字段；实际需携带该版本对应的完整同步数据。
UPDATE new_record
SET status = :source_status,
    core_serial_no = :source_core_serial_no,
    update_time = :source_update_time,
    version = :source_version
WHERE serial_no = :serial_no
  AND version < :source_version;
```

确认新表写入成功后，后台任务将旧库消息标记为完成；写入失败则保留待处理消息，进入重试。新表提交与旧库消息完成标记不是一个本地事务，因此仍可能重复执行，处理见 2.4.1。UPDATE 未命中不能一律算成功，需按 [2.7](#27-version-的作用边界防覆盖不等于最终一致已完成)区分原因。

### 2.4 同步消息写新表失败重试、历史迁移与校验修复阶段

以下场景都使用 2.3.2 的新表版本条件更新，但数据来源和处理职责不同；它们可与业务双写并发，不表示必须依次串行执行。

#### 2.4.1 同步消息写新表失败重试：沿用原消息，不生成新版本

**消息重试处理：** 后台任务处理同步消息、写入新表失败后，保留原消息并再次处理其中的数据与版本；失败记录重试次数，超过阈值告警。更新消息状态属于消息处理，不属于旧表业务更新；重试不重新执行旧表业务操作，也不递增旧表 version。重试退避、超限后处理及并发领取方式仍需按 007 落实，不以重新读取旧表替换原消息内容。

**新表处理：** 重复使用原消息的 version 执行条件更新。例如 version=2 的消息失败后，新表已经收到 version=3，重试 version=2 时不能覆盖新表。若此前新表已写入 version=2，但响应丢失或消息完成标记失败，再次处理时核对相同版本和内容，避免重复产生业务结果；同版本内容不同则保留差异并排查。消息完成状态的判定仍需实现验证。

#### 2.4.2 历史迁移：读取旧表已有数据与版本

**旧表：** 迁移工具读取同一条记录对应的业务数据与 version，不修改旧表，也不为搬运生成新版本。旧表继续接受业务更新，并按 2.3.1 递增版本、记录消息。

**新表：** 对已存在的记录，按迁移数据携带的版本执行条件更新。例如迁移读到 version=2，随后 version=3 的业务消息先写入新表，迁移再执行时 `3 < 2` 不成立，跳过旧数据；若迁移先到，后续 version=3 仍可更新。新表保存来源版本，不自行递增；目标记录缺失时进入 INSERT 流程，不能将 UPDATE 未命中视为已迁移成功。

#### 2.4.3 一致性校验修复：读取旧表依据，修复新表差异

**旧表：** 作为旧表主写阶段的比较依据，提供记录是否存在、业务字段和对应 version。校验读取不改变旧表版本；并发业务更新仍按 2.3.1 处理。

**新表：** 比较业务内容以发现差异，对已有记录的修复执行版本条件更新。例如校验读取旧表 version=2 后，业务更新为 version=3，且消息已写入新表，此时 version=2 的修复应被拒绝。随后重新核对差异，不能把跳过更新直接记为修复成功。

相同 version 不能替代字段校验；版本相同但内容不同仍需排查，具体修复方式不能由大小比较自动决定。校验修复保存来源版本，不自行递增。

### 2.5 切写交接阶段：先停旧写并清理旧方向任务

**采用方案与适用边界**

以下是用户自行确认的项目方案：本地消息表 + 定时扫描负责旧表主写期间的增量同步；最终切写采用短暂停写交接，按“暂停旧表业务写入 → 清理旧方向任务 → 最终核对 → 开放新表业务写入”执行。这是最终写入交接，不是读流量灰度期间关闭双写，也不声称整个迁移完全没有停写窗口。

**具体操作与完成条件**

1. **暂停旧表业务写入。** 关闭所有旧表业务写入口，包括相关接口、业务消息消费、定时任务和脚本；新表业务写入保持关闭。等待已进入旧表的事务提交或回滚，核实提交结果未知的事务，确认不再产生新的旧表业务变更和同步消息。不能只关闭接口就认为旧写已经结束。
2. **处理完未完成消息。** 在旧写已停止后，继续运行本地消息扫描与重试，将最终提交的消息处理完。失败、超限或结果未知的任务必须解决，不能删除消息或直接标记完成来清空积压。按既有版本及重复处理规则核实结果，确认没有待处理、重试中或正在执行的消息任务后，再停止旧表到新表的扫描与重试调度。
3. **结束迁移与修复任务。** 确认历史迁移范围处理完成、遗留差异完成修复，停止相关调度，等待已发出的数据库操作结束并核实结果。旧表业务写入和新表业务写入此时仍保持关闭；不能只停调度而留下在途写入。
4. **完成最终一致性核对。** 在两边业务停写、旧方向任务无在途写入的条件下，核对记录存在性、业务字段及对应 version，确认新表已承接旧表最终状态。发现差异时继续保持停写，完成修复、再次等待任务结束并重新核对；有差异或结果未知就不通过。
5. **隔离旧方向后开放新写。** 确认旧表写入口、消息扫描与重试、迁移和修复入口不会再向新表发起旧方向写入，并核对重启后不会按旧配置自动恢复。随后一次性将业务写入入口切到新表，按 2.6 的规则维护 version；旧表保持停止写入和同步。

每一步都以前一步完成为前提。任一步失败、仍有未解决任务或结果不明，都保持停写，不开放新表业务写入；故障处置及恢复方式需在演练中落实，不能临时跳过检查。

**为什么必须先清理再交接**

版本比较只能比较数值，不能代替写入职责交接。例如新表已由业务把 version=8 更新到 9，旧方向仍有携带 version=9 的消息时，双方的 9 未必代表同一次修改；若旧方向数据版本更大，还可能覆盖新表当前状态。因此不能仅靠比较 version 就允许旧方向任务继续写入。先完成旧状态同步、排空在途操作并隔离旧写，再把版本生成权交给新表，才能避免这类冲突。

停写窗口包含事务收尾、消息追平、任务退出和最终核对所需时间，不能预先承诺固定分钟数。窗口时长、超时处理及入口隔离能力必须通过演练评估；本节记录方案，不表示已实施或验证。

### 2.6 切写后阶段：新表业务更新自行递增 version

**旧表处理：** 旧表停止业务写入和同步，不再生成新的业务版本；旧方向消息、迁移和修复任务不再写新表。保留旧表数据不等于保留实时副本，回切旧表不能只改路由；切回前的数据恢复与验收方案仍待另行确认。

**新表处理：** 新表成为唯一业务主写表，业务更新时在同一事务中修改业务字段并递增自身 version，失败回滚时两者一起回滚。已有记录沿用切写时的版本，不重新初始化，也不再等待旧表提供新版本。

以下为新表已有记录的业务更新示例，与切写前“保存来源版本”的 SQL 区分：

```sql
-- expected_version 来自本次业务修改前读取的新表记录。
-- 未命中时重新读取并判断业务状态，不能直接执行无条件覆盖。
UPDATE new_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

例如新表切写时 version=8，成功更新后变为 9；重置为 1 会破坏已有版本顺序，业务数据变化而版本不变也无法标识新状态。切写前版本来自旧表，切写后版本由新表产生，但同一记录的版本序列持续递增。新建记录的初始化规则、业务请求重试幂等及并发失败处理仍需落实，不把本示例当作完整实现。

### 2.7 version 的作用边界：防覆盖不等于最终一致已完成

**UPDATE 没命中，先区分原因**

新表版本更大，表示这次数据较旧；版本相同且内容相同，可以按重复写入处理。版本相同但内容不同，需要保留差异并排查。目标记录不存在时也可能影响 0 行，不能一律当成成功；缺失记录需要补写，属于 INSERT 与校验补齐流程。

**最终追平仍需要可靠重试和校验**

例如旧表 version=3，新表仍为 version=2。version 比较不会主动把数据送到新表，需要同步消息写新表失败重试或校验修复真正写入 version=3。失败任务不能丢失，迁移范围不能遗漏，差异要持续处理并复核；当旧版本都无法覆盖、最新数据最终写入成功，才能让记录追平。

**本文不把其他问题归为版本比较已经解决**

物理删除会移除记录及版本，迟到 INSERT 仍可能重新插入旧数据。本文明确已有记录 UPDATE 的版本处理，以及切写前后版本生成方和旧任务交接方案；新增、删除、回切恢复和具体交接实现仍需分别落实，不能据此宣称所有问题都已解决。

## 3 已确认规则

- 采用本地消息表 + 定时扫描，由后台任务直接写新表；旧表业务数据与消息记录同一本地事务提交。
- 切写前旧表生成 version，新表比较并保存传入版本；切写后新表业务字段更新与 version 递增在同一事务中完成，沿用已有版本，不重置。
- 最终切写采用短暂停写交接：暂停旧表业务写入，等待在途事务结束，处理完未完成消息，结束迁移和修复任务，完成最终一致性核对，隔离旧方向后才开放新表业务写入；任一步未完成不进入下一步。
- 切写后旧表停止写入和同步；不得仅凭版本比较允许旧方向任务继续写新表。
- 文档需说明采用的方案、具体操作与完成条件、设计原因及尚未验证的边界；停写窗口时长需演练评估。

- 章节先按双写、同步消息写新表失败重试、历史迁移和一致性校验修复划分，再在各阶段内区分相关处理职责；双写流程以 007 的本地消息表与重试机制为依据。
- 同步消息写新表失败重试只涉及消息处理与新表写入，不属于旧表业务更新；消息表位于旧库，不等于重试需要重新处理旧表。

- **用户自行确认的项目方案：双写期间逐步完成查询改造和上线。** 后台列表查询由旧表切换到 ES，其他查询功能由旧表切换到新表；对应功能上线后，再开始灰度切换读流量。
- **读流量通过应用配置逐步切换。** 将少量读请求路由到对应的新查询链路（后台列表查 ES，其他查询查新表），其余读请求继续查旧表；可参考按用户 ID 哈希划分灰度范围，以 5% → 20% → 50% → 100% 逐步扩大比例。
- **每个灰度阶段都要观察后再扩大。** 监控业务成功率、查询结果、响应时间，以及 ES 或新库的负载；首阶段观察 30 分钟至 1 小时作为参考，正常后再扩大比例，每次扩大后仍需观察。比例和时间是参考值，不表示已通过实际验证。
- **整个切读期间必须持续双写。** 业务仍以旧表主写，并同步新表，不因暂停灰度或切换查询而关闭双写；旧表持续接收业务变更，以保留通过配置随时切回旧表查询的条件。仅保留旧表而停止写入，不能保证安全回切；实际回切能力仍需验证。
- **持续双写是对参考文章 04 切读步骤的项目调整。** 参考文章 04 的[读灰度与观察步骤](<./999_分库分表 + 数据迁移_参考文章_04.md:452>)作为参考，但不采用其[切读前暂停双写](<./999_分库分表 + 数据迁移_参考文章_04.md:444>)的安排。读流量灰度用于验证查询结果和性能，本阶段不切换业务主写目标。
- 本文回答双写、同步消息写新表失败重试、迁移和一致性校验修正执行 UPDATE 时，使用 update_time 还是 version、为什么，以及相应示例。
- 消费流程中可能在同一秒多次修改记录，例如补充核心流水号；这不代表整个消费流程一秒内完成。
- 同一笔交易通过 merchantNo 路由、serialNo 定位，serialNo 全局唯一且不复用。
- 时间或版本比较应在实际 UPDATE 中执行，不能只在 Java 查询后判断。
- 本次写入比较结论和 version 推荐方案；现有代码、字段和迁移文档的时间比较规则尚未统一改造，不将文档建议写成已实现事实。

- 未完成消息、超限重试和正在执行任务的排空标准，以及旧方向调度停止、重启隔离和在途写入收尾是否有效。
- 最终数据与版本核对的范围、完成标准，停写窗口耗时、超时及失败恢复演练。
- 新表主写后的原子版本递增、并发冲突、业务请求重试与新记录版本初始化。
- 切写后如需回切旧表，增量数据恢复和回切验收方案。

- 后台列表查 ES、其他查询查新表的灰度配置是否生效，持续双写期间切回旧表查询的正确性与操作流程是否经过验证。
- 旧表所有修改入口如何维护 version，初始化基线及部署顺序。
- 业务修改和版本递增是否在同一事务中，如何处理并发更新失败。
- 同步消息是否包含该版本的完整业务数据，如何确保数据与 version 对应。
- 旧表业务更新、版本递增和本地消息是否原子提交，原消息重试与完成标记是否能可靠恢复。
- 四条写入路径是否统一执行原子版本条件更新。

- 原有时间比较方案切换到 version 的具体实施，以及并发、乱序、漏写和重复执行测试。

## 5 异议与分析

**毫秒时间不等于业务修改序号**

提高时间精度可以减少碰撞，但不能保证两次修改绝不保存同一时间，也不能单靠精度解决时间来源不一致或时钟回退。因此，对同一记录的修改顺序有明确要求时，统一维护 version 更直接。

**version 的可靠性来自维护规则，而不是字段名**

只有业务修改都递增版本、数据和版本原子提交、新表接收对应数据并原子比较，版本才能表达先后。漏增版本、两边独立递增，或者把新版本配上旧数据，都可能破坏判断。推荐 version 的同时，也意味着需要改造并核验所有相关写入入口。

**已有文档与本篇的关系**

原有并发分析文档说明时间方案的风险，本篇给出比较结论和推荐改造方向。历史迁移流程仍见 [008](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/008_分库分表_不停机数据迁移_在线历史迁移.md:1>)。本文不将原有时间方案直接改写为已经采用 version，也不把参考文章的简略建议当作项目完整实现。
