## 参考文章与项目方案对比

#### 参考文章与项目如何防止旧数据覆盖新数据？两者有何差异，是否需要 Redis 锁？

**当前结论**：文章主要依靠 Redis 锁和 Java 比较业务 `version`；项目优先使用业务版本和 ES 的 `version_type=external` 原子比较。Redis 锁不是项目防旧写的核心条件。

Redis 锁只能减少同一业务键的应用线程并发，不能判断事件新旧，也不能撤回已经发出的 ES 请求。文章的版本判断还受查询近实时刷新影响，锁获取失败时直接跳过等代码边界也可能把未完成操作当成成功；因此不能把文章示例当作完整防旧写实现。

项目将新表业务版本、具体物理索引和稳定 `_id` 结合起来，由 ES 在同一索引、同一 `_id` 内原子拒绝相同或更低版本。这里的保护对象是新增、更新及其重投过程中的版本乱序；MySQL DELETE 不调用 ES Delete API，因此不设计删除状态或删除版本屏障。只有 ES 之外存在必须串行化的共享副作用时，才另行评估 Redis 锁。
