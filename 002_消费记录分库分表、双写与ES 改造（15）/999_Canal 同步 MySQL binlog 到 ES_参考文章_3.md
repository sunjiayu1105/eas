**二、文章原详细方案：按“总—分”结构整理**

**1. 总体方案：通过 Canal 同步 MySQL 数据，通过 ZooKeeper 协调主备**

文章要解决两个问题：

- 将 MySQL 数据变更同步到 Elasticsearch。
- 在同步节点发生故障后，由其他节点接替工作。

核心数据链路是：

```
MySQL binlog
    ↓
Canal Server：读取并解析数据变更
    ↓ TCP
Canal Adapter：消费变更、转换数据
    ↓
Elasticsearch：保存同步结果
```

配套职责是：

- **Canal Admin**：管理配置、节点和订阅任务。
- **ZooKeeper**：协调主备、帮助客户端找到活动 Server。
- **Prometheus + Grafana**：监控同步速度、延迟和积压。

文章以 TCP 直连 Canal Server 为主要示例，也说明 Adapter 可以改为订阅 Kafka、RocketMQ。

**2. 数据采集原理：Canal 模拟 MySQL 从库**

Canal Server 模拟 MySQL 的复制协议，以从库身份向 MySQL 请求 binlog，也就是数据库变更日志。

处理过程是：

1. Canal 向 MySQL 发起 binlog 订阅请求。
2. MySQL 推送 binlog。
3. Canal 解析日志，将其整理成结构化变更消息。
4. Adapter 消费消息并写入下游。

其中：

- **Server** 是运行 Canal 服务的进程。
- **Instance** 是 Server 承载的具体订阅任务，配置源库、账号和表过滤规则。
- 多个数据源可以分别建立多个 Instance。

**3. 高可用原理：Server 和 Client 分别协调运行资格**

文章将高可用分为 Server 侧和 Client 侧。

Server 侧依赖 ZooKeeper 的两种机制：

- **临时节点**：与客户端会话绑定，会话失效后移除。
- **Watcher 监听**：在节点状态变化时通知相关参与者。

工作流程是：

1. 多个 Server 竞争同一个 Instance 的运行资格。
2. 成功创建对应临时节点的 Server 启动该 Instance。
3. 其他 Server 上对应 Instance 保持备用状态。
4. 原工作节点的临时节点消失后，其他节点重新竞争。
5. 客户端通过 ZooKeeper 找到当前提供该 Instance 的 Server。

这意味着主备控制围绕 **Instance** 展开，不能简单理解成整个集群永远只有一台 Server 工作。

Client 侧也介绍了通过临时节点竞争消费资格的机制，协调：

- `get`：获取数据。
- `ack`：确认处理完成。
- `rollback`：回退未确认批次的消费状态。

文章将其目的概括为保证消费有序性。但该描述不能直接扩大为“任何不同订阅都不能消费同一个 Instance”，实际范围还需要结合订阅身份判断。

故障发现、会话失效、重新选举和重连都需要时间，因此该方案不代表零中断。

准备依赖：

**9. ES 映射配置：把关系表字段转换成 ES 文档**

|参数|作用|
|---|---|

|`sql`|定义字段和映射关系|
|`etlCondition`|配置全量导入条件|

原文还展示了 `upsert` 配置，其准确行为需要结合对应版本核对。

SQL 列名或别名与 ES 字段对应，不能使用 `select *` 隐式映射所有字段。

**10. 映射 SQL 的限制**

文章列出的限制包括：

- 主表不能是子查询。
- 使用 `LEFT OUTER JOIN`，最左侧表为主表。
- 关联从表如果使用子查询，子查询不能包含多张表。
- 主 SQL 不能包含 `WHERE`。
- 从表子查询中的过滤条件可能引入同步一致性问题。
- 关联条件使用字段之间的等值关联，不能随意添加常量判断。
- 关联字段需要满足出现在主查询字段中的要求。

其原因是 Adapter 不仅要生成查询结果，还要根据单张表的变更判断哪些 ES 文档受到影响。因此映射 SQL 不能等同于任意业务查询 SQL。

**11. 全量导入与增量同步**

文章说明 Adapter 同时支持：

- 全量导入已有数据。
- 持续同步新增变更。

但文章没有完整展开：

- 全量导入从哪个一致性时点开始。
- 增量起点如何与全量衔接。
- 全量与增量并发时如何避免旧数据覆盖新数据。
- 失败后如何恢复。

所以，这部分属于能力介绍，不能直接作为项目完整的历史初始化方案。

**12. 历史版本故障与监控**

文章记录了 `1.1.5-SNAPSHOT` 下的类加载异常 `LinkageError`，并提出：

- 暂时采用单实例。
- 修复问题。
- 改用 MQ 模式。

这是旧版本案例，不能直接认定当前 1.1.7 也存在同样问题。

监控方面，文章通过 Canal 的指标端口，接入 Prometheus 和 Grafana，主要观察：

- 事件、事务和数据行吞吐量。
- 同步延迟。
- 网络流量。
- 线程阻塞。

```
→ 故障后确认旧主停止或隔离
→ 启动备用进程
→ 使用相同订阅身份恢复
```

二者控制层次不同：

- 文章侧重谁可以消费。
- 008 侧重哪个 Adapter 进程允许运行。

这不是底层协议冲突，但必须明确采用哪种部署控制方式，不能把文章的 Client HA 原理写成 008 已实现的自动接管能力。

**2. ZooKeeper 发现 Server 与 Adapter 自动接管不能混为一谈**

配置 ZooKeeper 地址可以帮助发现活动 Server，但不能独自证明：

- 多 Adapter 消费资格已正确协调。
- 备用进程会自动启动。
- 旧主能够被隔离。
- 接管后位点正确恢复。

008 的外部管理器、仲裁和隔离方式目前仍待确认。

**3. 消费身份尚未明确**

008 要求备用节点使用相同订阅身份，但 `groups.groupId` 不能未经核对就视为完整 TCP 消费身份。

需要核对实际连接器如何标识客户端、如何关联位点，以及主备进程配置如何保持一致。

**4. 008 是整个进程接管，文章未证明相同切换粒度**

008 主 Adapter 同时消费 `db0`、`db1`，备用节点接管整个进程。

文章的客户端协调机制需要结合每个订阅连接判断，不能直接认定两个通道一定共同切换。

**5. 部署成功不等于满足项目写入要求**

即使 Adapter 能启动并收到消息，仍需要验证：

- 映射 SQL 能否加载。
- 各物理分表是否正确匹配。
- ES 字段及 `_id` 是否正确。
- 历史索引能否定位。
- 部分失败是否阻止 ack。
- 重放是否保持索引、操作语义和顺序。
- 接管后是否使用正确消费进度。

文章的通用部署步骤没有覆盖这些项目要求。

**6. 旧版本配置和热更新不能直接套用**

ES 参数层级、认证、`upsert`、重试、批量和热更新范围，都要按 Adapter 1.1.7 核对。

原文的 `1.1.5-SNAPSHOT` 类加载异常不能直接当作当前故障，也不能据此直接决定改为单实例或 MQ。
