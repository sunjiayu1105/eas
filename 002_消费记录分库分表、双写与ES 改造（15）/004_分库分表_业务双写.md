# 004_分库分表_业务双写

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

本文承接方案设计文档的业务双写章节及相关规则。已确认方案是设计要求，不代表实现和运行效果已经验证；旧表版本、补偿、迁移和校验采用本次整合的最新规则。

## 1 面试口述精炼版本

**保留旧业务，同时验证新表链路**

双写用于在旧表继续承接业务时，验证未来的新表写入及 ES 同步链路。分库分表与后台查询迁移到 ES 分期推进，旧表依赖未切完时不能直接停用旧表。发现差异后记录并排查原因，程序修数和复核；不能仅凭修数成功认定写入链路正确，具体见[失败处理](#23-高旧表主写与新表失败处理)及[收尾条件](#27-停止双写后的业务行为)。

**先完成改造，再并行双写与迁移**

先新增旧表版本字段、初始化为 1，并完成全部旧表写入口的版本维护改造，再开启应用层双写。双写生效后即可启动历史迁移，两者并行，不等待双写稳定观察期。这样迁移期间的业务变更也能进入新表写入和失败补偿流程，详见[上线顺序](#22-高上线顺序与双写开关)。

**先确认旧表提交，再尝试新表**

旧表仍为主写表。只有明确确认旧表事务提交成功，才尝试写新表；旧表失败或结果未知时，不继续写新表。新表失败不影响已提交的旧表业务，记录日志、告警并进入消息重试。人工排查原因，数据交由校验修正，详见[失败处理](#23-高旧表主写与新表失败处理)。

**业务更新、补偿和迁移分别维护版本**

旧表业务更新在 SQL 内递增版本；新表业务更新以读取到的新表版本进行乐观锁判断，成功后递增。更新补偿沿用原数据和原预期版本。迁移和校验使用旧表同一快照的数据及版本，不重新初始化或额外递增。不同场景的 SQL 和示例集中见[版本维护](#21-高双写补偿迁移与一致性校验的版本维护)。

**记录缺失时等待迁移，已有身份继续沿用**

历史记录尚未迁入时，新表更新或删除影响 0 行不阻断旧表业务，也不立即补建；等待迁移回填，旧快照覆盖及删除回插由校验处理。新旧表主键不同，通过全局唯一的 `serialNo` 关联；新表首次创建时生成 `consumeId`，后续沿用已有身份，详见[缺失记录](#24-高历史数据未迁入时的双写处理与一致性修正)和[身份关联](#25-中双写记录的身份关联)。

**校验通过后逐步切换，保留 ES 同步**

旧表与新表、新表与 ES 两项校验连续 1 个月无差异后，逐步切换查询；全部旧表依赖切换完成后，两项校验再次连续 3 个月无差异，再停止旧表写入。切换为新表主写时无需修改新表写入链路代码，新表到 ES 的同步及校验继续保留，详见[收尾行为](#27-停止双写后的业务行为)。

新表独立递增与来源版本比较仍有并发边界，尤其新表版本大于旧表时，现有修数 SQL 可能无法修复。本文保留这些风险，不将“有校验兜底”视为最终一致性已获证明。

## 2 详细方案

### 2.1 高：双写、补偿、迁移与一致性校验的版本维护

#### 2.1.1 参考文章方案

**通过更新时间判断数据新旧**：参考文章使用 `gmt_modified` 等更新时间字段判断迁移数据的新旧，没有明确要求为旧表新增 `version` 字段，也没有展开系统内所有写入口的统一改造。参考来源定位：[更新时间比较（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

#### 2.1.2 参考文章方案存在的问题

**时间戳相同不能判断数据新旧**：文章允许较晚或相等的更新时间覆盖，但没有说明时间精度不足、不同变更具有相同时间戳时如何排序。以下假设时间只保存到秒，不代表已核实当前项目字段精度。参考来源定位：[更新时间覆盖规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

**允许相等时间覆盖，可能覆盖新数据**：

1. `10:00:00.100`：旧表插入金额 **100**，双写新表成功。
2. `10:00:00.200`：迁移任务读取旧表金额 **100**，尚未写入新表。
3. `10:00:00.300`：业务将旧表金额更新为 **200**，双写新表成功。
4. `10:00:00.400`：迁移任务准备将金额 **100** 的旧快照写入新表。
5. 由于时间只保存到秒，旧快照和新表记录的更新时间都是 `10:00:00`。
6. 如果允许时间相等时覆盖，迁移就会把新表金额从 **200** 改回 **100**。

这是对文章允许相等时间覆盖规则的风险推演。参考来源定位：[允许相等时间覆盖（第 89 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

**改用严格大于，又可能拒绝同步真实变更**：

1. 同一秒内先插入金额 100，双写成功。
2. 旧表金额更新为 200，但新表更新失败。
3. 两边时间都保存为同一秒，金额却不同。
4. 校验发现差异，但若只允许严格较晚的来源时间覆盖，就会拒绝修复。

严格大于是对比用的假设方案，不是文章采用的规则；不能仅以时间相等认定内容一致。参考来源定位：[文章的时间比较规则（第 86 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:86>)。

#### 2.1.3 已确认方案

**共用前提**：旧表新增 `version`，排查业务代码、定时任务、批处理和脚本等写入口。以下五种版本规则由项目自行决定，参考文章未直接给出。SQL 按 MySQL 8.0.33、InnoDB 事务表说明；表名及金额字段为示意，`:参数名` 由应用绑定，并非可直接执行的客户端脚本。新表 SQL 执行前按 `merchantNo` 路由到目标分片，实际事务边界仍需验证。

##### 2.1.3.1 双写旧表：业务更新时递增

旧表历史记录及新增记录的 `version` 初始化为 `1`。业务更新时，业务字段与 `version = version + 1` 在同一条 SQL 中执行；事务回滚时一起回滚。这样才能让旧表版本随业务变更推进，而不是仅依赖更新时间区分变更。

**前置上线顺序**：先新增旧表 `version` 并使历史记录具有初始值 `1`，再发布全部旧表写入口的版本维护改造。这两步在“服务升级与双写”阶段之前完成；准备期间不开启双写或历史迁移，全部入口改造完成后才进入双写阶段。该前置阶段是项目自行确定的安排，不是参考文章给出的步骤。

例如：

1. 新增字段后，历史记录为金额 **100**、版本 **1**。
2. 版本维护改造发布期间，尚未升级的服务把金额改为 **200**，版本仍为 **1**；此时迁移尚未开始。
3. 全部写入口升级完成后，业务再把金额改为 **300**，版本同步递增为 **2**。
4. 后续开启双写并启动迁移时，读取当前数据及对应版本；不再统一重置版本，也不追溯上线前的更新次数。

**技术实现：单条 SQL 原子更新**

```sql
-- 旧表业务字段和版本一起更新，避免两次独立提交只完成一部分。
UPDATE consume_record_source
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no;
```

InnoDB 通过排他锁协调同一记录的并发更新，数据库基于当前值递增版本。该 SQL 没有预期版本条件，只保证字段与版本一起变化，不是乐观锁，也不能阻止过期业务数据覆盖。

**解决的问题一：业务字段已提交，版本却没有更新**

1. 旧表金额为 **100**、版本 **1**，假设应用把金额更新和版本递增拆成两次独立提交。
2. 第一条 SQL 将金额改为 **200**，提交成功。
3. 第二条 SQL 执行前应用退出，版本仍为 **1**，无法用版本识别这次金额变更。
4. 改为同一条 SQL 后，金额与版本一起提交；事务回滚时二者一起回滚，不会留下这类部分提交状态。

这里的前提是“两次独立提交”。两条 SQL 如果放在同一个事务中，并在失败时整体回滚，也能保证一起提交或回滚；单条 SQL 让这两个动作直接绑定。

**解决的问题二：应用计算版本后写回，可能丢失一次递增**

1. 请求 A、B 都读取旧表版本 **1**，各自在应用中计算得到 **2**。
2. A 将业务字段和固定版本 **2** 写入并提交。
3. B 也将业务字段和固定版本 **2** 写入并提交；两次更新成功，版本却只增加了 **1**。
4. 若两次更新都由数据库执行 `version = version + 1`，B 等待 A 提交后基于当前版本 **2** 递增到 **3**。

##### 2.1.3.2 双写新表：检查自身版本后递增

更新已有新表记录前，读取其当前版本作为 `expected_version`，在同一条 SQL 中检查版本、修改业务字段并递增。这样可以复用最终切换后的业务更新逻辑，并拒绝基于过期新表版本执行的更新。

```sql
UPDATE consume_record_target
SET amount = :amount,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

**解决的问题：拒绝基于过期业务数据的覆盖**

1. 请求 A、B 都读取新表金额 **100**、版本 **1**，分别准备将金额改为 **200**、**300**。
2. A 使用 `expected_version = 1` 更新成功，金额变为 **200**、版本变为 **2**。
3. 若 B 不检查版本，就会直接将金额覆盖为 **300**，无法发现自己基于过期状态操作；加上版本条件后，B 的版本 **1** 不再匹配，更新影响 **0 行**。
4. 应用需要区分记录不存在与版本冲突；如何重读、重算或返回冲突由业务规则决定，不能直接把旧请求的预期版本改成 **2** 后继续覆盖。

该 SQL 使用新表预期版本进行乐观锁检查，数据库内部仍会加锁；它不提供跨库原子性。旧表目前只确认原子递增，是否增加预期版本条件尚未确认。

本例只处理已有新表记录；缺失记录的双写处理见 [2.4](#24-高历史数据未迁入时的双写处理与一致性修正)。

##### 2.1.3.3 新表更新补偿：沿用原预期版本

补偿保留原业务数据及首次更新新表时使用的 `expected_version`，执行相同的条件更新；不能重新读取最新版本，将同一次操作当作新更新。不是所有重试都不递增，而是只有原更新尚未成功且条件仍满足时，重试才完成那一次递增。

**第一次没有提交**

1. 首次更新使用预期版本 **5**，但事务未提交。
2. 新表仍为版本 **5**，期间也没有其他更新。
3. 补偿仍使用预期版本 **5**，成功后递增为 **6**。

**第一次已提交，只是响应丢失**

1. 首次更新已成功，新表版本变为 **6**。
2. 补偿仍使用原预期版本 **5**。
3. 条件不成立，不会再次递增为 **7**。

这可以阻止同一预期版本的重复更新，前提是版本没有被重置或重复使用。影响 0 行也可能由其他并发修改造成，不能直接认定为补偿成功，具体复核和失败处理仍待确认。新增、删除的补偿不能直接套用这条 UPDATE SQL。

##### 2.1.3.4 历史迁移：使用来源版本

迁移读取同一次旧表快照中的业务数据和 `version`，一起写入新表。新表不存在记录时，插入来源数据及版本；已有记录时，按当前约定使用 `version <= :incoming_version` 条件更新，成功后保存来源版本，不执行 `version + 1`。迁移只是复制业务状态，不应额外产生一次业务版本。

1. 迁移读取旧表金额 **300**、版本 **3**。
2. 新表不存在对应记录。
3. 迁移按新表规则生成 `consumeId`，插入金额 **300**、版本 **3**。
4. 不把版本重新设为 **1**，也不因迁移将版本递增为 **4**。

**解决的问题：避免把旧业务数据配上新版本**

1. 假设迁移通过两次不共享同一快照的查询分别读取金额和版本：第一次读到旧表金额 **100**，当时版本为 **1**。
2. 业务随后将旧表更新为金额 **200**、版本 **2**。
3. 迁移第二次单独读取版本，得到 **2**，可能错误地组装出“金额 **100**、版本 **2**”。
4. 若将金额和版本从同一次记录快照中读取，就会得到“100、1”或“200、2”，不会拼接出上述不存在的业务状态。

同一快照只保证来源数据与版本配对正确；读取后的并发变更仍受 [2.3](<./999_分库分表 + 数据迁移_方案设计.md#23-高迁移快照与删除回插>) 和 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>) 的边界限制。

**SQL 示例：迁移和校验更新已有记录**：应用无需先查询新表版本，数据库在同一条 SQL 中完成来源版本判断和写入。

```sql
-- incoming_amount 与 incoming_version 必须来自同一次旧表记录快照。
-- 仅更新已有记录，不修改已有 consume_id，也不在此处补建缺失记录。
UPDATE consume_record_target
SET amount = :incoming_amount,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version <= :incoming_version;
```

**适用边界**：同一业务记录的同一来源版本应对应同一份业务数据，但新表独立递增后，跨表版本数值不一定代表业务先后。迁移覆盖风险见 [2.3](<./999_分库分表 + 数据迁移_方案设计.md#23-高迁移快照与删除回插>)；允许同版本修复的原因，以及新表版本更大时无法修复的反例，见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。

##### 2.1.3.5 一致性校验：按旧表版本修正，不自行递增

**适用前提**：旧表仍为可信数据源。校验读取旧表同一次快照中的业务字段和 `version`，修数只改变新表，不递增旧表版本。

- **更新已有记录**：复用上方来源版本 SQL，满足 `version <= :incoming_version` 时，将新表业务字段和版本一起设为旧表快照值，不执行 `version + 1`。版本相同但字段不同也允许修正；新表版本更大时不会更新，处理方式仍待确认。
- **补建缺失记录**：插入旧表快照中的业务数据及版本，不重新初始化为 `1`，也不因补建额外递增。这里是校验修数，与双写阶段“不立即补建”的职责不同；并发插入和重试的幂等方式仍需确认。
- **删除多余记录**：旧表确实不存在该记录时，修数目标是删除新表多余记录；物理删除后不保留该行的 `version`，不额外新增删除标记。如何可靠判定缺失、避免并发误删，见[方案设计的校验待确认项](<./999_分库分表 + 数据迁移_方案设计.md#314-待确认方案>)。
- **复核与重试**：复核只读，不改变版本；重试修数仍使用所读取来源快照的版本，不因重试自行加一。重新读取旧表后如何处理版本变化，仍待确认。

**解决的问题：避免修数额外抬高新表版本**

1. 旧表为金额 **300**、版本 **3**，新表落后，为金额 **100**、版本 **1**。
2. 校验按旧表快照修正，新表变为金额 **300**、版本 **3**。
3. 假设旧表没有新变更，同一快照再次用于修数时，版本仍保持 **3**；如果每次修数都自行递增，就可能把新表推到 **4**、**5**，使其超过旧表，阻碍后续来源版本更新。
4. 修复后重新比较业务字段和版本；一致时结束本次修复，不能仅凭 SQL 返回行数认定完成。

校验的完整修复流程及并发边界见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。

### 2.2 高：上线顺序与双写开关

#### 2.2.1 参考文章方案

**双写开启后迁移**：先升级服务开启应用层双写，再启动历史迁移，两者并行运行；正文未要求等待双写链路稳定后才启动迁移。参考来源定位：[服务升级与双写（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)、[历史数据迁移（第 77 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:77>)。

**观察建议不等于迁移门槛**：检查清单建议开启双写后观察一个业务高峰周期，但未明确将观察完成设为启动迁移的前置条件。参考来源定位：[执行检查清单（第 143 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:143>)。

**校验后灰度切换**：迁移和一致性校验完成后，先灰度切查询，再灰度切写入；新库稳定运行后关闭旧库双写。参考来源定位：[一致性校验（第 94 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:94>)、[流量切换（第 117 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:117>)。

#### 2.2.2 参考文章方案存在的问题

文章给出了总体顺序，但没有把每个阶段的进入条件、完成条件和失败处置定义清楚。例如，迁移任务已经跑完一遍但仍有失败消息未重试，或者校验刚完成后又出现双写失败，此时直接进入灰度切读可能把未追平的新表暴露给查询。

#### 2.2.3 已确认方案

**先完成版本改造，再双写、迁移与切换**：新增旧表 `version` 并建立初始值 → 上线全部旧表写入口的版本维护改造 → 服务升级，开启应用层双写并启动历史迁移（双写生效后即可迁移，两者并行运行，不等待稳定观察期） → 一致性校验 → 灰度切查询 → 灰度切写入 → 稳定且满足收尾条件后停止旧表写入。前两步是项目新增的前置上线阶段，具体说明见 [2.1](#21-高双写补偿迁移与一致性校验的版本维护)；双写异常处理见 [2.3](#23-高旧表主写与新表失败处理)，迁移完成判定见 [2.4](<./999_分库分表 + 数据迁移_方案设计.md#24-高增量补齐与迁移完成判定>)，切换及回退见[方案设计第 4 部分](<./999_分库分表 + 数据迁移_方案设计.md#4-流量切换与回滚预案>)。

**解决的问题：避免先迁移、后双写留下变更缺口**

1. 假设尚未开启双写，迁移已经把流水 S1 的金额 **100** 写入新表。
2. 业务随后把旧表 S1 改为 **200**；此时没有双写，新表仍为 **100**。
3. 之后才开启双写，并不会自动补发此前这次变更。
4. 先开启双写，能让迁移期间的业务变更进入新表写入及失败处理流程；它不保证每次都成功，剩余差异仍需补偿和校验处理。

#### 2.2.4 待确认方案

- 各阶段尚未细化的进入条件；
- 各阶段的观察指标；
- 各阶段的失败处置。迁移完成、校验验收及切换回退的具体事项分别在对应章节确认。

### 2.3 高：旧表主写与新表失败处理

#### 2.3.1 参考文章方案

**旧库主写、新库补偿**：旧库写入是主流程；新库失败不阻断业务，记录、告警并补偿。参考来源定位：[应用层双写伪代码与失败处理（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

#### 2.3.2 参考文章方案存在的问题

文章没有明确补偿消息的可靠投递、重复消费和最终失败处理。新表超时、消息生产确认丢失，都只能说明结果未知，不能直接判定没有写入或没有投递。

1. 旧表提交成功，新表写入超时，失败消息发送后也未收到确认。
2. 如果新表确实未提交、消息也未到达队列，又没有后续核实与校验，新表就会持续缺失记录。
3. 如果新表实际已提交或消息已入队，直接重复执行又可能造成重复效果，需要幂等处理。

#### 2.3.3 已确认方案

##### 2.3.3.1 先判定旧表提交结果

旧表仍为主写表。只有明确确认旧表事务提交成功，才能继续写新表；旧表明确失败时请求失败，不继续写新表；提交结果未知时也不继续。结果未知不能直接当作事务失败，接口返回及核实方式仍待确认。

例如：

1. 应用向旧表提交事务，但因连接中断未收到提交确认。
2. 此时事务可能已提交，也可能未提交，应用不能仅凭异常作出结论。
3. 本次流程不继续写新表，避免在旧表尚未确认成功时推进第二次写入。
4. 后续只有明确确认旧表提交成功，才具备执行新表写入的前提；具体核实与恢复流程仍待确认。

##### 2.3.3.2 新表失败进入补偿

旧表已提交成功时，新表失败不影响接口成功，但必须记录错误日志、告警并将失败数据送入消息队列重试。更新补偿沿用原预期版本，见 [2.1.3.3](#2133-新表更新补偿沿用原预期版本)。

**解决的问题：隔离新表故障，并保留后续处理路径**

1. 旧表已成功提交流水 S1，新表写入因连接故障失败。
2. 若把新表失败直接作为接口失败返回，调用方会收到失败，但旧表中的业务实际上已经完成。
3. 当前方案按旧表提交结果返回，记录新表失败并告警；在失败消息可靠入队的前提下，后续由补偿重试处理。
4. 若补偿仍未修复差异，则由校验发现并修正，人工排查故障原因。消息可靠投递等未定边界仍不能视为已解决。

##### 2.3.3.3 补偿失败及严重异常的处置

重试仍失败时，人工排查并修复代码、配置或运行问题，数据交由校验程序修正；人工直接修数的风险及程序修数边界见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。双写出现严重异常时暂停迁移，继续由旧表承接业务。

#### 2.3.4 待确认方案

**结果判定与补偿衔接**

- 旧表已提交后，失败消息未可靠入队或投递结果未知时的核实与恢复方式；
- 旧表提交结果未知时，接口返回方式；
- 旧表提交结果的核实方式及确认成功后的恢复流程；
- 新表更新或补偿影响 0 行时，如何区分缺失、冲突与原操作已成功；
- 新增、删除补偿的幂等与乱序处理方式；
- 重试最终失败后由一致性校验任务修正数据的具体衔接方式。

**重试与运行参数**

- 消息队列的重试次数；
- 消息队列的重试间隔；
- 失败状态记录方式；
- 告警升级规则；
- 人工介入时机。

### 2.4 高：历史数据未迁入时的双写处理与一致性修正

#### 2.4.1 参考文章方案

**同步改造增删改**：改造 `Insert`、`Update`、`Delete`，但未明确新表记录不存在时影响 0 行的处理。参考来源定位：[业务写操作改造（第 16 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:16>)、[迁移并发问题说明（第 81 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:81>)。

#### 2.4.2 参考文章方案存在的问题

文章没有说明历史迁移尚未回填某条记录时，`UPDATE` 或 `DELETE` 影响 0 行后是否立即补建、重试或等待迁移。下方分别用更新、删除两个时序说明这一缺口。

#### 2.4.3 已确认方案

**缺失记录等待历史迁移回填**：仅在历史记录尚未迁入的前提下，新表 `UPDATE`、`DELETE` 影响 0 行不阻断旧表业务，也不立即补建；仍存在于旧表的历史记录由迁移回填。已删除记录不需要重建；若旧快照被回插，则由校验修正。新表作为可信数据源的验收要求见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。

以下两个例子均假设新表记录尚未迁入。

**更新前快照写入新表**

1. 迁移任务读取旧表，得到金额 **100**，暂未写入新表。
2. 业务将旧表金额更新为 **200**，提交成功。
3. 业务尝试更新新表，但记录尚未迁入，`UPDATE` 影响 **0 行**。
4. 迁移任务将之前读取的金额 **100** 插入新表。
5. 此时旧表金额为 **200**，新表金额为 **100**，由一致性校验任务发现差异并修正。

**删除前快照重新插入新表**

1. 迁移任务读取旧表中的流水 **S1**，暂未写入新表。
2. 业务删除旧表中的 **S1**，提交成功。
3. 业务尝试删除新表中的 **S1**，但记录尚未迁入，`DELETE` 影响 **0 行**。
4. 迁移任务将之前读取的 **S1** 插入新表。
5. 此时旧表已无 **S1**，新表却存在 **S1**，由一致性校验任务发现多余记录并删除。

#### 2.4.4 待确认方案

本点暂无独立待确认项；校验修数期间的重读、重试和失败处理集中见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。

### 2.5 中：双写记录的身份关联

#### 2.5.1 参考文章方案

**按业务键和分片键定位新库**：按业务主键或分片键写入新库；文章未定义当前项目的 `consumeId` 和 `version` 规则。参考来源定位：[应用层双写和分片路由（第 14 行）](<./999_分库分表 + 数据迁移_参考文章_01_1.md:14>)。

#### 2.5.2 参考文章方案存在的问题

文章没有说明旧表和新表主键规则不一致时如何稳定关联同一业务记录。

1. 旧表流水 S1 的主键是 O1，新表首次写入时生成主键 N1；这些标识仅为示意。
2. 新表已写入成功，但响应丢失，调用方准备重试。
3. 若重试又生成 N2，且未按业务唯一标识限制重复，新表可能出现两条 S1。
4. 通过 `serialNo = S1` 定位并沿用 N1，可以保持同一交易的身份；首次并发创建时如何保证唯一，仍是待确认项。

#### 2.5.3 已确认方案

新旧表使用各自主键，以全局唯一的 `serialNo` 关联同一交易。首次创建新表记录时按 `003_分库分表.md` 规则生成 `consumeId`，后续沿用已有 `consumeId`。业务更新和补偿的版本规则见 [2.1](#21-高双写补偿迁移与一致性校验的版本维护)。

同一笔交易通过不变的交易流水号 `serialNo` 关联新旧记录，商户号 `merchantNo` 在交易生命周期内保持不变。应用沿用 ShardingSphere-JDBC 这一应用侧分片组件，按商户号将新表 SQL 路由到对应实例和物理表。分片和主键设计见[003_分库分表](<./003_分库分表.md>)，本文不重新定义路由规则。

双写覆盖新增、修改、撤销、退货和物理删除。撤销和退货分别新增独立交易记录，撤销记录使用 `tradeType=BS0013`，退货记录使用 `tradeType=BS0024`，并通过关联字段指向原消费记录；原消费记录不直接改成“撤销”或“退货”。保留期清理与业务操作的区别见[到期删除规则](<./013_ES改造_ES_生命周期管理_到期删除.md>)。


#### 2.5.4 待确认方案

- 首次写入发生并发或结果不确定时，如何可靠定位并复用已有 `consumeId`。

### 2.6 业务双写与 ES 同步的边界

业务双写负责旧表与新表的数据库写入；新表提交后，由 ROW 格式 binlog（按行记录变更）向后续同步链路提供数据。新增、更新经 Canal Server、RocketMQ 和自定义消费服务异步写入 ES。ES 文档 `_id` 使用 `consumeId`，业务版本规则和目标索引定位以[011_ES改造_ES_索引设计、创建与写入](<./011_ES改造_ES_索引设计、创建与写入.md>)为准。

数据库到期清理产生的 DELETE 不代表需要向 ES 逐条发送删除请求；按当前保留期方案，ES 由 ILM（索引生命周期管理）删除整个过期月份索引，详见[013_ES改造_ES_生命周期管理_到期删除](<./013_ES改造_ES_生命周期管理_到期删除.md>)。不能将到期清理的处理方式直接推广到未明确的业务删除场景。

双写期间，接口成功只按旧表提交结果判断；它既不能证明新表成功，也不能证明 ES 写入或搜索可见。旧表与新表校验检查双写结果，新表与 ES 校验检查搜索副本，两者不能互相替代。ES 侧校验见[015_ES改造_ES_新表与 ES 增量校验_整体实现](<./015_ES改造_ES_新表与 ES 增量校验_整体实现.md>)。

### 2.7 停止双写后的业务行为

**校验通过后开始切换查询流程**

旧表与新表、新表与 ES 的数据写入校验连续 1 个月无差异后，即可开始切换查询流程：业务查询切换到新表，后台列表查询切换到 ES。仍有旧表依赖或查询需要回退时，继续双写并运行校验；全部旧表依赖切换完成后，再持续观察两项校验连续 3 个月无差异，才进入最终收尾。任务必须持续运行并覆盖应检查范围，停滞或未执行不能算无差异。阶段条件以[ES 验收与查询切换的查询回退、最终关闭旧表写入两节](<./999_ES 验收与查询切换.md>)为依据。

**再关闭旧表写入与查询回退**

满足最终条件后，停止过渡性的旧表与新表增量校验，关闭旧表写入和旧表查询回退。保留旧链路代码或开关不表示旧表仍有最新数据；停止旧表写入后，不能仅切换开关就把旧表作为当前查询结果。

**新表提交成为接口成功依据**

此后业务请求直接沿用原有新表分片写入链路，以新表事务提交结果判断接口成功或失败。新表到 ES 的同步和新表与 ES 校验继续运行，新表提交成功仍不表示 ES 已完成同步或搜索可见。

## 3 已确认规则

### 3.1 上线顺序与业务边界

- 新增旧表 `version` 并建立初始值 → 上线全部旧表写入口的版本维护改造；两步均在“服务升级与双写”之前完成。
- 完成前置改造后，开启双写并启动历史迁移，两者并行运行；迁移开始前双写必须已生效，不等待双写链路稳定观察期。
- 切换为新表主写时，无需修改新表写入链路代码。
- 采用旧表优先双写，新表失败不阻断旧表业务；日志、告警、消息重试和人工排查按 2.3 执行，数据差异由校验任务修正。
- 旧表提交结果未知时，不继续写新表；必须明确确认旧表事务提交成功后，才能执行新表写入。未知不等于失败，接口结果及核实方式仍待确认。
- 历史记录未迁入时，新表更新、删除影响 0 行不阻断业务，也不立即补建；更新旧快照及删除回插按 2.4 和方案设计 2.3 交由校验修正，不采用删除标记机制。
- 校验是流量切换的门禁；程序先记录差异并按规则修数，人工排查原因，切换验收前须完成原因处理及复核，校验完成前新表不能作为最终可信数据源。观察窗口按 2.7 保留 1 个月及 3 个月条件。
- 旧表到新表不采用 Binlog；保留新表到 ES 的既有同步链路。ES 历史覆盖、灰度参数、灰度写入方式和停止旧表写入后的回退边界仍待确认。

### 3.2 记录身份、版本与修数

- 撤销和退货分别新增独立交易记录，使用 `BS0013` 和 `BS0024`，通过关联字段指向原消费记录；原消费记录不直接改成撤销或退货。
- 新旧表使用独立主键、通过 `serialNo` 关联；首次创建新表记录按新表规则生成 `consumeId`，后续沿用已有身份。
- 版本维护按 2.1 的五个场景执行：旧表业务更新递增；新表业务更新检查自身预期版本后递增；更新补偿沿用原数据及原预期版本；迁移和校验使用同一旧表快照的数据及版本，不重新初始化或额外递增。
- 已有记录的版本判断与写入在同一条 SQL 中执行；迁移和校验保留 `version <= :incoming_version`，不预先查询新表版本。迁移旧快照覆盖造成的差异由一致性校验发现并修正，修复后再次校验；该约定不代表跨表版本可比较性及最终收敛已经验证。
- 程序修数记录差异及修数前快照，按旧表数据修正，记录成功和失败结果并重新校验；具体版本条件、事务范围和未解决的并发边界见 2.1 和方案设计 3.1。项目自行决定的处理不标为参考文章原方案或已实践验证。

## 5 异议与分析

### 5.1 来源版本相同仍可能覆盖较新业务数据

2.1 的版本规则已确认，但新表独立递增后，版本不一定与旧表业务版本一一对应。以下针对新表已有记录的迁移更新：

1. 新旧表最初都是金额 **100**、版本 **1**。
2. 旧表更新为金额 **200**、版本 **2**，迁移读取这份快照；本次新表双写失败。
3. 旧表再次更新为金额 **300**、版本 **3**。
4. 本次新表双写读取自身版本 **1**，检查后更新为金额 **300**、版本 **2**。
5. 迁移随后写入金额 **200**、来源版本 **2**，`2 <= 2` 成立，仍可能覆盖新表中较新的业务数据。

**校验修正示例**：接续上述过程，假设修复期间没有新的业务变更。

1. 迁移覆盖后，新表为金额 **200**、版本 **2**；旧表为金额 **300**、版本 **3**。
2. 校验读取旧表金额 **300**、版本 **3**，比较业务字段后发现金额不同。
3. 新表满足 `2 <= 3`，校验将其修正为金额 **300**、版本 **3**。
4. 修复后再次校验，确认本条记录一致；若期间又发生业务变更，则继续复核和处理差异。

这是项目自行决定、未经实践验证的处理方式。该例能按当前 SQL 修复，不代表所有差异都能收敛；新表版本领先时的反例见 [3.1](<./999_分库分表 + 数据迁移_方案设计.md#31-高新旧表差异校验与修复>)。

**删除回插**：不采用删除时间点或删除标记机制，仍由校验发现并修正新表多余记录。缺失记录下的完整时序见 [2.4](#24-高历史数据未迁入时的双写处理与一致性修正)。

### 5.2 新表版本领先时无法按当前条件修复

以下假设两个请求在旧表按 A、B 顺序提交，但新表调用发生延迟；示例为未运行验证的时序推演。

1. 新旧表最初都是金额 **100**、版本 **1**。
2. 请求 A 将旧表更新为金额 **200**、版本 **2**，尚未执行新表更新。
3. 请求 B 将旧表更新为金额 **300**、版本 **3**，本次新表双写失败。
4. 迁移读取旧表当前快照，将新表更新为金额 **300**、版本 **3**。
5. A 恢复执行，读取新表自身版本 **3**，按原业务数据将金额更新为 **200**，版本递增到 **4**。
6. 校验发现旧表“300、3”与新表“200、4”不同，但 `4 <= 3` 不成立，无法按当前 SQL 修正。
7. 如果之后不再发生业务变更，继续执行同一校验和修复 SQL 仍会失败，不能认为重试即可自然收敛。

该例说明新表乐观锁只检查读取之后版本是否变化，不能识别延迟业务请求在旧表中的先后。保留 `<=` 的决定不变，但这一类差异需要另行确认处理方式，不能擅自删除版本条件或降低新表版本。

### 5.3 旧表停止写入后的回退边界

002 的相关表述已同步记录最终收尾前连续 3 个月无差异的条件；004 原文和验收文档明确关闭旧表写入时也关闭旧表查询回退。技术上，停止写入后的旧表不再持续更新，不能仅靠切换查询开关保证数据正确。本文保留查询回退作为过渡期间的处理动作，并在最终收尾时关闭它。

### 5.4 删除事件的同步范围

006、009 的部分旧描述仍包含将数据库 DELETE 转为 ES Delete 请求，而 011、013 已记录到期清理不逐条删除 ES、改由 ILM 删除过期索引。本文按到期清理规则明确同步边界；关联文档尚未在本次修改，业务删除的具体映射仍待确认，不能据文档记载认定删除链路已经验证。
