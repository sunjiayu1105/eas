# 008_分库分表_新旧表一致性校验

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 文档目标与适用边界

本文承接应用层双写和在线历史迁移，说明旧表与新表的数据一致性校验、差异修复、复核以及切换门禁。旧表仍是可信数据源时，校验按旧表当前业务数据修正新表；并发删除、扫描覆盖和 ES 衔接仍保留待确认边界。

旧表到新表不采用 Binlog 同步路线。新表到 ES 的 Binlog、Canal 和 RocketMQ 链路另行维护；新旧表校验不能替代新表到 ES 的校验。

项目基础规则仍为 2 个数据库实例、每个实例 16 张表、共 32 个物理分片，按 `merchantNo` 路由，使用 `consumeId` 作为新表主键、`serialNo` 关联同一笔业务记录。本文不修改这些规则。

## 2 面试口述精炼版本

**校验对象和时机**

历史迁移完成后，先确认旧表和新表的历史数据验收通过，再进入增量校验。校验按扫描轮次执行：每轮先确定 `scan_end_time`，第一页使用 `update_time` 的固定回看窗口，后续页面使用 `(update_time, consume_id)` 复合游标继续向后扫描。回看只用于每轮第一页，不能在每一页重复回看。

**比较和修复**

校验读取旧表和新表的当前状态，使用 `serialNo` 关联记录，按已确认业务字段比较，排除新表独有的 `version`。发现缺失、旧快照覆盖、错误新增、删除差异或字段不一致后，由独立修复流程按旧表数据修正并记录修数前快照、结果和重试信息；修复后必须再次校验。校验通过不等于写入链路已经被证明正确。

**并发和失败边界**

校验修数会与业务双写并发。更新时检查刚读取的新表记录 ID 和本地 version，只有版本未变化才修正并递增；冲突后记录日志，本次不重查或重试，留到下一轮，不比较跨表版本大小。旧表也可能在读取后变化，因此仍需修后复核及后续轮次处理。查询或进度保存失败时保留游标；修正未成功则记录未解决状态，留到下一轮，不能计为已修复。最终一致还依赖完整扫描、失败可恢复、足够处理能力及可靠的主写交接；这些条件尚未经过运行验证。

**校验任务支持断点续跑、幂等和限流**

校验按表和批次保存进度，任务中断后从已保存位置继续；重复执行时重新读取两边当前状态，字段一致不更新，补建、更新和删除都按条件处理，避免重复修数；同时限制线程数、批次大小和各数据库实例的读取、回查及修数写入速率，压力升高时降速或暂停。并行调度和按表维护进度的展开说明见 [3.10（第 235 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/008_分库分表_新旧表一致性校验.md:235>)，具体实现及效果仍需验证。

**切换门禁**

首次查询切换前，旧表与新表、新表与 ES 的校验连续 1 个月无差异；全部旧表依赖切换完成后，再连续 3 个月无差异，才能停止旧表写入，改为新表单写，并停止旧表与新表增量校验。两个观察窗口是项目既定规则，不能用参考文章示例时长替代。

## 3 详细方案

### 3.1 校验启动与扫描边界

历史迁移完成并通过新旧表历史验收后，保存各分片可恢复的校验进度、实例身份和采集时间，作为增量校验起点。不能把导入前位点或启动时最新位点当作验收基线；位点丢失、连续性无法确认或日志已断档时，应暂停并人工复核。

以下为增量扫描设计，不能单独替代两边 serialNo 并集的全范围覆盖；历史差异和物理删除的重复覆盖机制仍需明确。每轮校验先固定 `scan_end_time`，只处理不晚于该边界的数据。第一页按 `update_time >= scan_end_time - lookback` 查询，并按 `update_time ASC, consume_id ASC` 排序；后续页面使用上一页最后一条记录的 `(update_time, consume_id)` 作为复合游标，不能重新使用回看时间。固定边界和复合游标分别解决本轮范围稳定与分页不重不漏问题。

### 3.2 读取、关联与字段比较

使用 `serialNo` 关联旧表和新表记录，使用 `merchantNo` 按统一路由规则定位期望分片，并核对实际来源实例和物理表。实际来源与期望路由不一致时记录为路由异常，不能只查询期望分片后将错表记录判定为缺失。

比较时排除新表独有的 `version`，其余业务字段按项目确认的字段清单比较，区分 `NULL`、空字符串、金额单位、时间精度和枚举值。完整字段清单仍需结合实际 DDL、ROW 事件和转换代码确认。查询超时、连接失败或位点异常只能记录为执行异常，不能判定为一致或缺失。

### 3.3 差异分类与修复流程

以下情况均记录差异定位、来源业务快照、修数前快照和比较结果：

1. 新表缺失或旧表缺失；
2. 旧快照覆盖新表较新业务数据；
3. 新表错误新增、重复记录或删除差异；
4. 业务字段不一致；
5. 实际来源与期望路由不一致；
6. 查询、游标或位点执行异常。

程序负责记录差异并执行统一修数，人工负责排查写入代码、配置和数据原因。修复流程读取旧表当前业务数据，在新表事务内执行插入、更新或删除，版本规则复用 [006 版本维护](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md>) 中的新表本地版本条件；修复结果、重试次数和最终状态必须留痕。修复后重新读取两端并复核，只有复核通过才能关闭本次差异。

不采用删除标记机制。迁移旧快照造成的新表多余记录、删除回插和单端删除，都由新旧表比较发现并修正；不能只遍历旧表而忽略新表多余记录。

### 3.4 更新修数使用新表本地版本

**用户自行确认的项目方案，非参考文章方案**

旧表不再为本次改造新增 version。校验补建时新表版本初始化为 1；已有记录修正成功后，新表自身版本递增，同时供 ES 同步使用。字段相同则不写入。删除后重建复用 ES 文档 ID 的版本冲突仍待确认，见 006。

修正未成功时只记录日志，本次不立即重新查询或重试，留到下一轮。条件影响 0 行、唯一键冲突、数据库异常分别记录，不能一律认定为版本冲突，也不能将未确认修复计为通过。下一轮必须再次覆盖这些记录；覆盖机制未完成前，不能只记录日志并假定会自动收敛。

扫描进度与差异修复结果分开统计：若该页查询完成、失败项及统计已可靠记录，可以继续扫描；查询失败或进度保存失败仍保留游标。下一轮重新处理未修复项，不在本轮循环重试。具体覆盖与持久化实现尚待验证。

每次重读新表记录 ID、version 和业务字段，再读取旧表当前状态。字段一致不写入；字段不同则按新表记录 ID 和读取到的 version 条件更新，成功后新表 version 加 1，不依赖旧表版本。条件不匹配时记录日志，本次不重查或重试，留到下一轮重新读取判断，不重放旧结果。具体版本 SQL 见 006。

### 3.5 并发处理与最终一致性的成立条件

**校验修数会与业务并发**

校验既读数据也修改新表，因此会与业务双写、其他校验线程竞争。正式校验在历史迁移全部批次完成后启动，不再与正常历史迁移任务并行；若仍有迁移重试在写入，就不能视为历史迁移已完成。以下以旧表仍是事实来源、历史记录已迁入新表为前提，示例是逻辑推演，不是生产故障记录。

**示例一：新表版本条件阻止覆盖读取后的业务更新**

1. 校验读取新表金额 100、version = 5，再读取旧表金额 200。
2. 业务将旧表更新为金额 300，双写也把新表更新为金额 300、version = 6。
3. 校验仍按读取到的新表记录 ID 和 version = 5，尝试将金额修正为 200。
4. 新表已经是版本 6，条件不匹配，影响 0 行，不会覆盖这次业务更新。
5. 本次记录日志后跳过；下一轮重新读取两边，若金额均为 300，则不再修正。

**示例二：校验仍可能写入暂时过期的旧表状态**

1. 校验读取新表金额 100、version = 5，再读取旧表金额 200。
2. 业务把旧表金额更新为 300，但双写尚未更新新表。
3. 新表仍为版本 5，校验条件成立，将其修正为金额 200、version = 6。
4. 此时两边仍有差异。后续双写可能完成，也可能因版本冲突失败；需要修后复核和后续校验重新读取当前状态处理。
5. 若旧表最终稳定为 300，且这条记录再次被校验并成功修正，新表才能收敛为 300。

乐观锁只检查读取后目标记录是否变化，不保证旧表快照始终最新，也不能判断主写职责是否已经切换。

**项目当前的处理设计**

- 双向分批扫描，覆盖新旧表 serialNo 查询结果的并集，再查询两边当前记录；避免漏掉新表缺失和多余记录。
- 更新前重读新表记录 ID、版本和业务字段，按 ID 和本地版本条件修正，成功后递增；影响 0 行记录日志，留到下一轮重新判断，不直接当作成功。
- 字段一致不更新；补建依赖业务唯一约束，冲突后记录日志，留到下一轮处理；删除前重新确认旧表查询成功且确实不存在，再按新表 ID 和版本条件删除并复核。
- 按表保存校验进度，查询或进度保存失败保留游标，通过断点续跑恢复；单条修正未成功按 3.4 留到下一轮；查询失败不能当作记录不存在。
- 多线程校验限制并发及各库访问速率，同一工作单元避免重复运行，修正后再次核对，后续轮次持续覆盖差异。

并发删除仍需特别注意：确认旧表不存在之后，它可能又被创建。目标版本条件不能原子保护旧表重建，仍可能出现短暂误删，后续覆盖与重建处理需要验证。

**最终一致是有条件的，当前不能无条件保证**

1. 对应数据范围的事实来源明确；旧表为准的修数不能在新表接管后继续按旧规则执行。
2. 扫描能够完整覆盖两边记录，并且重复覆盖并发更新、删除及重建；仅扫描近期更新时间窗口不能单独证明历史差异或物理删除已全部覆盖。
3. 失败批次和失败修正不会永久丢失，任务能恢复，依赖故障能排除。
4. 重复修数具备幂等性，目标业务字段的所有修改入口都维护本地版本；删除重建的记录 ID 不复用等前提需验证。
5. 每条仍有差异的记录最终都有成功修复机会，不能因持续冲突而永久饥饿；整体处理能力需足以避免差异持续积压。
6. 主写切换正确处理在途双写、旧校验任务和最后一批差异，事实来源及修正方向可靠交接；具体机制仍待明确。

例如，假设每秒新增 1000 条互不相同的待修复记录，而每秒只能修复 500 条，积压会持续增长。这些数字仅为容量示例；不能简单用业务写入次数代替实际新增差异量，因为同一条记录的多次变更可能合并为一次当前状态修复。

连续多轮无差异是验收依据，不是未来绝不产生差异的证明。项目已记录上述处理设计，但扫描覆盖、并发修正、恢复能力及主写交接尚无运行验证，不能据此声称完整最终一致性已获保证。

### 3.6 迁移完成与切换条件

历史扫描游标到达末尾不代表数据已经追平。切换前必须同时确认历史扫描范围完成、失败批次处理完成、双写失败差异已经补齐，并通过新旧表校验。扫描、补偿和校验之间的具体完成判定仍需结合实际实现确认。

旧表与新表、新表与 ES 的校验连续 1 个月无差异后，才可逐步切换查询；查询稳定后再切换写入。全部旧表依赖切换完成后继续双写，两项校验再次连续 3 个月无差异，才可关闭旧表写入并改为新表单写。观察期间校验必须持续覆盖应检查范围，不能将任务停滞当作无差异。

### 3.7 ES 衔接边界

新旧表校验不能证明历史导入已经被新表到 ES 的校验完整覆盖。例如 ES 校验的 `update_time` 游标已经推进，之后才导入更新时间更早的历史记录，该记录可能落在扫描窗口之外。新旧表修数是否推进新表 `update_time`、同版本修复如何被 ES 校验覆盖，以及历史范围的复核方式仍待确认。

正常 ES 同步使用业务版本和 `version_type=external`；同版本字段差异的补偿规则见 [ES 自动补偿规则](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_ES改造_ES_新表与 ES 增量校验_自动补偿、并发与恢复.md>)。这些是项目文档中的设计，不是运行验证结论。

### 3.8 断点续跑与幂等：进度和修数分别保证

**方案状态与作用**

维护进度和失败状态只是实现断点续跑的基础，不能单独保证续跑或幂等。以下为补充的实现建议，尚未经过运行验证；适用于旧表仍是事实来源的校验阶段，不改变主写交接规则。

**断点续跑：整批完成后保存进度**

分别持久化旧表及每张新表的校验轮次、本轮扫描范围、已完成游标和任务状态。程序重启后读取进度，继续尚未完成的批次。轮次用于区分“恢复这一轮”和“开始下一轮”，新一轮不能沿用上一轮结束游标而跳过需要重新核对的数据。

1. 假设某张表已完成游标是 100，本批处理 101～200。这些数字只是分页示例，不表示新旧表主键相同。
2. 程序处理到 150 时退出；若提前保存游标 200，重启后会漏掉 151～200。
3. 因此整批处理完成后才能保存游标 200；未完成则保留 100，重启后重新处理这一批。
4. 若数据已经修正，但保存进度前退出，也会重跑本批，因而修数必须允许重复执行。

“扫描批次完成”与“差异全部修复”分开记录。单条修正未成功时记录日志和未解决统计，本次不立即重试，可以在该页处理结果保存后继续扫描，但本轮不能判为无差异。下一轮必须再次覆盖这些记录；若采用完整重复扫描，可由扫描范围保证覆盖，若仅增量扫描，则需另行明确遗漏记录如何再次进入校验。具体进度、统计持久化及覆盖方式仍待验证，不要求新增逐条补偿任务。

**幂等：重复处理不造成重复写入**

断点续跑解决从哪里继续；幂等解决同一批再次执行时不会造成错误。每次重试重新读取两边当前记录，不直接重放上次修数 SQL 或旧快照。

- 补建：依赖业务唯一约束防止重复插入，重复冲突后重新查询比较，不能把所有插入异常都当作成功。
- 更新：业务字段一致就不更新；存在差异时才按本次读取的新表记录 ID 和版本条件修正，成功后版本加 1。
- 删除：重新确认旧表查询成功且记录不存在，再按新表记录 ID 和版本条件删除；目标已经不存在则无需重复删除，随后仍按当前状态复核。

**示例：修数成功，但进度尚未保存**

1. 旧表金额 200，新表金额 100、版本 5。
2. 校验按新表版本 5 将金额改为 200、版本 6。
3. 程序在保存批次进度前退出，重启后重新处理该记录。
4. 若期间两边业务没有变化，重新比较发现金额都是 200，就不再更新，新表版本仍为 6。
5. 如果不比较业务字段，而是每次重新读取版本后无条件写入，第二次仍会递增为 7。乐观锁能检测读取后的并发变化，但不能单独保证幂等。

这些措施避免重复处理带来的无意义写入，不消除跨库读取期间的并发变化；仍需沿用条件修正、修后复核及后续轮次覆盖。

### 3.9 校验限流与数据库压力控制建议

**方案定位与执行顺序**

以下是根据参考文章“分批、限流”的要求补充的项目实现建议，不代表文章给出了相同配置，也不代表已经实现或验证。本节用于历史迁移全部批次完成后的正式一致性校验；迁移阶段的压力控制见 007。

建议先采用单个任务执行实例、有限线程池和有界队列，不额外引入分布式限流组件。所有后台线程共用按数据库实例划分的限流器；若以后部署多个执行实例，需要统一分配总额度，不能让每个进程都使用完整额度。业务请求不进入后台任务队列，后台连接池单独限制大小，为正常业务保留连接和资源余量；独立连接池本身不能隔离磁盘、CPU 和锁竞争。

**先限制每次工作量，再限制同时运行量**

校验按两边各自的扫描进度分批读取标识，并限制回查记录的批次大小。只查询需要的字段，确认分页、serialNo 回查及条件修数能使用合适索引；不能用更多线程弥补慢 SQL。数据库操作采用短事务，避免把整轮任务或多个分片写入放进一个长事务。

线程池限制同时处理的批次数，有界队列限制尚未处理的数据量。队列满时暂停生产下一批，不继续堆积内存。每个数据库实例再单独限制后台并发 SQL 数；不能只限制总线程数，因为不同线程可能同时访问同一个旧库或热点新库。

**按数据库实例共享速率额度**

分别为旧库、新库实例 0、新库实例 1 设置后台读取额度；为两个新库另外设置后台写入额度。额度至少限制 SQL 请求速率，并结合每批条数限制每秒处理行数；修数写入单独限速，避免大量差异突然转化为写入峰值。额度是上限，不是必须跑满的目标，具体值通过演练确定。

任务发起每次 SQL 前，先从对应实例的共享限流器取得额度，没有额度就等待。批量请求按请求次数和计划处理条数申请额度，等待期间不持有数据库连接、事务或行锁。额度可按无突发或小突发的节奏发放，避免每秒边界集中发送大量请求；遇到失败重试也要重新申请额度，不能绕过限流。

旧表扫描、新表扫描后的旧表回查，都消耗同一份旧库读取额度。新表扫描、业务字段回查及修后复核也分别计入实际访问实例的读取额度；迁移插入以及校验补建、更新、删除消耗对应新库写入额度。仅在每个线程完成批次后各自休眠，无法稳定限制所有线程叠加后的总速率。

**示例：新库分散，旧库压力仍会集中**

1. 假设校验开启 4 个线程，每个线程每秒向旧库发起 20 次回查，合计就是每秒 80 次；这些数字只是说明原理。
2. 如果每个线程分别设置每秒 20 次的限制，总压力仍为每秒 80 次。
3. 假设演练配置旧库共享上限为每秒 40 次，那么扫描旧表和全部回查请求共同使用这 40 次额度，额度不足的请求等待。
4. 假设其中发现大量差异，修数也要领取新库写入额度，不能因为读取未超限就一次性提交所有修复。
5. 40 次不是生产建议值；即使请求数低，缺少索引或单批过大仍可能产生高负载，因此还需联合限制批次大小并观察实际数据库压力。

**压力升高时降速，必要时暂停**

监控业务请求耗时、错误率、连接等待，以及数据库 CPU、磁盘延迟、慢查询、锁等待。先在无后台任务时记录基线，再通过演练确定告警线和暂停线。初期可由告警配合人工调整动态配置，不要求先实现复杂的自动调速算法。

超过告警线并持续一定时间时，降低后台速率或并发；达到暂停线、连接持续不足或出现大量超时时，停止领取新批次和发起新请求，告警并排查。已经发出的 SQL 按其超时和事务结果收尾，不假定暂停开关可以撤回在途提交。压力恢复并持续稳定后，从低速恢复，逐步提高；观察时长和阈值都待演练确定。

**示例：暂停不能导致漏数据或丢失进度**

1. 某批校验已经修正一部分记录，监控发现业务耗时明显升高，任务暂停。
2. 已确认完成的批次保存进度；当前批次未全部完成则不推进完成游标，不能将暂停标记为成功。
3. 恢复后按原范围继续，未完成批次可重跑，重新读取两边记录，已一致的不更新，补建依赖唯一约束，删除前重新确认。
4. 校验任务同样保留游标和失败项；恢复时重新读取两边当前状态，不重放暂停前的旧修数快照。
5. 超时但提交结果未知的操作，也按既有幂等和重新核对规则处理，不能直接当成未执行。

**参数确定与验证边界**

先以单线程、小批量启动演练，逐步增加处理速率，观察业务延迟和数据库负载，再确定线程数、批次大小、每库读取/写入额度及暂停条件。需验证两个新库负载不均、旧库集中回查、大量差异修数、失败重试及暂停恢复场景。限流只减少资源争抢，不保证不会影响业务，也不代替一致性和幂等控制；速度过低还会延长迁移和漏写修复时间，需要同时评估完成时长和校验积压。


**一致性校验也需要限流**

参考文章 04 在[第 37 行](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_04.md:37>)明确指出，校验会消耗大量数据库资源，差异修复还可能引入新差异，因此需要分批、限流。校验读取和差异修复都要纳入压力控制，不能只限制扫描线程数。

例如，即使只有 4 个线程，如果每个线程完成一批后立即查询下一批，仍可能持续向数据库发送大量请求。因此需要同时控制线程数、批次大小、单位时间处理量和修数写入速度；具体阈值待演练确定，具体限流方案见本文件[3.9（第 178 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/008_分库分表_新旧表一致性校验.md:178>)。



### 3.10 并行校验建议：按表拆任务，统一限制并发

**先明确表数量和任务含义**

按 [003：拓扑规模（第 35 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/003_分库分表.md:35>)，新库采用 2 个 MySQL 实例，每个实例 16 张消费记录表，共 32 张物理表。“每张表一个校验工作单元”和“同时运行 32 个线程”是两件事：前者决定数据范围和进度归属，后者决定同时给数据库多少压力。

**参考文章的做法**

参考文章 01_1 的[分片并行校验（第 108 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:108>)明确提出多个校验任务，每个任务负责一个分片的数据范围。文章没有规定这些任务必须是独立定时任务，也没有给出线程数。项目建议按主键范围拆小任务，并同时控制数据库查询压力；这部分是本项目的调度建议，不是参考文章明确给出的线程数。

参考文章 04 的[分块校验（第 339～342 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_04.md:339>)将数据按主键范围切块，比较新旧数据块的指纹；[差异定位及复核（第 417～421 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_04.md:417>)再逐行核对异常块、修复并复核。该节未明确调度任务数量或线程池配置，不能据此说文章采用了 32 线程。项目新旧主键不同，不能直接照搬相同主键区间作为两边对应范围；仍需按 serialNo 关联。指纹一致也不能代替项目已确认的业务字段核对。

**项目建议：一个调度入口，多个工作单元，共享有限线程池**

以下是本次新增建议，尚未确认为项目采用方案，也未经过运行验证。沿用历史迁移全部批次完成后才启动正式校验的前提。

1. 一个调度入口启动一轮校验，分别记录旧表扫描和 32 张新表扫描的进度；扫描两边才能同时发现新表缺失与多余记录。
2. 新表按物理表划分 32 个工作单元，各自分页、记录游标和失败状态；不要求在调度平台配置 32 个独立定时任务。
3. 旧表也必须分批扫描，取到 serialNo 和 merchantNo 后，按既有路由规则查询新表。不能只从新表出发，否则旧表有而新表没有的记录不会被发现；也不应让 32 个工作单元各自重复全扫旧表。
4. 使用一个大小可配置的线程池，并限制待执行队列及每批数量。线程数不与表数绑定；同时限制旧库和两个新库的查询压力，结合连接池余量、业务延迟、数据库负载及压测结果确定并发数。
5. 同一轮的同一工作单元不能重复运行。上一轮未结束时不再重叠启动整轮；多实例部署时还需确保只有一个调度者分配本轮任务，具体协调机制待确认。
6. 完成一个批次后保存进度；失败不能直接推进游标并记为通过。所有约定扫描范围和失败项处理完成后，才汇总本轮结果。双向扫描可能重复检查同一 serialNo，分页、去重及恢复机制仍按待确认事项落实。

**示例：32 张表不等于必须同时开启 32 个线程**

1. 假设演练时配置 4 个工作线程，这只是说明调度过程的例子，不是生产推荐值。
2. 调度器将旧表分页工作和新表工作单元送入受限队列，同时最多运行 4 个工作单元，其余等待；任务分配需兼顾两个新库及旧表扫描进度。
3. 某个工作单元完成后，线程继续执行下一个；某张表失败时保留其进度，不要求已经完成的表从头重跑。
4. 若直接开 32 个线程，即使读取分散在两个新库，回查旧表仍可能集中压到同一个旧库，拖慢正常业务。因此应限制并发并依据演练调整，不能仅按表数设置线程数。
5. 只有旧表扫描和全部新表扫描均完成，且本轮差异、失败项已按验收规则处理，才能汇总本轮结果；不能把“线程全部退出”当作“校验全部通过”。


## 4 已确认规则

- 多线程并行校验及按表维护进度属于展开内容，集中在 008；006 不保留校验任务能力口述段落，仅在详细方案提供导航。

- 面试口述必须包含一致性校验任务支持断点续跑、幂等和限流；设计要求不代表运行验证已完成。

- 新旧表业务字段比较排除新表独有的 `version`；版本初始化、同 SQL 递增、导入重跑不重置和消息重放稳定性单独验证。
- 历史迁移和新旧表验收完成后，才能进入增量校验和查询切换；扫描游标到末尾不能单独作为迁移完成依据。
- 每轮先固定 `scan_end_time`；10 分钟回看只用于该轮第一页，后续页面使用 `(update_time, consume_id)` 复合游标。
- 旧表仍为可信数据源时，以旧表业务字段修正；更新检查新表记录 ID 和本地版本，成功后递增，修复后重新校验。
- 不采用旧表到新表的 Binlog 同步路线；保留新表到 ES 的既有 Binlog、Canal 和 RocketMQ 链路。
- 首次查询切换前，两项校验连续 1 个月无差异；全部旧表依赖切换完成后，再连续 3 个月无差异，才能停止旧表写入并改为新表单写。

## 5 待确认或待验证事项

- 单一调度入口、按表工作单元与有限线程池建议是否采用；并发数、任务互斥及进度恢复需实现验证。

- 双向扫描如何持续覆盖历史差异、物理删除和并发重建，不能仅依赖近期更新时间窗口。
- 主写交接时如何处理在途双写、旧修数任务及最后一批差异。
- 完整业务字段比较清单、类型精度和规范化规则。
- 校验读取旧表后发生业务变更时的重读规则、版本变化后的重试和失败处理。
- 新表条件修数、重读及持续失败告警的实际行为。
- 修数失败重试上限、日志保存周期、灰度比例、观察指标和回退截止点。
- 历史扫描结束边界、失败批次完成条件，以及迁移、补偿和校验的衔接。
- 历史 `update_time` 早于 ES 游标时的复核方式；新旧表修数是否推进 `update_time`；同版本修复如何完整覆盖到 ES。
- 实际数据库、Canal、RocketMQ、ES、补偿程序和生产数据行为；本次静态整理未执行运行验证。

## 6 异议与分析

**参考文章没有覆盖项目关键边界：** 参考文章只提出分片比对、多轮复核和灰度切换，没有定义字段清单、复合游标、失败游标保留、新表版本领先、删除差异或 ES 历史覆盖。因此本文保留这些项目扩展，并明确其设计与运行证据的边界。

**自动修数不等于并发安全：** 修数程序统一留痕并便于复核，但仍可能读取过期旧表快照。修数成功只能说明本次写入完成，不能代替写入链路正确性验证或证明所有差异能够收敛。
