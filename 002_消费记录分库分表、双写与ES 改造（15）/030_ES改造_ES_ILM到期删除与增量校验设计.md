# 030_ES改造_ES_ILM到期删除与增量校验设计

## 1 已确认规则

1. 采用方案一：MySQL 到期 DELETE 不调用 ES 文档删除接口，ES 由 ILM（索引生命周期管理）删除整个过期月份索引。
2. MySQL 只物理清理原始 `create_time` 超过五年的消费记录，不存在业务提前物理删除；撤销不等同于保留期清理。
3. 前后端限制查询近五年，精确到日，并把日期条件下推到 ES；接受超期数据暂时保留，但查询不可见。
4. ES 根据不可变的原始 `create_time` 定位自然月索引 `records-yyyy.MM`，业务时区为 UTC+08:00，不使用 rollover。
5. 生命周期起点为所属月份下个月 1 日零点；cold、delete 的 `min_age` 分别为 `366d`、`1830d`，均从该起点计算。允许延后执行，不允许提前删除范围内数据。
6. MySQL 与 ES 独立清理，不要求先后顺序；历史回放和修复不向 ES 写入五年范围外的数据。
7. 历史回放期间使用只有 hot 阶段的临时策略，历史范围同步、校验和观察验收通过后才切换正式策略。

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准：Java 8、Spring Boot 2.7.18、MySQL 8.0.33、Elasticsearch 7.17.15、Canal Server 1.1.7、RocketMQ Spring Boot Starter 2.3.0、RocketMQ Client 5.2.0。

本文是方案一的设计稿。第 3 节给出建议的实现契约，尤其是日期包含关系、校验状态和跨日处理，不代表这些细节已获逐项确认或已经实现。选型依据见 [到期删除方案对比与选型](<./031_ES改造_ES_到期删除方案对比与选型.md>)。

## 2 面试口述精炼版本

**同步与清理分工**

我们只同步保留范围内的新增和更新，MySQL 到期删除不触发 ES 逐条删除。消费服务跳过消费记录表的 DELETE，继续处理同一消息的其他事件。ES 按原始创建月份存储，通过索引计龄保证整个月数据都超过五年后，再由 ILM 删除整个索引，减少冷节点的文档删除和段合并开销。

**查询与校验采用相同范围**

查询始终带上近五年的日期条件。校验也先按原始创建时间判断范围：超期对象记录为范围排除，范围内对象继续比较、修复并复核，整批处理完成后才推进进度。这样不会把 ES 暂时保留的超期文档误当成差异。消费端过滤、跨日状态处理和 ILM 执行仍需实现与验证，具体流程见 3.2～3.6。

## 3 详细设计

### 3.1 责任划分与统一日期边界

| 环节 | 负责的操作 |
|---|---|
| MySQL 清理任务 | 按业务保留规则清理源记录 |
| Canal 与 RocketMQ | 传递变更，保留 DELETE 的 ID 和删除前原始创建时间，供识别及校验使用 |
| ES 消费服务 | 过滤消费记录表 DELETE 和超期写入，处理范围内新增、更新及失败重试 |
| 查询服务 | 校验请求日期，并在 ES 查询中加入保留范围条件 |
| 独立校验任务 | 按 `update_time` 扫描当前仍存在的记录，比较两端当前状态并记录结果 |
| 独立修复流程 | 修复范围内差异，完成后交回校验任务复核 |
| ILM | 按索引策略执行冷热迁移和整索引删除 |

建议用统一的日期函数生成下界：`当天日期（UTC+08:00）减五个自然年，再取该日零点`，记为 `L`。建议采用 `create_time >= L` 为保留范围、`create_time < L` 为过期，边界当天整日保留。日期运算按自然年，不使用 `365 × 5` 天替代；该包含关系和闰日回退规则须在接入时与查询及 MySQL 清理统一。

示例：当天为 2026-10-23 时，建议下界为 `2021-10-23 00:00:00+08:00`。2021-10-22 的记录排除，2021-10-23 的记录保留。示例解释边界，不是生产执行记录。

### 3.2 消费端逐事件处理

建议在现有消费服务中按事件执行以下分支，不通过删掉 Canal 全局 DELETE 订阅来影响其他表：

1. 先匹配消费记录的库名和物理表名。其他表沿用原流程。
2. 对消费记录 DELETE，不调用 ES Delete API；保留用于审计及校验的必要事件信息，然后继续处理同一消息的下一个事件。
3. 对 INSERT、UPDATE，校验 ID、原始 `create_time` 和既有业务版本。创建时间缺失或格式错误属于异常，不能当作过期跳过。
4. 在准备写入时按当前日期计算 `L`。超期事件记录跳过原因，不写 ES；范围内事件按原始创建月份定位物理索引，沿用既有幂等和版本控制处理。
5. 所有事件及必要状态处理成功后，才确认整条消息。全部为可正常跳过的事件也可以确认；任一需要处理的事件失败，沿用原重试流程，不能提前确认。

重试时重新判断当前保留范围，不能复用首次失败时的“可写”结论。对 DELETE 发现范围内删除或创建时间缺失等异常时，仍不直接删除 ES，交由校验或异常流程调查；日志与告警不得代替应有的可靠事件接收。

本设计不直接删除原有删除状态或版本记录。应先核对其是否还承担旧消息保护、对账或审计职责，再决定如何调整；跳过 ES 删除不等于可以清空这些状态。

### 3.3 月份索引和 ILM 清理

每个月份索引使用自己的 `index.lifecycle.origination_date`：例如 `records-2021.10` 对应 `2021-11-01 00:00:00+08:00` 的毫秒时间戳。公共模板不能用一个固定值代替所有月份的起点；建议由受控的索引创建流程计算并设置。

正式策略从上述起点计龄，满 `366d` 后允许迁入 cold，满 `1830d` 后允许删除。`1830d` 是覆盖五个自然年的保守时长，策略余量和 ILM 调度可能进一步延后清理。ILM 不逐条检查文档日期；不提前删除的前提是原始创建时间正确、月份路由正确且计龄设置正确。

历史回放使用仅 hot 的临时策略。切换正式策略前确认历史范围同步、校验和观察验收完成，核对已过期索引清单，因为部分索引切换后可能很快获得删除资格。配置示例及现有设计见 [索引保留期与删除](<./038_ES改造_ES_索引保留期与删除.md>)。

建议消费与修复账号不具有随意创建历史索引的权限，索引创建交受控流程处理。这样即使过期请求在途，也不能在 ILM 删除后自行重建旧月份索引。实际权限、自动建索引设置及兼容性需验证；不能只用“写入前检查一次日期”宣称已消除所有竞争条件。

### 3.4 查询范围

后端按每次请求的业务日期计算 `L`，校验前端传入的日期范围，并在实际 ES 查询中加入 `create_time >= L`。用户选择的查询范围也必须保留，最终使用两个范围的交集；越界请求如何报错沿用业务接口约定。

只选择月份索引不能替代文档日期过滤：边界所在月份可能同时包含可查询与超期记录。查询列表、总数和聚合统计都应使用同一范围。前端限制不能替代后端校验与 ES 查询条件。

### 3.5 增量校验与进度推进

校验采用 [新表与 ES 增量校验](<./043_ES改造_ES_新表与 ES 增量校验总览.md>)确定的 `update_time` 扫描入口。每轮使用当前时间减五分钟作为扫描截止时间，扫描 MySQL 当前仍存在的记录，再读取 MySQL 和 ES 当前状态进行比较；已经物理删除的记录不会进入校验。比较、自动补偿和任务恢复分别见 045—047，扫描截止时间只用于避开 ES 正常同步延迟，不代表运行时验证已经完成。

建议固定的是事务范围；每轮比较开始时另取统一的日期下界并记录。批次跨日重试或复核时，用新一轮下界重新判断尚未完成对象。这样既保留完整事务范围，又不会为已过期记录持续执行恢复写入。不能在同一轮逐条使用不同日期边界。

| 判断结果 | 建议处理 | 是否允许该对象结束本批处理 |
|---|---|---|
| 原始创建时间已超期 | 标记“范围排除”，记录采用的日期下界；无需为清理目的读取或删除 ES 文档 | 是，但不能记成内容一致 |
| 范围内，两端存在且比较字段一致 | 标记“比较通过” | 是 |
| MySQL 当前记录存在，但 ES 缺失或字段不同 | 交程序自动补偿；补偿成功标记“补偿完成”，失败保留未完成并重试 | 补偿请求成功不等于直接比较一致 |
| MySQL 当前记录不存在 | 按当前扫描方案结束任务，不查询 ES、不创建删除差异 | 仅适用于已确认的到期清理规则 |
| ES 查询失败或结果不可用 | 记录查询异常，保留未完成并重试 | 不能直接判定为数据差异 |
| 创建时间缺失、索引不存在、超时、连接或分片失败 | 标记执行异常，保留未完成对象 | 否 |

“范围内索引不存在”属于异常；已可靠判定超期的对象可以直接排除，不必为其探测索引。当前校验入口只扫描 MySQL 当前存在的记录，因此不会为已经删除的记录创建校验任务。

扫描进度按 044、045 的复合游标和任务事务推进；单条任务独立更新状态，不以完整事务批次作为校验入口或完成条件。

任务状态、复合游标和执行结果须可靠持久化；重启后恢复未完成任务，并重新读取 MySQL 当前状态。校验覆盖扫描窗口内当前仍存在的 MySQL 记录，不据此宣称已扫描所有 ES 文档。

### 3.6 独立修复与跨日处理

校验任务发现明确差异后，由程序自动补偿，职责见 [047_ES改造_ES_自动补偿、并发与恢复](<./047_ES改造_ES_自动补偿、并发与恢复.md>)。

补偿前重新读取 MySQL 当前记录、字段和版本。记录仍存在时，使用当前源数据和既有版本规则写入 ES；不能将旧任务快照直接覆盖到 ES。补偿请求成功后标记“补偿完成”并结束本任务，失败则保留未完成并按计划重试。

如果记录已跨过保留边界，修复流程不再写入，返回“当前已超期”。校验任务在下一轮按统一新下界复核其范围，记为“范围排除”；不能把未执行的修复记成成功。源记录缺失且仍在范围内时，不擅自创建数据，也不自动删除 ES，保留异常供调查。

示例：某记录在当日仍需校验，差异修复排队到次日已超期。此时不重建 ES 文档，由校验任务确认范围后排除该对象；事务批次其余范围内对象仍继续比较。

### 3.7 监控、验收与关联调整

分别监控同步延迟与失败、校验未完成批次、范围内差异、超期事件跳过数量、ILM 错误及待删除索引积压。范围排除不等于物理清理完成：即使不再对超期记录逐条对账，也须通过索引层监控发现 ILM 长期未执行及磁盘增长。

| 验收场景 | 预期结果 |
|---|---|
| 同一消息混合 DELETE、超期 UPDATE、有效 INSERT | 前两者不操作 ES，有效事件正常处理；有效事件失败时不提前确认消息 |
| 五年下界前一天、当天及闰日 | 查询、写入过滤、校验和修复使用一致的包含关系 |
| 差异修复跨午夜后过期 | 不重新写入；校验新一轮记录范围排除，其他对象正常处理 |
| 全部对象超期的事务批次 | 有排除记录并可推进进度，不永久阻塞 |
| 范围内查询失败或索引缺失 | 不伪装成文档不存在或校验通过 |
| ILM 删除月份索引后旧消息重放 | 不重建过期索引 |
| ILM 失败或延后 | 查询仍屏蔽超期数据，索引积压可被监控发现 |

以上是待执行的验收用例，不是测试结果。后续接入须统一消费端 DELETE 分支、保留期文档、校验文档和修复入口；现有 016 文档无条件将“MySQL 删除、ES 存在”视为差异的表述不能直接用于本方案。此次只新增本文，未修改关联文档或代码。

## 5 异议与分析及依据

- 选择整索引清理不意味着机械硬盘无法执行文档删除。这里减少的是到期文档删除及后续合并成本，实际性能收益尚未压测。机制依据：[Elastic 7.17：Delete indices, not documents](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/size-your-shards.html#delete-indices-not-documents)，正文已在本会话前序检索中核实。
- “消费端跳过 DELETE”不等于“校验一律忽略 MySQL 缺失”。只有原始创建时间明确超期，才能作为保留范围排除；范围内异常仍需调查。
- ILM 不会自动理解业务五年窗口。整月安全删除依赖月份路由、计龄起点及策略配置，具体配置依据和验证缺口见第 3.3 节链接。
- 日期刷新、状态分类和跨日闭环属于本文提出的实现建议，不是外部文章中已经验证的项目案例。本次仅完成文档设计，未执行消息消费、数据修复、生产清理或集群验证。
