# 006_01 整体链路与 ES 写入前置

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 已确认规则

1. **链路与消息发送**：`MySQL → Canal Server（RocketMQ 模式）→ RocketMQ → 自定义 RocketMQ 消费与 ES 写入服务 → Elasticsearch`。统一使用“Canal Server 自带的消息发送功能”；Canal Adapter 不参与主链路。消费服务直接消费 RocketMQ 后调用 ES，不增加原始消息数据库表作为 ES 写入前置环节。

6. **消费确认、重试与校验**：不同消息并发处理，每次回调内逐条同步调用 ES；操作或必要状态保存异常时，中断当前消息并向外抛出运行时异常，由 RocketMQ 重投整条原消息。消息内全部事件处理及必要状态保存完成后，监听方法才能正常返回。自动校验任务每小时执行一次，发现差异后按数据库当前状态补偿；任务失败或延迟须告警。具体重试次数、退避、死信和恢复仍待核验。

7. **文章对照与验证边界**：吸收、差异和适配结论统一维护在“项目方案与参考文章方案的差异”一节；消息数据契约、索引设计与定位、旧写保护、幂等和失败恢复分别设题，避免把不同层次的知识点混在一起。区分文章设计思路、示例代码实际行为和项目待实现要求。文章使用 ES 8.4.2，却未使用 `if_seq_no`、`if_primary_term` 或 `version_type=external`；`response.version()` 是 ES 内部版本，不是业务 `version`。候选配置、伪代码及验收步骤不代表已部署、联调或完成故障演练。

8. **内容组织与同步维护**：本文集中维护九个待确认问题，按“总链路与选型→消息消费→消息数据契约→索引设计→物理索引定位→旧写保护→幂等→失败恢复”的知识依赖递进。索引创建与索引定位、旧写保护与幂等、失败处理与消费确认分别说明。回答先给结论，再说明原因、适用前提与验证边界；同步维护面试口述版本、规则记录和受影响引用。

## 参考文章与项目方案对比

#### 参考文章以及项目的整体链路是什么？ES 写入前是否先落库？二者之间是否存在差异？

**当前结论**：两者都是 `MySQL → Canal Server → RocketMQ → 消费服务 → ES`，都直接消费 RocketMQ 后调用 ES，不增加原始消息数据库表作为 ES 写入前置环节。

参考文章的 Spring Boot 消费者解析消息类型后，直接执行 ES 的新增、更新或删除。当前项目由自定义 RocketMQ 消费与 ES 写入服务直接处理消息；必要的来源版本、索引定位、删除和恢复状态属于可靠性控制，不等同于“先落消息表再异步写 ES”。两者共同采用消息交接来承接 MySQL 变更和 ES 写入之间的速度差异。项目还需要保存稳定来源版本、根据原始创建时间定位物理索引，并在必要状态完成后才确认消费；这些要求仍待实现与联调验证。
