# 006_分库分表_如何防止旧版本数据覆盖新版数据

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

本文比较双写、双写失败补偿、历史迁移和一致性校验修正执行 UPDATE 时，使用 update_time 还是 version 判断数据新旧。结论是推荐 version；具体实现与上线方案尚未核验，不表示已有时间比较代码已经改造完成。

## 1 面试口述精炼版本

**推荐 version：需要判断同一记录的修改先后**

update_time 记录修改时间，version 记录同一条记录第几次修改。时间能区分先后时，比较 update_time 可以拦住旧数据；但同一记录可能在同一秒内修改多次，如果保存的时间相同，就无法仅凭时间判断谁更新。version 每次业务修改递增，可以明确区分这两次修改。详见 [2.1](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_如何防止旧版本数据覆盖新版数据.md:23>)、[2.2](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_如何防止旧版本数据覆盖新版数据.md:46>)。

**四条写入路径使用同一套版本规则**

旧表主写期间，由旧表在修改业务数据的同一事务中递增 version。双写、失败补偿、迁移和校验修复都携带对应的数据与版本，新表只接受更大的 version，并保存传入版本，不自行加一。这样较新数据先到，就拒绝后到的旧数据；较旧数据先到，后续较新数据仍能更新。详见 [2.3](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_如何防止旧版本数据覆盖新版数据.md:76>)、[2.4](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_如何防止旧版本数据覆盖新版数据.md:116>)。

**版本防覆盖，重试和校验负责追平**

version 解决的是已有记录更新时的新旧顺序，不能自动补上漏写。还需要可靠保留失败任务、重试补写、迁移覆盖完整范围，以及校验发现差异后修复并复核。相同版本但字段不同、物理删除等情况不能仅靠比较版本解决。详见 [2.5](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_如何防止旧版本数据覆盖新版数据.md:144>)。

## 2 详细方案

### 2.1 update_time 能解决什么，不能解决什么

**共同点：都需要在实际 UPDATE 中比较**

不论使用时间还是版本，都不能只在 Java 查询后判断，再执行无条件 UPDATE。查询与更新之间，新表可能已被其他任务修改；条件必须在实际写入时生效，数据也必须携带与它对应的时间或版本。

**update_time：来源时间更晚时容易判断，相等时无法区分**

例如旧任务携带“异常、10:00”，新表已经是“成功、10:06”，条件更新能拒绝旧任务。这个场景不必为了处理并发就一定引入 version。

真正的缺口是：不同内容可能保存相同更新时间。

- 允许相等时间覆盖，迟到的旧数据可能覆盖较新内容。
- 只允许时间严格更晚，能拒绝相等时间的旧数据，也可能拒绝相等时间的较新数据。

所以，简单把 `<=` 改成 `<`，没有解决“如何辨认相等时间下的数据先后”。

**version：用修改序号区分同一条记录的不同状态**

例如某条记录先是 version=2，后来业务修改为 version=3。即使两次 update_time 相同，也能知道 version=3 更新。版本只比较同一条记录，不要求不同交易之间的 version 可比较。

参考文章 01_1 在[第 86～89 行](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:86>)采用更新时间、更晚或相等覆盖。参考文章 04 在[第 163 行](</D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_04.md:163>)提出 update_time 或 version 两种标识，但后续 SQL 使用时间戳，没有给出完整的 version 维护方案。本文的版本流程是结合项目目标提出的设计建议。

### 2.2 示例：同时间戳的旧补偿为什么可能覆盖新数据

**前提：两份内容不同，但保存的时间完全相同**

新表已有 S1。示例假设实际时间精度使两次修改都保存为 10:00:00；补偿保存失败时的原始数据，且 UPDATE 会写入核心流水号字段。这些实现前提尚未核验。

1. 消费过程中，旧表修改部分字段，形成数据 A，此时核心流水号为空，update_time=10:00:00。本次双写 UPDATE 失败，补偿保存 A。

2. 同一秒内，核心系统返回流水号，旧表补上该字段，形成数据 B，update_time 仍为 10:00:00。

3. B 双写成功，新表已有核心流水号。

4. 消费流程结束后，补偿重试 A。如果允许相等时间更新，就可能把新表中的核心流水号覆盖回空值。

这不要求整个消费流程在一秒内结束，只要求其中两次字段修改保存了相同时间戳。若补偿重新查询旧表，或两次时间实际不同，该具体例子便不成立。

**改用 version：两种到达顺序都能保留较新内容**

假设 A 对应 version=2，B 对应 version=3，数据和版本一起传递。

1. B 先写入新表，新表保存核心流水号及 version=3。

2. A 补偿随后到达，尝试用 version=2 更新。

3. 数据库判断 `新表 version < 来源 version`，即 `3 < 2` 不成立，拒绝 A。

4. 如果顺序相反，A 先到、B 后到，B 执行时 `2 < 3` 成立，仍能将新表推进到 version=3。

相同时间戳不再影响判断。相反，只采用严格时间比较时，A 如果先到，B 会因时间相等而被跳过，新表可能一直缺少流水号。

### 2.3 版本从哪里来，如何保证版本对应正确数据

**旧表生成版本，新表保存收到的版本**

旧表主写期间，两边各维护一个 version 字段。旧表新增记录时初始化版本，之后每次业务修改都递增；新表接收数据时保存旧表传入的版本，同步、重试和修复本身不产生新的业务版本。具体初始化与发布步骤需另行落实。

以下为推荐实现：修改旧表前读取当前 version，更新时检查它是否仍未变化，业务字段与 version 在同一个事务中更新。

```sql
-- expected_version 来自本次业务修改前读取的旧表记录。
-- 如果已被其他业务线程修改，本次更新不会命中，需重新读取并判断业务状态。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
```

只有确认业务更新成功，才能把对应的新版本与提交后的数据传给新表。同步数据与版本必须属于同一次更新，不能拿旧字段拼上后来查询到的新版本。如何可靠记录和投递这次提交的数据，是实现必须核验的部分。

**新表原子比较，不在同步时递增**

```sql
-- 已按 merchantNo 路由，serialNo 定位同一笔交易。
-- 示例仅展示部分字段；实际需携带该版本对应的完整同步数据。
UPDATE new_record
SET status = :source_status,
    core_serial_no = :source_core_serial_no,
    update_time = :source_update_time,
    version = :source_version
WHERE serial_no = :serial_no
  AND version < :source_version;
```

这里的 `source_version` 只是 SQL 参数名，值来自旧表 version，不表示新增 source_version 字段。新表保存传入版本，不能在每次补偿、迁移或校验时自行执行 version+1。

**为什么推荐完整同步数据**

如果 version=2 只修改字段 A，version=3 只修改字段 B，而同步只发送各自改动字段，version=3 先到后会让 version=2 被拒绝，字段 A 可能漏更新。因此，采用整条记录 version 拒绝旧消息时，较新数据需要包含截至该版本已提交的全部同步字段；不能直接把只含部分改动的消息当成完整记录覆盖。

### 2.4 四条 UPDATE 路径如何使用 version

**正常双写：传递本次旧表提交的数据与版本**

旧表更新成功后，携带对应数据与 version 写新表。只要版本更大就更新，乱序到达也按版本判断。例如 version=3 已写入，后到的 version=2 被拒绝。

**双写失败补偿：重试不产生新版本**

如果保存失败时的原始数据，就连同原 version 重试。例如 version=2 的 UPDATE 失败，新表后来收到 version=3，旧补偿重试时应跳过。

如果补偿重新读取旧表，则使用本次读取的完整数据和对应 version。例如这次已读到 version=4，就尝试同步 version=4，不能继续携带原 version=2。补偿具体使用哪种方式仍待核验。

**历史迁移：读取业务数据和 version，再执行相同的条件更新**

迁移读到 version=2 后，业务可能先将 version=3 双写到新表。迁移随后执行时发现 `3 < 2` 不成立，跳过。迁移只是搬运已有版本，不递增版本。

**一致性校验修正：版本用于防覆盖，业务字段用于发现差异**

校验仍比较业务内容和记录是否存在。对新表已有记录的修复，携带旧表数据与对应版本，并在 UPDATE 中判断版本。

1. 校验发现字段差异，读取旧表 version=2，准备修复。

2. 业务把旧表改为 version=3，并双写成功。

3. 校验写入 version=2 时被拒绝，随后重新核对差异，不能把跳过更新直接记为修复成功。

相同 version 不等于可以省略字段校验。版本相等但内容不同，说明存在需要排查的数据差异；具体修复方式不能由大小比较自动决定。

### 2.5 version 的作用边界：防覆盖不等于最终一致已完成

**UPDATE 没命中，先区分原因**

新表版本更大，表示这次数据较旧；版本相同且内容相同，可以按重复写入处理。版本相同但内容不同，需要保留差异并排查。目标记录不存在时也可能影响 0 行，不能一律当成成功；缺失记录需要补写，属于 INSERT 与校验补齐流程。

**最终追平仍需要可靠重试和校验**

例如旧表 version=3，新表仍为 version=2。version 比较不会主动把数据送到新表，需要双写重试或校验修复真正写入 version=3。失败任务不能丢失，迁移范围不能遗漏，差异要持续处理并复核；当旧版本都无法覆盖、最新数据最终写入成功，才能让记录追平。

**本文不把其他问题归为版本比较已经解决**

物理删除会移除记录及版本，迟到 INSERT 仍可能重新插入旧数据；切到新表主写后，版本生成方及旧任务交接也需要单独设计。本文只比较旧表主写期间已有记录的 UPDATE，不能据此宣称所有新增、删除和切换问题都已解决。

## 5 异议与分析

**毫秒时间不等于业务修改序号**

提高时间精度可以减少碰撞，但不能保证两次修改绝不保存同一时间，也不能单靠精度解决时间来源不一致或时钟回退。因此，对同一记录的修改顺序有明确要求时，统一维护 version 更直接。

**version 的可靠性来自维护规则，而不是字段名**

只有业务修改都递增版本、数据和版本原子提交、新表接收对应数据并原子比较，版本才能表达先后。漏增版本、两边独立递增，或者把新版本配上旧数据，都可能破坏判断。推荐 version 的同时，也意味着需要改造并核验所有相关写入入口。
