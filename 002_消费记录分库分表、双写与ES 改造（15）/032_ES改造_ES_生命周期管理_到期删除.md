### 原主题：032_ES改造_ES_生命周期管理_到期删除


## 1 已确认规则

1. 采用方案一：MySQL 到期 DELETE 不调用 ES 文档删除接口，ES 由 ILM（索引生命周期管理）删除整个过期月份索引。
2. MySQL 只物理清理原始 `create_time` 超过五年的消费记录，不存在业务提前物理删除；撤销不等同于保留期清理。
3. 前后端限制查询近五年，精确到日，并把日期条件下推到 ES；接受超期数据暂时保留，但查询不可见。
4. ES 根据不可变的原始 `create_time` 定位自然月索引 `records-yyyy.MM`，业务时区为 UTC+08:00，不使用 rollover。
5. 生命周期起点为所属月份下个月 1 日零点；cold、delete 的 `min_age` 分别为 `366d`、`1830d`，均从该起点计算。允许延后执行，不允许提前删除范围内数据。
6. MySQL 与 ES 独立清理，不要求先后顺序；历史回放和修复不向 ES 写入五年范围外的数据。
7. 历史回放期间使用只有 hot 阶段的临时策略，历史范围同步、校验和观察验收通过后才切换正式策略。

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准：Java 8、Spring Boot 2.7.18、MySQL 8.0.33、Elasticsearch 7.17.15、Canal Server 1.1.7、RocketMQ Spring Boot Starter 2.3.0、RocketMQ Client 5.2.0。

本文是方案一的设计稿。第 3 节给出建议的实现契约，尤其是日期包含关系、校验状态和跨日处理，不代表这些细节已获逐项确认或已经实现。选型依据见 [到期删除方案对比与选型](<./032_ES改造_ES_生命周期管理_到期删除.md>)。

## 2 面试口述精炼版本

**同步与清理分工**

我们只同步保留范围内的新增和更新，MySQL 到期删除不触发 ES 逐条删除。消费服务跳过消费记录表的 DELETE，继续处理同一消息的其他事件。ES 按原始创建月份存储，通过索引计龄保证整个月数据都超过五年后，再由 ILM 删除整个索引，减少冷节点的文档删除和段合并开销。

**查询与校验采用相同范围**

查询始终带上近五年的日期条件。校验也先按原始创建时间判断范围：超期对象记录为范围排除，范围内对象继续比较、修复并复核，整批处理完成后才推进进度。这样不会把 ES 暂时保留的超期文档误当成差异。消费端过滤、跨日状态处理和 ILM 执行仍需实现与验证，具体流程见 3.2～3.6。

## 3 详细设计

### 3.1 责任划分与统一日期边界

| 环节 | 负责的操作 |
|---|---|
| MySQL 清理任务 | 按业务保留规则清理源记录 |
| Canal 与 RocketMQ | 传递变更，保留 DELETE 的 ID 和删除前原始创建时间，供识别及校验使用 |
| ES 消费服务 | 过滤消费记录表 DELETE 和超期写入，处理范围内新增、更新及失败重试 |
| 查询服务 | 校验请求日期，并在 ES 查询中加入保留范围条件 |
| 独立校验任务 | 按 `update_time` 扫描当前仍存在的记录，比较两端当前状态并记录结果 |
| 独立修复流程 | 修复范围内差异，完成后交回校验任务复核 |
| ILM | 按索引策略执行冷热迁移和整索引删除 |

建议用统一的日期函数生成下界：`当天日期（UTC+08:00）减五个自然年，再取该日零点`，记为 `L`。建议采用 `create_time >= L` 为保留范围、`create_time < L` 为过期，边界当天整日保留。日期运算按自然年，不使用 `365 × 5` 天替代；该包含关系和闰日回退规则须在接入时与查询及 MySQL 清理统一。

示例：当天为 2026-10-23 时，建议下界为 `2021-10-23 00:00:00+08:00`。2021-10-22 的记录排除，2021-10-23 的记录保留。示例解释边界，不是生产执行记录。

### 3.2 消费端逐事件处理

建议在现有消费服务中按事件执行以下分支，不通过删掉 Canal 全局 DELETE 订阅来影响其他表：

1. 先匹配消费记录的库名和物理表名。其他表沿用原流程。
2. 对消费记录 DELETE，不调用 ES Delete API；保留用于审计及校验的必要事件信息，然后继续处理同一消息的下一个事件。
3. 对 INSERT、UPDATE，校验 ID、原始 `create_time` 和既有业务版本。创建时间缺失或格式错误属于异常，不能当作过期跳过。
4. 在准备写入时按当前日期计算 `L`。超期事件记录跳过原因，不写 ES；范围内事件按原始创建月份定位物理索引，沿用既有幂等和版本控制处理。
5. 所有事件及必要状态处理成功后，才确认整条消息。全部为可正常跳过的事件也可以确认；任一需要处理的事件失败，沿用原重试流程，不能提前确认。

重试时重新判断当前保留范围，不能复用首次失败时的“可写”结论。对 DELETE 发现范围内删除或创建时间缺失等异常时，仍不直接删除 ES，交由校验或异常流程调查；日志与告警不得代替应有的可靠事件接收。

本设计不直接删除原有删除状态或版本记录。应先核对其是否还承担旧消息保护、对账或审计职责，再决定如何调整；跳过 ES 删除不等于可以清空这些状态。

### 3.3 月份索引和 ILM 清理

每个月份索引使用自己的 `index.lifecycle.origination_date`：例如 `records-2021.10` 对应 `2021-11-01 00:00:00+08:00` 的毫秒时间戳。公共模板不能用一个固定值代替所有月份的起点；建议由受控的索引创建流程计算并设置。

正式策略从上述起点计龄，满 `366d` 后允许迁入 cold，满 `1830d` 后允许删除。`1830d` 是覆盖五个自然年的保守时长，策略余量和 ILM 调度可能进一步延后清理。ILM 不逐条检查文档日期；不提前删除的前提是原始创建时间正确、月份路由正确且计龄设置正确。

历史回放使用仅 hot 的临时策略。切换正式策略前确认历史范围同步、校验和观察验收完成，核对已过期索引清单，因为部分索引切换后可能很快获得删除资格。配置示例及现有设计见 [索引保留期与删除](<./032_ES改造_ES_生命周期管理_到期删除.md>)。

建议消费与修复账号不具有随意创建历史索引的权限，索引创建交受控流程处理。这样即使过期请求在途，也不能在 ILM 删除后自行重建旧月份索引。实际权限、自动建索引设置及兼容性需验证；不能只用“写入前检查一次日期”宣称已消除所有竞争条件。

### 3.4 查询范围

后端按每次请求的业务日期计算 `L`，校验前端传入的日期范围，并在实际 ES 查询中加入 `create_time >= L`。用户选择的查询范围也必须保留，最终使用两个范围的交集；越界请求如何报错沿用业务接口约定。

只选择月份索引不能替代文档日期过滤：边界所在月份可能同时包含可查询与超期记录。查询列表、总数和聚合统计都应使用同一范围。前端限制不能替代后端校验与 ES 查询条件。

### 3.5 增量校验与进度推进

校验采用 [新表与 ES 增量校验](<./043_ES改造_ES_新表与 ES 增量校验_整体实现.md>)确定的 `update_time` 扫描入口。每轮使用当前时间减五分钟作为扫描截止时间，扫描 MySQL 当前仍存在的记录，再读取 MySQL 和 ES 当前状态进行比较；已经物理删除的记录不会进入校验。比较、自动补偿和任务恢复分别见 045—047，扫描截止时间只用于避开 ES 正常同步延迟，不代表运行时验证已经完成。

建议固定的是事务范围；每轮比较开始时另取统一的日期下界并记录。批次跨日重试或复核时，用新一轮下界重新判断尚未完成对象。这样既保留完整事务范围，又不会为已过期记录持续执行恢复写入。不能在同一轮逐条使用不同日期边界。

| 判断结果 | 建议处理 | 是否允许该对象结束本批处理 |
|---|---|---|
| 原始创建时间已超期 | 标记“范围排除”，记录采用的日期下界；无需为清理目的读取或删除 ES 文档 | 是，但不能记成内容一致 |
| 范围内，两端存在且比较字段一致 | 标记“比较通过” | 是 |
| MySQL 当前记录存在，但 ES 缺失或字段不同 | 交程序自动补偿；补偿成功标记“补偿完成”，失败保留未完成并重试 | 补偿请求成功不等于直接比较一致 |
| MySQL 当前记录不存在 | 按当前扫描方案结束任务，不查询 ES、不创建删除差异 | 仅适用于已确认的到期清理规则 |
| ES 查询失败或结果不可用 | 记录查询异常，保留未完成并重试 | 不能直接判定为数据差异 |
| 创建时间缺失、索引不存在、超时、连接或分片失败 | 标记执行异常，保留未完成对象 | 否 |

“范围内索引不存在”属于异常；已可靠判定超期的对象可以直接排除，不必为其探测索引。当前校验入口只扫描 MySQL 当前存在的记录，因此不会为已经删除的记录创建校验任务。

扫描进度按 044、045 的复合游标和任务事务推进；单条任务独立更新状态，不以完整事务批次作为校验入口或完成条件。

任务状态、复合游标和执行结果须可靠持久化；重启后恢复未完成任务，并重新读取 MySQL 当前状态。校验覆盖扫描窗口内当前仍存在的 MySQL 记录，不据此宣称已扫描所有 ES 文档。

### 3.6 独立修复与跨日处理

校验任务发现明确差异后，由程序自动补偿，职责见 [047_ES改造_ES_新表与 ES 增量校验_自动补偿、并发与恢复](<./047_ES改造_ES_新表与 ES 增量校验_自动补偿、并发与恢复.md>)。

补偿前重新读取 MySQL 当前记录、字段和版本。记录仍存在时，使用当前源数据和既有版本规则写入 ES；不能将旧任务快照直接覆盖到 ES。补偿请求成功后标记“补偿完成”并结束本任务，失败则保留未完成并按计划重试。

如果记录已跨过保留边界，修复流程不再写入，返回“当前已超期”。校验任务在下一轮按统一新下界复核其范围，记为“范围排除”；不能把未执行的修复记成成功。源记录缺失且仍在范围内时，不擅自创建数据，也不自动删除 ES，保留异常供调查。

示例：某记录在当日仍需校验，差异修复排队到次日已超期。此时不重建 ES 文档，由校验任务确认范围后排除该对象；事务批次其余范围内对象仍继续比较。

### 3.7 监控、验收与关联调整

分别监控同步延迟与失败、校验未完成批次、范围内差异、超期事件跳过数量、ILM 错误及待删除索引积压。范围排除不等于物理清理完成：即使不再对超期记录逐条对账，也须通过索引层监控发现 ILM 长期未执行及磁盘增长。

| 验收场景 | 预期结果 |
|---|---|
| 同一消息混合 DELETE、超期 UPDATE、有效 INSERT | 前两者不操作 ES，有效事件正常处理；有效事件失败时不提前确认消息 |
| 五年下界前一天、当天及闰日 | 查询、写入过滤、校验和修复使用一致的包含关系 |
| 差异修复跨午夜后过期 | 不重新写入；校验新一轮记录范围排除，其他对象正常处理 |
| 全部对象超期的事务批次 | 有排除记录并可推进进度，不永久阻塞 |
| 范围内查询失败或索引缺失 | 不伪装成文档不存在或校验通过 |
| ILM 删除月份索引后旧消息重放 | 不重建过期索引 |
| ILM 失败或延后 | 查询仍屏蔽超期数据，索引积压可被监控发现 |

以上是待执行的验收用例，不是测试结果。后续接入须统一消费端 DELETE 分支、保留期文档、校验文档和修复入口；现有 016 文档无条件将“MySQL 删除、ES 存在”视为差异的表述不能直接用于本方案。此次只新增本文，未修改关联文档或代码。

## 5 异议与分析及依据

- 选择整索引清理不意味着机械硬盘无法执行文档删除。这里减少的是到期文档删除及后续合并成本，实际性能收益尚未压测。机制依据：[Elastic 7.17：Delete indices, not documents](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/size-your-shards.html#delete-indices-not-documents)，正文已在本会话前序检索中核实。
- “消费端跳过 DELETE”不等于“校验一律忽略 MySQL 缺失”。只有原始创建时间明确超期，才能作为保留范围排除；范围内异常仍需调查。
- ILM 不会自动理解业务五年窗口。整月安全删除依赖月份路由、计龄起点及策略配置，具体配置依据和验证缺口见第 3.3 节链接。
- 日期刷新、状态分类和跨日闭环属于本文提出的实现建议，不是外部文章中已经验证的项目案例。本次仅完成文档设计，未执行消息消费、数据修复、生产清理或集群验证。

## 2 面试口述精炼版本

**采用 ILM 整索引清理**

我们选择不同步 MySQL 的到期删除，由 ILM 删除过期月份索引。数据按原始创建月份存储，查询只覆盖近五年，也允许超期数据暂存，因此把索引删除时间设在整个月的数据都过期之后，统一清理。相比同步 MySQL DELETE、逐文档删除并取消 ILM 删除阶段，这样可以避免冷节点处理这些文档删除及后续段合并。两种方案的比较见 3.2。

**统一查询与校验范围**

代价是校验和修复要按原始创建时间限定近五年，超期暂存文档不作为差异修复。同步删除的方案比较直观，但仍需处理重试和空索引清理。目前选型已确认，消费端过滤、校验范围调整和 ILM 实际执行仍待核实。校验影响见 3.4。

## 3 详细方案

### 3.1 两种方案的处理方式

**方案一：不同步到期 DELETE，ILM 删除整个索引。**

保留范围内的新增、更新继续同步；MySQL 清理过期记录时，不调用 ES 文档删除接口。ILM 按索引计龄和策略条件删除对应索引，不逐条读取文档的 `create_time` 判断是否过期。必须先保证文档写入正确的创建月份索引，并把删除期限设在整个月份的数据都超出保留范围之后。MySQL 与 ES 独立清理，不要求彼此等待。

现有保留期设计将 `origination_date` 设为所属月份下个月 1 日零点，cold 和 delete 分别从该起点计龄 `366d`、`1830d`。固定天数属于项目的保守取值，不等于五个自然年，也不是官方推荐值；达到年龄条件不代表已经执行。配置与验证边界见 [索引保留期与删除](<./032_ES改造_ES_生命周期管理_到期删除.md>)。

**方案二：同步到期 DELETE，取消 ILM delete 阶段。**

消费服务根据删除前的业务 ID、原始 `create_time` 定位月份索引和文档，执行逐条删除。删除失败需要重试或补偿，并防止旧新增、更新消息把已删除记录重新写入。取消 delete 阶段不意味着取消冷热迁移；索引删空后仍需另行清理。

这里的“逐条删除”指以文档为删除对象，可以通过 Bulk 接口批量提交，不意味着每条文档单独发一次网络请求。批量提交可以减少请求开销，但不会把文档删除变成整索引删除。

方案二仅用于比较，不是当前采用的设计。

两种方案都要阻止超期新增、更新、重试和补偿重新写入 ES。方案一可能被重新创建已删除索引，方案二可能被重新写入已删除文档；这不是方案二独有的问题。方案二若保留冷层只读配置，还须核实目标索引是否允许文档删除，不能仅凭数据位于机械硬盘就认定可写或不可写。

### 3.2 优缺点对比

| 对比项 | 方案一：ILM 整索引删除 | 方案二：同步逐条删除 |
|---|---|---|
| 删除链路 | 消费服务不执行到期文档删除，清理由 ILM 负责；需维护生命周期策略 | 需要处理删除定位、失败重试、漏删补偿和旧消息重新写入 |
| 冷节点开销 | 整索引清理，避免这些文档删除引起的段合并；文件清理和集群状态更新仍有成本 | 按到期记录数量执行文档删除，可批量提交；仍有删除处理及后续段合并开销，实际影响需压测 |
| 空间回收 | 索引删除时直接清理对应存储文件，无需通过段合并逐条剔除文档 | 保留索引时，删除文档先标记删除，物理空间通常等段合并回收；若随后删除空索引，也可由整索引删除释放 |
| 到期精度 | 按月清理，部分超期数据暂时保留；还可能有策略余量及调度延迟 | 跟随 MySQL 删除批次处理，仍有消息传输、消费和搜索可见性延迟 |
| 查询边界 | 必须严格下推五年日期条件，隐藏物理上仍存在的超期数据 | 删除同步后两边状态更接近；查询范围限制仍需保留 |
| 校验与修复 | 需要增加统一保留范围判断，避免将超期暂存数据误报、误修复 | 删除结果比较更直观，但仍需处理异步延迟、失败和并发变化 |
| 索引管理 | 索引及其分片随整索引删除一并清理 | 删除全部文档不会自动删除索引，空索引和分片仍有管理开销 |
| 与 MySQL 清理的关系 | 两者独立；MySQL 清理延迟不阻止 ES 按策略清理 | ES 清理依赖 MySQL 产生删除事件，并依赖同步链路成功处理 |
| 故障关注点 | ILM 错误、索引积压、磁盘增长，以及过期写入重新建索引 | DELETE 消费失败、消息积压、漏删、旧消息重新写入及空索引积压 |
| 主要优势 | 适合按时间组织索引和整批过期，减少无查询收益的逐条删除 | 两端记录删除状态更接近，比较规则较直观 |
| 主要代价 | 统一查询、校验和修复的日期边界，接受物理清理延后 | 承担逐条删除链路和合并成本，仍需空索引清理机制 |

用户提供的规模是日均新增约 20 万条。只有五年前对应日期的数据规模相近、保留期清理稳定执行时，才可据此粗估日均到期删除约 20 万条；这不是实际删除量统计。首次历史清理、积压补清和集中执行的峰值也不能用日均值代替。

删除与空间回收机制依据见 [Elastic 7.17：Delete indices, not documents](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/size-your-shards.html#delete-indices-not-documents)。该依据支持机制比较，不提供本项目两种方案的性能差值。

### 3.3 为什么选择方案一

项目的数据按原始创建月份组织，只查询近五年，并接受超期数据暂时保留。这些前提使整索引删除与业务保留范围匹配。以此为基础，方案一减少了对冷节点的逐条删除操作，代价集中在日期边界和 ILM 运维管理上。

方案二并非不可行，其优势是删除结果比较直观；但仅为了让两边物理记录更接近，而持续删除已不再参与查询的文档，收益有限。综合判断选择方案一，不以“机械硬盘一定承受不了”为理由。

### 3.4 对 MySQL 与 ES 校验任务的影响

现有 [新表与 ES 增量校验](<./043_ES改造_ES_新表与 ES 增量校验_整体实现.md>)按 `update_time` 扫描 MySQL 当前仍存在的记录，再比较两端当前状态；扫描截止时间使用当前时间减五分钟，以避开 ES 正常同步延迟。由于到期 DELETE 后 MySQL 记录已不存在，删除记录不会进入本校验任务，也不会被直接判定为 ES 差异。

保留范围必须纳入校验和修复判断。以下是建议的实现方式，尤其是批次跨日和状态处理，尚未确认为最终实现：

1. 扫描只读取当前仍存在且满足 `update_time` 条件的 MySQL 记录，并使用复合游标和重叠窗口降低漏查风险。
2. 任务执行时重新读取 MySQL 当前记录和版本，再读取 ES 当前文档进行比较，不使用扫描时保存的旧数据补偿。
3. MySQL 记录不存在时，按当前方案结束任务，不查询 ES，也不把该记录创建为删除差异；这只适用于本方案已确认的到期清理场景。
4. 对仍存在的记录继续比较版本和业务字段；读取失败、版本冲突或明确差异按 043—047 的状态和重试规则处理。
5. 修复执行时再次核对当前保留范围，避免等待或重试期间已过期的记录被重新写入；该记录如何结束本批处理需要在实现中明确。

校验任务只读当前业务数据并记录结果，写入补偿由独立程序执行；不再以 GTID 或完整事务批次作为本校验入口。扫描进度、任务状态、比较结果和自动补偿分别由 044—047 说明，范围内的读取失败仍是执行异常。

因此，预计是局部规则调整，而非重写任务。但实际工作量取决于日期过滤是否集中、事件字段是否齐全，以及校验与修复是否分散在多个入口；未检查代码前不能量化改动量。

## 5 异议与分析

- **“ES 到期删除不会逐文档处理”过于绝对。**整批时间数据到期适合整索引删除；只需删除索引中部分记录时，文档级删除仍有用途。本项目选择方案一依赖明确的保留规则，而不是 ES 不支持另一种方式。
- **“机械硬盘不能执行删除”缺乏依据。**删除机制有官方说明，但是否影响业务取决于峰值速率、分片分布、磁盘能力和并发查询等因素；未压测不能断言每天 20 万条必然有问题。
- **“采用方案一校验不用改”不成立。**物理留存范围不同，必须先明确比较范围；否则会把正常暂存数据当作差异。
- **“取消 ILM delete 就无需额外清理”不成立。**逐条删空文档不会自动移除索引，仍需管理空索引及其分片。

我们根据记录的原始创建时间，将数据写入对应的自然月索引，通过 ILM（索引生命周期管理）处理冷热迁移和到期删除。

## 3 详细方案

### 3.1 撤销与保留期清理

撤销通过新增撤销记录表达，业务类型为 `BS0013`，并更新相关交易状态；相关业务依据见[项目介绍](<D:/000/sources/eas/000/000_E账通_项目介绍.md:180>)和[消费原内容](<D:/000/sources/eas/000/000_消费_原内容.md:1096>)。MySQL 五年清理产生的物理删除属于保留期清理，不是业务提前删除。

新增和更新继续通过 Canal、RocketMQ 同步到 ES；保留期清理产生的 DELETE 按本方案不执行 ES 文档级删除，而由生命周期机制删除整个过期自然月索引。

### 3.2 统一计龄与策略选择

由 ILM 统一负责冷热迁移和到期删除，减少额外清理任务的开发维护；仍须配置必要权限、监控、告警和失败恢复。

| 项目 | 最新方案 |
|---|---|
| 索引划分 | 按原始创建时间划分自然月索引 |
| 计龄起点 | 所属月份下个月 1 日 00:00:00（中国标准时间，UTC+08:00），对应毫秒时间戳 |
| 历史回放 | 绑定只有 hot 阶段的临时策略，不执行迁移或删除 |
| 正式策略启用 | 历史范围同步、校验及观察验收通过后切换 |
| 冷层迁移 | 已确认 `cold.min_age: 366d`，到期具备迁移资格 |
| 到期删除 | 已确认 `delete.min_age: 1830d`，删除整个索引 |
| 查询范围 | 按统一业务时区限制最近五年，屏蔽暂时保留的过期数据 |

本项目不使用 rollover，cold 和 delete 的 `min_age` 均相对于同一 `origination_date` 计算，不是从进入 cold 后重新计时。ILM 周期执行，达到期限不等于迁移或删除已经完成。

不同月份的起点由提前创建任务根据目标年月计算并显式设置，不在通用模板中复用固定时间戳。日常索引在上一个月准备，历史导入索引在导入前准备；模板负责公共结构，创建和配置核对流程见 [04 索引设计与创建](<030_ES改造_ES_索引设计、创建与写入.md>)。提前创建时未来起点的接受、阶段年龄计算和实际删除调度仍未通过集群验证。

[来源：ILM 设置](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/ilm-settings.html)支持显式设置计龄起点；[索引生命周期](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/ilm-index-lifecycle.html)说明阶段年龄条件与执行过程。具体业务取值来自已确认设计，不是官方规定。

### 3.3 为什么删除配置为 1830 天

`1830d = 366 × 5` 是覆盖五个自然年的保守固定时长。以所属月份结束后的零点计龄，再等待 1830 天，即使该月最后创建的记录也已超过五年。这个保证以数据按原始创建时间正确写入对应月份索引为前提；具体实现仍需测试验证。

例如，`records-2024.01` 从 `2024-02-01 00:00:00+08:00` 开始计龄，`366d` 和 `1830d` 都从这一时间点计算。达到 `1830d` 后允许整索引删除，实际调度可以延后，不逐条验证文档的 `create_time`。

假设 MySQL 每天清理“当天零点减 5 年”之前的数据：

| 日期 | MySQL 清理边界 | ES 对 `records-2021.10` 的处理 |
|---|---|---|
| 2026-10-15 | 清理 2021-10-15 零点之前的数据 | 保留，月份内仍有未过期数据 |
| 2026-11-01 | 清理 2021-11-01 零点之前的数据 | 整个月份达到五年保留要求；1830 天策略可继续保留至年龄条件满足 |

这里要区分“整月已经过期”和“ILM 已达到配置的删除期限”，不能把表中的最早删除资格日期写成 ILM 实际执行日期。固定天数不等于五个自然年；本方案利用允许延后删除的规则提供余量。

### 3.5 MySQL 与 ES 独立清理

ES 删除只按自身保留期限判断，不等待 MySQL 实际完成清理；两者没有先后顺序要求。ILM 无需感知 MySQL 清理任务是否失败或延迟。

### 3.6 切换与过期消息防护

历史索引切换正式策略时可能已经超过 1830 天，随后可能很快进入删除流程。切换前须确认历史范围同步、校验和观察验收已完成，并检查目标索引是否具备删除资格；不能仅凭策略绑定成功判断业务安全。

新增、更新、重试及补偿路径均须限制普通 Index 请求自动创建目标月份索引，防止绕过准备流程重建已删除月份。消费者不创建索引，索引缺失进入统一失败处理并保留重试能力，不新增专门恢复分支。仅过滤保留期 DELETE 不能解决旧 INSERT 或 UPDATE 重放问题；自动创建限制的实际配置、过期事件处置和在途请求行为仍待实现验证，不能将本设计写成已验证的防护效果。

### 3.7 消费端过滤 DELETE（建议方案，待确认与实现）

建议在现有 RocketMQ 消费服务中精确匹配消费记录的库名和物理表名，跳过该表的 DELETE，不调用 ES 删除接口；无需为此修改 Canal Server 或拆分 Instance。DELETE 仍经过 RocketMQ，ES 到期清理由 ILM 独立完成。本节为建议，不代表已实现。

以下为 Java 示意代码，类型及方法名称须适配现有代码：

```java
for (ChangeEvent event : events) {
    // 仅匹配消费记录表，避免误过滤其他表的删除事件。
    if (isConsumptionTable(event.getDatabase(), event.getTable())
            && "DELETE".equals(event.getType())) {
        continue; // 只跳过当前事件，继续处理同一消息中的其他事件。
    }
    processNormally(event); // 沿用原处理流程；失败时抛出异常。
}
```

消费记录表的 INSERT、UPDATE 正常同步，其他表的事件保持原有处理方式。整条消息的其余事件及必要状态处理成功后才正常确认；若全部事件均被过滤，也正常确认。失败时继续沿用异常抛出和消息重试流程，不能因跳过 DELETE 而提前确认整条消息。被过滤 DELETE 对既有删除状态维护的影响仍须核对。

依据：当前已确认的“消费记录仅有保留期物理删除”业务规则，以及本次提供的消费端过滤建议。示意代码未运行，尚未验证与现有消费服务的兼容性。

## 3 详细方案

### 3.1 查询范围

后端把查询起止日期限制在最近五年，单次跨度最多一个月。时间范围可以减少参与检索的索引、分片和结果合并，但范围内仍需处理多少候选记录，取决于查询条件、排序、分片布局和总数统计。

按日均约 20 万条估算，30 天约 600 万条，这是范围内记录量，不代表每次都扫描全部记录，也不代表每页只处理 100 条。

### 3.2 每页大小与候选结果

每页最多返回 100 条，主要控制文档读取、响应组装、网络传输和前端渲染成本。分片可能先提供排序候选，协调节点再合并出全局结果；候选数量不等于实际扫描记录数。

### 3.3 `search_after` 分页

`search_after` 使用上一页末条记录的完整排序值作为下一页起点，降低深分页成本。[来源：分页搜索](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/paginate-search-results.html)

当前示例按 `tradeTime DESC, consumeId DESC` 排序，要求 `consumeId` 单值、非空且全局唯一。时间字段用于范围查询和主排序，`consumeId` 通过 Doc Values 支持次排序，不等于建立了检索索引；索引排序能力仍需单独核验。[来源：索引排序](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/index-modules-index-sorting.html)。当前方案不使用 PIT，翻页期间数据变化可能造成重复或遗漏。
