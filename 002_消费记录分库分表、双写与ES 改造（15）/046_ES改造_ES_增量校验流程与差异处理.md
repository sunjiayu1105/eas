# 046_ES改造_ES_增量校验流程与差异处理

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

> 本文档是主文档“043_ES改造_ES_新表与 ES 增量校验总览”的拆分考点。共同已确认规则、完整待确认事项和异议分析以主文档为准；本文件只维护本考点的口述内容和详细方案。

## 1 面试口述精炼版本

本文采用异步校验：增量校验消费者先保存待校验任务，再确认 RocketMQ 消息；后续任务延迟读取 MySQL 新表和 ES，执行比较、补偿和复核。同步校验可以在消费回调内直接比较后确认，但会受 ES 可见性、回调耗时和重复重投影响；任务持久化、确认顺序和故障恢复仍待实现验证。

## 2 详细方案

### 2.1 同步校验对比与异步校验边界

同步和异步从机制上都可行，但本文采用异步校验；同步方式只用于说明取舍，不作为当前任务入口。

**同步校验**：增量校验消费者组在 RocketMQ 消费回调中直接读取 MySQL 与 ES，比较成功后确认消息，失败则抛出异常并等待 RocketMQ 重投。这种方式不一定需要独立的待校验任务表，但会受到 ES 写入延迟、消费回调耗时、消息内部分事件失败以及重投重复处理的影响；如果需要延迟读取或多次复核，就不能只依赖同步消费。

**示例**：假设 MySQL 新表中某条消费记录的业务版本从 `100` 更新为 `101`。Canal 产生增量事件后，ES 写入消费者将变更写入 ES，增量校验消费者同时接收对应消息并保存待校验任务。如果随后立即查询 ES，可能因为 ES 刷新延迟暂时读到版本 `100`，从而误判为写入失败。此时应延迟读取 MySQL 新表和 ES：如果 ES 已变为 `101`，说明只是查询可见性延迟；如果 MySQL 新表又已更新为 `102`，则按最新版本重新判断；多次复核后仍不一致，才进入补偿流程。

**异步校验**：增量校验消费者组接收 RocketMQ 消息后，提取业务主键、版本、操作类型等定位信息，保存一条待校验任务，再确认消息；后续由校验任务延迟读取 MySQL 新表和 ES 当前状态，执行比较、补偿和复核。这种方式符合本文当前的延迟读取、差异复核、独立补偿和校验进度设计。必须先可靠保存任务再确认消息：如果先确认、后保存，进程可能在任务状态持久化前退出，导致这条变更既没有可恢复的任务记录，也无法仅靠已推进的消费位点重新发现。任务表结构、任务状态持久化、保存任务与消息确认之间的一致性、重复任务和故障恢复仍待实现验证。

### 2.2 RocketMQ 消息处理与待校验任务落库

增量校验消费者接收 RocketMQ 消息后，不把消息中的事件快照直接作为最终比较结果，而是先提取后续查询所需的定位信息，例如业务主键、版本和操作类型，并将这次变更保存为待校验任务。文档当前只确认任务需要可靠落库，具体任务表字段、唯一键和状态枚举仍待实现确认。

任务成功落库后，消费者才确认对应的 RocketMQ 消息。落库失败不得确认消息，否则可能出现消费位点已经推进、待校验任务却没有保存的缺口；确认失败可能导致消息重放，因此重复任务的接收和执行仍需验证。

任务到期后，校验流程重新读取 MySQL 新表和 ES 的当前数据，按规定业务字段和版本进行比较。首次读取如果遇到 ES 刷新延迟，可以等待后复核；多次复核仍不一致时，记录差异并进入补偿流程，补偿完成后再次读取两端确认结果。
