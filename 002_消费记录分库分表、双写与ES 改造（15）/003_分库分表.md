# 3.1 分库分表

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 面试口述精炼版本

**分库分表规模**

基于 ShardingSphere-JDBC 对消费记录进行分库分表，拆分为 2 个库、每库 16 张表，2 个库部署在独立的 MySQL 实例上，共 32 个物理分片。

**分片键**

分片键选用商户号 `merchantNo`。

**分片策略**

对 `merchantNo` 进行哈希取模，得到分片编号 `shardIndex`，再根据分片编号确定数据存在哪个库、哪张表。

**主键设计**

新表主键由雪花 ID 拼接固定 2 位分片编号生成，按字符串保存。

**历史迁移后的数据对比**

历史迁移会重建主键。DBA 完成迁移后，通过不变的交易流水号 `serialNo` 对应新旧表中的同一笔记录，再对比数据。

**容量与维护验证**

容量评估还要考虑大商户集中带来的热点，并结合演练结果判断，详见[999_为什么选择 2 个库、每库 16 张表？.md](<D:/000_ 找工作_2026/sources/E账通/002_消费记录分库分表、双写与ES 改造（15）/999_为什么选择 2 个库、每库 16 张表？.md:6>)和[999_如何演练，确认单表索引维护能否满足维护窗口？.md](<D:/000_ 找工作_2026/sources/E账通/002_消费记录分库分表、双写与ES 改造（15）/999_如何演练，确认单表索引维护能否满足维护窗口？.md:6>)。

## 详细方案

## 3.1.1 分片键与分片策略

消费记录基于 ShardingSphere-JDBC 进行分库分表，由这一应用侧分片组件按配置的分片规则将 SQL 路由到对应库表。采用已确定的 2 个库、每库 16 张表，共 32 个物理分片；2 个库分别部署在有独立资源的 MySQL 实例上。分片键选用商户号 `merchantNo`：每笔消费记录都归属一个商户，创建记录时即可取得商户号，且该值在交易生命周期内保持不变。根据 `merchantNo` 哈希取模可得到 `shardIndex`；也可以从 `consumeId` 末尾固定 2 位直接取得 `shardIndex`。两种入口都按每库 16 张表计算逻辑库编号 `shardIndex / 16` 和逻辑表编号 `shardIndex % 16`，再通过统一名称映射定位具体库和表。该映射的生成、解析和一致性仍需结合实际路由代码验证。

同一商户不会被拆散，大商户仍可能形成热点，容量评估不能只看平均条数。哈希取模也不保证各分片的数据量或负载完全均匀；缺少商户号且没有其他可用路由信息的跨商户查询，仍需访问多个分片。容量依据及验证边界见 [999_为什么选择 2 个库、每库 16 张表？.md](<D:/000_ 找工作_2026/sources/E账通/002_消费记录分库分表、双写与ES 改造（15）/999_为什么选择 2 个库、每库 16 张表？.md:6>)。

## 3.1.2 主键设计与分片定位

**主键生成与回查**

`consumeId` 按“雪花算法 + 基因法”生成：雪花 ID 后拼接固定 2 位分片编号，整个值按字符串保存。后缀必须与 `merchantNo` 算出的 `shardIndex` 一致，例如 `07` 指向分片 7；按主键回查时，先解析后缀，再使用同一库表映射定位记录。只有后缀解析结果与路由映射一致时，才能继续执行目标分片查询。新表第 1 次创建记录时生成一次，后面更新或 Canal 重放都继续使用这个值。该设计仍需生成器、后缀解析和路由代码验证。
