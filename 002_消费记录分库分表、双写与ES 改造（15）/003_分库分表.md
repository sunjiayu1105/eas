# 003_分库分表

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。技术栈包括 Java 8、Spring Boot 2.7.18、MySQL 8.0.33 和 Elasticsearch 服务端 7.17.15。

## 1 面试口述精炼版本

以下按已确认方案说明；分片路由、主键生成和版本同步的实际实现仍需结合代码核验，容量和运行效果仍需演练验证。

**先根据容量目标确定分片规模**

项目以上一年度年新增 7,300 万条记录为基准，重点评估第 10 年时最近 5 年的累计保留数据量，数据库只保留最近 5 年。根据这个容量目标，最终采用 2 个 MySQL 实例、每个实例 16 张消费记录表，共 32 个物理分片，把数据、索引和维护压力分散到多个实例和物理表中。分库分表不会减少数据总量，容量是否满足仍需通过演练确认，详见[容量目标与拓扑规模](#21-容量目标与拓扑规模)。

**再用商户号完成分片路由**

分片键使用商户号 `merchantNo`。写入时对商户号哈希取模，计算分片编号 `shardIndex`，再由分片编号映射到实例和物理表，因此同一商户能够稳定落到同一个分片。查询条件没有商户号或其他分片定位信息时，可能需要访问多个分片并合并结果，详见[分片键与分片编号](#22-分片键与分片编号)和[分片编号到实例和物理表的路由](#23-分片编号到实例和物理表的路由)。

**主键携带分片信息，支持按主键回查**

新表的 `consumeId` 由雪花算法生成的 ID 拼接固定两位分片编号组成，首次写入后保持不变；按主键查询时解析末尾分片编号，就能定位目标库表，详见[主键设计与回查](#24-主键设计与回查)。

**版本字段支持 ES 同步控制**

新表比旧表增加业务版本号 `version`。同步到 ES 时携带这个版本，由 ES 比较新旧版本，防止乱序消息用旧数据覆盖新数据，详见[版本字段与 ES 同步](#25-版本字段与-es-同步)。

**历史迁移用业务流水号做验收依据**

历史迁移会重新生成 `consumeId`，所以不能比较旧表 `id` 和新表主键，而要用迁移前后不变且全局唯一的 `serialNo` 关联记录，再核对字段和数量，详见[历史迁移与数据验收](#26-历史迁移与数据验收)。

## 2 详细方案

### 2.1 容量目标与拓扑规模

项目按上一年度年新增 7,300 万条记录作为预测基准，结合未来增长率评估第 10 年时最近 5 年的累计保留数据量。未来 10 年的数据增长方向用于判断数据库、分库分表、归档和扩容方案能否持续演进；不把第 1 年至第 10 年的累计数据全部当作当前保留容量。

最终方案采用 2 个 MySQL 实例，每个实例部署 16 张消费记录表，共 32 个物理分片。分表用于控制单表数据、索引和维护任务的规模，分实例用于分散读写、索引维护、备份和后台查询对单个实例的资源占用。分库分表不会减少数据总量，实际收益还取决于数据分布、查询范围、索引设计和资源规格。

**容量计算过程**

以上一年度为第 0 年，新增量 `A0 = 7,300 万条`。历史年度增长率按 `（本年度新增量 - 上年度新增量）÷ 上年度新增量` 计算；未来各年采用的预测增长率 `g1～g10`，需根据历史趋势和已确认的业务计划确定，不能把未来实际新增量作为已知条件。

```text
第 N 年新增量 AN = 7,300 万条 × (1 + g1) × … × (1 + gN)
第 10 年末最近 5 年累计保留数据量 = A6 + A7 + A8 + A9 + A10
```

这里按完整年度估算第 10 年末的保留量；实际清理仍按最近 5 年的时间范围执行。预测增长率尚未提供，因此不能给出确定的容量结果，也不能仅凭 7,300 万条这一基准证明 32 个分片足够。还需用单条数据和索引占用换算存储空间，并结合分片倾斜、实例资源和维护空间验证。

### 2.2 分片键与分片编号

分片键使用 `merchantNo`。每笔消费记录归属于一个商户，创建记录时可以取得该字段，且商户号在交易生命周期内保持不变，因此可以在新增、更新和按商户查询时定位分片。

对规范化后的 `merchantNo` 做哈希取模：

```text
shardIndex = hash(merchantNo) mod 32
```

`shardIndex` 的范围为 `0～31`。这里的 mod 表示非负取模；Java 实现需处理负哈希值，不能直接假定 `% 32` 的结果非负。哈希取模可以把商户分散到 32 个分片，但不保证数据量和负载完全均匀；大商户集中时仍可能形成热点。

### 2.3 分片编号到实例和物理表的路由

每个实例承载 16 张表，使用整数除法和取余得到逻辑实例、逻辑表编号：

```text
实例编号 = shardIndex / 16    // 整数除法，结果为 0 或 1
表编号   = shardIndex % 16    // 余数范围为 0～15
```

例如：

```text
shardIndex = 7  → 实例 0、表 7
shardIndex = 23 → 实例 1、表 7
```

逻辑编号还要经过项目统一的库表名称映射，才能得到实际数据库和物理表名。新增、更新、查询和迁移工具必须使用同一套映射规则；当前映射生成、解析及与生产配置的一致性仍需结合实际路由代码验证。

如果查询条件既没有 `merchantNo`，也没有其他能够推导目标分片的信息，可能需要把请求路由到多个分片，再由分库分表中间件或上层合并结果。跨分片排序、分页和总数统计会增加数据库请求、数据传输和结果合并成本，具体性能仍需验证。

### 2.4 主键设计与回查

新表使用字符串类型的 `consumeId` 作为主键，规则为：

```text
consumeId = snowflakeId + twoDigit(shardIndex)
```

例如分片编号 7 写成 `07`。主键生成时使用与分片路由相同的 `merchantNo` 和取模规则，保证主键后缀与实际写入分片一致。记录首次创建时生成一次；后续更新、同步和 Canal 重放继续使用原值。

按主键回查时，先读取 `consumeId` 末尾固定两位并解析为 `shardIndex`，再使用 2.3 的映射定位实例和表。只有主键后缀、`merchantNo` 计算结果和库表映射相互一致，才能稳定定位目标分片。生成器、后缀解析、字段长度及路由代码仍需结合实际实现验证。

### 2.5 版本字段与 ES 同步

新表新增业务版本号 `version`，旧表不增加。按已确认方案，历史导入初始化为 `1`，后续更新在同一条 SQL 中修改业务字段并递增版本；导入重跑不重置已有版本，消息重试沿用原消息的数据和版本。版本维护规则见[004_业务双写](<./004_业务双写.md>)，该文档记录的是设计要求，不代表实现已经验证。

同步新增、更新数据时，消费服务将业务版本随 Index API 请求传给 ES，并设置 `version_type=external`。ES 在同一物理索引、同一文档 `_id` 内比较版本，仅接受更高版本的写入；相同或更低版本会发生版本冲突，需要区分重复、过期和异常。仅在表中增加字段并不能自动阻止旧数据覆盖，必须正确维护版本并传入 ES 请求。索引定位及写入规则见[011_ES改造_ES_索引设计、创建与写入](<./011_ES改造_ES_索引设计、创建与写入.md>)，实际代码和请求行为仍需验证。

### 2.6 历史迁移与数据验收

历史迁移会在新表生成新的 `consumeId`，旧表 `id` 与新表主键不直接相等。迁移校验应使用迁移前后保持不变且全局唯一的 `serialNo` 关联旧记录和新记录，再按验收清单比较业务字段、记录数量和必要的业务关系。新表独有的 `version` 不参与新旧字段等值比较，需单独验证历史初始化及导入重跑不重置版本的行为。

DBA 负责按迁移方案执行导入，记录批次、范围、结果和耗时。文档中的校验规则只是验收设计，不能据此认定字段映射、历史数据完整性或恢复能力已经验证。

### 2.7 容量、性能与维护验证

容量验证的主场景是第 10 年时最近 5 年的累计保留数据量。如果年度新增量波动较大，还要检查第 1～10 年各年度对应的最近 5 年累计保留数据量并取最大值；预测前几年的保留量还包含预测起点之前尚未到期的历史数据。验证范围还应包括大商户热点、数据和索引占用、跨分片查询、索引创建、表结构变更、备份恢复、迁移窗口和扩容窗口。

单项演练只能支持对应范围的结论。例如，单表索引维护演练只能说明特定数据规模和环境下的维护耗时，不能直接证明两个实例能够承接全部业务峰值；容量、路由、查询性能、迁移和恢复仍需分别验证。

## 3 已确认规则

- 以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。
- 采用 2 个 MySQL 实例，每个实例 16 张消费记录表，共 32 个物理分片。
- 使用 `merchantNo` 作为分片键，并按 32 个分片计算 `shardIndex`。
- `shardIndex` 按每实例 16 张表映射到实例编号和表编号；实际库表名称以统一映射配置为准。
- 新表主键使用字符串类型的 `consumeId`，由雪花 ID 拼接固定两位分片编号生成。
- 新表比旧表增加 `version` 字段，用于后续同步到 ES 时进行版本控制。
- 历史迁移使用不变的 `serialNo` 关联新旧记录，不能直接比较旧表 `id` 和新表 `consumeId`。
- 容量评估统一使用‘最近 5 年累计保留数据量’表述。
