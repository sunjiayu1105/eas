# 003_分库分表

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。技术栈包括 Java 8、Spring Boot 2.7.18、MySQL 8.0.33 和 Elasticsearch 服务端 7.17.15。

## 1 面试口述精炼版本

**先明确容量目标，再确定分片规模**

项目先按上一年度年新增 7,300 万条记录作为基准，预测未来 10 年的新增量，重点评估第 10 年时最近 5 年的滚动数据量。数据库只保留最近 5 年的数据，因此第 10 年的这 5 年滚动数据量是当前长期容量设计的主要校验目标。基于这个目标，方案采用 2 个 MySQL 实例，每个实例 16 张消费记录表，共 32 个物理分片。这样可以把数据、索引、读写请求和维护任务分散到不同实例和不同表中，降低单表和单实例的集中压力；具体容量效果仍需通过演练确认。

**用商户号决定记录落在哪个分片**

分片键选择 `merchantNo`。每笔消费记录都归属于一个商户，写入时能够取得商户号，同一商户也应保持稳定路由。系统对规范化后的 `merchantNo` 做哈希取模，得到 `shardIndex = hash(merchantNo) mod 32`，再由这个编号确定实例和物理表。没有 `merchantNo` 或其他可定位条件的查询，可能需要访问多个分片，跨分片排序、分页和统计的成本需要单独评估。

**按统一映射把分片编号转换成库表**

`shardIndex` 的范围是 `0～31`。每个实例承载 16 张表，因此实例编号为 `shardIndex / 16`，表编号为 `shardIndex % 16`，再通过统一的库表名称映射定位真实库表。新增、更新和按商户查询使用同一套路由规则；按主键回查时解析 `consumeId` 末尾的分片编号，也必须得到同一个目标分片。

**让主键携带分片信息**

新表使用字符串类型的 `consumeId` 作为主键，由雪花 ID 拼接固定两位的 `shardIndex` 组成。记录首次写入时生成一次，后续更新、同步和 Canal 重放继续使用原值，不能重新计算后覆盖主键。按主键回查时，先解析末尾两位分片编号，再按同一套映射定位实例和表。主键生成、解析及路由代码仍需结合实际实现核验。

**用稳定业务流水号校验历史迁移**

历史迁移后新表会重新生成 `consumeId`，所以不能直接比较旧表 `id` 和新表 `consumeId`。迁移校验应使用迁移前后保持不变且全局唯一的业务流水号 `serialNo` 关联新旧记录，再按验收清单比较字段、数量和必要的业务关系。文档中的校验规则不代表迁移已经完成或恢复能力已经验证。

## 2 详细方案

### 2.1 容量目标与拓扑规模

项目按上一年度年新增 7,300 万条记录作为预测基准，结合未来增长率评估第 10 年时最近 5 年的滚动数据量。未来 10 年的数据增长方向用于判断数据库、分库分表、归档和扩容方案能否持续演进；不把第 1 年至第 10 年的累计数据全部当作当前保留容量。

最终方案采用 2 个 MySQL 实例，每个实例部署 16 张消费记录表，共 32 个物理分片。分表用于控制单表数据、索引和维护任务的规模，分实例用于分散读写、索引维护、备份和后台查询对单个实例的资源占用。分库分表不会减少数据总量，实际收益还取决于数据分布、查询范围、索引设计和资源规格。

### 2.2 分片键与分片编号

分片键使用 `merchantNo`。每笔消费记录归属于一个商户，创建记录时可以取得该字段，且商户号在交易生命周期内保持不变，因此可以在新增、更新和按商户查询时定位分片。

对规范化后的 `merchantNo` 做哈希取模：

```text
shardIndex = hash(merchantNo) mod 32
```

`shardIndex` 的范围为 `0～31`。哈希取模可以把商户分散到 32 个分片，但不保证数据量和负载完全均匀；大商户集中时仍可能形成热点。

### 2.3 分片编号到实例和物理表的路由

每个实例承载 16 张表，使用整数除法和取余得到逻辑实例、逻辑表编号：

```text
实例编号 = shardIndex / 16    // 整数除法，结果为 0 或 1
表编号   = shardIndex % 16    // 余数范围为 0～15
```

例如：

```text
shardIndex = 7  → 实例 0、表 7
shardIndex = 23 → 实例 1、表 7
```

逻辑编号还要经过项目统一的库表名称映射，才能得到实际数据库和物理表名。新增、更新、查询和迁移工具必须使用同一套映射规则；当前映射生成、解析及与生产配置的一致性仍需结合实际路由代码验证。

如果查询条件既没有 `merchantNo`，也没有其他能够推导目标分片的信息，可能需要把请求路由到多个分片，再由 ShardingSphere-JDBC 或上层合并结果。跨分片排序、分页和总数统计会增加数据库请求、数据传输和结果合并成本，具体性能仍需验证。

### 2.4 主键设计与回查

新表使用字符串类型的 `consumeId` 作为主键，规则为：

```text
consumeId = snowflakeId + twoDigit(shardIndex)
```

例如分片编号 7 写成 `07`。主键生成时使用与分片路由相同的 `merchantNo` 和取模规则，保证主键后缀与实际写入分片一致。记录首次创建时生成一次；后续更新、同步和 Canal 重放继续使用原值。

按主键回查时，先读取 `consumeId` 末尾固定两位并解析为 `shardIndex`，再使用 2.3 的映射定位实例和表。只有主键后缀、`merchantNo` 计算结果和库表映射相互一致，才能稳定定位目标分片。生成器、后缀解析、字段长度及路由代码仍需结合实际实现验证。

### 2.5 历史迁移与数据验收

历史迁移会在新表生成新的 `consumeId`，旧表 `id` 与新表主键不直接相等。迁移校验应使用迁移前后保持不变且全局唯一的 `serialNo` 关联旧记录和新记录，再按验收清单比较字段、记录数量和必要的业务关系。

DBA 负责按迁移方案执行导入，记录批次、范围、结果和耗时。文档中的校验规则只是验收设计，不能据此认定字段映射、历史数据完整性或恢复能力已经验证。

### 2.6 容量、性能与维护验证

容量验证的主场景是第 10 年时最近 5 年的滚动数据量。如果年度新增量波动较大，还要检查第 1～10 年各年度的滚动 5 年数据量并取最大值。验证范围还应包括大商户热点、数据和索引占用、跨分片查询、索引创建、表结构变更、备份恢复、迁移窗口和扩容窗口。

单项演练只能支持对应范围的结论。例如，单表索引维护演练只能说明特定数据规模和环境下的维护耗时，不能直接证明两个实例能够承接全部业务峰值；容量、路由、查询性能、迁移和恢复仍需分别验证。

## 3 已确认规则

- 以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。
- 采用 2 个 MySQL 实例，每个实例 16 张消费记录表，共 32 个物理分片。
- 使用 `merchantNo` 作为分片键，并按 32 个分片计算 `shardIndex`。
- `shardIndex` 按每实例 16 张表映射到实例编号和表编号；实际库表名称以统一映射配置为准。
- 新表主键使用字符串类型的 `consumeId`，由雪花 ID 拼接固定两位分片编号生成。
- 历史迁移使用不变的 `serialNo` 关联新旧记录，不能直接比较旧表 `id` 和新表 `consumeId`。

## 4 待确认或待验证事项

- `merchantNo` 的规范化、哈希取模实现，以及 `shardIndex` 到实际库表名称的映射代码仍需核验。
- `consumeId` 生成器、主键后缀解析、固定长度和写入路由的一致性仍需核验。
- 第 10 年最近 5 年滚动数据量、年度波动、大商户热点和两个实例的资源规格仍需结合实际数据与压测确认。
- 跨分片查询的排序、分页、总数统计和并发资源占用仍需验证。
- 历史迁移的字段映射、数量核对、异常恢复和 `serialNo` 关联结果仍需按验收计划验证。
- 索引维护、表结构变更、备份恢复和扩容窗口仍需通过演练确认。
