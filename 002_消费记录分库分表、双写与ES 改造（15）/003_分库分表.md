# 003_分库分表

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。技术栈包括 Java 8、Spring Boot 2.7.18、MySQL 8.0.33 和 Elasticsearch 服务端 7.17.15。

## 1 面试口述精炼版本

**先确定实例和分表规模**

项目使用 ShardingSphere-JDBC 对消费记录进行分库分表，最终采用 2 个 MySQL 实例，每个实例部署 16 张消费记录表，共 32 个物理分片。容量评估以上一年度年新增 7,300 万条为基准，重点校验第 10 年时最近 5 年的滚动数据量；具体的容量和维护效果仍需通过演练确认，详见[容量与维护验证](#25-容量与维护验证)。

**再用商户号确定分片**

分片键选用商户号 `merchantNo`。每笔消费记录都归属于一个商户，新增时可以取得商户号，且同一商户始终路由到同一个分片。对 `merchantNo` 做哈希取模得到 `shardIndex`，再根据这个编号确定目标实例和物理表；没有可用分片定位条件的跨商户查询，可能需要访问多个分片。

**用统一规则把分片编号映射到库表**

`shardIndex` 的范围是 `0～31`。按每个实例 16 张表计算，实例编号为 `shardIndex / 16`，表编号为 `shardIndex % 16`，最后通过项目统一的库表名称映射定位实际库表。新增、更新和按商户查询使用 `merchantNo` 路由，按主键回查时解析 `consumeId` 末尾的两位分片编号；两种入口必须得到同一个分片。

**让主键携带分片信息**

新表主键使用字符串类型的 `consumeId`，由雪花 ID 拼接固定 2 位 `shardIndex` 组成。记录首次写入时生成一次，后续更新和 Canal 重放继续使用同一个值。主键回查先解析末尾分片编号，再定位目标库表；生成、解析和路由规则仍需结合实际代码验证，详见[数据模型](<./999_数据模型.md>)。

**用不变的业务流水号校验历史迁移**

历史迁移会在新表重建主键，因此不能直接比较旧表 `id` 和新表 `consumeId`。DBA 应使用迁移前后不变且全局唯一的交易流水号 `serialNo` 对应同一笔记录，再按验收范围比较字段，详见[历史迁移与数据库验收](<./999_历史迁移与数据库验收.md>)。

## 2 详细方案

### 2.1 实例、分库和分表规模

项目将消费记录拆分为 2 个库，每个库 16 张表，共 32 个物理分片；2 个库分别部署在 2 个有独立资源的 MySQL 实例上。分表的目标是降低单表数据、索引和维护任务的规模，分实例的目标是分散读写、索引维护和后台查询对单个实例的资源占用。

容量选型不能只看平均记录数。当前以上一年度年新增 7,300 万条作为预测基准，结合增长率评估第 10 年时最近 5 年的滚动数据量；还要关注大商户集中导致的热点，以及查询、索引维护、备份恢复和迁移窗口。2 个实例、每实例 16 张表是当前已确认的设计，是否满足目标负载仍需用实际数据和演练验证。

### 2.2 分片键和分片编号

分片键使用 `merchantNo`。每笔消费记录归属于一个商户，创建记录时可以取得该字段，且商户号在交易生命周期内保持不变，因此可以用它在新增、更新和按商户查询时定位分片。

对规范化后的 `merchantNo` 做哈希取模，得到扁平分片编号：

```text
shardIndex = hash(merchantNo) mod 32
```

`shardIndex` 的范围为 `0～31`。哈希取模能够把商户分散到 32 个分片，但不保证数据量和负载完全均匀；同一商户不会被拆散，大商户仍可能形成热点。

### 2.3 从分片编号定位实例和物理表

每个实例承载 16 张表，先用整数除法和取余得到逻辑实例、逻辑表编号：

```text
实例编号 = shardIndex / 16    // 整数除法，结果为 0 或 1
表编号   = shardIndex % 16    // 余数范围为 0～15
```

例如：

```text
shardIndex = 7  → 实例 0、表 7
shardIndex = 23 → 实例 1、表 7
```

逻辑编号还要经过项目统一的库表名称映射，才能得到实际数据库和物理表名。映射规则必须在新增、更新、查询和迁移工具中保持一致；当前映射生成、解析及与生产配置的一致性仍需结合实际路由代码验证。

如果查询条件既没有 `merchantNo`，也没有其他能够推导目标分片的信息，ShardingSphere-JDBC 可能需要把请求路由到多个分片，再由上层合并结果。跨分片查询的排序、分页和总数统计成本需要单独评估，后台列表因此由 ES 承接，相关原因见[001_改造原因](<./001_改造原因.md>)。

### 2.4 主键生成和按主键回查

新表使用字符串类型的 `consumeId` 作为主键。其设计是雪花 ID 加固定 2 位十进制分片编号：

```text
consumeId = snowflakeId + twoDigit(shardIndex)
```

例如，分片编号 7 写成 `07`。主键生成时使用与分片路由相同的 `merchantNo` 和取模规则，保证主键末尾的分片编号与实际写入分片一致。记录首次创建时生成一次；后续更新、同步和 Canal 重放继续使用原值，不能重新计算后覆盖主键。

按主键回查时，先读取 `consumeId` 末尾固定两位，解析为 `shardIndex`，再使用 2.3 的同一映射定位实例和表。只有主键后缀、`merchantNo` 计算结果和库表映射相互一致，才能继续查询目标分片。生成器、后缀解析、字段长度和路由代码仍需结合实际实现验证；相关主键拆解见[消费记录主键：雪花算法 + 基因法实现方案](<./999_消费记录主键_雪花算法与基因法实现方案.md>)。

### 2.5 历史迁移后的记录对应和数据校验

历史迁移会在新表生成新的 `consumeId`，旧表 `id` 与新表主键不直接相等。迁移校验应使用迁移前后保持不变且全局唯一的 `serialNo` 关联旧记录和新记录，再按验收清单比较字段、记录数量和必要的业务关系。

DBA 负责按已确认的迁移路由执行导入和记录批次、范围、结果及耗时；文档中的校验规则不等同于迁移已经完成，也不能仅凭文档记载认定字段映射、历史数据完整性或恢复能力已经验证。具体验收边界见[历史迁移与数据库验收](<./999_历史迁移与数据库验收.md>)。

### 2.6 容量与维护验证

容量验证应覆盖第 10 年时最近 5 年的滚动数据量；如果年度新增量波动较大，还要检查第 1～10 年各年度滚动 5 年数据量并取最大值。除总量外，还要覆盖大商户热点、数据和索引占用、跨分片查询、索引创建、表结构变更、备份恢复和迁移窗口。

演练结果应分别说明它能证明什么、不能证明什么。例如，单表索引维护演练只能说明特定数据规模和环境下的维护耗时，不能直接证明 2 个实例能够承接所有业务峰值；容量、路由、查询性能和迁移恢复仍需分别验证。具体选型依据见[为什么选择 2 个库、每库 16 张表？](<./999_为什么选择 2 个库、每库 16 张表？.md>)和[索引维护演练](<./999_如何演练，确认单表索引维护能否满足维护窗口？.md>)。

## 3 已确认规则

- 以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。
- 采用 2 个 MySQL 实例，每个实例 16 张消费记录表，共 32 个物理分片。
- 使用 `merchantNo` 作为分片键，并按 32 个分片计算 `shardIndex`。
- `shardIndex` 按每实例 16 张表映射到实例编号和表编号；实际库表名称仍以统一映射配置为准。
- 新表主键使用字符串类型的 `consumeId`，由雪花 ID 拼接固定 2 位分片编号生成。
- 历史迁移使用不变的 `serialNo` 关联新旧记录，不能直接比较旧表 `id` 和新表 `consumeId`。

## 4 待确认或待验证事项

- `merchantNo` 的规范化、哈希取模实现，以及 `shardIndex` 到实际库表名称的映射代码仍需核验。
- `consumeId` 生成器、主键后缀解析、固定长度和写入路由的一致性仍需核验。
- 第 10 年最近 5 年滚动数据量、年度波动、大商户热点和 2 个实例的资源规格仍需结合实际数据与压测确认。
- 跨分片查询的排序、分页、总数统计和并发资源占用仍需验证。
- 历史迁移的字段映射、数量核对、异常恢复和 `serialNo` 关联结果仍需按验收计划验证。
- 索引维护、表结构变更、备份恢复和扩容窗口仍需通过演练确认。
