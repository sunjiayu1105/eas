# 006_04 消息版本、来源顺序与事件身份

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 已确认规则

4. **业务版本与并发消费**：采用 `CONCURRENTLY` 并发消费；仅新分库分表的消费表增加业务 `version`，旧表不增加。历史导入初始化为 `1`，后续更新在同一条 SQL 中修改业务字段并执行 `version = version + 1`；导入重跑不重置已有版本，MQ 重试沿用消息中的版本与数据。以上是已确认、待实现验证的设计决策。

5. **自然月索引（已确认设计，待实现验证）**：新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；`records-read` 只用于跨月查询。按自然月分索引，不使用 rollover；所属自然月结束后满 180 天进入 cold。删除事件须携带删除前的创建时间，索引模板统一 Mapping、配置和读别名；首次 Index 写入自动建索引以配置和权限允许为前提。新增、更新调用 Index API，删除调用 Delete API，业务版本在同一物理索引、同一 `_id` 范围内比较。

6. **消费确认、重试与校验**：不同消息并发处理，每次回调内逐条同步调用 ES；操作或必要状态保存异常时，中断当前消息并向外抛出运行时异常，由 RocketMQ 重投整条原消息。消息内全部事件处理及必要状态保存完成后，监听方法才能正常返回。自动校验任务每小时执行一次，发现差异后按数据库当前状态补偿；任务失败或延迟须告警。具体重试次数、退避、死信和恢复仍待核验。

7. **文章对照与验证边界**：吸收、差异和适配结论统一维护在“项目方案与参考文章方案的差异”一节；消息数据契约、索引设计与定位、旧写保护、幂等和失败恢复分别设题，避免把不同层次的知识点混在一起。区分文章设计思路、示例代码实际行为和项目待实现要求。文章使用 ES 8.4.2，却未使用 `if_seq_no`、`if_primary_term` 或 `version_type=external`；`response.version()` 是 ES 内部版本，不是业务 `version`。候选配置、伪代码及验收步骤不代表已部署、联调或完成故障演练。

8. **内容组织与同步维护**：本文集中维护九个待确认问题，按“总链路与选型→消息消费→消息数据契约→索引设计→物理索引定位→旧写保护→幂等→失败恢复”的知识依赖递进。索引创建与索引定位、旧写保护与幂等、失败处理与消费确认分别说明。回答先给结论，再说明原因、适用前提与验证边界；同步维护面试口述版本、规则记录和受影响引用。

## 面试口述精炼版本

4. **消息契约**：新表携带业务 `version`，消息保留原始 `create_time`、删除前镜像和必要来源顺序信息；重试和拆分不能改变这些值，需要事件级去重时再采用稳定来源信息生成的 `eventId`。

## 参考文章与项目方案对比

#### 一条消息需要携带哪些业务版本、来源顺序和事件身份？参考文章与项目的要求有什么差异？

**当前结论**：消息至少要能识别业务记录、判断变更新旧、定位目标物理索引，并在拆分、重试和恢复时保持这些数据稳定。文章主要传递业务数据和 `version`，没有明确稳定源事件身份；项目还要求保留原始 `create_time`、删除前镜像和必要来源顺序。

仅新分库分表的消费表增加业务 `version`，历史导入初始化为 `1`，后续更新在同一条 SQL 中修改业务字段并递增版本。Canal 将行数据中的业务版本传入 MQ，重试沿用原版本，ES 版本不再由 binlog 坐标编码生成。

需要事件级去重时，可采用“业务主键 + 来源版本”，或采用来源实例与 binlog 行坐标组成的稳定 `eventId`；事件拆分、重新分批和重试必须保持不变。RocketMQ 消息 ID、消息 `keys`、批次 ID 和分批下标不能替代稳定来源信息。同一版本必须始终对应同一操作和同一内容；删除版本生成、业务键复用和删除后重建的版本衔接仍待实现验证。
