# 045_ES改造_ES_校验消息接收与任务持久化

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 主题边界

本文只说明 RocketMQ 消息如何进入校验任务，以及消息确认、延迟执行和故障恢复之间的边界。Binlog 入口选择见 [044](<./044_ES改造_ES_新表与 ES 增量校验方案选择.md>)；当前状态比较和差异修复见 [046](<./046_ES改造_ES_增量比较、差异处理与恢复.md>)。

## 2 面试口述精炼版本

增量校验消费者接收 RocketMQ 消息后，先提取 `consumeId`、来源数据库实例、实际物理数据库、实际物理表、操作类型和版本等定位信息。新增、更新事件创建可恢复的待校验任务；DELETE 事件均属于 MySQL 正常到期清理，只记录已按规则跳过的事件处理结果，不创建普通 ES 比较任务。当前消息对应的新增、更新任务及 DELETE 跳过记录可靠落库后，即可确认消息并由 RocketMQ 推进消费进度，不等待后续校验通过。校验任务单条独立执行和更新状态。落库失败不能确认，确认失败可能导致重放，当前允许重复创建任务并安全执行，暂不增加严格的事件去重。任务表保留自增主键 `task_id`；不设置独立的 `batch_id` 字段或校验批次表。

## 3 处理流程

```text
RocketMQ 投递变更消息
→ 校验消费者解析事件并固定定位信息
→ 保存消息来源标识、对应校验任务或 DELETE 跳过记录
→ 对应记录落库成功后确认当前消息，RocketMQ 推进消费进度
→ 后台按计划独立调度每条校验任务
→ 读取 MySQL 新表和 ES 当前状态
```

校验消费者与 ES 写入消费者使用不同 consumer group，分别维护消费位点；一个组的消费成功不能代替另一个组的校验完成。消息事件只用于定位和触发任务，不能直接当作最终比较快照。

如果一次消费回调接收多条消息，按整次回调返回成功的方式处理时，须确保本次消息对应的任务或跳过记录全部可靠落库后再返回成功；不等待后续比较、补偿或复核完成。可靠落库指数据库事务已经提交；一条消息包含多个事件时，须保证对应记录全部可靠保存。该要求由消费处理和数据库事务实现，不依赖独立的校验批次。

## 4 任务字段

任务表只维护完成调度、校验和恢复所需的核心字段：

- `task_id`：自增主键，用于唯一标识任务记录；
- `consumeId`：需要校验的业务记录标识；
- `source_instance`：来源 MySQL 数据库实例，用于确定查询的实例；
- `database`：事件实际来源的物理数据库，用于确定新表所在分片；
- `table`：事件实际来源的物理表，用于确定新表所在分片；
- `operation_type`：新增、更新或到期删除事件类型，用于选择任务处理分支；
- `version`：事件对应的业务版本，具体是否能从事件中可靠取得仍待验证；
- `status`：任务状态；
- `planned_execute_time`：计划执行时间；
- `retry_count`：重试次数；
- `failure_reason`：校验失败原因。

`task_id` 标识单条任务，来源实例、物理库、物理表和 `consumeId` 用于定位业务记录。后台根据任务状态和计划执行时间调度未完成任务，不维护独立批次的完成状态。DELETE 只可靠保存跳过处理结果，可复用已有事件处理记录，不为它新增专用任务表。

### 4.1 重复任务的处理选择

当前允许重复创建校验任务，暂不增加独立事件 ID、去重表或批次表。比较只读取 MySQL 新表和 ES 当前状态，并保存各自的任务结果；重复主要增加任务存储和查询开销，不执行扣款、计数累加等业务修改。补偿的版本约束见 [046 的补偿与复核](<./046_ES改造_ES_增量比较、差异处理与恢复.md#5-补偿与复核>)。这是已确认的设计选择，重复处理的安全性和容量仍待运行验证。

**消息重新交付示例：** 收到 M001 后创建任务 101，数据库事务已经提交，但消费者在消费进度可靠提交前退出。恢复或重新分配后，M001 可能再次交付，此时允许创建任务 102。两条任务独立查询当前状态并保存结果。这是重复消费，不一定是进入重试队列的消费失败重试。上游重新读取、分批并发布同一次变更，也可能产生新的消息和重复任务。

**字段边界：** `consume_id`（代码中映射为 `consumeId`）只能标识记录，不能区分后续更新；Canal 批次 ID 和 GTID 不能单独标识每条行变更；RocketMQ 消息 ID 不能覆盖上游重新发布的所有重复场景。来源库表、业务主键、操作类型与版本的组合只能作为未来去重候选，须先验证主键不复用、版本不重置以及同版本同操作同内容。本轮不据此建立唯一约束。依据见 [消息格式与字段边界](<./018_ES改造_Canal Server_消息格式与字段边界.md>) 和 [消息字段与事件身份](<./032_ES改造_ES_消息字段与事件身份.md>)。

DELETE 仍只保存跳过结果；允许重复记录时，不能把记录条数当作唯一删除事件数。若以后重复量影响容量，再根据实测评估去重，不以新增身份字段作为当前任务入口的前置条件。

## 5 持久化与失败边界

- 任务落库失败：不确认 RocketMQ 消息，保留重投机会。
- 消息确认失败：可能再次收到相同消息，允许重复保存任务并独立执行；不得仅按业务主键过滤后续合法更新。
- DELETE 事件：记录已按正常到期清理规则跳过的原因和事件处理结果，不创建普通 ES 比较任务，不查询 ES，也不调用 ES Delete API。
- 进程在消费进度可靠提交前退出：消息可能重新交付；若此前已经落库，则允许产生重复任务，不能将未保存的记录跳过。
- 进程在确认后退出：必须依赖已落库任务继续执行，不能只依赖消费位点重新发现变更。
- 任务执行失败：保留未完成状态，不把异常读取当成数据一致。

## 6 同步与异步的边界

同步方式在消费回调内读取两端并比较，回调失败时依赖消息重投，但会受 ES 刷新延迟、回调耗时和重复执行影响。本文采用异步方式，把消息接收和两端比较分开；异步并不自动解决重复任务、任务表一致性或恢复问题，这些仍需实现验证。

## 7 待确认或待验证事项

- 消息重新交付、上游重放及重复建任务场景下，是否验证了处理安全性和容量开销？
- 任务落库与 RocketMQ 确认之间如何实现可恢复的一致性？
- 首次等待、复核间隔和调度批量是否满足容量与延迟要求？
