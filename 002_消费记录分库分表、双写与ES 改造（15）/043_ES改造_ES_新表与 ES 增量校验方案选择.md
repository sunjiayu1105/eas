# 043_ES改造_ES_新表与 ES 增量校验方案选择

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

> 本文档是主文档“046_ES改造_ES_新表与 ES 增量校验”的拆分考点。本文件维护本考点的口述内容、详细方案和待确认事项；其他校验流程及异议分析见主文档。

## 1 已确认规则

- 本文讨论新表与 ES 的增量校验方案，采用按已提交 Binlog 定位变更、再回查两端当前状态的设计；按更新时间扫描仅作为对比方案。
- 面试口述版本说明选定方案时，同时说明未选择另一方案的直接原因及其成立条件；这是一项表达要求，不代表相关实现或运行效果已经验证。
- 方案选择不代表 Binlog 采集、批次持久化、差异补偿或故障恢复已经实现或验证。
- 校验独立于 ES 同步消费者组，消费确认不等于两端比较通过；范围外历史差异和额外 ES 文档不在本方案的自动发现承诺内。

## 2 面试口述精炼版本

针对新表与 ES 的增量校验，本文选择按已提交 Binlog 定位需要检查的记录，再回查 MySQL 和 ES 的当前状态。没有选择按 `update_time` 扫描，是因为事务可能先修改时间但延迟提交，提交后更新时间又可能早于新的扫描起点，从而漏查；同时也避免要求所有写入路径都维护该字段。Binlog 仍依赖日志连续、过滤正确、事务完整和进度可靠，这些条件待验证。

## 3 详细方案

### 3.1 两种方案对比

| 对比项 | 方案一：Binlog 定位，再回查 MySQL | 方案二：按更新时间扫描 MySQL |
|---|---|---|
| 对象来源 | 从新库已提交的行日志提取变化记录 | 查询固定时间窗口内新增或更新的记录 |
| 数据比较 | 回查 MySQL，与 ES 当前文档比较 | 读取 MySQL，与 ES 当前文档比较 |
| 进度管理 | 独立日志位点、完整事务范围和校验结果 | 每个分片的时间窗口、分页游标和校验结果 |
| 主要优势 | 不依赖业务更新时间字段，按日志覆盖已提交变更 | 减少独立日志采集、事务解析及位点衔接 |
| 主要条件 | 日志连续可读，批次与进度可靠保存 | 所有新增、更新维护更新时间，查询索引及延迟边界可靠 |
| 主要风险 | 日志过期、采集遗漏、位点丢失 | 时间字段漏维护、时间偏差或事务延迟提交导致漏查 |
| 并发更新 | 版本比较、延后复核 | 同样需要版本比较、延后复核 |

Binlog 决定“哪些记录需要检查”，不能直接把事件快照当成当前状态。时间窗口扫描也不是仅设置 `update_time <= 当前时间 - 延迟窗口`；只有上界会反复读取历史数据，还必须有可靠下界和分页进度。

现有分工依据见 [012_Canal 同步与增量校验如何分工](<./012_Canal 同步与增量校验如何分工.md>)：ES 同步消费者组与增量校验消费者组复用同一 Topic，但不能使用同一个 consumer group 竞争消费；校验独立于同步，读取两端当前数据，消费确认不代表比较通过。两种增量入口都不会自动发现范围外的历史差异或从未涉及的额外 ES 文档，不能仅凭追平宣称整个索引完全一致。

### 3.2 为什么选择 Binlog 方案

**选择方案一：Binlog 定位，再回查 MySQL。** 当前项目已经围绕导入前基线、完整事务批次和独立校验进度组织历史与增量覆盖。沿用这一设计，可以把“哪些提交过的变更需要检查”和“检查完成到哪里”对应起来；具体实现仍须验证。

**不依赖更新时间维护。** 只要相关写入产生可读取的 ROW binlog，就能从已提交变更中收集对象。更新时间扫描则要求业务修改、修复脚本等所有路径均维护该字段，目前这些条件没有验证。Binlog 并非天然无遗漏，过滤配置、日志连续性及可靠进度同样必须核验。

**避免时间窗口的晚提交缺口。** 按更新时间扫描通常同时设置开始时间和结束时间，例如查询 `update_time > 上次扫描时间 AND update_time <= 当前时间 - 延迟窗口`。示例取延迟窗口为五分钟：事务在 10:00 修改记录并设置 `update_time=10:00`，但直到 10:08 才提交；扫描任务在 10:06 执行时，结束时间是 10:01，这条未提交记录不可见。如果任务随后把 10:01 作为新的开始时间，记录在 10:08 提交后仍带着 10:00 的更新时间，后续窗口就可能跳过它。示例中的延迟窗口和有限重叠只能覆盖有界的提交延迟，不能无条件保证不漏。Binlog 按事务提交后的变更收集对象，不以业务更新时间作为检查边界。

**接受独立采集和恢复的成本。** 方案一需要维护每个来源实例的订阅、事务范围、待校验批次及可靠进度。所需日志过期、过滤错误或位点丢失仍会破坏覆盖能力，不能用“使用了 Binlog”替代恢复验证。方案二在更新时间契约、事务延迟边界及历史衔接可靠时仍可采用，本项目此次不选择它，并非认定它不可行。

**有可借鉴的实践，但不能替代项目验证。** [小红书 MySQL 数据一致性校验能力探索与实践](https://dbaplus.cn/news-11-6399-1.html) 的 3.4 节采用源端 Binlog 驱动、按主键定位、延迟点查及复查两端当前数据；文章同时讨论分库分表与数据分布差异。它支持本方案的校验思路，但没有明确证明目标端是 ES，不能视为本项目完整案例。

[JavaGuide：MySQL 数据同步到 Elasticsearch](https://javaguide.cn/database/mysql/mysql-to-elasticsearch-sync.html) 的“定期对账，并保留重建能力”说明按业务分区或主键范围定位差异、比较约定字段或规范化摘要、交修复任务重建文档。它支持 MySQL—ES 对账与独立修复，不证明固定等待窗口即可消除并发或漏查。本文结合两篇参考与项目规则形成设计，未照搬文章的删除和写入方式。
