# <font style="color:rgb(0, 0, 0);">1. 功能描述</font>
<font style="color:rgb(0, 0, 0);">“消费业务”模块，通过 ShardingSphere-JDBC 框架， 以商户ID Hash的方式对“消费记录”表进行分库分表，并通过雪花算法生成分布式ID， 以及通过基因法将商户ID和主键ID进行关联映射，解决MySQL海量数据下的存储和业务维度查询问题。</font>

# <font style="color:rgb(0, 0, 0);">2. 面试回答</font>
## <font style="color:rgb(0, 0, 0);">2.1. 单库单表存在的问题</font>
<font style="color:rgb(0, 0, 0);">在消费业务模块中，消费记录表承载 APP 内消费、扫码付、闪付、快捷支付、撤销、退货等交易数据。</font>

<font style="color:rgb(0, 0, 0);">我们按照日均新增 20 万条记录，保留 5 年的数据来做容量评估，如果继续放在 MySQL 单表里，写入和查询都会越来越慢。</font>

## <font style="color:rgb(0, 0, 0);">2.2. 分库分表方案</font>
<font style="color:rgb(0, 0, 0);">所以我基于 ShardingSphere-JDBC 对消费记录表做了分库分表，设计为2个库，每个库16张表，一共32个物理分片。</font>

<font style="color:rgb(0, 0, 0);">分片键选 merchantId，因为大多数查询场景都是以商户为维度查询的，比如对账清算、统计报表等。</font>

<font style="color:rgb(0, 0, 0);">分片策略采用 merchantId Hash 取模，这样就可以把单表数据量控制在比较健康的范围内。</font>

<font style="color:rgb(0, 0, 0);">主键方面，我没有使用 MySQL 自增 ID，而是采用“雪花算法 + 基因法”。先通过雪花算法生成 snowflakeId，再通过商户id计算出shardindex，把 shardIndex 固定两位拼接到 snowflakeId 末尾，比如 snowflakeId 后面拼接 07，表示这条数据落在第 7 个分片。这样主键既全局唯一，又能通过 ID 末尾两位反推出分片位置，从而精确路由到分片，避免全库全表查询 。在订单回查、撤销/退货查询原订单这些场景下就能根据消费记录id 精确定位到具体的物理分片，而不用上送分片键了。</font>
