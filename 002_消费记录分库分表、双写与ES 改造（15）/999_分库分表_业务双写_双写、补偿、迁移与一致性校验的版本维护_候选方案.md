## 1 面试口述精炼版本

**同步与业务写入分开，职责更简单**

旧表主写期间，先修改旧表并提交，再把完整数据和版本同步到新表。切写后，新表使用独立的业务代码，负责业务校验、数据修改和版本递增。同步逻辑与新表主写逻辑不要求使用同一份代码，两套逻辑可以提前部署，通过开关或路由选择。详见[总体流程](#21-总体流程同步逻辑与新表业务逻辑分开)。

**主写表产生版本，新表比较后保存**

修改记录时，先读取当前主写表的版本，再生成“原版本加 1”的目标版本，业务数据和版本一起保存。旧表主写时，新表接收旧表已提交的数据和版本：缺失就插入，版本较低就更新，已有更高版本就跳过；同版本还要核对内容。这样新表已经是“成功、版本 2”时，迟到的“异常、版本 1”不会覆盖它。详见[旧表方法](#22-写入旧表方法提交成功后返回数据和版本)、[新表方法](#23-新表同步方法比较并保存旧表版本)。

**四个功能分工，补齐遗漏并处理乱序**

双写传递本次提交结果；失败重试沿用原快照和版本；历史迁移分批读取旧表；一致性校验重新读取两边当前数据，补缺失、修差异、清理多余记录。重试和迁移都不额外增加版本。漏发 MQ 的记录由完整校验兜底，因此保证最终一致还依赖扫描覆盖完整、失败重试和修复成功。详见[双写](#24-双写旧表提交后同步新表)、[重试](#25-双写重试重放原数据和原版本)、[迁移](#26-历史迁移比较快照版本再保存进度)、[校验](#27-一致性校验按差异类型修复新表)。

**切写先交接，切后以新表为准**

切写前处理旧表在途写入和积压任务，确认新表追平，再停止旧方向修复。切写后，新表独立处理业务，通过版本条件更新，在同一事务内修改数据并递增版本。此时新表失败属于业务失败，不能按双写补偿成功返回，也不再要求停止更新的旧表继续追平。详见[切写与交接](#28-新表主写切换交接与事务边界)。

## 2 详细方案

### 2.1 总体流程：同步逻辑与新表业务逻辑分开

**先明确前提**

- 开启双写前，旧表新增 version，存量初始化为 1，所有修改入口维护版本。
- 新表从空表开始，先双写，再迁移。旧表主写期间，两边追平后数据和 version 一致。
- 新旧表各只有一个 version；新增为 1，业务修改生成下一版本，同步沿用已提交版本。
- 新表通过 merchantNo + serialNo 定位：merchantNo 路由到分表，serialNo 匹配记录。serialNo 全局唯一、有唯一索引，删除后不复用。
- 项目使用物理删除。下图说明新增、修改的主流程，删除清理见 2.7。

**职责划分：旧表产生版本，新表接收版本**

旧表业务代码负责读取、业务校验、版本递增、条件更新和提交，提交成功后提供完整快照。快照包括业务标识、路由信息、全部同步字段及对应版本，不能拼接不同时间的数据与版本。

新表同步方法 syncNewRecord 接收旧表已提交的完整快照，比较后插入或更新，保存来源版本，不额外加 1。双写、双写重试、历史迁移和校验补齐共用这套规则；同版本错误内容由校验受保护地修复。

切写后，新表业务代码独立校验业务、修改数据并递增 version，不再接收旧表版本。以下方法名仅用于说明职责，不代表已有实现。

~~~mermaid
flowchart TD
    A["业务请求"] --> B{"当前写入模式"}
    B -->|"双写：旧表主写"| C["旧表业务代码<br/>校验、修改数据、version 加 1"]
    C --> D{"旧表提交成功？"}
    D -->|"否"| E["处理业务失败或冲突"]
    D -->|"是"| F["已提交的完整快照"]
    F --> G["新表同步方法 syncNewRecord<br/>比较并保存来源版本"]
    G --> H["确认同步结果<br/>失败则补偿，差异由校验修正"]
    B -->|"切写后：新表主写"| I["独立的新表业务代码<br/>校验、修改数据、version 加 1"]
    I --> J["成功提交<br/>失败回滚或处理冲突"]
~~~

业务模式提前实现，切换前完成主写交接，不能仅靠开关广播就认为切换已经安全完成。双写开关开启时先旧后新，关闭并完成交接后进入新表主写，详见 2.8。

### 2.2 写入旧表方法：提交成功后返回数据和版本

**更新步骤：读取版本，带条件修改**

1. 在旧表事务内读取记录，保存读到的 version，记为 expected_version。
2. 校验业务状态，生成修改后的完整数据，计算 target_version=expected_version+1。
3. 使用 expected_version 作为更新条件，同时保存业务数据和 target_version。
4. 在事务内取得修改后的完整快照，提交成功后返回；回滚或失败时不发送给新表。

~~~sql
-- 位于旧表业务事务中。实际查询和更新包含所需业务字段。
SELECT status, version FROM old_record WHERE serial_no = :serial_no;

-- expected_version 来自本次查询；target_version = expected_version + 1。
-- 实际 WHERE 还需包含合法业务状态条件。
UPDATE old_record
SET status = :new_status, version = :target_version
WHERE serial_no = :serial_no AND version = :expected_version;
~~~

**示例：并发修改时不覆盖其他操作**

1. 本次操作读到旧表 S1 的版本 3，准备写目标版本 4。
2. 另一个操作先完成更新，将旧表推进到版本 4。
3. 本次 UPDATE 的条件仍是 version=3，因此影响 0 行。
4. 本次操作重新读取并判断业务，不去掉版本条件强行覆盖，也不发送未提交的快照。

影响 0 行也可能是记录已删除或业务条件不满足，需要结合重新查询的结果判断。

### 2.3 新表同步方法：比较并保存旧表版本

**比较规则：缺失补插，更高版本更新**

按 merchantNo 路由、serialNo 定位后，新表缺失就插入；传入版本更高就更新全部同步字段和 version；更低就跳过。版本相同时，内容相同返回“已经完成”，内容不同返回冲突，不能无条件覆盖。写入方法不再额外执行 version+1。

~~~mermaid
flowchart TD
    A["完整数据和目标版本"] --> B["按 merchantNo + serialNo 定位"]
    B --> C{"新表记录存在？"}
    C -->|"否"| D["插入完整数据和目标版本"]
    D --> E{"插入结果"}
    E -->|"成功"| OK["返回写入成功"]
    E -->|"同一 serialNo 唯一键冲突"| B
    E -->|"其他错误"| FAIL["返回失败"]
    C -->|"是"| F{"比较版本"}
    F -->|"传入版本更高"| G["原子条件更新数据和版本"]
    G --> H{"更新结果"}
    H -->|"成功"| OK
    H -->|"影响 0 行"| B
    H -->|"数据库错误"| FAIL
    F -->|"传入版本更低"| OLD["返回已有更高版本"]
    F -->|"版本相同"| SAME{"内容相同？"}
    SAME -->|"是"| DONE["返回已经完成"]
    SAME -->|"否"| CONFLICT["返回同版本内容冲突"]
~~~

**落库要求：版本比较和更新原子执行**

~~~sql
-- 已按 merchantNo 路由；实际 SET 包含全部同步字段。
UPDATE new_record
SET status = :incoming_status, version = :incoming_version
WHERE serial_no = :serial_no AND version < :incoming_version;
~~~

影响 0 行、同一 serialNo 的插入唯一键冲突，都需要重新查询再判断；其他数据库错误按失败处理。重复尝试须有次数或超时限制。方法返回成功后，仍要确认所属事务提交成功。

“已有更高版本”可以结束过期同步事件，不能直接解释为本次业务请求成功。同版本同内容也不是通用的业务请求去重凭据。四个功能如何使用这些结果，分别见下文。

### 2.4 双写：旧表提交后同步新表

**处理顺序：先调用旧表方法，再调用新表方法**

writeOldRecord 成功提交后，将返回的完整快照交给 syncNewRecord。新表缺失就补插，版本较低就更新，版本较高则跳过；同版本核对内容。新表保存旧表传入版本，不单独加 1。

**示例：异常变为成功，两边保存版本 2**

1. 旧表 S1 为“异常、版本 1”，回查确认成功。
2. writeOldRecord 按 version=1 更新并提交“成功、版本 2”，返回完整快照。
3. 调用 syncNewRecord，通过 M1 + S1 定位新表。
4. 新表版本为 1，条件更新为“成功、版本 2”；若尚无记录，则插入版本 2。
5. 确认新表提交成功后，本次同步完成。

**失败处理：已提交的旧表不因新表失败而回滚**

新表失败时发送 MQ 补偿，发送失败也应重试和告警。同版本差异要修复或可靠登记到后续修复流程，不能当作已经一致；已有更高版本可结束本次过期同步事件。

**示例：消息没有进入队列，由校验补齐**

1. 旧表已提交“成功、版本 2”。
2. 进程在写新表、发送补偿消息之前崩溃。
3. MQ 没有这次消息，消费重试无法补齐。
4. 完整校验发现新表缺失或落后，读取旧表当前快照修复。

这类遗漏的恢复时间受校验周期影响，不能承诺实时一致。

### 2.5 双写重试：重放原数据和原版本

**输入与比较：使用失败时保留的已提交快照**

消费者不再修改旧表，也不重新生成版本。每次重试都查询新表当前状态：缺失或版本较低则写入原快照；已有更高版本则跳过；同版本同内容直接结束；同版本内容不同转入校验修正。

**示例：低版本补偿晚到，不能回退终态**

1. 旧表创建“异常、版本 1”，双写失败，版本 1 快照进入 MQ，新表无记录。
2. 回查确认成功，旧表提交“成功、版本 2”。
3. 版本 2 的双写先成功，在新表插入“成功、版本 2”。
4. 版本 1 补偿到达，发现 1 < 2，跳过并结束该事件。
5. 若版本 2 快照再次到达，版本和内容相同，不重复修改，新表仍是版本 2。

**完成条件：确认结果后再确认消息**

写入已提交、同版本同内容或已有更高版本时，才能结束本次同步事件。失败继续重试并告警；同版本差异须修复，或可靠登记为仍会继续处理的修复事项。这里是同步重试，不是新表主写阶段的业务请求重试。

### 2.6 历史迁移：比较快照版本，再保存进度

**输入与比较：固定范围内分批读取旧表**

开始扫描前获取最大 ID，分批读取完整数据和 version。范围可能包含已双写的记录，因此不能假设新表为空。新表缺失或版本较低则写入迁移快照；已有更高版本则跳过；同版本核对内容，存在差异进入修复。

完整快照可以跨版本补齐，例如从版本 1 更新为版本 3；“金额加 10”等增量指令不能按此规则跳过中间操作。

**示例：迁移快照被双写的新状态超过**

1. 迁移读到“异常、版本 1”，尚未写入。
2. 回查将旧表改为“成功、版本 2”，双写成功更新新表。
3. 迁移尝试写版本 1，条件更新影响 0 行。
4. 重查新表发现版本 2，跳过旧快照，保留成功状态。

**完成条件：本批处理完成后再推进游标**

失败不能被游标越过；同版本差异应修复或可靠登记待修复事项，登记不代表最终一致。恢复时若重新查询旧表，就使用本次查询的数据和版本。

**示例：数据写入成功，游标保存前崩溃**

1. 已保存游标为 100，本批读取 ID 101～200。
2. 本批已写入新表，但保存游标 200 前任务崩溃。
3. 恢复后从 101 重新读取旧表，再尝试写入。
4. 同版本同内容跳过；读取到更高版本则更新，落后于新表则跳过。
5. 本批全部处理完成后保存游标 200。

批次部分成功后整批重试也可能重复处理；从已完成游标之后恢复，不会重做此前已确认完成的批次。

### 2.7 一致性校验：按差异类型修复新表

**扫描范围：两边标识去重，再回查当前记录**

旧表主写期间，以旧表为准。分批扫描两边 serialNo，合并去重，保留 merchantNo 用于新表路由，再查询两边当前记录。必须覆盖新表扫描，才能发现旧表已删除、新表仍存在的记录。

**修复动作：区分缺失、版本差异和内容差异**

- 新表缺失或版本较低：读取旧表最新完整快照，调用 syncNewRecord 补齐。冲突或影响 0 行时重查，不强行覆盖。
- 版本和内容一致：通过；两边都不存在也无需修复。
- 同版本内容不同：重新读取旧表，在新表事务中锁定目标行，再次确认版本后修正内容，version 不增加。
- 新表版本更高：重查旧表主库，排除先后读取的时序差异；仍异常则调查，不直接降版本。
- 旧表无、新表有：重查旧表主库确认不存在后，删除新表多余记录。查询失败不能当成不存在。

**示例：同版本错误内容，在锁内修正**

1. 旧表为“成功、版本 3”，新表错误保存为“异常、版本 3”。
2. 校验重新读取旧表完整快照。
3. 按 merchantNo 路由，在新表事务内按 serialNo 用 SELECT ... FOR UPDATE 锁定记录。
4. 确认目标仍为版本 3，再修正为成功，版本保持 3。
5. 若目标已到更高版本，放弃旧快照；若缺失或版本较低，按对应分支处理。
6. 提交后重新校验，仍有差异继续处理。

这要求旧表同一个 version 对应确定内容；来源漏增版本，目标行锁无法判断来源数据新旧。

**示例：内容改回原值，也要接收更高版本**

以下仅假设某个可修改字段允许 A→B→A，不表示终态可以回退为异常。

1. 新表为“字段 A、版本 1”。
2. 旧表先改为“字段 B、版本 2”，再改为“字段 A、版本 3”。
3. 校验虽然看到该字段同为 A，仍按旧表完整快照将新表推进到版本 3。
4. 迟到的版本 2 被拒绝，新表保留 A 和版本 3。

**示例：物理删除后，旧快照重新插入**

1. 迁移读取 S1 快照后，业务物理删除旧表和新表中的 S1。
2. 迁移晚到，发现新表缺失，又插入旧快照。
3. 校验扫描新表发现 S1，重查旧表主库确认不存在。
4. 删除新表 S1 并复核；如果还有迟到写入，后续校验继续清理。

物理删除后没有行内 version 拦截旧快照，因此最后一次迟到写入后仍需完成清理。serialNo 不复用，重新出现的是已删除的旧记录。该项目方向和参考依据见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:176>)。

### 2.8 新表主写：切换交接与事务边界

**切换顺序：停止旧表新写入，追平后再交接**

先阻止新的旧表主写请求进入，等待在途事务结束，处理积压补偿、完成迁移和最终校验修复。确认新表追平后，停止旧表到新表的补偿、迁移和校验修正，协调所有实例进入新表单写，再放行业务写入。配置广播本身不能证明所有实例和任务已经完成交接。

这是候选方案需要满足的顺序约束；拦截入口、任务退出和实例确认机制仍待实现验证。总体切换及回滚方向见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:201>)。

**独立业务逻辑：校验业务，原子修改数据和版本**

1. 完成交接并关闭双写后，调用新表独立的业务方法。
2. 按 merchantNo + serialNo 读取记录和 version，校验业务状态。
3. 在新表事务内，按读取版本作为条件修改业务数据，并执行 version+1。
4. 成功则提交；版本冲突则重新读取并判断业务，其他失败回滚或按失败处理。

新增记录的 version 为 1，通过唯一索引识别插入冲突。修改请求发现记录不存在时按业务规则处理，不能擅自变成新增。这里维护的是新表自身业务版本，不调用旧表快照同步方法。

**示例：直接修改新表，不再同步旧表**

1. 切写交接完成，新表 S1 为“异常、版本 5”。
2. 回查确认成功，新表业务代码读取版本 5 并通过状态校验。
3. 按 version=5 条件更新，在同一次更新中保存成功状态并执行 version+1。
4. 提交后新表为“成功、版本 6”，旧表不再更新。
5. 若版本条件不满足，重新读取并判断，不能强行覆盖。

新表失败属于业务失败，不能沿用“旧表已成功”的补偿语义。提交结果不确定时的业务重试仍需结合业务规则处理，本文不展开通用请求去重设计。

### 2.9 最终一致性：版本防覆盖，重试和校验补遗漏

**示例：未删除记录最终追平**

1. 旧表 S1 最终停在“成功、版本 8”，不再修改。
2. 双写或补偿送达版本 8；即使漏发 MQ，完整校验也发现差异。
3. 新表缺失或落后时接收版本 8，同版本错误内容由校验修复。
4. 版本 1～7 再到达时被跳过，重复版本 8 不改变结果。
5. 复核后，两边数据和版本一致。

成立条件是所有修改入口正确维护版本，故障最终恢复，扫描覆盖完整，重试和修复最终成功。物理删除还依赖持续清理；误写得过高的目标版本需要调查和受控修正。持续业务写入期间允许暂时落后。

这些结论适用于旧表主写阶段。切写后旧表停止更新，不再要求两边持续相等，也不能继续用旧表修正新表。

### 2.10 ES 同版本修复：数据库一致不代表 ES 一致

**示例：新表修复成功，ES 仍拒绝相同版本**

1. 新表和 ES 都错误保存为“异常、版本 3”。
2. 校验将新表修正为“成功、版本 3”，不增加版本。
3. 如果 ES 只接受严格更大的版本，这次版本 3 修复就被拒绝。
4. 新旧表一致，但 ES 仍是异常状态。

需要单独设计受保护的 ES 修复方式，防止迟到的同版本错误数据再次覆盖修复结果；尚未完成设计及运行验证。

## 3 已确认规则

- 新旧表各维护一个 version；旧表主写期间追平后，两边数据和版本一致。
