本文整理统一 version 的候选机制，整套方案尚未确认采用，也未完成运行验证。完整新表业务链路如何在切写前后保持一致，仍是待设计问题。当前方案、删除处理及切换回滚由 [006](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:1>) 维护；本文不将局部设计写成已落地方案。

## 1 面试口述精炼版本

**先明确目标：最终一致，以及完整链路不变**

我们希望双写、失败重试、历史迁移和校验修正能够共同保证新旧表最终一致。同时，切写前后新表的参数组装、业务校验、版本处理、数据库写入和异常处理都使用同一套链路代码。当前只整理了版本比较和补偿等局部机制，完整链路如何统一还没有完成设计。详见[目标与设计状态](#21-改造目标与当前设计状态)。

**旧表产生版本，新表按版本接收数据**

在旧表主写阶段，每次修改旧表记录，都让业务数据和 version+1 一起成功或一起失败。同步时将完整数据和对应版本一起传给新表：没有记录就插入，版本落后就更新，已有更高版本就跳过。例如新表已经收到“成功、版本 2”，迁移的“异常、版本 1”晚到时就不会把它覆盖。详见[旧表版本维护](#22-旧表主写期间修改数据并递增版本)、[新表比较规则](#23-新表接收同步完整数据与版本一起保存)。

**失败重试补漏写，校验处理遗漏和差异**

双写失败后通过 MQ 重试，迁移任务分批补齐存量，两者都复用新表的比较规则。校验以旧表为准，检查缺失、版本和内容差异，以及新表多余记录。旧表提交后若进程在发送 MQ 前崩溃，就靠完整校验补齐；因此允许暂时落后，最终一致依赖重试和修复成功。详见[失败重试](#25-切写前补偿用原数据和原版本重试)、[校验修复](#27-旧表主写期间校验并修正新表)。

**切写还需要交接，不能只看版本大小**

切写前要处理旧表在途写入、积压补偿和旧方向校验任务，确认新表追平。新表接管后，旧表不再接收新变更，就不能继续拿旧表修正新表。共用一个底层写入方法还不能证明完整业务链路相同，这部分需要继续设计。详见[切写与设计缺口](#28-切写前后完整新表业务链路仍待统一)。

## 2 详细方案

本节示例只解释处理规则，不是生产记录或测试结果。S1 表示一条消费记录，M1 表示其商户；“内容相同”指全部需要同步的字段相同。状态变更以“异常（未确认）变为成功或失败”为背景，后文用成功举例。

### 2.1 改造目标与当前设计状态

**已确认目标：完整的新表业务写入链路保持一致**

切写前后的参数组装、业务校验、版本处理、数据库写入和异常处理，都应使用同一套新表链路代码。切写时改变业务请求路由，不能仅凭共用 writeNewRecord 或相同 SQL，就说完整链路已经一致。

**已有设计基础：版本比较与差异修复**

下文说明旧表主写期间，如何维护版本、同步数据、重试失败、迁移存量和校验差异。这些机制用于评估最终一致性，不代表完整新表业务链路已设计完成。该缺口集中放在 2.8，避免与已能说明的局部规则混在一起。

**执行前提：先准备版本，再双写、迁移**

1. 开启双写前，旧表新增 version，存量记录初始化为 1。
2. 所有旧表修改入口都维护 version，包括人工修数。
3. 新表从空表开始，先开启双写，再执行历史迁移。
4. 新旧表各只有一个 version；旧表主写期间，追平后两边业务数据和版本一致。
5. 项目使用物理删除；serialNo 全局唯一，删除后不复用。

以上是用户已确认的设计前提，不等同于已经实施。

### 2.2 旧表主写期间：修改数据并递增版本

**旧表更新规则：业务数据和版本一起修改**

旧表新增记录时 version=1。每次修改旧表记录数据，都在同一次原子更新中执行 version+1，让数据和版本一起成功或一起失败。

**并发条件：使用本次读到的旧表版本**

expected_version 是本次修改前读取的旧表 version，由应用作为参数传入。下面是 MySQL 8.0.33 核心示意；实际表名、字段及合法状态条件需按业务实现。

~~~sql
-- 读取旧表当前数据及版本，供业务判断和条件更新使用。
SELECT status, version
FROM old_record
WHERE serial_no = :serial_no;

-- :expected_version 取自上面的查询结果。
-- 实际 UPDATE 还需包含合法业务状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

**示例：旧表正常修改成功**

1. 应用读取 S1，得到“异常、版本 1”。
2. 回查确认成功，应用携带 expected_version=1 更新旧表。
3. 旧表仍为版本 1，更新成功，成为“成功、版本 2”。
4. 旧表事务提交后，这份完整数据和版本 2 才能同步给新表。

**示例：查询后，旧表被另一个操作修改**

1. 本次操作读到旧表版本 3。
2. 另一个写入先成功，将旧表更新到版本 4。
3. 本次 UPDATE 携带 expected_version=3，影响 0 行。
4. 应用重新查询旧表并做业务判断，不去掉版本条件强行覆盖。

影响 0 行也可能是记录已删除或业务条件不满足，必须结合查询结果处理。这里按可能存在并发修改设计。

### 2.3 新表接收同步：完整数据与版本一起保存

**适用范围：先说明同步落库，不等于完整业务链路**

下文的 writeNewRecord 是示意性的底层写入方法。双写、失败重试、迁移和校验补齐可以复用这些比较规则；它如何与切写后的正常业务组成同一套完整链路，仍见 2.8 的待设计问题。

**入参规则：同一份数据配同一个版本**

完整快照就是同一次读取取得的业务标识、路由信息、全部同步字段和 version，不能把不同时间读到的数据与版本拼起来。

**入参示例**

1. 旧表 S1 当前为“成功、版本 2”。
2. 本次读取同时取得 merchantNo=M1、serialNo=S1、全部同步字段和版本 2。
3. 调用方将这份完整快照传给 writeNewRecord。
4. 假设新表没有 S1，方法插入这份数据，保存 version=2。

**定位规则：按商户路由，按业务标识找记录**

merchantNo 用于定位新表的实际分表；serialNo 用于匹配同一笔消费记录。新表首次插入生成自己的 consumeId，后续更新保留它。

**定位示例**

1. 旧表记录为 merchantNo=M1、serialNo=S1、id=100。
2. 新表写入先按 M1 路由，再查询 S1。
3. S1 不存在时插入，生成新表 consumeId，例如 900。
4. 后续更新 S1 时仍修改 consumeId=900 的记录，不使用旧表 id=100 定位新表。

**版本职责：调用方提供版本，新表保存该版本**

同步落库方法接收旧表已提交的数据和 version，不再为同一次变更生成版本。

**职责示例**

1. 旧表已提交“成功、版本 2”。
2. 调用方将版本 2 的完整快照传给新表。
3. 新表保存“成功、版本 2”。
4. 本次同步不把新表版本额外加到 3。

**判断一：新表没有记录，插入完整快照**

1. 迁移读取旧表 S1 的“成功、版本 5”。
2. 新表没有 S1，直接插入完整数据和版本 5。
3. 若并发插入导致同一业务唯一键冲突，则重新读取新表。
4. 若另一任务已写入相同数据和版本 5，视为已同步；若已是版本 6，则保留版本 6。

其他约束错误或数据库故障仍按失败处理，不能都当成重复插入。

**判断二：传入版本更大，更新数据和版本**

1. 新表已有“异常、版本 1”。
2. 补偿传入旧表已提交的“成功、版本 3”完整快照。
3. 新表在同一次更新中保存全部同步字段，并将 version 设置为 3。
4. 更新完成后，新表为“成功、版本 3”。

能够跳过版本 2，是因为传入的是完整字段值。如果传入的只是“金额加 10”这样的操作指令，就不能套用这条规则跳过中间操作。

**判断三：传入版本更小，跳过旧数据**

1. 新表已是“成功、版本 3”。
2. 迁移的“异常、版本 1”快照晚到。
3. 比较发现 1 小于 3，跳过写入。
4. 新表仍为“成功、版本 3”。

**判断四：版本和内容都相同，作为重复处理**

1. 新表已保存 S1 的版本 3 完整数据。
2. MQ 再次投递相同的版本 3 快照。
3. 方法核对版本及全部同步字段，确认均相同。
4. 不再修改新表，version 仍为 3。

**判断五：版本相同但内容不同，报告差异并修复**

1. 旧表为“成功、版本 3”，新表错误保存为“异常、版本 3”。
2. 同步方法发现同版本差异，不无条件覆盖。
3. 校验任务重新读取旧表，并在新表事务内锁住目标记录。
4. 锁内重新确认新表仍为版本 3 时修正内容，版本保持 3。
5. 若新表已到更高版本，则放弃旧快照，保留新表当前状态。

这是旧表主写期间的修复示例，完整处理见[校验修复](#27-旧表主写期间校验并修正新表)。

**原子更新：比较与保存必须一起执行**

~~~sql
-- 已按 merchantNo 路由到实际分表。
-- 实际 SET 应包含全部同步字段，示例只展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

**并发示例**

1. 新表当前为版本 1，迁移准备写版本 2。
2. 迁移写入前，双写先把新表更新为版本 3。
3. 迁移执行 version < 2 的条件更新，影响 0 行。
4. 迁移重新读取，发现新表已有版本 3，跳过旧快照。

影响 0 行不能一律视为成功：目标缺失要尝试插入，版本相同要核对内容。判断后无条件更新，会留下旧快照覆盖新数据的窗口。

**版本推进：业务字段相同，也要接收更高版本**

下面假设某个允许修正的业务字段能够从 A 改成 B，再改回 A，仅用于说明排序规则，不表示成功或失败可以回退为异常。

1. 新旧表最初都为“字段 A、版本 1”。
2. 旧表把该字段改成 B，版本增至 2。
3. 旧表又把该字段改回 A，版本增至 3。
4. 版本 3 先到新表，即使该业务字段仍为 A，也要保存版本 3，并同步其他字段。
5. 版本 2 随后到达时被拒绝，新表保留字段 A 和版本 3。

### 2.4 切写前双写：旧表提交后再同步新表

**处理顺序：先取得本次快照，再提交旧表、写新表**

1. 在旧表业务事务内修改数据和 version。
2. 在该事务内取得修改后的完整快照，保证数据与版本对应。
3. 提交旧表事务；回滚时不发送本次快照。
4. 提交成功后调用新表写入方法；失败时发送 MQ 补偿消息。

**遗漏示例：旧表提交后，进程在发送 MQ 前崩溃**

1. 旧表已提交“成功、版本 2”。
2. 新表尚未写入，进程也没有来得及发送 MQ。
3. 进程崩溃，因此 MQ 中没有这次消息。
4. 后续完整校验发现新表缺失或落后，读取旧表当前快照并补齐。

发送 MQ 失败也应重试、告警。未进入队列的遗漏依赖完整校验兜底，恢复时间受校验周期影响，不能承诺实时一致。

### 2.5 切写前补偿：用原数据和原版本重试

**重试原则：复制旧表已提交的结果**

MQ 消费者使用原数据和原 version，调用 2.3 的写入规则，不修改旧表，也不因重试递增版本。

**示例：低版本补偿晚于终态到达**

1. 旧表创建“异常、版本 1”，写新表失败，补偿消息进入 MQ，新表无记录。
2. 回查确认成功，旧表提交“成功、版本 2”。
3. 版本 2 的双写先成功，在新表插入“成功、版本 2”。
4. 版本 1 的补偿到达，比较后跳过，新表保留成功。
5. 若版本 2 也被重复投递，版本和内容相同，直接结束。

**完成条件：结果可确认，任务才能结束**

新表写入已提交、目标已是同版本同内容，或者已有更高版本，才可确认同步事件处理完成。同版本差异需要修复，或可靠登记为可继续处理的修复任务。持续失败要重试和告警，不能只打印日志就丢弃。

本节仅适用于旧表已提交结果的同步重试；不能直接套用为切写后正常业务请求的重试策略。

### 2.6 切写前迁移：写入新表后再保存进度

**迁移顺序：固定范围，分批读取，成功后记游标**

开始扫描前确定本次最大 ID，分批读取旧表完整数据及 version，再调用 2.3 的写入规则。只有本批全部处理完成，才能保存完成游标。恢复时若重新查询旧表，就使用本次查询结果。

**示例：数据已写入，但进度还没有保存**

1. 持久化游标为 100，当前批次读取 ID 101～200。
2. 这批数据已写入新表。
3. 任务在保存游标 200 前崩溃，游标仍为 100。
4. 恢复后从 101 重新查询旧表，再次尝试写入。
5. 新表按版本及内容识别重复，不会重复创建业务记录，也不会让旧版本覆盖新版本。

批次部分成功后整批重试也可能重复处理；从已确认完成游标之后恢复，则不会重做之前已完成的批次。同版本差异应先修复或可靠登记待修复任务，其他失败不能被游标越过。

### 2.7 旧表主写期间：校验并修正新表

**校验对象：两边的存在性、版本和全部同步字段**

分批扫描两边的 serialNo，合并去重后回查当前记录。必须扫描新表，才能发现旧表已删除而新表仍存在的记录。

- 新表缺失或版本落后：读取旧表最新完整快照，调用写入方法补齐。
- 版本和内容相同：通过。
- 同版本内容不同：按下面的并发保护流程修复。
- 新表版本更高：重查旧表主库，先排除查询时序差异；仍异常则调查版本维护和写入来源，不能直接降版本。
- 旧表无、新表有：重查旧表主库确认不存在后，删除新表多余记录。查询失败不能当成不存在。

**示例：修正同版本的错误内容**

1. 旧表是“成功、版本 3”，新表错误保存为“异常、版本 3”。
2. 校验重新从旧表读取完整快照。
3. 开启新表事务，使用 SELECT ... FOR UPDATE 锁定对应记录。
4. 锁内确认新表仍为版本 3，再修正内容，version 保持 3。
5. 若目标已是更高版本，放弃当前旧快照；缺失或版本更低则按 2.3 处理。
6. 提交后复核，失败时重新读取并重试。

此流程依赖旧表同一个 version 对应确定内容；若旧表修改数据却漏增版本，目标行锁无法替来源判断新旧。

**示例：删除后，迁移旧快照又插入新表**

1. 迁移读取 S1 快照，尚未写入新表。
2. 业务物理删除旧表和新表中的 S1。
3. 迁移晚到，发现新表没有 S1，再次插入旧快照。
4. 校验扫描新表发现 S1，重查旧表主库，确认 S1 不存在。
5. 校验删除新表 S1 并复核；若仍有迟到任务再次插入，后续校验继续清理。

serialNo 删除后不复用，步骤 3 是旧数据重新出现，不是创建了另一笔同编号业务。删除最终一致要求最后一次迟到写入后仍完成清理。以上为项目确认的方向，依据与边界见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

### 2.8 切写前后：完整新表业务链路仍待统一

**先完成交接：旧表停止主写，旧方向任务退出**

新表承接主写前，要处理旧表在途写入、积压补偿，确认新表追平，并完成迁移及旧方向校验任务的退出或交接。不能让旧任务继续按旧表修改、删除新表数据。总体切换和回滚方向见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)；具体交接机制仍待验证。

**示例：共用底层方法，不等于完整链路一致**

1. 切写前，调用方取得旧表已提交的“成功、版本 2”。
2. 新表底层方法比较并保存这份数据和版本。
3. 切写后，原局部设计先读取并锁定新表，再做业务判断、生成下一版本。
4. 最后仍调用同一个底层方法，但前面的参数、判断和版本处理已经不同。
5. 因此，这个局部设计还没有满足用户要求的完整链路一致。

**待设计重点：同时满足链路一致、版本一致和并发安全**

需要把新表的参数组装、业务校验、版本处理、数据库写入和异常处理设计成同一套完整流程，并与旧表同步、历史迁移、重试和校验衔接。目前只统一了部分落库规则，不能写成切写时仅改路由就已具备全部能力。

原局部方案中的新表行锁、同事务写入，只能说明一种并发保护思路；是否保留以及如何接入完整链路，需在整体设计中确定。新增记录的版本初始化、唯一键冲突、业务失败回滚及提交结果不确定后的重试，也需要在该设计中闭合。

### 2.9 最终一致性：最新数据能送达，旧数据不能覆盖

**示例：未删除记录最终追平**

1. 旧表 S1 最终停在“成功、版本 8”，不再发生修改。
2. 双写或重试将版本 8 送达新表；即使漏发 MQ，完整校验也能发现差异。
3. 新表缺失或落后时接受版本 8，同版本错误内容经校验修复。
4. 迟到的版本 1～7 被拒绝，重复版本 8 不改变结果。
5. 复核后，新旧表业务数据和 version 一致。

**成立条件：送达、修复和版本维护都可靠**

上述示例要求故障最终恢复，扫描覆盖完整，重试和修复最终成功，所有修改入口正确维护版本。持续业务写入期间仍可能暂时落后；物理删除还需要 2.7 的持续清理。目标版本被误写得过高时，普通同步不能自动纠正，需要另行调查和受控修数。

这些条件说明旧表主写期间的局部收敛逻辑，不证明 2.8 的完整链路目标已经完成，也不证明生产效果已经验证。

### 2.10 ES 同版本修复：需要单独处理

**示例：新表修复成功，ES 却拒绝相同版本**

1. 新表和 ES 都错误保存为“异常、版本 3”。
2. 校验依据旧表将新表修正为“成功、版本 3”，版本不增加。
3. 若 ES 只接受严格更大的版本，版本 3 的修复写入就会被拒绝。
4. 新旧表已经一致，ES 仍可能停在异常状态。

需要独立设计受保护的 ES 修复方式，防止迟到的同版本错误数据再次覆盖修复结果。该部分仍待确认和运行验证。

## 5 异议与分析

### 5.1 共用底层写入方法不能证明完整链路一致

**判断：**调用相同方法，只能说明复用了这一段代码。2.8 的示例中，调用前的数据来源、业务判断和版本生成不同，因此当前局部设计未满足完整链路目标。本文保留设计缺口，不以修改标题代替实现方案。

### 5.2 version 不能单独保证最终一致性

**判断：**版本只能帮助决定已有记录是否接受本次写入。2.4 的漏发消息示例说明，数据根本没有送达时，新表无法比较；2.7 的删除示例说明，行被删除后也没有目标版本可拦截旧快照。最终一致还依赖完整扫描、失败恢复、差异修复和正确交接。
