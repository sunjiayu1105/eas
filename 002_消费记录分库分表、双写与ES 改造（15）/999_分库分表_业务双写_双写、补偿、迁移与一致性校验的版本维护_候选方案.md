## 1 面试口述精炼版本

**先明确目标：最终一致，以及完整链路不变**

我们希望双写、失败重试、历史迁移和校验修正能够共同保证新旧表最终一致。同时，切写前后新表的参数组装、业务校验、版本处理、数据库写入和异常处理都使用同一套链路代码。当前只整理了版本比较和补偿等局部机制，完整链路如何统一还没有完成设计。详见[目标与设计状态](#21-改造目标与当前设计状态)。

**旧表产生版本，新表按版本接收数据**

在旧表主写阶段，每次修改旧表记录，都让业务数据和 version+1 一起成功或一起失败。同步时将完整数据和对应版本一起传给新表：没有记录就插入，版本落后就更新，已有更高版本就跳过。例如新表已经收到“成功、版本 2”，迁移的“异常、版本 1”晚到时就不会把它覆盖。详见[旧表版本维护](#22-旧表主写期间修改数据并递增版本)、[双写比较与写入](#24-双写比较本次旧表提交版本再写入新表)。

**失败重试补漏写，校验处理遗漏和差异**

双写失败后通过 MQ 重试，迁移任务分批补齐存量，两者都复用新表的比较规则。校验以旧表为准，检查缺失、版本和内容差异，以及新表多余记录。旧表提交后若进程在发送 MQ 前崩溃，就靠完整校验补齐；因此允许暂时落后，最终一致依赖重试和修复成功。详见[失败重试](#25-双写重试重新比较原版本避免重复或倒序覆盖)、[校验修复](#27-一致性校验修正以旧表当前数据为准修复新表)。

**切写还需要交接，不能只看版本大小**

切写前要处理旧表在途写入、积压补偿和旧方向校验任务，确认新表追平。新表接管后，旧表不再接收新变更，就不能继续拿旧表修正新表。共用一个底层写入方法还不能证明完整业务链路相同，这部分需要继续设计。详见[切写与设计缺口](#28-切写前后完整新表业务链路仍待统一)。

## 2 详细方案

本节示例只解释处理规则，不是生产记录或测试结果。S1 表示一条消费记录，M1 表示其商户；“内容相同”指全部需要同步的字段相同。状态变更以“异常（未确认）变为成功或失败”为背景，后文用成功举例。

### 2.1 改造目标与当前设计状态

**已确认目标：完整的新表业务写入链路保持一致**

切写前后的参数组装、业务校验、版本处理、数据库写入和异常处理，都应使用同一套新表链路代码。切写时改变业务请求路由，不能仅凭共用 writeNewRecord 或相同 SQL，就说完整链路已经一致。

**已有设计基础：版本比较与差异修复**

下文说明旧表主写期间，如何维护版本、同步数据、重试失败、迁移存量和校验差异。这些机制用于评估最终一致性，不代表完整新表业务链路已设计完成。该缺口集中放在 2.8，避免与已能说明的局部规则混在一起。

**执行前提：先准备版本，再双写、迁移**

1. 开启双写前，旧表新增 version，存量记录初始化为 1。
2. 所有旧表修改入口都维护 version，包括人工修数。
3. 新表从空表开始，先开启双写，再执行历史迁移。
4. 新旧表各只有一个 version；旧表主写期间，追平后两边业务数据和版本一致。
5. 项目使用物理删除；serialNo 全局唯一，删除后不复用。

以上是用户已确认的设计前提，不等同于已经实施。

### 2.2 旧表主写期间：修改数据并递增版本

**旧表更新规则：业务数据和版本一起修改**

旧表新增记录时 version=1。每次修改旧表记录数据，都在同一次原子更新中执行 version+1，让数据和版本一起成功或一起失败。

**并发条件：使用本次读到的旧表版本**

expected_version 是本次修改前读取的旧表 version，由应用作为参数传入。下面是 MySQL 8.0.33 核心示意；实际表名、字段及合法状态条件需按业务实现。

~~~sql
-- 读取旧表当前数据及版本，供业务判断和条件更新使用。
SELECT status, version
FROM old_record
WHERE serial_no = :serial_no;

-- :expected_version 取自上面的查询结果。
-- 实际 UPDATE 还需包含合法业务状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

**示例：旧表正常修改成功**

1. 应用读取 S1，得到“异常、版本 1”。
2. 回查确认成功，应用携带 expected_version=1 更新旧表。
3. 旧表仍为版本 1，更新成功，成为“成功、版本 2”。
4. 旧表事务提交后，这份完整数据和版本 2 才能同步给新表。

**示例：查询后，旧表被另一个操作修改**

1. 本次操作读到旧表版本 3。
2. 另一个写入先成功，将旧表更新到版本 4。
3. 本次 UPDATE 携带 expected_version=3，影响 0 行。
4. 应用重新查询旧表并做业务判断，不去掉版本条件强行覆盖。

影响 0 行也可能是记录已删除或业务条件不满足，必须结合查询结果处理。这里按可能存在并发修改设计。

### 2.3 四个功能的共同前提：定位方式与完整快照

**定位方式：merchantNo 路由，serialNo 查找记录**

双写、双写重试、历史迁移和一致性校验修正，都通过 merchantNo + serialNo 定位新表记录。merchantNo 用于路由到实际分表；serialNo 全局唯一、不重复，并建立唯一索引。不使用 consumeId 或旧表 id 定位新表。

**输入要求：业务数据和 version 必须来自同一份快照**

完整快照包含 merchantNo、serialNo、全部同步字段及对应的 version，不能把不同时间读到的数据和版本拼起来。下面四个功能都将旧表已提交的数据和版本一起写入新表，不额外递增新表版本。

本节及 2.4～2.7 只说明旧表主写期间的同步机制。它们如何与切写后的业务组成相同的完整链路，仍是 2.8 的待设计问题。

### 2.4 双写：比较本次旧表提交版本，再写入新表

**输入数据：旧表本次修改后的完整快照**

1. 在旧表事务内修改业务数据并执行 version+1。
2. 在同一事务内取得修改后的完整快照。
3. 旧表事务提交成功后，再将快照用于新表双写；旧表回滚则不发送。

**比较与写入：新表只接收更高版本，缺失时补插**

按 merchantNo + serialNo 定位后，分别处理：

- 新表没有记录：插入完整快照，version 直接保存旧表传入值。
- 传入版本大于新表版本：在一次条件更新中写入全部同步字段，并将 version 设置为传入值。
- 传入版本小于新表版本：说明这份快照已落后，跳过写入。
- 版本相同、内容相同：已同步，不重复修改。
- 版本相同、内容不同：报告差异，交由 2.7 的校验修正，不无条件覆盖。

**原子更新：让数据库在写入时比较版本**

~~~sql
-- 已根据 merchantNo 路由到实际分表，使用 serialNo 定位。
-- 实际 SET 包含全部同步字段，示例只展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

影响 0 行时重新读取并判断：可能是记录缺失、版本相同或新表已有更高版本，不能一律当作成功。缺失时尝试插入；若发生同一 serialNo 的唯一键冲突，重新查询并比较版本。其他约束错误、数据库故障仍按失败处理。后续重试、迁移和校验中的“高版本更新”也使用这个原子条件，不能先比较再无条件覆盖。

**完成条件：确认写入结果，失败进入补偿**

新表事务已提交、已存在同版本同内容，或已有更高版本时，本次同步可以结束。同版本差异应修复或可靠登记待修复事项，不能当成数据已经一致。写新表失败时发送 MQ 补偿消息；发送失败也要重试和告警。

**示例：旧表异常状态改为成功，新表接收版本 2**

1. 旧表 S1 为“异常、版本 1”，新表也已存在这条记录。
2. 回查确认成功，旧表事务将 S1 改为“成功、版本 2”并提交。
3. 双写携带版本 2 的完整快照，通过 M1 + S1 定位新表。
4. 新表版本为 1，满足 1 < 2，条件更新成功。
5. 新表保存“成功、版本 2”，不会额外加到版本 3。
6. 若新表原本没有 S1，则插入“成功、版本 2”，而不是把 UPDATE 影响 0 行当成成功。

**遗漏示例：旧表已提交，但进程在发送 MQ 前崩溃**

1. 旧表已提交“成功、版本 2”。
2. 新表尚未写入，进程也没有来得及发送 MQ 就崩溃。
3. MQ 没有这次消息，无法仅靠消费重试补齐。
4. 后续完整校验发现新表缺失或落后，读取旧表当前快照并修复。

这类遗漏依赖完整校验兜底，恢复时间受校验周期影响，不能承诺实时一致。

### 2.5 双写重试：重新比较原版本，避免重复或倒序覆盖

**输入数据：失败时保留的旧表已提交快照**

MQ 消费者使用消息中的原数据和原 version。重试不再修改旧表，也不为新表额外生成版本。本节只说明同步失败重试，不代表切写后业务请求的重试策略。

**比较与写入：每次重试都以新表当前版本为准**

- 新表仍缺失：插入消息中的完整数据和 version。
- 消息版本更高：按 2.4 的原子条件更新数据，将新表 version 设置为消息版本。
- 消息版本更低：跳过旧消息，保留新表较新数据。
- 版本和内容相同：说明此前已写入，直接结束本次重复处理。
- 同版本内容不同：报告差异并转入校验修正，不反复无条件覆盖。

插入发生同一 serialNo 的唯一键冲突，或条件更新影响 0 行时，重新查询新表再判断；数据库异常继续按失败重试。

**完成条件：确认结果后再确认消息处理完成**

新表写入已提交、同版本同内容或已有更高版本时，才能结束本次同步事件。同版本差异须完成修复，或可靠登记到后续可继续处理的修复流程；登记不代表已经一致。持续失败要重试和告警，不能只打印日志后丢弃。

**示例：低版本补偿晚于终态到达**

1. 旧表创建“异常、版本 1”，双写失败，版本 1 的完整快照进入 MQ，新表无记录。
2. 回查确认成功，旧表提交“成功、版本 2”。
3. 版本 2 的双写先成功，在新表插入“成功、版本 2”。
4. 版本 1 的补偿消息到达，比较发现 1 < 2，跳过写入。
5. 新表保留“成功、版本 2”，版本 1 的补偿事件可以结束。

**示例：新表已经写成功，MQ 又投递一次**

1. 补偿将 S1 的版本 2 快照写入新表并提交。
2. MQ 再次投递同一份版本 2 快照。
3. 消费者核对新表版本和全部同步字段，确认均相同。
4. 不再修改新表，version 仍为 2，确认本次消息处理完成。

### 2.6 历史迁移：比较读取快照的版本，成功后保存进度

**输入数据：固定迁移范围内的旧表完整快照**

开始扫描前获取本次最大 ID，按主键分批读取旧表完整数据和 version。这个范围可能包含开启双写后已经写入新表的记录，所以迁移不能假设新表一定为空。

**比较与写入：补齐缺失，拒绝落后的迁移快照**

- 新表缺失：插入本次读取的完整数据和 version。
- 迁移快照版本更高：通过原子条件更新全部同步字段和 version。
- 迁移快照版本更低：保留新表较新数据，跳过这条旧快照。
- 同版本同内容：已同步，视为本条处理完成。
- 同版本内容不同：修复或可靠登记待修复事项，不无条件覆盖。

并发插入出现同一 serialNo 的唯一键冲突、条件更新影响 0 行时，都重新查询新表并比较。迁移传入完整字段值，因此可以从新表版本 1 直接更新到来源版本 3；不能将此规则用于“金额加 10”一类增量操作。

**完成条件：本批处理完成，再保存完成游标**

只有本批全部处理完成，才能推进游标。差异可以先修复或可靠登记待修复事项；登记后的差异仍需后续闭合，其他写入失败不能被游标越过。恢复时若重新查询旧表，使用这次查到的数据和版本，不默认重放上次缓存。

**示例：迁移读取后，双写先写入了更高版本**

1. 迁移读到旧表 S1 的“异常、版本 1”，尚未写入新表。
2. 回查确认成功，旧表变为“成功、版本 2”，双写成功写入新表。
3. 迁移携带版本 1 快照执行条件更新，不满足新表 version < 1，影响 0 行。
4. 迁移重查发现新表为版本 2，跳过旧快照。
5. 新表保留“成功、版本 2”。

**示例：数据已写入，但进度还没有保存**

1. 持久化游标为 100，本批读取 ID 101～200。
2. 本批数据已成功写入新表。
3. 任务在保存游标 200 前崩溃，游标仍为 100。
4. 恢复后从 101 重新读取旧表，再次尝试写入。
5. 相同版本、相同内容直接跳过；读到更高版本则更新，落后于新表则跳过。
6. 本批全部处理完成后，保存游标 200。

批次部分成功后整批重试也可能重复处理；从已确认完成游标之后恢复，则不会重做之前已完成的批次。

### 2.7 一致性校验修正：以旧表当前数据为准修复新表

**输入数据：两边记录的存在性、版本和同步字段**

分批扫描新旧表的 serialNo，合并去重，并保留回查所需的 merchantNo，再查询两边当前记录。必须覆盖新表，才能发现旧表已删除而新表仍存在的记录。以下判断只适用于旧表主写阶段。

**比较与写入：按差异类型选择修复动作**

- 旧表有、新表无：读取旧表最新完整快照，插入数据和对应 version；唯一键冲突则重查新表再判断。
- 旧表版本更高：用旧表快照执行 version < 传入版本的条件更新，同时保存全部同步字段和 version。影响 0 行则重查，不能强行覆盖。
- 版本和内容相同：本条校验通过。
- 版本相同、内容不同：重新读取旧表，在新表事务内锁定目标行，再次比较后修正内容，version 保持来源版本。
- 新表版本更高：重查旧表主库，排除先后读取导致的时序差异；仍异常则调查版本维护及写入来源，不直接降低新表版本。
- 旧表无、新表有：重查旧表主库确认不存在后，删除新表多余记录；查询失败不能当成不存在。
- 两边均不存在：无需修复。

**版本处理：接收来源版本，不能因修复额外加 1**

新表接受更高版本时，即使当前业务字段看起来相同，也要更新 version，否则迟到的中间版本仍可能被接受。相同版本的内容修复则保留该版本，不伪造一次旧表业务变化。

**示例：内容又改回原值，版本仍要推进**

此例假设某个可修改字段允许从 A 改为 B 再改回 A，仅解释版本排序，不表示终态可以回退为异常。

1. 新表为“字段 A、版本 1”。
2. 旧表先改为“字段 B、版本 2”，再改为“字段 A、版本 3”。
3. 校验读取旧表版本 3 的完整快照。
4. 虽然该字段同为 A，仍更新全部同步字段，并将新表版本推进到 3。
5. 迟到的版本 2 被拒绝，新表保留字段 A 和版本 3。

**示例：修正同版本的错误内容**

1. 旧表为“成功、版本 3”，新表错误保存为“异常、版本 3”。
2. 校验重新从旧表读取版本 3 的完整快照。
3. 通过 merchantNo 路由，在新表事务内按 serialNo 使用 SELECT ... FOR UPDATE 锁住记录。
4. 锁内确认新表仍为版本 3，再修正内容，version 保持 3。
5. 若已是更高版本，放弃当前旧快照；若缺失或版本更低，按本节对应分支重新处理。
6. 提交后重新校验，失败则重新读取并重试。

该流程要求旧表同一个 version 对应确定内容；旧表修改数据却漏增版本时，目标行锁无法判断来源数据的新旧。

**示例：物理删除后，迁移旧快照再次插入**

1. 迁移读到 S1 快照，尚未写入新表。
2. 业务物理删除旧表和新表的 S1。
3. 迁移晚到，发现新表没有 S1，又插入旧快照。
4. 校验扫描新表发现 S1，重查旧表主库确认 S1 不存在。
5. 校验删除新表 S1 并复核；若仍有迟到任务插入，后续校验继续清理。

serialNo 删除后不复用，步骤 3 是旧数据重新出现。物理删除后没有目标 version 可供比较，因此删除最终一致依赖最后一次迟到写入之后仍完成清理。项目方向及来源见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

**完成条件：修复提交后复核，仍有差异继续处理**

发起修复不等于修复成功。重新查询后确认内容及版本一致，或确认多余记录已删除，才算这条差异修复完成；并发修改导致新差异时继续处理。整体最终一致还依赖完整扫描、故障恢复和后续重试，详见 2.9。

### 2.8 切写前后：完整新表业务链路仍待统一

**先完成交接：旧表停止主写，旧方向任务退出**

新表承接主写前，要处理旧表在途写入、积压补偿，确认新表追平，并完成迁移及旧方向校验任务的退出或交接。不能让旧任务继续按旧表修改、删除新表数据。总体切换和回滚方向见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)；具体交接机制仍待验证。

**示例：共用底层方法，不等于完整链路一致**

1. 切写前，调用方取得旧表已提交的“成功、版本 2”。
2. 新表底层方法比较并保存这份数据和版本。
3. 切写后，原局部设计先读取并锁定新表，再做业务判断、生成下一版本。
4. 最后仍调用同一个底层方法，但前面的参数、判断和版本处理已经不同。
5. 因此，这个局部设计还没有满足用户要求的完整链路一致。

**待设计重点：同时满足链路一致、版本一致和并发安全**

需要把新表的参数组装、业务校验、版本处理、数据库写入和异常处理设计成同一套完整流程，并与旧表同步、历史迁移、重试和校验衔接。目前只统一了部分落库规则，不能写成切写时仅改路由就已具备全部能力。

原局部方案中的新表行锁、同事务写入，只能说明一种并发保护思路；是否保留以及如何接入完整链路，需在整体设计中确定。新增记录的版本初始化、唯一键冲突、业务失败回滚及提交结果不确定后的重试，也需要在该设计中闭合。

### 2.9 最终一致性：最新数据能送达，旧数据不能覆盖

**示例：未删除记录最终追平**

1. 旧表 S1 最终停在“成功、版本 8”，不再发生修改。
2. 双写或重试将版本 8 送达新表；即使漏发 MQ，完整校验也能发现差异。
3. 新表缺失或落后时接受版本 8，同版本错误内容经校验修复。
4. 迟到的版本 1～7 被拒绝，重复版本 8 不改变结果。
5. 复核后，新旧表业务数据和 version 一致。

**成立条件：送达、修复和版本维护都可靠**

上述示例要求故障最终恢复，扫描覆盖完整，重试和修复最终成功，所有修改入口正确维护版本。持续业务写入期间仍可能暂时落后；物理删除还需要 2.7 的持续清理。目标版本被误写得过高时，普通同步不能自动纠正，需要另行调查和受控修数。

这些条件说明旧表主写期间的局部收敛逻辑，不证明 2.8 的完整链路目标已经完成，也不证明生产效果已经验证。

### 2.10 ES 同版本修复：需要单独处理

**示例：新表修复成功，ES 却拒绝相同版本**

1. 新表和 ES 都错误保存为“异常、版本 3”。
2. 校验依据旧表将新表修正为“成功、版本 3”，版本不增加。
3. 若 ES 只接受严格更大的版本，版本 3 的修复写入就会被拒绝。
4. 新旧表已经一致，ES 仍可能停在异常状态。

需要独立设计受保护的 ES 修复方式，防止迟到的同版本错误数据再次覆盖修复结果。该部分仍待确认和运行验证。

## 5 异议与分析

### 5.1 共用底层写入方法不能证明完整链路一致

**判断：**调用相同方法，只能说明复用了这一段代码。2.8 的示例中，调用前的数据来源、业务判断和版本生成不同，因此当前局部设计未满足完整链路目标。本文保留设计缺口，不以修改标题代替实现方案。
