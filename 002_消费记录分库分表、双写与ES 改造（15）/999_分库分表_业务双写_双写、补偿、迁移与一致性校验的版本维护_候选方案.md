## 1 面试口述精炼版本

**先明确两个目标**

这套候选方案有两个目标：让双写、失败重试、历史迁移和校验修正共同保证新旧表最终一致；把业务写入从旧表切到新表时，不用临时修改新表业务代码。

**分开业务变更与数据同步**

业务先写旧表时，每次实际修改记录，都把该记录的 version 加 1。新表同步方法保存旧表传来的数据和版本，不让旧版本覆盖已经收到的新版本。新表业务方法提前写好；切写时把请求转到这个方法，每次实际修改记录，都在已有版本上加 1。

**既要防止旧数据覆盖，也要补齐没写成功的数据**

四类任务共用同步方法：新表没有记录就插入，已有记录就比较版本，只接受更高版本；同版本内容不同则重新核对旧表后修复。旧表提交后写新表，失败通过 MQ 重试；历史迁移补齐存量，完整校验发现漏发消息和其他差异并修正。最终一致还要求故障能够恢复、多余记录能够清理、切写时能完成旧任务交接；ES 是否一致需要单独验证。整套方案尚未确认采用。详见[目标与前提](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:23>)、[最终一致性条件](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:161>)。

## 2 详细方案

### 2.1 改造目标、适用阶段与准备工作

**目标一：多个任务同时处理同一条记录，最终数据仍然一致。**

双写、写入失败重试、历史迁移和一致性校验可能同时处理同一条记录。目标是补齐漏写、修正差异，并防止迟到的旧数据覆盖新表已经收到的较新状态。业务先写旧表、再同步新表期间，新表可以暂时落后；等该记录的最新变更同步成功后，两边的业务数据和 version 应一致。切写后旧表若不再接收新变更，则不要求它继续与新表保持一致。

**目标二：切写时无需修改新表业务写入链路的代码。**

提前将新表业务方法与同步方法分开：业务方法负责业务修改和版本递增，同步方法负责接收旧表的数据及版本。切写时通过路由切换启用已准备好的新表业务链路，无需临时修改、发布该链路的代码；但仍需处理已经开始、尚未结束的写入，以及原有补偿和校验任务的退出或交接。

**谁维护版本：切写前由旧表负责，切写后由新表负责。**

新旧表各只维护一个 version，不增加 source_version。旧表主写期间，旧表产生版本，新表的同步方法复制对应的数据和版本，不独立递增。新表接管主写后，由其业务方法继续维护同一个 version，已有版本不重置。[006 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:41>) 的本地版本方案与本候选方案分开说明；切换时的任务交接见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)。

**实施顺序：先准备版本，再开启双写，最后迁移存量。**

- **旧表初始化（本候选方案已明确的前提）**：开启双写前，给旧表新增 version 字段，将存量记录初始化为 1，并确保所有修改入口在实际修改数据时，让数据修改和 version + 1 一起成功或一起失败，不能只改数据、不改版本。
- **新表起点与执行顺序（已确认）**：开启双写前，新表为空；先开启双写，再执行历史迁移。新表首次写入记录时，同时保存旧表快照中的业务数据及 version，后续写入按 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:86>) 的统一规则处理。历史迁移开始时，新表可能已有双写写入的记录，仍需比较版本，避免迁移的旧快照覆盖较新数据。

### 2.2 版本维护：业务修改时加 1，同步时保存传入版本

**旧表主写期间：旧表产生变更和版本。**

旧表主写期间，新增记录时 version=1。**每次修改一条旧表记录的数据，都要同时将该记录的 version 加 1。数据修改和版本递增应在同一次原子更新中完成，一起成功或一起失败。** 所有修改入口，包括人工修数，都必须遵守这条规则。

例如旧表从“异常、版本 1”更新为“成功、版本 2”，新表同步后也是“成功、版本 2”。新表保存旧表传来的版本，不自行加一。

下面的 SQL 适用于读取后可能有其他写入修改同一记录的情况。expected_version 是本次修改前从旧表读取到的 version，由应用保存并作为更新参数传入，不是新增字段，也不是另行生成的版本号。例如读到 version=3，就传入 expected_version=3；更新时旧表仍为版本 3 才能修改成功，并将版本加到 4。下面先查询，再执行条件更新；版本比较、业务数据修改和版本加 1 在同一条 UPDATE 中完成。以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准；SQL 仅为 MySQL 8.0.33 的核心条件示例，表名、字段名和命名参数均作示意，不是现有代码或完整实现。

~~~sql
-- 1. 读取本次要修改的旧表记录；实际查询应包含业务判断所需字段。
SELECT status, version
FROM old_record
WHERE serial_no = :serial_no;

-- 2. 应用保存查询结果中的 version，作为后续 UPDATE 的 expected_version。
-- 例如读取到 version=3，则绑定 :expected_version=3。
-- 记录不存在时应单独处理，不继续执行下面的更新。

-- 3. 业务判断通过后，带着刚才读到的版本执行更新。
-- 前提：业务状态转换合法；实际更新须包含相应状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

查询和更新之间，记录可能被其他操作修改。例如旧表已从版本 3 变为 4，本次携带 expected_version=3 的 UPDATE 就影响 0 行，应重新读取并判断，不能去掉版本条件强行覆盖。影响 0 行也可能是记录已删除或其他业务条件不满足，需要结合重新查询的结果处理。

同步时传递完整快照，即同一次读取取得的业务标识、路由信息、全部同步字段和 version。同一个版本必须对应确定的数据内容，不能先读到“异常”，再单独读到版本 2，就把它们拼成“异常、版本 2”发送。

按 merchantNo 找到记录所在的分表，用 serialNo 判断新旧表中哪些记录对应同一笔交易。serialNo 全局唯一，删除后也不重复使用。新表第一次插入时生成自己的 consumeId，以后更新继续使用它，不把旧表 id 当作新表主键。

**用户自行确认的项目方案：新表业务方法保持不变，同步逻辑独立。**

在本候选设计中，提前实现两类新表写入方法，切写时不临时修改版本维护代码：

- **业务方法**：处理新的业务请求，负责业务校验和业务数据修改。新增记录时 version=1；修改已有记录时，在同一次原子更新中修改业务字段并执行 version+1。这个职责切写前后保持不变，但旧表主写期间，双写不调用它重复执行业务变更。
- **同步方法**：供双写、失败重试、历史迁移和一致性校验使用，接收旧表的完整数据及 version，按 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:86>) 的条件写入；同版本差异按 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:139>) 修复。它复制已有变更，不再次执行业务动作，也不自行递增版本。

例如同步收到“成功、版本 8”，新表保存版本 8；只有执行新的业务修改时，才由业务方法递增版本。

### 2.3 同步方法：先比较版本，再决定是否写入

四类任务都调用本节的同步方法，把旧表的数据和版本写入新表。下文“传入版本”指旧表快照携带的 version，“目标版本”指新表当前保存的 version。此处先讨论旧表中仍存在的记录，物理删除另见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

1. **目标不存在：插入。** 版本直接取传入值，首次收到版本 5 就插入版本 5。如果另一个任务已经插入了同一业务记录，导致唯一键冲突，就重新读取新表并比较版本；其他约束或 SQL 错误仍按失败处理。
2. **传入版本更大：更新。** 在同一次更新中写入全部需要同步的字段，并将新表 version 设置为传入值。传入的是版本 3 的完整数据时，可以直接把版本 1 更新到 3；如果传入的只是“金额加 10”这种操作指令，就不能跳过中间操作。
3. **传入版本更小：跳过。** 不修改业务字段或版本。
4. **版本相同、内容相同：已经同步，不再修改。** 不更新、不加版本。
5. **版本相同、内容不同：标记差异，交给校验修复。** 进入 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:139>) 的修复流程：锁定新表记录、重新核对后再改，不能忽略差异，也不能直接覆盖。

~~~sql
-- 已按 merchantNo 路由到实际分表。
-- 实际 SET 应包含全部同步字段，此处仅展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

上面的 SQL 将版本比较和更新合为一个数据库操作，避免“判断时可以更新，真正写入时目标却已变新”的窗口。影响 0 行不能直接视为同步成功：需要读取目标，区分记录缺失、版本更高、同版本同内容或同版本内容不同，再按上述分支处理。目标缺失时尝试插入，遇到并发插入的唯一键冲突后重新比较。

即使可见业务字段恰好相同，收到更大版本也要把新表 version 更新为这个版本。更新时间作为普通同步字段保留，不再负责本候选方案的新旧排序。

### 2.4 双写：旧表提交后写新表，失败通过 MQ 重试

旧表业务提交后，调用同步方法写新表；失败时将完整快照和 version 发送到 MQ，后续继续补偿。快照应在旧表业务事务内取得，确保数据与版本对应，事务提交后才能发送。

**完整校验兜底漏发消息。** 例如旧表提交“成功、版本 2”后，进程在写新表、发送 MQ 前崩溃，这次变化没有进入队列，需要完整一致性校验发现并补齐。MQ 发送失败时应重试、告警；仍未进入队列的遗漏也由完整校验兜底。恢复时间取决于校验周期，不能承诺实时一致。

**可选增强：事务发件箱。** 如果希望减少对校验周期的依赖，可以把待发送事件与旧表修改放在同一事务中保存，再由后台投递。这样进程恢复后仍能找回事件，但需要增加事件表和投递管理，本次简化不把它作为必选设计。

### 2.5 失败重试：原数据、原版本再次同步

写新表失败后，MQ 消费者用原数据和 version 调用同一个同步方法，不增加两边版本：目标缺失就插入，版本落后就更新，已是相同版本和内容就结束；旧事件已被更高版本替代，也可以结束。

**示例：旧消息晚到，不覆盖终态。**

1. 旧表创建“异常、版本 1”，写新表失败，版本 1 进入补偿队列，新表无记录。
2. 回查得到成功，旧表更新为“成功、版本 2”；本次双写通过缺失插入，新表成为“成功、版本 2”。
3. 版本 1 的补偿随后到达，发现新表已有版本 2，跳过旧数据。
4. 如果版本 2 再次重试，新表版本和内容均相同，也不重复修改。

只有目标写入已提交、已同步或已被更高版本替代，才能确认消息处理完成。同版本内容不同，须修复或可靠登记为待修复任务；仍然失败的任务继续重试，长期失败告警处理，不能直接丢弃。

### 2.6 历史迁移：分批同步，成功后保存进度

开始扫描前确定最大 ID，分批读取旧表完整数据和 version，调用同步方法。本批全部处理完成后才保存游标；失败后从上次已确认完成的位置继续。重新查询旧表时，使用本次读到的数据，不默认沿用上次缓存。

例如游标为 100，ID 101～200 已写入新表，但保存游标前进程崩溃，恢复后会再次读取这批记录。同步方法根据版本和内容识别重复，不会插入两份，也不会让旧快照覆盖更高版本。若从已确认完成的游标之后恢复，则不会重复此前已完成的批次。

同版本差异须先修复，或可靠登记为待修复任务，才能推进进度；不能越过尚未处理的失败记录。迁移旧快照晚到时，版本比较规则与上一节的补偿示例相同。

### 2.7 一致性校验：以旧表为准补齐和修正

分批读取两边的 serialNo，合并去重后回查当前记录，比较存在性、版本和全部同步字段：

- 旧表有、新表缺失或版本落后：重新读取旧表完整快照，调用同步方法补齐。
- 版本和内容相同：通过。
- 版本相同、内容不同：按下面的流程修复。
- 新表版本更高：重查旧表主库，排除读取时序差异；仍异常则调查错误写入，不能直接降低版本。
- 新表有、旧表没有：重新查询旧表主库确认不存在后物理删除新表记录；查询失败不能当成不存在。

**同版本差异的修复。** 例如旧表是“成功、版本 2”，新表错误保存为“异常、版本 2”：重新读取旧表快照，在新表事务内用 SELECT ... FOR UPDATE 锁住目标，再核对版本。目标仍为版本 2 才修复内容，version 保持 2；已到更高版本就放弃旧快照。若目标缺失或版本更低，按同步规则处理。提交后复核，失败重试。

项目使用物理删除，serialNo 删除后不复用。迟到快照仍可能重新插入已删除记录，因此需要持续扫描两边，在迟到任务处理完后再次清理、复核多余记录。详见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

### 2.8 切写：切换路由，业务方法保持不变

新表业务方法提前实现。切写时完成旧表在途写入、积压补偿和旧方向校验任务的退出或交接，再让业务请求进入新表业务方法。不能让两边同时独立生成版本，也不能继续用落后的旧表修正新表。

例如新表已同步到“异常、版本 8”，切写后回查确认成功，新表业务方法将状态改为成功，同时把版本从 8 增至 9，不重置版本。新表新增业务记录才从版本 1 开始。

“无需改代码”指不临时修改新表业务方法，并不意味着同步方法与业务方法执行相同 SQL。切换及回滚按 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>) 完成交接，具体机制待验证。切写后旧表不再接收新变更，就不再要求它持续与新表一致。

### 2.9 最终一致性：版本防回退，重试和校验补遗漏

以旧表最终停在“成功、版本 8”、记录未删除为例：双写或重试可以将它同步到新表；即使漏发 MQ，完整校验也应发现并修复差异。新表收到版本 8 后，迟到的版本 1～7 无法覆盖它，重复的版本 8 不再修改，因此两边最终追平。

这个结论要求故障最终恢复、完整校验覆盖全部记录、差异修复成功，且所有写入遵守版本规则。业务持续变更期间允许暂时落后。物理删除后的迟到写入需要持续清理；错误高版本不能靠普通同步自动纠正，应调查并受控修数。ES 同版本修复也需要独立验证。

### 2.10 历史迁移中 update_time 与来源 version 的取舍

以下四个问题说明改用 version 的收益和限制；当前仍采用 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的时间戳规则。各链路共同保障最终一致性的条件，见[候选方案 2.9](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:161>)，该设计尚未确认采用。

#### 2.10.1 历史迁移用 update_time 比较有什么问题

**前提：目标已有记录，但不同状态保存了相同时间。**

时间戳相等不能证明业务状态相同；毫秒精度只能降低碰撞概率，不能保证每次更新都产生不同时间。以下用同一时序对比两种方案，版本值仅用于后面的候选分析，不表示旧表已有 version 字段。具体时间是假设，不代表项目字段精度或回查耗时。

1. **迁移读取，暂未写入。**  旧表为“异常（未确认）、10:00:00.123”，候选来源版本为 1；新表也已有该异常记录。
2. **回查得到成功。** 旧表更新为成功，保存时间仍为 10:00:00.123；候选来源版本随变更增至 2。新表尚未更新，仍为异常。
3. **双写实际更新已有目标。** 新表成为“成功、10:00:00.123”；候选方案下同时保存来源版本 2。
4. **迁移提交第 1 步的旧快照。** 新表已是成功，迁移仍携带异常、相同时间及候选版本 1。

按参考文章允许时间相等覆盖的规则，第 4 步可能把成功回退成异常；终态为失败时同理。即使原子执行条件更新，也无法消除比较值相等的歧义。规则来源见[参考文章 01_1：相等时间允许覆盖（第 89 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

若改成严格大于，旧快照会被拒绝；但反过来，目标是异常、来源已成功且时间相等，真正的新状态也会被拒绝。仅调整等号不能同时解决两个方向的问题。

**前提：时间不可比，或者比较与写入分开。**

这两类属于 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的实现前提未满足。例如旧状态在 10:05 迁入并错误记录为落库时间，就可能拒绝业务时间为 10:04 的较新终态；不同机器的时钟偏差也可能颠倒时间顺序。又如迁移先判断 10:04 比目标 10:00 新，双写随后更新目标到 10:05，迁移再无条件写入 10:04，仍会覆盖新状态。项目时间来源和原子写入方式尚待核实。

#### 2.10.2 用 version 比较能解决这些问题吗

**前提：使用统一来源版本，原子执行比较和写入。**

来源版本就是主写表记录的 version。只有每次修改都正确递增、同步时数据和版本对应，版本大小才能表示同一记录的变更先后。它与 [006 2.2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:60>) 的新表本地 version 职责不同。

**同一时序的处理结果**

两种方案都要判断快照是否过期；差别在于相同时间不能区分变更先后，而正确维护的来源版本可以。

**update_time 比较：**[候选方案 2.10.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:171>) 第 4 步的时间与目标相等，按当前规则允许覆盖，成功状态可能回退。

**来源 version 比较：** 要求来源版本更大才更新，迁移的 1 小于目标的 2，因此拒绝旧写入。反过来，目标为异常、版本 1，来源为成功、版本 2，就能补齐终态。

来源版本不依赖物理时钟，能避免单纯时钟偏差造成的先后误判。但它不会自动让写入原子化；先查版本再无条件更新，仍有同类并发窗口。

#### 2.10.3 是否有必要改成根据 version 比较

**判断依据是防回退要求和改造范围。**

若要求新表已经收到较新状态后，迟到快照不得将它回退，当前时间戳规则不够，建议优先评估统一来源版本，并让全部相关写入路径遵守同一协议。来源版本不是唯一可能的并发控制方法。

若接受短暂差异、希望控制旧表改造范围，可继续评估时间戳加校验，但必须明确同时间戳差异如何修复、迟到任务如何停止干扰，并验证收敛条件。不能仅因存在校验任务就认定实现安全。

项目异常回查一般在 1 天内得到成功或失败终态，因此重点关注仍可能变更的记录及其在途双写、补偿和修复；已稳定且不再修改的历史记录风险较低。这不是严格一天截止，也不能证明时间戳碰撞不存在。

采用来源版本需改造旧表和相关更新入口，设计存量初始化、发布兼容，以及主写切换后的版本归属和对新表本地版本机制的替换及与 ES 的衔接。当前时间戳方案与候选统一版本方案分别说明；候选方案已明确双写前给旧表新增 version 并初始化为 1，但整套方案尚未确认采用。详见[目标与前提](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:23>)、[最终一致性条件](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:161>)。

#### 2.10.4 用 version 比较还会有什么问题

**有的修改没有正确维护版本，就无法据此判断新旧。**

某个入口将异常改为成功却漏增版本，两种状态仍同为版本 1；先读取旧异常数据、再单独读取新版本 2，则会给旧数据配上新版本。所有相关入口都必须维护版本，业务字段与版本必须来自同一份读取结果。

**同版本内容不同：严格大于会漏掉修复。**

若新表已是版本 2，但某字段写错，仅接受更大版本会漏掉修复，也不能因此放开同版本无条件覆盖。处理流程见 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:139>)，具体实现尚未验证。

**目标缺失：仅比较版本，不能补齐漏写。**

以下反例假设双写只执行 UPDATE，没有按同步方法处理记录缺失。它说明版本字段本身的限制，不是本候选方案的完整写入流程。

1. 迁移读取旧表“异常、来源版本 1”，新表无记录，暂未插入。
2. 回查将旧表更新为“成功、来源版本 2”，新表仍无记录。
3. 双写执行 UPDATE，影响 0 行，成功状态和版本 2 都未保存；这不等于 SQL 一定报错，也不代表同步成功。
4. 迁移按缺失插入“异常、版本 1”。目标没有版本 2，无法仅靠版本比较拒绝旧状态。
5. 仍需补偿或校验发现差异，读取旧表终态并补齐；版本比较本身不会触发漏写发现。

**记录被删除或扫描遗漏时，版本字段本身无法解决。**

物理删除会同时删除行内版本，迟到快照可能重新插入已删除的旧记录，需要通过 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>) 的持续校验清理。游标越过后才提交等导致的扫描遗漏，也不会因记录有版本就自动补齐。

### 2.11 ES 同版本修复：候选版本方案的独立边界

本候选方案修复同版本内容差异时，不递增新表 version。例如新表原为“异常、版本 2”，修复后成为“成功、版本 2”；若 ES 已保存异常、版本 2，且只接受严格更大的版本，这次修复就无法写入 ES。

需要单独设计受保护的 ES 修复机制。不能简单允许所有同版本消息覆盖，否则迟到的错误内容可能再次覆盖修复结果。新旧表一致与 ES 一致应分别验证。
