## 1 面试口述精炼版本

**先明确两个目标**

这套候选方案有两个目标：让双写、失败重试、历史迁移和校验修正共同保证新旧表最终一致；把业务写入从旧表切到新表时，不用临时修改新表业务代码。

**分开业务变更与数据同步**

业务先写旧表时，每次实际修改记录，都把该记录的 version 加 1。新表同步方法保存旧表传来的数据和版本，不让旧版本覆盖已经收到的新版本。新表业务方法提前写好；切写时把请求转到这个方法，每次实际修改记录，都在已有版本上加 1。

**既要防止旧数据覆盖，也要补齐没写成功的数据**

这四类任务调用同一个同步方法。待同步的数据先可靠保存，失败后继续重试；校验发现遗漏或错误，再补齐或修正。最终一致还要求故障能够恢复、多余记录能够清理、切写时能完成旧任务交接；ES 是否一致需要单独验证。整套方案尚未确认采用。详见[目标与前提](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:23>)、[最终一致性条件](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:254>)。

## 2 详细方案

### 2.1 改造目标、适用阶段与准备工作

**目标一：多个任务同时处理同一条记录，最终数据仍然一致。**

双写、写入失败重试、历史迁移和一致性校验可能同时处理同一条记录。目标是补齐漏写、修正差异，并防止迟到的旧数据覆盖新表已经收到的较新状态。业务先写旧表、再同步新表期间，新表可以暂时落后；等该记录的最新变更同步成功后，两边的业务数据和 version 应一致。切写后旧表若不再接收新变更，则不要求它继续与新表保持一致。

**目标二：切写时无需修改新表业务写入链路的代码。**

提前将新表业务方法与同步方法分开：业务方法负责业务修改和版本递增，同步方法负责接收旧表的数据及版本。切写时通过路由切换启用已准备好的新表业务链路，无需临时修改、发布该链路的代码；但仍需处理已经开始、尚未结束的写入，以及原有补偿和校验任务的退出或交接。

**谁维护版本：切写前由旧表负责，切写后由新表负责。**

新旧表各只维护一个 version，不增加 source_version。旧表主写期间，旧表产生版本，新表的同步方法复制对应的数据和版本，不独立递增。新表接管主写后，由其业务方法继续维护同一个 version，已有版本不重置。[006 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:41>) 的本地版本方案与本候选方案分开说明；切换时的任务交接见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)。

**实施顺序：先准备版本，再开启双写，最后迁移存量。**

- **旧表初始化（本候选方案已明确的前提）**：开启双写前，给旧表新增 version 字段，将存量记录初始化为 1，并确保所有修改入口在实际修改数据时，让数据修改和 version + 1 一起成功或一起失败，不能只改数据、不改版本。
- **新表起点与执行顺序（已确认）**：开启双写前，新表为空；先开启双写，再执行历史迁移。新表首次写入记录时，同时保存旧表快照中的业务数据及 version，后续写入按 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:89>) 的统一规则处理。历史迁移开始时，新表可能已有双写写入的记录，仍需比较版本，避免迁移的旧快照覆盖较新数据。

### 2.2 版本维护：业务修改时加 1，同步时保存传入版本

**旧表主写期间：旧表产生变更和版本。**

旧表主写期间，新增记录时 version=1；每次实际修改记录的数据，业务数据修改与 version+1 在同一事务中一起提交或回滚。所有修改入口，包括人工修数，都必须遵守这条规则。新表直接保存旧表传来的版本，不自行加一。

例如旧表从“异常、版本 1”更新为“成功、版本 2”，新表同步后也是“成功、版本 2”。version 表示这条记录的变更先后，不是同步任务执行了多少次。重复请求应先判断是否已经处理，不能仅因重试再次修改业务和递增版本。

**示例：业务更新已成功，响应丢失后再次请求。**

同一次业务操作可能被请求多次，但业务修改和版本递增只能执行一次。假设一条消费记录当前为“异常、version=1”，异常回查得到成功：

1. **第一次请求执行成功。**旧表将状态改为成功，同时把 version 从 1 加到 2，事务已经提交。
2. **成功响应丢失。**调用方没有收到结果，以为失败，于是再次发送同一个请求。
3. **不识别重复的后果。**如果重试又无条件执行状态更新和 version+1，就会得到“成功、version=3”。这次并没有新的业务变化，却多增加了一次版本。
4. **正确处理。**确认这是同一次操作，并且上次已经完成后，返回已处理结果，不再次修改数据或增加版本，记录仍为“成功、version=2”。

这里要区分重试和新的业务修改：同一次操作重试，不重复加版本；以后确实发生了新的业务数据修改，仍应正常加版本。下方 SQL 的预期版本条件能阻止旧版本请求直接重复更新，但条件不满足时，仍需判断是之前已经处理成功，还是发生了其他并发修改，不能简单读取新版本后继续重复执行。

识别同一次操作，可以考虑业务请求唯一标识，或结合合法状态转换条件判断，具体方式尚待确定。仅凭当前状态相同，不一定适用于所有业务。这是业务请求重复的示例；同步任务重复写新表时，按同步方法比较版本和内容，不重新执行业务修改。

下面的 SQL 只在记录仍是调用方预期的版本时，才修改数据并把版本加 1。这三个动作在同一条 SQL 中完成。以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准；SQL 仅为 MySQL 8.0.33 的核心条件示例，表名、字段名和命名参数均作示意，不是现有代码或完整实现。

~~~sql
-- 前提：业务状态转换合法；实际更新须包含相应状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

版本条件不满足，说明记录可能已被其他操作修改，应重新读取并判断，不能去掉条件强行覆盖。版本判断也不能代替业务状态是否合法的校验。

同步时传递完整快照，即同一次读取取得的业务标识、路由信息、全部同步字段和 version。同一个版本必须对应确定的数据内容，不能先读到“异常”，再单独读到版本 2，就把它们拼成“异常、版本 2”发送。

按 merchantNo 找到记录所在的分表，用 serialNo 判断新旧表中哪些记录对应同一笔交易。serialNo 全局唯一，删除后也不重复使用。新表第一次插入时生成自己的 consumeId，以后更新继续使用它，不把旧表 id 当作新表主键。

**用户自行确认的项目方案：新表业务方法保持不变，同步逻辑独立。**

在本候选设计中，提前实现两类新表写入方法，切写时不临时修改版本维护代码：

- **业务方法**：处理新的业务请求，负责业务校验、重复请求识别及业务数据修改。新增记录时 version=1；修改已有记录时，在同一次原子更新中修改业务字段并执行 version+1。这个职责切写前后保持不变，但旧表主写期间，双写不调用它重复执行业务变更。
- **同步方法**：供双写、失败重试、历史迁移和一致性校验使用，接收旧表的完整数据及 version，按 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:89>) 的条件写入；同版本差异按 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:186>) 修复。它复制已有变更，不再次执行业务动作，也不自行递增版本。

两类方法可以复用路由、数据访问等底层组件，但不能混淆“接收已有版本”和“产生新版本”。例如同步收到“成功、版本 8”，应保存版本 8，不能再调用业务方法把版本增加到 9。

### 2.3 同步方法：先比较版本，再决定是否写入

下文的“同步方法”由双写、失败重试、历史迁移和校验修正共同调用，专门把旧表的数据写入新表，不重新执行业务操作。下文“传入版本”指旧表快照携带的 version，“目标版本”指新表当前保存的 version。此处先讨论旧表中仍存在的记录，物理删除另见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

1. **目标不存在：插入。**版本直接取传入值，首次收到版本 5 就插入版本 5。如果另一个任务已经插入了同一业务记录，导致唯一键冲突，就重新读取新表并比较版本；其他约束或 SQL 错误仍按失败处理。
2. **传入版本更大：更新。**在同一次更新中写入全部需要同步的字段，并将新表 version 设置为传入值。传入的是版本 3 的完整数据时，可以直接把版本 1 更新到 3；如果传入的只是“金额加 10”这种操作指令，就不能跳过中间操作。
3. **传入版本更小：跳过。**不修改业务字段或版本。
4. **版本相同、内容相同：已经同步，不再修改。**不更新、不加版本。
5. **版本相同、内容不同：标记差异，交给校验修复。**进入 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:186>) 的修复流程：锁定新表记录、重新核对后再改，不能忽略差异，也不能直接覆盖。

~~~sql
-- 已按 merchantNo 路由到实际分表。
-- 实际 SET 应包含全部同步字段，此处仅展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

上面的 SQL 将版本比较和更新合为一个数据库操作，避免“判断时可以更新，真正写入时目标却已变新”的窗口。影响 0 行不能直接视为同步成功：需要读取目标，区分记录缺失、版本更高、同版本同内容或同版本内容不同，再按上述分支处理。目标缺失时尝试插入，遇到并发插入的唯一键冲突后重新比较。

即使可见业务字段恰好相同，收到更大版本也要把新表 version 更新为这个版本。更新时间作为普通同步字段保留，不再负责本候选方案的新旧排序。

### 2.4 双写：先保存待同步数据，再尝试写新表

建议在旧表提交后立即尝试写新表，同时把待同步数据提前保存下来。具体做法是增加一张事件表，保存要发送的数据和版本，并让事件记录与旧表业务修改在同一个事务中提交。这种做法叫“事务发件箱”，增加的是同步记录，不是业务表中的第二个版本字段。

以一次状态修改为例，旧表事务内依次完成：

1. 校验业务状态，更新记录并递增 version。
2. 在同一事务内取得本次更新后的完整快照，保持它与待提交的 version 一致；不能提交后另查一次，再把其他变更的数据当成本次事件。
3. 保存对应待同步事件。
4. 一起提交；事务回滚时业务修改和事件均不生效。

事务提交后，业务线程可以立即尝试调用新表同步方法；后台任务把事件表中待发送的记录发到消息队列（MQ），消费者再调用同一个同步方法。两条路径可能重复发送同一份数据，新表根据版本和内容识别重复，不重复修改。

**示例：旧表提交后进程崩溃。**

旧表和事件已提交，但进程尚未写新表、发送 MQ 就崩溃。事件仍在数据库，后台恢复后可以继续投递；只依赖 catch 后发送消息则覆盖不了这个窗口。

这套设计解决的是“旧表已经提交，但同步工作丢失”的问题。下一节再说明事件发送失败、写入失败，以及响应丢失时怎样重试。

长期失败必须保留记录、告警并跟踪处理。哪些事件已发送、多个任务如何避免抢同一条事件、何时确认消费成功，以及失败后从哪里继续，都需要实现和验证，不能只建一张事件表就认为问题已经解决。

### 2.5 失败重试：重复发送原数据，不生成新版本

消息发送失败时继续发送；发送成功但投递状态未保存时，也允许重发。写入新表失败时，重试仍携带原事件的数据和 version，调用 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:89>) 的同步方法，不增加两边版本。下面三个场景分别说明乱序、漏写和重复处理。

**场景一：较新事件先成功，旧事件重试晚到。**

1. 旧表创建“异常、版本 1”，保存事件 A。
2. A 写新表失败，新表仍无记录。
3. 回查得到成功，旧表变为“成功、版本 2”，保存事件 B。
4. B 先到达，通过缺失插入将新表写成“成功、版本 2”。
5. A 重试，发现 1 小于 2，跳过旧快照并完成任务，新表保留成功。

**场景二：重试时目标仍缺失或版本落后。**

B 携带“成功、版本 2”重试：目标无记录就插入完整快照；目标为“异常、版本 1”就原子更新为“成功、版本 2”。仅执行 UPDATE 并忽略 0 行结果不能补齐缺失记录。

**场景三：写入已经成功，但响应丢失。**

1. B 已将新表写成“成功、版本 2”，调用方却收到超时。
2. B 重试，读取到相同版本和相同内容。
3. 作为重复处理完成，不更新、不增加版本。

**什么时候才能确认消息完成？**

新表写入已提交、目标已是相同版本和相同内容，或者目标已收到更高版本，才可以确认该事件已处理。同版本内容不同，必须完成修复，或先把差异持久化保存为修复任务、确保进程重启后仍能继续处理，再确认；数据库仍不可用，则保留失败继续重试。不能仅因调用结束或打印了日志就丢弃任务。

### 2.6 历史迁移：读取数据和版本，处理成功后再保存进度

迁移读取旧表数据及其 version，复用同步方法，不增加旧表版本。扫描前确定本次迁移的最大 ID，再分批读取并记录完成位置；失败后从保存的位置继续。如果恢复时重新查询旧表，就使用这次读到的数据，不能默认还是上次缓存的旧数据。

**先处理数据，再保存批次进度。**

游标记录已确认完成的位置。只有当前批次的记录都处理成功、已是重复结果或已被更高版本取代，才能保存完成进度；遇到同版本内容不同，须先修复，或将差异持久化登记为可继续处理的修复任务。不能越过尚未处理的失败记录。

例如持久化游标为 100，当前批次读取 ID 101～200：

1. 新表已成功写入这一批记录。
2. 任务在保存游标 200 前崩溃，持久化游标仍为 100。
3. 恢复后从 101 重新查询旧表，因此会再次处理这一批；使用的是本次查询结果，不是默认沿用上次快照。
4. 同步方法按版本和内容判断，不重复创建记录，也不让低版本覆盖高版本。

批次只写成功一部分后整批重试，也可能再次遇到已成功记录。若从已确认完成的游标之后恢复，则不会重做此前已完成的批次。

**示例：迁移快照晚于业务终态到达。**

1. 迁移读到“异常、版本 1”，暂未写入。
2. 回查将旧表更新为“成功、版本 2”。
3. 双写实际将新表写成“成功、版本 2”，目标可能原本存在，也可能由同步方法补建。
4. 迁移提交版本 1，被版本条件拒绝，新表保留成功。

如果第 3 步失败且新表仍缺失，迁移可能先插入“异常、版本 1”；版本 2 的可靠事件重试或后续校验再将其追平。该结果允许短暂落后，但已写入的较新版本不能被低版本覆盖。

### 2.7 一致性校验：检查记录是否存在、版本和内容是否一致

校验的职责是发现遗漏和错误，不能只比较 version。以旧表为准，分批读取两边的 serialNo，合并去重后回查当前记录，先检查存在性，再检查版本和全部同步字段。

- **目标缺失或版本落后**：重新读取旧表完整快照，调用同步方法补齐。
- **版本及内容都相同**：通过。
- **版本相同、内容不同**：按下面的行锁流程修复。
- **新表版本比旧表更高**：重新查询旧表主库，先排除之前读到旧数据、或两次查询之间发生更新的情况。如果重新查询后仍如此，就检查版本是否维护错误、数据从哪里写入、当前究竟由哪张表主写，不能直接降低新表版本。
- **目标多余**：重新查询旧表主库，确认记录不存在后物理删除新表对应记录，并复核、失败重试；查询失败不能视为不存在。迟到写入后的再次清理见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

**同版本内容不同：锁住目标，重新核对后修复。**

普通同步方法对已有记录只允许更高版本更新，因此同版本的错误内容需要专门修复。行锁使同一新表记录的并发更新依次执行；持锁后还要重新检查版本，避免覆盖已经到达的更高版本。以下以旧表为“成功、版本 2”，新表错误保存为“异常、版本 2”为例：

1. 重新从旧表读取完整的“成功、版本 2”。
2. 开启新表事务，以 SELECT ... FOR UPDATE 锁定对应目标记录，并在锁内重新核对版本、内容。
3. 若目标仍为“异常、版本 2”，修正为成功，version 保持 2。
4. 若目标已到版本 3，放弃当前快照；若缺失或版本更低，转入同步方法的对应分支。
5. 提交后复核，失败时重新读取、重试。

~~~sql
-- 在旧表主库取得完整快照后，进入目标分表事务。
START TRANSACTION;

SELECT status, version
FROM new_record
WHERE serial_no = :serial_no
FOR UPDATE;

-- 应用在锁内确认：记录存在、版本相同、内容不同，才执行此分支。
-- 实际修复包含已核对的全部同步字段；不递增 version。
UPDATE new_record
SET status = :verified_status
WHERE serial_no = :serial_no
  AND version = :verified_version;

COMMIT;
~~~

修复事务持有行锁期间，其他更新这条新表记录的事务需要等待；锁释放后，它们仍须按版本条件决定能否更新。这里的前提是旧表同一个版本只对应一份确定的数据。如果有人改了旧表数据却没改版本，仅靠新表加锁无法判断哪份内容更新。

如果旧表已经更新到版本 3，但新表还没收到，按版本 2 修复可能暂时成功；版本 3 随后到达时，仍可以把新表更新到最新状态。记录身份由全局唯一且不复用的 serialNo 确定，版本用于判断同一记录的变更顺序。

### 2.8 切写：请求改走新表业务方法，已有版本继续累加

**切写之后：业务路由进入新表业务方法。**

完成主写交接后，新业务请求调用预先准备好的新表业务方法。同步进来的已有记录沿用当前 version；新表首次创建的新业务记录才从 1 开始。以下 SQL 示意新表业务修改如何维护版本，不用于接收旧表快照：

~~~sql
-- 前提：新表已接管业务主写；实际更新须包含合法业务状态条件。
UPDATE new_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

条件不满足时重新读取并判断，不能无条件修改。业务请求重试也须识别是否已处理，不能仅因重试而再次递增版本。

**示例：同一条记录从同步写入转为业务主写。**

1. 切写前，旧表将某记录改为“异常、版本 8”，双写调用新表同步方法，新表保存相同数据及版本 8。
2. 完成主写交接后，异常回查得到成功，调用新表业务方法。
3. 新表业务方法将状态改为成功，同时把版本从 8 增至 9，不重新初始化，也不等待旧表传来版本 9。

因此，“代码保持一致”指新表业务方法前后不变，不是要求同步方法和业务方法执行同一条更新 SQL。切写仍要切换路由，并处理旧表在途写入、积压补偿和旧方向校验任务；不能让两边同时独立生成版本，也不能继续以落后的旧表修复新表。交接边界见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)，具体控制机制仍待实现验证。切写后不再要求已经停止接收新变更的旧表与新表版本持续相同。

### 2.9 最终一致性：最新数据最终写入，旧数据不能再覆盖

版本比较只决定“这次数据能不能写”，不会主动找回丢失的数据。可靠事件、重试和完整校验负责把数据最终送到新表，两部分缺一不可。以下以旧表最终停在“成功、版本 8”、且记录未被删除为例：

1. 提交版本 8 时，同步事件一起落库。
2. 后台重试或完整校验最终将“成功、8”送达新表。
3. 目标缺失或版本落后时接受它，同版本内容错误则锁定记录、重新核对后修复。
4. 迟到的版本 1～7 被拒绝，版本 8 的相同内容重投不改变目标。
5. 复核后两边数据、版本一致；没有违反协议的写入，就不会被迟到任务破坏。

物理删除会同时移除行内版本，迟到快照重新插入后的清理依赖 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>) 的持续校验；本节的版本比较不能代替删除处理。候选方案下 ES 的同版本修复也需要单独处理，见 [候选方案 2.11](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:345>)。

以上过程要求旧表版本正确，新表也没有被误写成比旧表更高的版本。若旧表最终停在版本 8，新表却因错误操作变成版本 100，普通同步会拒绝版本 8，不能靠重试自动纠正；应调查并通过另行受控的修数流程恢复，具体方案待确认。

要做到最终一致，需要故障最终恢复、重试和校验持续执行、该检查的记录没有遗漏、修复最终成功，并且所有写入都遵守前面的规则。永久不可用、持续绕过规则或无人处理的永久失败，不能仅靠版本字段解决。如果业务还在不断修改数据，新表可能暂时落后，不能承诺完成某一轮校验后就永远一致。

### 2.10 历史迁移中 update_time 与来源 version 的取舍

以下四个问题集中说明为什么评估来源版本，以及这种改造的成本和限制。统一来源版本仅为候选方案；当前仍采用 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的时间戳规则。各链路共同保障最终一致性的条件，见[候选方案 2.9](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:254>)，该设计尚未确认采用。

#### 2.10.1 历史迁移用 update_time 比较有什么问题

**前提：目标已有记录，但不同状态保存了相同时间。**

时间戳相等不能证明业务状态相同；毫秒精度只能降低碰撞概率，不能保证每次更新都产生不同时间。以下用同一时序对比两种方案，版本值仅用于后面的候选分析，不表示旧表已有 version 字段。具体时间是假设，不代表项目字段精度或回查耗时。

1. **迁移读取，暂未写入。**旧表为“异常（未确认）、10:00:00.123”，候选来源版本为 1；新表也已有该异常记录。
2. **回查得到成功。**旧表更新为成功，保存时间仍为 10:00:00.123；候选来源版本随变更增至 2。新表尚未更新，仍为异常。
3. **双写实际更新已有目标。**新表成为“成功、10:00:00.123”；候选方案下同时保存来源版本 2。
4. **迁移提交第 1 步的旧快照。**新表已是成功，迁移仍携带异常、相同时间及候选版本 1。

按参考文章允许时间相等覆盖的规则，第 4 步可能把成功回退成异常；终态为失败时同理。即使原子执行条件更新，也无法消除比较值相等的歧义。规则来源见[参考文章 01_1：相等时间允许覆盖（第 89 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

若改成严格大于，旧快照会被拒绝；但反过来，目标是异常、来源已成功且时间相等，真正的新状态也会被拒绝。仅调整等号不能同时解决两个方向的问题。

**前提：时间不可比，或者比较与写入分开。**

这两类属于 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的实现前提未满足。例如旧状态在 10:05 迁入并错误记录为落库时间，就可能拒绝业务时间为 10:04 的较新终态；不同机器的时钟偏差也可能颠倒时间顺序。又如迁移先判断 10:04 比目标 10:00 新，双写随后更新目标到 10:05，迁移再无条件写入 10:04，仍会覆盖新状态。项目时间来源和原子写入方式尚待核实。

#### 2.10.2 用 version 比较能解决这些问题吗

**前提：使用统一来源版本，原子执行比较和写入。**

来源版本就是当前主写表记录的 version，用来表示同一条记录的变更先后。旧表每次实际修改记录数据，都在同一次原子更新中将该记录的 version 递增；双写、迁移、补偿和校验携带与数据配套的版本，新表保存已接收的来源版本。它与 [006 2.2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:60>) 的新表本地 version 职责不同。

**同一时序的处理结果**

两种方案都要判断快照是否过期；差别在于相同时间不能区分变更先后，而正确维护的来源版本可以。

**update_time 比较：**[候选方案 2.10.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:274>) 第 4 步的时间与目标相等，按当前规则允许覆盖，成功状态可能回退。

**来源 version 比较：**要求来源版本更大才更新，迁移的 1 小于目标的 2，因此拒绝旧写入。反过来，目标为异常、版本 1，来源为成功、版本 2，就能补齐终态。

来源版本不依赖物理时钟，能避免单纯时钟偏差造成的先后误判。但它不会自动让写入原子化；先查版本再无条件更新，仍有同类并发窗口。

#### 2.10.3 是否有必要改成根据 version 比较

**判断依据是防回退要求和改造范围。**

若要求新表已经收到较新状态后，迟到快照不得将它回退，当前时间戳规则不够，建议优先评估统一来源版本，并让全部相关写入路径遵守同一协议。来源版本不是唯一可能的并发控制方法。

若接受短暂差异、希望控制旧表改造范围，可继续评估时间戳加校验，但必须明确同时间戳差异如何修复、迟到任务如何停止干扰，并验证收敛条件。不能仅因存在校验任务就认定实现安全。

项目异常回查一般在 1 天内得到成功或失败终态，因此重点关注仍可能变更的记录及其在途双写、补偿和修复；已稳定且不再修改的历史记录风险较低。这不是严格一天截止，也不能证明时间戳碰撞不存在。

采用来源版本需改造旧表和相关更新入口，设计存量初始化、发布兼容，以及主写切换后的版本归属和对新表本地版本机制的替换及与 ES 的衔接。当前时间戳方案与候选统一版本方案分别说明；候选方案已明确双写前给旧表新增 version 并初始化为 1，但整套方案尚未确认采用。详见[目标与前提](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:23>)、[最终一致性条件](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:254>)。

#### 2.10.4 用 version 比较还会有什么问题

**有的修改没有正确维护版本，就无法据此判断新旧。**

某个入口将异常改为成功却漏增版本，两种状态仍同为版本 1；先读取旧异常数据、再单独读取新版本 2，则会给旧数据配上新版本。所有相关入口都必须维护版本，业务字段与版本必须来自同一份读取结果。

**同版本内容不同：严格大于会漏掉修复。**

同版本同内容可作为重复处理；若目标已是版本 2，但某字段写错，仅接受更大版本就会一直跳过差异。需要重新读取权威来源，并在并发保护下修复，不能直接放开同版本无条件覆盖；候选修复协议见 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:186>)，具体实现尚未验证。

**目标缺失：仅比较版本，不能补齐漏写。**

以下反例假设双写只执行 UPDATE，没有按同步方法处理记录缺失。它说明版本字段本身的限制，不是本候选方案的完整写入流程。

1. 迁移读取旧表“异常、来源版本 1”，新表无记录，暂未插入。
2. 回查将旧表更新为“成功、来源版本 2”，新表仍无记录。
3. 双写执行 UPDATE，影响 0 行，成功状态和版本 2 都未保存；这不等于 SQL 一定报错，也不代表同步成功。
4. 迁移按缺失插入“异常、版本 1”。目标没有版本 2，无法仅靠版本比较拒绝旧状态。
5. 仍需补偿或校验发现差异，读取旧表终态并补齐；版本比较本身不会触发漏写发现。

**记录被删除或扫描遗漏时，版本字段本身无法解决。**

物理删除会同时删除行内版本，迟到快照可能重新插入已删除的旧记录，需要通过 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>) 的持续校验清理。游标越过后才提交等导致的扫描遗漏，也不会因记录有版本就自动补齐。

### 2.11 ES 同版本修复：候选版本方案的独立边界

本候选方案修复同版本内容差异时，不递增新表 version。例如新表原为“异常、版本 2”，修复后成为“成功、版本 2”；若 ES 已保存异常、版本 2，且只接受严格更大的版本，这次修复就无法写入 ES。

需要单独设计受保护的 ES 修复机制。不能简单允许所有同版本消息覆盖，否则迟到的错误内容可能再次覆盖修复结果。新旧表一致与 ES 一致应分别验证。

## 5 异议与分析

### 5.1 version 只能参与并发判断，不能单独保证最终一致性

**前提：**候选方案中，同一记录的版本由当前主写方维护，数据和版本配套传递；目标存在时，通过原子版本比较阻止低版本覆盖。该机制有明确适用范围，不能扩展成“有版本就必然一致”。

**判断：**同步失败的数据仍需可靠重试；漏扫记录仍需完整校验；物理删除会带走行内版本，迟到快照仍可能重新插入。主写切换后若仍错误地以旧表为准，版本比较也不能纠正修复方向。

**项目处理：**版本比较负责阻止旧数据覆盖已有的新数据；已保存的同步任务、重试和校验负责补齐遗漏、修正差异及清理多余记录。切写时还要确定以哪张表为准，以及旧任务何时退出。上述机制全部满足条件，才有最终收敛的依据，不能将候选设计当作生产保证。详见[候选方案 2.9](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:254>)、[006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)、[006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)。
