## 1 面试口述精炼版本

**目标：切写前后共用同一个新表写入方法**

这套候选方案要让双写、失败重试、迁移和校验共同保证最终一致性，同时让双写阶段和切写后都调用 writeNewRecord，执行同一套新表写入逻辑。

**先生成数据和版本，再交给统一方法保存**

切写前，旧表业务修改与 version+1 一起提交，将本次完整数据和版本交给 writeNewRecord。切写后，在新表事务内锁住记录，完成业务判断，生成当前版本加 1 的数据，再调用同一个 writeNewRecord，最后提交事务。写入方法始终比较并保存传入版本，不自行生成版本。

**版本防回退，重试和校验补遗漏**

新表缺失就插入，传入版本更大才更新；相同版本和内容视为已写入，同版本差异由受保护的校验修复处理。旧表主写期间，失败通过 MQ 重试，完整校验补齐漏发消息及其他差异。最终一致仍依赖故障恢复和修复成功，切写前要追平并停止旧方向任务。详见 2.3 的统一规则、2.8 的切写流程和 2.9 的收敛条件；整套方案仍为候选设计。

## 2 详细方案

### 2.1 改造目标、适用阶段与准备工作

**目标一：多个任务同时处理同一条记录，最终数据仍然一致。**

双写、写入失败重试、历史迁移和一致性校验可能同时处理同一条记录。目标是补齐漏写、修正差异，并防止迟到的旧数据覆盖新表已经收到的较新状态。业务先写旧表、再同步新表期间，新表可以暂时落后；等该记录的最新变更同步成功后，两边的业务数据和 version 应一致。切写后旧表若不再接收新变更，则不要求它继续与新表保持一致。

**目标二：切写前后调用同一个新表写入方法，执行相同逻辑。**

业务处理层先确定本次完整数据和 version，再调用统一的 writeNewRecord 保存。切写前以旧表提交结果为来源，切写后在新表事务及行锁保护下生成下一版本；新表写入方法不随阶段切换。切写仍需处理在途写入和旧任务交接。

**谁维护版本：切写前由旧表负责，切写后由新表负责。**

新旧表各只维护一个 version。旧表主写期间，旧表产生版本，新表的统一写入方法复制对应的数据和版本，不独立递增。新表接管主写后，由业务处理层在新表事务内生成下一 version，再调用统一方法保存，已有版本不重置。[006 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:41>) 的本地版本方案与本候选方案分开说明；切换时的任务交接见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)。

**实施顺序：先准备版本，再开启双写，最后迁移存量。**

- **旧表初始化（本候选方案已明确的前提）**：开启双写前，给旧表新增 version 字段，将存量记录初始化为 1，并确保所有修改入口在实际修改数据时，让数据修改和 version + 1 一起成功或一起失败，不能只改数据、不改版本。
- **新表起点与执行顺序（已确认）**：开启双写前，新表为空；先开启双写，再执行历史迁移。新表首次写入记录时，同时保存旧表快照中的业务数据及 version，后续写入按 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:77>) 的统一规则处理。历史迁移开始时，新表可能已有双写写入的记录，仍需比较版本，避免迁移的旧快照覆盖较新数据。

### 2.2 旧表主写期间：修改旧表数据并递增旧表版本

**旧表主写期间：旧表产生变更和版本。**

旧表主写期间，新增记录时 version=1。**每次修改一条旧表记录的数据，都要同时将该记录的 version 加 1。数据修改和版本递增应在同一次原子更新中完成，一起成功或一起失败。** 所有修改入口，包括人工修数，都必须遵守这条规则。

例如旧表从“异常、版本 1”更新为“成功、版本 2”，新表同步后也是“成功、版本 2”。新表保存旧表传来的版本，不自行加一。

**旧表并发更新：使用本次读取的旧表版本**

下面的 SQL 适用于读取后可能有其他写入修改同一记录的情况。expected_version 是本次修改前从旧表读取到的 version，由应用保存并作为更新参数传入，不是新增字段，也不是另行生成的版本号。例如读到 version=3，就传入 expected_version=3；更新时旧表仍为版本 3 才能修改成功，并将版本加到 4。下面先查询，再执行条件更新；版本比较、业务数据修改和版本加 1 在同一条 UPDATE 中完成。以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准；SQL 仅为 MySQL 8.0.33 的核心条件示例，表名、字段名和命名参数均作示意，不是现有代码或完整实现。

~~~sql
-- 1. 读取本次要修改的旧表记录；实际查询应包含业务判断所需字段。
SELECT status, version
FROM old_record
WHERE serial_no = :serial_no;

-- 2. 应用保存查询结果中的 version，作为后续 UPDATE 的 expected_version。
-- 例如读取到 version=3，则绑定 :expected_version=3。
-- 记录不存在时应单独处理，不继续执行下面的更新。

-- 3. 业务判断通过后，带着刚才读到的版本执行更新。
-- 前提：业务状态转换合法；实际更新须包含相应状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

**旧表更新影响 0 行：重新查询旧表并判断原因**

查询和更新之间，记录可能被其他操作修改。例如旧表已从版本 3 变为 4，本次携带 expected_version=3 的 UPDATE 就影响 0 行，应重新读取并判断，不能去掉版本条件强行覆盖。影响 0 行也可能是记录已删除或其他业务条件不满足，需要结合重新查询的结果处理。

### 2.3 新表统一写入方法：切写前后均比较并保存传入版本

本节示例仅说明处理规则，标识和版本均为示意，不代表生产记录；示例中未展开的其他同步字段，按所述相同或差异前提处理。

**新表入参：完整业务数据与版本必须配套**

切写前，调用方传入同一次读取取得的旧表业务标识、路由信息、全部同步字段和 version。切写后，调用方传入新表事务内生成的完整业务结果和下一版本。同一个版本必须对应确定的数据内容，不能先读到“异常”，再单独读到版本 2，就把它们拼成“异常、版本 2”发送。

**入参示例（切写前）：** 旧表 S1 当前为“成功、版本 2”，本次读取同时取得商户 M1、业务标识 S1、全部同步字段和版本 2。调用方将这份快照传给新表；若目标缺失，新表插入完整数据及版本 2，而不是把先前读取的异常状态与版本 2 拼在一起。

**新表记录定位：按 merchantNo 路由，按 serialNo 匹配**

按 merchantNo 找到记录所在的分表，用 serialNo 判断新旧表中哪些记录对应同一笔交易。serialNo 全局唯一，删除后也不重复使用。新表第一次插入时生成自己的 consumeId，以后更新继续使用它，不把旧表 id 当作新表主键。

**定位示例：** 旧表记录的 merchantNo=M1、serialNo=S1、id=100。写新表时先按 M1 路由，再查 S1；目标缺失则插入并生成新表 consumeId，例如 900。以后 S1 更新到更高版本时仍修改这条 consumeId=900 的记录，旧表 id=100 不作为新表主键。

**新表写入职责：保存调用方提供的数据和版本**

双写阶段和切写后都调用 writeNewRecord(recordSnapshot)。recordSnapshot 包含业务标识、路由信息、完整业务字段和本次 version。

- **业务处理层**：读取当前主写表、完成业务判断，确定本次数据和版本。切写前以旧表为准；切写后在新表事务及行锁保护下计算下一版本。
- **统一写入方法**：按 2.3 的规则比较新表现有版本，保存传入的数据和版本。切写前后代码及判断规则不变，方法内部不自行执行 version+1。

例如切写前传入旧表已提交的“成功、版本 8”，方法保存版本 8；切写后业务处理层锁定新表版本 8，生成合法业务变更及版本 9，仍由这个方法保存版本 9。同版本错误内容的校验修复属于专门修复流程，不是切写时切换的新表业务写入入口。

**职责示例（切写后）：** 业务处理层在新表事务内锁住 S1，读到“异常、版本 8”，回查确认成功后生成“成功、版本 9”。writeNewRecord 接收这份结果，将新表写成版本 9；业务处理层负责生成 9，写入方法负责保存 9，不再把它加成 10。

**统一入口：双写、切写后业务和同步任务共用规则**

双写、重试、迁移、校验补齐以及切写后业务都调用 writeNewRecord。下文“传入版本”指调用方提供的完整数据中的 version，“目标版本”指新表当前保存的 version。切写前传入旧表快照，切写后传入事务内生成的业务结果。此处讨论完整记录的插入与更新；旧表主写期间的物理删除另见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

1. **目标不存在：插入。** 版本直接取传入值，首次收到版本 5 就插入版本 5。如果另一个任务已经插入了同一业务记录，导致唯一键冲突，就重新读取新表并比较版本；其他约束或 SQL 错误仍按失败处理。

   **示例：** 切写前，新表没有 S1，迁移传入旧表“成功、版本 5”，新表直接插入版本 5。若插入时唯一键冲突，重新查询发现另一任务已插入相同数据和版本 5，则按重复结果结束；若已有版本 6，则保留版本 6。

2. **传入版本更大：更新。** 在同一次更新中写入全部需要同步的字段，并将新表 version 设置为传入值。传入的是版本 3 的完整数据时，可以直接把版本 1 更新到 3；如果传入的只是“金额加 10”这种操作指令，就不能跳过中间操作。

   **示例：** 新表已有“异常、版本 1”，补偿传入旧表已提交的“成功、版本 3”完整快照。原子更新后，新表成为“成功、版本 3”，无需先补版本 2；因为保存的是最终字段值，而不是漏执行的增量操作。

3. **传入版本更小：跳过。** 不修改业务字段或版本。

   **示例：** 新表已是“成功、版本 3”，迟到的迁移快照为“异常、版本 1”。版本 1 小于 3，跳过，新表仍为“成功、版本 3”。

4. **版本相同、内容相同：已经同步，不再修改。** 不更新、不加版本。

   **示例：** 新表已保存 S1 的版本 3 全部数据，MQ 又投递同一份版本 3 快照。版本与全部同步字段均相同，判定已同步，新表数据和 version 都保持不变。

5. **版本相同、内容不同：标记差异，交给校验修复。** 进入 [候选方案 2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:192>) 的修复流程：锁定新表记录、重新核对后再改，不能忽略差异，也不能直接覆盖。

   **示例（旧表主写期间）：** 旧表为“成功、版本 3”，新表却是“异常、版本 3”。统一方法报告差异；校验重新读取旧表并锁住新表，确认目标仍为版本 3 后将状态修正为成功，版本保持 3。若目标已到更高版本，就放弃这份旧快照。


~~~sql
-- 已按 merchantNo 路由到实际分表。
-- 实际 SET 应包含全部同步字段，此处仅展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

**原子更新：比较与写入一起完成**

上面的 SQL 将版本比较和更新合为一个数据库操作，避免“判断时可以更新，真正写入时目标却已变新”的窗口。影响 0 行不能直接视为同步成功：需要读取目标，区分记录缺失、版本更高、同版本同内容或同版本内容不同，再按上述分支处理。目标缺失时尝试插入，遇到并发插入的唯一键冲突后重新比较。

**并发示例：** 新表已有版本 1，迁移任务准备写版本 2；写入前，双写先把新表更新为版本 3。迁移执行带 version < 2 条件的 UPDATE，影响 0 行，重新读取发现目标为版本 3，跳过旧快照，新表保留版本 3。若目标原本就不存在，UPDATE 同样可能影响 0 行，但应进入插入分支，不能判定已同步。

**版本推进：内容相同也要接收更高版本**

即使可见业务字段恰好相同，收到更大版本也要把新表 version 更新为这个版本。更新时间作为普通同步字段保留，不再负责本候选方案的新旧排序。

**版本推进示例：** 假设某个允许修正的同步字段先从 A 改为 B，再改回 A，旧表版本依次为 1、2、3，版本 3 的全部同步字段恰好与版本 1 相同。新表仍停在版本 1，收到版本 3 时也必须保存 version=3；这样迟到的版本 2 才会被拒绝，字段保留 A。本例仅说明允许修正字段的版本顺序，不表示终态可以回退为异常。

### 2.4 切写前双写：旧表提交后，新表接收数据和版本

**执行顺序：先提交旧表，再同步新表**

旧表业务提交后，调用统一写入方法写新表；失败时将完整快照和 version 发送到 MQ，后续继续补偿。快照应在旧表业务事务内取得，确保数据与版本对应，事务提交后才能发送。

**完整校验兜底漏发消息。**

例如旧表提交“成功、版本 2”后，进程在写新表、发送 MQ 前崩溃，这次变化没有进入队列，需要完整一致性校验发现并补齐。MQ 发送失败时应重试、告警；仍未进入队列的遗漏也由完整校验兜底。恢复时间取决于校验周期，不能承诺实时一致。

### 2.5 切写前补偿：重试将旧表已提交的数据写入新表

**重试原则：复制旧表已提交的数据和版本**

本节针对旧表主写期间的同步失败。写新表失败后，MQ 消费者用原数据和 version 调用同一个统一写入方法，不增加两边版本：目标缺失就插入，版本落后就更新，已是相同版本和内容就结束；旧事件已被更高版本替代，也可以结束。

**示例：旧消息晚到，不覆盖终态。**

1. 旧表创建“异常、版本 1”，写新表失败，版本 1 进入补偿队列，新表无记录。
2. 回查得到成功，旧表更新为“成功、版本 2”；本次双写通过缺失插入，新表成为“成功、版本 2”。
3. 版本 1 的补偿随后到达，发现新表已有版本 2，跳过旧数据。
4. 如果版本 2 再次重试，新表版本和内容均相同，也不重复修改。

**完成条件：确认结果后再结束任务**

只有目标写入已提交、已同步或已被更高版本替代，才能确认消息处理完成。同版本内容不同，须修复或可靠登记为待修复任务；仍然失败的任务继续重试，长期失败告警处理，不能直接丢弃。

### 2.6 切写前迁移：分批读取旧表，写入新表后保存进度

**迁移流程：分批处理，成功后保存游标**

开始扫描前确定最大 ID，分批读取旧表完整数据和 version，调用统一写入方法。本批全部处理完成后才保存游标；失败后从上次已确认完成的位置继续。重新查询旧表时，使用本次读到的数据，不默认沿用上次缓存。

**恢复示例：进度未保存可能导致重复处理**

例如游标为 100，ID 101～200 已写入新表，但保存游标前进程崩溃，恢复后会再次读取这批记录。统一写入方法根据版本和内容识别重复，不会插入两份，也不会让旧快照覆盖更高版本。若从已确认完成的游标之后恢复，则不会重复此前已完成的批次。

**进度约束：不能跳过未处理的失败**

同版本差异须先修复，或可靠登记为待修复任务，才能推进进度；不能越过尚未处理的失败记录。迁移旧快照晚到时，版本比较规则与上一节的补偿示例相同。

### 2.7 旧表主写期间的校验：以旧表为准补齐和修正新表

**校验步骤：先检查存在性，再比较版本和内容**

分批读取两边的 serialNo，合并去重后回查当前记录，比较存在性、版本和全部同步字段：

- 旧表有、新表缺失或版本落后：重新读取旧表完整快照，调用统一写入方法补齐。
- 版本和内容相同：通过。
- 版本相同、内容不同：按下面的流程修复。
- 新表版本更高：重查旧表主库，排除读取时序差异；仍异常则调查错误写入，不能直接降低版本。
- 新表有、旧表没有：重新查询旧表主库确认不存在后物理删除新表记录；查询失败不能当成不存在。

**同版本差异的修复。**

例如旧表是“成功、版本 2”，新表错误保存为“异常、版本 2”：重新读取旧表快照，在新表事务内用 SELECT ... FOR UPDATE 锁住目标，再核对版本。目标仍为版本 2 才修复内容，version 保持 2；已到更高版本就放弃旧快照。若目标缺失或版本更低，按同步规则处理。提交后复核，失败重试。

**删除处理：持续清理迟到写入的多余记录**

项目使用物理删除，serialNo 删除后不复用。迟到快照仍可能重新插入已删除记录，因此需要持续扫描两边，在迟到任务处理完后再次清理、复核多余记录。详见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

### 2.8 切写后：基于新表生成下一版本，再调用统一写入方法

**交接前提：追平数据，停止旧方向写入和修复**

按 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>) 完成切换。新表开始产生业务版本前，要处理旧表在途写入和积压补偿、确认追平，并停止旧表主写及旧方向迁移、校验修复，避免旧任务继续修改或删除新表数据。

**新表业务更新：业务处理层在同一事务内锁定、计算并写入**

1. 开启新表事务，按业务标识执行 SELECT ... FOR UPDATE，锁定当前记录。
2. 业务处理层读取新表当前业务字段和 version，检查状态转换是否合法，在内存中生成修改后的完整数据及下一版本；此时尚未更新数据库。
3. 业务处理层调用 writeNewRecord，将这份数据和版本写入新表；该方法必须加入当前事务，使用同一数据库连接，不能另开独立事务或异步写入。
4. 确认本次更新实际成功后提交。失败则回滚，不把跳过旧版本或同版本冲突当成本次业务修改成功。

例如锁内读到“异常、版本 8”，回查确认成功，就生成“成功、版本 9”并传入统一方法。另一个并发业务请求必须等锁释放，重新读取版本和状态再判断，不能在锁外提前生成另一份版本 9。

**新表主写期间的新增与重试：版本 1 配合唯一键**

新业务记录从版本 1 开始，并以业务唯一键防止重复插入。业务新增遇到已存在记录时要核对结果，不能将不同内容的冲突当成成功。事务明确回滚后，重新读取并执行业务判断；提交结果不确定时先核实结果，不能把尚未提交的候选快照直接当成旧表已提交的补偿事件重放。具体业务重试识别仍需实现验证。

**职责边界：写入代码相同，数据来源随主写路由改变**

切写前后均调用同一个 writeNewRecord，执行同一套版本比较与保存 SQL。改变的是调用前读取哪张主表、如何产生本次版本；版本生成和保存必须在上述事务保护下衔接。切写后旧表不再接收新变更，就不再要求它持续与新表一致。

### 2.9 最终一致性：版本防回退，重试和校验补遗漏

**收敛过程：补齐最新版本，拒绝迟到旧版本**

以旧表最终停在“成功、版本 8”、记录未删除为例：双写或重试可以将它同步到新表；即使漏发 MQ，完整校验也应发现并修复差异。新表收到版本 8 后，迟到的版本 1～7 无法覆盖它，重复的版本 8 不再修改，因此两边最终追平。

**成立条件：故障恢复、完整校验和修复成功**

这个结论要求故障最终恢复、完整校验覆盖全部记录、差异修复成功，且所有写入遵守版本规则。业务持续变更期间允许暂时落后。物理删除后的迟到写入需要持续清理；错误高版本不能靠普通同步自动纠正，应调查并受控修数。ES 同版本修复也需要独立验证。

### 2.10 ES 同版本修复：候选版本方案的独立边界

**问题示例：表内修复可能无法同步到 ES**

本候选方案修复同版本内容差异时，不递增新表 version。例如新表原为“异常、版本 2”，修复后成为“成功、版本 2”；若 ES 已保存异常、版本 2，且只接受严格更大的版本，这次修复就无法写入 ES。

**处理边界：ES 修复需要独立设计和验证**

需要单独设计受保护的 ES 修复机制。不能简单允许所有同版本消息覆盖，否则迟到的错误内容可能再次覆盖修复结果。新旧表一致与 ES 一致应分别验证。
