## 1 面试口述精炼版本

**版本判断新旧，可靠同步补齐遗漏**

候选方案中新旧表各只有一个 version。旧表主写时递增版本，新表同步方法复制数据和版本；低版本跳过，同版本差异受保护修复。四条链路共用同步规则，可靠事件和重试负责补齐遗漏。

**业务方法与同步方法分开**

新表业务方法负责业务修改及版本递增，切写后沿用已有版本；同步方法不自行递增。最终一致仍依赖完整校验、故障恢复和主写交接，删除及 ES 修复另有边界。方案尚未采用，运行效果未验证。详见 [候选方案 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:92>)。

## 2 详细方案

### 2.1 历史迁移中 update_time 与来源 version 的取舍

以下四个问题讨论来源新旧判断。统一来源版本仅为候选方案；当前仍采用 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的时间戳规则。各链路如何维护版本及追平数据，见[候选方案 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:92>)，该设计尚未确认采用。

#### 2.1.1 历史迁移用 update_time 比较有什么问题

**前提：目标已有记录，但不同状态保存了相同时间。**

时间戳相等不能证明业务状态相同；毫秒精度只能降低碰撞概率，不能保证每次更新都产生不同时间。以下用同一时序对比两种方案，版本值仅用于后面的候选分析，不表示旧表已有 version 字段。具体时间是假设，不代表项目字段精度或回查耗时。

1. **迁移读取，暂未写入。**旧表为“异常（未确认）、10:00:00.123”，候选来源版本为 1；新表也已有该异常记录。
2. **回查得到成功。**旧表更新为成功，保存时间仍为 10:00:00.123；候选来源版本随变更增至 2。新表尚未更新，仍为异常。
3. **双写实际更新已有目标。**新表成为“成功、10:00:00.123”；候选方案下同时保存来源版本 2。
4. **迁移提交第 1 步的旧快照。**新表已是成功，迁移仍携带异常、相同时间及候选版本 1。

按参考文章允许时间相等覆盖的规则，第 4 步可能把成功回退成异常；终态为失败时同理。即使原子执行条件更新，也无法消除比较值相等的歧义。规则来源见[参考文章 01_1：相等时间允许覆盖（第 89 行）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表 + 数据迁移_参考文章_01_1.md:89>)。

若改成严格大于，旧快照会被拒绝；但反过来，目标是异常、来源已成功且时间相等，真正的新状态也会被拒绝。仅调整等号不能同时解决两个方向的问题。

**前提：时间不可比，或者比较与写入分开。**

这两类属于 [006 2.2.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:43>) 的实现前提未满足。例如旧状态在 10:05 迁入并错误记录为落库时间，就可能拒绝业务时间为 10:04 的较新终态；不同机器的时钟偏差也可能颠倒时间顺序。又如迁移先判断 10:04 比目标 10:00 新，双写随后更新目标到 10:05，迁移再无条件写入 10:04，仍会覆盖新状态。项目时间来源和原子写入方式尚待核实。

#### 2.1.2 用 version 比较能解决这些问题吗

**前提：使用统一来源版本，原子执行比较和写入。**

来源版本是同一条记录在权威来源中的变更序号。旧表每次实际修改记录数据，都在同一次原子更新中将该记录的 version 递增；双写、迁移、补偿和校验携带与数据配套的版本，新表保存已接收的来源版本。它与 [006 2.2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:60>) 的新表本地 version 职责不同。

**同一时序的处理结果**

两种方案都要判断快照是否过期；差别在于相同时间不能区分变更先后，而正确维护的来源版本可以。

**update_time 比较：**[候选方案 2.1.1](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:23>) 第 4 步的时间与目标相等，按当前规则允许覆盖，成功状态可能回退。

**来源 version 比较：**要求来源版本更大才更新，迁移的 1 小于目标的 2，因此拒绝旧写入。反过来，目标为异常、版本 1，来源为成功、版本 2，就能补齐终态。

来源版本不依赖物理时钟，能避免单纯时钟偏差造成的先后误判。但它不会自动让写入原子化；先查版本再无条件更新，仍有同类并发窗口。

#### 2.1.3 是否有必要改成根据 version 比较

**判断依据是防回退要求和改造范围。**

若要求新表已经收到较新状态后，迟到快照不得将它回退，当前时间戳规则不够，建议优先评估统一来源版本，并让全部相关写入路径遵守同一协议。来源版本不是唯一可能的并发控制方法。

若接受短暂差异、希望控制旧表改造范围，可继续评估时间戳加校验，但必须明确同时间戳差异如何修复、迟到任务如何停止干扰，并验证收敛条件。不能仅因存在校验任务就认定实现安全。

项目异常回查一般在 1 天内得到成功或失败终态，因此重点关注仍可能变更的记录及其在途双写、补偿和修复；已稳定且不再修改的历史记录风险较低。这不是严格一天截止，也不能证明时间戳碰撞不存在。

采用来源版本需改造旧表和相关更新入口，设计存量初始化、发布兼容，以及主写切换后的版本归属和对新表本地版本机制的替换及与 ES 的衔接。当前时间戳方案与候选统一版本方案分别说明；候选方案已明确双写前给旧表新增 version 并初始化为 1，但整套方案尚未确认采用。

#### 2.1.4 用 version 比较还会有什么问题

**维护协议不完整：版本不再代表数据新旧。**

某个入口将异常改为成功却漏增版本，两种状态仍同为版本 1；先读取旧异常数据、再单独读取新版本 2，则会给旧数据配上新版本。所有相关入口都必须维护版本，业务字段与版本必须来自同一份读取结果。

**同版本内容不同：严格大于会漏掉修复。**

同版本同内容可作为重复处理；若目标已是版本 2，但某字段写错，仅接受更大版本就会一直跳过差异。需要重新读取权威来源，并在并发保护下修复，不能直接放开同版本无条件覆盖；候选修复协议见 [候选方案 2.2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:267>)，具体实现尚未验证。

**目标缺失：没有较新版本可供比较。**

1. 迁移读取旧表“异常、来源版本 1”，新表无记录，暂未插入。
2. 回查将旧表更新为“成功、来源版本 2”，新表仍无记录。
3. 双写执行 UPDATE，影响 0 行，成功状态和版本 2 都未保存；这不等于 SQL 一定报错，也不代表同步成功。
4. 迁移按缺失插入“异常、版本 1”。目标没有版本 2，无法仅靠版本比较拒绝旧状态。
5. 仍需补偿或校验发现差异，读取旧表终态并补齐；版本比较本身不会触发漏写发现。

**删除或漏扫：行内版本不能覆盖这些边界。**

物理删除会同时删除行内版本，迟到快照可能重新插入已删除的旧记录，需要通过 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>) 的持续校验清理。游标越过后才提交等导致的扫描遗漏，也不会因记录有版本就自动补齐。

### 2.2 候选方案：双写、失败重试、历史迁移与校验修正的最终一致性（尚未确认采用）

**状态与来源：本节是本次对话提出的候选实现方案，用户已确认记录目标和设计约束，尚未确认正式采用。不是参考文章原方案，也不是已实现或经过运行验证的项目能力。当前时间戳方案见 [006 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:41>)。**

本节按三个问题展开：先说明版本由谁维护、新表如何判断是否接受数据；再说明双写、重试、迁移和校验分别如何使用这些规则；最后说明它们在什么条件下能让数据最终一致。

#### 2.2.1 先明确目标和实施前提

**目标：四条链路交叉执行，最终仍能得到正确结果。**

双写、写入失败重试、历史迁移和一致性校验可能同时处理同一条记录。目标是补齐漏写、修正差异，并防止迟到的旧数据覆盖新表已经收到的较新状态。同步过程中允许暂时落后；追平后，新旧表的业务数据和 version 应一致。

**适用前提：旧表仍是主写来源。**

新旧表各只维护一个 version，不增加 source_version。旧表主写期间，旧表产生版本，新表的同步方法复制对应的数据和版本，不独立递增。新表接管主写后，由其业务方法继续维护同一个 version，已有版本不重置。[006 2.2](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:41>) 的本地版本方案与本候选方案分开说明；切换时的任务交接见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)。

**实施顺序：先准备版本，再开启双写，最后迁移存量。**

- **旧表初始化（本候选方案已明确的前提）**：开启双写前，给旧表新增 version 字段，将存量记录初始化为 1，并确保所有修改入口在实际修改数据时，将数据修改与 version + 1 原子完成。
- **新表起点与执行顺序（已确认）**：开启双写前，新表为空；先开启双写，再执行历史迁移。新表首次写入记录时，同时保存旧表快照中的业务数据及 version，后续写入按 [候选方案 2.2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:170>) 的统一规则处理。历史迁移开始时，新表可能已有双写写入的记录，仍需比较版本，避免迁移的旧快照覆盖较新数据。

#### 2.2.2 分开业务方法与同步方法，明确版本由谁维护

**旧表主写期间：旧表产生变更和版本。**

旧表主写期间，新增记录时 version=1；每次实际修改记录的数据，业务修改与 version+1 在同一事务中原子完成。所有修改入口，包括人工修数，都必须遵守这条规则。新表直接保存旧表传来的版本，不自行加一。

例如旧表从“异常、版本 1”更新为“成功、版本 2”，新表同步后也是“成功、版本 2”。version 表示这条记录的变更先后，不是同步任务执行了多少次。重复请求应先判断是否已经处理，不能仅因重试再次修改业务和递增版本。

下面的 SQL 展示“检查预期版本、修改数据、递增版本”如何一次完成。以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准；SQL 仅为 MySQL 8.0.33 的核心条件示例，表名、字段名和命名参数均作示意，不是现有代码或完整实现。

~~~sql
-- 前提：业务状态转换合法；实际更新须包含相应状态条件。
UPDATE old_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

版本条件不满足，说明记录可能已被其他操作修改，应重新读取并判断，不能去掉条件强行覆盖。版本判断也不能代替业务状态是否合法的校验。

同步时传递完整快照，即同一次读取取得的业务标识、路由信息、全部同步字段和 version。同一个版本必须对应确定的数据内容，不能先读到“异常”，再单独读到版本 2，就把它们拼成“异常、版本 2”发送。

身份和路由沿用现有项目约束：按 merchantNo 路由，通过全局唯一且删除后不复用的 serialNo 关联同一交易；新表首次创建生成 consumeId，后续沿用，不拿旧表 id 替换新表主键。

**用户自行确认的项目方案：新表业务方法保持不变，同步逻辑独立。**

在本候选设计中，提前实现两类新表写入方法，切写时不临时修改版本维护代码：

- **业务方法**：处理新的业务请求，负责业务校验、重复请求识别及业务数据修改。新增记录时 version=1；修改已有记录时，在同一次原子更新中修改业务字段并执行 version+1。这个职责切写前后保持不变，但旧表主写期间，双写不调用它重复执行业务变更。
- **同步方法**：供双写、失败重试、历史迁移和一致性校验使用，接收旧表的完整数据及 version，按 [候选方案 2.2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:170>) 的条件写入；同版本差异按 [候选方案 2.2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:267>) 修复。它复制已有变更，不再次执行业务动作，也不自行递增版本。

两类方法可以复用路由、数据访问等底层组件，但不能混淆“接收已有版本”和“产生新版本”。例如同步收到“成功、版本 8”，应保存版本 8，不能再调用业务方法把版本增加到 9。

**切写之后：业务路由进入新表业务方法。**

完成主写交接后，新业务请求调用预先准备好的新表业务方法。同步进来的已有记录沿用当前 version；新表首次创建的新业务记录才从 1 开始。以下 SQL 示意新表业务修改如何维护版本，不用于接收旧表快照：

~~~sql
-- 前提：新表已接管业务主写；实际更新须包含合法业务状态条件。
UPDATE new_record
SET status = :new_status,
    version = version + 1
WHERE serial_no = :serial_no
  AND version = :expected_version;
~~~

条件不满足时重新读取并判断，不能无条件修改。业务请求重试也须识别是否已处理，不能仅因重试而再次递增版本。

**示例：同一条记录从同步写入转为业务主写。**

1. 切写前，旧表将某记录改为“异常、版本 8”，双写调用新表同步方法，新表保存相同数据及版本 8。
2. 完成主写交接后，异常回查得到成功，调用新表业务方法。
3. 新表业务方法将状态改为成功，同时把版本从 8 增至 9，不重新初始化，也不等待旧表传来版本 9。

因此，“代码保持一致”指新表业务方法前后不变，不是要求同步方法和业务方法执行同一条更新 SQL。切写仍要切换路由，并处理旧表在途写入、积压补偿和旧方向校验任务；不能让两边同时独立生成版本，也不能继续以落后的旧表修复新表。交接边界见 [006 2.5](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:146>)，具体控制机制仍待实现验证。切写后不再要求已经停止接收新变更的旧表与新表版本持续相同。

#### 2.2.3 统一同步入口：四条链路使用相同规则

下文的“统一入口”专指独立的同步方法，由双写、失败重试、历史迁移和校验修正共同调用，不是新表业务方法。它按同一套规则插入或更新记录。下文“传入版本”指旧表快照携带的 version，“目标版本”指新表当前保存的 version。此处先讨论旧表中仍存在的记录，物理删除另见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

1. **目标不存在：插入。**版本直接取传入值，首次收到版本 5 就插入版本 5。并发插入若发生同一业务唯一键冲突，重新进入已有记录的比较；其他约束或 SQL 错误仍作为失败处理。
2. **传入版本更大：更新。**原子覆盖完整同步字段，并把目标 version 设置为传入值。完整快照可从版本 1 直接追到 3，不适用于必须逐条执行的“金额加 10”等操作指令。
3. **传入版本更小：跳过。**不修改业务字段或版本。
4. **版本相同、内容相同：重复完成。**不更新、不加版本。
5. **版本相同、内容不同：返回差异状态。**进入 [候选方案 2.2.7](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:267>) 的受保护修复，不能忽略，也不能在普通同步中无条件覆盖。

~~~sql
-- 已按 merchantNo 路由到实际分表。
-- 实际 SET 应包含全部同步字段，此处仅展示状态。
UPDATE new_record
SET status = :incoming_status,
    version = :incoming_version
WHERE serial_no = :serial_no
  AND version < :incoming_version;
~~~

上面的 SQL 将版本比较和更新合为一个数据库操作，避免“判断时可以更新，真正写入时目标却已变新”的窗口。影响 0 行不能直接视为同步成功：需要读取目标，区分记录缺失、版本更高、同版本同内容或同版本内容不同，再按上述分支处理。目标缺失时尝试插入，遇到并发插入的唯一键冲突后重新比较。

即使可见业务字段恰好相同，收到更大版本也要推进目标版本。更新时间作为普通同步字段保留，不再负责本候选方案的新旧排序。

#### 2.2.4 双写：及时写新表，同时留下可恢复的同步记录

建议保留旧表提交后的即时双写，同时使用事务发件箱：将待同步事件保存在事件表中，并与旧表业务更新一起提交。这增加的是可靠投递所需的事件记录，不是业务表的第二个版本字段。

以一次状态修改为例，旧表事务内依次完成：

1. 校验业务状态，更新记录并递增 version。
2. 取得本次更新后的完整快照。
3. 保存对应待同步事件。
4. 一起提交；事务回滚时业务修改和事件均不生效。

提交后，业务线程可立即调用新表同步方法；后台持续将已落库事件投递到 MQ，消费者调用同一入口。即时双写与后台投递允许重复，目标按版本和内容去重。

**示例：旧表提交后进程崩溃。**

旧表和事件已提交，但进程尚未写新表、发送 MQ 就崩溃。事件仍在数据库，后台恢复后可以继续投递；只依赖 catch 后发送消息则覆盖不了这个窗口。

这套设计解决的是“旧表已经提交，但同步工作丢失”的问题。下一节再说明事件发送失败、写入失败，以及响应丢失时怎样重试。

长期失败必须保留记录、告警并跟踪处理。事件表投递状态、并发领取、消费确认及失败恢复的具体实现仍需验证；事务发件箱不会自动提供这些能力。

#### 2.2.5 失败重试：重复发送原数据，不生成新版本

消息发送失败时继续发送；发送成功但投递状态未保存时，也允许重发。写入新表失败时，重试仍携带原事件的数据和 version，调用 [候选方案 2.2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:170>) 的统一入口，不增加两边版本。下面三个场景分别说明乱序、漏写和重复处理。

**场景一：较新事件先成功，旧事件重试晚到。**

1. 旧表创建“异常、版本 1”，保存事件 A。
2. A 写新表失败，新表仍无记录。
3. 回查得到成功，旧表变为“成功、版本 2”，保存事件 B。
4. B 先到达，通过缺失插入将新表写成“成功、版本 2”。
5. A 重试，发现 1 小于 2，跳过旧快照并完成任务，新表保留成功。

**场景二：重试时目标仍缺失或版本落后。**

B 携带“成功、版本 2”重试：目标无记录就插入完整快照；目标为“异常、版本 1”就原子更新为“成功、版本 2”。仅执行 UPDATE 并忽略 0 行结果不能补齐缺失记录。

**场景三：写入已经成功，但响应丢失。**

1. B 已将新表写成“成功、版本 2”，调用方却收到超时。
2. B 重试，读取到相同版本和相同内容。
3. 作为重复处理完成，不更新、不增加版本。

**什么时候才能确认消息完成？**

新表写入已提交、目标已是相同版本和相同内容，或者目标已收到更高版本，才可以确认该事件已处理。同版本内容不同，必须完成修复，或可靠移交给可恢复的修复任务后再确认；数据库仍不可用，则保留失败继续重试。不能仅因调用结束或打印了日志就丢弃任务。

#### 2.2.6 历史迁移：搬运完整快照，保护批次进度

迁移读取旧表数据及其 version，复用统一入口，不增加旧表版本。保留固定 ID 上界、分批扫描和断点恢复思路；恢复时重新查询，就使用本次读取的快照，不能默认重放上次缓存。

**先处理数据，再保存批次进度。**

游标记录已确认完成的位置。只有当前批次的记录都处理成功、已是重复结果或已被更高版本取代，才能保存完成进度；同版本差异则须完成修复或可靠登记后续修复任务。不能越过尚未处理的失败记录。

例如持久化游标为 100，当前批次读取 ID 101～200：

1. 新表已成功写入这一批记录。
2. 任务在保存游标 200 前崩溃，持久化游标仍为 100。
3. 恢复后从 101 重新查询旧表，因此会再次处理这一批；使用的是本次查询结果，不是默认沿用上次快照。
4. 统一入口按版本和内容判断，不重复创建记录，也不让低版本覆盖高版本。

批次只写成功一部分后整批重试，也可能再次遇到已成功记录。若从已确认完成的游标之后恢复，则不会重做此前已完成的批次。

**示例：迁移快照晚于业务终态到达。**

1. 迁移读到“异常、版本 1”，暂未写入。
2. 回查将旧表更新为“成功、版本 2”。
3. 双写实际将新表写成“成功、版本 2”，目标可能原本存在，也可能由统一入口补建。
4. 迁移提交版本 1，被版本条件拒绝，新表保留成功。

如果第 3 步失败且新表仍缺失，迁移可能先插入“异常、版本 1”；版本 2 的可靠事件重试或后续校验再将其追平。该结果允许短暂落后，但已写入的较新版本不能被低版本覆盖。

#### 2.2.7 一致性校验：检查存在性、版本与业务内容

校验的职责是发现遗漏和错误，不能只比较 version。以旧表为准，分批读取两边的 serialNo，合并去重后回查当前记录，先检查存在性，再检查版本和全部同步字段。

- **目标缺失或版本落后**：重新读取旧表完整快照，调用统一入口补齐。
- **版本及内容都相同**：通过。
- **版本相同、内容不同**：按下面的行锁流程修复。
- **目标版本更高**：重新从旧表主库读取，排除旧快照或读取时序问题；持续出现则调查版本维护、数据来源或主写归属，不能自动降低目标版本。
- **目标多余**：重新查询旧表主库，确认记录不存在后物理删除新表对应记录，并复核、失败重试；查询失败不能视为不存在。迟到写入后的再次清理见 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>)。

**同版本内容不同：锁住目标，重新核对后修复。**

普通入口只允许更高版本更新，因此同版本的错误内容需要专门修复。行锁使同一新表记录的并发更新依次执行；持锁后还要重新检查版本，避免覆盖已经到达的更高版本。以下以旧表为“成功、版本 2”，新表错误保存为“异常、版本 2”为例：

1. 重新从旧表读取完整的“成功、版本 2”。
2. 开启新表事务，以 SELECT ... FOR UPDATE 锁定对应目标记录，并在锁内重新核对版本、内容。
3. 若目标仍为“异常、版本 2”，修正为成功，version 保持 2。
4. 若目标已到版本 3，放弃当前快照；若缺失或版本更低，转入统一入口的对应分支。
5. 提交后复核，失败时重新读取、重试。

~~~sql
-- 在旧表主库取得完整快照后，进入目标分表事务。
START TRANSACTION;

SELECT status, version
FROM new_record
WHERE serial_no = :serial_no
FOR UPDATE;

-- 应用在锁内确认：记录存在、版本相同、内容不同，才执行此分支。
-- 实际修复包含已核对的全部同步字段；不递增 version。
UPDATE new_record
SET status = :verified_status
WHERE serial_no = :serial_no
  AND version = :verified_version;

COMMIT;
~~~

其他目标更新会与行锁协调，必须等持锁事务结束后再判断写入条件。本机制依赖同一版本对应唯一来源内容；存在绕过旧表版本维护的修数时，不能靠锁补救错误的版本语义。

若来源已推进到版本 3，但目标尚未收到，版本 2 的修复可能暂时成功；版本 3 后续仍可正常推进。记录身份由全局唯一且不复用的 serialNo 确定，版本用于判断同一记录的变更顺序。

#### 2.2.8 最终一致性：既要最终送达，也要防止旧数据覆盖

版本比较只决定“这次数据能不能写”，不会主动找回丢失的数据。可靠事件、重试和完整校验负责把数据最终送到新表，两部分缺一不可。以下以旧表最终停在“成功、版本 8”、且记录未被删除为例：

1. 提交版本 8 时，同步事件一起落库。
2. 后台重试或完整校验最终将“成功、8”送达新表。
3. 目标缺失或版本落后时接受它，同版本内容错误则受保护修复。
4. 迟到的版本 1～7 被拒绝，版本 8 的相同内容重投不改变目标。
5. 复核后两边数据、版本一致；没有违反协议的写入，就不会被迟到任务破坏。

物理删除会同时移除行内版本，迟到快照重新插入后的清理依赖 [006 2.4](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/006_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护.md:121>) 的持续校验；本节的版本比较不能代替删除处理。候选方案下 ES 的同版本修复也需要单独处理，见 [候选方案 2.3](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/999_分库分表_业务双写_双写、补偿、迁移与一致性校验的版本维护_候选方案.md:324>)。

保证成立需要故障最终恢复、任务持续推进、扫描覆盖完整、修复最终成功，以及全部写入遵守协议。永久不可用、持续绕过规则或无人处理的永久失败，不能仅靠版本字段解决。持续变化时允许追赶，不能承诺固定一轮校验后永久一致。

### 2.3 ES 同版本修复：候选版本方案的独立边界

本候选方案修复同版本内容差异时，不递增新表 version。例如新表原为“异常、版本 2”，修复后成为“成功、版本 2”；若 ES 已保存异常、版本 2，且只接受严格更大的版本，这次修复就无法写入 ES。

需要单独设计受保护的 ES 修复机制。不能简单允许所有同版本消息覆盖，否则迟到的错误内容可能再次覆盖修复结果。新旧表一致与 ES 一致应分别验证。
