## 面试口述精炼版本

**同步调用再确认**：Canal Server 原生 RocketMQ 生产端把 binlog 事件发布到 topic；RocketMQ 消费服务同步逐项调用 ES。任一操作抛出异常就中断当前消息并由 RocketMQ 重投整条消息，已成功的操作不会自动回滚。RocketMQ 发布、Broker 持久化、MQ 消费确认和 ES 处理仍须分别核对，不能把链路状态合并成一个成功标记。

**按消费失败路径重投**：采用并发消费，网络超时、429、5xx、映射错误、索引不存在和定位缺失等异常统一向外抛出，由 RocketMQ 重投当前消息，其他消息可以继续处理。版本冲突须区分重复、过期与异常，避免无意义重试。具体次数、退避、死信、告警和人工修复仍待核验；重试不能消除数据或配置错误，404 不能一概当作成功。

**保留日志供恢复**：未确认发布单元可能重放，稳定 `_id` 不能单独保证幂等，还要保持来源版本稳定并命中原具体索引，由 ES 原子拒绝旧写入。日志不足以证明位点连续时暂停推进；不能取最新位点跳过缺口。Canal 位点、RocketMQ 消费确认和 ES 写入结果属于不同层次，不能混为一个恢复位置。

**覆盖超时和留存边界**：ES 超时不代表请求已取消。旧请求携带正确外部版本、且 ES 仍保留新版本时，会被 ES 拒绝；物理删除后的旧请求仍须单独保护，处理日志不能撤回已发出的请求。MQ 留存须覆盖下游暂停与追赶，不能用 30 天 binlog 目标替代。具体保护与补偿仍待实现验证。

**按验收项恢复**：单机 Server 故障后人工核对本地位点并重启，再分别检查 `db0`、`db1` 的原生 RocketMQ 发布恢复，核对位点、binlog 连续性、RocketMQ 积压和 ES 实际结果；还要覆盖 跨月历史 UPDATE、DELETE、定位缺失、单项异常导致整条消息重投、超时在途请求和死信恢复。上述为待执行要求，不是已完成测试。

## 详细方案

**分清 Canal 批次与 ES 操作数**

MySQL binlog 按序产生事件，Canal Server 解析并由内置 RocketMQ 生产端发布。默认 FlatMessage JSON 按 data/old 解析，二进制封装才按 Entry/RowData 解析；消息可能含多行，但按键分区也可能把一个源 Entry 拆为多个单行 Entry。因此 MQ 消息数不等于 ES 文档数，分区后的消息也不保证完整事务。Canal Server 的发布批量、MQ 消息拆分和 ES 操作数分别评估，不把旧 Adapter 的 `canal.tcp.batch.size` 配置键套成自定义服务参数。

**同步完成后确认**

Canal Server 原生 RocketMQ 生产端可能把一个发布单元拆成多条消息；ES 写入服务并发消费不同消息，每次回调仍逐条同步调用当前消息的操作。任一操作或必要状态保存异常就中断并向外抛出，由 MQ 重试整条消息。前序成功操作不会自动回滚，重试重新经过完整处理流程及既有幂等检查；消息内处理及必要状态保存完成后才正常返回。不能异步提交 ES 任务后立即返回，也不能把异常吞掉当作成功。RocketMQ Spring 2.3.0 的 `CONCURRENTLY` 异常返回 `RECONSUME_LATER`，正常返回 `CONSUME_SUCCESS`；具体次数、死信和恢复行为仍按 client 5.2.0、Broker 和 ES 联调核验。

异常触发当前消息重投，其他消息可以继续并发处理，后续新事件可能先于旧消息的重试完成。每条事件都须携带正确来源版本，命中同一记录可靠绑定的目标物理索引；版本冲突按重复、过期和异常分类处理，必要状态不能被旧重试回退。一条消息内仍逐项同步调用 ES，并完成必要状态保存；任一操作失败都重试整条消息，全部事件处理完成后才能正常返回。并发线程容量、重试积压和中途故障重放仍待验收。

**分清发布、持久化和消费确认**

原生 RocketMQ 模式下，Canal Server 负责把事件发布到 topic；RocketMQ 生产结果、Broker 刷盘与复制、Canal 位点持久化、MQ 消费确认和 ES 写入是不同阶段。007 已按 1.1.7 源码核对内部 getWithoutAck、发送回调与 ack/rollback 路径，不套用独立 TCP 客户端的连接假设；原生生产端没有显式检查 SendResult 是否为 SEND_OK，因此提交回调也不能单独证明可靠交接。非 SEND_OK、部分发送成功、超时结果不明及位点恢复须按实际发行包、Server 内置客户端和 Broker 配置核验。

ES 写入成功而 MQ 消费确认或 Canal 位点未可靠保存时，故障恢复仍可能重复处理。恢复必须保留稳定来源版本并沿用具体物理索引，不能用最新 GTID 跳过未核实的消息缺口。没有其他副作用且同一记录的相同版本对应相同操作和内容时，可以重复请求 ES，不必另设独立 `eventId`；版本冲突仍须核对，不能一律反复重试。

恢复需结合 Server 本地持久化进度、源日志完整性及 ES 结果核验。单机进程故障会同时中断两个通道的采集和发布；本地文件丢失或日志断档时暂停复核，不将初始 GTID 回退待定事项改为自动恢复方案。

**重放时保持顺序和原索引**

未确认批次重放可能再次写入。稳定 `_id` 只能避免同一具体索引中出现第二篇同 ID 文档，不能单独保证重放幂等；同一 `consumeId` 的事件顺序、操作类型与目标具体索引也须正确。增删改及重试须按原始创建时间计算同一月份索引；DELETE 后保留来源顺序与删除标记，搜索未命中不能单独证明不存在。重复写入、删除、版本控制、故障恢复和确认语义须按最终消费端联调，不能宣称已实现 exactly-once（每个事件恰好处理一次）；[100_ES 文档如何写入与检索.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/100_ES 文档如何写入与检索.md:1>)另有边界。

INSERT/UPDATE/DELETE 均使用新表业务 `version` 规则，MQ 重试沿用原消息数据和版本；不再将 binlog 坐标映射为 ES 整数版本。只有选用坐标事件 ID 时，才须按 007、008 补齐默认消息缺失的坐标和原行序号。Delete API 的版本传递、持久化删除状态、`index.gc_deletes=3h`、索引模板继承和每半小时校验与兜底补偿仍须实现并验证。

业务版本检查还须覆盖在途请求：旧 ES 请求超时后可能继续执行，应用检查和处理日志不能撤回它。Index API、Delete API 都应携带原业务版本规则，结果不明时按原条件核对；发生冲突不能直接换取新条件重发旧载荷。物理删除后的旧创建请求隔离须结合删除状态和 `index.gc_deletes=3h` 验证；每半小时自动校验与兜底补偿发现异常后按数据库当前状态补偿，任务失败或延迟须告警，但自动补偿不能保证整个半小时内始终不复活。

**按最慢链路保留日志并处理缺口**

新库 binlog 保留期与空间须覆盖历史导入、首次同步、故障追赶和两项校验中最长的读取需要；旧库也须覆盖旧表与新表校验。查询切换前连续 2 周无差异不等于 binlog 保留时长，一条链路追平也不能清理其他链路仍需的日志。无法证明恢复位点之后的日志连续时，暂停推进并复核缺口，不能从最新位置重启。校验链路各自的恢复规则见[015_旧表与新表增量校验.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/015_旧表与新表增量校验.md:6>)和[043_ES改造_ES_新表与 ES 增量校验_整体实现.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/043_ES改造_ES_新表与 ES 增量校验_整体实现.md:6>)。

MQ 的消息留存与容量单独核对，需覆盖下游故障、人工修复和积压追赶；消费位点落后不等于消息不会过期。Canal 已推进位点后发生 MQ 消息断档，常规重启不能自动重发缺失范围。应保留现场并复核源日志、发布范围、MQ 缺口和 ES 状态，确认受控重放或补偿方案后再恢复；Broker 留存参数及该流程尚未验证。
