# 001_改造原因
## 1 面试口述精炼版本

**分库分表：控制单表规模，分散单实例压力**

消费记录持续增长后，数据和索引占用不断增加。如果继续集中在单表或单个实例中，读写请求和维护任务也会集中，可能使读写压力上升，备份、加索引等维护成本增加。因此，项目方案将消费记录拆分为多个物理表，并分布到独立的 MySQL 实例，让每个表和实例只承载部分数据、索引及读写请求，从而控制单表规模、分散单实例压力，并让维护范围更可控。该方案不会减少数据总量；查询效果仍取决于查询范围、索引设计和缓存等因素，详见[表变大后的查询与维护影响](<./999_表变大后，为什么范围查询、维护索引和修改表结构可能变慢？.md>)。

**列表查询迁移到 ES：减少与交易写入的资源争用**

后台列表查询和交易写入共用数据库。列表查询压力增大时，会与交易写入争用数据库资源，可能影响交易响应。因此，项目方案将后台列表的过滤、排序和分页迁移到 Elasticsearch（ES），必要的主数据仍由 MySQL 补充，从而减少复杂列表查询对交易数据库资源的占用。MySQL 仍是交易权威数据源，查询细节见[消费记录列表接口处理逻辑](<./999_消费记录列表接口处理逻辑.md>)。
## 2 详细方案

### 2.1 分库分表解决规模和资源集中问题

消费记录持续增长时，单表数据、索引和维护任务会持续扩大。项目方案将记录拆分到多个物理表，并分布到独立的 MySQL 实例，使单表和单个实例只承担部分数据、索引及读写请求，从而控制单表规模并分散资源压力。分表不会减少数据总量，具体查询和维护效果仍取决于查询范围、索引设计、数据分布和资源条件；相关影响见[表变大后的查询与维护影响](<./999_表变大后，为什么范围查询、维护索引和修改表结构可能变慢？.md>)。

### 2.2 ES 承接后台列表查询

后台列表查询与交易写入共用数据库时，复杂过滤、排序和分页可能与交易写入争用资源。项目方案将列表查询的过滤、排序和分页交给 Elasticsearch（ES），再由 MySQL 补充必要的主数据；MySQL 仍是交易权威数据源。列表接口的处理过程见[消费记录列表接口处理逻辑](<./999_消费记录列表接口处理逻辑.md>)。该方案的响应时间、资源占用和切换效果仍需结合验收数据确认。
