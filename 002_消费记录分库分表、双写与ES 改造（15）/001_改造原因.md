# 001_改造原因
## 1 面试口述精炼版本

**控制单表规模，降低单表维护成本**

消费记录按日均新增 20 万条、数据库保留最近 5 年数据进行容量评估。如果一直集中在单表中，数据和索引会持续增大，备份、加索引等维护成本也可能增加。因此，项目将消费记录拆成 32 张物理表，控制每张表的数据和索引规模，让单表维护范围更可控。分表不会减少数据总量，具体收益仍需验证，详见[分库分表解决规模和资源集中问题](#21-分库分表解决规模和资源集中问题)。

**分散单实例的读写和资源压力**

如果这些分表仍放在同一个 MySQL 实例中，读写请求和维护任务仍会集中使用该实例的资源。因此，最终方案采用 2 个 MySQL 实例，每个实例部署 16 张消费记录表，让每个实例承担部分数据、索引和读写请求，分散单实例压力；实际容量和热点情况仍需评估，详见[分库分表解决规模和资源集中问题](#21-分库分表解决规模和资源集中问题)。

**减少无法定位分片时的跨分片查询成本**

分库分表后，如果查询条件不包含用于定位库表的分片键，也无法通过其他条件确定目标分片，就可能需要查询全部 32 张分表，再合并结果；全局排序、分页和总数统计会进一步增加处理成本。因此，项目将消费记录同步到 Elasticsearch（ES），由 ES 承接后台列表检索，减少这类请求对 MySQL 消费记录分表的查询压力。ES 自身也可能跨分片检索，性能收益仍需验证，详见[ES 承接后台列表查询](#22-es-承接后台列表查询)。

**兼顾多条件检索与索引维护成本**

后台查询条件组合多。MySQL 的联合索引由多个字段组成，少量联合索引难以兼顾主要查询；继续增加索引又会占用更多存储，并增加交易写入时的维护成本。这也是将后台列表检索交给 ES 的原因，但不能理解为 MySQL 索引越多，查询必然越慢，详见[ES 承接后台列表查询](#22-es-承接后台列表查询)。

**减少列表查询与交易写入的资源争用**

后台列表查询和交易写入共用数据库，复杂过滤、排序和分页可能与交易写入争用资源，影响交易响应。因此，项目方案由 ES 完成列表过滤、排序和分页，必要的主数据再由 MySQL 补充，减少复杂列表查询对交易数据库资源的占用。实际响应时间和资源占用仍需结合验收数据确认，详见[ES 承接后台列表查询](#22-es-承接后台列表查询)。

**业务接受几秒级延迟，交易结果仍以 MySQL 为准**

项目 ES 刷新间隔为 3 秒。在同步链路没有积压、重试且处理及时的情况下，后台列表预期有几秒级延迟，业务可以接受这一范围，因此具备采用异步检索方案的业务前提。3 秒刷新间隔不保证 3 秒内可查，实际端到端延迟仍需验证；单笔详情及最终交易状态以 MySQL 为准，详见[同步延迟与业务接受边界](#23-同步延迟与业务接受边界)。

## 2 详细方案

### 2.1 分库分表解决规模和资源集中问题

消费记录持续增长时，单表数据、索引和维护任务会持续扩大。以日均新增 20 万条记录、数据库保留最近 5 年的数据为容量评估依据，最终方案将消费记录拆分为 32 张物理表，分布在 2 个 MySQL 实例上，每个实例 16 张表，使单表和单个实例只承担部分数据、索引及读写请求，从而控制单表规模并分散资源压力。分表不会减少数据总量，具体查询和维护效果仍取决于查询范围、索引设计、数据分布和资源条件；相关影响见[表变大后的查询与维护影响](<./999_表变大后，为什么范围查询、维护索引和修改表结构可能变慢？.md>)。

### 2.2 ES 承接后台列表查询

**无法定位分片时，查询和结果合并成本增加**

分片键是用来确定数据所在库表的字段。项目以商户号 `merchantNo` 作为分片键，也设计了从消费记录主键 `consumeId` 解析分片编号的定位方式。因此，不能简单把“不带分片键”等同于“查询全部分片”；只有查询条件无法提供可用的分片定位信息时，才可能需要访问全部 32 张分表。路由设计及实现验证边界见[分库分表](<./003_分库分表.md>)。

例如，仅按消费时间、交易状态和金额组合查询，且这些条件无法用于定位分片时，就需要向多个分片发送查询，再汇总结果。全局排序、分页和总数统计可能需要进一步合并各分片的候选记录或统计值，增加数据库请求、数据传输和结果合并成本；整体响应也容易受到较慢分片的影响。并行执行可以减少部分等待，但不能消除整体资源开销。跨分片查询通常比定位到单个分片的查询成本更高，实际耗时仍取决于查询范围、索引、数据量和并发，不能直接认定一定很慢。

**查询组合多，索引覆盖与维护成本需要取舍**

联合索引由多个字段组成，其使用效果与字段顺序、过滤条件、范围查询和排序要求有关。后台查询条件组合灵活，同一个联合索引未必能兼顾不同查询；应优先覆盖高频、关键查询，而不是为每一种组合都建立索引。

增加合适的索引通常能提升对应查询的速度，但也会占用磁盘和缓存，并增加插入、删除及相关字段更新时的索引维护成本。因此，准确的理由是“少量索引难以兼顾主要查询，继续增加索引又会增加存储和写入维护成本”，不能写成“索引越多，查询必然越慢”。资源争用可能间接影响查询，但需结合实际负载验证。

**将列表检索交给 ES，减少交易数据库的资源争用**

后台列表查询与交易写入共用数据库时，跨分片查询、复杂过滤、排序和分页可能争用数据库资源。项目方案将消费记录同步到 ES，由 ES 完成列表过滤、排序和分页，再由 MySQL 补充必要的主数据，减少列表检索对 MySQL 消费记录分表的查询压力。处理过程及同步延迟边界见[消费记录列表接口处理逻辑](<./999_消费记录列表接口处理逻辑.md>)。

ES 自身也可能跨分片检索，并有索引写入和维护成本，不能认为迁移后就没有跨分片开销或一定更快。引入 ES 还会增加同步链路、数据一致性保障和运维成本。项目后台列表业务可以接受正常情况下的几秒级同步延迟，因此采用该异步检索方案；单笔详情及最终交易状态仍以 MySQL 为准。性能收益、同步延迟是否满足业务要求及查询切换效果，均需结合验收数据确认。

### 2.3 同步延迟与业务接受边界

**3 秒是刷新间隔，不是端到端延迟**

按本次用户确认，项目 ES 的 `refresh_interval`（使新写入数据可被搜索的周期刷新间隔）为 3 秒。既有[原始材料的刷新间隔记录](<./999_003_原内容.md#refresh_interval>)也记录了这一取值；这些依据说明项目采用的设置，不能代替对实际索引配置及运行延迟的核验。

本文的端到端可见延迟，从 MySQL 事务提交开始，到对应记录在 ES 中可被列表查询检索到为止，可近似拆分为：Canal 采集延迟 + RocketMQ 传输及消费等待 + 消费处理与 ES 写入耗时 + 等待刷新可见的时间。它不等同于一次列表接口请求的响应时间。

在持续查询、周期刷新正常执行的情况下，写入 ES 后等待刷新可按约 0～3 秒估算；若写入时刻在刷新周期内均匀分布，平均等待约 1.5 秒。这是理想化的刷新阶段估算，不是端到端平均延迟，也不是严格上限；刷新执行耗时和调度延迟等仍会影响实际可见时间。

**几秒级是条件性估算，具体数值不是实测结果**

仅用于说明计算方法：假设没有消息积压和消费重试，且从 MySQL 提交到 ES 写入完成约耗时 0.2～1 秒，再叠加上述刷新等待，则端到端延迟可粗略估算为约 0.2～4 秒。在写入时刻均匀分布的假设下，平均刷新等待为 1.5 秒；若刷新前链路的平均耗时也处于 0.2～1 秒范围内，则平均总延迟约为 1.7～2.5 秒。

其中 0.2～1 秒是计算示例的假设，没有项目实测依据。因此，当前只能将几秒级作为上述正常条件下的预期，不能承诺“3 秒内一定可查”或“最多 4 秒”。消息积压、消费重试、组件故障及刷新变慢都可能使延迟更长。

**业务接受几秒级延迟，实际达标情况仍需验证**

已确认后台列表业务可以接受同步链路无积压、无重试且处理及时情况下预期的几秒级延迟，单笔详情及最终交易状态仍以 MySQL 为准。业务接受这一延迟范围，不等于实际同步链路已经测得或持续达到该水平，也不代表接受异常情况下任意时长的延迟。

量化验收时，具体秒数上限和达标比例仍需明确，不能将上述估算直接作为硬性承诺。异常情况下允许的延迟和提示方式也需单独明确。之后应测量从 MySQL 提交到 ES 可检索的端到端延迟，覆盖正常负载、峰值及积压恢复场景，记录延迟分布并按约定标准验收，不能仅用平均值证明全部请求达标。

## 3 已确认规则

- 面试口述中的改造原因，每个原因单独一个段落，并用一个简短、具体的加粗小标题概括该原因。
- 以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。
- 最终方案采用 2 个 MySQL 实例，每个实例 16 张消费记录物理表，共 32 张表。
- 容量评估依据为日均新增 20 万条记录，数据库保留最近 5 年的数据。
- 列表查询迁移到 ES 的原因包括无法定位分片时的跨分片查询成本、多条件组合下的索引取舍，以及与交易写入的资源争用。
- ES 刷新间隔为 3 秒；该数值不代表端到端同步延迟，也不代表业务容忍上限。
- 后台列表业务可以接受同步链路无积压、无重试且处理及时情况下预期的几秒级延迟；实际延迟仍需验证。

## 4 待确认或待验证事项

- 分库分表后的容量、热点、查询性能和维护窗口，需要结合专项评估与运行验证确认。
- 列表查询迁移到 ES 后的响应时间、资源占用和切换效果，需要结合主要查询组合、不能定位分片的查询及预期并发进行验证。
- 已确认业务接受正常情况下的几秒级延迟；用于量化验收的具体秒数上限和达标比例仍需明确。
- 异常情况下允许的延迟和提示方式，仍需确认。
- 实际索引的刷新间隔及端到端可见延迟分布，仍需核验；0.2～4 秒和平均 1.7～2.5 秒均为条件性估算，不是实测结果。
