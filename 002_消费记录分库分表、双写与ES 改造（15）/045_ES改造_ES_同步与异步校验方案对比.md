# 045_ES改造_ES_同步与异步校验方案对比

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

> 本文档是主文档“043_ES改造_ES_新表与 ES 增量校验总览”的拆分考点。共同已确认规则、完整待确认事项和异议分析以主文档为准；本文件只维护本考点的口述内容和详细方案。

## 1 面试口述精炼版本

校验消费者组先可靠保存完整事务批次，再延迟回查 MySQL 和 ES 的当前状态，比较版本和约定字段。并发变化或暂时差异需要重读复核，持续差异交给独立补偿；正常到期 DELETE 按规则跳过 ES 删除，但异常删除不能直接忽略。整批完成后才能推进进度，采集和恢复能力仍待验证。

## 2 详细方案

### 2.1 选定方案的处理流程

```text
增量校验消费者组读取 RocketMQ Topic 中的新库 Binlog 消息
→ 固定完整事务批次，提取新增、更新及 DELETE 事件涉及的对象
→ 延迟回查 MySQL 和对应月份的 ES 当前文档
→ 比较业务版本及约定字段
→ 暂时差异延后复核，持续差异交独立补偿
→ 按 MySQL 当前数据和版本补偿后重查
→ 整批完成后可靠推进校验进度
```

**第一步：保存每个实例的独立基线。** 历史导入前，DBA 为新库 A、新库 B 分别保存完整 GTID 集合、实例身份和采集时间，用于初始化独立校验订阅。历史验收后集合标记历史范围终点，不能替换导入前起点。GTID 是已提交事务的全局标识，不能简化为最大事务号，也不能合并两个实例的集合。历史导入及修复须产生可读取的 ROW binlog。

**第二步：可靠保存完整事务批次。** 每批保存来源实例、起止 GTID 集合、完整事务范围和待校验对象。从新增、更新及 DELETE 行事件提取 `consumeId`、原始 `create_time` 和实际库表位置，确保能回查正确分片。字段缺失保留异常，不用空值定位，也不丢弃对象。不得在事务中间截断并推进完成进度。

校验使用独立 consumer group、消费位点与校验进度，不能只检查 ES 同步消费者报告成功的记录，否则同步链路漏掉的对象可能同样不被检查。已可靠接收消息与整批校验通过是两件事：若消费确认早于比较完成，须先可靠保存可恢复的事务批次和对象；校验消费者位点推进不能替代校验完成进度。控制表与 Canal 位点衔接待实现验证。

**第三步：按操作类型确定是否比较。** 新增、更新进入后续校验。能够按已确认的正常到期清理规则识别的 DELETE，记录为按规则跳过，不查询并删除 ES 文档；它仍计入所在事务批次的处理状态。混合事务继续检查其余新增、更新；只有这类到期 DELETE 的批次完成跳过记录后，也可正常推进。无法确认属于正常到期清理的 DELETE 不能直接跳过，应保留为异常处理。跳过不是“已证明两端数据相同”。

**第四步：等待后读取两端当前状态。** 按对象实际库表和主键回查 MySQL，同次读取当前业务字段、`version` 和原始 `create_time`，再按创建月份定位 `records-yyyy.MM`，以 `consumeId` 查询 ES 文档及版本。Binlog 行值用于定位，不直接作为最终比较快照。当前设计至少等待一分钟，具体调度与延迟仍待验证；等待不能证明同步已追平。

**第五步：比较、复核及独立补偿。** 按 [2.2 数据比较与并发复核](#22-数据比较与并发复核) 区分正常一致、并发变化、持续差异和查询异常；按 [2.3 补偿、到期清理与长期监控](#23-补偿到期清理与长期监控) 执行独立修复并复核。不能因为请求成功、消息消费完成或一个等待周期结束就判定数据一致。

**第六步：整批完成后推进。** 全部需比较对象通过，且已确认正常到期清理的 DELETE 跳过对象已记录处理原因后，可靠提交本批完成状态和校验进度。部分通过不推进整批，未完成批次不能被最新 GTID 覆盖。后续发生的变更仍进入后续批次，不能因本批查到了较新状态就直接跳过后续日志范围。

**第七步：按可靠状态恢复。** 重启恢复原基线、事务范围、未完成对象及独立进度，先检查日志连续、事务完整和位点可信。所需日志过期或覆盖范围无法核实时暂停处理并核对缺口，不能跳到最新位点或重置基线后宣称恢复成功。

各实例导入前到验收后的相关事务全部按本规则完成，才算覆盖历史范围；一次比较通过不能替代历史回放完成确认。基线采集依据见 [999_历史迁移与数据库验收](<./999_历史迁移与数据库验收.md>)，整批推进和独立修复见 [999_增量校验总览与差异处理](<999_增量校验总览与差异处理.md>)。不另设周期性五年全量扫描，也不为校验停写；日志未涉及的额外 ES 文档不属于本任务的完整覆盖承诺。

### 2.2 数据比较与并发复核

**先确认字段契约。** 按完整映射比较业务字段，核对 `consumeId` 与 `_id`。现有 [999_ES Mapping 设计](<999_ES Mapping 设计.md>)记录 Mapping 有 17 个字段，完整字段契约仍待核验；不能直接等同于新表完整结构。ES 外部版本元数据不会自动写入 `_source.version`，版本读取方式及是否保存该字段仍须确认，不擅自扩充 Mapping 或删减验收字段。

**先判断查询是否成功。** 超时、连接失败、分片失败或结果不完整属于执行异常，不能当作不存在。索引不存在须核对目标索引与生命周期状态，不能直接当普通缺失文档补写。

| 比较结果 | 处理方式 |
|---|---|
| 业务版本和约定字段一致 | 本次对象检查通过 |
| ES 版本高于本次读取的 MySQL 版本 | 重新读取 MySQL 并复核；不能拿旧数据覆盖 ES，持续异常保留差异 |
| ES 文档缺失或版本落后 | 等待后重读两端，持续不一致再进入独立补偿 |
| 相同版本但业务字段不同 | 记录异常并重新核对字段映射和两端状态，不能当重复消息忽略 |
| MySQL 回查不存在 | 核实是否正常到期清理；确认后按不再需要同步处理，不删除 ES，无法解释则保留异常 |

并发示例：校验先读 MySQL 的版本 5，业务随后更新到版本 6 并同步 ES；此时读取 ES 得到版本 6，与刚读出的旧快照不同。两端读取不是同一快照，固定等待窗口不能阻止读取后发生更新；Binlog 触发也无法消除这种差异。持续变化的对象延后复核，未完成状态必须保存。

### 2.3 补偿、到期清理与长期监控

**按当前数据独立补偿。** 校验只读取业务数据并记录结果，修复由独立流程执行。补偿重新读取 MySQL 同一行的当前业务数据和版本，按原始创建时间定位索引，使用既定 `version_type=external` 写入。并发导致版本冲突时重新核对当前状态，不能将所有冲突直接视为补偿成功。

相同版本但内容不同，普通 external 写入会拒绝相同版本，不能靠原消息重投自动修复，也不能擅自改成无版本覆盖、切换版本策略或伪造更大版本。该异常的受控修复流程待确认。版本规则依据见 [旧数据覆盖与 Redis 锁](<./039_ES改造_ES_旧数据覆盖与 Redis 锁.md>)。

**复核后关闭差异。** 写入请求成功不等于校验通过；补偿后重新读取两端并比较，仍有差异或执行异常就保留批次。若使用搜索接口，还须考虑 refresh 后的搜索可见性，不能混用不同读取接口的可见性语义。

**正常到期差异与 ILM 分工。** MySQL 到期删除后 ES 暂时保留文档是预期行为，不执行 ES Delete API。只有确认属于正常到期清理，才不作为普通差异；不能把所有“ES 有、MySQL 无”都归为正常。ILM 是否成功删除过期索引单独监控，增量任务追平不能证明 ILM 清理成功。

查询切换及旧表下线后，新表到 ES 的同步和本校验长期保留。监控未完成批次、进度延迟、查询失败、持续差异、补偿失败和恢复状态。原材料的每半小时执行一次作为待核验调度参数保留；它与首次比较的等待时长是两个概念，不代表差异一定在半小时内消除。
