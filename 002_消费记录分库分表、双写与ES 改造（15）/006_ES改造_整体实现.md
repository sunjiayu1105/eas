## 面试口述精炼版本

### 整体概括

本方案把新分表已提交的增删改异步同步到 Elasticsearch（ES）：MySQL 将变更记入 binlog（二进制日志），Canal Server 读取并解析，再通过自带的消息发送功能把变更发送到 RocketMQ，最后由自定义消费服务写入 ES。RocketMQ 暂存变更消息，ES 处理较慢时，消息可以先排队等待，从而缓冲两边的速度差异；采集端与写入端通过消息交接，Canal Server 不必等待每次 ES 写入完成，两端由此解耦。

为了提高吞吐量，消费服务采用并发消费，但同一记录的消息可能乱序完成，旧变更就可能晚于新变更写入。因此，每条事件需要携带新表业务 `version`，由 ES 在写入时原子比较，拒绝旧写入。新增、更新通过携带 `version_type=external` 的 Index API 写入完整文档，删除通过 Delete API 携带同一版本规则执行。这个比较只在同一物理索引、同一 `_id`（文档标识）内生效，所以还要可靠确定文档所在的索引，重放和更新删除都继续使用根据原始创建时间计算的同一物理索引。历史导入版本为 `1`，更新与业务字段在同一条 SQL 中递增，重试保持原值。项目按原始 `create_time` 和统一业务时区计算月份索引，增删改及重试都操作同一索引，并通过删除状态和定时校验处理物理删除后的旧请求；自动校验与兜底补偿任务每半小时执行一次，`index.gc_deletes` 设计值为 `3h`，任务失败或延迟须告警。客户端实现、索引模板继承、删除保护和故障场景仍待验证。

消费服务确认 ES 写入成功后，才能向 RocketMQ 确认这条消息已处理完成。不同消息可以并发处理，一条消息内仍逐项同步处理：需要生效的变更完成 ES 操作，重复或过期事件核实后按幂等规则处理，也就是重复处理仍得到正确结果；再保存必要状态，全部完成才让监听方法正常返回。中途出现未解决的异常，就向外抛出运行时异常，由 RocketMQ 重投整条消息。前面成功的操作不会自动回滚，因此重投必须继续使用根据原始创建时间计算的同一物理索引和原版本，避免重复处理改变正确结果；具体重试、死信和恢复仍待核验。

由于写入是异步的，MySQL 与 ES 允许存在延迟，方案目标是最终一致。ES 写入成功后，相关分片还须 refresh（刷新），变更才对搜索可见；搜索可见也不能证明与源库数据一致，所以另有独立校验发现差异，并按源库当前状态补偿。消费完成、搜索可见和校验通过分别判断，最终一致的效果仍须验收。

## 详细方案

### 总链路与职责

同步对象是新分表已提交的新增、修改和删除。两个独立 MySQL 实例各有 16 张分表，通过 ROW 格式 binlog（按行记录变更）提供行数据；历史导入前分别保存 GTID（全局事务标识）基线，即当时已执行事务的完整集合，作为首次起点。历史导入本身也须进入 binlog，才能从该基线覆盖导入和后续变更。日志条件、基线采集和可追赶窗口由 006 说明。

Canal Server 以 MySQL 复制客户端的方式读取日志，按库表过滤并解析变更，再通过自带的消息发送功能向 RocketMQ 发布消息。一个单机 Server 进程承载 db0、db1 两个 destination（同步通道），各自维护源库、配置和进度；发布时按稳定业务键选择队列，具体字段、队列映射及重试后的路由与来源顺序仍须核验。Server 配置与发布、位点恢复由 007 说明。

RocketMQ 暂存变更消息，ES 处理较慢时先排队等待，以此缓冲两边的处理速度差异；Canal Server 与消费服务通过消息交接，采集端不必等待每次 ES 写入完成，以此解耦日志采集与 ES 处理。积压仍受队列容量和消息保留时间限制，下游暂停、修复和追赶所需的窗口须按实际 Broker 核验。

自定义 RocketMQ 消费与 ES 写入服务接到消息后，解析行数据及其业务 `version`，再确定目标物理索引。不同消息并发处理可能使旧事件晚完成，因此新增、更新通过携带 `version_type=external` 的 Index API 写入完整文档，由 ES 原子拒绝旧版本；删除通过 Delete API 携带同一版本规则执行。比较只在同一索引、同一 `_id` 内生效，新增、更新和删除均按原始 `create_time` 计算目标月份索引，再执行对应操作。原始创建时间计算索引和删除状态用于处理跨月重放和物理删除后的旧请求；自动校验与兜底补偿任务每半小时运行一次，任务失败或延迟须告警。核对每项结果并保存必要状态后，才允许整条消息正常返回。业务版本的初始化、递增、消息传递、索引模板配置、删除保护与故障恢复仍待验证，完整 binlog 坐标不是生成该版本的前置条件。

### 自然月索引与跨月增删改

新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。例如 10 月 31 日创建的记录写入 `records-2026.10`，11 月更新或删除仍操作该索引。历史导入不能把导入时间当成原始创建时间，删除消息须保留删除前的创建时间。缺失时进入受控修复，不能用当前时间猜测月份。

`records-read` 覆盖各月份索引，仅用于跨月查询。提前配置匹配 `records-*` 的模板，统一字段映射、配置和读别名；配置及权限允许时，首次 Index 写入触发自动创建，ES 不会每月主动建索引。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后进入 cold；冷热迁移不改变索引名，也不等于只读。生命周期实现及容量边界见 017、018。

业务时区、创建时间实际列名及传递、7 天修改窗口是否为硬限制、历史删除范围、重试与乱序恢复仍需核验。按月定位不替代业务版本或删除保护；索引清理后的旧消息重放须防止误建已过期索引。

### 重复处理与一致性边界

可靠投递以“至少一次”为设计目标，即事件可能重复，但不能漏掉应处理的变更。重试、部分发送成功或确认失败都可能造成重放；存在重复风险并不能证明已经满足至少一次保证。007 已记录 Canal Server 自带的消息发送功能未显式检查发送状态的风险，实际发行包、Broker（MQ 服务端）的持久化与留存，以及恢复流程均须验证。

消息可能重复，也可能乱序完成，因此需要分别处理“同一事件再次执行”和“旧事件晚于新事件执行”。幂等是重复处理仍得到正确结果；防旧写则要求晚到的旧事件不能覆盖新结果。项目优先评估稳定来源版本与 ES 外部版本控制，在可靠绑定的目标物理索引内让 ES 原子拒绝相同或更低版本，随后核对冲突是重复、过期还是异常。允许重复请求 ES 且没有其他副作用时，可以不额外使用独立 `eventId`，但同版本必须对应同操作同内容；需要事件级去重时，再采用“业务主键 + 来源版本”或独立事件 ID。物理删除后的版本保留有限，已发出的旧请求又不能被应用检查撤回，因此删除保护须单独实现验证，不能由前述版本比较推导出已永久防止复活。

MQ 消费确认采用参考文章的整条消息重投模型：每次回调逐条同步调用 ES，操作或必要状态保存出现未解决的异常，就中断并向外抛出运行时异常，由 MQ 重投原消息。此前成功的操作不自动回滚，所以重投必须继续使用根据原始创建时间计算的同一物理索引、原版本并经过幂等流程。已核实的重复或过期冲突，可以按既定规则完成处理及状态恢复，再继续消息中的其余事件；只有整条消息全部处理及必要状态保存完成，监听方法才能正常返回。这样区分了“当前请求是否再次写入”和“该事件是否已正确处理”，避免把正常重复当作持续失败，也避免漏处理剩余事件。不采用 Bulk 单项失败分类和状态驱动的恢复流程，具体重试、死信和恢复仍按 009 及实际发行包核验。

正常返回只表示本条消息按消费规则处理完成；ES 中的变更还须在相关分片 refresh（刷新）后才对搜索可见。搜索可见只说明可以检索到相应状态，不能证明源库与 ES 在规定范围内一致，因此两项增量校验各自独立比较并维护进度，差异由补偿流程处理。自动校验与兜底补偿任务每半小时执行一次，失败或延迟超过预期须告警；物理删除异常最多可能在一个校验周期内短暂复活，自动补偿属于事后修复。补偿同样须遵守既定业务版本和索引定位规则，不能无版本覆盖；补偿须读取相互对应的当前业务数据与 `version`。同步负责写入，校验负责比较，具体分工和验收条件见 009、011、018。

### 各层进度与恢复范围

采集、发布和消费分别推进，恢复时须先确定事件在哪一层完成可靠交接，再核对该层之后的数据是否仍可读取：

| 层次 | 需要核对的进度或结果 | 恢复依赖 |
| --- | --- | --- |
| MySQL | 导入前基线、各读取通道的可靠起点 | 所需 binlog 连续且未被清理；30 天是项目保留目标 |
| Canal Server | 发布结果、内部确认与本地持久化位点 | 位点和源日志对应，已发送但未确认的部分可能重放 |
| RocketMQ | 消息留存范围、各队列消费位点 | 所需消息仍在，留存与容量覆盖下游暂停、修复和追赶 |
| ES 写入服务 | 原索引路由、事件状态、ES 实际结果 | 重复与旧事件保护，也须覆盖结果不明的在途请求 |

binlog 保留 30 天不等于 MQ 也保留 30 天，MQ 消费落后也不能假定会阻止消息清理。若事件已可靠交给 MQ，Canal 位点已推进，而 MQ 中未消费消息又过期，常规重启不能自动补回缺口；应暂停复核可重放范围和补偿方案，不能直接回退位点或跳到最新位置。Broker 留存参数、实际可读范围、容量及补偿流程尚未验证。
