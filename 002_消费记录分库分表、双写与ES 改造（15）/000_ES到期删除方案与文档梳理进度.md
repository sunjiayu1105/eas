# 000_ES到期删除方案与文档梳理进度

更新时间：2026-10-24。本文记录讨论与文档处理进度，不作为功能实现或生产验收证明。

## 1 最初目标与已确认规则

最初目标是：采用“MySQL 到期 DELETE 不同步到 ES、ES 由 ILM 删除整月索引”后，逐项调整 ES 写入链路文档，清理重复或不再适用的删除设计，并明确消息、版本、同步、校验和生命周期各自的职责。

- 新库新表只保留近五年数据，新增、更新同步到 ES；MySQL 到期 DELETE 不执行 ES Delete API。
- ES 按自然月索引，由 ILM 删除整个过期月份索引；前后端查询只允许近五年，精确到日。
- 月份索引由自动任务在上一个月提前创建；历史导入所需索引在导入前单独准备。创建时逐月设置次月 1 日零点（UTC+08:00）的 `origination_date`，绑定适用策略并应用模板。
- 首次创建失败后再重试 3 次，仍失败则告警；后台提供手动启动入口，任务代码异常时由运维手动创建。重复执行须核对已有索引配置，创建成功且配置核对通过才算准备完成。
- 消费者使用单条 Index 请求，不创建索引，不增加索引缺失专门恢复分支；写入失败统一处理并保留重试能力，不能当作消费成功。限制普通 Index 请求自动创建目标月份索引。
- delete 从所属月份次月月初起算 `1830d`，达到期限后允许整索引删除，实际执行可以延后，不允许提前删除仍在五年查询保留范围内的数据。
- 本轮只确认查询范围和日期精度，不确认具体日期下界计算或边界样例；这些详细方案内容不阻塞后续核对。
- 不考虑提前删除；业务通常三个月内确定，但系统没有强制禁止后续修改。
- 正常增量、基于 MySQL 的历史回放和修复，均同步新库新表中的新增、更新数据。
- 业务版本和 ES 外部版本控制仍负责防止新增、更新及其消息重投乱序；消息重投不是独立业务操作类型。
- 新表与 ES 校验采用 Binlog 收集变更，延迟回查两端当前状态，再复核与补偿。校验进度独立于同步消费进度。
- 进度说明直接描述采用的做法，省略未采用的措施。
- 逐项核对、逐项修改，不一次性扩大处理范围；后续事项按依赖顺序排列，说明先确定什么才能确定下一项；Markdown 一级标题与文件名保持一致。

以下涉及技术的内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。
