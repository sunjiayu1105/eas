# 004_业务双写

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 面试口述精炼版本

以下说明已确认的双写方案；事务边界、请求重试和差异修复的实际实现仍需核验，不能据此认定一致性已经得到运行验证。

**为什么要双写**

双写是为了让系统从旧表平稳迁移到分库分表后的新表。过渡期间，旧表继续承接业务，新表同时接收真实业务写入，通过新旧表一致性校验，验证新表写入链路是否正确。如果发现差异，要先定位原因；涉及代码问题的，先修复并验证，再手工订正新表数据，避免靠补数掩盖写入缺陷。确认新表链路稳定并满足后续收尾条件后，再切换为新表单写。

另一个原因是分库分表和后台列表查询迁移到 ES 适合分期优化：先通过双写验证新表和 ES 链路，再逐步切换查询。如果同一期同时完成分库分表、业务改造和后台查询迁移，改动范围和工作量都会过大，增加上线风险。

**恢复写入前，全部修改入口纳入双写**

历史数据迁移并验收通过后，在停写期间完成所有修改旧表入口的双写改造，并上线同步和校验链路，再恢复业务写入。新增、更新和删除等操作都要有对应的新表写入，不能只改部分接口，否则遗漏入口仍只修改旧表，就会产生数据差异。这里要求的是恢复写入时全部入口已经就绪，不是所有服务必须在同一秒部署；实际入口覆盖情况仍需核验，详见[双写的启用与数据定位](#21-双写的启用与数据定位)。

**查询先保留旧表，校验通过后逐步切换**

双写初期，查询继续使用旧表。旧表与新表、新表与 ES 的数据写入校验连续 1 个月无差异后，再逐步将业务查询切换到新表、后台列表查询切换到 ES。查询切换期间继续双写和校验，并保留旧表查询回退的条件；满足最终收尾条件后才改为新表单写，详见[停止双写后的业务行为](#26-停止双写后的业务行为)。

**先提交旧表，再尝试新表**

业务请求先写旧表，确认旧表事务提交成功后，再按商户号路由到新表写入。旧表明确提交失败时，请求失败，不继续写新表；旧表提交成功后，即使新表写入失败，接口仍按成功处理。两次写入不是一个原子事务，新表失败不能回滚已经提交的旧表，因此还需要独立校验发现差异，详见[写入顺序与接口结果](#22-写入顺序与接口结果)。

**写新表时同步维护业务版本**

只有新表增加业务版本号 `version`。历史导入初始化为 `1`，后续更新在同一条 SQL 中修改业务字段并递增版本，供后续 ES 同步判断数据新旧。删除后重新导入时 `version` 重新初始化为 `1`，消息重试沿用原消息的数据和版本，详见[新表版本维护与重试边界](#23-新表版本维护与重试边界)。


**新表提交后异步同步 ES**

新表提交后的新增、更新通过 binlog（二进制日志）、Canal 和 RocketMQ 交给消费服务写入 ES。接口返回成功不代表新表一定写入成功，也不代表 ES 已可搜索；旧表与新表、新表与 ES 分别需要校验，详见[业务双写与 ES 同步的边界](#25-业务双写与-es-同步的边界)。

**满足收尾条件后改为新表单写**

全部旧表业务和查询依赖切换完成后，继续双写，并让旧表与新表、新表与 ES 两项校验持续覆盖应检查范围。再次连续 3 个月无差异后，关闭旧表写入，改成新表单写，停止旧表与新表校验。此后接口以新表事务提交结果判断成功，新表到 ES 的同步及校验长期保留，详见[停止双写后的业务行为](#26-停止双写后的业务行为)。

## 2 详细方案

### 2.1 双写的启用与数据定位

双写用于历史迁移完成后的过渡阶段。先停写并完成历史导入及数据库验收，再在停写状态下上线双写、新表到 ES 的同步，以及两项增量校验；链路就绪后恢复业务。启用顺序见[002_改造计划](<./002_改造计划.md>)，这里只展开业务请求的写入行为。

恢复业务写入前，应逐项核对所有会修改旧表的入口是否已覆盖对应的新表写入。排查范围包括业务接口，以及实际存在的定时任务、批处理、后台管理和人工脚本等入口，不能只检查在线接口。这些是需要核查的入口类型，不代表项目已确认存在全部类型，也不代表已完成改造验证。所有入口就绪后才能恢复写入；部署可以分步完成，但不能在仍有入口只写旧表时恢复业务。

全部入口覆盖双写是避免遗漏变更的前提，不代表两次写入成为原子事务。即使入口没有遗漏，新表写入仍可能失败，因此还需要持续校验和差异处理。查询不必与写入改造同步切换，可以先保留旧表，达到校验条件后再按 2.6 节逐步切换。

同一笔交易通过不变的交易流水号 `serialNo` 关联新旧记录，商户号 `merchantNo` 在交易生命周期内保持不变。应用沿用 ShardingSphere-JDBC 这一应用侧分片组件，按商户号将新表 SQL 路由到对应实例和物理表。分片和主键设计见[003_分库分表](<./003_分库分表.md>)，本文不重新定义路由规则。

双写覆盖新增、修改、撤销、退货和物理删除。撤销和退货分别新增独立交易记录，撤销记录使用 `tradeType=BS0013`，退货记录使用 `tradeType=BS0024`，并通过关联字段指向原消费记录；原消费记录不直接改成“撤销”或“退货”。保留期清理与业务操作的区别见[到期删除规则](<./013_ES改造_ES_生命周期管理_到期删除.md>)。

### 2.2 写入顺序与接口结果

应用先执行旧表写入，确认旧表事务已经提交，再尝试新表写入。旧表 SQL 执行成功不等于事务已提交；新表异常也不能使已经提交的旧表回滚。该方案允许短暂不一致，后续依赖差异校验和修复收敛，不能描述为跨库原子双写。

| 写入结果 | 接口与后续处理 |
| --- | --- |
| 旧表明确提交失败 | 请求失败，不继续写新表 |
| 旧表提交成功，新表提交成功 | 接口按成功处理；新表变更进入后续同步链路 |
| 旧表提交成功，新表写入失败 | 接口仍按成功处理；记录可取得的失败信息，由独立校验发现差异后交修复流程 |
| 旧表提交结果未知，例如提交响应丢失 | 不能直接判定成功或失败；结果核实、请求重试和新表后续写入策略仍需结合实现确认 |

上述顺序是已确认设计，事务配置、异常传播和接口返回行为仍需结合代码验证。尤其要检查新表异常是否被错误传播成整个业务请求失败，以及旧表提交尚未完成时是否已经执行新表写入。

### 2.3 新表版本维护与重试边界

**业务数据与版本一起更新**

仅新表增加 `version`。历史导入初始化为 `1`；后续更新在同一条 SQL 中修改业务字段并执行 `version = version + 1`，保证这一行的业务数据与版本一起变化。删除后重新导入时 `version` 重新初始化为 `1`。独立修复若修改新表业务数据，也要遵守版本维护规则。

版本用于后续 ES 同步判断来源数据的新旧，具体写入规则见[011_ES改造_ES_索引设计、创建与写入](<./011_ES改造_ES_索引设计、创建与写入.md>)。日常新增的初始值、字段类型和各写入入口的实现仍需核实，不能从历史导入规则直接推定。

**消息重试与业务重试分别处理**

RocketMQ 消息重试沿用原消息的数据和版本，不再次修改新表版本。业务接口重试则可能重新执行数据库写入，必须避免同一请求重复产生业务效果。旧表已经提交但调用方未收到响应时，也可能发生业务重试。

现有材料未提供请求身份识别、同一业务的 `consumeId` 复用，以及并发请求或修复任务交错写入的完整实现。递增 `version` 不能替代业务幂等处理，也不能单独证明新表业务状态正确；这些行为仍需分别验证。

### 2.4 旧表与新表增量校验的职责边界

旧表与新表的变更监听、业务字段比较、差异修复和复核由 005 负责，004 只说明双写产生差异后交由该校验流程处理。`version` 不参与新旧业务字段等值比较，版本初始化、递增、删除后重新导入时 `version` 重新初始化为 `1` 及消息重放稳定性按版本规则单独验证，详见[005_业务双写_旧表与新表增量校验](<./005_业务双写_旧表与新表增量校验.md>)。

### 2.5 业务双写与 ES 同步的边界

业务双写负责旧表与新表的数据库写入；新表提交后，由 ROW 格式 binlog（按行记录变更）向后续同步链路提供数据。新增、更新经 Canal Server、RocketMQ 和自定义消费服务异步写入 ES。ES 文档 `_id` 使用 `consumeId`，业务版本规则和目标索引定位以[011_ES改造_ES_索引设计、创建与写入](<./011_ES改造_ES_索引设计、创建与写入.md>)为准。

数据库到期清理产生的 DELETE 不代表需要向 ES 逐条发送删除请求；按当前保留期方案，ES 由 ILM（索引生命周期管理）删除整个过期月份索引，详见[013_ES改造_ES_生命周期管理_到期删除](<./013_ES改造_ES_生命周期管理_到期删除.md>)。不能将到期清理的处理方式直接推广到未明确的业务删除场景。

双写期间，接口成功只按旧表提交结果判断；它既不能证明新表成功，也不能证明 ES 写入或搜索可见。旧表与新表校验检查双写结果，新表与 ES 校验检查搜索副本，两者不能互相替代。ES 侧校验见[015_ES改造_ES_新表与 ES 增量校验_整体实现](<./015_ES改造_ES_新表与 ES 增量校验_整体实现.md>)。

### 2.6 停止双写后的业务行为

**校验通过后开始切换查询流程**

旧表与新表、新表与 ES 的数据写入校验连续 1 个月无差异后，即可开始切换查询流程：业务查询切换到新表，后台列表查询切换到 ES。仍有旧表依赖或查询需要回退时，继续双写并运行校验；全部旧表依赖切换完成后，再持续观察两项校验连续 3 个月无差异，才进入最终收尾。任务必须持续运行并覆盖应检查范围，停滞或未执行不能算无差异。阶段条件以[002_改造计划](<./002_改造计划.md>)及[ES 验收与查询切换的查询回退、最终关闭旧表写入两节](<./999_ES 验收与查询切换.md>)为依据。

**再关闭旧表写入与查询回退**

满足最终条件后，停止过渡性的旧表与新表增量校验，关闭旧表写入和旧表查询回退。保留旧链路代码或开关不表示旧表仍有最新数据；停止旧表写入后，不能仅切换开关就把旧表作为当前查询结果。

**新表提交成为接口成功依据**

此后业务请求直接沿用原有新表分片写入链路，以新表事务提交结果判断接口成功或失败。新表到 ES 的同步和新表与 ES 校验继续运行，新表提交成功仍不表示 ES 已完成同步或搜索可见。

## 3 已确认规则

- 双写用于平稳迁移并验证未来的新表单写链路；发现差异先定位原因，涉及代码问题的先修复并验证，再手工订正新表数据，不能靠补数掩盖写入缺陷。
- 恢复业务写入前，所有修改旧表的入口必须具备对应的新表写入能力；查询先保留旧表，达到校验条件后逐步切换，切换期间继续双写和校验。
- 本次重新梳理 004，按业务阶段和处理顺序阐述；每个口述主题单独成段，并用简短小标题概括。
- 双写期间先确认旧表提交，再尝试新表写入；旧表明确失败时不写新表，旧表成功后新表失败不改变接口按成功处理的规则。
- 撤销和退货分别新增独立交易记录，分别使用 `BS0013` 和 `BS0024`，通过关联字段指向原消费记录；原消费记录不直接改成撤销或退货。
- 两次写入不构成原子事务；差异由校验发现，交独立流程修复后复核。
- 仅新表增加业务 `version`，历史导入初始化为 `1`，更新时在同一条 SQL 中修改业务字段并递增版本。
- 删除后重新导入时 `version` 重新初始化为 `1`，MQ 重试沿用原消息数据和版本；新旧业务字段比较排除 `version`，版本行为单独验证。
- 旧表与新表、新表与 ES 的数据写入校验连续 1 个月无差异后，开始切换查询流程：业务查询切换到新表，后台列表查询切换到 ES。
- 全部旧表依赖切换完成后，两项校验连续 3 个月无差异，关闭旧表写入，改成新表单写，停止旧表与新表校验；新表到 ES 的同步与校验长期保留。
- 保留此前确认的文档命名调整：Canal Server、自定义消费服务、总链路、MySQL 和 ES 写入检索文档的名称及引用随重命名同步；重命名本身不改变技术结论。

## 4 待确认或待验证事项

以下事项按恢复写入前的检查、双写运行和最终切换的顺序整理。方案要求已明确，不等于实现和运行效果已验证；下列事项仍需结合代码、配置及验收记录逐项核实。

### 4.1 修改入口与分片路由

- 是否已列全修改旧表的实际入口，包括实际存在的定时任务、批处理、后台管理和人工脚本。
- 每个入口是否都已验证对应的新表写入，能够在恢复业务前覆盖全部修改操作。
- 是否存在保留期内的物理删除业务。
- ShardingSphere-JDBC 实际使用的版本是什么。
- 实际路由配置是否符合按商户号定位新表实例和物理表的设计。

### 4.2 事务边界与接口结果

- 是否仅在旧表事务明确提交成功后才执行新表写入。
- 旧表明确提交失败时，是否返回失败且不继续写新表。
- 旧表已提交、新表写入失败时，异常处理是否仍保持接口按成功返回。
- 旧表提交结果未知时，如何核实实际提交结果。
- 核实提交结果后，如何决定业务请求重试和后续新表写入。

### 4.3 请求重试与版本维护

- 如何识别同一业务请求，并避免重试产生重复业务效果。
- 同一业务的 `consumeId` 在重试时能否稳定复用。
- 日常新增记录的 `version` 初始值是什么。
- `version` 的字段类型及可用取值范围是否明确。
- 各实际写入入口是否遵守已确认的版本初始化、递增和消息重试规则。

### 4.4 差异定位与修复

- 差异定位、代码修复与验证、手工数据订正分别由谁负责。
- 手工订正新表数据时，如何确定正确的业务状态和修改依据。
- 并发请求与手工订正交错执行时，如何避免较旧业务状态覆盖较新状态。
- 修复失败或中断后，如何恢复处理并完成复核。

### 4.5 校验覆盖与切换验收

- 旧表与新表、新表与 ES 两项校验是否持续覆盖应检查范围。
- 首次切换查询前，是否具备两项校验连续 1 个月无差异的验收记录。
- 全部旧表依赖切换完成后，是否具备两项校验再次连续 3 个月无差异的验收记录。
- 是否演练过关闭旧表写入、改为新表单写、停止旧表与新表校验的收尾过程。

## 5 异议与分析

**旧表停止写入后的回退边界**

002 的相关表述已同步记录最终收尾前连续 3 个月无差异的条件；004 原文和验收文档明确关闭旧表写入时也关闭旧表查询回退。技术上，停止写入后的旧表不再持续更新，不能仅靠切换查询开关保证数据正确。本文保留查询回退作为过渡期间的处理动作，并在最终收尾时关闭它。

**删除事件的同步范围**

006、009 的部分旧描述仍包含将数据库 DELETE 转为 ES Delete 请求，而 011、013 已记录到期清理不逐条删除 ES、改由 ILM 删除过期索引。本文按到期清理规则明确同步边界；关联文档尚未在本次修改，业务删除的具体映射仍待确认，不能据文档记载认定删除链路已经验证。
