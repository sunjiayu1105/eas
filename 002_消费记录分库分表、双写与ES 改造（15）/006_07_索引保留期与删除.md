# 006_07 索引保留期与删除

## 1 已确认规则

1. MySQL 物理删除仅用于清理创建时间超过 5 年的数据，边界精确到日；不存在业务提前物理删除。
2. ES 索引保留五年，到期后按索引所属数据时间范围删除整个自然月索引，不逐条校验文档的 `create_time`。
3. 撤销通过新增撤销记录表达，业务类型为 `BS0013`，并更新相关交易状态；撤销不等同于保留期物理清理。
4. ES 可以暂时多保留过期数据，但不能提前删除仍在保留范围内的数据。

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 2 面试口述精炼版本

MySQL 按天清理，ES 按自然月分索引，两者删除粒度不同。因此 ES 不能按 MySQL 每天的删除事件逐条删除，而是在整个自然月都满足五年保留条件后，删除该月份索引。查询端限制最近五年，暂时多保留的数据由查询条件屏蔽。

## 3 详细方案

### 3.1 撤销与保留期清理

撤销通过新增撤销记录表达，业务类型为 `BS0013`，并更新相关交易状态；相关业务依据见[项目介绍](<D:/000/sources/eas/000/000_E账通_项目介绍.md:180>)和[消费原内容](<D:/000/sources/eas/000/000_消费_原内容.md:1096>)。MySQL 五年清理产生的物理删除属于保留期清理，不是业务提前删除。

### 3.2 索引级删除

新增和更新继续通过 Canal、RocketMQ 同步到 ES；保留期清理产生的 DELETE 不执行 ES 文档级删除，而由生命周期机制按索引所属数据时间范围删除整个自然月索引。这样可以减少 cold 层历史索引的逐条删除。

### 3.3 为什么要等整个月份过期

假设 MySQL 每天清理“当天零点减 5 年”之前的数据：

| 日期 | MySQL 清理边界 | ES 对 `records-2021.10` 的处理 |
|---|---|---|
| 2026-10-15 | 清理 2021-10-15 零点之前的数据 | 保留，月份内仍有未过期数据 |
| 2026-11-01 | 清理 2021-11-01 零点之前的数据 | 整个月份达到删除条件 |

因此删除资格按整月判断，不能把按日清理边界直接套到索引删除上。

### 3.4 与 MySQL 清理进度的协调

是否只按保留期限判断，还是必须等待 MySQL 实际完成清理，当前仍待确认。ILM 无法感知 MySQL 清理任务是否失败或延迟；如果要求以后者为准，需要增加清理完成状态检查，不能只依赖固定时间配置。

## 4 待确认或待验证事项

- DELETE 事件在哪一层过滤，以及同一消息中的其他事件和状态如何处理。
- ES 删除是否必须等待 MySQL 实际清理完成。
- ILM 五年删除策略、权限、调度和失败恢复。
- 迟到数据、过期消息和已删除月份索引的重建防护。

**已确认规则**：本文只整理五年保留期、撤销边界、索引级删除和 MySQL 协调问题；具体 ILM 删除配置仍待验证。
