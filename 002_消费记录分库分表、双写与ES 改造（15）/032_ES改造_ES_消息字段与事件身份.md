# 032_ES改造_ES_消息字段与事件身份

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 已确认规则

- 消息必须保留业务主键、操作类型、业务 `version`、原始 `create_time` 和操作所需数据。MySQL DELETE 事件保留删除前的 `consumeId` 和原始 `create_time`，用于消息契约、对账或状态判断；该事件不触发 ES 逐条 Delete。
- 消息拆分、重试和重新投递必须保持原事件的版本、数据、操作和来源身份不变。
- 事件级去重是否需要独立 `eventId` 尚待确认；RocketMQ 消息 ID 和 `keys` 不能单独作为稳定源事件身份。

## 2 面试口述精炼版本

**消息字段支撑定位和写入**

按项目设计，消息中的主键标识记录，操作类型区分增删改，业务版本 `version` 判断新增和更新的新旧；消费服务按原始 `create_time` 所属月份确定索引。新增、更新携带变更后的完整数据。MySQL DELETE 事件只保留删除前的主键和创建时间，用于消息契约、对账或状态判断，不同步调用 ES Delete；ES 文档由 ILM 按索引保留策略删除。详见 3.1。

**事件身份识别同一次变更**

主键只能识别记录；可在主键范围明确、同版本只对应同一次操作和内容时，用“主键 + 业务版本”识别变更。拆分、重试和重投须保持版本、操作、数据和来源身份不变。独立 `eventId` 尚未确定，RocketMQ 消息 ID 或 `keys` 不能单独作为稳定事件身份。详见 3.2。

## 3 详细方案

### 3.1 消息字段各自解决什么问题

以下是内部事件的逻辑要求，不代表 Canal 原生消息已经完整提供这些字段。

| 信息 | 用途 | 保持条件 |
|---|---|---|
| 业务主键及必要库表信息 | 识别业务记录及来源；项目以 `consumeId` 作为 ES 文档 `_id` | 明确主键唯一性范围，拆分重试不改变 |
| 操作类型 | 区分新增、更新和删除 | 同一事件重投不能改变操作 |
| 业务 `version` | 比较新增、更新的同一记录的新旧 | 新增、更新取同次变更的行后值；MySQL DELETE 不要求为 ES 逐条删除生成专用删除版本 |
| 原始 `create_time` | 保留业务记录最初创建的时间，供 05 确定所属月份索引 | 更新、拆分、重试和重投不改变；不能用事件发生时间或消息处理时间替换 |
| 行后业务数据 | 组装新增、更新的完整文档 | 是否包含所需字段须验证 |
| 删除前信息 | 保留 `consumeId`、原始 `create_time` 等定位数据 | 删除事件不存在可直接套用的“删除后行数据” |
| 必要来源信息、可选 `eventId` | 追踪来源或标识同一次变更 | 跨重新分批、重投和回放仍稳定 |

新增、更新必须把同一次变更的业务数据与 `version` 一起传递，不能重试时重新查询当前数据，却继续沿用旧事件版本。这里的“行后数据”指该次新增或更新完成后的行数据；它是否包含组装 ES 完整文档所需的字段，仍须核对实际消息及转换逻辑。

消息携带 `version` 只是提供判断新旧的依据，不代表已经完成防旧写。项目设计由消费服务把业务版本作为外部版本随写入请求提交，交给 ES 在同一物理索引、同一 `_id` 内比较；不是仅靠消费端先查后比来保证并发安全。具体请求和保护边界见 [05 新增、更新与外部版本请求](<036_ES改造_ES_物理索引定位与增删改.md>)。

MySQL DELETE 没有删除后行数据，因此保留删除前的 `consumeId` 和原始 `create_time`，用于消息契约、对账或状态判断。项目不把该事件转换为 ES 逐条 Delete；ES 按自然月物理索引由 ILM 统一执行保留期删除，具体见 [07 索引保留期与删除](<038_ES改造_ES_索引保留期与删除.md>)。

项目依据：[自定义消费服务“消息契约与顺序”](<025_ES改造_自定义消费服务_自定义 ES 消费服务处理逻辑.md>)记录了业务版本与数据配对、原始创建时间传递及 JSON/二进制转换要求；[02 业务版本与来源顺序](<033_ES改造_ES_业务版本与来源顺序.md>)说明版本来源；[05 物理索引定位与增删改](<036_ES改造_ES_物理索引定位与增删改.md>)说明 `consumeId` 与月份索引的用途。以上是项目设计记录，本次静态核对不证明字段已端到端传递。

### 3.2 可选事件身份与去重边界

业务主键回答“是哪条记录”，业务版本用于比较同一记录不同变更的新旧，事件身份回答“是否为同一次源数据变更”。例如，同一记录发生两次更新，主键相同，但应能区分两次变更；其中一次更新被重新投递，仍应识别为原来那次变更。这是概念示例，不是运行验证结果。

“业务主键 + 业务版本”只有在主键范围明确、同版本对应同一次操作和同一内容时，才可作为新增或更新事件识别的候选依据。若主键只在某个库表内唯一，识别键就必须包含区分该范围的信息；主键复用或版本重置可能让不同事件得到同一个识别键。MySQL DELETE 不进入 ES 逐条删除分支，其事件身份主要服务于消息契约、对账或状态判断。以上是候选方案的成立条件，不代表事件识别方案已经选定或实现。

采用来源实例与 binlog 行坐标生成 `eventId` 也是候选方案。这里的坐标指源 binlog 文件、事件位置和事件内原始行序号，用来定位某一次行变更；重新分批后的行下标不能代替原始行序号。关联 Server 文档记录了原生 JSON 缺少完整坐标、二进制按键拆行缺少原行序号等边界，不能直接假设拿到消息就能构造稳定事件 ID。采用该方案前，须在拆分导致信息丢失之前补齐来源身份及行级坐标，并验证重放稳定性；本次未独立复核 Canal 源码或实际消息，这些格式边界仍以关联文档记录为依据。

RocketMQ 消息 ID 标识的是消息：一条消息可能包含多个事件，同一事件也可能被重新发布为另一条消息，因此不能单独用它标识源数据中的某次变更。`keys` 是消息查询用的业务键，不自动保证每个源事件都有唯一且稳定的值；例如按业务主键设置时，同一记录的多次变更会使用相同的键。批次 ID 和分批下标依赖本次分批结果，重新分批后也不能保证不变。这里不假定每次消费重试都会改变消息 ID，而是要求身份方案同时覆盖重新发布和重新分批。

独立事件 ID 也不等于已经实现幂等，即同一事件重复处理仍得到正确结果。还需要核对处理状态和执行结果，具体见 [09 重复消息幂等](<040_ES改造_ES_重复消息幂等.md>)。事件身份也不能替代业务版本比较新旧。

依据：Canal Server 原总览（原文档已删除，依据待补充）与 [消费服务的可选去重要求](<025_ES改造_自定义消费服务_自定义 ES 消费服务处理逻辑.md>)。

## 4 待确认或待验证事项

- 原生消息转换后是否保留完整业务主键及行后字段？
- 新增、更新的数据和 `version` 是否始终对应同一次变更？
- 删除前的 `consumeId` 和原始 `create_time` 是否完整传递？
- MySQL DELETE 事件的删除前信息是否完整传递？
- 是否需要独立事件级去重？
- 如采用“业务主键 + 业务版本”识别事件，主键复用或版本重置时如何避免身份碰撞？
- 如采用坐标事件 ID，如何稳定标识来源实例？
- 如采用坐标事件 ID，如何在拆分前保留完整的原始行坐标？
- 同一事件经过拆分、重试和重新投递后，版本、操作、数据与来源身份是否保持一致？

## 5 异议与分析

- **创建时间的对象需要纠正。** 原文将 `create_time` 描述为“事件的原始创建时间”，容易误导读者按本次变更时间定位索引。项目 009 的消息契约与 05 的定位规则明确指向业务记录最初的创建时间，本次据此修正，不改变原有业务规则。
- **MySQL DELETE 不等于 ES 逐条 Delete。** 原文把删除版本和 ES Delete API 放在同一处理链路中，容易误导为消费端要操作已经进入 cold 的索引。按当前项目规则，ES 删除由 ILM 按保留期统一管理；DELETE 事件只保留必要源信息并用于对账或状态判断。
