# 046_ES改造_ES_增量比较、差异处理与恢复

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 主题边界

本文只说明任务落库后的执行过程：如何读取 MySQL 新表和 ES 当前状态、分类结果、补偿、复核、更新单条任务状态和恢复。消息接收与任务持久化见 [045](<./045_ES改造_ES_校验消息接收与任务持久化.md>)。

## 2 面试口述精炼版本

任务到期后，校验器重新读取 MySQL 新表和对应月份的 ES 文档，按业务字段、`consumeId` 和版本比较。读取失败属于执行异常，不能判断为一致或缺失；暂时差异先等待并复核，持续差异交独立补偿。补偿后必须重新读取两端确认，通过后只完成当前任务，不等待其他任务。RocketMQ 消息在对应任务或跳过记录落库后即可确认，不等待校验通过。系统不存在业务主动删除操作，所有 DELETE 均按 MySQL 正常到期清理处理：记录已按规则跳过的原因和事件处理结果，不创建普通 ES 比较任务、不查询 ES，也不调用 ES Delete API。

## 3 当前状态读取与定位

Binlog 行事件只负责定位对象。执行时先根据来源数据库实例、实际物理数据库和实际物理表确定 MySQL 新表所在分片，再使用 `consumeId` 回查当前记录，同时读取当前 `version`、业务字段和原始 `create_time`；再按 `create_time` 定位 `records-yyyy.MM`，以 `consumeId` 查询 ES 文档及其版本。两端不是同一事务快照，读取后仍可能发生新变更，因此需要版本判断和复核。

## 4 比较结果

| 结果 | 处理 |
|---|---|
| 版本和约定字段一致 | 当前对象通过 |
| ES 暂时读到旧状态或正在并发变化 | 等待后重新读取两端 |
| ES 缺失、版本落后或字段不一致 | 记录差异，持续不一致后交独立补偿 |
| 查询超时、连接失败、分片失败或结果不完整 | 记录执行异常，不判定一致或缺失 |
| MySQL 不存在 | 核实是否属于正常到期清理；确认后按规则跳过 ES 删除，否则保留异常 |

新表与 ES 的字段契约需要单独确认；新旧表校验中排除 `version` 的规则不自动适用。ES 外部版本元数据也不等于 `_source.version`，不能在未确认前扩充 Mapping。

新增、更新事件进入 MySQL 新表与 ES 的比较流程；到期删除事件只保存跳过处理记录。跳过结果可复用已有事件处理记录，不建立独立校验批次或 DELETE 专用任务表。

## 5 补偿与复核

校验器只读取并记录结果，独立补偿流程重新读取 MySQL 新表当前数据和版本，按原始 `create_time` 定位索引后使用既定外部版本规则写入 ES。写入请求成功不代表校验通过；补偿完成后必须再次读取两端。相同版本但内容不同不能靠原消息重投自动修复，受控修复方式仍待确认。

正常到期删除不调用 ES Delete API，由 ILM 删除过期月份索引；ILM 删除结果单独监控，不能用增量任务追平证明 ILM 已成功。

## 6 单条任务完成与恢复

每条新增、更新校验任务独立记录比较结果。当前任务比较或补偿后复核通过，才将该任务标记为完成；差异或执行异常未消除时，保留该任务的未完成状态，后续重试。其他任务无需等待它完成，后续新变更仍生成新任务。DELETE 跳过记录落库后即可确认对应消息，不参加普通 ES 比较。

恢复时，已确认消息对应的未完成任务从持久化状态继续执行；尚未确认的消息可能重投，需要处理重复接收。RocketMQ 消费位点与单条校验任务状态分别管理，不用任务是否通过决定消息确认。若需从上游重新采集，还须核对基线、位点和日志连续性；日志过期或覆盖范围无法核实，不能跳到最新位置或重置基线后宣称恢复成功。
