# 4.10 待补充事项（不作为已完成能力口述）

## 已确认规则

- 本次文件维护仅按用户确认的新名称重命名文档，并同步名称标识及关联引用；不调整正文技术结论。新建的 MySQL、Canal Server、自定义消费服务文档为空白占位文件。

- **自然月索引（已确认设计，待实现验证）**：新增、更新、删除、重试及补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。业务 ID 作为 `_id`，`records-read` 作为跨月读别名。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后进入 cold。删除事件须携带删除前的创建时间，索引模板统一 Mapping、配置和读别名；首次 Index 写入自动建索引以配置和权限允许为前提。
- INSERT/UPDATE 的来源版本取自新表业务 `version`，不再由 binlog 坐标编码；MQ 重试保持原消息数据与版本。该设计尚待实现验证，字段维护及新旧表比较规则见 005。
- 当前同步主链路为 MySQL → Canal Server（RocketMQ 模式）→ RocketMQ → 自定义 RocketMQ 消费与 ES 写入服务 → Elasticsearch；Adapter 1.1.7 保留版本边界，但不作为主写入组件。
- db0、db1 分别维护 GTID 起点和本地消费进度，由一个单机 Server 进程承载，不使用 ZooKeeper 主备。故障后人工核对并重启，按 destination 验收原生 RocketMQ 发布恢复和 MQ 到 ES 的恢复，不共用一个确认位置。
- 本表记录待实现或待验证事项。旧 Adapter 的 retries、双别名映射和进程安排仅属历史方案，不能继续写成当前 009 的已确认规则。
- ES 消费与失败处理按 005、008、010 维护：采用 `CONCURRENTLY` 并发消费，每条事件携带稳定来源版本并写入正确目标物理索引，由 ES 外部版本控制拒绝旧写入；这是已确认、待实现验证的设计决策。继续采用逐条同步调用、异常抛出和整条消息重投模型，不采用 Bulk 单项失败分类和状态驱动的恢复流程；冲突区分重复、过期与异常，既有幂等、原索引与必要状态保存要求继续适用，实际重试、死信和并发恢复效果仍待验证。
