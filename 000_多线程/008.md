## 1 问题

Redis 锁和数据库行锁分别适用于什么场景，应该如何选择？

## 2 高级 Java 面试核心考点

- 区分互斥、事务原子性及业务幂等：幂等是指重复执行不会重复产生业务效果。

### 3.1 先看保护的资源和重复执行的后果

选锁时，我先看要保护的资源在哪里、操作能否放进同一个数据库事务，再看重复执行是否会破坏业务正确性。两种锁都能协调并发，但不能只因为应用部署了多个实例，就认定必须用 Redis 锁。

### 3.2 Redis 锁适合跨实例的业务协调

例如多个实例同时重建一份热点缓存，用 Redis 锁减少重复查询和计算。如果锁过期后偶尔重复重建可以接受，而且并发写入不会造成不可接受的旧值覆盖，这种场景比较适合。锁过期不会停止原线程，所以扣款、创建订单等不能重复产生效果的业务，还需要幂等、唯一约束或条件更新等保护。Redis 锁也不能代替数据库事务。

### 3.3 行锁适合同一数据库中的短事务

例如启动迁移批次，先用 SELECT FOR UPDATE 锁住已有批次记录，再检查状态、初始化任务并更新状态，最后提交事务。行锁负责启动互斥，事务保证相关写入一起提交或回滚，提交后的状态继续拦截重复启动。行锁也能协调不同应用实例，但应尽快释放，避免锁等待和死锁；不能持锁等待整个迁移完成，也不能靠行锁保护事务外的外部操作。

### 3.4 简单操作不一定需要显式加锁

如果一个原子操作就能完成检查和修改，应优先考虑它。例如 Redis 原子命令或 Lua 脚本，以及数据库中的单条条件 UPDATE。数据库 UPDATE 仍可能自动取得行锁，只是不需要应用先执行 SELECT FOR UPDATE。

## 4 详细方案

### 4.1 保护范围与事务边界

两种锁都可以让遵守同一协议的请求协调访问同一资源，包括来自不同应用实例的请求。差异在于锁与业务数据的关系。

**Redis 锁：** 通常按业务资源标识设置锁，例如同一个缓存键或任务标识。它可以协调数据库之外的业务流程，但 Redis 中的锁记录和 MySQL 事务属于不同系统。获得锁不代表数据库操作成功，也不能让数据库写入与外部接口调用一起提交或回滚。

**数据库行锁：** 适合保护同一数据库事务中的记录检查与修改。例如所有启动入口都按主键锁住同一条已有批次记录，在持锁事务内检查状态、初始化任务并更新状态。事务提交或完整回滚时释放相关锁；其他请求随后取得锁，再检查最新状态，决定是否允许启动。

### 4.2 典型场景与使用前提

两种方案都需要明确保护对象，不能仅按“分布式业务”或“数据库业务”的标签选择。

**Redis 锁：** 热点缓存重建、减少重复计算比较典型，前提是偶尔重复执行的后果可接受。比如锁失效后两个实例都查询数据库并计算同一结果，主要代价是重复工作；如果旧计算结果可能覆盖新结果并影响业务，则仍需版本校验等保护，不能仅靠锁保证正确性。跨实例任务协调也可以使用 Redis 锁，但任务若有不可重复的副作用，就必须补充相应保护。

**数据库行锁：** 适用于同库短事务中的“先检查、再修改”，例如根据当前库存或余额作出判断后更新记录，以及批次状态检查与任务初始化。涉及多条相关写入时，必须明确事务边界；多个账户或多条库存记录还应采用一致的加锁顺序，减少死锁风险。批次初始化应保持事务足够短，实际耗时需验证，不能把全部数据迁移放在持锁事务中。

### 4.3 锁失效与异常处理的边界

两种锁都不能自动保证完整业务正确，也不能用“请求报错了”证明全部操作已经停止。

**Redis 锁：** A 暂停期间锁过期，B 获得锁后开始处理；随后 A 恢复，两个请求就可能同时执行。延长有效期、自动续期和只释放自己持有的锁有助于正确使用锁，但不能消除所有失效情况。严格业务还需要资源端保护，例如用唯一约束阻止重复创建、用条件更新检查状态或版本，必要时拒绝过期持有者的写入。每种措施只保护对应的业务不变量，不能认为添加任意一项就能覆盖全部风险。

**数据库行锁：** 同一锁定记录的冲突访问由数据库协调，不依赖 Redis 的独立有效期，但仍可能发生锁等待、死锁及事务异常。缺少合适索引时，锁定范围也可能扩大。锁等待超时不必然回滚整个事务，应用应正确结束失败事务；提交响应丢失时，应核实结果，不能直接假定回滚后重试。数据库行锁不能阻止已经发出的外部请求，也不会自动撤销外部副作用。

### 4.4 能用原子操作时，避免额外的加锁流程

Redis 计数递增可以使用原子命令；Redis 内的条件检查与修改可以考虑 Lua 脚本。脚本原子执行指执行期间不会与其他客户端命令交错，不表示运行出错时已经执行的写入会自动回滚，也不覆盖 MySQL 或外部接口。

数据库简单库存扣减可以使用带“剩余库存足够”条件的单条 UPDATE，并检查影响行数。它仍受数据库锁和事务机制保护，但省去了应用先查询再更新之间的竞争窗口。是否足以满足需求，取决于业务检查和写入能否在该原子操作内完整表达。
