### 3.1 总述：根据资源和重复执行的后果选择

选择锁时，主要看保护的资源和重复执行的后果。如果锁失效后，重复执行只是增加查询或计算开销，而且不会造成业务数据错误，这种代价又可以接受，可以使用 Redis 锁减少重复工作。如果重复执行会导致重复扣款、重复创建订单，或者旧数据覆盖新数据并影响业务，就不能只依赖 Redis 锁，必须有幂等、唯一约束或版本校验等相应保护。如果检查和修改都在同一数据库的短事务中，使用数据库行锁更直接；如果单个原子操作就能完成需求，就不必额外申请锁。

### 3.2 Redis 锁：按业务资源协调请求

Redis 锁可以按缓存键、任务标识等业务资源协调请求，常见用途是减少重复查询和计算。对于重复执行代价可接受的场景，比较适合。

#### 3.2.1 示例：减少重复重建缓存

A 获得某个缓存键对应的 Redis 锁后查询数据库、重建缓存；B 获取锁失败，就暂不重复查询。如果 A 卡住直到锁过期，B 就可能获得锁并开始重建，A 恢复后也可能继续执行。假设源数据不变、计算结果相同，两次重建主要增加查询和计算开销。

#### 3.2.2 边界：减少重复，不等于杜绝重复

Redis 锁能减少上述重复工作，但锁过期不会停止原线程。如果重复执行会导致重复扣款、重复创建订单，或者旧缓存覆盖新缓存，就需要相应的幂等、唯一约束或版本校验等保护。Redis 锁也不能代替数据库事务。

### 3.3 数据库行锁：保护同库短事务

如果需要保护的是同一数据库内的“检查记录，再修改相关数据”，可以在短事务中使用行锁。

#### 3.3.1 示例：阻止重复启动批次

A 用 SELECT FOR UPDATE 锁住已有批次记录，确认允许启动后，初始化任务并改为运行中；B 锁定同一条记录时等待。A 提交后，B 获得锁，读到运行中状态，就拒绝重复启动。

#### 3.3.2 边界：行锁、事务和状态各有职责

行锁负责启动互斥，事务保证相关写入一起提交或回滚，状态检查阻止后续重复启动。应尽快结束事务，减少锁等待和死锁风险；不能持锁等待整个迁移完成，也不能靠行锁保护事务外的外部操作。

### 3.4 能用原子操作完成，就不必额外申请锁

如果检查和修改能用一个原子操作完成，可以使用 Redis 原子命令、Lua 脚本或数据库条件 UPDATE。

#### 3.4.1 示例：用条件更新扣减库存

假设库存为 1，A、B 同时各扣减 1，更新条件是“库存至少为 1”。A 先扣减并提交后，B 检查到库存为 0，影响行数为 0，应用据此判定扣减失败，只有一个请求扣减成功。UPDATE 仍会使用数据库行锁，只是不需要先执行 SELECT FOR UPDATE。这里的库存数值仅用于示例。

## 4 详细方案

### 4.1 先明确保护范围与事务边界

先列出需要一起保护的检查和修改操作，再判断它们能否放进同一个数据库事务。两种锁都能协调来自不同应用实例的请求，关键差异是锁与业务数据的关系；还需检查所有入口是否遵守同一套加锁和状态检查流程。

**Redis 锁：** 通常按业务资源标识设置锁，例如同一个缓存键或任务标识。它可以协调数据库之外的业务流程，但 Redis 中的锁记录和 MySQL 事务属于不同系统。获得锁不代表数据库操作成功，也不能让数据库写入与外部接口调用一起提交或回滚。

**数据库行锁：** 适合保护同一数据库事务中的记录检查与修改。例如所有启动入口都按主键锁住同一条已有批次记录，在持锁事务内检查状态、初始化任务并更新状态。事务提交或完整回滚时释放相关锁；其他请求随后取得锁，再检查最新状态，决定是否允许启动。

### 4.2 典型场景与使用前提

两种方案都需要明确保护对象，不能仅按“分布式业务”或“数据库业务”的标签选择。

**Redis 锁：** 热点缓存重建、减少重复计算比较典型，前提是偶尔重复执行的后果可接受。比如锁失效后两个实例都查询数据库并计算同一结果，主要代价是重复工作；如果旧计算结果可能覆盖新结果并影响业务，则仍需版本校验等保护，不能仅靠锁保证正确性。跨实例任务协调也可以使用 Redis 锁，但任务若有不可重复的副作用，就必须补充相应保护。

**数据库行锁：** 适用于同库短事务中的“先检查、再修改”，例如根据当前库存或余额作出判断后更新记录，以及批次状态检查与任务初始化。涉及多条相关写入时，必须明确事务边界；多个账户或多条库存记录还应采用一致的加锁顺序，减少死锁风险。批次初始化应保持事务足够短，实际耗时需验证，不能把全部数据迁移放在持锁事务中。

### 4.3 锁失效与异常处理的边界

两种锁都不能自动保证完整业务正确，也不能用“请求报错了”证明全部操作已经停止。

**Redis 锁：** A 暂停期间锁过期，B 获得锁后开始处理；随后 A 恢复，两个请求就可能同时执行。延长有效期、自动续期和只释放自己持有的锁有助于正确使用锁，但不能消除所有失效情况。严格业务还需要资源端保护，例如用唯一约束阻止重复创建、用条件更新检查状态或版本，必要时拒绝过期持有者的写入。这些措施各有作用：唯一约束可以阻止相同业务标识被重复创建，但不能自动阻止外部接口被调用两次。因此要逐项明确需要保证什么，不能认为添加任意一项就能覆盖全部风险。

**数据库行锁：** 同一锁定记录的冲突访问由数据库协调，不依赖 Redis 的独立有效期，但仍可能发生锁等待、死锁及事务异常。缺少合适索引时，锁定范围也可能扩大。锁等待超时不必然回滚整个事务，应用应正确结束失败事务；提交响应丢失时，应核实结果，不能直接假定回滚后重试。数据库行锁不能阻止已经发出的外部请求，也不会自动撤销外部副作用。

### 4.4 能用原子操作时，避免额外的加锁流程

Redis 计数递增可以使用原子命令；Redis 内的条件检查与修改可以考虑 Lua 脚本。脚本原子执行指执行期间不会与其他客户端命令交错，不表示运行出错时已经执行的写入会自动回滚，也不覆盖 MySQL 或外部接口。

数据库简单库存扣减可以使用带“剩余库存足够”条件的单条 UPDATE，并检查影响行数。它仍受数据库锁和事务机制保护，但省去了应用先查询再更新之间的竞争窗口。是否足以满足需求，取决于业务检查和写入能否在该原子操作内完整表达。
