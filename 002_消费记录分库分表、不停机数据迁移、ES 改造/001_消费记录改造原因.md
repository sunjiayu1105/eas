# 001_消费记录改造原因

## 1 说明

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 2 问题

为什么要对消费记录做分库分表、在线迁移，并把后台列表查询迁到 ES？

## 3 高级 Java 面试核心考点

存储容量与维护压力、迁移期间的业务连续性，以及交易写入和跨商户检索对数据布局的不同要求。

## 4 面试口述版本

口述内容字符数：151

消费流水持续增长，单表的数据和索引越来越大，维护压力也随之增加。按商户号把交易记录分散到多个库表，交易写入和按商户回查仍能定位到一个分片。业务还要继续受理交易，所以历史流水在线搬，搬运期间用双写同步新增和修改，最后停写追平再交接。后台列表经常跨商户筛选、排序和分页，让 ES 承接允许短暂延迟的查询，可以减少这些查询对交易库的占用。

## 5 详细方案

分片将数据、索引和维护工作分散到多个物理表和实例。分片键决定哪些请求能直接定位，也决定了热点商户可能集中在哪个分片。容量与负载收益仍需验证。[分库分表方案](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/007_分库分表.md:1>)

历史搬运的耗时取决于存量和可用于迁移的资源。搬运时由旧表继续主写，增量同步和版本判断共同防止旧值覆盖新值。主写最终交接仍需等在途写入结束并核对数据。[在线迁移的原因](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/004_改造计划_在线迁移原因.md:1>)

后台列表缺少单一商户条件时需要跨片合并结果。用 ES 承接可容忍延迟的检索后，需要维护查询副本并检查数据同步情况。[追问 1.1：后台列表查询从 MySQL 迁到 ES 的原因](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/002_消费记录改造原因_后台列表查询从 MySQL 迁到 ES 的原因.md:1>)
