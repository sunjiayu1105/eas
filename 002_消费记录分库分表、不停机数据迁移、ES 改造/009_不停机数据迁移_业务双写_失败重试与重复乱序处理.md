# 009_不停机数据迁移_业务双写_失败重试与重复乱序处理

## 1 面试口述精炼版本

口述内容字符数：188

**原消息保留重试**

旧表业务数据和消息同事务提交后，后台直接写新表，确认成功再标记消息完成；失败保留消息重试，超限告警。重试使用原数据，不重做业务修改；沿用原消息版本。详见 [2.1](#21-扫描重试与重复处理)。

**重复不多写，旧消息不覆盖新状态**

新表提交后，响应或完成标记可能丢失，导致重复执行。写入须幂等，旧消息晚到也不能覆盖新状态。具体实现、并发领取和超限处置仍需验证；开启双写前须先完成旧表版本改造。详见 [2.1](#21-扫描重试与重复处理)。

## 2 详细方案

### 2.1 扫描重试与重复处理

前提：旧表主写，业务数据与消息已在旧库同一本地事务提交。本地消息机制来自参考文章_03；本文从 008 拆出失败处理的展开内容，不代表代码已实现。

**后台扫描消息，成功完成，失败重试**

1. 后台任务扫描已提交的待处理消息，取得操作类型、业务身份和对应数据，按项目分片规则写入新表。
2. 确认新表写入成功后，将旧库消息记录标记为完成。
3. 写入失败时保留未完成消息，记录重试次数，由后续扫描继续处理；重试超过阈值时告警。

来源：[参考文章_03：扫描、写入与重试（第 493 行起）](<./999_不停机数据迁移_参考文章_03.md:493>)。原文的扫描间隔、每批数量是示例；项目参数、超限后是否继续自动重试及人工恢复方式仍待确认。该链路由任务直接写新表，不以额外 MQ 投递作为必经步骤；新表到 ES 的既有 MQ 链路不受影响。

**示例：提交后崩溃也保留同步依据**

1. 旧库在同一事务中新增流水 S2 和待同步消息，随后提交。
2. 应用在新表写入前崩溃；消息已在旧库持久化，不会因这次进程退出而丢失。
3. 后台任务恢复后扫描该消息，继续写入新表，再标记完成。

这一设计解决业务提交与同步任务记录之间的原子性问题；实际恢复仍依赖扫描任务正常运行和失败处理落实。

**重复执行和乱序仍需防护**

重试使用原消息的业务数据，不重新执行业务修改；按已确认的 006 版本设计，沿用消息原有版本。

新表已提交，但响应丢失或消息完成标记失败时，同一消息会再次执行。因此写入必须幂等，即重复执行不产生额外业务结果；同一记录的旧消息也不能覆盖较新的状态。具体消息身份、并发领取及新增、更新、删除处理仍需验证。版本防覆盖设计见 [006](<./006_不停机数据迁移_如何防止旧版本数据覆盖新版数据.md>)，开启双写前，旧表版本改造及全部写入口发布必须完成。原文主要展示 INSERT，不能把该示例当作所有写操作均已实现。

## 3 已确认规则

- 用户自行确认的项目方案：开启双写前，先为旧表新增 version 字段，将已有记录初始化为 1；新增记录 version = 1，业务更新在同一条 SQL 中校验预期版本、修改业务字段并递增 version。所有相关写入入口完成改造并上线后，才开启双写。

- 沿用参考文章_03 的本地消息表方案，后台直接写新表，成功后标记完成，失败保留重试、超限告警。
- 重试使用原消息，不重新执行业务修改；版本方案沿用 006 的已确认设计，实际实现仍需验证。
- 来源与用户自行确认的项目方案分别标识；示例不作为实现或运行验证证据。

## 4 待确认或待验证事项

- 扫描任务并发领取、幂等和乱序防护的实现。

- 新表影响 0 行的分类和后续处理。
- 消息字段是否完整覆盖新增、更新、删除。
