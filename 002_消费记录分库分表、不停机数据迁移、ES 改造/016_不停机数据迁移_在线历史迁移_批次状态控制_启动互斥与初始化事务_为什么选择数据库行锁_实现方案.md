### 3.1 先锁住记录，再判断启动场景

在同一数据库事务中，按主键执行 `SELECT ... FOR UPDATE`，锁住预先存在的批次记录并读取状态。这是锁定读取：其他请求要修改或锁定同一记录，需要等待；在读已提交或可重复读下，普通快照查询通常仍能读取可见版本，但不能据此获得启动资格。只允许未启动或已暂停的批次继续，并检查相应启动条件。

### 3.2 首次启动：完整初始化后一起提交

批次为未启动时，查询旧表最小、最大 ID，保存批次扫描上下界，并按项目已确认的 100 万 ID 跨度生成完整任务清单（不是每个任务固定 100 万条数据），任务初始状态为待处理。扫描边界、任务清单和运行中状态在同一事务中保存，任一步失败就完整回滚。例如第三个任务插入失败，前两个任务和扫描边界也一起撤销，避免留下半份任务清单。

### 3.3 恢复启动：沿用任务和进度

批次为已暂停时，先确认上次执行已安全结束、异常已修复，再在锁定事务内检查状态和恢复条件，将批次改为运行中。不重新查询扫描边界、不重新初始化任务，也不重置进度。人工排查在启动前完成，不能持锁等待人工处理。

### 3.4 确认提交后，再调度任务

事务提交或完整回滚后释放行锁；只有确认提交成功才调度迁移任务，不持锁等待迁移结束。例如 A 提交运行中状态后，B 获得锁并读到运行中，就拒绝再次启动。行锁保护本次检查与更新，持久化状态拦截后续请求。

### 3.5 发生异常：结束事务，未知结果先核实

锁等待超时不一定回滚整个事务，应用应让异常向外传播，结束整个启动事务。提交响应丢失时不能假定已回滚，也不能继续调度或自动重试；先告警并核实。提交后、调度前宕机同样按人工恢复规则处理。以下是教学实现，实际并发、回滚及故障行为仍待验证。

## 4 详细方案

### 4.1 事务内的锁定读取

`FOR UPDATE` 不会修改数据，而是在读取时申请排他锁，为后续检查和更新提供互斥保护。锁定读取读取当前记录；如果记录正被其他未结束的事务修改，需要等待冲突锁释放，再读取并判断结果，不能拿先前普通查询的快照结果替代这次状态检查。

下面的简短 SQL 只演示已暂停批次的状态检查和更新，首次启动与恢复启动的完整 Java 骨架见 4.5。前提是上次执行已安全收尾、异常已修复，批次控制记录已存在且 `id` 是主键；完整启动校验和首次初始化由本篇 4.5 展开。状态更新与完整任务清单必须一起提交或回滚，原因及失败示例见 [为什么状态更新与任务初始化必须在同一事务中](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_为什么状态更新与任务初始化必须在同一事务中.md>)。

```sql
START TRANSACTION;

SELECT status
FROM migration_batch
WHERE id = 1
FOR UPDATE;

-- 应用读取结果：无记录或状态不允许启动时，ROLLBACK 并返回。
-- 仅在查询结果为 PAUSED，且其他启动检查通过时，继续执行：
UPDATE migration_batch
SET status = 'RUNNING'
WHERE id = 1 AND status = 'PAUSED';

-- 应用核对更新行数为 1；否则 ROLLBACK 并返回失败。
COMMIT;
```

示例中的 `id = 1` 是教学数据，`PAUSED` 和 `RUNNING` 分别示意已暂停和运行中。应用必须执行注释中的分支，不能不检查结果就连续执行全部 SQL。确认提交成功后才能提交迁移任务；提交结果未知时先核实，不贸然启动。

**行锁与条件更新的分工**

当前示例主要由悲观锁保护：前面的 `SELECT ... FOR UPDATE` 已在同一事务中锁住批次记录，其他事务修改这条记录时需要等待，因此读取状态、检查状态和更新状态不会被其他事务的冲突修改穿插。不能仅因 UPDATE 带有状态条件，就把整套方案称为乐观锁方案。

`AND status = 'PAUSED'` 是额外的状态校验：只有记录当前仍为已暂停，才允许改为运行中，并检查影响行数是否为 `1`。在前面的锁定检查正确执行、事务未结束的情况下，其他事务不能在检查和更新之间把这条记录改走；这个条件主要明确允许的状态转换，并配合影响行数检查防止误更新。

如果去掉前面的锁定查询，直接执行这条条件 UPDATE，再根据影响行数判断是否取得启动资格，可以将其理解为基于状态的 CAS（比较并更新）或乐观并发控制。例如两个请求都尝试把已暂停改为运行中，先成功更新并提交的请求影响行数为 `1`，在状态没有再次恢复为已暂停的前提下，后一个请求重新检查条件时已不满足，影响行数为 `0`；只有更新成功且确认事务提交后才能继续提交迁移任务。这里的 UPDATE 在 InnoDB 内部仍会加锁，不是完全无锁。

条件更新只保证这次状态转换的原子性，不能自动保证任务清单完整，也不能替代其他启动校验。首次初始化若要采用这种方式，任务清单、扫描边界和状态更新仍须在同一事务中完成，并重新设计和核验执行顺序；本项目继续沿用前述行锁方案，不在这里切换实现。

锁定查询、检查和更新必须处于同一数据库事务、使用同一连接。可以显式开启事务，也可以由应用事务管理器管理；不能在自动提交模式下单独查询后，再另开事务更新。行锁在事务提交或回滚时释放，不能把一次 SELECT 返回当作释放点，也不能靠方法名推断事务已生效。

例如 A、B 都先用普通查询读到已暂停，再各自提交迁移任务，即使各自最后都执行了 UPDATE，也可能重复启动。把读取和检查放进同一个锁定事务，才使这段检查与状态更新串行执行。

依据：[MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html) 中关于锁定读取、事务与锁释放的说明；原站点此前访问返回 HTTP 403，此前已通过 [Oracle 官方镜像](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-locking-reads.html) 核验事务内锁定读取与锁释放说明；仍无项目运行证据。

### 4.2 哪些操作等待，以及锁住多大范围

在本方案按主键等值查到已有记录的前提下，重点保护该记录对应的索引记录，不能理解为锁住整张表。InnoDB 的行锁实际作用于索引记录；它还会使用表级意向锁来协调加锁，但这不等于阻塞整张表的所有读写。

- 其他事务对同一记录执行 `SELECT ... FOR UPDATE`、`UPDATE` 或 `DELETE` 时，要取得冲突的锁，默认等待当前事务释放锁。等待期间可能发生锁等待超时或死锁，不能承诺一定获得锁。
- 在读已提交或可重复读隔离级别下，普通非锁定 `SELECT` 通常通过多版本并发控制（MVCC）读取可见的已提交版本，不必等待这把记录锁释放。查询能返回，不代表已经拿到启动资格；仍须经过锁定检查。可串行化隔离级别下不能直接套用普通查询不加锁的结论。
- 主键或完整唯一索引等值命中已有记录，与范围扫描、非唯一索引查询、查询不到记录的情况不同。后几种情况的锁范围要结合隔离级别与实际扫描路径判断；例如可重复读下的范围锁定读取通常可能包含间隙锁，影响范围内的插入。缺少合适索引还可能扩大扫描和加锁范围。

本项目设计只允许按主键锁定预先存在的批次控制记录。查不到记录时拒绝启动，不能误以为“没有返回行就不需要互斥”。生产表的索引、事务隔离级别与执行计划仍需核实。

本例使用默认等待行为，不使用 `NOWAIT` 或 `SKIP LOCKED`；后者会改变冲突时的处理方式，不能把跳过批次控制记录当作允许启动。

依据：[InnoDB Locking](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html)、[Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。以上是机制说明，未验证项目的实际锁范围。

### 4.3 正常结束与异常情况下如何释放锁

本方案按主键锁定已有批次记录，在同一事务中完成检查和状态更新。事务提交或完整回滚后，释放持有的记录锁；查询返回、方法返回或客户端超时，都不能单独证明数据库事务已结束。

- **正常提交或完整回滚：** 数据库完成事务处理后释放锁。回滚到保存点不是结束整个事务，不能按完整回滚理解锁的释放。
- **锁等待超时：** InnoDB 默认通常只回滚当前超时语句，事务此前持有的锁可能仍在。本方案让异常向外传播，由事务管理器结束并回滚整个启动事务，不捕获后继续提交迁移任务。实际行为还需核对 `innodb_rollback_on_timeout` 等配置。
- **死锁：** InnoDB 会选择一个事务回滚。应用处理异常并结束本次启动，不使用先前查询结果继续迁移；已有设计不自动重试。
- **进程宕机或连接异常：** 数据库确认连接终止后，回滚未提交事务并释放锁；断连检测与回滚可能需要时间。客户端收到异常时，应先核实数据库中的事务和操作是否已经结束，不能立刻恢复迁移。

例如事务先锁住批次记录，随后等待其他锁发生超时，如果应用只捕获异常却不结束事务，批次记录的锁仍可能被占用。因此“某条 SQL 失败”与“整个事务回滚并释放锁”必须分开判断。具体锁等待、事务与数据库请求超时参数仍待确认。

本节针对本方案已锁住的批次记录，不能推广为所有扫描记录的锁都只能在提交时释放；读已提交下，不匹配条件的记录锁可能提前释放。这里仅说明当前批次启动场景，通用锁机制不在本专题展开。

此前已核对 [Oracle 官方镜像的 InnoDB Error Handling](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-error-handling.html)：锁等待超时默认回滚当前语句，死锁回滚被选中的整个事务。该资料核验不代表项目故障处理已实现或通过实验。

### 4.4 为什么提交后释放锁仍能防重

1. A 开启事务，锁定批次记录，读取到允许启动的状态。
2. B 对同一记录执行锁定读取，因为与 A 的锁冲突而等待。
3. A 完成检查与必要初始化，把批次改为运行中并提交，锁随事务结束释放。
4. B 获得锁后读到运行中，拒绝启动并结束事务，不再提交迁移任务。

这解决了两个请求都通过启动检查的问题。行锁只负责保护本次检查与状态转换；持久化的运行中状态负责拦截后续请求。所有启动入口必须遵守同一协议，不能绕过检查；也不能在旧执行仍未结束时把状态改回已暂停。

如果 A 回滚，B 获得锁后按回滚后的实际状态重新检查，并不保证一定拒绝 B。若运行中状态已经提交，它不会因进程宕机自动恢复；仍按人工故障恢复规则核实后修复。

完整初始化、提交未知与恢复流程见 [启动互斥与初始化事务](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务.md>)。事务异常与释放边界见 4.3；完整初始化实现见 4.5，人工恢复仍以批次状态控制专题为准。

### 4.5 核心实现代码：首次启动与恢复启动

以下使用 Spring JDBC 的 `JdbcTemplate` 和 `TransactionTemplate` 展示核心控制流程，不依赖 MyBatis 或 JPA，也不表示项目已采用 Spring JDBC。示例需引入与 Spring Boot 2.7.18 配套的 JDBC 依赖；批次表和任务表都使用 InnoDB，并通过同一 DataSource 参与同一个本地事务；事务内的查询和写入必须使用同一连接。表名、状态枚举字符串及批次主键 `1` 均为教学示意。

代码分成两段：`tx.execute` 内完成加锁、检查、初始化或恢复以及更新状态；它正常返回后，才调用调度器。启动入口禁止加入外层事务，避免事务模板返回时外层事务尚未提交，就提前执行迁移。运维已经核实上次执行结束、修复未知结果，才允许将批次恢复为已暂停；代码不能仅凭任务状态代替人工核实。

```java
import java.util.List;
import java.util.Objects;
import javax.sql.DataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.transaction.support.TransactionSynchronizationManager;
import org.springframework.transaction.support.TransactionTemplate;

public final class MigrationStarter {
    private static final long BATCH_ID = 1L; // 所有入口使用同一控制记录。
    private static final long ID_SPAN = 1_000_000L; // 已确认的 ID 跨度，不是行数。
    private final JdbcTemplate jdbc;
    private final TransactionTemplate tx;
    private final Dispatcher dispatcher;
    private final int maxTasks; // 初始化任务数上限，由资源预算配置，不是生产固定值。

    public MigrationStarter(DataSource dataSource, Dispatcher dispatcher,
                            int maxTasks) {
        if (maxTasks <= 0) throw new IllegalArgumentException("maxTasks 必须为正数");
        this.jdbc = new JdbcTemplate(dataSource);
        this.tx = new TransactionTemplate(
                new DataSourceTransactionManager(dataSource));
        this.dispatcher = Objects.requireNonNull(dispatcher, "dispatcher 不能为空");
        this.maxTasks = maxTasks;
    }

    public void start() {
        // 本入口不加 @Transactional，也不允许事务方法间接调用它。
        if (TransactionSynchronizationManager.isActualTransactionActive()) {
            throw new IllegalStateException("启动入口不能处于外层事务中");
        }
        Boolean ready = tx.execute(transaction -> {
            List<String> states = jdbc.query(
                    "SELECT status FROM migration_batch WHERE id = ? FOR UPDATE",
                    (rs, rowNum) -> rs.getString(1), BATCH_ID);
            if (states.size() != 1) {
                throw new IllegalStateException("批次控制记录必须预先存在");
            }
            String state = states.get(0);
            if ("NOT_STARTED".equals(state)) {
                initializeTasks();
            } else if ("PAUSED".equals(state)) {
                // 不再查询旧表边界、不重新插入任务、不重置进度。
                if (!hasResumableTasks()) {
                    if (jdbc.update("UPDATE migration_batch SET status = 'NEEDS_ATTENTION' "
                            + "WHERE id = ? AND status = 'PAUSED'", BATCH_ID) != 1) {
                        throw new IllegalStateException("异常状态保存失败");
                    }
                    return false; // 正常提交异常状态；不能抛异常把这次更新回滚掉。
                }
            } else {
                throw new IllegalStateException("当前批次状态不允许启动：" + state);
            }
            int changed = jdbc.update(
                    "UPDATE migration_batch SET status = 'RUNNING' "
                            + "WHERE id = ? AND status = ?", BATCH_ID, state);
            if (changed != 1) throw new IllegalStateException("批次状态更新失败");
            return true;
        }); // 回调异常时回滚；正常返回才表示这次事务提交已被确认。

        // 提交失败或响应未知会抛异常，不会执行到这里；不能捕获后强行继续。
        if (!Boolean.TRUE.equals(ready)) {
            throw new IllegalStateException("批次已转为异常待处理，需告警并人工核实");
        }
        dispatcher.dispatchCommittedBatch(BATCH_ID);
    }

    private void initializeTasks() {
        Long existing = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task", Long.class);
        if (existing == null || existing != 0L) {
            throw new IllegalStateException("未启动批次不应存在残留任务，先核实");
        }
        Long[] bounds = jdbc.queryForObject(
                "SELECT MIN(id), MAX(id) FROM old_consume_record",
                (rs, rowNum) -> new Long[] {
                        rs.getObject(1, Long.class), rs.getObject(2, Long.class) });
        if (bounds == null || bounds[0] == null || bounds[1] == null) {
            throw new IllegalStateException("旧表为空，零任务规则待确认，不生成虚假任务");
        }
        long minId = bounds[0], maxId = bounds[1];
        // 本示例只支持能装入 Java long 的 ID；超出表示范围时拒绝，不截断。
        long distance = Math.subtractExact(maxId, minId);
        if (distance < 0) throw new IllegalStateException("扫描范围非法");
        long planned = distance / ID_SPAN + 1;
        if (planned > maxTasks) throw new IllegalStateException("任务数超过配置上限");
        if (jdbc.update("UPDATE migration_batch SET min_id = ?, max_id = ? WHERE id = ?",
                minId, maxId, BATCH_ID) != 1) {
            throw new IllegalStateException("扫描边界保存失败");
        }
        long inserted = 0;
        for (long startId = minId; ; ) {
            long endId = Math.addExact(startId,
                    Math.min(ID_SPAN - 1, Math.subtractExact(maxId, startId)));
            // 教学映射：用范围起点作为稳定 task_id，主键约束防止重复插入。
            int n = jdbc.update("INSERT INTO migration_task "
                            + "(task_id, start_id, end_id, current_id, status, failure_reason) "
                            + "VALUES (?, ?, ?, NULL, 'PENDING', NULL)",
                    startId, startId, endId);
            if (n != 1) throw new IllegalStateException("任务保存失败");
            inserted++;
            if (endId == maxId) break;
            startId = Math.addExact(endId, 1);
        }
        if (inserted != planned) throw new IllegalStateException("任务清单不完整");
    }

    private boolean hasResumableTasks() {
        Long total = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task", Long.class);
        Long invalid = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task "
                + "WHERE status IS NULL OR status NOT IN ('PENDING', 'PAUSED', 'SUCCESS')",
                Long.class);
        return total != null && total > 0 && total <= maxTasks
                && invalid != null && invalid == 0;
    }

    public interface Dispatcher {
        void dispatchCommittedBatch(long batchId);
    }
}
```

**事务内失败与提交结果未知**

`NOT_STARTED`、`RUNNING`、`PAUSED` 分别表示未启动、运行中、已暂停；`NEEDS_ATTENTION` 表示异常待处理。任务状态 `PENDING`、`PAUSED`、`SUCCESS` 表示待处理、已暂停、成功。初始化中的任意写入失败、算术溢出或状态校验失败，异常向外传播，使本次事务回滚；不能捕获异常后返回正常结果。提交阶段发生连接或响应异常时，结果可能未知，调用方应告警并核实数据库，不得假定已经回滚后自动重试。

例如初始化第三个范围失败，已插入的前两个范围和批次扫描边界一起回滚，批次尚未执行运行中状态更新，仍保持未启动；下一次启动不会沿用半份任务清单。具体回滚行为仍需用真实数据库验证。为了突出事务边界，示例逐条插入任务；实际初始化耗时、任务数上限和是否改用 JDBC 批量写入需要验证。MIN/MAX 查询假设可由索引高效完成；否则按 013 的边界规划要求调整，不能长期占用控制记录锁。

**调度器必须承担的交接职责**

`Dispatcher` 是尚待实现的业务接口，不能用空实现后声称迁移已完成。其实现沿用线程池调度专题：提交前复查批次状态与停止信号，只查询待处理、已暂停任务；按原状态更新为处理中后才扫描。线程池核心数、最大数均为按数据库预算压测确定的 `N`，队列及提交上限遵循该专题，不在此重复创建另一套线程池。

事务提交后可能立即收到暂停请求，因此仅在 `dispatchCommittedBatch` 入口查询一次运行中还不够，提交循环、任务入口和分页边界也要检查停止信号。提交被拒或部分提交失败时，调度器负责立即停止新处理、告警、保留已接收的 Future 并组织安全收尾；不能将异常直接丢给启动调用方后放任已运行任务继续。调度器随后按完整任务表汇总状态，不能直接把批次改回未启动或已暂停。

**示例的实现边界**

任务表仅保存这次迁移的任务，不混入其他迁移历史，不新增批次 ID。示例的恢复校验发现空清单及失败、处理中等非法状态时，先提交异常待处理状态，再拒绝启动，但不能仅靠记录条数证明范围完整；还需依靠初始化事务、稳定唯一约束和禁止随意修改清单。人工修数后必须按保存的范围核实完整性与未知结果，确认安全后才能恢复。

示例没有实现 Controller、告警、调度器和人工恢复流程，也没有读取生产配置。它展示的是可落地的事务与 JDBC 调用骨架，不是完整迁移服务；实际 DataSource、事务管理器接线、超时配置以及驱动对 ID 类型的映射需在实现时验证。Spring 事务接口查阅入口：[TransactionTemplate](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/transaction/support/TransactionTemplate.html)、[DataSourceTransactionManager](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/jdbc/datasource/DataSourceTransactionManager.html)；已核对 TransactionTemplate 官方 API 中回调运行时异常触发回滚并向外传播的说明，并依据 [Spring Boot 2.7.18 BOM](https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-dependencies/2.7.18/spring-boot-dependencies-2.7.18.pom) 确认其管理的 Spring Framework 版本为 5.3.31。此前文档记录使用该依赖与 Java 8 编译示例通过，本轮仅核对并保留原代码，未重新编译；这不证明项目已引入相同依赖或事务接线已生效，实际依赖树、数据库运行及故障行为仍待验证。
