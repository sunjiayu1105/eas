**先拆任务，保存进度**

**固定线程，按需领取**

专用线程池固定 N 个线程，N 根据数据库承受能力压测确定。每个线程反复领取一个待执行任务，将其改为执行中，分页迁移并保存结果，再领取下一个。恢复启动前，先核实暂停任务的旧执行和数据库操作已停止，再将其恢复为待执行；暂停期间不领取。领取时保证同一个任务只能被一个执行者拿到；分页读取控制内存占用，每页写入结果确认后才保存进度，供中断后恢复。 详见：[线程数选择](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:53>)、[领取流程](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:239>)。

**失败告警，人工恢复**

任务失败就保留确认进度、记录原因并告警，不自动重试，同时暂停整体的新任务领取，让已运行任务安全收尾。人工排查修复，确认旧执行和数据库操作已停止、未知写入结果已核实后，通过恢复接口将任务改为待执行，再开启领取，从保存的进度继续。恢复不清空进度，重复写入不能产生额外影响，也不能用旧数据覆盖新数据。 详见：[失败处理与恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:264>)。

**按任务表判断完成**

没有可领取任务、执行中任务或未核实结果时，本次执行可以收尾；失败触发暂停时，仍可留有未执行任务。协调方再核对完整任务表：有失败则告警并人工排查；无失败但仍有未完成任务则尚未完成；全部成功才判迁移执行成功，随后做一致性校验。执行结束不等于迁移成功，失败发生时就告警，不等收尾。 详见：[完成判定](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:190>)、[执行收尾](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:223>)。

**暂停要等当前操作收尾**

先禁止领取新任务，正在执行的任务处理并核实当前页，只保存已确认进度，再退出。最后确认线程和数据库操作都已结束，结果未知时不能跳过这页。 详见：[安全暂停](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_线程池_实现方案.md:223>)。

## 3 详细方案

### 3.1 主文档职责

本文说明迁移专用线程池的选择与调度衔接。限流由 012 维护，批次性能调优由 013 维护，线程数压测由 015 维护，断点续跑由 016 维护；通用线程池概念、参数、队列和拒绝策略见 `000_线程池` 目录。本文不把线程池配置当作任务进度、幂等或事务方案。

### 3.2 总体流程

先规划并保存完整任务清单，再启动 N 个工作循环。“工作循环”就是线程反复执行“领取一个范围 → 分页迁移 → 保存结果 → 领取下一个范围”。每次领取必须保证同一范围只有一个执行者获得处理资格，这就是原子领取。协调方负责观察这些循环是否正常、汇总整轮结果，并管理暂停、退出和恢复。

线程池执行的是工作循环，范围任务由工作循环直接调用处理方法；每个范围不再单独提交到线程池。数据库任务表保存待办，内存不再维护范围任务等待队列、完成队列或派发窗口计数。

### 3.3 线程池边界与选择理由

长范围任务的主要耗时在数据库读写。每个工作循环处理完一个范围再领取下一个，可以减少内存调度状态；是否比预排队方案更快仍需压测，不能宣称性能已提升。

固定线程数仅限制本线程池的工作线程数量。其他线程池、多实例及任务内部额外异步操作都可能增加数据库并发；任务表领取互斥不能代替全局并发预算。线程资源隔离也不等于数据库资源隔离。

来源：[参考文章_04：工具架构与性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:192>)提供分批与并发调整方向；工作循环和领取协议属于本项目设计，未验证运行效果。

### 3.4 类型与线程数：专用固定线程池

手工创建专用 ThreadPoolExecutor，corePoolSize 和 maximumPoolSize 均为正整数 N；由一个生命周期入口只提交 N 个工作循环。N 是单实例工作循环上限，不是范围任务总数。每个循环同步处理一个范围，不在内部再创建迁移线程。

N 按源库和目标库连接预算、每循环连接占用、数据库负载、在线延迟、迁移时限及实例数压测确定。2、4、8 是候选测试点，不是生产配置。选择满足指标且有资源余量的较小值，不能直接照搬连接池大小或 CPU 核数。

一次运行内保持 N 不变，调整前先暂停并确认旧执行收尾，再启动新配置；多实例需共享领取规则和总并发预算。

### 3.5 任务存储与线程池队列

约 300 个范围及其进度全部保存在数据库任务表。每个循环一次只领取一个范围，处理并保存结果后才领取下一个；内存主要保留最多 N 个当前范围描述、各自分页数据及固定数量工作循环的管理信息。

线程池配置示例采用 SynchronousQueue，不存储待执行任务。它用于表达“线程池不缓冲范围任务”，不是让所有范围逐一直接交接给线程。新建线程池不预启动核心线程，启动阶段最多提交 N 个工作循环；补建、重复启动和关闭竞争必须由生命周期管理处理，不能假定永远不会拒绝。

任务闭包和日志不得长期引用历史页；每页写入与进度确认后解除数据引用，回收时机仍由 JVM 决定。实际内存峰值需要结合 N、页大小、字段和驱动缓冲实测。

### 3.6 拒绝策略与工作循环异常

采用 AbortPolicy 暴露工作循环提交被拒的异常，不使用静默丢弃策略，也不让 CallerRunsPolicy 将长期循环交给协调线程执行。这里拒绝的是工作循环的启动，不是某个数据库范围任务；范围在工作循环真正启动后才领取。

启动拒绝或线程创建失败时，不把本轮标成成功。生命周期管理停止继续启动，通知已启动循环暂停并核实收尾，告警后受控恢复；不能忙循环重复提交。提交入口还需防止同一次迁移重复启动两组工作循环。

范围处理失败、控制逻辑异常、状态持久化失败或结果未知，统一暂停新领取并告警，不根据故障类别决定是否自动重试。使用 submit 时，工作循环异常会进入 Future；协调方必须检查已完成 Future 的 get 结果，及时触发同一暂停与人工处理流程，不能只看线程池线程数。线程池补建物理线程不等于自动重新运行已结束的工作循环。

### 3.7 初始化与核心执行机制

以下是 Java 8 配置片段，需要导入 java.util.concurrent、java.util 和 AtomicBoolean。runWorkerLoop 为业务方法，需落实 3.12 的领取、失败处理与退出协议；本片段不是完整可运行实现。

```java
if (N <= 0) {
    throw new IllegalArgumentException("N must be positive");
}
AtomicBoolean pause = new AtomicBoolean(false);
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        N, N, 0L, TimeUnit.MILLISECONDS,
        new SynchronousQueue<Runnable>(),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy());
List<Future<?>> workers = new ArrayList<>(N);
try {
    for (int i = 0; i < N; i++) {
        // 循环内部领取范围；不在提交之前领取数据库任务。
        workers.add(pool.submit(() -> runWorkerLoop(pause)));
    }
} catch (RuntimeException startupFailure) {
    pause.set(true);
    pool.shutdown();
    // 上层必须核实已启动循环和数据库操作收尾，再决定恢复。
    throw startupFailure;
}
```

协调方在迁移线程池之外运行，周期检查整体结果、控制信号和工作循环 Future；不能把协调任务排在已被 N 个长期循环占满的线程池中。检查周期 1 秒可作教学示例，生产值待确认；只有 Future.isDone() 后才通过 get 检查退出结果，避免顺序等待一个长循环而看不到其他循环异常。

Future 代表整个工作循环的结束，不代表某个范围成功。协调方根据任务表汇总业务结果，恢复时不复用旧 Future。shutdownNow、cancel(true) 和 awaitTermination 均不能单独证明数据库操作已结束，优先合作式暂停。

Java 行为参考：[ThreadPoolExecutor API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[SynchronousQueue API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/SynchronousQueue.html)、[Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。本次未联网核验或运行示例。

### 3.8 详细拆分方案：固定边界，按范围分页

用户补充的项目背景：旧表约有 3 亿条数据，主键递增。按每个任务平均约 100 万条记录估算，3 亿 ÷ 100 万 ≈ 300，因此可规划约 300 个范围任务。这是工作量规划，不是 300 个工作线程，也不是要求每个范围恰好有 100 万条；实际数据量和各范围记录数未在本次查询核验。

递增主键仍可能存在空洞，不能直接把主键跨度 100 万当成 100 万条记录。具体范围边界需结合主键分布和记录量测定；可以保持范围连续且不重叠，允许各任务记录数不同，再按分布调整过大或过小的范围。边界生成方式尚待落实。下面三个小范围仅用于演示左开右闭规则，不代表项目仅规划三个任务。

以下为建议实现方案，前提是源表具有适合稳定排序和范围查询的主键。本例使用正数、唯一且迁移期间不改变的数值主键 id，实际主键类型、迁移过滤条件及是否满足此前提仍待核实；不能直接套用于复合主键或会变更的主键。

开始规划时记录本轮最大主键 endId，将其与来源表和迁移条件一起保存，恢复时沿用原边界。假设历史范围为 (0, 300000]，可按 100000 的主键跨度拆成三个范围，所有数值均为教学示例：

| 任务 | 区间 | 查询边界 |
| --- | --- | --- |
| T1 | (0, 100000] | id > 0 AND id <= 100000 |
| T2 | (100000, 200000] | id > 100000 AND id <= 200000 |
| T3 | (200000, 300000] | id > 200000 AND id <= 300000 |

统一左开右闭，前一个任务的上界等于后一个任务的下界，边界记录只属于一个范围。范围跨度不等于记录数：主键可能有空洞，数据也可能分布不均，因此不能保证三个任务耗时相同。任务清单生成完毕后记录“规划完成”，核对范围首尾、连续性和唯一性，再据此判断整轮是否完成，不能只统计已经领取的任务。

每个范围从自己的最后确认位置 lastId 继续，初始值为区间下界。下面是参数化查询示意，不是可直接运行的完整 SQL；表名取自受控配置，值参数绑定传入，迁移过滤条件各页保持一致。

```sql
SELECT 所需字段
FROM 源表
WHERE id > :lastId
  AND id <= :rangeEnd
ORDER BY id
LIMIT 500;
```

500 是每页最多读取的记录数示例，不是主键跨度或生产配置。执行过程如下：

1. 成功读取一页；查询异常必须报告失败，不能当作空页。
2. 按分片规则写入目标表，逐项确认写入成功或按版本规则可安全跳过。
3. 本页全部结果已确认后，保存本页最后一个主键为该任务进度；保存成功后才读取下一页。
4. 写入失败、部分结果未知或进度保存未确认时，不推进恢复位置，报告未完成；恢复可能重做本页，因此仍需幂等与版本控制。
5. 查询成功且结果为空，说明范围扫描结束；成功状态可靠保存后，才能将该范围计为成功。最后一页可能不足 500 条，主键有空洞时 lastId 也不一定等于 rangeEnd，不能只按游标等于上界判断完成。

固定 endId 只限定扫描边界，不形成数据库快照。双写需覆盖迁移期间的业务变更，扫描到的旧版本不能覆盖新版本；低于 endId 的晚提交数据也不能仅靠一次主键扫描保证捕获，仍需同步与一致性校验兜底。本方案不能据此声称已实现无遗漏迁移。

与 [016 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_断点续跑.md>) 保持一致：按独立范围保存进度是本篇建议落地方式，不用全局最大主键掩盖较小范围的失败。存储结构和事务边界尚未实现验证。

### 3.9 任务描述：领取范围信息，执行时分页读取

建议任务描述只保存标识和扫描范围，例如下面的 Java 8 数据结构；字段为设计示例：

```java
final class RangeTaskSpec {
    final String taskId;       // 与本轮任务清单中的任务关联
    final String sourceTable;  // 来自受控配置，不能接受任意表名
    final long startExclusive;
    final long endInclusive;

    RangeTaskSpec(String taskId, String sourceTable,
                  long startExclusive, long endInclusive) {
        this.taskId = taskId;
        this.sourceTable = sourceTable;
        this.startExclusive = startExclusive;
        this.endInclusive = endInclusive;
    }
}
```

工作循环从任务表原子领取 RangeTaskSpec 对应范围后，直接调用范围处理方法，不把范围包装成新的线程池任务。一次只保留当前范围描述和进度，再分页读取数据。

例如 T2 尚待领取时只保存“查哪个表、从 100000 到 200000”的信息；得到工作线程后，才开始按每页最多 500 条读取。这样内存数据量主要受正在执行的任务和批次大小影响，而不是受所有待领取范围的数据总量影响；字段大小及任务描述大小仍需评估。


**长时间执行与数据引用的生命周期**

每个任务处理约 100 万条记录，可能持续较长时间，实际耗时需测量。执行期间，任务 ID、范围边界、进度和执行所需的服务引用可以持续保留；并不因此把该范围的 100 万条数据库记录同时保存在内存。

数据按页读取，例如每页最多 500 条是教学示例。应在本页写入结果已确认、进度成功保存后，解除对本页记录及不再需要的写入缓冲的引用，再读取下一页；不得将各页不断追加到任务级大列表，也不要让闭包、日志缓存或结果对象长期持有历史页。异常路径若需保留现场，应保留必要标识和错误信息，不能无界积累数据；未确认进度仍按原位置恢复。

释放引用不等于内存立刻归还：只有对象不再被其他存活引用持有时，才具备被垃圾回收器回收的条件，实际回收时机由 JVM 决定。不能通过任务执行时间长直接判断内存一定持续增长，也不能只因采用分页就保证没有内存泄漏。

因此，长期保留的是有限任务的必要描述；分页记录和写入缓冲随每页处理循环使用。实际内存峰值仍取决于并发 N、页大小、字段大小、驱动与批量写入缓冲、引用保留情况，需实测。数据库任务表保存完整清单，不等于应用同时加载约 300 个任务对象。

进程重启后根据持久化清单和各范围确认进度恢复。重新领取前核实旧执行者及在途操作已经收尾，防止同一范围重叠执行。多实例领取与防重协议仍待落实。

### 3.10 任务表字段与整体完成判定

**任务表保存什么**

先将所有迁移任务写入数据库，初始状态统一设为待执行，初始进度为扫描范围下界。任务表只保存本次需要完成的完整任务清单，不按批次区分，也不混入其他迁移的历史任务。字段名为实现建议，具体表结构尚未验证。

| 字段 | 建议字段名 | 含义 |
| --- | --- | --- |
| 任务 ID | task_id | 唯一标识一个范围任务 |
| 扫描起始 ID | start_id | 范围下界，不包含；恢复时不改成当前进度 |
| 扫描结束 ID | end_id | 范围上界，包含；迁移期间固定 |
| 处理进度 | current_id | 最后确认处理成功并保存的位置，初始为范围下界 |
| 处理结果 | status | 区分待执行、执行中、成功、失败、暂停；具体枚举待实现 |
| 失败原因 | failure_reason | 记录失败阶段及原因，未知写入结果也要说明 |

不维护批次 ID、执行者标识和执行尝试编号。任务 ID 是范围标识，不是执行次数编号。普通领取只处理待执行状态。恢复启动时，先通过人工触发的恢复接口核实暂停任务，确认旧执行及数据库操作已停止，再将其改为待执行；不直接查询所有暂停任务就执行。失败或残留执行中任务同样先核实后恢复，暂停指令未解除时禁止领取。

**直接从完整任务表汇总结果**

只有任务清单全部生成并可靠入库后，才判断整体是否完成。启动阶段核对规划数量、实际记录数及范围完整性，约 300 是估算，不能硬编码为成功门槛。规划完成的控制状态需要可靠保存，保存方式待实现；不能把暂时为空的任务表当作迁移成功。

协调方根据任务表的一致数据视图直接汇总，无需批次结果表：

1. 任意任务失败：整体失败，即使还有任务未完成也优先判失败。
2. 没有失败，但仍有任务尚未成功：整体尚未完成，界面可显示执行中；待执行、执行中、暂停和结果未知都不算成功。
3. 完整清单中的所有任务均可靠保存成功状态：迁移执行成功，随后仍需一致性校验。

单个范围只有扫描结束、各页结果已确认、进度与成功状态均保存成功，才能计为成功。查询异常不能当作空页，最后确认位置也不一定等于范围上界。线程结束、领不到任务或任务表查询失败，都不能替代成功判定。

整体失败不代表所有工作线程都已停止。任意任务失败都触发整体暂停新领取，已运行任务按 3.11 安全收尾，不继续领取其他范围；人工恢复后按当前任务状态重新汇总，可以从失败回到尚未完成或成功。历史失败通过日志保留，不靠额外执行尝试字段管理。零任务迁移的判定仍待确认。

例如 T1 成功、T2 失败、T3 执行中，整体失败；T2 恢复为待执行后，若已无失败任务，则整体尚未完成；所有任务可靠保存成功状态后才判成功。

### 3.11 正常收尾与主动暂停

**正常收尾**

工作循环暂时领不到任务时，限时等待并检查控制状态；等待 1 秒仅为教学示例，生产间隔待确认。规划完成后，协调方核对待执行、暂停、执行中及结果未知的任务。正常执行中，没有可领取任务、正在执行的任务或尚未核实的领取和写入结果，才可以正常收尾；尚未恢复的暂停任务仍算未完成，不能直接判成功。

协调方发出本次执行结束信号，循环在领取前检查并退出，随后调用 shutdown、检查循环 Future，并等待线程池终止与数据库操作收尾。若全部计划任务成功则进入一致性校验；若仍有失败或未知状态，则保留未完成结果。无法确认运行任务是否已结束时进入排查，不能仅因心跳超时判成功。

shutdown 只禁止新的线程池提交，不会阻止已有长期循环继续从任务表领取，所以必须由业务控制信号和领取协议决定停止领取。等待超时不能当作停止成功。

**主动暂停或失败触发暂停**

先设置暂停控制状态，禁止新领取；各循环在领取前、领取成功后开始扫描前以及分页边界检查。领取与暂停存在竞争时，刚领取但尚未扫描的范围应安全保存为可恢复状态，并退出，不能悄悄继续扫描。

任意失败立即记录原因并告警，同时禁止新领取，不必等本次执行结束才告警。暂停收尾允许任务表仍有待执行、暂停或失败任务，不要求全部任务都被执行过。正在处理的页先核实结果，只保存已确认进度；失败或未知不推进。随后循环报告暂停并退出，协调方 shutdown 并等待线程及在途数据库操作收尾。多实例暂停需要共享控制状态，单机 AtomicBoolean 不能通知其他实例。暂停不算成功，恢复后沿用原范围与进度。

### 3.12 原子领取与协调汇总

**领取与执行顺序**

1. 完整任务清单以待执行状态入库并确认规划完成后，受控启动最多 N 个工作循环。恢复启动先核实暂停或失败任务，经恢复接口改为待执行，再由人工解除整体暂停。
2. 每个循环检查暂停及依赖状态，再原子领取一个待执行范围。通过任务 ID 和待执行状态条件完成领取，只有确认更新成功者才能扫描。
3. 按该范围的最后确认进度分页处理；每页结果和进度确认后再继续。一个循环同时只处理一个范围。
4. 范围成功后保存成功状态；仅在没有暂停信号时继续领取。任意范围失败都保留确认进度、记录失败原因并告警，触发整体暂停新领取；失败范围不直接混入普通领取查询。
5. 状态保存失败或结果未知时同样暂停新领取并报告协调方，转入人工核实；不能因为失败状态写不进去就继续领取，也不能放弃当前范围后领取新范围。
6. 暂时没有可领取任务时限时等待并检查结束指令。协调方按完整清单汇总、决定正常收尾或受控暂停；下一次恢复可重新启动工作循环。

**领取必须是原子的**

用 task_id 和 status=待执行作为条件，将状态原子更新为执行中；只有影响行数为 1 且提交结果确认成功的线程才能处理该任务。查到候选记录不等于已获得执行权。竞争失败则重新检查控制状态，避免无间隔争抢。领取事务必须短小，不在整个范围迁移过程中持有任务表行锁。

数据库提交响应丢失时，领取可能已经成功，也可能由其他线程领取。没有执行身份字段，不能只看到状态为执行中就认定属于自己；应暂停新领取，核实相关线程和数据库操作后再恢复，不能直接开始扫描或把任务重置。进度更新可检查任务 ID 和执行中状态，但该条件不能防止恢复后的旧执行写入。具体 SQL、索引、事务与恢复互斥仍待实现验证。

**协调方的职责**

协调方独立监测工作循环健康、汇总任务表和整体结果，并管理停止。例：T1 失败、T2 尚待执行，无论 T1 是数据问题还是数据库故障，T2 都暂不领取；其他已运行范围在安全位置收尾，等待人工处理后恢复。没有领到任务、工作循环全部结束或线程池队列为空，都不能替代完整清单的成功判定。

若工作循环意外退出而仍有待办，协调方必须发现并告警，不能把剩余任务遗留后报告成功。补建循环或恢复前核实旧范围与在途操作收尾，限制同一执行组最多 N 个有效循环。多实例还需全局预算与故障接管协议；整体结果按全部任务的当前状态判断，不区分批次。

该设计不再维护范围级 CompletionService、inFlight 或 W=N+Q。范围状态以任务表为准，固定数量的 Future 仅用于观察工作循环生命周期。

### 3.13 执行失败：统一告警、人工排查与恢复

失败统一采用“暂停新领取 → 记录与告警 → 人工排查修复 → 核实旧操作 → 恢复待执行”的流程。程序不自动按原因分类重试，根因由人工结合日志和监控判断。这样处理规则更简单，但短暂故障也需要人工介入，迁移可能暂停更久。以下为已确认设计，不代表已经实现或验证。

**保存失败现场，保留确认进度**

任务失败时先触发暂停新领取，保留最后成功保存的 current_id，在任务表记录失败结果和原因，并发送告警。日志补充 task_id、失败阶段（读取源表、写目标表、保存进度）、本页范围、可定位的出错记录 ID、异常堆栈、SQLState、数据库错误码和发生时间；这些诊断信息不要求成为任务表独立字段，任务表也不保存整批业务数据。记录状态或发送告警失败，不能阻止暂停流程继续执行。

另外记录本页写入结果是否未知。写入或提交响应超时可能发生在数据库已经提交之后，不能将超时等同于没有写入，也不能直接跳过该页。恢复位置不推进，先核实原操作，再依靠幂等和版本控制安全重做。

如果任务表所在数据库也不可用，失败状态可能无法落库，任务会残留为运行中。此时通过独立可用的日志和告警报告状态持久化失败；这些机制也可能故障，不承诺必然记录成功。存储恢复后核对任务及日志再修复状态，不能把“没有失败记录”当作没有失败。

**任意失败都暂停新领取**

失败范围不在当前线程内自动重试，也不直接改回待执行。任意任务失败都通知协调方暂停整体的新任务领取，其他已运行任务按 3.11 核实当前页、保存确认进度并退出；未执行任务继续留在任务表。因暂停而安全退出的任务按现有暂停状态处理，已完成成功的任务保持成功，不能把所有任务统一改为失败。

暂停信号需要各工作循环及时检查，多实例还需要共享控制；不能宣称某个任务失败的瞬间所有 SQL 都已停止。对于已经发出的请求继续核实结果，不通过取消 Future 就认定数据库操作结束。

**人工排查，不直接跳过错误数据**

人工根据异常、出错记录、数据库监控和代码配置定位原因并修复。连接超时可能来自数据库不可用、网络或连接池耗尽，不能仅凭异常名称判断宕机；数据问题也不能直接跳过后标记成功。即使数据库已经能够连接，也要核实业务读写和上次未决操作，而不是立即重跑。

例如当前确认进度为 1000，下一页某条记录字段过长导致写入失败：进度保留在 1000，记录问题记录 ID 并暂停新领取。人工确认是源数据、目标表定义还是转换代码的问题，按业务规则修复后再恢复。本例数字仅说明恢复位置，不是生产参数。

**按任务或全部未完成任务恢复**

采用人工触发的恢复接口，按 task_id 恢复单个任务，或对全部未完成任务逐项核实后恢复，不以直接手工改表作为常规恢复方式。接口用于检查原状态、防止重复恢复并保留失败日志；人工确认旧操作收尾是前置条件，接口不能仅凭状态字段证明这一点。不能直接将所有执行中任务批量重置为待执行，按以下顺序处理：

1. 确认依赖服务已恢复，或代码、配置、数据问题已修复；对未知结果先完成核实。
2. 确认原执行者已退出，原事务、在途写入及未决提交已收尾，避免两个执行者重叠迁移同一范围。
3. 从数据库任务表读取原扫描范围与最后确认进度，不重新生成覆盖原任务的范围，也不把成功任务重新置为待调度。
4. 保持整体领取关闭，恢复操作与正常领取互斥进行。保留失败日志后，通过任务 ID 和原状态条件更新，将已核实的失败任务改为待执行；暂停或残留执行中任务先逐项核实，再改为待执行。恢复不清空确认进度、不改变扫描范围，也不抹去失败信息；没有执行身份字段，禁止旧执行未结束就重置状态。
5. 核实完成后，由人工明确重新开启领取；单独将任务改为待执行不会自动解除整体暂停。本次工作循环已退出则重新启动，线程池已关闭则重新创建。生命周期管理防止重复启动，未恢复的失败任务不被普通循环领取。
6. 执行时以 id > current_id AND id <= end_id 读取下一页。已写成功但未确认保存进度的页可能被重复处理，按幂等及版本规则核实，确认整页后再保存新进度。

例如已确认进度为 1000，当前页写入部分成功后连接中断，不能直接将进度改为该页最后主键。原操作收尾并核实后，从 1000 之后重新读取该页；已成功数据按版本与幂等规则处理，避免旧值覆盖新值。本例数字仅解释恢复位置，不是生产批次配置。

**残留执行中任务需要人工核实**

进程崩溃可能来不及把任务改成失败，因此恢复不能只查失败任务，还应排查残留的执行中任务。本方案不维护执行者标识、执行尝试编号或用于自动接管的租约字段，不支持仅凭心跳超时就重置任务。

恢复前必须确认旧线程、进程及相关数据库操作已经停止，并核实未知写入结果。无法确认时，保持未完成状态并告警，不重新领取。状态条件更新只能防止普通并发重复领取，不能区分恢复前后的执行身份，不能据此声称旧执行无法覆盖新进度。

**失败历史与整体结果**

失败原因保存在任务表；恢复前将必要的失败信息写入日志，关联 task_id 和发生时间，不增加执行尝试编号或独立执行尝试表。日志保留策略和可靠性仍需落实，不能承诺状态库故障时一定保存成功。

受控恢复后，协调方重新汇总完整任务表。只有全部任务成功才判整体成功；点击恢复或数据库重新可用都不能直接改为成功。再次失败时记录新的失败原因和日志，保留原确认进度。

恢复位置继续遵循 016 的“最后确认进度、失败页允许重做”；任务领取和恢复过程的互斥、数据库操作收尾以及故障演练尚未验证。

## 4 已确认规则

- 新任务初始状态统一为待执行；暂停任务在恢复启动前经核实、通过恢复接口改为待执行，暂停生效期间禁止领取。
- 区分正常收尾与失败暂停收尾：任意失败立即告警并暂停，可保留未执行任务；本次执行结束不等于全部迁移成功。

- 表达易于理解、适用于面试口述；口述按拆分、领取执行、失败恢复、完成判定和暂停顺序展开，实现细节保留在详细方案。
- 本文保留迁移线程池设计总览职责；通用线程池知识已归入 `000_线程池` 目录，旧职责编号按当前文件布局修正。
- 补充线程池类型、核心线程数、最大线程数、队列类型选择和拒绝策略，并区分建议与已验证配置。
- 补充范围划分详细方案、任务描述含义、各配置选择理由、整轮完成判定，以及正常收尾和主动暂停的区别。
- 用户补充：旧表约有 3 亿条数据，主键递增；可按每个任务平均约 100 万条规划约 300 个任务。
- 任务表维护任务 ID、扫描起始 ID、扫描结束 ID、处理进度、处理结果和失败原因。
- 不维护批次 ID、执行者标识、执行尝试编号，不设批次结果表；直接从完整任务表汇总，失败优先，全部成功才判迁移执行成功。
- 最新方案采用专用固定 N 线程的工作循环，每个循环从数据库原子领取一个范围，当前范围收尾后再领取下一个；不再逐范围提交线程池任务。
- 由独立协调方监测工作循环、汇总完整任务清单和控制停止；循环退出或领不到任务不代表整轮成功。
- 完整任务描述和进度持久化到任务表，不预加载约 300 个范围对象；每个循环一次持有一个范围。
- 工作循环分页处理，确认本页结果并保存进度后解除数据引用，不累积整个范围数据。
- 线程数不是固定为 2；按连接预算、在线业务负载、迁移时限和多实例总并发压测选择。
- 历史迁移执行失败统一记录原因并告警，不自动分类重试；任意任务失败都暂停整体新领取，已有任务安全收尾，由人工排查修复。
- 通过人工触发的恢复接口，将核实后的失败或未完成任务改为待执行，再明确开启领取；恢复前确认旧线程、进程和数据库操作已停止并核实未知结果，不清空进度、不改变范围、不抹去失败信息。
- 受控恢复后重新汇总全部任务状态；失败信息通过任务表原因和日志保留，不维护独立执行尝试记录。
- 线程池不代替进度、幂等、事务和全局并发控制。
- 提交被拒、任务异常、结果未知和停止都不能直接记为迁移完成。

## 5 待确认或待验证事项

- N 的生产取值、连接预算及在线业务验收指标需压测确定。
- 工作循环启动、异常退出检测、暂停及重启恢复尚未验证；SynchronousQueue 与 AbortPolicy 为配置实现示例。
- 并发 N 下当前范围描述、分页数据和写入缓冲的内存峰值待测量。
- 单个约 100 万条范围的执行耗时、各路径数据引用释放及长时间运行的内存变化尚未验证。
- 工作循环启动拒绝、部分启动失败后的收尾与受控补建尚未验证。
- 源表主键类型、稳定性和迁移过滤条件是否满足示例前提。
- 任务表的具体结构、状态枚举及整体汇总的一致数据视图。
- 任务进度、结果保存与恢复操作的事务协议。
- 统一失败告警、人工恢复接口的状态检查、重复恢复防护及重新开启领取的控制流程。

- 状态存储不可用、进程崩溃、提交结果未知及恢复后再失败的故障演练。
- 实际零任务的迁移如何结束。
- 线程池生命周期、任务状态和协调方的衔接。
- 多实例部署下的全局并发和故障接管。
- 停止协议、JDBC 超时和在途写入核实。
