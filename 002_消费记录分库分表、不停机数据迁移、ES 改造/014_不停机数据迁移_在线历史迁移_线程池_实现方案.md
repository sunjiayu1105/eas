# 014_不停机数据迁移_在线历史迁移_线程池_实现方案

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。具体实现和运行效果尚未验证。

## 1 问题

线程池如何配合在线历史迁移完成并发控制、任务执行和安全停止？

## 2 面试口述精炼版本

口述内容字符数：762

**范围任务与配置**

旧表约有 3 亿条数据，主键递增，可按每个任务平均约 100 万条规划约 300 个任务。固定扫描上界，按数据分布拆成不重叠的左开右闭范围，主键跨度不等于记录数。专用 ThreadPoolExecutor 的核心数、最大数均为可配置的 N，使用容量为 Q 的 ArrayBlockingQueue。完整任务描述和进度保存在任务表，内存仅保留有限任务描述，执行时分页读写；每页结果与进度确认后释放数据引用。N、Q 分别按资源和内存预算压测确定，不按总任务数设置。

**派发与结果收集**

以 W=N+Q 限制已提交但未收集结果的任务数。有可领取任务、窗口有空位且允许继续派发时，通过 CompletionService 提交；成功才增加计数，AbortPolicy 拒绝后保留任务，按线程池状态退避或停止提交。限时 poll 收集结果，处理后释放名额，再决定是否补任务；暂停或结果未知时不补，释放名额不代表成功，也不代表立即重跑失败任务。

**任务进度与批次结果**

每个任务记录扫描起止 ID、确认进度、处理结果和失败原因。规划完成后，批次表按当前任务状态汇总：有失败则失败，无失败但未全部完成则执行中，全部可靠保存成功状态才成功，随后仍需一致性校验。

**正常收尾与主动暂停**

正常收尾在全部任务已提交后调用 shutdown，等待并核对结果；主动暂停则先停止提交，让任务在批次边界保存已确认进度后退出。暂停不算成功，异常或未知结果不推进进度。

**失败分类与恢复**

失败保留确认进度，结合异常和监控分类。已核实可重试的暂时故障，在任务内部有限退避，仍占原名额；重试耗尽或不可重试则结束并报告失败，不自动进入下一轮派发。数据库整体故障时暂停整轮。修复并核实旧执行者及未知写入已收尾后，通过恢复入口原子领取原任务，从确认进度继续，按幂等与版本规则重做未确认页。保留失败历史，恢复后重新汇总批次状态。

## 3 详细方案

### 3.1 主文档职责

本文说明迁移专用线程池的选择与调度衔接。限流由 012 维护，批次性能调优由 013 维护，线程数压测由 015 维护，断点续跑由 016 维护；通用线程池概念、参数、队列和拒绝策略见 `000_线程池` 目录。本文不把线程池配置当作任务进度、幂等或事务方案。

### 3.2 总体流程

~~~text
记录扫描边界，生成并可靠保存本轮完整范围任务清单
  → 最多维持 W=N+Q 个已提交但未收集结果的任务；完整清单保存在任务表
      ├─ 拒绝：保留待调度状态；容量恢复且线程池仍运行时重试
      └─ 接收：执行或进入有界等待队列，不标记完成
  → 分批读取、写入并核实结果
      ├─ 失败或未知：保留原恢复位置，报告未完成
      └─ 成功或安全跳过：保存本批进度，再读取下一批
  → 范围查询成功且为空：保存该范围成功状态
  → CompletionService 收集并处理结果，释放在途名额；允许继续时补充可派发任务
      └─ 失败任务不直接重派：分类、核实并受控恢复后，才能再次参与派发
  → 正常收尾：全部任务成功提交后关闭接收，收集剩余结果并核对清单
  → 所有范围成功：本轮迁移完成，进入一致性校验

执行途中需要主动暂停：
停止提交新任务 → 设置暂停信号 → 任务在批次边界收尾
  → 保存已确认进度并报告暂停 → 等待线程和在途数据库操作收尾
~~~

### 3.3 线程池边界

固定线程数只限制该线程池的工作线程数量；同进程其他线程池或多个实例仍可能增加数据库并发，不能代替全局并发控制。任务表保留完整清单，ArrayBlockingQueue 缓冲尚未执行的任务，CompletionService 的完成队列保存待收集结果。两个内存队列都占内存，不能替代进度持久化。shutdownNow 或 cancel(true) 只请求中断，不能单独证明数据库操作已经停止。

### 3.4 类型与线程数：专用线程池，可配置并发 N

采用专用 ThreadPoolExecutor，显式配置线程数、任务队列和拒绝策略，避免迁移占用在线请求的工作线程。线程资源隔离不等于数据库资源隔离，两者仍可能争抢连接、磁盘与锁。

corePoolSize 和 maximumPoolSize 均设为可配置的正整数 N，限制一次运行的池内并发，避免任务积压时自动扩容。N 不等于任务总数，也不固定为 2；约 300 个范围由最多 N 个工作线程分批处理。线程按需创建，构造后不保证已经启动 N 个线程。

N 按源库和目标库的连接预算、每任务占用连接数、数据库负载、在线延迟、迁移时限及实例数量压测确定。2、4、8 可作为候选测试点，不是生产配置；固定分页大小等其他条件，选择满足在线指标与迁移时限、且有资源余量的较小并发值。不能把连接池大小或 CPU 核数直接当作线程数。

本方案建议先在一次运行中保持 N 不变，调整时按 3.11 暂停收尾后用新配置恢复。配置可调不等于已经实现安全的在线热调节；若后续实现热调节，还需同步调整派发上限，降低线程数也不会立即停止在途数据库操作。

### 3.5 任务队列：小容量有界缓冲，全部任务持久化

采用容量为正整数 Q 的 ArrayBlockingQueue。核心数和最大数均为 N：最多 N 个池内工作线程执行迁移，最多 Q 个任务在执行队列等待。约 300 个范围任务的描述和进度记录持久化到数据库任务表，调度方按剩余名额分批读取待调度记录，不把全部任务对象或数据库记录预加载到内存。

有界队列仍占内存，只是限制等待数量。内存开销包括队列引用数组、Runnable 或 Callable 包装对象、Future、范围描述及其间接引用；任务闭包可能引用大列表，不能仅凭字段少就断言内存很小。任务只携带 task_id、来源表和扫描范围等必要描述，真正执行时才分页查询；完成结果也只返回必要状态，不返回整批数据列表。

N 控制数据库执行并发，Q 控制内存等待缓冲，二者分别配置。Q 不应直接设为总任务数，也不要求等于 N。结合单任务对象的保留内存、结果对象大小、迁移内存预算和调度开销选择小容量起点，再通过压测调整；分页读取占用的内存还应结合 N、每页记录数和字段大小单独评估。实际对象大小尚未测量，本文不提供未经核验的字节数。

例如 N=2、Q=2 仅为演示值：A、B 执行，C、D 等待，其他范围留在任务表；此时额外提交 E 可能因饱和被拒。该示例不是生产配置。有界缓冲避免每个新任务都必须立即找到接收线程，但不能保证永不拒绝，仍需保留 AbortPolicy 及恢复逻辑。

为了同时限制运行任务、排队任务和未收集结果，建议派发窗口 W=N+Q。“在途数”定义为提交成功但尚未收集结果的任务数，最多 W 个；完成结果未消费前仍占名额，避免 CompletionService 的默认完成队列长期积压。N、Q 在一次运行内保持稳定，调整前按暂停流程收尾。

### 3.6 拒绝策略：AbortPolicy 反馈拒绝，调度方保留任务

采用 AbortPolicy 抛出 RejectedExecutionException。提交成功才增加在途数，并保存 Future 与 task_id 的关联；提交抛拒绝异常时不增加在途数、不等待该次提交的完成结果，保留待调度任务。若提交前已领取任务，则需安全释放或恢复该领取状态，不能直接遗失该范围。

线程池仍运行时，由调度方退避后重试，期间继续检查暂停信号并收集其他完成结果。教学示例可设置提交拒绝重试间隔 10 毫秒、完成结果 poll 等待 1 秒，二者均可配置且需压测；不是数据库任务超时，也不是生产取值。不得无间隔忙重试；即使当前在途数为 0，提交被拒后也要继续按退避逻辑尝试，不能只阻塞等待一个不会出现的完成结果。

线程池关闭时停止向其提交，任务留待恢复。持续拒绝、线程创建失败等情况需暴露给监控并暂停派发，告警阈值待确认，不能无限隐蔽重试。

不使用 DiscardPolicy 或 DiscardOldestPolicy 静默丢弃当前或队头任务。CallerRunsPolicy 会让调度线程执行迁移，可能突破池内并发上限，且关闭后丢弃任务，因此不采用。AbortPolicy 本身不持久化任务、不自动重试，可靠性仍依赖任务表和调度恢复协议。

### 3.7 配置片段与完成队列

以下为 Java 8 初始化方法内的配置片段，需要导入 java.util.concurrent 中的对应类型。N、Q 分别为配置注入并经过资源评估的正整数，TaskResult 为任务返回结果类型，不是 JDK 自带类型。keepAliveTime 为 0 秒且不开启核心线程超时；固定池内并发时不靠空闲超时调节压力。

```java
if (N <= 0 || Q <= 0) {
    throw new IllegalArgumentException("N and Q must be positive");
}
ThreadPoolExecutor migrationPool = new ThreadPoolExecutor(
        N, N,
        0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<Runnable>(Q),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy());
ExecutorCompletionService<TaskResult> completion =
        new ExecutorCompletionService<>(migrationPool);
```

CompletionService 是结果协调组件，不是另一种线程池。默认完成队列保存已完成 Future，与 ArrayBlockingQueue 待执行任务队列用途不同。前者由调度方及时消费；在途数按“已提交但未收集结果”计数，因此已完成但尚未消费的结果也占名额，不会仅因任务完成就无限追加提交。

线程池跨范围任务复用；所有任务都经同一个受控派发入口提交，不能由其他代码绕过 W 的派发窗口提交迁移任务。成功返回的 TaskResult 也必须对应已可靠保存的任务结果，不能只依赖 Java 方法正常返回。

shutdownNow 和 cancel(true) 只请求中断，不能证明 JDBC 操作结束。主动取消 Future 后，不应仅因其显示已取消就释放数据库并发名额；本方案优先采用合作式暂停，确认旧任务与数据库操作收尾后再恢复。

来源参考：[ThreadPoolExecutor API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[ArrayBlockingQueue API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ArrayBlockingQueue.html)、[ExecutorCompletionService API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ExecutorCompletionService.html)。本次未联网核验或执行代码测试；方案选型已获用户授权写入，不代表已部署或生产最优。

### 3.8 详细拆分方案：固定边界，按范围分页

用户补充的项目背景：旧表约有 3 亿条数据，主键递增。按每个任务平均约 100 万条记录估算，3 亿 ÷ 100 万 ≈ 300，因此可规划约 300 个范围任务。这是工作量规划，不是 300 个工作线程，也不是要求每个范围恰好有 100 万条；实际数据量和各范围记录数未在本次查询核验。

递增主键仍可能存在空洞，不能直接把主键跨度 100 万当成 100 万条记录。具体范围边界需结合主键分布和记录量测定；可以保持范围连续且不重叠，允许各任务记录数不同，再按分布调整过大或过小的范围。边界生成方式尚待落实。下面三个小范围仅用于演示左开右闭规则，不代表项目仅规划三个任务。

以下为建议实现方案，前提是源表具有适合稳定排序和范围查询的主键。本例使用正数、唯一且迁移期间不改变的数值主键 id，实际主键类型、迁移过滤条件及是否满足此前提仍待核实；不能直接套用于复合主键或会变更的主键。

开始规划时记录本轮最大主键 endId，将其与来源表、迁移条件和本轮标识一起保存，恢复时沿用原边界。假设历史范围为 (0, 300000]，可按 100000 的主键跨度拆成三个范围，所有数值均为教学示例：

| 任务 | 区间 | 查询边界 |
| --- | --- | --- |
| T1 | (0, 100000] | id > 0 AND id <= 100000 |
| T2 | (100000, 200000] | id > 100000 AND id <= 200000 |
| T3 | (200000, 300000] | id > 200000 AND id <= 300000 |

统一左开右闭，前一个任务的上界等于后一个任务的下界，边界记录只属于一个范围。范围跨度不等于记录数：主键可能有空洞，数据也可能分布不均，因此不能保证三个任务耗时相同。任务清单生成完毕后记录“规划完成”，核对范围首尾、连续性和唯一性，再据此判断整轮是否完成，不能只统计已经提交的任务。

每个范围从自己的最后确认位置 lastId 继续，初始值为区间下界。下面是参数化查询示意，不是可直接运行的完整 SQL；表名取自受控配置，值参数绑定传入，迁移过滤条件各页保持一致。

```sql
SELECT 所需字段
FROM 源表
WHERE id > :lastId
  AND id <= :rangeEnd
ORDER BY id
LIMIT 500;
```

500 是每页最多读取的记录数示例，不是主键跨度或生产配置。执行过程如下：

1. 成功读取一页；查询异常必须报告失败，不能当作空页。
2. 按分片规则写入目标表，逐项确认写入成功或按版本规则可安全跳过。
3. 本页全部结果已确认后，保存本页最后一个主键为该任务进度；保存成功后才读取下一页。
4. 写入失败、部分结果未知或进度保存未确认时，不推进恢复位置，报告未完成；恢复可能重做本页，因此仍需幂等与版本控制。
5. 查询成功且结果为空，说明范围扫描结束；成功状态可靠保存后，才能将该范围计为成功。最后一页可能不足 500 条，主键有空洞时 lastId 也不一定等于 rangeEnd，不能只按游标等于上界判断完成。

固定 endId 只限定扫描边界，不形成数据库快照。双写需覆盖迁移期间的业务变更，扫描到的旧版本不能覆盖新版本；低于 endId 的晚提交数据也不能仅靠一次主键扫描保证捕获，仍需同步与一致性校验兜底。本方案不能据此声称已实现无遗漏迁移。

与 [016 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_断点续跑.md>) 保持一致：按独立范围保存进度是本篇建议落地方式，不用全局最大主键掩盖较小范围的失败。存储结构和事务边界尚未实现验证。

### 3.9 任务描述：待派发的是范围信息，不是整批数据

建议任务描述只保存标识和扫描范围，例如下面的 Java 8 数据结构；字段为设计示例：

```java
final class RangeTaskSpec {
    final String taskId;       // 与本轮任务清单中的任务关联
    final String sourceTable;  // 来自受控配置，不能接受任意表名
    final long startExclusive;
    final long endInclusive;

    RangeTaskSpec(String taskId, String sourceTable,
                  long startExclusive, long endInclusive) {
        this.taskId = taskId;
        this.sourceTable = sourceTable;
        this.startExclusive = startExclusive;
        this.endInclusive = endInclusive;
    }
}
```

调度方根据 RangeTaskSpec 创建 Callable<TaskResult> 并交给 CompletionService；后者包装为交给线程池执行的 Runnable，内部维护 Future。ArrayBlockingQueue 最多保存 Q 个待执行包装对象。任务持有范围描述和执行服务引用，真正执行后才读取持久化进度并分页查数据，不应先加载整个范围的数据再通过闭包持有。

例如 T2 等待派发时只保存“查哪个表、从 100000 到 200000”的信息；得到工作线程后，才开始按每页最多 500 条读取。这样内存数据量主要受正在执行的任务和批次大小影响，而不是受所有待派发范围的数据总量影响；字段大小及任务描述大小仍需评估。


**长时间执行与数据引用的生命周期**

每个任务处理约 100 万条记录，可能持续较长时间，实际耗时需测量。执行期间，任务 ID、范围边界、进度和执行所需的服务引用可以持续保留；并不因此把该范围的 100 万条数据库记录同时保存在内存。

数据按页读取，例如每页最多 500 条是教学示例。应在本页写入结果已确认、进度成功保存后，解除对本页记录及不再需要的写入缓冲的引用，再读取下一页；不得将各页不断追加到任务级大列表，也不要让闭包、日志缓存或结果对象长期持有历史页。异常路径若需保留现场，应保留必要标识和错误信息，不能无界积累数据；未确认进度仍按原位置恢复。

释放引用不等于内存立刻归还：只有对象不再被其他存活引用持有时，才具备被垃圾回收器回收的条件，实际回收时机由 JVM 决定。不能通过任务执行时间长直接判断内存一定持续增长，也不能只因采用分页就保证没有内存泄漏。

因此，长期保留的是有限任务的必要描述；分页记录和写入缓冲随每页处理循环使用。实际内存峰值仍取决于并发 N、页大小、字段大小、驱动与批量写入缓冲、未收集结果及引用保留情况，需实测。数据库任务表保存完整清单，不等于应用同时加载约 300 个任务对象。

任务等待队列和完成队列都不能可靠保存迁移进度。进程重启后，应根据持久化清单和每个范围的确认进度恢复；重新派发前必须确认旧执行者及在途操作已经收尾，防止同一范围重叠执行。多实例领取与防重协议仍待落实。

### 3.10 完成判定：以完整任务清单为准

用户已确认采用任务进度表和批次结果表：每个范围任务维护一条进度记录，每轮迁移维护一条批次记录。这里“批次”指包含约 300 个范围任务的整轮迁移，不是任务内分页读取的单个数据批次。两张表的用途与汇总规则已经确认，具体表名、字段名和存储实现仍未验证。

**任务进度表**

用户指定的业务字段如下；字段名为实现建议，边界沿用左开右闭约定。

| 业务字段 | 建议字段名 | 含义 |
| --- | --- | --- |
| 扫描起始 ID | start_id | 范围下界，不包含；恢复时不能把它改成当前进度 |
| 扫描结束 ID | end_id | 范围上界，包含；本轮固定 |
| 当前进度 | current_id | 最后成功保存的已确认位置，初始为起始 ID |
| 处理结果 | status | 记录待调度、运行中、成功、失败、暂停等结果；具体枚举为建议 |
| 处理失败原因 | failure_reason | 失败阶段与原因，供排查；不能只记录异常而把结果标成成功 |

为标识任务及关联所属批次，建议另加 task_id 和 batch_id。任务失败时保留原确认进度并记录原因；被拒尚未执行的任务仍可保持待调度，不等于迁移执行失败。查询成功且范围为空也可完成，不能要求 current_id 必须等于 end_id。

**批次结果表**

用户要求记录整轮执行结果。建议至少有 batch_id 和 execution_result，并增加规划完成标记 plan_completed 及计划任务数 planned_task_count，防止任务尚未生成完毕就误判成功。计划任务数保存实际生成数量，约 300 只是估算，不能硬编码为完成门槛。

任务清单完整后，按以下优先级汇总并保存批次结果：

1. 任意任务为失败：批次结果为失败，即使同时存在未完成任务，仍优先判失败。
2. 没有失败任务，但任意任务尚未成功完成：批次结果为执行中。待调度、运行中、暂停或结果未知都不能计为成功。这里“执行中”表示整轮尚未完成，不保证此刻有线程正在执行。
3. 所有计划任务都已可靠保存成功状态：批次结果为执行成功。成功不仅要求执行线程结束，还要求扫描结果和进度已确认。

规划未结束或实际任务记录数与计划数不符时不得判成功；不能对暂时为空的任务表直接得出“全部成功”。零任务迁移的最终判定另行确认。

建议由同一批次的汇总操作串行执行，在一致的数据视图下重新统计后写入批次表，避免多个工作线程分别拿到旧计数并覆盖新结果。任务结果是明细依据，批次结果是汇总；若任务结果已保存而批次更新失败，应可重新汇总修复，不能报告整体成功。具体锁、事务边界及故障恢复协议尚待实现验证。

批次失败只是结果汇总，不代表其他工作线程已停止。数据库整体故障时暂停整轮新任务派发；单个任务失败是否需暂停其余任务，按故障范围判断，具体判定阈值待确认。同一批次允许受控恢复，按当前任务状态重新汇总；失败执行尝试历史保留，不能清空历史来伪装首次成功，详见 3.13。

任务等待队列为空也不能说明工作已完成，工作线程可能仍在执行或完成结果尚未收集；“线程池终止”只说明池内工作已结束，任务可能失败或因暂停退出。两者都不能单独证明迁移成功。

单个范围只有扫描结束、所有批次处理结果已确认、进度及成功状态均保存成功，才能计为成功。进度或成功状态保存失败、任务抛异常、取消、暂停、结果未知，都不能计为成功。整轮完成必须同时满足：任务规划已完成，且完整清单中的每个范围都已可靠标记成功；没有遗漏的待调度、运行、失败、暂停或未知结果任务。

通过 CompletionService.submit 收集每次成功提交的 Future，通过完成队列取出后调用 get 获取结果或 ExecutionException。但任务不能吞掉异常后把正常返回伪装成成功，正常返回的“暂停”结果也不等于成功。被拒任务可能没有返回 Future，仍要留在任务清单中；进程重启后也无法依赖原内存中的 Future 恢复。

例如 T1 成功、T2 失败、T3 运行中，批次结果为失败；T1、T2 成功而 T3 被拒尚未重试时，批次结果为执行中，即使队列为空、两个 Future 都成功，本轮仍未完成；只有三个任务都成功并保存结果后，才能汇总为执行成功。所有范围成功之后还需执行一致性校验，不能直接据此切换流量。

### 3.11 正常收尾与主动暂停分别处理

**正常收尾：全部提交后关闭接收，等待结果**

派发指调用 execute 或 submit 提交范围任务。正常收尾时，先确认任务规划已结束、所有范围均已提交处理，没有尚待首次提交或被拒后待重试的范围，再调用 shutdown 停止接收新任务。已接收任务继续执行，不设置主动暂停信号；继续消费 CompletionService 的剩余完成结果，直到本次在途数归零，再用 awaitTermination 等待线程池终止，并按 3.10 核对任务表和批次结果。取完结果不代表工作线程已经完全退出。

不必等所有任务执行完才调用 shutdown。等待超时也不代表任务已停止，更不能标记迁移成功；等待上限需结合实际范围耗时制定，本文未给出生产值。如果已接收任务失败，需要保留失败范围，在确认原操作收尾后另行恢复；已经关闭的线程池不能再次接收重试任务。

**主动暂停：尚未迁完，提前停止提交和继续扫描**

例如数据库负载超过已约定的业务验收阈值，需要提前暂停。建议按以下步骤处理，阈值与停止协议尚待验证：

1. 先停止调度方继续调用 execute、submit，保留未提交或被拒的范围。
2. 设置线程间可见的暂停信号，例如 AtomicBoolean；同时调用 shutdown 停止该线程池接收新任务。
3. 运行任务在本批结果与进度确认后、下一批开始前检查信号，报告暂停并退出。当前批失败或结果未知时报告未完成，保留原确认进度，不等待无限重试才允许退出。
4. 尚未派发的范围留在任务表；已排队任务被工作线程领取后，先检查暂停信号，未开始扫描则保留可恢复状态并退出。shutdown 会继续处理排队任务，因此不能省略入口检查，也不能把暂停返回当作成功。
5. 等待线程收尾，并单独核实数据库在途写入和未知提交结果；确认后再允许恢复执行者接管。

假设 T1 扫描了一部分、T2 尚待派发，暂停后 T1 可退出执行，T2 继续保持未完成，但 T1、T2 都不能被标记为迁移成功。若某个范围在暂停前已经完整完成并保存成功，则保留其成功状态。

Java 行为参考：[ExecutorService 的 shutdown、awaitTermination](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ExecutorService.html)、[Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。本次未联网核验或执行代码测试。

### 3.12 有限派发与按完成顺序收集结果

建议由一个调度循环统一维护本轮派发状态；多实例仍需共享任务领取和全局并发约束，不能仅靠各自的 N 保证不重叠；每次只读取派发窗口内所需的待调度记录，避免另建一个无界内存待办列表。

**什么时候提交：有待派发任务，窗口有空位，而且允许继续派发**

调度方通过 completion.submit 提交任务，由 ThreadPoolExecutor 决定交给工作线程还是放入 ArrayBlockingQueue，不直接调用线程池队列的 put 或 offer。不能只看等待队列是否为空来决定补任务，因为工作线程可能仍在执行，完成队列也可能还有结果未收集。

用 inFlight 表示“提交成功但尚未收集结果”的任务数，包括正在执行、等待执行以及已经完成但结果尚未收集的任务。派发窗口上限 W=N+Q；同时满足任务表还有可领取的待派发范围、inFlight < W、未暂停且线程池仍接收任务时，才尝试提交。窗口有空位是提交条件，不是一定提交成功的保证。

**启动填充，收集结果后补充**

1. 完整任务清单与规划完成标记持久化后，初始化在途计数为 0，选择尚未提交的范围。
2. 按可用名额读取任务并逐个尝试 completion.submit；提交成功后保存返回的 Future 与任务标识关联，inFlight 加 1。重复填充到 W，或没有可派发任务、遇到暂停或拒绝时停止本轮填充；拒绝不增加计数，按 3.6 保留任务并处理。
3. 有在途任务时，通过 completion.poll(timeout, unit) 获取已完成 Future。等待超时仅代表当前没有结果，应检查暂停信号、心跳或长时间未完成任务，不得直接判失败或成功；需要响应控制指令时不使用无限等待的 take。
4. 取得完成 Future 后，调用 get 检查返回值或 ExecutionException，核对并保存任务结果；异常不能被吞掉而标成功，暂停也不是成功。收集到的 Future 从映射移除，在途数减 1；结果持久化未确认时暂停新派发并保留未决状态，不能把空出的计算名额当作该任务已完成。
5. 没有暂停且任务清单仍有待派发范围时，继续补交。单个范围执行失败不等于自动取消其他任务；数据库整体故障时暂停新派发，运行任务按停止协议收尾，详见 3.13。提交成功与任务结果持久化之间的崩溃窗口，由任务表和恢复协议核实，不由内存计数证明安全。
6. 确认所有范围都已成功提交本次执行、没有被拒后待提交的任务，调用 shutdown；继续收集剩余结果。在途数归零后核对线程池终止、任务清单和持久化结果，得到本轮最终结果。

普通派发只领取可调度状态的任务，不能把失败任务直接混入下一次待办查询。成功或失败的执行结果被收集后，均可释放该次提交的窗口名额；是否继续提交其他任务，仍取决于故障范围和状态持久化结果。主动取消不作为旧执行结束的证明，沿用 3.7 的限制。

| 收集到的结果 | 状态处理 | 是否补充其他任务 |
| --- | --- | --- |
| 成功 | 核对进度与成功状态已可靠保存 | 允许继续派发时补充 |
| 失败 | 保存原因，保留最后确认进度，不直接重派该任务 | 按故障范围判断 |
| 暂停 | 保存确认进度，保持未完成 | 本轮暂停期间不补充 |
| 结果或状态持久化未知 | 保留未决状态，先核实 | 暂停新派发 |

例如 T1 因局部数据问题失败、T2 尚待执行：记录 T1 失败后，若确认不影响其他范围，可以继续派发 T2，修复后再恢复 T1；若判断为数据库整体故障，T2 也暂不提交。窗口名额释放不等于任务成功，更不等于失败任务已经满足恢复条件。

take() 可以阻塞等待并取走一个完成结果，适合解释“等一个完成，再补一个”的基本机制。本方案需要定期响应暂停和检查心跳，因此使用限时 poll；超时未取得 Future 时不减少 inFlight。具体等待时间沿用 3.6 的教学示例，生产值待确认。inFlight 为 0 时不等待完成结果，应检查剩余待派发任务、拒绝退避或收尾条件。

例如 N=4、Q=8、W=12 均为教学演示值，不是生产配置。启动时最多成功提交 12 个任务，其中最多 4 个运行、8 个等待。收集一个完成结果后，inFlight 从 12 减为 11；结果处理已确认、还有待派发任务且没有暂停时，再尝试补交一个，成功后恢复为 12。如果发现数据库整体故障需要暂停，即使窗口有空位也不补任务。

**空位不保证提交成功**

完成结果进入完成队列时，工作线程可能尚未返回取任务循环；即使调度方已收集结果、释放窗口名额，等待队列仍可能暂时满着。线程池也可能在检查之后被关闭，因此仍需捕获 RejectedExecutionException。拒绝后保留任务，不增加 inFlight，不等待该次提交的结果；线程池仍运行时退避重试，已经关闭则停止向它派发，不进行忙循环。

进程重启后，Future 映射和计数均不能复用，按任务表恢复；恢复前确认旧执行者与在途数据库操作收尾。仅有批次“失败”结果并不证明所有已提交任务结束，最终反馈仍须核对执行是否收尾。批次表继续沿用失败、执行中、成功三个结果，不在此次修改中新增“暂停”结果；暂停体现在任务状态和控制信号中。

### 3.13 执行失败：分类、核实与恢复派发

以下为用户授权写入的设计方案，不代表已实现故障识别或自动恢复。失败分类用于选择处置路径，不能只凭异常名称断言根因。

**保存失败现场，保留确认进度**

任务失败时保留最后成功保存的 current_id，记录失败结果和原因。建议补充失败阶段（读取源表、写目标表、保存进度）、task_id、batch_id、执行尝试编号、本页主键范围、异常类型、SQLState、数据库错误码、时间及重试次数；用日志标识关联完整堆栈，任务表不保存整批业务数据。

另外记录本页写入结果是否未知。写入或提交响应超时可能发生在数据库已经提交之后，不能将超时等同于没有写入，也不能直接跳过该页。恢复位置不推进，先核实原操作，再依靠幂等和版本控制安全重做。

如果任务表所在数据库也不可用，失败状态可能无法落库，任务会残留为运行中。此时通过独立可用的日志、告警和心跳观测报告状态持久化失败；这些机制也可能故障，不承诺必然记录成功。存储恢复后核对任务及日志再修复状态，不能把“没有失败记录”当作没有失败。

**按证据区分故障**

| 分类 | 可观察现象 | 处理原则 |
| --- | --- | --- |
| 疑似下游暂时故障 | 连接失败、中断、服务不可用 | 结合数据库监控、连接探测、其他任务表现核实依赖状态 |
| 事务冲突 | 死锁、锁等待超时 | 核实事务是否回滚、是否仍有未决操作，再按规则有限重试 |
| 代码、配置或数据问题 | 空指针、SQL 语法错误、字段不存在、权限不足、转换失败 | 停止盲目重试，修复后再恢复 |
| 原因或结果未知 | 请求超时、提交响应丢失 | 保留原进度，先排查和核实，不自动标成功或无限重试 |

例如连接超时可能由数据库宕机、网络故障、连接池耗尽或慢 SQL 占用连接造成。异常堆栈说明出错位置，SQLState 和错误码提供分类线索，监控与探测提供依赖状态证据；多个任务同时失败支持公共依赖异常的判断，但仍不能单独证明数据库宕机。不得捕获所有 SQLException 后统一认定可重试。

**任务内部重试与执行结束后的恢复分开**

仅对已经明确允许重试、且结果与旧操作已核实的暂时故障执行有上限的退避重试。可将“初次失败后最多重试 3 次，间隔 1、2、4 秒”作为教学示例；生产次数、退避和抖动参数待确认，不适用于所有 SQL 异常。超过上限记录失败并告警；代码、配置、数据问题和未核实的未知结果不按此规则自动重试。

有限重试在原任务内部执行，任务尚未返回，Future 尚未完成，仍占原来的 inFlight 名额；不另向线程池提交同一范围的副本。每次重试前检查暂停信号，暂停时按停止协议收尾。只有本页全部结果与进度确认后才能继续下一页。

重试耗尽或出现不可重试问题时，原任务结束并报告失败；不能在收集失败结果后立即无条件重新提交。问题修复并满足下述恢复条件后，通过恢复入口使原任务重新具备可调度资格，再由正常窗口领取和提交。恢复使用新的执行尝试，成功任务保持成功，不重复派发；只有尚无已确认进度时，才从原范围下界开始扫描。

数据库整体故障时暂停本轮新派发，并按 3.11 通知已有任务合作式收尾，避免约 300 个任务不断请求故障库；暂停不意味着正在执行的 SQL 已终止。下游恢复后才进入恢复核实流程，不能仅依靠一次连接成功就证明业务读写已经恢复。

**按任务或批次恢复**

提供以 task_id 或 batch_id 指定范围的恢复入口，按以下顺序执行：

1. 确认依赖服务已恢复，或代码、配置、数据问题已修复；对未知结果先完成核实。
2. 确认原执行者已退出，原事务、在途写入及未决提交已收尾，避免两个执行者重叠迁移同一范围。
3. 从数据库任务表读取原扫描范围与最后确认进度，不重新生成覆盖原任务的范围，也不把成功任务重新置为待调度。
4. 在受控恢复操作中保留上一执行尝试，创建新的尝试编号。通过带原状态和版本条件的原子更新领取任务，只有更新成功者可以派发；具体字段、锁和事务协议仍需实现验证。
5. 线程池已关闭则由生命周期管理逻辑重新创建，再通过现有有界派发窗口提交。提交被拒时保留可恢复状态，不丢失任务，不把它计为执行成功。
6. 执行时以 id > current_id AND id <= end_id 读取下一页。已写成功但未确认保存进度的页可能被重复处理，按幂等及版本规则核实，确认整页后再保存新进度。

例如已确认进度为 1000，当前页写入部分成功后连接中断，不能直接将进度改为该页最后主键。原操作收尾并核实后，从 1000 之后重新读取该页；已成功数据按版本与幂等规则处理，避免旧值覆盖新值。本例数字仅解释恢复位置，不是生产批次配置。

**识别失联任务，防止重复接管**

进程崩溃可能来不及把任务改成失败，恢复不能只查询失败任务。建议记录执行者标识、执行尝试编号、心跳或租约到期信息，用于发现长时间残留的运行任务；心跳间隔和租约时长需结合长事务及网络暂停测定，具体生产值待确认。

心跳过期只说明可能失联，不证明旧进程或数据库操作已经停止。接管前要确认旧执行者收尾，或实现能够阻止旧执行者继续产生有效写入的隔离机制。仅在任务表更新一个新执行者标识，并不能阻止旧线程继续写目标数据库；无法确认安全时保留待核实状态并告警，不自动并发重跑。

**执行历史与批次状态回转**

建议使用独立执行尝试记录，至少关联 task_id、attempt_id、开始与结束时间、结果和失败原因。当前任务记录用于调度与恢复，历史用于排查；恢复时不直接清空旧失败原因。旧尝试也不能在新尝试开始后覆盖其任务进度或状态，更新需校验执行尝试身份。

同一批次允许恢复后重新汇总当前任务状态：失败任务经核实并正式转入待调度或运行中，若已没有其他失败任务但仍有未完成任务，批次变为执行中；若仍有任务失败，则仍为失败；全部计划任务成功才变为成功。仅点击恢复或探测到数据库可用，不直接把批次改成功。新一轮执行又失败时，新增失败历史，并按同一规则汇总。

上述恢复入口、分类、重试和状态回转与 016 的“保留最后确认进度、失败页允许重做”一致，具体持久化事务、并发领取和故障演练尚未验证。

## 4 已确认规则

- 本文保留迁移线程池设计总览职责；通用线程池知识已归入 `000_线程池` 目录，旧职责编号按当前文件布局修正。
- 补充线程池类型、核心线程数、最大线程数、队列类型选择和拒绝策略，并区分建议与已验证配置。
- 补充范围划分详细方案、任务描述含义、各配置选择理由、整轮完成判定，以及正常收尾和主动暂停的区别。
- 用户补充：旧表约有 3 亿条数据，主键递增；可按每个任务平均约 100 万条规划约 300 个任务。
- 每个任务维护进度记录，包含扫描起始 ID、扫描结束 ID、当前进度、处理结果和处理失败原因。
- 另设批次表记录整轮结果，按失败优先、无失败但未全部完成则执行中、全部成功完成才成功的顺序汇总。
- 最新方案采用可配置核心数与最大数 N、容量为 Q 的 ArrayBlockingQueue、AbortPolicy 和 ExecutorCompletionService；调度方分批补充，建议派发窗口 W=N+Q。
- 明确补任务时机：启动按窗口填充，收集结果后释放名额；有待派发任务且允许继续派发时才补交。提交成功才增加在途数，暂停时不补交，窗口有空位仍需处理拒绝。
- 完整任务描述和进度持久化到数据库任务表，调度方仅按可用名额分批读取并提交，不把约 300 个任务对象全部预加载到内存。
- 内存队列只缓冲必要任务描述；执行时分页读取，本页处理并保存进度后解除数据引用，不累积整个范围数据。队列容量不直接取总任务数。
- 线程数不是固定为 2；按连接预算、在线业务负载、迁移时限和多实例总并发压测选择。
- 增加失败分类、日志与监控核实、有限重试、按任务或批次恢复入口及执行尝试历史；恢复前确认旧执行者和未知写入结果。
- 区分任务内部有限重试与结束后的恢复：内部重试仍占原派发名额；失败结束后不直接进入下一轮普通派发，满足恢复条件后再调度。
- 同一批次受控恢复后按当前任务状态重新汇总，可从失败回到执行中或成功，保留全部失败尝试历史。
- 线程池不代替进度、幂等、事务和全局并发控制。
- 提交被拒、任务异常、结果未知和停止都不能直接记为迁移完成。
