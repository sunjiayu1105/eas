**一次提交，固定并发**

本方案一次只运行一个迁移实例。启动时查询全部待执行任务，只加载任务描述，一次性提交给固定 N 个线程的专用线程池，保存每次提交返回的 Future。N 按数据库预算压测确定，队列容量按本次任务数设置并限制任务总数。排队对象会持续占内存，但不提前加载各范围的数据；真正执行后才分页读写，每页结果和进度确认后再继续。

**失败立即停止新处理**

任意任务失败，就设置共享停止信号、记录原因并告警，不自动重试。运行中的任务核实当前页并保存确认进度后退出；排队任务轮到执行时先检查信号，不再扫描，保持待执行。不能只调用 shutdown，因为它仍会执行排队任务。

## 3 详细方案

### 3.1 主文档职责

本文说明迁移专用线程池的选择与调度衔接。限流由 012 维护，批次性能调优由 013 维护，线程数压测由 015 维护，断点续跑由 016 维护；通用线程池概念、参数、队列和拒绝策略见 `000_线程池` 目录。本文不把线程池配置当作任务进度、幂等或事务方案。

### 3.2 总体流程

完整任务清单入库 → 确认没有旧迁移实例运行 → 核实并恢复暂停或失败任务 → 查询本次全部待执行任务描述 → 校验数量和内存预算 → 逐个提交到固定线程池并保存 Future → 关闭线程池提交入口 → 等待所有已提交任务收尾 → 核对完整任务表。

“一次提交”指启动阶段集中逐个 submit，不是一次 SQL 搬完数据，也不是同时启动约 300 个线程。正常流程不再设置长期工作循环从任务表反复领取；若提交过程中发生停止或拒绝，则中止后续提交，未提交任务仍在任务表。

### 3.3 适用条件与实现边界

本方案限定同一时刻只有一个迁移执行实例，包括同进程重复启动、跨机器启动及恢复启动。启动入口必须防重；仅有单机锁不能防止另一台机器运行。单实例保障方式尚需落实，无法确认旧实例停止时不得启动新实例。

通过接受有限数量轻量任务对象长期占用内存，省去数据库持续领取循环和派发窗口控制。实际内存必须测量；任务数持续增长、超过上限或需要多实例接管时，应重新评估方案，不直接改成无界队列。

来源：[参考文章_04：工具架构与性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:192>)支持分批和并发调整方向；本文的一次提交与停止协议属于设计，未验证运行效果。

### 3.4 类型与线程数：专用固定线程池

手工创建 ThreadPoolExecutor，核心数与最大数都设为正整数 N，线程执行的是一个个范围任务。N 依据连接预算、数据库负载、在线业务延迟和迁移时限压测确定，2、4、8 仅为候选测试值。一次运行中不改变 N，需要调整时先停止并核实收尾。

每个范围同步分页处理，不再内部创建迁移线程。专用线程池隔离线程资源，但仍会与在线业务竞争数据库连接、锁和磁盘资源。

### 3.5 有界队列与内存预算

令 M 为本次查询到的待执行任务数，使用容量 M 的 ArrayBlockingQueue，固定 N 个线程。正在执行的任务不占等待队列容量；容量 M 足以缓冲本次清单，前提是只通过这一入口提交该清单一次。

必须先检查 M 不超过配置的任务总数上限 MAX_TASKS，再创建队列和任务对象。MAX_TASKS 由单任务描述、包装对象、Future 及其引用的内存测量确定，生产取值待确认；约 300 个任务是规划估算，不是无限增长的许可。示例 M=300 表示队列最多缓冲 300 个任务，不代表实际必然排满。

内存长期保留 M 个任务描述及至多 M 个 Future，并可能保留返回结果；任务结果只返回状态，不返回整页数据。约 300 个轻量对象也占内存，不能声称可忽略。分页数据的峰值另受 N、每页条数、字段和驱动缓冲影响。

先核对数据库数量，再以最多 MAX_TASKS+1 条的受限查询加载描述，超过上限即拒绝启动；规划完成后禁止并发新增任务或修改恢复状态，避免查询期间清单变化。M=0 时不创建容量为 0 的队列，直接核对完整任务表，不能据此自动判成功。

### 3.6 拒绝策略与提交中断

采用 AbortPolicy，提交失败抛 RejectedExecutionException。保存成功返回的 Future；被拒任务没有本次可等待的 Future，仍留在任务表，不能静默丢弃或标成功。不用 CallerRunsPolicy，以免调度线程执行迁移而增加数据库并发。

发生提交拒绝、线程创建失败、执行异常或状态保存失败时，先设置停止信号，再记录与告警，停止后续提交。已接收任务按入口及分页边界检查信号，未提交范围保持待执行。不要自动重复提交被拒任务；核实收尾后人工处理。部分提交失败仍需等待所有已经接收的任务，不能直接返回后启动另一组线程。

### 3.7 初始化与等待结果

以下为 Java 8 核心流程示意，需导入 java.util、java.util.concurrent 和 AtomicBoolean；TaskSpec、TaskResult 及业务方法均需实现，不是可直接运行的完整代码。任务查询、数量上限、单实例防重和旧操作收尾在进入片段前完成。

```java
int m = specs.size();
if (N <= 0 || MAX_TASKS <= 0 || m > MAX_TASKS) {
    throw new IllegalArgumentException("Invalid thread or task count");
}
if (m == 0) {
    // 没有待执行任务不代表全部成功，必须查完整清单。
    inspectAllTaskStates();
    return;
}
AtomicBoolean stop = new AtomicBoolean(false);
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        N, N, 0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<Runnable>(m),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy());
List<Future<TaskResult>> futures = new ArrayList<>(m);
try {
    for (TaskSpec spec : specs) {
        if (stop.get()) {
            break;
        }
        futures.add(pool.submit(() -> executeRange(spec, stop)));
    }
} catch (RuntimeException submissionFailure) {
    stop.set(true);
    reportSubmissionFailure(submissionFailure);
} finally {
    pool.shutdown(); // 已接收任务仍会执行，入口必须检查 stop。
}
for (Future<TaskResult> future : futures) {
    try {
        inspectResult(future.get()); // 暂停或未开始不能当成功。
    } catch (ExecutionException taskFailure) {
        stop.set(true);
        reportTaskFailure(taskFailure.getCause());
    } catch (InterruptedException interrupted) {
        stop.set(true);
        // 转入统一收尾，核实全部已提交任务和数据库操作；不能立即恢复。
        drainAcceptedTasksAndCheckDatabase(pool, futures);
        Thread.currentThread().interrupt();
        return;
    }
}
awaitPoolAndCheckDatabase(pool);
inspectAllTaskStates();
```

executeRange 在入口检查 stop，停止时不扫描、不改变待执行状态；否则确认状态从待执行更新为执行中，再次检查 stop，并开始分页。范围处理发生异常时，必须在任务内部先设置 stop，记录失败和告警后再抛异常或返回失败结果；不能只依赖调度方 get 才通知其他任务停止。

逐个 get 可以简化等待，但前面的任务很慢时，后面的异常可能较晚被调度方读取。因此立即告警依赖任务内部异常处理；任务入口、状态更新和分页处理都要覆盖，告警失败不能绕过停止动作。严重进程故障仍靠外部监控与人工恢复兜底。

代码中的报告、收尾和核对方法是待实现的业务协议；报告方法必须内部处理日志或告警失败，不向外抛出而跳过后续等待。结果检查方法也应记录业务状态，不通过抛异常提前跳过其余 Future；这些约束需在实现中验证。get 或 awaitTermination 等待超时、被中断或 Future 被取消，都不证明 JDBC 已停止。应配置数据库请求超时并核实在途结果，生产参数待确认；不因等待结束直接判整体成功。

来源：[ThreadPoolExecutor API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。本次未联网核验或编译运行示例。

### 3.8 详细拆分方案：固定边界，按范围分页

用户补充的项目背景：旧表约有 3 亿条数据，主键递增。按每个任务平均约 100 万条记录估算，3 亿 ÷ 100 万 ≈ 300，因此可规划约 300 个范围任务。这是工作量规划，不是 300 个工作线程，也不是要求每个范围恰好有 100 万条；实际数据量和各范围记录数未在本次查询核验。

递增主键仍可能存在空洞，不能直接把主键跨度 100 万当成 100 万条记录。具体范围边界需结合主键分布和记录量测定；可以保持范围连续且不重叠，允许各任务记录数不同，再按分布调整过大或过小的范围。边界生成方式尚待落实。下面三个小范围仅用于演示左开右闭规则，不代表项目仅规划三个任务。

以下为建议实现方案，前提是源表具有适合稳定排序和范围查询的主键。本例使用正数、唯一且迁移期间不改变的数值主键 id，实际主键类型、迁移过滤条件及是否满足此前提仍待核实；不能直接套用于复合主键或会变更的主键。

开始规划时记录本轮最大主键 endId，将其与来源表和迁移条件一起保存，恢复时沿用原边界。假设历史范围为 (0, 300000]，可按 100000 的主键跨度拆成三个范围，所有数值均为教学示例：

| 任务 | 区间 | 查询边界 |
| --- | --- | --- |
| T1 | (0, 100000] | id > 0 AND id <= 100000 |
| T2 | (100000, 200000] | id > 100000 AND id <= 200000 |
| T3 | (200000, 300000] | id > 200000 AND id <= 300000 |

统一左开右闭，前一个任务的上界等于后一个任务的下界，边界记录只属于一个范围。范围跨度不等于记录数：主键可能有空洞，数据也可能分布不均，因此不能保证三个任务耗时相同。任务清单生成完毕后记录“规划完成”，核对范围首尾、连续性和唯一性，再据此判断整轮是否完成，不能只统计已提交的任务。

每个范围从自己的最后确认位置 lastId 继续，初始值为区间下界。下面是参数化查询示意，不是可直接运行的完整 SQL；表名取自受控配置，值参数绑定传入，迁移过滤条件各页保持一致。

```sql
SELECT 所需字段
FROM 源表
WHERE id > :lastId
  AND id <= :rangeEnd
ORDER BY id
LIMIT 500;
```

500 是每页最多读取的记录数示例，不是主键跨度或生产配置。执行过程如下：

1. 成功读取一页；查询异常必须报告失败，不能当作空页。
2. 按分片规则写入目标表，逐项确认写入成功或按版本规则可安全跳过。
3. 本页全部结果已确认后，保存本页最后一个主键为该任务进度；保存成功后才读取下一页。
4. 写入失败、部分结果未知或进度保存未确认时，不推进恢复位置，报告未完成；恢复可能重做本页，因此仍需幂等与版本控制。
5. 查询成功且结果为空，说明范围扫描结束；成功状态可靠保存后，才能将该范围计为成功。最后一页可能不足 500 条，主键有空洞时 lastId 也不一定等于 rangeEnd，不能只按游标等于上界判断完成。

固定 endId 只限定扫描边界，不形成数据库快照。双写需覆盖迁移期间的业务变更，扫描到的旧版本不能覆盖新版本；低于 endId 的晚提交数据也不能仅靠一次主键扫描保证捕获，仍需同步与一致性校验兜底。本方案不能据此声称已实现无遗漏迁移。

与 [016 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_断点续跑.md>) 保持一致：按独立范围保存进度是本篇建议落地方式，不用全局最大主键掩盖较小范围的失败。存储结构和事务边界尚未实现验证。

### 3.9 任务描述：队列保存范围，执行时分页读取

建议任务描述只保存标识和扫描范围，例如下面的 Java 8 数据结构；字段为设计示例：

```java
final class RangeTaskSpec {
    final String taskId;       // 与本轮任务清单中的任务关联
    final String sourceTable;  // 来自受控配置，不能接受任意表名
    final long startExclusive;
    final long endInclusive;

    RangeTaskSpec(String taskId, String sourceTable,
                  long startExclusive, long endInclusive) {
        this.taskId = taskId;
        this.sourceTable = sourceTable;
        this.startExclusive = startExclusive;
        this.endInclusive = endInclusive;
    }
}
```

启动时加载本次全部 RangeTaskSpec，逐个包装为范围任务并提交线程池；任务闭包只引用轻量描述与执行服务，执行时再读取确认进度和分页数据，不提前加载整个范围。

例如 T2 等待执行时只保存“查哪个表、从 100000 到 200000”的信息；得到工作线程后，才开始按每页最多 500 条读取。这样内存数据量主要受正在执行的任务和批次大小影响，而不是受所有待执行范围的数据总量影响；字段大小及任务描述大小仍需评估。


**长时间执行与数据引用的生命周期**

每个任务处理约 100 万条记录，可能持续较长时间，实际耗时需测量。执行期间，任务 ID、范围边界、进度和执行所需的服务引用可以持续保留；并不因此把该范围的 100 万条数据库记录同时保存在内存。

数据按页读取，例如每页最多 500 条是教学示例。应在本页写入结果已确认、进度成功保存后，解除对本页记录及不再需要的写入缓冲的引用，再读取下一页；不得将各页不断追加到任务级大列表，也不要让闭包、日志缓存或结果对象长期持有历史页。异常路径若需保留现场，应保留必要标识和错误信息，不能无界积累数据；未确认进度仍按原位置恢复。

释放引用不等于内存立刻归还：只有对象不再被其他存活引用持有时，才具备被垃圾回收器回收的条件，实际回收时机由 JVM 决定。不能通过任务执行时间长直接判断内存一定持续增长，也不能只因采用分页就保证没有内存泄漏。

因此，等待期间会保留本次 M 个任务描述、包装对象和 Future；范围耗时长时，这部分内存也会保留较久。分页记录随处理循环释放引用，实际峰值仍需结合 N、页大小、字段、驱动缓冲及返回结果测量。

进程重启后根据任务表和确认进度恢复；核实旧实例、线程和数据库操作停止后，重新查询待执行清单并创建线程池，不复用旧队列或 Future。本方案不支持多实例同时迁移或自动接管。

### 3.10 任务表字段与整体完成判定

**任务表保存什么**

先将所有迁移任务写入数据库，初始状态统一设为待执行，初始进度为扫描范围下界。任务表只保存本次需要完成的完整任务清单，不按批次区分，也不混入其他迁移的历史任务。字段名为实现建议，具体表结构尚未验证。

| 字段 | 建议字段名 | 含义 |
| --- | --- | --- |
| 任务 ID | task_id | 唯一标识一个范围任务 |
| 扫描起始 ID | start_id | 范围下界，不包含；恢复时不改成当前进度 |
| 扫描结束 ID | end_id | 范围上界，包含；迁移期间固定 |
| 处理进度 | current_id | 最后确认处理成功并保存的位置，初始为范围下界 |
| 处理结果 | status | 区分待执行、执行中、成功、失败、暂停；具体枚举待实现 |
| 失败原因 | failure_reason | 记录失败阶段及原因，未知写入结果也要说明 |

不维护批次 ID、执行者标识和执行尝试编号。任务 ID 是范围标识，不是执行次数编号。启动查询只加载待执行任务。恢复启动时，先通过人工触发的恢复接口核实暂停任务，确认旧执行及数据库操作已停止，再将其改为待执行；不直接提交未经核实的暂停任务。失败或残留执行中任务同样先核实后恢复，暂停指令未解除时禁止启动新处理。

**直接从完整任务表汇总结果**

只有任务清单全部生成并可靠入库后，才判断整体是否完成。启动阶段核对规划数量、实际记录数及范围完整性，约 300 是估算，不能硬编码为成功门槛。规划完成的控制状态需要可靠保存，保存方式待实现；不能把暂时为空的任务表当作迁移成功。

协调方根据任务表的一致数据视图直接汇总，无需批次结果表：

1. 任意任务失败：整体失败，即使还有任务未完成也优先判失败。
2. 没有失败，但仍有任务尚未成功：整体尚未完成，界面可显示执行中；待执行、执行中、暂停和结果未知都不算成功。
3. 完整清单中的所有任务均可靠保存成功状态：迁移执行成功，随后仍需一致性校验。

单个范围只有扫描结束、各页结果已确认、进度与成功状态均保存成功，才能计为成功。查询异常不能当作空页，最后确认位置也不一定等于范围上界。线程结束、队列为空或任务表查询失败，都不能替代成功判定。

整体失败不代表所有工作线程都已停止。任意任务失败都触发整体停止新处理，已运行任务按 3.11 安全收尾，不再开始其他范围扫描；人工恢复后按当前任务状态重新汇总，可以从失败回到尚未完成或成功。历史失败通过日志保留，不靠额外执行尝试字段管理。零任务迁移的判定仍待确认。

例如 T1 成功、T2 失败、T3 执行中，整体失败；T2 恢复为待执行后，若已无失败任务，则整体尚未完成；所有任务可靠保存成功状态后才判成功。

### 3.11 正常收尾与主动暂停

**正常收尾**

提交清单结束后调用 shutdown，禁止后续提交，已接收任务继续执行。调度线程逐个等待所有已成功提交的 Future 并检查结果，再等待线程池终止、核实数据库操作收尾，最后按完整任务表判断成功、失败或未完成。任务队列为空不代表运行任务已结束，所有 Future 结束也不等于业务成功。

**主动暂停或失败触发暂停**

先设置共享停止信号，调度方停止尚未完成的提交。任务入口先检查信号：尚未开始的排队任务轮到执行时直接退出，仍保持待执行。入口检查后与停止信号发生竞争时，状态已改为执行中但尚未扫描的任务，安全保存为暂停后退出。

已经运行的任务在分页边界检查信号，核实当前页结果，只保存确认进度，再保存暂停状态退出；失败任务保留失败，已成功任务不变。shutdown 仍会执行队列任务，所以必须保留入口检查；不依赖 shutdownNow 清空队列，以免丢失已提交任务的收尾管理。

停止信号不等于所有 SQL 立即结束。等待线程和在途数据库操作收尾后才允许人工恢复；未知结果先核实，不能跳过该页。排队任务逐个退出可能仍需时间，但不再读取迁移数据。

### 3.12 一次提交与状态确认

**提交与执行顺序**

1. 完整任务清单入库，确认规划完成；人工恢复任务后再启动单实例迁移，运行期间不修改任务恢复状态。
2. 受限查询全部待执行任务描述，检查数量上限和内存预算，创建固定线程池。
3. 逐个 submit 并保存成功返回的 Future；正常情况一次提交完整清单，停止或拒绝时中止后续提交。
4. 任务入口检查停止信号，确认待执行状态更新为执行中后再扫描；按页写入并保存确认进度。
5. 成功保存任务成功状态；失败设置停止信号、记录原因并告警，不自动重试。
6. 关闭提交入口，等待所有已提交任务收尾，按完整任务表汇总；未提交或未开始的任务仍为待执行，不计成功。

**状态更新与单实例保障**

用 task_id 和 status=待执行作为更新条件，只有影响行数为 1 且提交确认成功才允许执行。更新结果不符或响应丢失时停止并人工核实，不能把执行中状态当作自己可以继续扫描的证据。

该条件用于防止重复开始，但不能替代全局单实例限制；没有执行身份字段，恢复前必须确认旧线程、进程和数据库操作已停止。任务状态更新异常也要触发共享停止信号。

例如 N=4、M=300 仅为教学示例：最多 4 个任务执行，其余描述等待。一个任务失败后，正在运行的任务安全收尾，排队任务到达入口即退出，未开始任务仍待执行。人工处理后重新查询待执行清单，不复用旧队列或旧 Future。

### 3.13 执行失败：统一告警、人工排查与恢复

失败统一采用“停止新处理 → 记录与告警 → 人工排查修复 → 核实旧操作 → 恢复待执行”的流程。程序不自动按原因分类重试，根因由人工结合日志和监控判断。这样处理规则更简单，但短暂故障也需要人工介入，迁移可能暂停更久。以下为已确认设计，不代表已经实现或验证。

**保存失败现场，保留确认进度**

任务失败时先触发停止新处理，保留最后成功保存的 current_id，在任务表记录失败结果和原因，并发送告警。日志补充 task_id、失败阶段（读取源表、写目标表、保存进度）、本页范围、可定位的出错记录 ID、异常堆栈、SQLState、数据库错误码和发生时间；这些诊断信息不要求成为任务表独立字段，任务表也不保存整批业务数据。记录状态或发送告警失败，不能阻止暂停流程继续执行。

另外记录本页写入结果是否未知。写入或提交响应超时可能发生在数据库已经提交之后，不能将超时等同于没有写入，也不能直接跳过该页。恢复位置不推进，先核实原操作，再依靠幂等和版本控制安全重做。

如果任务表所在数据库也不可用，失败状态可能无法落库，任务会残留为运行中。此时通过独立可用的日志和告警报告状态持久化失败；这些机制也可能故障，不承诺必然记录成功。存储恢复后核对任务及日志再修复状态，不能把“没有失败记录”当作没有失败。

**任意失败都停止新处理**

失败范围不在当前线程内自动重试，也不直接改回待执行。任意任务失败都通知协调方暂停整体的新任务处理，其他已运行任务按 3.11 核实当前页、保存确认进度并退出；未执行任务继续留在任务表。因暂停而安全退出的任务按现有暂停状态处理，已完成成功的任务保持成功，不能把所有任务统一改为失败。

暂停信号需要各范围任务在入口和分页边界及时检查，本方案限制单实例；不能宣称某个任务失败的瞬间所有 SQL 都已停止。对于已经发出的请求继续核实结果，不通过取消 Future 就认定数据库操作结束。

**人工排查，不直接跳过错误数据**

人工根据异常、出错记录、数据库监控和代码配置定位原因并修复。连接超时可能来自数据库不可用、网络或连接池耗尽，不能仅凭异常名称判断宕机；数据问题也不能直接跳过后标记成功。即使数据库已经能够连接，也要核实业务读写和上次未决操作，而不是立即重跑。

例如当前确认进度为 1000，下一页某条记录字段过长导致写入失败：进度保留在 1000，记录问题记录 ID 并停止新处理。人工确认是源数据、目标表定义还是转换代码的问题，按业务规则修复后再恢复。本例数字仅说明恢复位置，不是生产参数。

**按任务或全部未完成任务恢复**

采用人工触发的恢复接口，按 task_id 恢复单个任务，或对全部未完成任务逐项核实后恢复，不以直接手工改表作为常规恢复方式。接口用于检查原状态、防止重复恢复并保留失败日志；人工确认旧操作收尾是前置条件，接口不能仅凭状态字段证明这一点。不能直接将所有执行中任务批量重置为待执行，按以下顺序处理：

1. 确认依赖服务已恢复，或代码、配置、数据问题已修复；对未知结果先完成核实。
2. 确认原执行者已退出，原事务、在途写入及未决提交已收尾，避免两个执行者重叠迁移同一范围。
3. 从数据库任务表读取原扫描范围与最后确认进度，不重新生成覆盖原任务的范围，也不把成功任务重新置为待调度。
4. 确认旧执行已完全收尾，恢复操作与新一轮提交互斥进行。保留失败日志后，通过任务 ID 和原状态条件更新，将已核实的失败任务改为待执行；暂停或残留执行中任务先逐项核实，再改为待执行。恢复不清空确认进度、不改变扫描范围，也不抹去失败信息；没有执行身份字段，禁止旧执行未结束就重置状态。
5. 核实完成后，由人工明确重新启动提交；单独将任务改为待执行不会自动启动迁移。旧执行收尾后，重新查询清单并创建线程池。生命周期管理防止重复启动，未恢复的失败任务不进入提交清单。
6. 执行时以 id > current_id AND id <= end_id 读取下一页。已写成功但未确认保存进度的页可能被重复处理，按幂等及版本规则核实，确认整页后再保存新进度。

例如已确认进度为 1000，当前页写入部分成功后连接中断，不能直接将进度改为该页最后主键。原操作收尾并核实后，从 1000 之后重新读取该页；已成功数据按版本与幂等规则处理，避免旧值覆盖新值。本例数字仅解释恢复位置，不是生产批次配置。

**残留执行中任务需要人工核实**

进程崩溃可能来不及把任务改成失败，因此恢复不能只查失败任务，还应排查残留的执行中任务。本方案不维护执行者标识、执行尝试编号或用于自动接管的租约字段，不支持仅凭心跳超时就重置任务。

恢复前必须确认旧线程、进程及相关数据库操作已经停止，并核实未知写入结果。无法确认时，保持未完成状态并告警，不重新执行。状态条件更新只能防止同一状态下重复开始，不能区分恢复前后的执行身份，不能据此声称旧执行无法覆盖新进度。

**失败历史与整体结果**

失败原因保存在任务表；恢复前将必要的失败信息写入日志，关联 task_id 和发生时间，不增加执行尝试编号或独立执行尝试表。日志保留策略和可靠性仍需落实，不能承诺状态库故障时一定保存成功。

受控恢复后，协调方重新汇总完整任务表。只有全部任务成功才判整体成功；点击恢复或数据库重新可用都不能直接改为成功。再次失败时记录新的失败原因和日志，保留原确认进度。

恢复位置继续遵循 016 的“最后确认进度、失败页允许重做”；任务启动和恢复过程的互斥、数据库操作收尾以及故障演练尚未验证。

## 4 已确认规则

- 面试口述各主题应提供跳转到详细方案对应位置的链接，并在链接文字中标明目标行号；文档调整后同步核对链接目标与行号。
- 新任务初始状态统一为待执行；暂停任务在恢复启动前经核实、通过恢复接口改为待执行，暂停生效期间禁止新处理。
- 区分正常收尾与失败暂停收尾：任意失败立即告警并暂停，可保留未执行任务；本次执行结束不等于全部迁移成功。

- 表达易于理解、适用于面试口述；口述按拆分、提交执行、失败恢复、完成判定和暂停顺序展开，实现细节保留在详细方案。
- 本文保留迁移线程池设计总览职责；通用线程池知识已归入 `000_线程池` 目录，旧职责编号按当前文件布局修正。
- 补充线程池类型、核心线程数、最大线程数、队列类型选择和拒绝策略，并区分建议与已验证配置。
- 补充范围划分详细方案、任务描述含义、各配置选择理由、整轮完成判定，以及正常收尾和主动暂停的区别。
- 用户补充：旧表约有 3 亿条数据，主键递增；可按每个任务平均约 100 万条规划约 300 个任务。
- 任务表维护任务 ID、扫描起始 ID、扫描结束 ID、处理进度、处理结果和失败原因。
- 不维护批次 ID、执行者标识、执行尝试编号，不设批次结果表；直接从完整任务表汇总，失败优先，全部成功才判迁移执行成功。
- 最新方案采用单实例、固定 N 线程，一次查询并提交全部待执行任务描述，使用有界队列与 AbortPolicy，保存 Future 并逐个等待结果。
- 调度线程在池外等待结果，任务内部失败立即设置停止信号并告警；Future 全部结束不等于任务全部成功。
- 完整任务清单持久化；允许本次约 300 个轻量描述、包装对象及 Future 长期留在内存，任务总数设上限并测量内存，不加载整批业务数据。
- 范围任务分页处理，确认本页结果并保存进度后解除数据引用，不累积整个范围数据。
- 线程数不是固定为 2；按连接预算、在线业务负载、迁移时限压测选择；一次只运行一个迁移实例。
- 历史迁移执行失败统一记录原因并告警，不自动分类重试；任意任务失败都停止整体新处理，已有任务安全收尾，由人工排查修复。
- 通过人工触发的恢复接口，将核实后的失败或未完成任务改为待执行，再明确启动提交；恢复前确认旧线程、进程和数据库操作已停止并核实未知结果，不清空进度、不改变范围、不抹去失败信息。
- 受控恢复后重新汇总全部任务状态；失败信息通过任务表原因和日志保留，不维护独立执行尝试记录。
- 线程池不代替进度、幂等、事务和全局并发控制。
- 提交被拒、任务异常、结果未知和停止都不能直接记为迁移完成。

## 5 待确认或待验证事项

- N 的生产取值、连接预算及在线业务验收指标需压测确定。
- 单实例防重、ArrayBlockingQueue、AbortPolicy、Future 等待与停止协议尚未运行验证。
- MAX_TASKS 的生产上限，以及 M 个描述、包装对象、Future 和并发 N 份分页数据的内存峰值待测量。
- 单个约 100 万条范围的执行耗时、各路径数据引用释放及长时间运行的内存变化尚未验证。
- 部分提交拒绝、线程创建失败、等待中断、数据库请求超时及已接收任务的收尾尚未验证。
- 源表主键类型、稳定性和迁移过滤条件是否满足示例前提。

- 线程池生命周期、任务状态和协调方的衔接。
