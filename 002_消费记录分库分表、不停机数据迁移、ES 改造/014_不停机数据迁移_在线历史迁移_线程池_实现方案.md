## 1 问题

线程池如何配合在线历史迁移完成并发控制、任务执行和安全停止？

## 2 面试口述精炼版本

口述内容字符数：316

**范围任务与配置**

固定扫描上界，将主键按左开右闭区间拆成任务。队列中的任务只携带范围信息，执行时再分页读数据。建议专用 ThreadPoolExecutor 隔离迁移线程，核心数与最大数均为 2，限制池内并发；容量为 2 的 ArrayBlockingQueue 限制积压。这些数值仅为压测起点。

**拒绝与完成判定**

AbortPolicy 反馈拒绝，调度方保留任务再处理。完整任务清单中所有范围均扫描结束、结果和进度已确认并保存成功状态，才算本轮迁移完成，随后仍需一致性校验。

**正常收尾与主动暂停**

正常收尾在全部任务已提交后调用 shutdown，等待并核对结果；主动暂停则先停止提交，让任务在批次边界保存已确认进度后退出。暂停不算成功，异常或未知结果不推进进度。

## 3 详细方案

### 3.1 主文档职责

本文说明迁移专用线程池的选择与调度衔接。限流由 012 维护，批次性能调优由 013 维护，线程数压测由 015 维护，断点续跑由 016 维护；通用线程池概念、参数、队列和拒绝策略见 `000_线程池` 目录。本文不把线程池配置当作任务进度、幂等或事务方案。

### 3.2 总体流程

~~~text
记录扫描边界，生成并可靠保存本轮完整范围任务清单
  → 按容量派发任务
      ├─ 拒绝：保留待调度状态；容量恢复且线程池仍运行时重试
      └─ 接收：排队或执行，不标记迁移完成
  → 分批读取、写入并核实结果
      ├─ 失败或未知：保留原恢复位置，报告未完成
      └─ 成功或安全跳过：保存本批进度，再读取下一批
  → 范围查询成功且为空：保存该范围成功状态
  → 正常收尾：全部任务已提交后关闭接收，等待执行并核对任务清单
  → 所有范围成功：本轮迁移完成，进入一致性校验

执行途中需要主动暂停：
停止提交新任务 → 设置暂停信号 → 任务在批次边界收尾
  → 保存已确认进度并报告暂停 → 等待线程和在途数据库操作收尾
~~~

### 3.3 线程池边界

固定线程数只限制该线程池的工作线程数量；同进程其他线程池或多个实例仍可能增加数据库并发，不能代替全局并发控制。队列只保存任务描述，不能代替进度持久化。shutdownNow 或 cancel(true) 只请求中断，不能单独证明数据库操作已经停止。

来源：[参考文章_04：工具架构与性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:192>)提供通用方向；版本判断和 Java 调度属于项目设计，未执行运行验证。

### 3.4 类型与线程数：手工创建固定并发的线程池

建议使用专用 ThreadPoolExecutor，显式指定线程数、队列和拒绝策略，避免与在线请求共用线程池而相互争抢执行资源。这里的“专用”只隔离线程资源，不隔离底层数据库负载。

沿用本文原有设计示例，将 corePoolSize 和 maximumPoolSize 均设为 2。两者相等，队列满时不会继续扩容，因此最多有 2 个池内工作线程执行范围任务；线程按需创建，并不是构造完成就一定已有 2 个线程。无需为了固定并发而使用 Executors.newFixedThreadPool，它默认使用近似无界队列，不能直接满足本文限制积压的目标。

核心数取 2，是先用低并发建立压测基线，让两个范围并行而不过早放大数据库压力；最大数也取 2，是避免队列满时自动扩容。选择固定并发是设计取舍，选择具体数字 2 则只是压测起点，没有证据证明 2 是最优值。2 不是已确认的生产取值。可在固定其他压测条件后比较核心数和最大数均为 2、均为 4 的两组配置，结合连接等待、数据库负载、迁移吞吐及在线延迟选择。不得仅根据任务总量或 CPU 核数倍数确定并发；多实例还需控制各实例总并发。

### 3.5 队列选择：ArrayBlockingQueue 限制等待任务

建议使用容量明确的 ArrayBlockingQueue，按先进先出顺序保存范围任务描述，示例容量为 2，不把整批数据库记录提前加载到队列中。使用有界队列是为了限制进程内积压，并让调度方及时感知容量不足。

例如 A、B 正在执行，C、D 已排队，再提交 E 时队列无法接收，而线程数已经达到最大值 2，于是触发拒绝策略。只有 E 被本次拒绝处理，A—D 不因此被丢弃。示例假设线程池正常运行且前面的任务尚未完成。

显式指定容量的 LinkedBlockingQueue 也能提供有界缓冲；本文建议 ArrayBlockingQueue 是为了直接固定等待容量，并非它在所有场景中性能都更好。SynchronousQueue 不存储等待任务，不符合本例保留 2 个排队任务的安排；无界队列则不能提供所需的积压上限。队列容量取 2，是为两个执行任务预留一个小的等待缓冲，同时尽早向调度方反馈积压；不是按历史数据总量计算出的容量。容量 2 仍需压测，任务描述也应控制大小。

### 3.6 拒绝策略：AbortPolicy 让调度方感知失败

建议使用 AbortPolicy，在任务无法接收时抛出 RejectedExecutionException。调度方捕获异常后保留任务的待调度状态，降低或暂停派发，容量恢复且线程池仍在运行时再尝试；不得把拒绝标记为迁移完成。线程池关闭也会触发拒绝，此时应停止向该实例重试，等待恢复流程处理，不能无间隔循环提交。

不建议在本设计中使用 DiscardPolicy 或 DiscardOldestPolicy，因为静默丢弃当前或队头任务不符合迁移任务必须可追踪的要求。CallerRunsPolicy 虽能拖慢提交者，但会让调度线程亲自执行迁移任务，池外执行可能突破预期的数据库并发，并且关闭后仍会丢弃任务，因此不作为本例的拒绝策略。

AbortPolicy 只负责反馈拒绝，不负责保存、重试或保证不丢任务。范围任务与进度仍须由调度方可靠保存；应用崩溃后如何恢复、退避间隔及重试条件还需实现与验证。

### 3.7 配置片段与生命周期

以下 Java 8 代码放在初始化方法中，导入 java.util.concurrent 中的对应类型。它只展示配置，不包含任务持久化或调度恢复实现。2 个线程、队列容量 2、keepAliveTime 为 0 秒均为本篇设计示例；未开启核心线程超时。

```java
ThreadPoolExecutor migrationPool = new ThreadPoolExecutor(
        2, 2, // 核心数与最大数相等，固定池内并发上限
        0L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<Runnable>(2), // 只排队任务描述
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy());
```

这里使用 defaultThreadFactory 只是创建线程的工厂，不是通过 Executors 工厂方法创建整个线程池。迁移线程池应复用，不要每提交一个范围任务就重新创建。正常收尾与主动暂停按 3.11 分别处理；只有已确认写入结果并成功保存的进度才能推进，异常或结果未知时保留原恢复位置。

shutdownNow 只尝试中断，返回的未开始任务仍需保留恢复状态；不能据此认定在途数据库写入已经停止。等待线程池终止和核实数据库操作收尾是不同检查。

以上类型、队列和拒绝策略为本次补充的设计建议，具体实现及生产适用性尚未验证。Java 行为参考：[ThreadPoolExecutor API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[ArrayBlockingQueue API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ArrayBlockingQueue.html)；本次未联网核验外部页面。

### 3.8 详细拆分方案：固定边界，按范围分页

以下为建议实现方案，前提是源表具有适合稳定排序和范围查询的主键。本例使用正数、唯一且迁移期间不改变的数值主键 id，实际主键类型、迁移过滤条件及是否满足此前提仍待核实；不能直接套用于复合主键或会变更的主键。

开始规划时记录本轮最大主键 endId，将其与来源表、迁移条件和本轮标识一起保存，恢复时沿用原边界。假设历史范围为 (0, 300000]，可按 100000 的主键跨度拆成三个范围，所有数值均为教学示例：

| 任务 | 区间 | 查询边界 |
| --- | --- | --- |
| T1 | (0, 100000] | id > 0 AND id <= 100000 |
| T2 | (100000, 200000] | id > 100000 AND id <= 200000 |
| T3 | (200000, 300000] | id > 200000 AND id <= 300000 |

统一左开右闭，前一个任务的上界等于后一个任务的下界，边界记录只属于一个范围。范围跨度不等于记录数：主键可能有空洞，数据也可能分布不均，因此不能保证三个任务耗时相同。任务清单生成完毕后记录“规划完成”，核对范围首尾、连续性和唯一性，再据此判断整轮是否完成，不能只统计已经提交的任务。

每个范围从自己的最后确认位置 lastId 继续，初始值为区间下界。下面是参数化查询示意，不是可直接运行的完整 SQL；表名取自受控配置，值参数绑定传入，迁移过滤条件各页保持一致。

```sql
SELECT 所需字段
FROM 源表
WHERE id > :lastId
  AND id <= :rangeEnd
ORDER BY id
LIMIT 500;
```

500 是每页最多读取的记录数示例，不是主键跨度或生产配置。执行过程如下：

1. 成功读取一页；查询异常必须报告失败，不能当作空页。
2. 按分片规则写入目标表，逐项确认写入成功或按版本规则可安全跳过。
3. 本页全部结果已确认后，保存本页最后一个主键为该任务进度；保存成功后才读取下一页。
4. 写入失败、部分结果未知或进度保存未确认时，不推进恢复位置，报告未完成；恢复可能重做本页，因此仍需幂等与版本控制。
5. 查询成功且结果为空，说明范围扫描结束；成功状态可靠保存后，才能将该范围计为成功。最后一页可能不足 500 条，主键有空洞时 lastId 也不一定等于 rangeEnd，不能只按游标等于上界判断完成。

固定 endId 只限定扫描边界，不形成数据库快照。双写需覆盖迁移期间的业务变更，扫描到的旧版本不能覆盖新版本；低于 endId 的晚提交数据也不能仅靠一次主键扫描保证捕获，仍需同步与一致性校验兜底。本方案不能据此声称已实现无遗漏迁移。

与 [016 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_断点续跑.md>) 保持一致：按独立范围保存进度是本篇建议落地方式，不用全局最大主键掩盖较小范围的失败。存储结构和事务边界尚未实现验证。

### 3.9 任务描述：排队的是工作指令，不是整批数据

建议任务描述只保存标识和扫描范围，例如下面的 Java 8 数据结构；字段为设计示例：

```java
final class RangeTaskSpec {
    final String taskId;       // 与本轮任务清单中的任务关联
    final String sourceTable;  // 来自受控配置，不能接受任意表名
    final long startExclusive;
    final long endInclusive;

    RangeTaskSpec(String taskId, String sourceTable,
                  long startExclusive, long endInclusive) {
        this.taskId = taskId;
        this.sourceTable = sourceTable;
        this.startExclusive = startExclusive;
        this.endInclusive = endInclusive;
    }
}
```

ArrayBlockingQueue<Runnable> 实际保存的是 Runnable；使用 submit 时通常是 FutureTask 包装对象。任务对象持有上述范围信息和执行服务引用，工作线程真正执行后才读取已持久化的进度、查询一页数据并迁移。它不是把 RangeTaskSpec 直接塞进 Runnable 队列，也不应提前加载整个范围的数据列表再通过闭包持有。

例如 T2 排队时只持有“查哪个表、从 100000 到 200000”的信息；得到工作线程后，才开始按每页最多 500 条读取。这样内存数据量主要受正在执行的任务和批次大小影响，而不是受所有排队范围的数据总量影响；字段大小及任务描述大小仍需评估。

内存队列不可靠保存任务。进程重启后，应根据持久化清单和每个范围的确认进度恢复；重新派发前必须确认旧执行者及在途操作已经收尾，防止同一范围重叠执行。多实例领取与防重协议仍待落实。

### 3.10 完成判定：以完整任务清单为准

建议每轮保留完整任务清单，为每个范围记录待调度、运行中、成功、失败或暂停等状态；尚未开始执行的已接收任务也必须可追踪。状态名称及存储结构属于本篇建议，不是已有实现事实。

“队列为空”只说明没有等待任务，工作线程可能仍在执行；“线程池终止”只说明池内工作已结束，任务可能失败或因暂停退出。两者都不能单独证明迁移成功。

单个范围只有扫描结束、所有批次处理结果已确认、进度及成功状态均保存成功，才能计为成功。进度或成功状态保存失败、任务抛异常、取消、暂停、结果未知，都不能计为成功。整轮完成必须同时满足：任务规划已完成，且完整清单中的每个范围都已可靠标记成功；没有遗漏的待调度、运行、失败、暂停或未知结果任务。

如果使用 submit，可收集每次成功提交返回的 Future，通过 get 获取结果或 ExecutionException。但任务不能吞掉异常后把正常返回伪装成成功，正常返回的“暂停”结果也不等于成功。被拒任务可能没有返回 Future，仍要留在任务清单中；进程重启后也无法依赖原内存中的 Future 恢复。

例如 T1、T2 成功，但 T3 被拒尚未重试，即使队列为空、两个 Future 都成功，本轮仍未完成。所有范围成功之后还需执行一致性校验，不能直接据此切换流量。

### 3.11 正常收尾与主动暂停分别处理

**正常收尾：全部提交后关闭接收，等待结果**

派发指调用 execute 或 submit 提交范围任务。正常收尾时，先确认任务规划已结束、所有范围均已提交处理，没有尚待首次提交或被拒后待重试的范围，再调用 shutdown 停止接收新任务。已有运行和排队任务继续执行，不设置主动暂停信号；随后用 awaitTermination 等待线程池终止，并按 3.10 核对任务结果。

不必等所有任务执行完才调用 shutdown。等待超时也不代表任务已停止，更不能标记迁移成功；等待上限需结合实际范围耗时制定，本文未给出生产值。如果已接收任务失败，需要保留失败范围，在确认原操作收尾后另行恢复；已经关闭的线程池不能再次接收重试任务。

**主动暂停：尚未迁完，提前停止提交和继续扫描**

例如数据库负载超过已约定的业务验收阈值，需要提前暂停。建议按以下步骤处理，阈值与停止协议尚待验证：

1. 先停止调度方继续调用 execute、submit，保留未提交或被拒的范围。
2. 设置线程间可见的暂停信号，例如 AtomicBoolean；同时调用 shutdown 停止该线程池接收新任务。
3. 运行任务在本批结果与进度确认后、下一批开始前检查信号，报告暂停并退出。当前批失败或结果未知时报告未完成，保留原确认进度，不等待无限重试才允许退出。
4. 排队任务被线程领取时先检查信号，若需暂停则不开始数据库扫描，保留可恢复状态并退出。
5. 等待线程收尾，并单独核实数据库在途写入和未知提交结果；确认后再允许恢复执行者接管。

假设 T1 扫描了一部分、T2 尚在队列中，暂停后两者都可退出线程池，但 T1、T2 都不能被标记为迁移成功。若某个范围在暂停前已经完整完成并保存成功，则保留其成功状态。

Java 行为参考：[ExecutorService 的 shutdown、awaitTermination](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ExecutorService.html)、[Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。本次未联网核验或执行代码测试。
