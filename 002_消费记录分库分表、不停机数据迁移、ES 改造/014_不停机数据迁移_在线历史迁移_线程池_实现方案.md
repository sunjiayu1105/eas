# 014_不停机数据迁移_在线历史迁移_线程池_实现方案

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。具体实现和运行效果尚未验证。

## 1 问题

线程池如何配合在线历史迁移完成并发控制、任务执行和安全停止？

## 2 面试口述精炼版本

口述内容字符数：536

**先拆任务，保存进度**

这套方案把约 3 亿条历史数据按主键范围拆成约 300 个任务，每个任务平均约 100 万条。先固定扫描上界，保证范围不重叠，再把任务清单和进度存入数据库。

**固定线程，按需领取**

专用线程池固定 N 个线程，N 根据数据库承受能力压测确定。每个线程反复做三件事：领取一个任务、分页迁移、保存结果，再领取下一个。领取时保证同一个任务只能被一个执行者拿到；分页读取控制内存占用，每页写入结果确认后才保存进度，供中断后恢复。

**失败先判断，再恢复**

确认可以安全重试的临时故障，就在当前线程内有限重试；仍失败则保留进度和原因，不马上重新领取。局部问题不影响其他任务时继续处理，数据库整体故障或写入结果未知时暂停领取。修复并确认上次执行已停止、写入结果已核实后，从保存的进度恢复，重复写入不能产生额外影响，也不能用旧数据覆盖新数据，保留失败历史。

**按任务表判断完成**

协调方负责汇总整轮结果：有任务失败就判失败；没有失败但尚未全部成功，就判执行中；完整任务清单全部保存成功状态才判成功，随后再做一致性校验。线程退出或领不到任务，都不代表迁移成功。

**暂停要等当前操作收尾**

先禁止领取新任务，正在执行的任务处理并核实当前页，只保存已确认进度，再退出。最后确认线程和数据库操作都已结束，结果未知时不能跳过这页。

## 3 详细方案

### 3.1 主文档职责

本文说明迁移专用线程池的选择与调度衔接。限流由 012 维护，批次性能调优由 013 维护，线程数压测由 015 维护，断点续跑由 016 维护；通用线程池概念、参数、队列和拒绝策略见 `000_线程池` 目录。本文不把线程池配置当作任务进度、幂等或事务方案。

### 3.2 总体流程

先规划并保存完整任务清单，再启动 N 个工作循环。“工作循环”就是线程反复执行“领取一个范围 → 分页迁移 → 保存结果 → 领取下一个范围”。每次领取必须保证同一范围只有一个执行者获得处理资格，这就是原子领取。协调方负责观察这些循环是否正常、汇总整轮结果，并管理暂停、退出和恢复。

线程池执行的是工作循环，范围任务由工作循环直接调用处理方法；每个范围不再单独提交到线程池。数据库任务表保存待办，内存不再维护范围任务等待队列、完成队列或派发窗口计数。

### 3.3 线程池边界与选择理由

长范围任务的主要耗时在数据库读写。每个工作循环处理完一个范围再领取下一个，可以减少内存调度状态；是否比预排队方案更快仍需压测，不能宣称性能已提升。

固定线程数仅限制本线程池的工作线程数量。其他线程池、多实例及任务内部额外异步操作都可能增加数据库并发；任务表领取互斥不能代替全局并发预算。线程资源隔离也不等于数据库资源隔离。

### 3.4 类型与线程数：专用固定线程池

手工创建专用 ThreadPoolExecutor，corePoolSize 和 maximumPoolSize 均为正整数 N；由一个生命周期入口只提交 N 个工作循环。N 是单实例工作循环上限，不是范围任务总数。每个循环同步处理一个范围，不在内部再创建迁移线程。

N 按源库和目标库连接预算、每循环连接占用、数据库负载、在线延迟、迁移时限及实例数压测确定。2、4、8 是候选测试点，不是生产配置。选择满足指标且有资源余量的较小值，不能直接照搬连接池大小或 CPU 核数。

一次运行内保持 N 不变，调整前先暂停并确认旧执行收尾，再启动新配置；多实例需共享领取规则和总并发预算。

### 3.5 任务存储与线程池队列

约 300 个范围及其进度全部保存在数据库任务表。每个循环一次只领取一个范围，处理并保存结果后才领取下一个；内存主要保留最多 N 个当前范围描述、各自分页数据及固定数量工作循环的管理信息。

线程池配置示例采用 SynchronousQueue，不存储待执行任务。它用于表达“线程池不缓冲范围任务”，不是让所有范围逐一直接交接给线程。新建线程池不预启动核心线程，启动阶段最多提交 N 个工作循环；补建、重复启动和关闭竞争必须由生命周期管理处理，不能假定永远不会拒绝。

任务闭包和日志不得长期引用历史页；每页写入与进度确认后解除数据引用，回收时机仍由 JVM 决定。实际内存峰值需要结合 N、页大小、字段和驱动缓冲实测。

### 3.6 拒绝策略与工作循环异常

采用 AbortPolicy 暴露工作循环提交被拒的异常，不使用静默丢弃策略，也不让 CallerRunsPolicy 将长期循环交给协调线程执行。这里拒绝的是工作循环的启动，不是某个数据库范围任务；范围在工作循环真正启动后才领取。

启动拒绝或线程创建失败时，不把本轮标成成功。生命周期管理停止继续启动，通知已启动循环暂停并核实收尾，告警后受控恢复；不能忙循环重复提交。提交入口还需防止同一批次重复启动两组工作循环。

范围处理失败与工作循环崩溃需要区分：已分类的局部失败在保存结果后可以继续领取其他范围；控制逻辑异常、状态持久化失败或未知结果应暂停并上报。使用 submit 时，循环异常会进入 Future；协调方必须检查已完成 Future 的 get 结果，不能只看线程池线程数。线程池补建物理线程不等于自动重新运行已结束的工作循环。

### 3.7 初始化与核心执行机制

以下是 Java 8 配置片段，需要导入 java.util.concurrent、java.util 和 AtomicBoolean。runWorkerLoop 为业务方法，需落实 3.12 的领取、失败处理与退出协议；本片段不是完整可运行实现。

```java
if (N <= 0) {
    throw new IllegalArgumentException("N must be positive");
}
AtomicBoolean pause = new AtomicBoolean(false);
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        N, N, 0L, TimeUnit.MILLISECONDS,
        new SynchronousQueue<Runnable>(),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy());
List<Future<?>> workers = new ArrayList<>(N);
try {
    for (int i = 0; i < N; i++) {
        // 循环内部领取范围；不在提交之前领取数据库任务。
        workers.add(pool.submit(() -> runWorkerLoop(pause)));
    }
} catch (RuntimeException startupFailure) {
    pause.set(true);
    pool.shutdown();
    // 上层必须核实已启动循环和数据库操作收尾，再决定恢复。
    throw startupFailure;
}
```

协调方在迁移线程池之外运行，周期检查批次状态、控制信号和工作循环 Future；不能把协调任务排在已被 N 个长期循环占满的线程池中。检查周期 1 秒可作教学示例，生产值待确认；只有 Future.isDone() 后才通过 get 检查退出结果，避免顺序等待一个长循环而看不到其他循环异常。

Future 代表整个工作循环的结束，不代表某个范围成功。协调方根据任务表汇总业务结果，恢复时不复用旧 Future。shutdownNow、cancel(true) 和 awaitTermination 均不能单独证明数据库操作已结束，优先合作式暂停。

Java 行为参考：[ThreadPoolExecutor API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[SynchronousQueue API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/SynchronousQueue.html)、[Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。本次未联网核验或运行示例。

### 3.8 详细拆分方案：固定边界，按范围分页

用户补充的项目背景：旧表约有 3 亿条数据，主键递增。按每个任务平均约 100 万条记录估算，3 亿 ÷ 100 万 ≈ 300，因此可规划约 300 个范围任务。这是工作量规划，不是 300 个工作线程，也不是要求每个范围恰好有 100 万条；实际数据量和各范围记录数未在本次查询核验。

递增主键仍可能存在空洞，不能直接把主键跨度 100 万当成 100 万条记录。具体范围边界需结合主键分布和记录量测定；可以保持范围连续且不重叠，允许各任务记录数不同，再按分布调整过大或过小的范围。边界生成方式尚待落实。下面三个小范围仅用于演示左开右闭规则，不代表项目仅规划三个任务。

以下为建议实现方案，前提是源表具有适合稳定排序和范围查询的主键。本例使用正数、唯一且迁移期间不改变的数值主键 id，实际主键类型、迁移过滤条件及是否满足此前提仍待核实；不能直接套用于复合主键或会变更的主键。

开始规划时记录本轮最大主键 endId，将其与来源表、迁移条件和本轮标识一起保存，恢复时沿用原边界。假设历史范围为 (0, 300000]，可按 100000 的主键跨度拆成三个范围，所有数值均为教学示例：

| 任务 | 区间 | 查询边界 |
| --- | --- | --- |
| T1 | (0, 100000] | id > 0 AND id <= 100000 |
| T2 | (100000, 200000] | id > 100000 AND id <= 200000 |
| T3 | (200000, 300000] | id > 200000 AND id <= 300000 |

统一左开右闭，前一个任务的上界等于后一个任务的下界，边界记录只属于一个范围。范围跨度不等于记录数：主键可能有空洞，数据也可能分布不均，因此不能保证三个任务耗时相同。任务清单生成完毕后记录“规划完成”，核对范围首尾、连续性和唯一性，再据此判断整轮是否完成，不能只统计已经领取的任务。

每个范围从自己的最后确认位置 lastId 继续，初始值为区间下界。下面是参数化查询示意，不是可直接运行的完整 SQL；表名取自受控配置，值参数绑定传入，迁移过滤条件各页保持一致。

```sql
SELECT 所需字段
FROM 源表
WHERE id > :lastId
  AND id <= :rangeEnd
ORDER BY id
LIMIT 500;
```

500 是每页最多读取的记录数示例，不是主键跨度或生产配置。执行过程如下：

1. 成功读取一页；查询异常必须报告失败，不能当作空页。
2. 按分片规则写入目标表，逐项确认写入成功或按版本规则可安全跳过。
3. 本页全部结果已确认后，保存本页最后一个主键为该任务进度；保存成功后才读取下一页。
4. 写入失败、部分结果未知或进度保存未确认时，不推进恢复位置，报告未完成；恢复可能重做本页，因此仍需幂等与版本控制。
5. 查询成功且结果为空，说明范围扫描结束；成功状态可靠保存后，才能将该范围计为成功。最后一页可能不足 500 条，主键有空洞时 lastId 也不一定等于 rangeEnd，不能只按游标等于上界判断完成。

固定 endId 只限定扫描边界，不形成数据库快照。双写需覆盖迁移期间的业务变更，扫描到的旧版本不能覆盖新版本；低于 endId 的晚提交数据也不能仅靠一次主键扫描保证捕获，仍需同步与一致性校验兜底。本方案不能据此声称已实现无遗漏迁移。

与 [016 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_断点续跑.md>) 保持一致：按独立范围保存进度是本篇建议落地方式，不用全局最大主键掩盖较小范围的失败。存储结构和事务边界尚未实现验证。

### 3.9 任务描述：领取范围信息，执行时分页读取

建议任务描述只保存标识和扫描范围，例如下面的 Java 8 数据结构；字段为设计示例：

```java
final class RangeTaskSpec {
    final String taskId;       // 与本轮任务清单中的任务关联
    final String sourceTable;  // 来自受控配置，不能接受任意表名
    final long startExclusive;
    final long endInclusive;

    RangeTaskSpec(String taskId, String sourceTable,
                  long startExclusive, long endInclusive) {
        this.taskId = taskId;
        this.sourceTable = sourceTable;
        this.startExclusive = startExclusive;
        this.endInclusive = endInclusive;
    }
}
```

工作循环从任务表原子领取 RangeTaskSpec 对应范围后，直接调用范围处理方法，不把范围包装成新的线程池任务。一次只保留当前范围描述和进度，再分页读取数据。

例如 T2 尚待领取时只保存“查哪个表、从 100000 到 200000”的信息；得到工作线程后，才开始按每页最多 500 条读取。这样内存数据量主要受正在执行的任务和批次大小影响，而不是受所有待领取范围的数据总量影响；字段大小及任务描述大小仍需评估。


**长时间执行与数据引用的生命周期**

每个任务处理约 100 万条记录，可能持续较长时间，实际耗时需测量。执行期间，任务 ID、范围边界、进度和执行所需的服务引用可以持续保留；并不因此把该范围的 100 万条数据库记录同时保存在内存。

数据按页读取，例如每页最多 500 条是教学示例。应在本页写入结果已确认、进度成功保存后，解除对本页记录及不再需要的写入缓冲的引用，再读取下一页；不得将各页不断追加到任务级大列表，也不要让闭包、日志缓存或结果对象长期持有历史页。异常路径若需保留现场，应保留必要标识和错误信息，不能无界积累数据；未确认进度仍按原位置恢复。

释放引用不等于内存立刻归还：只有对象不再被其他存活引用持有时，才具备被垃圾回收器回收的条件，实际回收时机由 JVM 决定。不能通过任务执行时间长直接判断内存一定持续增长，也不能只因采用分页就保证没有内存泄漏。

因此，长期保留的是有限任务的必要描述；分页记录和写入缓冲随每页处理循环使用。实际内存峰值仍取决于并发 N、页大小、字段大小、驱动与批量写入缓冲、引用保留情况，需实测。数据库任务表保存完整清单，不等于应用同时加载约 300 个任务对象。

进程重启后根据持久化清单和各范围确认进度恢复。重新领取前核实旧执行者及在途操作已经收尾，防止同一范围重叠执行。多实例领取与防重协议仍待落实。

### 3.10 完成判定：以完整任务清单为准

用户已确认采用任务进度表和批次结果表：每个范围任务维护一条进度记录，每轮迁移维护一条批次记录。这里“批次”指包含约 300 个范围任务的整轮迁移，不是任务内分页读取的单个数据批次。两张表的用途与汇总规则已经确认，具体表名、字段名和存储实现仍未验证。

**任务进度表**

用户指定的业务字段如下；字段名为实现建议，边界沿用左开右闭约定。

| 业务字段 | 建议字段名 | 含义 |
| --- | --- | --- |
| 扫描起始 ID | start_id | 范围下界，不包含；恢复时不能把它改成当前进度 |
| 扫描结束 ID | end_id | 范围上界，包含；本轮固定 |
| 当前进度 | current_id | 最后成功保存的已确认位置，初始为起始 ID |
| 处理结果 | status | 记录待调度、运行中、成功、失败、暂停等结果；具体枚举为建议 |
| 处理失败原因 | failure_reason | 失败阶段与原因，供排查；不能只记录异常而把结果标成成功 |

为标识任务及关联所属批次，建议另加 task_id 和 batch_id。任务失败时保留原确认进度并记录原因；工作循环启动失败时，未领取的范围仍保持待调度，不等于该范围执行失败。查询成功且范围为空也可完成，不能要求 current_id 必须等于 end_id。

**批次结果表**

用户要求记录整轮执行结果。建议至少有 batch_id 和 execution_result，并增加规划完成标记 plan_completed 及计划任务数 planned_task_count，防止任务尚未生成完毕就误判成功。计划任务数保存实际生成数量，约 300 只是估算，不能硬编码为完成门槛。

任务清单完整后，按以下优先级汇总并保存批次结果：

1. 任意任务为失败：批次结果为失败，即使同时存在未完成任务，仍优先判失败。
2. 没有失败任务，但任意任务尚未成功完成：批次结果为执行中。待调度、运行中、暂停或结果未知都不能计为成功。这里“执行中”表示整轮尚未完成，不保证此刻有线程正在执行。
3. 所有计划任务都已可靠保存成功状态：批次结果为执行成功。成功不仅要求执行线程结束，还要求扫描结果和进度已确认。

规划未结束或实际任务记录数与计划数不符时不得判成功；不能对暂时为空的任务表直接得出“全部成功”。零任务迁移的最终判定另行确认。

建议由同一批次的汇总操作串行执行，在一致的数据视图下重新统计后写入批次表，避免多个工作线程分别拿到旧计数并覆盖新结果。任务结果是明细依据，批次结果是汇总；若任务结果已保存而批次更新失败，应可重新汇总修复，不能报告整体成功。具体锁、事务边界及故障恢复协议尚待实现验证。

批次失败只是结果汇总，不代表其他工作线程已停止。数据库整体故障时暂停整轮新任务领取；单个任务失败是否需暂停其余任务，按故障范围判断，具体判定阈值待确认。同一批次允许受控恢复，按当前任务状态重新汇总；失败执行尝试历史保留，不能清空历史来伪装首次成功，详见 3.13。

没有领到任务不能说明整轮完成，其他循环可能仍在处理范围；线程池终止也可能由失败或暂停导致，不能单独证明迁移成功。

单个范围只有扫描结束、所有批次处理结果已确认、进度及成功状态均保存成功，才能计为成功。进度或成功状态保存失败、任务抛异常、取消、暂停、结果未知，都不能计为成功。整轮完成必须同时满足：任务规划已完成，且完整清单中的每个范围都已可靠标记成功；没有遗漏的待调度、运行、失败、暂停或未知结果任务。

协调方读取任务表中的持久化结果汇总批次状态，检查工作循环 Future 用于发现意外退出。循环正常返回不等于其处理的所有范围成功；不能吞掉范围异常后把失败标成成功。

例如 T1 成功、T2 失败、T3 运行中，批次失败；T1、T2 成功而 T3 尚待领取时，批次执行中；只有完整清单全部成功并可靠保存后才汇总为成功。所有范围成功之后仍需一致性校验，不能直接据此切换流量。

### 3.11 正常收尾与主动暂停

**正常收尾**

工作循环暂时领不到任务时，通过限时等待再检查控制状态，避免空转；等待 1 秒仅为教学示例，生产间隔待确认。协调方在规划完成后核对待领取、运行及未决任务；已无可领取或正在处理的范围时，可以结束本次工作循环，但仍保留失败任务并将批次汇总为失败，不能要求失败任务无限等待自动恢复。

协调方发出本次执行结束信号，循环在领取前检查并退出，随后调用 shutdown、检查循环 Future，并等待线程池终止与数据库操作收尾。若全部计划任务成功则进入一致性校验；若仍有失败或未知状态，则保留未完成结果。无法确认运行任务是否已结束时进入排查，不能仅因心跳超时判成功。

shutdown 只禁止新的线程池提交，不会阻止已有长期循环继续从任务表领取，所以必须由业务控制信号和领取协议决定停止领取。等待超时不能当作停止成功。

**主动暂停**

先设置暂停控制状态，禁止新领取；各循环在领取前、领取成功后开始扫描前以及分页边界检查。领取与暂停存在竞争时，刚领取但尚未扫描的范围应安全保存为可恢复状态，并退出，不能悄悄继续扫描。

正在处理的页先核实结果，只保存已确认进度；失败或未知不推进。随后循环报告暂停并退出，协调方 shutdown 并等待线程及在途数据库操作收尾。多实例暂停需要共享控制状态，单机 AtomicBoolean 不能通知其他实例。暂停不算成功，恢复后沿用原范围与进度。

### 3.12 原子领取与协调汇总

**领取与执行顺序**

1. 完整任务清单和规划完成标记持久化后，受控启动最多 N 个工作循环。
2. 每个循环检查暂停及依赖状态，再原子领取一个待执行范围。领取时保存执行者与执行尝试编号，只有领取成功者才能扫描。
3. 按该范围的最后确认进度分页处理；每页结果和进度确认后再继续。一个循环同时只处理一个范围。
4. 范围成功后保存成功状态；可核实的局部失败保存失败状态并保留进度。允许继续时再领取另一个范围，失败范围不直接混入普通领取查询。
5. 状态保存失败、结果未知或公共依赖故障时暂停新领取并报告协调方；当前持有的范围不能被悄悄放弃后继续领新范围。
6. 暂时没有可领取任务时限时等待并检查结束指令。协调方按完整清单汇总、决定正常收尾或受控暂停；下一次恢复可重新启动工作循环。

**领取必须是原子的**

建议用带 batch_id、待调度状态和记录版本条件的条件更新完成领取，检查实际影响行数；查到候选记录不等于已获得执行权。领取竞争失败后重新检查控制状态并查找其他候选，避免无间隔争抢。领取事务必须短小，不能在处理百万条数据的整个过程中持有任务表行锁。

数据库提交响应丢失时，领取可能已经成功；先按执行尝试标识核实归属，不直接执行，也不立刻领另一个范围。进度和状态更新同样校验执行尝试身份。具体 SQL、索引、事务与并发争抢退避参数待实现验证。

**协调方的职责**

协调方独立监测工作循环健康、汇总任务表、更新批次结果并管理停止。例：T1 失败、T2 尚待执行，若 T1 是局部数据问题且状态已保存，循环可以领取 T2；若数据库整体不可用，则暂停全部新领取。没有领到任务、工作循环全部结束或线程池队列为空，都不能替代完整清单的成功判定。

若工作循环意外退出而仍有待办，协调方必须发现并告警，不能把剩余任务遗留后报告成功。补建循环或恢复前核实旧范围与在途操作收尾，限制同一执行组最多 N 个有效循环。多实例还需全局预算与故障接管协议；失败、执行中、成功三种批次结果维持不变。

该设计不再维护范围级 CompletionService、inFlight 或 W=N+Q。范围状态以任务表为准，固定数量的 Future 仅用于观察工作循环生命周期。

### 3.13 执行失败：分类、核实与恢复领取

以下为用户授权写入的设计方案，不代表已实现故障识别或自动恢复。失败分类用于选择处置路径，不能只凭异常名称断言根因。

**保存失败现场，保留确认进度**

任务失败时保留最后成功保存的 current_id，记录失败结果和原因。建议补充失败阶段（读取源表、写目标表、保存进度）、task_id、batch_id、执行尝试编号、本页主键范围、异常类型、SQLState、数据库错误码、时间及重试次数；用日志标识关联完整堆栈，任务表不保存整批业务数据。

另外记录本页写入结果是否未知。写入或提交响应超时可能发生在数据库已经提交之后，不能将超时等同于没有写入，也不能直接跳过该页。恢复位置不推进，先核实原操作，再依靠幂等和版本控制安全重做。

如果任务表所在数据库也不可用，失败状态可能无法落库，任务会残留为运行中。此时通过独立可用的日志、告警和心跳观测报告状态持久化失败；这些机制也可能故障，不承诺必然记录成功。存储恢复后核对任务及日志再修复状态，不能把“没有失败记录”当作没有失败。

**按证据区分故障**

| 分类 | 可观察现象 | 处理原则 |
| --- | --- | --- |
| 疑似下游暂时故障 | 连接失败、中断、服务不可用 | 结合数据库监控、连接探测、其他任务表现核实依赖状态 |
| 事务冲突 | 死锁、锁等待超时 | 核实事务是否回滚、是否仍有未决操作，再按规则有限重试 |
| 代码、配置或数据问题 | 空指针、SQL 语法错误、字段不存在、权限不足、转换失败 | 停止盲目重试，修复后再恢复 |
| 原因或结果未知 | 请求超时、提交响应丢失 | 保留原进度，先排查和核实，不自动标成功或无限重试 |

例如连接超时可能由数据库宕机、网络故障、连接池耗尽或慢 SQL 占用连接造成。异常堆栈说明出错位置，SQLState 和错误码提供分类线索，监控与探测提供依赖状态证据；多个任务同时失败支持公共依赖异常的判断，但仍不能单独证明数据库宕机。不得捕获所有 SQLException 后统一认定可重试。

**任务内部重试与执行结束后的恢复分开**

仅对已经明确允许重试、且结果与旧操作已核实的暂时故障执行有上限的退避重试。可将“初次失败后最多重试 3 次，间隔 1、2、4 秒”作为教学示例；生产次数、退避和抖动参数待确认，不适用于所有 SQL 异常。超过上限记录失败并告警；代码、配置、数据问题和未核实的未知结果不按此规则自动重试。

有限重试由持有当前范围的工作循环执行，仍占一个工作线程，不再向线程池提交副本。每次重试前检查暂停信号；只有本页全部结果与进度确认后才能继续下一页。

重试耗尽或不可重试时，结束当前范围处理，保存失败状态；若确认故障局部、旧操作已收尾且状态已保存，工作循环可继续领取其他范围。失败范围经修复和核实后，通过恢复入口重新取得可领取资格，不能在下一次普通领取中直接重试。恢复建立新的执行尝试，成功范围不重复领取；无已确认进度时才从原范围下界开始。

数据库整体故障时暂停本轮新领取，并按 3.11 通知已有任务合作式收尾，避免约 300 个任务不断请求故障库；暂停不意味着正在执行的 SQL 已终止。下游恢复后才进入恢复核实流程，不能仅依靠一次连接成功就证明业务读写已经恢复。

**按任务或批次恢复**

提供以 task_id 或 batch_id 指定范围的恢复入口，按以下顺序执行：

1. 确认依赖服务已恢复，或代码、配置、数据问题已修复；对未知结果先完成核实。
2. 确认原执行者已退出，原事务、在途写入及未决提交已收尾，避免两个执行者重叠迁移同一范围。
3. 从数据库任务表读取原扫描范围与最后确认进度，不重新生成覆盖原任务的范围，也不把成功任务重新置为待调度。
4. 受控恢复保留上一执行尝试历史，通过带原状态和版本条件的更新恢复待领取资格；工作循环原子领取时建立新执行尝试，具体字段、锁与事务协议待验证。
5. 若已有健康工作循环，可由其按正常流程领取；本次执行已结束则重新创建线程池并启动工作循环。生命周期管理防止重复启动，启动失败时未领取范围仍留在任务表。
6. 执行时以 id > current_id AND id <= end_id 读取下一页。已写成功但未确认保存进度的页可能被重复处理，按幂等及版本规则核实，确认整页后再保存新进度。

例如已确认进度为 1000，当前页写入部分成功后连接中断，不能直接将进度改为该页最后主键。原操作收尾并核实后，从 1000 之后重新读取该页；已成功数据按版本与幂等规则处理，避免旧值覆盖新值。本例数字仅解释恢复位置，不是生产批次配置。

**识别失联任务，防止重复接管**

进程崩溃可能来不及把任务改成失败，恢复不能只查询失败任务。建议记录执行者标识、执行尝试编号、心跳或租约到期信息，用于发现长时间残留的运行任务；心跳间隔和租约时长需结合长事务及网络暂停测定，具体生产值待确认。

心跳过期只说明可能失联，不证明旧进程或数据库操作已经停止。接管前要确认旧执行者收尾，或实现能够阻止旧执行者继续产生有效写入的隔离机制。仅在任务表更新一个新执行者标识，并不能阻止旧线程继续写目标数据库；无法确认安全时保留待核实状态并告警，不自动并发重跑。

**执行历史与批次状态回转**

建议使用独立执行尝试记录，至少关联 task_id、attempt_id、开始与结束时间、结果和失败原因。当前任务记录用于调度与恢复，历史用于排查；恢复时不直接清空旧失败原因。旧尝试也不能在新尝试开始后覆盖其任务进度或状态，更新需校验执行尝试身份。

同一批次允许恢复后重新汇总当前任务状态：失败任务经核实并正式转入待调度或运行中，若已没有其他失败任务但仍有未完成任务，批次变为执行中；若仍有任务失败，则仍为失败；全部计划任务成功才变为成功。仅点击恢复或探测到数据库可用，不直接把批次改成功。新一轮执行又失败时，新增失败历史，并按同一规则汇总。

上述恢复入口、分类、重试和状态回转与 016 的“保留最后确认进度、失败页允许重做”一致，具体持久化事务、并发领取和故障演练尚未验证。

## 4 已确认规则

- 表达易于理解、适用于面试口述；口述按拆分、领取执行、失败恢复、完成判定和暂停顺序展开，实现细节保留在详细方案。
- 本文保留迁移线程池设计总览职责；通用线程池知识已归入 `000_线程池` 目录，旧职责编号按当前文件布局修正。
- 补充线程池类型、核心线程数、最大线程数、队列类型选择和拒绝策略，并区分建议与已验证配置。
- 补充范围划分详细方案、任务描述含义、各配置选择理由、整轮完成判定，以及正常收尾和主动暂停的区别。
- 用户补充：旧表约有 3 亿条数据，主键递增；可按每个任务平均约 100 万条规划约 300 个任务。
- 每个任务维护进度记录，包含扫描起始 ID、扫描结束 ID、当前进度、处理结果和处理失败原因。
- 另设批次表记录整轮结果，按失败优先、无失败但未全部完成则执行中、全部成功完成才成功的顺序汇总。
- 最新方案采用专用固定 N 线程的工作循环，每个循环从数据库原子领取一个范围，当前范围收尾后再领取下一个；不再逐范围提交线程池任务。
- 由独立协调方监测工作循环、汇总完整任务清单和控制停止；循环退出或领不到任务不代表整轮成功。
- 完整任务描述和进度持久化到任务表，不预加载约 300 个范围对象；每个循环一次持有一个范围。
- 工作循环分页处理，确认本页结果并保存进度后解除数据引用，不累积整个范围数据。
- 线程数不是固定为 2；按连接预算、在线业务负载、迁移时限和多实例总并发压测选择。
- 增加失败分类、日志与监控核实、有限重试、按任务或批次恢复入口及执行尝试历史；恢复前确认旧执行者和未知写入结果。
- 当前范围内部有限重试仍占一个工作线程；范围失败后不直接重新领取，满足恢复条件后再恢复领取资格。
- 同一批次受控恢复后按当前任务状态重新汇总，可从失败回到执行中或成功，保留全部失败尝试历史。
- 线程池不代替进度、幂等、事务和全局并发控制。
- 提交被拒、任务异常、结果未知和停止都不能直接记为迁移完成。

## 5 待确认或待验证事项

- N 的生产取值、连接预算及在线业务验收指标需压测确定。
- 工作循环启动、异常退出检测、暂停及重启恢复尚未验证；SynchronousQueue 与 AbortPolicy 为配置实现示例。
- 并发 N 下当前范围描述、分页数据和写入缓冲的内存峰值待测量。
- 单个约 100 万条范围的执行耗时、各路径数据引用释放及长时间运行的内存变化尚未验证。
- 工作循环启动拒绝、部分启动失败后的收尾与受控补建尚未验证。
- 源表主键类型、稳定性和迁移过滤条件是否满足示例前提。
- 任务表和批次表的具体表结构、状态枚举及批次汇总并发控制。
- 任务进度、结果与批次汇总的事务和故障恢复协议。
- 公共下游故障识别阈值、自动重试白名单和生产退避参数。
- 心跳或租约参数、旧执行者隔离与任务原子领取协议。
- 状态存储不可用、进程崩溃、提交结果未知及恢复后再失败的故障演练。
- 实际零任务的迁移批次如何结束。
- 线程池生命周期、任务状态和协调方的衔接。
- 多实例部署下的全局并发和故障接管。
- 停止协议、JDBC 超时和在途写入核实。
