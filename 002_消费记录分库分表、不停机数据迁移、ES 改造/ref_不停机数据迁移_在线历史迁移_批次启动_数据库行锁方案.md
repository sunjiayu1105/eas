## 1 问题

如何只用数据库行锁和状态防止批次重复启动，并保证初始化完整提交？

## 2 高级 Java 面试核心考点

- 行锁与持久化状态：短事务内串行检查，提交后由状态阻止重复启动。
- 事务原子性：边界、完整清单和运行中状态一起提交。
- 故障窗口：明确回滚、提交未知和提交后宕机分别处理。

## 3 面试口述精炼版本

### 3.1 先锁定批次，检查能否启动

启动分成事务内准备和提交后调度两步。在同一数据库事务中，按主键执行 `SELECT ... FOR UPDATE`，锁住已有批次记录并读取状态。只有未启动或已暂停的批次才允许继续，其他状态或记录不存在时拒绝启动。锁定读取使其他启动请求等待，避免两个请求同时通过检查。

### 3.2 首次启动：完整初始化，一起提交

批次为未启动时，把扫描上下界保存到批次信息表，把完整任务清单写入任务表，再将批次改为运行中。这些写入在同一事务中提交或回滚，任务初始状态为待处理。例如初始化中途失败且事务完整回滚，已经写入的任务和扫描边界一起撤销，批次仍为未启动，下次可以重新初始化。

### 3.3 恢复启动：检查条件，复用任务

恢复前先确认上一次工作线程和数据库操作已结束，异常已修复；人工核实不能占用启动行锁。在锁定事务内确认批次为已暂停且满足恢复条件后，将批次改为运行中，沿用已有任务、扫描范围和进度，不重新初始化。

### 3.4 确认运行中状态提交后，再调度任务

只有确认运行中状态提交成功，才由调度器查询待处理、已暂停任务并提交线程池，行锁不持有到迁移结束。例如 A 提交运行中状态后，B 获得行锁并读到运行中，就拒绝启动。行锁保护检查与状态变更，持久化状态阻止后续重复启动。

### 3.5 结果未知或进程宕机，先核实再恢复

提交响应丢失时，不能假定事务已回滚，也不能直接重试初始化或继续调度。事务已提交、调度前宕机时，任务清单和运行中状态已经保存，须由运维核实上次执行安全结束后按恢复规则处理，不能重置为未启动。以上事务与故障处理仍需联调验证。

## 4 详细方案

### 4.1 启动检查

所有启动入口在同一数据库事务、同一连接中，按主键用 SELECT ... FOR UPDATE 锁住同一条预先存在的批次记录。记录不存在或状态不是未启动、已暂停时拒绝启动；未启动进入首次初始化流程，已暂停则在恢复检查通过后更新为运行中，复用原清单和进度。

恢复启动时，检查失败任务、未知结果及残留处理中任务是否已修复；发现未修复失败、未知结果或无法确认上一次执行安全结束时，按异常待处理流程阻止启动；异常状态无法保存也不能继续调度。人工排查必须在启动前完成，不能持有行锁等待运维处理。事务内只检查已具备的恢复条件。

行锁负责串行检查，持久化的运行中状态负责在提交后拦截后续启动请求。[选锁理由](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_在线历史迁移_批次启动_为什么选择数据库行锁.md>)、[加锁与释放机制](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_在线历史迁移_批次启动_数据库行锁实现.md>) 和 [初始化原子性](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_批次状态控制_启动处理逻辑_为什么状态更新与任务初始化必须在同一事务中.md>) 分别展开技术依据；本篇负责将它们组织成启动流程。恢复核实步骤见 [暂停与故障恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_批次状态控制_异常待处理批次恢复.md>)。

### 4.2 初始化事务与故障窗口

**初始化与状态转换必须一起提交**

批次初始状态为“未启动”，任务初始状态称“待处理”，不混用两个层级。任务数量由 ID 跨度计算，清单只写范围等信息，本方案在一个短事务内完成以下操作；事务容量、锁等待和实际耗时仍需验证。

1. 开启数据库事务，按批次主键执行 SELECT ... FOR UPDATE，锁定已有的批次记录并检查状态。首次启动时，锁定查询、状态检查与任务初始化必须处于同一事务，不能检查后先释放锁、再另开事务初始化；恢复启动不再初始化任务，只需在同一事务中完成状态检查和状态更新。
2. 批次状态为未启动时，将整个批次的扫描上下界写入批次信息表，将完整任务清单写入任务表。各任务保存自己的扫描范围，状态为待处理、确认进度为 NULL，并核对范围和计划数量。
3. 在同一事务中将批次信息表中的批次状态改为运行中，然后提交并释放行锁。
4. 确认运行中状态提交成功后，才查询任务并向线程池提交。行锁只覆盖启动事务，不持有到迁移完成；事务中不执行数据迁移，也不等待 Future。

批次信息表中的状态、扫描上下界与任务表中的完整任务清单必须在同一数据库事务中保存，使用支持事务的存储引擎。任务表需有唯一约束防止重复写入，任务 ID 或范围唯一键必须稳定，不能每次生成新 ID 就认为能够防重。范围计算如需昂贵扫描，应在事务外规划，并在事务中核对并保存同一份边界，避免长期占用控制记录锁。

由此保证：批次正常离开未启动状态时，完整任务清单已可靠保存。初始化明确回滚时，状态仍为未启动，下次可重新初始化；事务已提交但进程在提交线程池前宕机时，清单完整、状态为运行中，须确认上一次迁移的线程和数据库操作已结束后恢复，不能再次初始化。提交响应丢失时先查询核实事务结果，不直接重试初始化，也不贸然启动线程池。

初始化中途失败与分别提交的对比见 [初始化原子性](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_批次状态控制_启动处理逻辑_为什么状态更新与任务初始化必须在同一事务中.md>)。若人工修数或旧实现破坏了清单完整性，必须停止启动并核对。确认初始化完整回滚后，仍允许从未启动状态重新初始化，失败告警通过日志报告。

再次启动已暂停的批次时，在同一启动互斥保护下，仅将批次状态原子改为运行中，复用原任务清单和各任务进度。检查与状态转换不能被其他启动请求穿插；未确认状态转换成功，不得提交任务。

启动事务结束就释放行锁，不等待迁移完成。后续请求必须重新锁定并检查持久化状态；正常运行中状态拒绝再次启动。锁等待超时或死锁时结束整个启动事务，不绕过锁执行；具体异常释放和并发时序由 [加锁与释放机制](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_在线历史迁移_批次启动_数据库行锁实现.md>) 维护，超时配置仍待验证。

任务划分与字段见 [任务范围划分](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/026_不停机数据迁移_在线历史迁移_任务范围划分.md>)。本节事务只保存任务计划，不迁移业务数据。核心示例见 [完整启动实现](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_在线历史迁移_批次启动_数据库行锁实现.md>)。确认运行中状态提交成功后，由 [线程池调度](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/027_不停机数据迁移_在线历史迁移_线程池调度.md>) 查询并提交任务。
