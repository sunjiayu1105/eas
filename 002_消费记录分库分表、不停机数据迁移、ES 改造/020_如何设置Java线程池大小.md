# 020_如何设置Java线程池大小

## 1 说明

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。适用于 Java 8 平台线程执行阻塞任务的常见场景。

## 2 问题

一般情况下，如何设置 Java 线程池的大小？

### 2.1 考点

1. 根据任务在计算和阻塞等待上花的时间，判断增加线程能否提高 CPU 利用率。
2. 根据线程池可用的 CPU 预算、计算时间和等待时间估算初始线程数。
3. 判断连接数、下游并发能力等约束会怎样限制有效并发。
4. 用代表性负载检验吞吐量、排队时间和尾延迟，确定满足目标的取值。

### 2.2 答题范围

分别说明计算密集型和阻塞 I/O 密集型任务的起始线程数怎样确定。先给完整估算公式，再用假设的 CPU 预算、计算时间和等待时间算出候选值，说明下游并发限制及压测结果如何改变取值。

### 2.3 候选理由

线程数会同时影响资源利用率和请求等待时间。能否解释候选值怎样得到、又怎样验证，比记住某个固定倍数更能体现判断依据。[线程池原始材料](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/078_线程池大小与任务积压原始材料.md:1>)

## 3 面试口述版本

**计算密集型任务**

如果线程大部分时间都在计算，比如做哈希运算，阻塞等待时间接近零，我会按分给这个线程池的 CPU 算力估算。

**起始线程数 ≈ 分给线程池的 CPU 核数**

我会先在代表性高峰负载下，让这个池暂时不接任务，连续观察多个采样窗口，估算同一实例上其他业务的 CPU 用量。容器部署时，总算力和用量都按同一容器计算。

**其他业务平均占用的核数 ≈ 窗口内累计消耗的 CPU 时间 ÷ 窗口时长**

假设实例可用 8 核，在一个较忙的 10 秒窗口里，其他业务的线程合计用了 30 秒 CPU 时间，平均就占了 30 ÷ 10 = 3 核。多个核可以同时工作，所以累计 CPU 时间可以超过 10 秒。假设再给高峰波动留 1 核，线程池可用的预算就是 8 − 3 − 1 = 4 核。我会从 **4 个线程** 开始压测，同时看原有业务的慢请求耗时是否仍达标，再决定预留多少算力。

**同步阻塞 I/O 型任务**

如果线程既要计算，又要同步查库或调用远程接口，等结果时它仍占着工作线程。我会测量同一类任务平均计算多久、阻塞等待多久，用下面的公式估算。

**起始线程数 ≈ 分给线程池的 CPU 核数 ×（1 + 平均阻塞等待时间 ÷ 平均计算时间）**

假设仍能用 4 个核心，每个任务平均计算 10 毫秒、阻塞等待 20 毫秒。一个线程平均只有三分之一的时间在计算，所以从 `4 ×（1 + 20 ÷ 10）= 12` 个线程开始压测。任务在工作队列里等待领取的时间不计入公式。如果 I/O 是异步的，工作线程发出请求就返回池中，等待远程响应的时间也不计入。

比如，数据库连接已经用满，增加线程只会让更多线程等连接。

假设目标是每秒处理 300 个请求，95% 的请求在 100 毫秒内返回。保持请求组合不变，每秒发 300 个请求。

- 用 8 个线程时，每秒只完成 260 个，请求越积越多。
- 用 12 个线程时，每秒完成 300 个，队列不再增长，95% 的请求在 80 毫秒内返回。
- 加到 16 个线程，每秒仍完成 300 个，95% 的请求在 95 毫秒内返回。

我会选 12 个线程，因为处理量和响应时间都已达标。

## 4 详细方案

用同一组有代表性的任务测量每个任务的线程 CPU 时间 C 和执行期间的阻塞等待时间 W。任务进入线程池之前或在工作队列中排队的时间要单独统计。线程平均占用一个核心的比例约为 C / (C + W)，所以候选线程数约为 CPU 预算 × (1 + W / C)。CPU 预算要考虑进程配额、同机其他负载和希望留出的余量。等待时间随并发增长时，重新测量。

以固定大小的池做对比，改变线程数时保持队列策略和负载一致。配置弹性池时还要看工作队列。核心线程都忙时，ThreadPoolExecutor 会先尝试入队，入队失败后才尝试扩到最大线程数。使用近似无界的队列时，单独调大 maximumPoolSize 往往起不到扩容作用。[Java 8 ThreadPoolExecutor](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)
