# 020_如何设置Java线程池大小

## 1 说明

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。适用于 Java 8 平台线程执行阻塞任务的常见场景。

## 2 问题

一般情况下，如何设置 Java 线程池的大小？

### 2.1 考点

1. **估算线程池能用多少 CPU。** 怎样根据高峰期的 CPU 使用时间估算其他业务占用的核数，并给流量波动留出余量？
2. **估算计算密集型任务的起始线程数。** 当线程大部分时间都在计算时，为什么可以从接近可用 CPU 核数的线程数开始压测？
3. **估算同步阻塞 I/O 任务的起始线程数。** 怎样根据平均计算时间和平均阻塞等待时间估算线程数？哪些等待时间可以计入公式？
4. **判断增加线程能否提高吞吐量。** 当等待主要来自数据库连接已用满时，为什么增加工作线程可能只会让更多线程等连接？
5. **用压测确定最终线程数。** 在请求类型、比例和到达速率相同的条件下，怎样根据完成量、队列是否持续增长，以及第 95 百分位响应时间，选出满足目标的较小线程数？

### 2.2 答题范围

按一般场景回答。先用一个假设算例说明线程池能分到多少 CPU。再分别给出计算密集型任务和同步阻塞 I/O 任务的估算公式，代入数值算出各自从多少个线程开始测。解释 I/O 公式时，讲清哪些等待会占住工作线程，以及数据库连接用满后继续增加线程会发生什么。最后用同一负载下几档线程数的压测结果，说明为什么选中其中一档。

### 2.3 候选理由

项目材料涉及线程池大小与任务积压。在讨论迁移任务具体开多少个线程前，可以先用这道通用问题考查候选人是否掌握取值方法。其中有两个值得听候选人解释的判断：**同样有 4 核可用，为什么两类任务可以从不同的线程数开始测？如果 12 个和 16 个线程都达到吞吐目标，又凭什么选 12 个？** 前者考查能否根据任务特征估算，后者考查能否根据实际表现做决定。[线程池大小与任务积压原始材料](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/078_线程池大小与任务积压原始材料.md:1>)

### 3.1 估算线程池可用的 CPU 核数

我会先让这个池暂时不接任务，在有代表性的业务高峰连续观察几个时间窗口，看其他业务用了多少 CPU。服务跑在容器里时，按这个容器可用的 CPU 和实际用量来算。

**其他业务平均占用的核数 ≈ 这段时间累计使用的 CPU 时间 ÷ 观察时长** [Kubernetes 资源指标文档 · Measuring resource usage / CPU](<https://kubernetes.io/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/#cpu>)

假设实例有 8 核。在较忙的 10 秒里，其他业务的线程合计用了 30 秒 CPU 时间，相当于平均占用 3 核。多个核心能同时工作，所以 10 秒内可以用掉 30 秒 CPU 时间。假设再留 1 核应对流量波动，线程池就能用 `8 − 3 − 1 = 4` 核。实际留多少，要看高峰波动和压测时原有业务的响应时间。

### 3.2 按任务类型估算起始线程数

#### 3.2.1 计算密集型任务

像哈希计算这样的任务，线程大部分时间都在用 CPU。

**起始线程数 ≈ 线程池可用的 CPU 核数**

按上面的 4 核预算，我会从 **4 个线程** 开始测。[Zalando 工程文章 · 搜索 blocking coefficient，见等待时间接近零时的估算](<https://engineering.zalando.com/posts/2019/04/how-to-set-an-ideal-thread-pool-size.html>)

#### 3.2.2 同步阻塞 I/O 型任务

比如线程查数据库，发出请求后要等结果才能继续。它等待时，其他线程可以用 CPU，所以还要看每个任务算多久、等多久。

**起始线程数 ≈ 线程池可用的 CPU 核数 ×（1 + 平均阻塞等待时间 ÷ 平均计算时间）**

假设一个任务计算 10 毫秒、等数据库 20 毫秒，一个线程平均只有三分之一的时间在用 CPU。要用上 4 核，可以从 `4 ×（1 + 20 ÷ 10）= 12` 个线程开始测。公式只计工作线程被占住的等待时间。任务还在队列里排队，或者异步请求发出后线程已经返回池中，这些时间都要排除。数据库连接已经用满时，也要留意加线程是否只会增加等待。[Zalando 工程文章 · 搜索 Target CPU utilization，核对公式和数据库连接池限制](<https://engineering.zalando.com/posts/2019/04/how-to-set-an-ideal-thread-pool-size.html>) · [Java 8 ThreadPoolExecutor · Queuing 中的 Bounded queues](<https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html>)

### 3.3 比较压测结果，确定线程数

假设目标是每秒处理 300 个请求，并且至少 95% 的请求在 100 毫秒内返回。我会保持请求类型和比例相同，每秒都发 300 个请求，只调线程数。假设测到以下结果：

- **8 个线程**：每秒完成 260 个，请求越积越多。
- **12 个线程**：每秒完成 300 个，队列不再增长，95% 的请求在 80 毫秒内返回。
- **16 个线程**：每秒仍完成 300 个，95% 的请求在 95 毫秒内返回。

我会选 **12 个线程**。这一档已经满足处理量和响应时间要求，加到 16 个也没有多处理请求。[Grafana k6 · Constant arrival rate，每次迭代发一个请求即可固定请求到达速率](<https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/>) · [Grafana k6 · Thresholds，用第 95 百分位响应时间判断是否达标](<https://grafana.com/docs/k6/latest/using-k6/thresholds/>)

## 4 详细方案

用同一组有代表性的任务测量每个任务的线程 CPU 时间 C 和执行期间的阻塞等待时间 W。任务进入线程池之前或在工作队列中排队的时间要单独统计。线程平均占用一个核心的比例约为 C / (C + W)，所以候选线程数约为 CPU 预算 × (1 + W / C)。CPU 预算要考虑进程配额、同机其他负载和希望留出的余量。等待时间随并发增长时，重新测量。

以固定大小的池做对比，改变线程数时保持队列策略和负载一致。配置弹性池时还要看工作队列。核心线程都忙时，ThreadPoolExecutor 会先尝试入队，入队失败后才尝试扩到最大线程数。使用近似无界的队列时，单独调大 maximumPoolSize 往往起不到扩容作用。[Java 8 ThreadPoolExecutor](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)
