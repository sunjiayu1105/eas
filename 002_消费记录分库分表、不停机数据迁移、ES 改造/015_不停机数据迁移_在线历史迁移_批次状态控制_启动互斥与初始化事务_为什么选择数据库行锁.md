### 3.1 总体选型：用数据库行锁保护批次启动

本场景选择数据库行锁，通过在事务中执行 `SELECT ... FOR UPDATE`，锁住同一条批次记录，再检查状态，防止多个启动请求同时通过检查。

**首次启动：** 批次状态更新、扫描上下界保存和完整任务清单初始化在同一事务中完成，一起提交或回滚。

**恢复已暂停的批次：** 检查状态及恢复条件后，只更新批次状态，不重新初始化任务清单。两种场景都在确认事务提交成功后才调度迁移任务。

这些操作涉及的数据都在同一个数据库中，行锁与业务写入可以由同一个短事务管理。当前请求提交后，后续请求读到“运行中”，就拒绝再次启动。

如果改用 Redis 锁，还要处理锁失效后原请求继续执行的情况：原请求没有停止，新请求又拿到锁，缺少额外保护时，两者就可能重复创建任务或并发修改批次状态。因此，本场景直接使用数据库行锁，减少额外的锁有效期和续期管理。

### 3.2 首次启动：状态更新与任务初始化一起提交

先在事务中用 SELECT ... FOR UPDATE 锁住已有批次记录，并读取当前状态。确认批次为“未启动”后，将批次改为“运行中”、保存扫描上下界并初始化完整任务清单。这些写入一起提交，任一步失败就完整回滚；可以先更新状态，也可以先插入任务，不能分别提交。确认提交成功后才调度迁移任务。

#### 3.2.1 示例：只有 A 初始化任务清单

A 锁住批次记录并开始初始化任务清单，B 在锁定同一条记录时等待。A 成功提交运行中状态并释放锁后，B 获得锁，读到运行中状态，就拒绝启动，不再初始化任务清单。行锁负责启动互斥，事务保证本次写入一起提交或回滚，状态检查阻止后续重复启动。

### 3.3 恢复启动：检查并更新状态，不重新初始化任务

恢复启动也要先在事务中锁住批次记录，再读取状态。确认批次为“已暂停”且满足恢复条件后，将状态改为“运行中”。这个事务不重新初始化任务清单；确认提交成功后，再调度已有任务，从保存的进度继续迁移。单条状态更新本身是原子的，但先查询、再更新不会自动防止两个请求同时通过检查，所以仍需行锁保护。

#### 3.3.1 示例：只有 A 获准恢复批次

A 锁住已暂停批次的记录，检查通过后更新为运行中，B 等待同一行锁。A 提交后，B 获得锁并读到运行中状态，就拒绝再次恢复，避免两个请求重复调度已有任务。

### 3.4 Redis 锁的风险：锁过期不代表原操作停止

Redis 锁到期后，其他请求可以重新获取锁，但原来持锁的线程不会因此停止，已经发出的 MySQL 操作也不会自动取消。

#### 3.4.1 示例：A、B 同时初始化任务清单

假设改用 Redis 锁协调首次启动：A 获得锁，读到未启动状态后卡住；锁过期后，B 获得锁，仍读到未启动，便开始初始化任务清单。B 尚未提交运行中状态时，A 恢复并继续执行；如果没有数据库端的额外保护，两个请求就可能同时为同一批次创建任务、修改状态。

#### 3.4.2 延长有效期和续期仍有局限

延长有效期不能保证 A 一定在锁到期前结束，续期也可能失败。如果锁已失效而 A 仍在执行，就可能与新持锁请求同时初始化任务清单。因此，不能仅凭有效期较长或配置了续期，就认为不会重复创建任务。

### 3.5 两种启动都要遵守的事务边界

行锁只持有到启动事务结束，不等待整个迁移完成。启动事务发生数据库异常或提交结果未知时，不能继续调度迁移任务，应先核实批次状态和任务清单，再按既有恢复规则处理，不能直接重试或重置批次状态。当前方案已确认，实际并发和故障行为仍待验证。

## 4 详细方案

### 4.1 先确定保护对象，再选择锁

需要串行执行的是批次启动事务。所有启动入口在同一事务、同一连接中按主键锁住同一条已有批次记录，检查状态后分两种情况处理。

**首次启动：** 批次为未启动时，将批次状态改为运行中、保存扫描上下界和初始化完整任务清单。这些写入必须一起提交或一起回滚，事务内部的执行先后不改变这一要求。

**恢复启动：** 批次为已暂停且满足恢复条件时，将状态改为运行中，不重新写入扫描边界或初始化任务清单。状态检查与更新之间保持行锁，避免两个请求都依据已暂停状态继续启动。单条 UPDATE 的原子性不能代替对整个“检查再更新”过程的并发保护。

恢复前的人工排查按主文档要求完成，不能持锁等待人工处理；事务内只检查已具备的恢复条件。两种场景都在确认提交成功后才调度任务。

行锁只保护这段启动过程，数据迁移在提交确认后执行。不在事务里迁移全部历史数据，也不持锁等待线程池任务结束。本篇只解释选型理由及必要的事务边界；具体如何加锁、等待和释放锁，以及异常处理方式，见 [批次启动实现](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_为什么选择数据库行锁_批次启动实现.md>)。完整启动流程及初始化约束由 013 维护，实现代码由 016 统一维护。

### 4.2 互斥、原子性与状态分别负责什么

行锁让其他启动请求等待，避免检查和更新被并发穿插；同库事务保证扫描边界、任务清单和运行中状态一起提交或回滚；运行中状态在锁释放后继续阻止重复启动。这三个作用不能全部归因于“用了行锁”。

例如 A 锁住批次记录并开始初始化，B 在锁定查询处等待。A 提交后，B 获得锁并读取运行中状态，因此拒绝启动。如果 A 初始化失败并完整回滚，B 读取回滚后的状态重新判断。所有请求都必须遵守这套流程，不能绕过检查直接提交任务。

### 4.3 为什么 Redis 锁没有简化本场景

两种锁都可以用于协调并发请求，但它们与业务数据的事务边界不同。

**数据库行锁：** 锁住的就是本次要检查和更新的控制记录。在当前同库事务方案中，锁的持有期与事务结束关联，不需要再维护一份独立的锁有效期及续期机制。仍须正确管理事务、连接、超时及死锁。

**Redis 锁：** 锁记录与 MySQL 业务事务属于两个系统。取得 Redis 锁并不意味着 MySQL 初始化已成功；释放锁前必须明确数据库操作结果，状态和任务清单依然需要数据库事务保证原子性。不能把“拿到锁”当作“可以不检查数据库状态”。

“Redis 锁不能替代数据库事务”说明的是职责边界，两者可以配合使用，不能仅凭仍需事务就排除 Redis 锁。本场景采用数据库行锁，是因为受保护数据和事务已经在同一数据库内，能够减少额外协调机制；不是证明 Redis 锁不可用，也不是未经压测就断言行锁性能更好。

### 4.4 锁过期为什么不能代表原请求结束

以下是假设仅用 Redis 锁协调启动、未保留数据库端互斥保护的示例，不是当前行锁方案的执行流程。假设 A 取得 Redis 锁后发生长时间停顿，锁的有效期已经结束，但 A 的线程或数据库操作尚未结束。B 随后取得锁，A 又恢复执行，两个请求就可能继续处理同一业务。加长有效期只能减少某些超时概率，还会延长持有者宕机后的等待时间，不能证明原请求的操作必定在到期前结束；自动续期也必须考虑失败和进程停顿。

可靠实现还需要处理失去锁后的行为、只释放自己持有的锁，以及在必要时由数据库或其他资源端拒绝过期持有者的操作。仅在写入前查询一次 Redis 锁是否存在仍可能发生检查后过期。本项目不新增这套实现，也不设置未经确认的 Redis 过期时间。

### 4.5 行锁的适用前提和剩余风险

本方案要求控制表和任务表使用支持事务的 InnoDB、初始化写入处于同库事务、按主键锁定已存在的控制记录，并保持启动事务足够短。缺少合适索引、初始化耗时过长或事务未生效，都会影响锁范围、等待时间或正确性；实际耗时和超时值仍待验证。

锁等待超时不必然回滚整个事务，启动失败时应结束整个启动事务；数据库识别断连和回滚也可能需要时间。提交响应丢失时不能假定未提交，已提交的运行中状态也不会因应用宕机自动复原。必须沿用主文档的人工核实和恢复规则，不能为重新启动直接重置状态。

如果以后要协调的资源跨数据库或没有合适的控制记录，需要重新评估协调方案，不能把本场景结论推广为所有分布式场景都应使用行锁。具体 Redis 产品版本与客户端未确认，本篇不提供相关配置或实现代码。

依据：主文档的同库事务与提交后调度设计，以及 [MySQL 8.0 Locking Reads](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-locking-reads.html) 的事务内锁定读取规则。此前已核对 MySQL 官方页面关于事务提交或回滚释放锁、SELECT FOR UPDATE 读取最新可用数据的说明；本轮未重新在线核验。Redis 锁有效期示例用于机制分析，不代表已经验证某个 Redis 部署或客户端的故障行为。Redis 官方[分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)此前访问返回 HTTP 403，相关来源内容待核验。

### 5.1 方案选择与职责边界

- 本文解释批次启动为什么选择数据库行锁；沿用数据库行锁与批次状态方案，不引入 Redis 锁。
- 015 明确通过 `SELECT ... FOR UPDATE` 使用行锁，并说明首次初始化的同一事务要求；具体加锁、等待、释放及异常处理实现由 016 展开。
- 不将“仍需数据库事务”单独作为不使用 Redis 锁的理由；Redis 锁与事务可以配合使用，“不能替代事务”只用于说明职责边界。

### 5.2 启动与初始化约束

- 既要防止同一批次被并发重复启动，也要防止首次启动时任务清单被重复初始化；恢复启动沿用已有任务和进度，不重新初始化。
- 恢复启动时，在同一事务中锁定批次记录、检查状态及恢复条件，并更新为运行中；确认提交成功后才调度已有任务继续迁移，不将数据迁移放入状态更新事务。
- 首次启动时，批次状态从未启动更新为运行中，与扫描边界保存、完整任务清单初始化在同一事务中提交；任一步失败则完整回滚，不要求固定事务内写入顺序。
- 沿用批次状态名称“未启动／运行中／已暂停”，不与任务状态“待处理／处理中”混用；表达优化不得改变已确认的技术结论、成立条件和验证状态。

## 7 异议与分析

“Redis 锁设置足够长就安全”不成立：锁的有效期结束与原请求是否结束是两件事。数据库行锁也不自动保证完整业务正确，仍依赖事务原子性、状态检查和安全恢复。本篇说明当前场景的选择依据，不进行无证据的性能排名。
