## 3 面试口述精炼版本

口述内容字符数：286

**要保护的操作都在数据库内**

本场景要防止多个请求同时检查批次状态、初始化任务并改成运行中。这些数据在同一个数据库内，所以我会在短事务中用 SELECT FOR UPDATE 锁住已有批次记录，完成检查和初始化后一起提交。行锁负责启动互斥，事务保证清单和状态一起提交，提交后的运行中状态拦截后续启动请求。

**减少两套机制的协调**

Redis 锁也能协调请求，但不能代替数据库事务，还需处理锁过期、续期失败以及释放时机。锁过期不代表旧请求已经停止，单纯加长有效期不能保证安全。本场景已有数据库事务，因此沿用行锁更直接；不持锁到迁移结束，数据库异常和提交结果未知时仍需停止启动并核实。

## 4 详细方案

### 4.1 先确定保护对象，再选择锁

需要串行执行的是批次启动事务：查询并锁住预先存在的批次控制记录，由应用判断是否允许启动；首次启动保存扫描上下界和完整任务清单，再更新运行中状态。所有启动入口使用同一条主键记录，并在同一事务、同一连接中完成这些操作。

行锁只保护这段启动过程，数据迁移在提交确认后执行。不在事务里迁移全部历史数据，也不持锁等待线程池任务结束。完整代码及初始化边界由主文档维护；本篇只解释为什么选择该方案。

### 4.2 互斥、原子性与状态分别负责什么

行锁让其他启动请求等待，避免检查和更新被并发穿插；同库事务保证扫描边界、任务清单和运行中状态一起提交或回滚；运行中状态在锁释放后继续阻止重复启动。这三个作用不能全部归因于“用了行锁”。

例如 A 锁住批次记录并开始初始化，B 在锁定查询处等待。A 提交后，B 获得锁并读取运行中状态，因此拒绝启动。如果 A 初始化失败并完整回滚，B 读取回滚后的状态重新判断。所有请求都必须遵守这套流程，不能绕过检查直接提交任务。

### 4.3 为什么 Redis 锁没有简化本场景

两种锁都可以用于协调并发请求，但它们与业务数据的事务边界不同。

**数据库行锁：** 锁住的就是本次要检查和更新的控制记录。在当前同库事务方案中，锁的持有期与事务结束关联，不需要再维护一份独立的锁租约。仍须正确管理事务、连接、超时及死锁。

**Redis 锁：** 锁记录与 MySQL 业务事务属于两个系统。取得 Redis 锁并不意味着 MySQL 初始化已成功；释放锁前必须明确数据库操作结果，状态和任务清单依然需要数据库事务保证原子性。不能把“拿到锁”当作“可以不检查数据库状态”。

因此本场景采用数据库行锁，是因为受保护数据和事务已经在同一数据库内，能够减少额外协调机制；不是证明 Redis 锁不可用，也不是未经压测就断言行锁性能更好。

### 4.4 锁过期为什么不能代表旧请求结束

假设 A 取得 Redis 锁后发生长时间停顿，锁的有效期已经结束，但 A 的线程或数据库操作尚未结束。B 随后取得锁，A 又恢复执行，两个请求就可能继续处理同一业务。加长有效期只能减少某些超时概率，还会延长持有者宕机后的等待时间，不能证明旧操作必定在到期前结束；自动续期也必须考虑失败和进程停顿。

可靠实现还需要处理失去锁后的行为、只释放自己持有的锁，以及在必要时由数据库或其他资源端拒绝过期持有者的操作。仅在写入前查询一次 Redis 锁是否存在仍可能发生检查后过期。本项目不新增这套实现，也不设置未经确认的 Redis 过期时间。

### 4.5 行锁的适用前提和剩余风险

本方案要求控制表和任务表使用支持事务的 InnoDB、初始化写入处于同库事务、按主键锁定已存在的控制记录，并保持启动事务足够短。缺少合适索引、初始化耗时过长或事务未生效，都会影响锁范围、等待时间或正确性；实际耗时和超时值仍待验证。

锁等待超时不必然回滚整个事务，启动失败时应结束整个启动事务；数据库识别断连和回滚也可能需要时间。提交响应丢失时不能假定未提交，已提交的运行中状态也不会因应用宕机自动复原。必须沿用主文档的人工核实和恢复规则，不能为重新启动直接重置状态。

如果以后要协调的资源跨数据库或没有合适的控制记录，需要重新评估协调方案，不能把本场景结论推广为所有分布式场景都应使用行锁。具体 Redis 产品版本与客户端未确认，本篇不提供相关配置或实现代码。

依据：主文档的同库事务与提交后调度设计，以及 [MySQL 8.0 Locking Reads](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-locking-reads.html) 的事务内锁定读取规则。Redis 租约故障示例用于机制分析，不代表已经验证某个 Redis 部署或客户端的故障行为。

## 7 异议与分析

“Redis 锁设置足够长就安全”不成立：租约到期与旧执行是否结束是两件事。数据库行锁也不自动保证完整业务正确，仍依赖事务原子性、状态检查和安全恢复。本篇说明当前场景的选择依据，不进行无证据的性能排名。
