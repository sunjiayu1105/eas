# 011_不停机数据迁移_在线历史迁移

## 1 问题

如何在业务不停机的情况下，把旧表历史数据安全迁移到新表？

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。具体实现和运行效果尚未验证。

## 2 面试口述精炼版本

口述内容字符数：232

**先双写，再迁移**

先完成旧表 version 改造并开启双写，再启动历史迁移。双写负责同步迁移期间的新变化，历史迁移负责补齐启动前的存量数据，两条链路同时运行但职责不同。

**按范围分批处理**

把旧表递增主键划成互不重叠的任务范围，每个范围再按批次读取。每批处理成功后保存进度，失败批次允许重做。

**写入与校验**

新表按 merchantNo + serialNo 定位，缺失就插入，已有记录只接受更大 version。全部范围完成后，以旧表为准做一致性校验和修复，确认连续多轮无差异后再进入灰度读。

## 3 详细方案

### 3.1 先让双写生效，再启动迁移

开启双写前，先完成旧表 version 初始化和业务写入口改造。双写生效后启动历史迁移；双写持续同步新建、修改和删除，迁移只补齐启动前已经存在的存量记录。

迁移读取旧表当前数据和业务版本，不自行生成或递增版本。整体扫描范围和终点必须先明确，具体边界待项目确认。

### 3.2 一批数据的处理顺序

~~~text
双写开启
  → 确定旧表迁移范围
  → 按互不重叠的主键范围分批读取
  → 按 merchantNo 路由，使用 serialNo 定位
  → 缺失则插入；已有则按 version 条件更新
  → 核实本批每条结果
      ├─ 失败或结果未知：保留进度，重试或告警
      └─ 成功或安全跳过：保存本批进度
  → 全部范围完成
  → 新旧表一致性校验与修复
  → 灰度读
~~~

每个任务平均约 100 万条、总量约 3 亿条时，可先按约 300 个范围任务规划；这是规模规划，不等于并发数。每批 500—1000 条是参考调参范围，实际值需压测。

### 3.3 三个机制如何配合

- 限流：限制同时运行的任务数和批间请求频率。
- 断点续跑：整批结果确认后才保存进度；未确认批次恢复时重做。
- 重试幂等：重复插入受唯一约束保护，更新在 SQL 中比较 version，旧版本不能覆盖新版本。

线程池只负责执行和生命周期管理，不能代替进度存储、幂等判断或多实例全局并发控制。

### 3.4 迁移完成和灰度读的条件

迁移进度完成不等于数据已经一致。需要以旧表为基准完成新旧表校验，修复缺失、多余和字段差异，并核对修复结果。连续多轮完整校验无差异、双写正常、补偿无积压后，才具备灰度读条件；最终切写仍需按停写交接方案执行。

## 4 已确认规则

- 先开启业务双写，再启动历史迁移；双写负责在线变化，迁移负责补齐存量。
- 不同迁移任务处理互不重叠的主键范围。
- 旧表保留最近 5 年、约 3 亿条数据，按每个任务平均约 100 万条规划约 300 个任务。
- 每批 500—1000 条只是参考调参范围，实际批次、并发和等待时长需压测。
- 新表按 merchantNo + serialNo 定位；serialNo 全局唯一并建立唯一索引。
- 缺失记录插入，已有记录按 version 条件更新；迁移不生成新版本。
- 迁移完成后必须校验和修复，再进入灰度读。
