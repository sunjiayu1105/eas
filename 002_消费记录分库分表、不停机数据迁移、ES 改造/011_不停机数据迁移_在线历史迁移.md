# 011_不停机数据迁移_在线历史迁移

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。本文说明迁移整体设计，具体实现和运行效果尚未验证。

主分文档层级见 [专题导航](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/README.md>)。

## 1 问题

如何在业务继续运行时，将旧表历史数据迁移到分库分表后的新表，并确认可以切换查询？

## 2 高级 Java 面试核心考点

- 存量与增量衔接：先让业务双写生效，再搬运历史数据。
- 并发迁移与恢复：按固定范围分页处理，限制数据库压力，保存各任务确认进度。
- 幂等与版本保护：重复写入不新增业务记录，旧数据不覆盖较新版本。
- 验收与切换边界：任务完成后校验数据，查询灰度与最终停写交接分别处理。

**分批处理，保存进度**

将固定范围拆成任务，用固定 N 个线程分页处理，N 按数据库预算压测确定，并通过分页间等待控制访问频率。每页结果确认后保存各任务进度；任务失败就停止新处理并告警，人工修复、确认上次操作结束后再从原进度继续。

详见：[执行任务与控制压力（第 50 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/011_不停机数据迁移_在线历史迁移.md:50>)。

## 4 详细方案

### 4.1 存量与增量的交接

开启双写前，先完成旧表 version 初始化和全部相关业务写入口改造。旧表业务修改与版本递增、本地消息记录在同一事务中提交，后台任务将消息写入新表；这是当前项目设计，不能仅凭文档认定已上线。版本及增量同步依据见 [006 版本与同步方案](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/006_不停机数据迁移_如何防止旧版本数据覆盖新版数据.md>)。

双写生效后首次查询旧表 MIN/MAX，将扫描上下界保存到批次信息表，再生成完整任务清单。恢复时不重新查询边界或扩大范围。固定上界不形成数据库快照：例如迁移已扫描过某个 ID，相关事务之后才提交，一次扫描不能自行保证捕获它，仍需增量同步和一致性校验。

双写和历史迁移的失败处理不同：同步消息按消息补偿规则处理；历史迁移任务不自动重试，统一暂停、告警并由人工恢复。不能把参考文章中的消息重试队列当成历史任务自动重派的依据。

### 4.2 执行任务与控制压力

按以下顺序交接，各专题只维护自己的详细机制：

1. 批次启动检查和完整任务初始化提交成功后，才提交线程池；暂停、恢复和收尾由 [批次状态与操作控制](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/012_不停机数据迁移_在线历史迁移_批次状态控制.md>) 统一控制。
2. 按每段 100 万 ID 跨度划分闭区间，末段截止到最大 ID；约 3 亿条是数据规模背景，只有 ID 总跨度约 3 亿时才约 300 个任务。边界及任务字段见 [任务范围划分](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/019_不停机数据迁移_在线历史迁移_任务范围划分.md>)。
3. 任务提交给固定 N 个线程的专用线程池，N 由数据库预算与压测确定；任务对象只存范围等信息，实际数据执行时分页读取。任务提交见 [线程池调度](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/020_不停机数据迁移_在线历史迁移_线程池调度.md>)，线程数选择见 [线程数选择](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/021_不停机数据迁移_在线历史迁移_线程池调度_线程数选择.md>)。
4. 每页成功并保存进度后，等待配置的时间再读下一页，以降低持续请求频率；等待时长和并发调整见 [限流](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/022_不停机数据迁移_在线历史迁移_限流.md>)。每页 500—1000 条是参考调参目标，不是生产参数；性能取舍见 [批次性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/025_不停机数据迁移_在线历史迁移_批次性能调优.md>)。
5. 每个任务保存自己的确认进度；失败或结果未知不推进，人工恢复后可能重做未确认页。首次包含范围起点，续跑从确认 ID 之后查询，见 [断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/023_不停机数据迁移_在线历史迁移_断点续跑.md>)。

本方案只允许一个迁移实例；固定线程数限制实例内并发，不能替代批次启动互斥或故障恢复检查。

### 4.3 写入结果与切换条件

迁移读取旧表当前数据及对应 version，不重新执行业务、不生成新版本。先按 merchantNo 路由，再按 serialNo 查询目标；缺失执行 INSERT，已有记录在 SQL 中用来源版本条件 UPDATE。唯一键冲突、同版本字段差异和 UPDATE 影响 0 行都需核实，具体规则见 [重试幂等](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/024_不停机数据迁移_在线历史迁移_重试幂等.md>)。

例如迁移读到 version=2，但双写已将新表更新到 version=3，迁移不能再覆盖为 2；这只证明旧写应被拒绝，不代表整体数据已一致。迁移期间的物理删除与迟到 INSERT 防护仍待确认，不能将已有记录的版本比较推广为完整删除保护。

完整任务清单全部成功才表示本批次执行完成。随后以旧表为依据进行新旧数据一致性校验，修复缺失、多余及字段差异，并重新核对结果。连续多轮完整校验无差异、双写正常、补偿无积压后，才具备灰度切读条件；具体轮数与验收指标仍待确认。任务完成判定见 [完成结果判定](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/018_不停机数据迁移_在线历史迁移_批次状态控制_完成结果判定.md>)。

查询灰度期间继续以旧表主写并保持双写。最终切写另外执行已确认的短暂停写交接：暂停旧写、核实在途事务，处理完同步消息和迁移修复任务，最终核对并隔离旧方向后，再开放新表业务写入。交接细节沿用 006，不在历史迁移总览重复展开。

## 5 已确认规则

- 先完成旧表版本与业务写入口改造并开启双写，再迁移历史数据；双写负责在线变化。
- 旧表保留最近 5 年、约 3 亿条数据；按每段 100 万 ID 跨度划分任务，任务数由跨度决定。
- 首次保存扫描边界，恢复复用原任务和各自确认进度；同一时刻只允许一个迁移实例。
- 每页 500—1000 条只是参考调参目标，实际并发、页大小和等待时长需压测。
- merchantNo 用于路由，serialNo 全局唯一且不复用；插入防重复，更新只接受更大的来源版本。
- 历史任务任意失败立即停止新处理并告警，人工核实修复后再启动，不自动重试。
- 任务完成后仍需校验修复再灰度切读；最终切写采用短暂停写交接。
