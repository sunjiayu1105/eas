## 1 面试口述精炼版本

口述内容字符数：355

**分批限流，控制迁移压力**

按旧表主键范围分批，参考每批 500—1000 条作为调参起点，实际条数受主键空洞影响。通过批次大小、并发度和批次间等待控制速度，观察数据库负载与业务延迟，必要时降速或暂停。具体参数待压测。详见[批次限流](#21-批次范围与限流)。

**成功后存进度，中断后续跑**

一批全部处理成功后才保存进度，失败或结果未知时不推进。恢复从已保存位置继续；数据已写入但进度未保存时会重做。并行任务不能让后完成的较大主键位置跳过前面的失败批次。详见[断点续跑](#22-断点续跑)。

**允许重试，但不能重复建记录或覆盖新状态**

用同一业务身份的唯一约束防止重复插入，UPDATE 在 SQL 内比较版本，只接受更大的来源版本。同版本字段不同要记录异常，不能当成功。幂等写入负责安全重做，持久化进度负责恢复位置，两者都需要。以上是设计要求，保存协议与并发恢复效果尚未验证。详见[重试幂等](#23-失败重试与幂等)。

## 2 详细方案

### 2.1 批次范围与限流

迁移按旧表主键范围拆分批次。参考文章_04 第 3 节建议从 500—1000 的批次参数开始测试；本文沿用每批 500—1000 条的参考目标，只能作为调参起点，不能直接视为项目固定配置。项目需要结合数据库负载、在线请求延迟和迁移吞吐，通过压测与演练确定批次范围、并发度、限流阈值和事务边界。

文章示例按起止主键划定区间，而不是按实际返回条数分页；主键有空洞或记录已删除时，区间内记录会少于预期。例如区间 [1001, 1500] 的宽度是 500，但只剩 420 条记录时，本批实际读取 420 条。边界不得漏掉主键；项目采用何种区间生成和分页方式仍待确认。来源：[参考文章_04：区间计算与读取（第 273 行）](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/999_不停机数据迁移_参考文章_04.md:273>)。

批次过小会增加网络往返，批次过大则会增加内存占用和单次失败的影响范围；并发过高会增加数据库 I/O 和 CPU 压力。批次间等待可降低连续执行速度；文章第 301—303 行仅给出限流注释，没有实际等待代码，不能视为已实现限流。运行期间应观察吞吐、延迟、错误数和数据库负载，必要时降低速度或暂停任务。暂停由调度器或控制台的暂停机制负责，不是进度保存自动产生的结果。

来源：[参考文章_04 第 3 节：批次处理与性能调优](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/999_不停机数据迁移_参考文章_04.md:319>)。具体参数尚未完成生产验证。

### 2.2 断点续跑

每批数据处理完成并确认成功后，才保存该批次的完成位置。任务恢复时，从最近一次成功保存的位置之后继续；未成功保存本批完成位置时，允许重做本批，不能跳过。全部处理成功包括确认写入成功或按版本规则安全跳过，不能只看批量调用正常返回；分片部分成功、结果未知和未处理差异都需要逐项核实。

如果数据已经写入新表，但进度保存失败，恢复任务可能再次读取同一批。这里分析的是数据写入成功、进度尚未保存成功的失败窗口；实际事务边界和保存协议待验证，不能仅凭进度记录认定不会重复处理。

**并行任务要保留失败缺口**

例如批次 A 处理 1—500 失败，批次 B 处理 501—1000 成功；若直接保存全局进度 1000，重启就会漏掉 A。由“不能跳过失败批次”的已确认规则可知，恢复记录必须能够识别未完成区间；可以按独立任务保存进度，或维护批次状态并只推进连续完成位置，具体方案待确认，本文不选定实现。

空区间只有查询成功且确认该范围无记录时才能视为扫描完成；查询异常不能当作空结果。任务扫描完成也不能代替后续一致性校验。

文章仅展示写入后调用进度记录器，并未给出进度表、持久化协议或并行恢复算法。来源：[参考文章_04：写入与记录进度（第 285 行）](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/999_不停机数据迁移_参考文章_04.md:285>)。

### 2.3 失败重试与幂等

数据库错误、锁等待超时或死锁等异常发生时，保留失败状态和恢复位置，再按错误原因与重试策略处理；超过重试阈值要告警，不能把失败批次当成已完成。持续的字段错误或约束错误不能靠无限重试解决；重试次数、退避间隔及人工介入方式仍待确认。

重试可能再次执行 INSERT 或版本条件 UPDATE：

- 新表没有记录时，按 merchantNo 路由、serialNo 关联同一业务记录，INSERT 必须受相应业务唯一约束保护；遇到重复记录时重新读取并判断，不能生成重复交易。
- 新表已有记录时，在同一条 UPDATE 中执行目标 version 小于来源 version 的条件判断，并一起写入业务字段和来源版本，不自行递增；不能先查询版本再无条件更新。只接受更大的业务版本；来源版本较旧或相等时不直接覆盖；相等版本仍存在字段差异时应排查，不能直接算修复成功。

上述版本规则依据 [005 的迁移与同步版本方案](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/005_不停机数据迁移_如何防止旧版本数据覆盖新版数据.md>)，不是参考文章已提供的完整实现。UPDATE 影响 0 行可能是记录缺失或版本条件未命中，不能直接判成功；应核实当前记录状态后，区分补建、安全跳过与同版本字段异常。

因此，幂等性、版本条件和进度保存要配合使用：幂等性解决重复执行，版本条件防止旧数据覆盖新数据，进度保存提供恢复位置。

### 2.4 示例：写入成功，但进度保存失败

以下为故障恢复示例，不代表生产中已发生；假设当前批次内的记录已经写入新表，但任务尚未成功保存本批进度。

1. 任务中断后，从上一次成功保存的进度恢复，再次读取本批旧表当前数据。

2. 对已写成功的记录，唯一键阻止重复插入；发生冲突后，重新读取新表并按版本判断。

3. 例如新表已有版本 3，本次读到的迁移数据是版本 2，则拒绝覆盖；相同版本且内容相同则无需重复修改。

4. 本批全部处理成功后保存进度，再继续下一批。若再次失败，保留恢复位置，不能跳过未完成批次。

恢复重读时使用此次读取到的业务数据及其对应版本，不默认沿用上次失败时的旧快照。本批若只有部分目标分片写入成功，也不能推进整批完成位置；已成功部分可能随批次重做，仍须经过唯一约束和版本判断。

## 3 已确认规则

- 批次限流、断点续跑和重试幂等是面试考察重点，口述时必须分别说明控制迁移压力、恢复进度和安全重复执行的机制。
- 批次数据量使用范围表达；参考文章的 500—1000 条只是调参起点，不是项目固定配置。
- 每批成功后保存进度；进度保存失败时允许重做，不能跳过批次。
- 迁移写入必须幂等，重复 INSERT 不能产生重复记录，旧版本 UPDATE 不能覆盖新版本。

## 4 待确认或待验证事项

- 项目最终批次范围及主键区间生成方式。
- 迁移并发度、限流阈值和暂停恢复机制。
- 各目标分片写入的事务边界。
- 进度记录的实际存储与可靠保存协议。
- 并行任务如何记录失败缺口及恢复位置。
- INSERT 的业务唯一约束是否在实际分片中生效。
- UPDATE 影响 0 行的状态核实和处理方式。
- 同版本字段差异的排查、修复及批次状态处理。
- 重试次数、退避间隔和超限人工介入条件。
- 部分写入成功、提交结果未知和进度保存失败的故障演练。
- 监控指标与告警阈值。

## 5 异议与分析

**批次大小不能直接等同于实际记录数**

参考文章按主键数值计算区间，不能据参数为 500 就认定一定读到 500 条数据；主键空洞反例见 2.1。本文保留 500—1000 条的参考目标，实际读取量和资源消耗仍须测量。

**进度与版本条件各有边界**

保存最大已完成主键不能证明之前所有范围都已成功，并行失败反例见 2.2。版本条件只保护已有记录：物理删除后目标不存在，迟到 INSERT 仍可能重新创建记录，唯一约束不能阻止已释放身份的再次插入。该问题由总体迁移及一致性校验方案处理，不能将本篇重试幂等表述为全部删除场景安全或最终一致已验证。
