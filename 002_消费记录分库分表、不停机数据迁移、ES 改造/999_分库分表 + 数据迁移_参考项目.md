**1. FlockDB + Gizzard：最值得参考整体机制**

它的流程接近你的需求：旧分片继续提供查询，新分片先接收写入，后台复制历史数据，并比较、修复分片间的差异。

已核实的代码：

- **分片路由**：[ForwardingManager.scala，第 24～33 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/ForwardingManager.scala#L24-L33)，根据记录标识和图标识寻找目标分片。
- **多副本写入**：[ReadWriteShardAdapter.scala，第 38～52 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/shards/ReadWriteShardAdapter.scala#L38-L52)，将写操作发送到路由树中的写入节点。
- **历史迁移与差异比较**：[Copy.scala，第 64～122 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/jobs/Copy.scala#L64-L122)，分批读取各分片，比较同一条记录的 `updatedAt`，把较新的记录补到缺失或落后的分片。
- **实际落库修复**：[SqlShard.scala，第 557～595 行](https://github.com/twitter-archive/flockdb/blob/master/src/main/scala/com/twitter/flockdb/shards/SqlShard.scala#L557-L595)，将复制任务收集的差异写入数据库。

例如，旧分片记录的更新时间是 100，新分片是 90，复制任务会选择时间 100 的记录修复新分片。

**区别**：它不是“始终以旧表为准”，也不是独立任务逐字段核对所有差异；相同时间戳但字段不同，不能凭这段比较逻辑保证发现。项目已归档，适合研究机制，不建议直接照搬部署。

**2. mall-sale：Java 实现最贴近，但有明确缺口**

这次核实到了实际代码，补充了此前只看到 README 的证据：

- **分表配置**：[user_config.yml，第 47～54 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/user/src/main/nacos/user_config.yml#L47-L54)，按 `mobile % 8` 路由到八张用户表。这里是分表，未据此确认多库分片。
- **应用双写**：[CouponTemplateDoubleWriteServiceImpl.java，第 35～46 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/coupon/src/main/java/com/eugene/service/impl/CouponTemplateDoubleWriteServiceImpl.java#L35-L46)，根据开关执行旧服务单写、新旧双写或新服务单写。
- **历史迁移**：[AdminServiceImpl.java，第 118～135 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/user/src/main/java/com/eugene/service/impl/AdminServiceImpl.java#L118-L135)，分批读旧表，按分片键分组，由线程池写入新表。
- **一致性比较**：[CheckUserDataHandle.java，第 31～49 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/user/src/main/java/com/eugene/threads/CheckUserDataHandle.java#L31-L49)，查询新表对应记录，收集缺失或内容不同的 ID。
- **修复差异**：[AdminServiceImpl.java，第 174～188 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/user/src/main/java/com/eugene/service/impl/AdminServiceImpl.java#L174-L188)，重新读取旧表，新表缺失就插入，存在就更新。

**不能忽略的缺口**：用户模块实现了校验，但双写示例在优惠券模块；优惠券的 [CheckCouponTemplateDataHandle.java，第 25～28 行](https://github.com/zhoujinyou0616/mall-sale/blob/master/couponNew/src/main/java/com/eugene/threads/CheckCouponTemplateDataHandle.java#L25-L28) 仍是 `TODO`，直接返回 `null`。用户校验也只从旧表扫描，无法靠这一流程发现新表多余记录。

**3. webook：适合参考你正在讨论的“主写切换后怎么修复”**

它有明确的源码处理方向：

- [双写连接池，第 104～131 行](https://github.com/DDLGitGzzhM/webook/blob/main/webook/pkg/gormx/connpool/double_write_pool.go#L104-L131)：支持旧库优先、新库优先及单写模式。
- [校验方向选择，第 194～202 行](https://github.com/DDLGitGzzhM/webook/blob/main/webook/pkg/migrator/scheduler/scheduler.go#L194-L202)：旧库优先时以旧库为依据；新库优先时交换两边角色，以新库为依据。
- [修复消费者，第 67～76 行](https://github.com/DDLGitGzzhM/webook/blob/main/webook/pkg/migrator/events/fixer/consumer.go#L67-L76)：按差异事件携带的方向选择修复器。
- [修复实现，第 39～55 行](https://github.com/DDLGitGzzhM/webook/blob/main/webook/pkg/migrator/fixer/fix.go#L39-L55)：重新读取依据库，存在则插入或更新目标，不存在则删除目标。

**但它不是完整答案**：分片连接池 `sharding.go` 只有空结构；修复 SQL 没有版本条件，迟到事件仍携带旧方向，也不能据此证明主写交接的并发问题已经解决。
