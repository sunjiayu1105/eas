# 015_不停机数据迁移_在线历史迁移_线程池_线程池类型选择

问题：历史迁移为什么选择 ThreadPoolExecutor，而不是直接使用 Executors 的默认线程池？

以下内容按照当前项目 AGENTS.md 项目级规则为准，使用 Java 8。本文为设计分析，示例未运行验证。

## 1 面试口述精炼版本

口述内容字符数：245

**显式控制资源**

迁移需要同时限制工作线程数、排队任务数和拒绝行为，因此建议直接构造 ThreadPoolExecutor，显式设置线程数、有界队列和拒绝策略。

**常见线程池的边界**

固定线程池默认使用无界队列，可能持续积压；缓存线程池可能创建过多线程；单线程执行器吞吐有限；定时线程池适合触发，不负责执行长任务。实际参数需压测。

## 2 详细方案

### 2.1 选择 ThreadPoolExecutor

它能显式配置 corePoolSize、maximumPoolSize、队列、线程工厂和拒绝策略，适合把数据库访问并发作为明确资源上限。线程池只负责执行，不负责进度持久化和幂等。

### 2.2 常见实现取舍

- newFixedThreadPool：线程数固定，但默认无界队列，不适合直接作为迁移限流器。
- newSingleThreadExecutor：串行执行，适合必须单线程的场景，吞吐较低。
- newCachedThreadPool：可能快速扩展线程，数据库变慢时风险高。
- newScheduledThreadPool：适合周期触发，耗时迁移仍应交给工作线程池。
- ForkJoinPool：适合可拆分计算，阻塞 JDBC 场景不能直接当数据库并发上限。

## 3 已确认规则

- 线程池类型选择独立成篇。
- 采用显式配置的 ThreadPoolExecutor 作为设计建议；未确认已实现。
- 线程池参数必须结合数据库容量和在线负载压测。
