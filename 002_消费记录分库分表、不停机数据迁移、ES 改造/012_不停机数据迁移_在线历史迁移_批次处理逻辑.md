# 012_不停机数据迁移_在线历史迁移_批次处理逻辑

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。本文是批次控制设计，具体实现和运行效果尚未验证。

## 1 问题

不停机历史迁移中，批次如何启动、暂停、收尾和恢复，并判断迁移是否真正成功？

## 3 详细方案

### 3.1 批次控制状态

批次控制状态用于控制启动和暂停，直接展示在批次列表中；不新增任务表批次 ID。建议状态如下：

| 状态 | 含义 |
| --- | --- |
| 未启动 | 尚未完成初始化；首次启动需在事务中保存完整清单 |
| 运行中 | 初始化已提交，正在准备提交或执行任务，允许暂停 |
| 暂停中 | 已收到暂停或失败信号，正在等待任务和数据库操作收尾 |
| 已暂停 | 本次已安全收尾，可以再次启动 |
| 已完成 | 完整任务清单全部成功 |
| 异常待处理 | 存在失败、未知结果或无法确认的残留执行，需运维处理 |

批次列表直接显示当前状态，不设置单独的“查询状态”操作。未启动、已暂停时仅启动可用；运行中时仅暂停可用；暂停中、已完成和异常待处理时两个按钮都禁用。后端仍须校验状态并防止重复启动，不能只依赖前端置灰。服务器重启后不得直接把运行状态重置为未启动，应核实旧执行和残留任务后再允许启动。

### 3.2 任务表与初始状态

首次启动时查询旧消费记录表当前的最大 ID，将其作为扫描上界，与完整任务清单一起保存；后续恢复沿用原上界，不重新查询或扩大范围。旧表约 3 亿条数据，按每个任务平均约 100 万条规划约 300 个任务，再结合主键分布划分互不重叠的范围。100 万条是平均记录数，不能直接作为主键跨度；约 300 是规划估算，不是线程数或固定成功门槛。固定最大 ID 仅限定扫描范围，不形成数据库快照，期间的数据变化仍由双写和一致性校验处理。实际数据量和各范围分布尚未查询核验。

任务表至少维护以下字段：

| 字段 | 含义 |
| --- | --- |
| task_id | 唯一标识范围任务 |
| start_id | 扫描起始 ID，不包含 |
| end_id | 扫描结束 ID，包含 |
| current_id | 最后确认处理成功并保存的位置 |
| status | 待处理、处理中、成功、失败、已暂停 |
| failure_reason | 失败阶段和原因 |

首次写入时，任务状态为待处理，`current_id` 初始化为范围下界。再次启动不重新生成任务，也不重置已经保存的进度。任务表不维护批次 ID、执行者标识和执行尝试编号。

**初始化与状态转换必须一起提交**

本文沿用批次初始状态“未启动”，任务初始状态称“待处理”，不混用两个层级。约 300 个任务只写范围等信息，可以考虑在一个短事务内完成以下操作；事务容量、锁等待和实际耗时仍需验证。

1. 锁定唯一的迁移控制记录并检查状态，重复启动请求必须重新检查锁后的状态。
2. 状态为未启动时，保存固定扫描上界与完整范围清单，新任务状态为待处理、确认进度为范围下界，并核对范围和计划数量。
3. 在同一事务中将批次状态改为运行中，然后提交。
4. 确认提交成功后，才查询任务并向线程池提交。事务中不执行数据迁移，也不等待 Future。

控制记录、扫描边界和任务清单必须处在同一数据库事务边界内，使用支持事务的存储引擎。任务表需有唯一约束防止重复写入，任务 ID 或范围唯一键必须稳定，不能每次生成新 ID 就认为能够防重。范围计算如需昂贵扫描，应在事务外规划，并在事务中核对并保存同一份边界，避免长期占用控制记录锁。

由此保证：批次正常离开未启动状态时，完整任务清单已可靠保存。初始化明确回滚时，状态仍为未启动，下次可重新初始化；事务已提交但进程在提交线程池前宕机时，清单完整、状态为运行中，须核实旧执行后恢复，不能再次初始化。提交响应丢失时先查询核实事务结果，不直接重试初始化，也不贸然启动线程池。

例如计划 300 个任务，插入第 100 个时失败：事务回滚，不能留下部分清单却显示运行中。如果约束被人工修数或旧实现破坏，应停止启动并核对清单，不能仅凭状态跳过检查。首次初始化失败且已确认回滚时，不应将批次永久改成代表初始化完成的状态；告警通过日志报告。

### 3.3 启动流程

启动接口只允许在批次状态为未启动或已暂停时执行，并且同一时间只能有一个迁移实例。启动时按顺序处理：

1. 检查是否已经存在其他迁移实例；无法确认旧实例停止时，进入异常待处理，不启动新实例。
2. 检查失败任务、结果未知和任务表中的处理中任务。发现未修复失败或未核实结果时进入异常待处理，阻止启动。服务器宕机可能留下处理中状态，不能直接把它当作可执行任务；先由运维确认旧线程、进程、事务和数据库操作已经停止，并核实未知写入。
3. 首次启动按 3.2 的事务初始化完整清单；后续启动不生成新范围、不重置进度。已暂停可在核实后继续，运行中和暂停中禁止重复启动，异常待处理先修复，已完成不再次启动。残留处理中任务经运维核实后改为已暂停，失败任务修复后改为待处理。
4. 首次启动的运行中状态随初始化事务提交；后续从已暂停恢复时，仅原子改为运行中并复用原清单。互斥覆盖检查和启动，未确认状态转换成功不得提交任务。初始化提交后的启动失败进入异常待处理，等待已接收任务收尾，不能回退到未启动。启动和暂停存在竞争时，提交前检查最新控制状态，不得覆盖暂停请求。
5. 受限查询状态为待处理或已暂停的任务，校验任务总数上限和内存预算，超过上限拒绝启动；已暂停任务可以直接提交，不必先改为待处理。
6. 创建固定 N 个线程的专用线程池，一次提交本次查询到的任务描述，保存每个 Future。

### 3.4 任务执行与状态转换

任务进入线程池后，在真正读取数据前检查共享停止信号，并通过任务 ID 和原状态条件将状态更新为处理中。只有以任务 ID 和待处理或已暂停原状态为条件的更新影响行数为 1，且提交结果确认成功，线程才开始处理；更新失败或结果未知时不扫描，交给异常处理。

任务从 `current_id` 之后分页读取，按 `id > current_id AND id <= end_id` 处理。每页全部写入结果确认且进度保存成功后，才读取下一页；失败、部分成功或结果未知都不推进 `current_id`。查询成功且范围内没有剩余数据后，保存成功状态。

分页数据不应长期保存在任务对象或 Future 中。任务只携带范围和状态所需信息，实际数据按页读取；页面处理完成并保存进度后释放引用。约 300 个任务描述、包装对象和 Future 仍可能在等待期间占用内存，需通过 `MAX_TASKS` 和压测控制。

### 3.5 暂停流程

用户点击暂停时，后端先将批次状态从运行中原子改为暂停中，再设置共享停止信号。暂停中状态下，启动和暂停按钮都禁用。

- 尚未提交的任务不再提交，继续保持待处理或已暂停。
- 已提交但尚未开始的任务，在线程入口检查停止信号后退出，保留原状态。
- 已开始处理的任务在分页边界检查停止信号，核实当前页结果并保存确认进度后退出；未完成任务改为已暂停。
- 已成功任务保持成功，失败任务保持失败。

`shutdown()` 只禁止后续提交，仍会执行队列中的任务，所以任务入口和分页边界必须检查停止信号。`shutdownNow()`、`cancel(true)` 或线程中断都不能单独证明 JDBC 请求和数据库事务已经结束。

只有所有已提交任务的线程、数据库操作和任务状态保存都已收尾，且没有失败或未知结果，批次状态才能从暂停中改为已暂停。若收尾时完整清单已经全部成功，可显示已完成；失败收尾仍进入异常待处理。无法确认结果或保存状态失败时，改为异常待处理，不允许直接重新启动。

### 3.6 失败处理与运维恢复

任意任务失败都立即设置停止信号、记录失败原因并告警，不自动重试。其他已运行任务按暂停流程安全收尾；排队任务在入口检查信号后退出。失败发生时就告警，不等待所有 Future 结束。

运维负责排查代码、配置、数据、数据库和网络问题。修复后按以下顺序恢复：

1. 确认旧线程、进程、事务和数据库操作已经停止，核实未知写入结果。
2. 失败任务由运维改为待处理；服务器宕机残留且已核实安全的处理中任务改为已暂停。保留原范围、`current_id` 和失败日志。
3. 运维在核实全部旧操作已收尾且不存在未处理异常后，将运行状态恢复为已暂停，再点击启动；启动时查询待处理和已暂停任务，重新创建线程池和 Future。
4. 从原确认进度继续，允许重做未确认页；幂等和版本规则必须防止重复写入产生业务影响或旧数据覆盖新数据。

不支持仅凭处理中状态持续时间、心跳过期或 Redis 锁过期自动接管。没有执行者标识和执行尝试编号时，恢复前必须人工确认旧执行已经停止。

### 3.7 正常收尾与完成判定

提交任务结束后关闭线程池提交入口，等待全部已提交 Future 收尾，再核对完整任务表。Future 全部结束只表示本次提交结束，不代表迁移成功。

- 任意任务失败：批次状态为异常待处理。
- 无失败且安全暂停收尾后仍有待处理或已暂停任务：显示已暂停。
- 正常执行期间尚有运行任务：维持运行中。线程退出后仍残留处理中、存在未知结果或无法确认数据库操作收尾：显示异常待处理，不能当作已暂停。
- 完整任务清单中的所有任务都可靠保存成功状态：批次状态为已完成，随后进行一致性校验。

正常情况下，任务全部成功后自动结束；不需要手动点击停止。暂停或失败导致的收尾不代表迁移成功。

### 3.8 线程池边界与待落地配置

采用专用 ThreadPoolExecutor，核心数和最大数均为 N，使用有界 ArrayBlockingQueue 与 AbortPolicy。本次提交任务数为 M 时，可采用容量 M 的队列；M 必须先受 MAX_TASKS 限制，M=0 时不创建零容量队列，直接检查完整任务表。N 可从 2、4、8 等测试点压测，这些只是候选值，不是生产配置。

调度方保存成功提交的 Future；提交被拒或中断时停止后续提交，未提交任务保留原状态，已接收任务仍须收尾。范围任务内部立即设置停止信号并告警，不能依赖调度线程按顺序 get 才触发停止。已暂停任务和待处理任务在执行前均通过原状态条件更新为处理中；排队时不提前标为处理中。

运行状态须可靠保存，重启后结合旧进程和数据库操作核实，不能简单重置为未启动。初始化在首次启动内部完成，不增加页面操作按钮。上述线程池配置和状态控制是设计建议，尚未运行验证。

## 4 已确认规则

- 页面只显示批次当前状态，提供启动和暂停操作，不单独提供查询状态操作。
- 同一时间只允许一个迁移实例运行。
- 首次启动初始化完整任务清单；扫描边界、任务清单与未启动到运行中的状态转换在同一事务内保存，提交确认后才运行线程池；后续复用任务和进度。
- 新任务初始状态为待处理；已暂停任务启动时可以直接提交，不必先改为待处理。
- 任意任务失败都停止新处理、记录原因并告警，不自动重试。
- 暂停中时按钮置灰；安全收尾且没有失败或未知结果后才改为已暂停，全部成功则已完成。
- 异常任务由运维处理，恢复前确认旧执行和未知写入结果。
- 完整任务全部成功才判迁移完成，随后进行一致性校验。

## 5 待确认或待验证事项

- 批次控制记录、扫描边界和任务清单的同库事务、稳定唯一约束、初始化回滚与提交响应丢失验证。
- 单实例防重及跨进程、跨机器启动互斥。
- `MAX_TASKS`、线程数 N、队列容量和任务描述的内存峰值。
- 启动、暂停、失败告警、Future 等待和数据库操作收尾的故障演练。
- 运维修改任务状态的权限、审计和并发保护。
- 未知提交结果、服务器宕机及恢复后重复写入的验证。
