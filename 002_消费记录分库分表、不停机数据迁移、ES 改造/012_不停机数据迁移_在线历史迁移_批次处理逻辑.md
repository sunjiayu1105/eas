# 012_不停机数据迁移_在线历史迁移_批次处理逻辑

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。本文是批次控制设计，具体实现和运行效果尚未验证。

## 1 问题

不停机历史迁移中，批次如何启动、暂停、收尾和恢复，并判断迁移是否真正成功？

## 3 详细方案

### 3.1 启动检查

启动接口只允许批次状态为未启动或已暂停时执行，同一时间只允许一个迁移实例运行。先检查批次状态与旧执行，再进入初始化或恢复流程。

1. 检查是否已经存在其他迁移实例；无法确认旧实例停止时，进入异常待处理，不启动新实例。
2. 检查失败任务、结果未知和任务表中的处理中任务。发现未修复失败或未核实结果时进入异常待处理，阻止启动。服务器宕机可能留下处理中状态，不能直接把它当作可执行任务；先由运维确认旧线程、进程、事务和数据库操作已经停止，并核实未知写入。

批次信息表保存批次状态和整个批次的扫描上下界，任务表保存各任务的扫描范围、状态和处理进度。批次状态用于控制启动和暂停，直接展示在批次列表中；不新增任务表批次 ID。建议状态如下：

| 状态 | 含义 |
| --- | --- |
| 未启动 | 尚未完成初始化；首次启动需在事务中保存完整清单 |
| 运行中 | 初始化已提交，正在准备提交或执行任务，允许暂停 |
| 暂停中 | 已收到暂停或失败信号，正在等待任务和数据库操作收尾 |
| 已暂停 | 本次已安全收尾，可以再次启动 |
| 已完成 | 完整任务清单全部成功 |
| 异常待处理 | 存在失败、未知结果或无法确认的残留执行，需运维处理 |

批次列表直接显示当前状态，不设置单独的“查询状态”操作。未启动、已暂停时仅启动可用；运行中时仅暂停可用；暂停中、已完成和异常待处理时两个按钮都禁用。后端仍须校验状态并防止重复启动，不能只依赖前端置灰。服务器重启后不得直接把运行状态重置为未启动，应核实旧执行和残留任务后再允许启动。

### 3.2 首次初始化或恢复

首次启动批次时，通过同一次查询取得旧消费记录表的 MIN(id) 和 MAX(id)，作为 minId、maxId 保存在批次信息表中，分别表示整个批次的扫描下界和上界。再次启动同一批次时沿用这两个边界，不重新查询或扩大范围。每段固定覆盖 1,000,000 个 ID 值，不保证包含 100 万条记录。闭区间划分如下：

- 第一段：[minId, min(minId + 999999, maxId)]。
- 第二段：[minId + 1000000, min(minId + 1999999, maxId)]，仅当起点不超过 maxId 时生成。
- 后续按同样跨度推进，最后一段结束于 maxId，相邻范围连续且不重叠。

非空表的任务数为 floor((maxId - minId) / 1000000) + 1，等价于向上取整((maxId - minId + 1) / 1000000)。例如 minId=10、maxId=2000010，生成 [10,1000009]、[1000010,2000009]、[2000010,2000010] 三个任务；数字仅演示边界。

约 3 亿条是记录量背景；只有 ID 总跨度约为 3 亿时，任务数量才约为 300。固定跨度可能产生空范围或不同耗时的任务。生成前校验任务总数上限，算术使用可容纳主键范围的类型并防止溢出，不直接以 long 做可能溢出的加减。空表的 MIN/MAX 返回 NULL，须走明确的零任务流程，不能套用公式或生成虚假范围；零任务最终状态待确认。

固定上下界不形成数据库快照，期间的数据变化仍由双写和一致性校验处理。实际数据量、ID 分布和类型尚未查询核验。

任务表至少维护以下字段：

| 字段 | 含义 |
| --- | --- |
| task_id | 唯一标识范围任务 |
| start_id | 扫描起始 ID，包含 |
| end_id | 扫描结束 ID，包含 |
| current_id | 最后确认处理成功并保存的位置；初始为 NULL，表示尚无确认页 |
| status | 待处理、处理中、成功、失败、已暂停 |
| failure_reason | 失败阶段和原因 |

首次写入时，任务状态为待处理，`current_id` 初始化为 NULL。再次启动同一批次时不重新生成任务；需要继续执行的任务沿用任务表中各自的扫描范围和 current_id，不重置已经保存的进度。任务表不维护批次 ID、执行者标识和执行尝试编号。

**初始化与状态转换必须一起提交**

本文沿用批次初始状态“未启动”，任务初始状态称“待处理”，不混用两个层级。任务数量由 ID 跨度计算，清单只写范围等信息，可以考虑在一个短事务内完成以下操作；事务容量、锁等待和实际耗时仍需验证。

1. 锁定批次信息表中唯一的批次记录并检查批次状态，重复启动请求必须重新检查锁后的状态。
2. 批次状态为未启动时，将整个批次的扫描上下界写入批次信息表，将完整任务清单写入任务表。各任务保存自己的扫描范围，状态为待处理、确认进度为 NULL，并核对范围和计划数量。
3. 在同一事务中将批次信息表中的批次状态改为运行中，然后提交。
4. 确认提交成功后，才查询任务并向线程池提交。事务中不执行数据迁移，也不等待 Future。

批次信息表中的状态、扫描上下界与任务表中的完整任务清单必须在同一数据库事务中保存，使用支持事务的存储引擎。任务表需有唯一约束防止重复写入，任务 ID 或范围唯一键必须稳定，不能每次生成新 ID 就认为能够防重。范围计算如需昂贵扫描，应在事务外规划，并在事务中核对并保存同一份边界，避免长期占用控制记录锁。

由此保证：批次正常离开未启动状态时，完整任务清单已可靠保存。初始化明确回滚时，状态仍为未启动，下次可重新初始化；事务已提交但进程在提交线程池前宕机时，清单完整、状态为运行中，须核实旧执行后恢复，不能再次初始化。提交响应丢失时先查询核实事务结果，不直接重试初始化，也不贸然启动线程池。

例如计划 300 个任务（教学示例），插入第 100 个时失败：事务回滚，不能留下部分清单却显示运行中。如果约束被人工修数或旧实现破坏，应停止启动并核对清单，不能仅凭状态跳过检查。首次初始化失败且已确认回滚时，不应将批次永久改成代表初始化完成的状态；告警通过日志报告。

再次启动已暂停的批次时，在同一启动互斥保护下，仅将批次状态原子改为运行中，复用原任务清单和各任务进度。检查与状态转换不能被其他启动请求穿插；未确认状态转换成功，不得提交任务。

### 3.3 提交并执行任务

确认初始化或恢复事务提交成功后，再查询和提交任务。提交前检查最新批次状态，不得覆盖暂停请求。初始化提交后的启动失败进入异常待处理，等待已接收任务收尾，不能回退到未启动。

1. 受限查询状态为待处理或已暂停的任务，校验任务总数上限和内存预算，超过上限拒绝启动；已暂停任务可以直接提交，不必先改为待处理。
2. 创建固定 N 个线程的专用线程池，一次提交本次查询到的任务描述，保存每个 Future。

**线程池配置与提交异常**

采用专用 ThreadPoolExecutor，核心数和最大数均为 N，使用有界 ArrayBlockingQueue 与 AbortPolicy。本次提交任务数为 M 时，可采用容量 M 的队列；M 必须先受 MAX_TASKS 限制，M=0 时不创建零容量队列，直接检查完整任务表。N 可从 2、4、8 等测试点压测，这些只是候选值，不是生产配置。

调度方保存成功提交的 Future；提交被拒或中断时停止后续提交，未提交任务保留原状态，已接收任务仍须收尾。范围任务内部立即设置停止信号并告警，不能依赖调度线程按顺序 get 才触发停止。已暂停任务和待处理任务在执行前均通过原状态条件更新为处理中；排队时不提前标为处理中。

运行状态须可靠保存，重启后结合旧进程和数据库操作核实，不能简单重置为未启动。初始化在首次启动内部完成，不增加页面操作按钮。上述线程池配置和状态控制是设计建议，尚未运行验证。

**任务开始处理与分页进度**

任务进入线程池后，在真正读取数据前检查共享停止信号，并通过任务 ID 和原状态条件将状态更新为处理中。只有以任务 ID 和待处理或已暂停原状态为条件的更新影响行数为 1，且提交结果确认成功，线程才开始处理；更新失败或结果未知时不扫描，交给异常处理。

任务范围为 [start_id,end_id]。current_id 为 NULL 时，首批查询使用 id >= start_id AND id <= end_id；已有确认进度时，使用 id > current_id AND id <= end_id。两种查询均按 id 升序并限制页大小，500 条仅为教学示例。不能将初始进度设为 start_id 后直接使用大于条件，否则会漏掉范围起点。每页全部写入结果确认且进度保存成功后，才读取下一页；失败、部分成功或结果未知都不推进 `current_id`。查询成功且范围内没有剩余数据后，保存成功状态。全空范围可保持 current_id 为 NULL，不能要求进度等于 end_id 才算成功。失败在首批确认前发生时仍保留 NULL，恢复必须再次使用包含 start_id 的首批查询。

分页数据不应长期保存在任务对象或 Future 中。任务只携带范围和状态所需信息，实际数据按页读取；页面处理完成并保存进度后释放引用。本次全部任务描述、包装对象和 Future 仍可能在等待期间占用内存，需通过 `MAX_TASKS` 和压测控制。

### 3.4 暂停或失败处理

用户点击暂停时，后端先将批次状态从运行中原子改为暂停中，再设置共享停止信号。暂停中状态下，启动和暂停按钮都禁用。

- 尚未提交的任务不再提交，继续保持待处理或已暂停。
- 已提交但尚未开始的任务，在线程入口检查停止信号后退出，保留原状态。
- 已开始处理的任务在分页边界检查停止信号，核实当前页结果并保存确认进度后退出；未完成任务改为已暂停。
- 已成功任务保持成功，失败任务保持失败。

`shutdown()` 只禁止后续提交，仍会执行队列中的任务，所以任务入口和分页边界必须检查停止信号。`shutdownNow()`、`cancel(true)` 或线程中断都不能单独证明 JDBC 请求和数据库事务已经结束。

只有所有已提交任务的线程、数据库操作和任务状态保存都已收尾，且没有失败或未知结果，批次状态才能从暂停中改为已暂停。若收尾时完整清单已经全部成功，可显示已完成；失败收尾仍进入异常待处理。无法确认结果或保存状态失败时，改为异常待处理，不允许直接重新启动。

任意任务失败都立即设置停止信号、记录失败原因并告警，不自动重试。其他已运行任务按暂停流程安全收尾；排队任务在入口检查信号后退出。失败发生时就告警，不等待所有 Future 结束。

### 3.5 判断本次执行结果

提交任务结束后关闭线程池提交入口，等待全部已提交 Future 收尾，再核对完整任务表。Future 全部结束只表示本次提交结束，不代表迁移成功。

- 任意任务失败：批次状态为异常待处理。
- 无失败且安全暂停收尾后仍有待处理或已暂停任务：显示已暂停。
- 正常执行期间尚有运行任务：维持运行中。线程退出后仍残留处理中、存在未知结果或无法确认数据库操作收尾：显示异常待处理，不能当作已暂停。
- 完整任务清单中的所有任务都可靠保存成功状态：批次状态为已完成，随后进行一致性校验。

正常情况下，任务全部成功后自动结束；不需要手动点击停止。暂停或失败导致的收尾不代表迁移成功。

### 3.6 修复后再次启动

运维负责排查代码、配置、数据、数据库和网络问题。修复后按以下顺序恢复：

1. 确认旧线程、进程、事务和数据库操作已经停止，核实未知写入结果。
2. 失败任务由运维改为待处理；服务器宕机残留且已核实安全的处理中任务改为已暂停。保留原范围、`current_id` 和失败日志。
3. 运维在核实全部旧操作已收尾且不存在未处理异常后，将运行状态恢复为已暂停，再点击启动；启动时查询待处理和已暂停任务，重新创建线程池和 Future。
4. 需要继续执行的任务从任务表中各自保存的确认进度继续，允许重做未确认页；幂等和版本规则必须防止重复写入产生业务影响或旧数据覆盖新数据。

不支持仅凭处理中状态持续时间、心跳过期或 Redis 锁过期自动接管。没有执行者标识和执行尝试编号时，恢复前必须人工确认旧执行已经停止。

修复后再次启动，仍回到 3.1 进行启动检查，再按 3.2 复用原批次边界和任务进度；不跳过启动检查直接执行任务。

## 4 已确认规则

- 按启动检查、初始化或恢复、提交执行、暂停或失败、结果判定、修复重启的顺序阐述批次流程。
- 页面只显示批次当前状态，提供启动和暂停操作，不单独提供查询状态操作。
- 同一时间只允许一个迁移实例运行。
- 批次信息表保存整个批次的扫描上下界和批次状态；任务表保存各任务的扫描范围、状态和处理进度。
- 首次启动批次时，在同一事务中保存批次扫描上下界、完整任务清单和运行中状态，提交确认后才运行线程池；再次启动同一批次不重新生成任务，各任务沿用各自保存的范围和进度。
- 按最小 ID 到最大 ID，以每段 100 万的主键跨度划分闭区间；任务数取决于 ID 跨度，不等于记录数除以 100 万。
- current_id 初始为 NULL，首批包含 start_id，后续分页从最后确认 ID 之后读取。
- 新任务初始状态为待处理；已暂停任务启动时可以直接提交，不必先改为待处理。
- 任意任务失败都停止新处理、记录原因并告警，不自动重试。
- 暂停中时按钮置灰；安全收尾且没有失败或未知结果后才改为已暂停，全部成功则已完成。
- 异常任务由运维处理，恢复前确认旧执行和未知写入结果。
- 完整任务全部成功才判迁移完成，随后进行一致性校验。
