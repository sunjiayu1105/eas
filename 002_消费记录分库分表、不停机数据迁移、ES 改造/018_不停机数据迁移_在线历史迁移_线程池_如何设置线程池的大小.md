# 018_不停机数据迁移_在线历史迁移_线程池_如何设置线程池的大小

问题：如何为在线历史迁移设置线程池大小？

以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准，使用 Java 8。本文为设计分析，参数未完成压测验证。

## 1 面试口述精炼版本

口述内容字符数：152

**先给出资源约束**

线程池大小不能按 300 个任务直接推导。要先看数据库可用连接、CPU、磁盘、锁等待，并为在线业务预留资源。

**逐步压测**

从 2 个工作线程开始，固定批次和事务方式，再比较 4 个线程；同时观察吞吐、批次耗时、连接等待、数据库负载和业务延迟。吞吐提升很小而业务指标变差时，退回较低并发。2 和 4 只是压测候选值。

## 2 详细方案

### 2.1 并发度：看数据库承载能力，不看任务总数

约 300 个范围任务是工作总量，不能直接开 300 个线程，也不能机械套用 CPU 核数倍数公式。线程数要结合数据库 CPU、磁盘读写、连接等待、锁等待和在线业务延迟确定。IOPS 指每秒磁盘读写次数。

数据库连接预算只是容量约束之一，必须为在线业务预留资源。单个任务占用连接数取决于源库读取、目标分片写入和事务实现，不能假定一个工作线程永远只占一个连接。

**示例：固定其他变量，比较两个线程与四个线程**

以下是压测方法，不能视为已确认配置或测试结果。

1. 在每批 500—1000 条的参考范围中选定一个候选值，固定字段大小、分片分布、在线负载和事务提交方式。

2. 以核心数和最大数均为 2 的固定线程池、100 毫秒批间等待建立基线，再比较核心数和最大数均为 4 的配置。线程数和等待时长是示例；切换前确认上一组任务及在途操作已结束。

3. 比较迁移吞吐、批次耗时、可用连接与连接等待、数据库 CPU 和磁盘负载、锁等待、在线延迟及错误率。

4. 吞吐增长很小而资源竞争或业务延迟明显增加时，退回较低并发；不能因为等待队列里还有任务就继续加线程。

实际参数和业务验收阈值待压测。安全降低并发的执行步骤见 [017 执行机制：安全停止](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/017_不停机数据迁移_在线历史迁移_线程池_执行机制.md>)，本篇只维护容量判断和实验方法。

## 3 已确认规则

- 线程池大小使用压测确定，不由任务总数直接推导。
- 性能参数必须给出具体数值或范围、单位、作用对象和取值状态。
- 2、4 个线程只是候选压测值。
