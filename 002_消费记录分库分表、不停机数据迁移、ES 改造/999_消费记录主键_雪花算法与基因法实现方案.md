# 消费记录主键：雪花算法 + 基因法实现方案

## 2. 已确认的实现约定

### 2.1 商户字段

统一使用 `merchantNo` 作为分片键和基因计算字段。

生成主键、写入分片以及其他需要计算分片的代码，必须使用同一个规范化后的 `merchantNo`。不能在生成主键时使用 `merchantNo`，而在写入路由时改用另一个商户字段，否则主键末尾的基因与实际路由可能不一致。

### 2.2 分片数量和基因范围

消费记录规划为 2 个库、每个库 16 张表，共 32 个物理分片。本文只负责计算扁平的分片编号，不负责把编号映射成数据库和表。

```java
int shardIndex = Math.floorMod(merchantNo.hashCode(), 32);
```

因此 `shardIndex` 的取值范围是 `0~31`，最终编码为两位十进制字符串：

```text
0  -> 00
7  -> 07
31 -> 31
```

这里的“基因”是附加在主键末尾的十进制字符串，不是 Snowflake 位布局中的一个二进制字段。

### 2.3 最终主键格式

```text
consumeId = 19 位 snowflakeId + 2 位 shardIndex
```

例如：

```text
snowflakeId：419442695
格式化后：  0000000000419442695
shardIndex：7
最终主键：  000000000041944269507
```

最终 `consumeId` 固定为 21 位，Java 使用 `String` 保存，数据库建议使用 `CHAR(21)`。不能把完整的 21 位字符串转换成 `long` 或 MySQL `BIGINT`。

## 3. 整体生成流程

```text
业务代码收到 merchantNo
        |
        v
校验 merchantNo 非空
        |
        v
ConsumeIdGenerator.nextId()
        |
        +-- 获取当前毫秒
        +-- 检查时钟回拨
        +-- 更新同一毫秒内的 sequence
        +-- 组装 timestampPart、workerId、sequence
        |
        v
得到基础 snowflakeId
        |
        v
Math.floorMod(merchantNo.hashCode(), 32)
        |
        v
得到两位 shardIndex 基因
        |
        v
按 %019d%02d 格式拼接
        |
        v
返回 21 位 String 类型 consumeId
```

生成主键的职责分为两层：

```text
ConsumeIdGenerator：只生成基础 snowflakeId
ConsumeIdFactory：  计算 merchantNo 基因并拼成最终 consumeId
```

这样可以保持 `nextId()` 的职责单一，也避免把业务字段耦合到 Snowflake 的位运算实现中。

## 4. Snowflake 位布局

Java `long` 是 64 位有符号整数。本文采用如下布局：

```text
[1 位符号位][41 位 timestampPart][10 位 workerId][12 位 sequence]
```

### 4.1 字段含义

| 字段 | 位范围 | 取值范围 | 作用 |
|---|---:|---:|---|
| 符号位 | bit 63 | 固定为 0 | 保证生成结果为非负 `long` |
| `timestampPart` | bit 62~22 | `0~2^41-1` | 当前时间相对于 EPOCH 的毫秒数 |
| `workerId` | bit 21~12 | `0~1023` | 应用实例的全局唯一编号 |
| `sequence` | bit 11~0 | `0~4095` | 同一毫秒内的序列号 |

### 4.2 位移组装公式

```java
snowflakeId = (timestampPart << 22)
        | (workerId << 12)
        | sequence;
```

其中：

- `timestampPart << 22`：给 `workerId` 和 `sequence` 预留低 22 位；
- `workerId << 12`：给 `sequence` 预留低 12 位；
- `sequence`：直接放入最低 12 位；
- 三个字段互不重叠，所以可以使用按位或 `|` 合并。

`timestampPart` 虽然在 Java 源码中是十进制 `long`，但整数在 JVM 中本来就以二进制位参与运算，因此可以直接执行 `<<`。不需要先把变量手工转换成二进制字符串。

### 4.3 并发和容量

同一个 JVM 内只使用一个生成器实例，`nextId()` 使用 `synchronized` 保证 `lastTimestamp` 和 `sequence` 的更新具有原子性。锁内只包含时间读取、序列递增和位运算，不执行数据库、RPC 或其他 I/O。

一个 `workerId` 在同一毫秒最多生成：

```text
2^12 = 4096 个 ID
```

如果同一毫秒内序列号耗尽，生成器等待到下一毫秒，不会通过覆盖旧序列号的方式生成重复 ID。所有运行实例的 `workerId` 必须全局唯一；`synchronized` 只能保证单个 JVM 内的线程安全，不能替代跨实例的 `workerId` 分配机制。

## 5. 核心代码一：Snowflake 生成器

```java
/**
 * 只负责生成基础 Snowflake ID。
 *
 * 这个类在一个 JVM 内必须只实例化一次，例如注册为 Spring 单例 Bean。
 * 如果每次请求都重新创建实例，lastTimestamp 和 sequence 会被重置，
 * 会破坏同一实例内的唯一性和单调生成逻辑。
 */
public final class ConsumeIdGenerator {

    /** workerId 占用 10 位，取值范围为 0~1023。 */
    private static final int WORKER_ID_BITS = 10;

    /** sequence 占用最低 12 位，取值范围为 0~4095。 */
    private static final int SEQUENCE_BITS = 12;

    /** workerId 左移 12 位，为 sequence 预留低 12 位。 */
    private static final int WORKER_ID_SHIFT = SEQUENCE_BITS;

    /** 时间部分左移 22 位，为 workerId 和 sequence 预留空间。 */
    private static final int TIMESTAMP_SHIFT =
            WORKER_ID_BITS + SEQUENCE_BITS;

    /** 10 位 workerId 能表示的最大值：2^10 - 1。 */
    private static final long MAX_WORKER_ID =
            (1L << WORKER_ID_BITS) - 1;

    /** 12 位 sequence 的掩码：低 12 位为 1，即 4095。 */
    private static final long SEQUENCE_MASK =
            (1L << SEQUENCE_BITS) - 1;

    /** 41 位时间部分能表示的最大值：2^41 - 1。 */
    private static final long MAX_TIMESTAMP =
            (1L << 41) - 1;

    /** 自定义时间起点，单位为毫秒。 */
    private final long epochMillis;

    /** 当前应用实例的全局唯一编号。 */
    private final long workerId;

    /**
     * 上一次成功生成 ID 时使用的真实时间戳。
     * 初始化为 -1，保证第一次调用可以正常进入新毫秒分支。
     */
    private long lastTimestamp = -1L;

    /** 上一次生成使用的同毫秒序列号。 */
    private long sequence = 0L;

    public ConsumeIdGenerator(long epochMillis, long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException(
                    "workerId 必须在 0~1023 之间");
        }

        this.epochMillis = epochMillis;
        this.workerId = workerId;
    }

    /**
     * 生成一个基础 snowflakeId。
     *
     * 注意：本方法不读取 merchantNo，也不计算 shardIndex。
     * 商户基因由外层 ConsumeIdFactory 负责拼接。
     */
    public synchronized long nextId() {
        // 获取当前真实时间，单位为毫秒。
        long currentTimestamp = System.currentTimeMillis();

        // 如果当前时间早于上一次生成时间，说明发生了时钟回拨。
        // 继续生成可能与历史 ID 冲突，因此直接停止生成并抛出异常。
        if (currentTimestamp < lastTimestamp) {
            throw new IllegalStateException(
                    "系统时间发生回拨，不能生成 ID");
        }

        if (currentTimestamp == lastTimestamp) {
            // 仍处于同一毫秒，序列号加一，并保留低 12 位。
            sequence = (sequence + 1) & SEQUENCE_MASK;

            /*
             * sequence 从 4095 加一后会变成 0。
             * 这不是重新使用 0，而是说明本毫秒的 4096 个序列号已经用完。
             */
            if (sequence == 0) {
                currentTimestamp = waitNextMillis(lastTimestamp);
                sequence = 0;
            }
        } else {
            // 进入新的毫秒，序列号从 0 重新开始。
            sequence = 0;
        }

        /*
         * 使用相对时间，减少时间字段占用的数值范围：
         * timestampPart = 当前毫秒 - 自定义 EPOCH 毫秒值。
         */
        long timestampPart = currentTimestamp - epochMillis;

        /*
         * 左移操作不会自动把任意数值“变成 41 位”，所以必须显式校验。
         * 只有在这个范围内，timestampPart 左移 22 位才不会占用符号位。
         */
        if (timestampPart < 0 || timestampPart > MAX_TIMESTAMP) {
            throw new IllegalStateException(
                    "timestampPart 超出 41 位范围");
        }

        // 生成成功后记录本次实际使用的时间戳。
        lastTimestamp = currentTimestamp;

        /*
         * 组装 64 位 long：
         *
         * timestampPart << 22：放到高 41 位；
         * workerId << 12：放到中间 10 位；
         * sequence：放到最低 12 位。
         *
         * 三个位段互不重叠，因此使用按位或合并。
         */
        return (timestampPart << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence;
    }

    /**
     * 忙等到严格大于 lastTimestamp 的下一毫秒。
     *
     * 该方法不加 synchronized，是因为它只会由已经持有 nextId 锁的线程调用。
     * 如果生产环境对自旋 CPU 消耗敏感，可以在压测后改为 park/yield 策略，
     * 但必须保持“等待到严格下一毫秒”的语义。
     */
    private long waitNextMillis(long lastTimestamp) {
        long currentTimestamp;

        do {
            currentTimestamp = System.currentTimeMillis();
        } while (currentTimestamp <= lastTimestamp);

        return currentTimestamp;
    }
}
```

## 6. 核心代码二：基因拼接工厂

```java
import java.util.Locale;
import java.util.Objects;

/**
 * 负责将基础 Snowflake ID 和 merchantNo 计算出的分片基因拼成最终主键。
 *
 * 本类只负责生成主键，不负责解析主键，也不负责定位数据库和表。
 */
public final class ConsumeIdFactory {

    /** 2 个库、每库 16 张表，共 32 个分片。 */
    private static final int TOTAL_SHARDS = 32;

    /** Snowflake ID 的固定十进制宽度。 */
    private static final int SNOWFLAKE_WIDTH = 19;

    /** 末尾分片基因的固定十进制宽度。 */
    private static final int SHARD_INDEX_WIDTH = 2;

    /** 最终 consumeId 的固定长度。 */
    private static final int CONSUME_ID_WIDTH =
            SNOWFLAKE_WIDTH + SHARD_INDEX_WIDTH;

    private final ConsumeIdGenerator generator;

    public ConsumeIdFactory(ConsumeIdGenerator generator) {
        this.generator = Objects.requireNonNull(
                generator, "generator 不能为空");
    }

    /**
     * 生成最终消费记录主键。
     *
     * @param merchantNo 参与分片和基因计算的规范化商户编号
     * @return 固定 21 位的 consumeId 字符串
     */
    public String nextConsumeId(String merchantNo) {
        requireMerchantNo(merchantNo);

        // 第一步：获取全局唯一的基础 Snowflake ID。
        long snowflakeId = generator.nextId();

        // 第二步：根据 merchantNo 计算 0~31 的分片基因。
        // floorMod 可以把负数 hashCode 规范为非负分片编号。
        int shardIndex = Math.floorMod(
                merchantNo.hashCode(), TOTAL_SHARDS);

        /*
         * 第三步：固定宽度拼接。
         *
         * %019d：Snowflake 部分不足 19 位时在左侧补 0；
         * %02d ：分片部分不足 2 位时在左侧补 0，例如 7 输出为 07。
         *
         * 这里必须返回 String，不能把 21 位结果转换成 long。
         */
        String consumeId = String.format(
                Locale.ROOT,
                "%019d%02d",
                snowflakeId,
                shardIndex);

        // 这是格式契约检查，防止后续修改破坏固定长度。
        if (consumeId.length() != CONSUME_ID_WIDTH) {
            throw new IllegalStateException(
                    "生成的 consumeId 不是固定 21 位");
        }

        return consumeId;
    }

    private static void requireMerchantNo(String merchantNo) {
        if (merchantNo == null || merchantNo.isEmpty()) {
            throw new IllegalArgumentException(
                    "merchantNo 不能为空");
        }
    }
}
```

## 7. 最小调用示例

```java
// EPOCH 需要在所有实例之间统一；下面仅展示调用形式。
long epochMillis = 1577836800000L;

// workerId 必须由配置中心、注册中心或其他机制保证全局唯一。
long workerId = 3L;

// 在 Spring 应用中，这两个对象应注册为单例 Bean。
ConsumeIdGenerator generator =
        new ConsumeIdGenerator(epochMillis, workerId);

ConsumeIdFactory factory =
        new ConsumeIdFactory(generator);

String consumeId =
        factory.nextConsumeId("merchant-001");
```

实际业务写入消费记录时，只需要把返回的 `consumeId` 作为字符串主键保存。

## 8. 关键边界和注意事项

1. **生成器必须是单例**：同一个 JVM 内不能为每个请求重复创建 `ConsumeIdGenerator`。
2. **`workerId` 必须全局唯一**：`synchronized` 只能解决单 JVM 并发，不能解决多个实例使用相同 `workerId` 的问题。
3. **商户键必须统一**：生成基因时使用的 `merchantNo`，必须与业务分片约定中的商户键保持一致。
4. **不能丢失前导零**：`07` 必须保留为两位，Snowflake 部分也必须固定为 19 位。
5. **最终主键按字符串保存**：21 位主键可能超过 Java `Long` 和 MySQL `BIGINT` 的安全范围，建议使用 `CHAR(21)`。
6. **时钟回拨直接失败**：生产环境应对异常进行告警，并由基础设施保证系统时钟稳定。
7. **EPOCH 不能随意变更**：所有生成同一类主键的实例必须使用相同的 `epochMillis`。
8. **性能扩展要保持状态原子性**：如果未来单 JVM 的生成量接近单个 `workerId` 的容量，应通过增加独立 `workerId` 或采用经过验证的 ID 组件扩展，不能简单删除 `synchronized`。
