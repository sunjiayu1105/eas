## 2 详细方案

### 2.1 一个线程执行什么

已确认的规模规划是约 300 个主键范围任务，每个任务平均约 100 万条有效记录；范围内再按每批 500—1000 条的参考目标处理。一个工作线程执行一个范围任务，内部按顺序处理多个批次；任务完成或退出后，线程再处理后续任务。任务规模和线程数不能等同。

任务交给线程池之前只携带任务编号、起止主键和必要参数，不把整个范围的数据提前读进队列。数据由执行线程按批次读取，避免待执行任务占用大量内存。

实际线程数仍待确认，应结合数据库容量、连接池可用连接及在线负载压测确定；压测方法由性能调优分文档维护。

### 2.2 建议用专用线程池与有界队列

历史迁移使用独立线程池，避免长时间执行的迁移任务占用业务请求的线程资源。线程池独立只隔离线程资源，数据库连接和数据库负载仍需一起控制。

建议显式创建 ThreadPoolExecutor：corePoolSize 与 maximumPoolSize 先配置为相同的并发上限；队列用有界队列，控制等待中的任务数量。固定线程数是初始设计，不代表上线后无需调参。

Java 8 的 Executors.newFixedThreadPool 默认使用无界队列，不能因为固定了线程数，就认为排队数量也受限制。这里优先显式配置队列容量，避免后续任务规模增长时无限积压。

**核心配置示例**

以下为 Java 8 配置片段，workers 和 queueCapacity 均须为正数，取值待压测；它不是完整的迁移调度实现。

~~~java
ThreadPoolExecutor migrationPool = new ThreadPoolExecutor(
    workers, workers,
    0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<Runnable>(queueCapacity),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.AbortPolicy()
);
~~~

参数职责：

- workers：最多同时执行多少个范围任务。
- queueCapacity：最多缓存多少个待执行任务描述。
- AbortPolicy：队列满或线程池关闭后，显式抛出 RejectedExecutionException，让调度方知道本次提交未被接受。

### 2.3 队列满时如何处理

调度方按容量逐步提交任务，不要求一次把约 300 个任务全部塞入线程池。用 execute 提交时，应捕获 RejectedExecutionException：未接收的任务保持可再次调度，不记为已完成；等待容量恢复后再尝试。停机期间的拒绝应停止提交，不能无限忙重试。

任务状态的“领取、提交、执行、完成”必须衔接，避免同一个范围被重复派发或提交失败后永久停留在“处理中”。内存队列不是可靠任务存储，进程重启仍需从可靠状态与进度恢复，不能只依赖线程池中的 Runnable。

不建议在这个设计中使用静默丢弃策略。CallerRunsPolicy 会让提交线程也执行迁移任务，可能使数据库并发超过工作线程数；使用它之前必须重新定义总并发限制，不能直接当成无代价的限流方式。

**示例：两个工作线程处理约 300 个任务**

两个线程和两个排队位置只是说明机制的示例，不是项目配置。

1. 工作线程先执行范围任务 A、B，C、D 在队列等待，其他任务尚未提交。

2. A 完成后，空闲线程执行 C，调度方再提交后续任务。

3. 若提交时队列仍满，任务 E 被拒绝；调度方保留 E 的待调度状态，等待后重试。

4. 无论任务有多少，同一进程最多由这两个工作线程执行迁移；不能在范围任务内部另外无限创建写入线程。

### 2.4 失败、降并发和停止如何处理

**失败要可见**

工作线程中的数据库异常必须被记录并关联到任务范围，不能捕获后仍标记成功。若采用 submit 返回 Future，调度方还必须观察结果，不能忽略 Future 中保存的异常。具体重试次数和任务状态实现仍待确认。

**降并发不是强停在途写入**

停止继续派发只能减少后续任务；正在执行的范围可能很大，因此应在批次边界检查暂停或退出信号。需要降低实际并发时，允许部分工作任务完成当前批次并保存已确认进度后退出，待重新调度时继续。具体调节协议需实现验证，不假定修改配置立即生效。

**先停止接收，再等待安全退出**

停止调度后设置协作停止信号，正在执行的任务在下一批开始前检查信号。排队任务开始执行时也应检查，未执行完的范围保留可恢复状态。

shutdown 只是不再接收新任务，已排队任务默认仍会继续执行；要暂停迁移，需要上述任务级停止检查。shutdownNow 或 Future.cancel(true) 也只是发出中断请求，不能证明 JDBC 操作、网络请求或数据库事务已经停止。等待超时或写入结果未知时，不得推进完成进度，恢复时需核实结果。

进度与失败缺口的保存详见[014 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_断点续跑.md>)，安全重复执行详见[015 重试幂等](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/015_不停机数据迁移_在线历史迁移_重试幂等.md>)。

### 2.5 多进程限制与监控

单个线程池只约束当前进程。如果多个迁移进程同时运行，应控制进程数与各进程并发的总量，并保证任务领取不会重复。本文未选定多实例调度方案，也不声称单机线程池已经提供全局并发限制。

监控活动线程数、排队任务数、拒绝次数、任务耗时和失败数，并结合数据库负载、连接等待与在线延迟判断是否调参。线程池是否健康不能只看队列是不是空：可能还有在途任务、失败范围或尚未派发的任务。

并发数和其他参数的压测方法见[012 性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/012_不停机数据迁移_在线历史迁移_性能调优.md>)。

## 5 异议与分析

固定线程数只限制该线程池内同时执行的任务，不能限制所有进程、提交线程或任务内部另起线程的总并发。线程池队列也不能代替任务进度存储，停止线程池不能代替确认数据库写入结果。
