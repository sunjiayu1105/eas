## 1 问题

批次状态如何控制历史迁移的启动、暂停、完成和故障恢复？

## 2 高级 Java 面试核心考点

- 状态机与操作约束：用持久化状态控制请求，前端按钮不能替代后端校验。
- 并发启动与状态转换：启动检查和状态更新在同一个加锁事务中完成。
- 异步停止与恢复边界：收到暂停请求不等于执行结束，异常恢复必须先核实残留操作。

## 4 详细方案

### 4.1 批次与任务的区别及批次状态

一个迁移批次包含多个范围任务。批次状态描述整组任务的执行阶段，任务状态描述单个范围的处理结果，两者不能混用。

批次共有以下六种状态：

| 批次状态 | 含义 |
| --- | --- |
| 未启动 | 尚未完成初始化 |
| 运行中 | 初始化已提交，正在准备提交或执行任务 |
| 暂停中 | 正在等待任务和数据库操作收尾 |
| 已暂停 | 已安全收尾，可以继续处理 |
| 已完成 | 完整任务清单全部成功 |
| 异常待处理 | 存在失败、未知结果或无法确认的残留执行 |

“已完成”只表示本批次任务全部成功，不代表新旧数据已通过一致性校验。“暂停中”仍在等待执行结束，“已暂停”才允许继续启动。

### 4.2 启动时的状态转换

批次信息表保存整个批次的扫描上下界和控制状态，任务表保存各任务的范围、状态、确认进度和失败原因；不新增任务表批次 ID。批次控制以批次信息表中的状态为准。

只有未启动、已暂停可以进入运行中。后端必须在同一个加锁事务中完成状态检查与变更，不能先检查、再单独更新；其他状态拒绝启动。本设计只允许一个迁移实例，不采用 Redis 锁。

首次启动须完整保存任务清单后才能执行；恢复启动沿用原范围、任务和各自确认进度。初始化与状态变更的事务边界由启动专题展开，不能因进程重启就把批次改回未启动。

锁与事务细节见 [启动互斥与初始化事务](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务.md>)，扫描边界和任务字段见 [任务范围划分](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/017_不停机数据迁移_在线历史迁移_任务范围划分.md>)，提交执行见 [线程池调度](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/018_不停机数据迁移_在线历史迁移_线程池调度.md>)。本文维护状态转换条件，不重复展开各专题实现。

### 4.3 暂停、结束和恢复的状态转换

| 触发条件 | 状态变化与处理 |
| --- | --- |
| 用户暂停 | 运行中原子改为暂停中，通知停止新处理，等待当前执行收尾 |
| 任意任务失败 | 立即停止新处理并告警，尝试保存暂停中及任务失败状态；数据库不可用也不能继续派发 |
| 实际执行已收尾，完整任务清单全部成功且没有未知结果 | 更新为已完成，随后进入数据一致性校验 |
| 实际执行已安全收尾，没有失败或未知结果，但仍有未完成任务 | 更新为已暂停，允许后续启动继续处理 |
| 存在失败、未知结果或无法确认残留执行 | 进入异常待处理，禁止直接启动；状态无法落库时由告警和人工核实兜底 |
| 运维完成修复并核实上次操作已结束 | 恢复为已暂停，再走正常启动检查；不自动接管、不重新初始化 |

暂停中禁止重新启动；正常全部成功会自动结束，无需手动暂停。

服务器重启不代表数据库中的原操作必然结束。运行中或暂停中状态残留时，必须先核实上一次迁移的线程、进程和数据库操作，再修复任务与批次状态。恢复细节及失败原因诊断见 [暂停与故障恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/015_不停机数据迁移_在线历史迁移_批次状态控制_暂停与故障恢复.md>)；Future 收集、完整清单汇总和零任务边界见 [完成结果判定](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_批次状态控制_完成结果判定.md>)；进度续跑和重复写入分别见 [断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/021_不停机数据迁移_在线历史迁移_断点续跑.md>)、[重试幂等](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/022_不停机数据迁移_在线历史迁移_重试幂等.md>)。

### 4.4 异常处理后如何再次启动

“异常待处理”不能直接启动，须先完成修复，再恢复启动条件：

1. **修复原因并确认上次执行已结束**：运维确认上一次迁移的线程、进程和数据库操作已停止；写入结果不明的，先核实，不能仅因数据库恢复连接就重新启动。
2. **修复任务状态**：失败任务改为待处理；宕机残留的处理中任务，经核实安全后改为已暂停；已成功任务保持成功。原扫描范围、确认进度和失败日志保留。
3. **修复批次状态**：确认没有未处理异常后，由运维将批次从异常待处理改为已暂停，使其满足再次启动的状态条件。修数期间不能同时启动迁移。
4. **通过原入口再次启动**：点击启动按钮，后端完成启动检查并确认运行中状态提交成功后，查询待处理和已暂停任务，从各自保存的确认进度继续处理。已成功任务不重复执行，不重新初始化任务清单；未确认页可能重做，仍须遵守幂等规则。

修改状态不能代替修复故障，也不新增异常恢复接口。故障诊断、在途操作核实和人工修数边界继续由 [暂停与故障恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/015_不停机数据迁移_在线历史迁移_批次状态控制_暂停与故障恢复.md:68>) 维护。

### 4.5 页面操作与后端校验

| 批次状态 | 启动按钮 | 暂停按钮 |
| --- | --- | --- |
| 未启动 | 可用 | 禁用 |
| 运行中 | 禁用 | 可用 |
| 暂停中 | 禁用 | 禁用 |
| 已暂停 | 可用 | 禁用 |
| 已完成 | 禁用 | 禁用 |
| 异常待处理 | 禁用 | 禁用 |

列表直接显示当前状态，不单独提供“查询状态”操作，也不增加异常恢复接口。启动、暂停接口仍校验数据库中的状态，前端按钮禁用只是操作提示，不能承担并发控制。例如页面仍显示已暂停，但另一个请求已经启动成功，后端应按最新运行中状态拒绝再次启动。

## 5 已确认规则

- 按启动检查、初始化或恢复、提交执行、暂停或失败、结果判定、修复重启顺序阐述。
- 页面只显示当前状态，提供启动和暂停操作；后端独立校验状态。
- 同一时刻只允许一个迁移实例；启动使用数据库行锁和批次状态，不使用 Redis 锁。
- 首次初始化一次性保存完整任务；恢复保留原扫描范围和各任务进度。
- 任意任务失败均停止新处理、告警并由运维排查，不自动重试。
- 安全收尾后才允许恢复；完整任务全部成功后还需一致性校验。
- 异常修复后由运维修复任务状态，将批次改为已暂停，再通过原启动入口处理待处理和已暂停任务；保留原范围和确认进度。
- 批次与任务的区别、六种批次状态及其含义放在详细方案中，不单设必要概念说明章节。
