## 1 问题

多实例部署时，如何保证同一迁移批次同一时间只由一个服务实例执行，并处理两个并发启动请求？首次启动和暂停恢复分别做什么？已经记录异常、宕机后状态残留，以及其他执行异常应该如何处理？

## 2 高级 Java 面试核心考点

- 状态机与操作约束：用持久化状态控制请求，前端按钮不能替代后端校验。
- 启动与执行互斥：Redisson 锁协调启动请求，数据库条件更新决定哪次请求取得启动资格，持久化状态限制整个执行期间的再次启动。
- 异步停止与恢复边界：收到暂停请求不等于执行结束，异常恢复必须先核实残留操作。

## 3 面试口述精炼版本

**先决定谁能启动，再决定从哪里继续**

多个服务实例部署时，同一个迁移批次共用一条数据库控制记录。两个启动请求并发到达，先竞争同一把 Redisson 启动锁。拿锁后在事务里按原状态更新，只有更新成功并确认提交的请求才可以调度。提交后释放启动锁，其他请求即使随后拿到锁，也会被数据库中的运行中状态挡住。首次启动在同一事务保存扫描边界和任务清单，暂停后恢复则沿用原任务和确认进度。

## 4 详细方案

### 4.1 批次与任务的区别及批次状态

一个迁移批次包含多个范围任务。批次状态描述整组任务的执行阶段，任务状态描述单个范围的处理结果，两者不能混用。

批次共有以下六种状态：

| 批次状态 | 含义 |
| --- | --- |
| 未启动 | 尚未完成初始化 |
| 运行中 | 初始化已提交，正在准备提交或执行任务 |
| 暂停中 | 正在等待任务和数据库操作收尾 |
| 已暂停 | 已安全收尾，可以继续处理 |
| 已完成 | 完整任务清单全部成功 |
| 异常待处理 | 存在失败、未知结果或无法确认的残留执行 |

“已完成”只表示本批次任务全部成功，不代表新旧数据已通过一致性校验。“暂停中”仍在等待执行结束，“已暂停”才允许继续启动。

### 4.2 多实例执行与并发启动

本文的多个实例指迁移服务的多个部署实例。同一个迁移批次在这些实例之间共用一把启动锁和一条批次控制记录。批次信息表保存扫描上下界和控制状态，任务表保存范围、状态、确认进度和失败原因。沿用现有任务表设计，不新增批次 ID。

1. 收到两个并发启动请求时，先竞争同一把 Redisson 启动锁。拿不到锁的请求结束本次启动。取得锁后，重新读取数据库状态，避免沿用请求到达时看到的状态。
2. 拿到锁的请求开启数据库事务，读取批次状态，仅允许“未启动”或“已暂停”。更新时带上批次标识和本次读到的原状态，将状态改为“运行中”。只有影响一行且事务提交得到确认，这个请求才取得调度资格。
3. 启动准备事务确认提交后，由持有锁的线程释放启动锁，再提交任务。启动锁的过期时间按已确认规则为 15 分钟。执行期间，数据库中的“运行中”或“暂停中”继续拒绝启动。即便启动锁提前过期，竞争请求仍须通过数据库条件更新。锁过期也不构成接管依据。

“运行中”涵盖启动事务已提交但尚未提交线程池任务的阶段。数据库状态只记录控制进度，无法证明旧实例当前已停止。故障恢复时，先确认旧执行无法继续派发、写入或更新进度，再修复状态并允许下一次启动。当前方案走人工恢复。若旧实例仍有可能从挂起中恢复，必须先阻止它继续执行，再重置批次状态。

### 4.3 首次启动和暂停后恢复

| 启动场景 | 事务内处理 | 提交确认后 |
| --- | --- | --- |
| 首次启动 | 从“未启动”取得启动资格。在同一事务保存扫描上下界、完整任务清单和“运行中”状态，任务初始为“待处理” | 释放启动锁，按已保存的任务范围调度 |
| 暂停后恢复 | 从“已暂停”取得启动资格并转为“运行中”。沿用原扫描范围、任务清单和确认进度 | 释放启动锁，调度“待处理”和“已暂停”的任务，已成功任务保留原结果 |

首次初始化失败时，确认整个事务回滚后才允许重新初始化。事务提交结果未知时，停止本次启动并核实数据库。恢复时，按各任务最后一个已确认的进度继续。启动后的任务提交流程见 [线程池调度](./020_不停机数据迁移_在线历史迁移_线程池调度.md)，分页恢复规则见 [断点续跑](./023_不停机数据迁移_在线历史迁移_断点续跑.md)。

### 4.4 暂停、结束和恢复的状态转换

| 触发条件 | 状态变化与处理 |
| --- | --- |
| 用户暂停 | 运行中原子改为暂停中，通知停止新处理，等待当前执行收尾 |
| 任意任务失败 | 立即停止新处理并告警，尝试保存任务失败状态，并将运行中批次转入暂停中等待收尾；数据库不可用也不能继续派发 |
| 实际执行已收尾，完整任务清单全部成功且没有未知结果 | 更新为已完成，随后进入数据一致性校验 |
| 实际执行已安全收尾，没有失败或未知结果，但仍有未完成任务 | 更新为已暂停，允许后续启动继续处理 |
| 存在失败、未知结果或无法确认残留执行 | 进入异常待处理，禁止直接启动；状态无法落库时由告警和人工核实兜底 |
| 运维完成修复并核实上次操作已结束 | 恢复为已暂停，再走正常启动检查；不自动接管、不重新初始化 |

暂停中禁止重新启动；正常全部成功会自动结束，无需手动暂停。

检查完整任务清单时，需要把已接收、已执行和未调度的任务都纳入结果判断。某次调度没有可提交任务时，也应核对完整清单。旧表为空时的零任务最终状态仍待确认。

### 4.5 异常处理后如何再次启动

1. 停止派发和领取新任务，保留异常信息并告警。“异常待处理”期间启动入口拒绝请求。
2. 运维根据异常记录、任务状态和最后确认进度定位问题。确认旧实例已无法继续调度，核对在途写入和进度事务的提交结果，处理失败任务和残留的“处理中”任务。
3. 已确认成功的任务保留结果。需要重做的范围按最后确认进度恢复为可续跑状态，保留原任务清单。未确认的页经核对后从确认边界按幂等规则重做。参见 [重试幂等](./022_不停机数据迁移_在线历史迁移_重试幂等.md)。
4. 故障已修复、旧执行确认收尾且任务状态已修复后，由运维将仍需续跑的批次改为“已暂停”，再走原启动入口。若完整任务清单已全部确认成功，则按完成条件收尾。运维修复时复核批次当前状态并记录处理结果，避免覆盖其他操作已经更新的状态。

### 4.6 宕机后如何判断能否重新启动

“运行中”或“暂停中”可能是宕机前留下的状态。先检查原实例是否仍能派发或恢复执行，再检查实际写库的数据库会话与事务，核实提交、回滚或仍在进行的操作。最后对照已持久化的任务清单、任务状态和确认进度，区分尚未开始、已确认完成和结果未知的任务。事务已提交但线程池尚未接收任务时，仍应保留原任务清单。

只要旧执行可能继续，或最后一次写入和进度结果尚无法确认，就继续阻止启动并告警。确认旧执行已停止且结果已核实后，按异常处理流程修复残留状态，经“已暂停”恢复需要续跑的任务。实例失联、启动锁到期、服务重启都只能触发排查。

### 4.7 其他执行异常

| 场景 | 处理 |
| --- | --- |
| 初始化或恢复事务提交响应丢失 | 停止调度，核实批次状态和任务清单是否已提交。确认完整回滚后才允许按原状态重新启动 |
| 线程池只接收了部分任务，随后发生拒绝或线程创建失败 | 停止提交，通知已接收任务在安全边界收尾，保留未接收任务的原状态，按完整清单核对 |
| 目标库写入超时，或写入结束但保存进度失败 | 停止该范围的后续处理，按最后确认进度核实未确认页。修复后按重试幂等规则续跑 |
| 批次或任务状态更新失败 | 停止新处理并告警，排查数据库和实际执行结果。原状态可能残留，恢复前人工核实 |
| 暂停等待超时，旧线程或数据库操作仍未明确结束 | 保留禁止启动状态并告警，待实际执行确认收尾后再修复批次和任务状态 |

### 4.8 页面操作与后端校验

| 批次状态 | 启动按钮 | 暂停按钮 |
| --- | --- | --- |
| 未启动 | 可用 | 禁用 |
| 运行中 | 禁用 | 可用 |
| 暂停中 | 禁用 | 禁用 |
| 已暂停 | 可用 | 禁用 |
| 已完成 | 禁用 | 禁用 |
| 异常待处理 | 禁用 | 禁用 |

列表直接显示当前状态，不单独提供“查询状态”操作，也不增加异常恢复接口。启动、暂停接口仍校验数据库中的状态，前端按钮禁用只是操作提示，不能承担并发控制。例如页面仍显示已暂停，但另一个请求已经启动成功，后端应按最新运行中状态拒绝再次启动。

## 5 已确认规则

- 按启动检查、初始化或恢复、提交执行、暂停或失败、结果判定、修复重启顺序阐述。
- 页面只显示当前状态，提供启动和暂停操作；后端独立校验状态。
- 同一时刻只允许一个迁移实例；启动使用 Redis 锁、数据库条件更新与同库事务；Redis 锁过期时间为 15 分钟，启动准备提交后主动释放。
- 首次初始化一次性保存完整任务；恢复保留原扫描范围和各任务进度。
- 任意任务失败均停止新处理、告警并由运维排查，不自动重试。
- 安全收尾后才允许恢复；完整任务全部成功后还需一致性校验。
- 异常修复后由运维修复任务状态，将批次改为已暂停，再通过原启动入口处理待处理和已暂停任务；保留原范围和确认进度。
- 批次与任务的区别、六种批次状态及其含义放在详细方案中，不单设必要概念说明章节。
