### 5.1 总链路与职责

同步对象是新分表已提交的新增、修改和删除。两个独立 MySQL 实例各有 16 张分表，通过 ROW 格式 binlog（按行记录变更）提供行数据；历史导入前分别保存 GTID（全局事务标识）基线，即当时已执行事务的完整集合，作为首次起点。历史导入本身也须进入 binlog，才能从该基线覆盖导入和后续变更。日志条件、基线采集和可追赶窗口见[双库采集](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/042_MySQL到ES同步_双库采集.md:1>)。

Canal Server 以 MySQL 复制客户端的方式读取日志，按库表过滤并解析变更，再通过自带的消息发送功能向 RocketMQ 发布消息。一个单机 Server 进程承载 db0、db1 两个 destination（同步通道），各自维护源库、配置和进度；发布时按稳定业务键选择队列，具体字段、队列映射及重试后的路由与来源顺序仍须核验。消息发布与位点提交见[发布与位点提交](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/045_MySQL到ES同步_消息发布与位点提交.md:1>)，中断恢复见[Canal 中断恢复](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/046_MySQL到ES同步_Canal中断恢复.md:1>)。

RocketMQ 暂存变更消息，ES 处理较慢时先排队等待，以此缓冲两边的处理速度差异；Canal Server 与消费服务通过消息交接，采集端不必等待每次 ES 写入完成，以此解耦日志采集与 ES 处理。积压仍受队列容量和消息保留时间限制，下游暂停、修复和追赶所需的窗口须按实际 Broker 核验。

自定义消费者把 INSERT 和 UPDATE 转成完整文档，按原始创建月份和业务主键定位，使用携带 `version_type=external` 的 Index API 写入。同一物理索引、同一 `_id` 下，ES 才会比较来源版本。收到保留期 DELETE 时保存必要的事件信息，再处理消息里的下一行。全部行及必要状态处理完成后才能确认消费。

### 5.2 自然月索引与跨月增删改

新增、更新及其重试和补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。例如 10 月 31 日创建的记录写入 `records-2026.10`，11 月更新时仍写该索引。历史导入不能把导入时间当成原始创建时间，删除消息须保留删除前的创建时间。缺失时进入受控修复，不能用当前时间猜测月份。

`records-read` 覆盖各月份索引，仅用于跨月查询。提前配置匹配 `records-*` 的模板，统一字段映射、配置和读别名；日常月份索引由自动任务提前一个月创建。创建失败时告警，任务无法完成创建时由运维手工创建。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后达到迁冷的年龄条件；冷热迁移不改变索引名，也不等于只读。月索引准备、冷热迁移和到期清理见[索引与生命周期](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/055_ES索引与生命周期.md:1>)及其追问。

业务时区、创建时间实际列名及传递、7 天修改窗口是否为硬限制、历史删除范围、重试与乱序恢复仍需核验。按月定位不替代业务版本或删除保护；索引清理后的旧消息重放须防止误建已过期索引。

### 5.3 重复处理与一致性边界

可靠投递以“至少一次”为设计目标，即事件可能重复，但不能漏掉应处理的变更。重试、部分发送成功或确认失败都可能造成重放；存在重复风险并不能证明已经满足至少一次保证。039 已记录 Canal Server 自带的消息发送功能未显式检查发送状态的风险，实际发行包、Broker（MQ 服务端）的持久化与留存，以及恢复流程均须验证。

消息可能重复，也可能乱序完成，因此需要分别处理“同一事件再次执行”和“旧事件晚于新事件执行”。幂等是重复处理仍得到正确结果；防旧写则要求晚到的旧事件不能覆盖新结果。项目优先评估稳定来源版本与 ES 外部版本控制，在可靠绑定的目标物理索引内让 ES 原子拒绝相同或更低版本，随后核对冲突是重复、过期还是异常。允许重复请求 ES 且没有其他副作用时，可以不额外使用独立 `eventId`，但同版本必须对应同操作同内容；需要事件级去重时，再采用“业务主键 + 来源版本”或独立事件 ID。年度任务清理过期索引后，回放和补偿须先检查保留范围，防止重新创建过期月份索引。

MQ 消费确认采用参考文章的整条消息重投模型：每次回调逐条同步调用 ES，操作或必要状态保存出现未解决的异常，就中断并向外抛出运行时异常，由 MQ 重投原消息。此前成功的操作不自动回滚，所以重投必须继续使用根据原始创建时间计算的同一物理索引、原版本并经过幂等流程。已核实的重复或过期冲突，可以按既定规则完成处理及状态恢复，再继续消息中的其余事件；只有整条消息全部处理及必要状态保存完成，监听方法才能正常返回。这样区分了“当前请求是否再次写入”和“该事件是否已正确处理”，避免把正常重复当作持续失败，也避免漏处理剩余事件。不采用 Bulk 单项失败分类和状态驱动的恢复流程，具体重试、死信和恢复仍结合 044、045 和实际发行包核验。

正常返回只表示本条消息按消费规则处理完成；ES 中的变更还须在相关分片 refresh（刷新）后才对搜索可见。搜索可见只说明可以检索到相应状态，不能证明源库与 ES 在规定范围内一致，因此两项增量校验各自独立比较并维护进度，差异由补偿流程处理。自动校验与兜底补偿任务每半小时执行一次，失败或延迟超过预期须告警；每半小时是任务的调度周期。扫描只覆盖仍存在的源行，实际修复时长还取决于扫描、重试和可用性。补偿同样须遵守既定业务版本和索引定位规则，不能无版本覆盖；补偿须读取相互对应的当前业务数据与 `version`。同步负责写入，校验负责比较，具体分工和验收条件见[自定义消费服务](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/049_自定义消费服务.md:1>)、[新旧表校验](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/035_新旧表一致性校验.md:1>)与[新表与 ES 增量校验](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/060_新表与ES增量校验.md:1>)。

### 5.4 各层进度与恢复范围

采集、发布和消费分别推进，恢复时须先确定事件在哪一层完成可靠交接，再核对该层之后的数据是否仍可读取：

| 层次 | 需要核对的进度或结果 | 恢复依赖 |
| --- | --- | --- |
| MySQL | 导入前基线、各读取通道的可靠起点 | 所需 binlog 连续且未被清理；30 天是项目保留目标 |
| Canal Server | 发布结果、内部确认与本地持久化位点 | 位点和源日志对应，已发送但未确认的部分可能重放 |
| RocketMQ | 消息留存范围、各队列消费位点 | 所需消息仍在，留存与容量覆盖下游暂停、修复和追赶 |
| ES 写入服务 | 原索引路由、事件状态、ES 实际结果 | 重复与旧事件保护，也须覆盖结果不明的在途请求 |

binlog 保留 30 天不等于 MQ 也保留 30 天，MQ 消费落后也不能假定会阻止消息清理。若事件已可靠交给 MQ，Canal 位点已推进，而 MQ 中未消费消息又过期，常规重启不能自动补回缺口；应暂停复核可重放范围和补偿方案，不能直接回退位点或跳到最新位置。Broker 留存参数、实际可读范围、容量及补偿流程尚未验证。

1. **链路与消息发送**：`MySQL → Canal Server（RocketMQ 模式）→ RocketMQ → 自定义 RocketMQ 消费与 ES 写入服务 → Elasticsearch`。统一使用“Canal Server 自带的消息发送功能”；主语明确时可简称“自带的消息发送功能”。Canal Adapter 不参与主链路，不配置 32 份映射。消费服务直接消费 RocketMQ 后调用 ES，不增加原始消息数据库表作为 ES 写入前置环节。
2. **源库、首次起点与日志**：两个独立 MySQL 实例各含 `consume_record_01`～`consume_record_16`，共 32 张表，分别对应 db0、db1 destination。各通道独立维护源库、过滤、起点和进度，不共用起点，不承诺跨库全局顺序。在双写产生首笔新表变更前分别保存 GTID 基线，双写上线时开启新表到 ES 的同步。基线用于首次启动；历史导入及后续写入保持 `sql_log_bin=ON`。binlog 目标保留 30 天，实际参数、磁盘空间和恢复窗口仍需核验。
3. **单机 Server 与路由**：1 台主机的 1 个 Server 进程承载 db0、db1，使用本地 `canal.properties`、各通道 `instance.properties` 和 `file-instance.xml`；不使用 ZooKeeper、canal-admin、管理库、集中配置管理或自动主备切换。Server 按库表过滤，以 `canal.mq.partitionHash` 按稳定业务键选队列；自定义服务按库、表和事件类型路由。实际字段、队列映射及重试后的路由与来源顺序仍需核验。
4. **投递、进度与恢复**：发布结果、Canal 本地持久化位点、MQ 消费进度和 ES 处理结果分别核对，MQ 或 ES 成功不证明 Canal 位点已持久化。消息拆分、发送确认、失败重试及位点持久化须按 1.1.7 发行包核验；消息发布与位点提交一题所引的发送源码未显式检查 `SendResult` 是否为 `SEND_OK`，内部提交回调不能单独证明可靠交接。Server 故障同时中断两通道采集与发布，人工核对本地位点和日志连续性后重启。MQ 留存与 binlog 保留窗口分别核验，位点丢失或消息断档时暂停复核；至少一次投递是设计目标，不承诺端到端 exactly-once（恰好一次）。
5. **业务版本与并发消费**：采用 `CONCURRENTLY` 并发消费；首次创建订单时，当前主写表写入 `version = 1`。切写前由旧表生成业务版本，历史迁入与双写保留来源版本。切写后由新表继续维护版本，每次成功更新都在同一条 SQL 中修改业务字段并递增版本。同步到 ES 和消息重投沿用原事件版本；导入重跑不重置已有版本，MQ 重试沿用消息中的版本与数据。新旧表校验排除 `version`，其他口径不变，版本初始化、递增和重放稳定性单独验证。以上是已确认、待实现验证的设计决策。Canal 传递行数据中的业务版本，ES 版本不再由 binlog 坐标编码生成。
6. **自然月索引（已确认设计，待实现验证）**：新增、更新及其重试和补偿均根据不可变的原始 `create_time`，按统一业务时区计算 `records-yyyy.MM`，直接操作该物理索引；正常路径不先搜索，也不维护业务 ID 到索引名的持久化映射。业务 ID 作为 `_id`，`records-read` 作为跨月读别名。按自然月分索引，不使用 rollover；历史回放期间暂停相关索引的 ILM cold 迁移，回放完成且新表与 ES 校验通过后恢复 ILM，所属月份下个月 1 日零点起算满 `366d` 后达到迁冷的年龄条件。删除事件须携带删除前的创建时间，索引模板统一 Mapping、配置和读别名；自动任务提前一个月创建日常月份索引，创建失败时告警，任务无法完成创建时由运维手工创建。稳定业务主键作为 `_id`，仅在同一物理索引内唯一；外部版本也只在同一物理索引、同一 `_id` 范围内比较。新增、更新调用 Index API，将完整文档连同业务 `version` 一次性写入目标物理索引，由 ES 原子比较版本。保留期 DELETE 保存必要的事件信息。每年 1 月 1 日由自动任务按自然年保留下界删除整月索引，ILM 负责冷热迁移。版本须稳定递增，同版本必须对应同操作和同内容；版本冲突需区分重复、过期和异常。
7. **消费确认、重试与校验**：不同消息并发处理，每次回调内仍逐条同步调用 ES；操作或必要状态保存异常时，中断当前消息并向外抛出运行时异常，由 RocketMQ 重投整条原消息。此前成功的操作不自动回滚，因此重投须继续使用根据原始创建时间计算的同一物理索引、原版本并经过既有幂等流程。已核实的重复或过期冲突按幂等规则处理，继续完成其余事件；消息内全部事件处理及必要状态保存完成后，监听方法才能正常返回。不采用 Bulk 单项失败分类和状态驱动的恢复流程；索引路由和并发版本判断见[ES 月索引设计](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/055_ES索引与生命周期.md:1>)和[并发乱序](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/050_自定义消费服务_并发乱序.md:1>)。具体重试次数、退避、死信和恢复仍待核验。自动校验与兜底补偿任务每半小时执行一次，以源表仍存在的行核对 ES，发现差异后按源库当前状态补偿。源行已删除时，此扫描无法发现 ES 单独多出的文档。任务失败或延迟须告警。同步处理完成、搜索可见和独立校验通过分别判断，校验发现差异后按源库当前状态补偿，补偿也须遵守既定版本和索引定位规则。
