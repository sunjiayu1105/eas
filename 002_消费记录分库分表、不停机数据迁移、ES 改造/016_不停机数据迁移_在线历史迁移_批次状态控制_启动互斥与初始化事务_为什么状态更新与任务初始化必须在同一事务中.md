## 1 问题

为什么批次状态更新与批次内任务初始化必须放在同一个数据库事务中？

## 2 高级 Java 面试核心考点

- 用事务原子性保证批次状态和批次内任务清单一致。
- 分析分别提交时的失败窗口，区分单条语句失败与整个事务回滚。
- 区分事务原子性、启动互斥及提交结果未知。

## 3 面试口述精炼版本

口述内容字符数：329
**批次状态和批次内任务清单必须一起成功**

后续启动会根据批次状态判断是否需要初始化，所以首次初始化提交后，批次变为运行中时，批次内的完整任务清单也必须已经保存。如果批次状态先提交，批次内任务只初始化了一部分就失败，下次启动会被运行中状态拦住；反过来，先提交批次内任务、后更新批次状态失败，也可能导致再次初始化。

**失败时回滚整个事务**

因此要将批次扫描边界、批次内全部任务插入和批次状态更新放在同一事务中，一起提交；任一步失败，就回滚整个事务。比如计划 300 个任务，批次内插入 100 个任务后失败，完整回滚会撤销这 100 个任务及本次批次状态变更。这个保证来自事务原子性，不等于已经解决并发启动；互斥仍沿用行锁方案。提交结果未知时先核实，不能直接当作回滚成功。

## 4 详细方案

### 4.1 为什么状态与任务清单不能分别保存

批次状态决定下一次启动是否需要初始化；批次内任务清单决定哪些范围会被迁移。首次初始化必须同时保存批次表中的扫描上下界、任务表中的完整任务清单和批次的运行中状态，才能使批次状态与批次内任务的实际准备情况一致。任务初始状态为待处理，与批次未启动状态属于不同层级。

这里的“一起成功”指事务提交后的持久化结果，不要求事务内部某一条 SQL 执行后，其他 SQL 就已经完成。事务内可以先插入任务再更新状态，但不能把中间结果单独提交。后续任务处理必须等提交成功得到确认之后再开始。

### 4.2 分别提交会留下什么问题

下面比较相同目标：保存一份完整的批次内任务清单，同时把批次改为运行中。区别在于失败时能否统一撤销。

**分别提交：** 假设批次状态已经单独提交为运行中，计划生成 300 个批次内任务，却在插入 100 个后失败。即使任务插入事务回滚，已提交的批次运行中状态也不会一起撤销；如果任务分多次提交，还可能留下部分批次内任务。下一次启动读到运行中就拒绝，无法按正常首次初始化流程补齐。

**同一事务：** 批次状态更新和 300 个批次内任务插入都尚未提交时，第 100 个任务之后失败，应用完整回滚该事务。该事务已插入的批次内任务、修改的批次扫描边界及批次状态变更一起撤销，不会留下“批次运行中但批次内任务清单不完整”的已提交结果。

反过来，先独立提交完整的批次内任务，再更新批次状态也不能解决问题：若批次状态更新失败，数据库仍显示未启动，下次可能再次初始化；唯一约束可以拦住重复任务记录，却不能自动修复批次状态与任务清单不一致。

### 4.3 事务应怎样组织

1. 开启数据库事务，按主键锁定已有批次记录，应用检查状态。
2. 首次启动时，在该事务中保存批次扫描上下界、完整的批次内任务清单，并将批次改为运行中。
3. 任一步失败或清单校验不通过，明确回滚整个事务，不吞掉异常后提交。
4. 只有提交成功得到确认，才提交迁移任务；不在初始化事务内执行历史数据迁移。

批次表和任务表应使用 InnoDB，批次状态、批次扫描边界和批次内任务清单的写入必须参与同一数据库事务和连接。不能让任务插入使用自动提交、独立事务或异步线程，否则外层回滚无法统一撤销这些已提交写入。Spring 事务是否真正生效、异常是否触发完整回滚，都要验证，不能只凭方法有事务注解判断。

完整核心实现见 [启动互斥与初始化事务](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务.md>)；本篇专门解释事务边界，不复制另一份初始化代码。已暂停批次恢复时沿用原任务清单和进度，不重新初始化。

### 4.4 回滚与提交结果未知要分开处理

仅一条 SQL 失败，不代表数据库已经回滚整个事务。例如锁等待超时默认可能只回滚当前语句，应用应结束并回滚整个初始化事务。确认完整回滚后，才可按原未启动状态重新初始化。

如果 COMMIT 的响应丢失，数据库可能已经提交，不能因为客户端异常就认定状态和任务均已撤销。此时应停止本次启动、核实持久化结果，再按既有人工恢复规则处理。事务已提交但进程在调度前宕机，也会留下运行中状态和完整任务清单；这属于调度与恢复问题，不是事务原子性失效。

事务原子性解决的是本次写入一起成功或失败；启动互斥解决的是多个请求不能同时通过检查。Redis 锁有效期的讨论不改变本篇事务要求，本次不替换现有锁方案。

依据：[MySQL 8.0 COMMIT 与 ROLLBACK](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/commit.html) 及 [InnoDB Error Handling](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-error-handling.html)。本次依据现有方案和事务语义整理，未重新联网核验全部来源，也未执行故障实验。
