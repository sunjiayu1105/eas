## 1 问题

如何通过 Redis 锁、数据库条件更新和事务，实现批次首次启动与恢复启动？

## 2 高级 Java 面试核心考点

- Redis 锁的获取、过期与持有者校验：锁只覆盖启动准备，不覆盖整轮迁移。
- 数据库条件更新防重：用原状态作为更新条件，只有更新成功的请求取得启动资格。
- 事务原子性与调度交接：首次初始化和批次状态一起提交，确认提交后才调度。
- 故障处理：区分初始化回滚、提交未知和提交后尚未调度，保留安全恢复前提。

### 3.1 获取启动锁，检查批次状态

先获取同一批次的 Redis 锁，过期时间为 15 分钟，获取失败就返回。获取成功后，在数据库事务中读取批次状态；只有未启动或已暂停才允许继续，其他状态直接结束，并释放自己持有的锁。

### 3.2 首次启动：状态更新与任务初始化一起提交

批次为未启动时，先通过条件更新将批次改为运行中，只有影响行数为 1 才初始化任务。扫描上下界保存在批次信息表，完整任务清单写入任务表，各任务初始状态为待处理。这些操作在同一事务中提交或回滚。例如任务初始化中途失败，之前写入的任务、扫描边界和运行中状态一起回滚，不能留下半份清单。

### 3.3 恢复启动：校验已有任务，不重复初始化

恢复前，运维先确认上一次的工作线程和数据库操作已结束，存在的故障已处理完。启动事务中通过条件更新将已暂停改为运行中，再检查已有任务是否允许恢复；校验失败则回滚状态更新并告警，人工排查后才能重启。校验通过就沿用原任务和进度，不重新初始化。

### 3.4 提交后释放锁，再调度任务

确认运行中状态提交成功后，主动释放自己持有的 Redis 锁，再开始调度任务，不等迁移完成才释放。后续请求即使拿到锁，也会因批次已是运行中而退出。释放锁时必须原子校验持有者，不能删除其他请求重新获取的锁。

### 3.5 过期时间是故障兜底，不是安全证明

15 分钟是锁的过期时间，不是必须持锁的时长。进程宕机、无法主动释放时，锁到期失效，避免永久占用。但到期不会停止原线程，所以不能仅凭代码少就认定绝不会超时。即使两个请求都进入启动流程，也要通过数据库条件更新竞争同一次启动资格。提交结果未知，或提交后、调度前宕机时，先核实再恢复，不能直接重新初始化。

## 4 详细方案

### 4.1 核心流程与辅助方法职责

以下使用匿名内部类，不使用 Lambda。`tx` 表示以同一 DataSource 配置的 `TransactionTemplate`，使用默认 REQUIRED 传播方式。入口拒绝外层事务，因此 `execute` 会在回调前开启事务；回调正常返回且未标记仅回滚时提交，抛出运行时异常或 Error 时回滚。这里省略配置、import 和辅助方法实现。

```java
void start() {
    if (TransactionSynchronizationManager.isActualTransactionActive()) {
        throw new IllegalStateException("启动入口不能处于外层事务中");
    }
    // 原子获取同一批次的锁并设置 15 分钟过期时间；token 标识本次持有者。
    String token = tryAcquireRedisLock(15, TimeUnit.MINUTES);
    if (token == null) {
        return;
    }

    Boolean ready;
    try {
        // 先开启事务，再执行回调；execute 返回前完成提交。
        ready = tx.execute(new TransactionCallback<Boolean>() {
            @Override
            public Boolean doInTransaction(TransactionStatus status) {
                String state = queryBatchState();
                if (!"NOT_STARTED".equals(state) && !"PAUSED".equals(state)) {
                    return false;
                }
                // WHERE id = ? AND status = ?；更新为 RUNNING。
                if (changeBatchToRunningIfStateMatches(state) != 1) {
                    return false;
                }
                if ("NOT_STARTED".equals(state)) {
                    initializePendingTasks();
                } else {
                    checkResumeConditions(); // 校验失败抛异常，回滚运行中状态。
                }
                return true;
            }
        });
    } finally {
        // 原子比较 token 后删除；只释放自己仍持有的锁。
        // 调用失败不得被吞掉；本示例保守地结束启动，交由告警和人工核实。
        releaseRedisLockIfOwned(token);
    }

    if (Boolean.TRUE.equals(ready)) {
        dispatchTasks(); // 数据库已确认提交，Redis 解锁调用已完成。
    }
}
```

**辅助方法的必要职责**

- `tryAcquireRedisLock`：所有启动入口使用同一批次对应的锁键；原子完成“不存在才写入”、设置唯一 token 和 15 分钟过期时间。不能先写入再另设过期时间。确定未获取时返回空；通信异常或获取结果未知时结束本次启动，不进入数据库流程，并告警。
- `queryBatchState`：查询预先存在的批次记录；不存在则拒绝启动。普通查询结果只用于分支选择，最终启动资格由条件更新结果决定。
- `changeBatchToRunningIfStateMatches`：在当前事务中执行下节的条件 UPDATE，返回影响行数；本场景按主键最多更新一条记录。
- `initializePendingTasks`：拒绝残留任务，读取旧表最小、最大 ID，保存批次扫描范围，按 100 万 ID 跨度生成任务。每段不是保证有 100 万行；完整清单初始为待处理，确认进度为 NULL。检查范围、数量上限、算术溢出和写入结果，任务 ID 或范围唯一键保持稳定。旧表为空的规则仍待确认，当前按失败处理，不直接判为成功。
- `checkResumeConditions`：核对原任务清单完整，且不存在未处理失败、未知结果或残留处理中任务；不重新初始化、不重置进度。数据库检查不能替代运维确认旧线程和数据库操作已经结束。
- `releaseRedisLockIfOwned`：在 Redis 端原子比较 token 并删除。锁已过期或归别人持有时不删除；通信异常交由调用方告警核实。本示例中释放异常会阻止后续调度，数据库可能已经提交，不能据此重置状态或重新初始化。若启动与解锁同时失败，应在实际实现中保留原始异常和解锁异常，便于核实。
- `dispatchTasks`：仅调度待处理、已暂停任务；提交循环、任务入口和分页边界检查暂停信号。部分提交失败时停止新派发、告警并组织已接收任务安全收尾，不能放任已有任务继续而直接重启。

### 4.2 数据库条件更新与事务边界

```sql
UPDATE migration_batch
SET status = 'RUNNING'
WHERE id = ? AND status = ?;
-- 原状态只允许 NOT_STARTED 或 PAUSED。
-- 影响行数为 1 才继续初始化或恢复校验；否则结束，不调度。
```

首次启动时，条件更新、扫描范围保存和完整任务初始化都在同一个 InnoDB 事务、同一连接中完成。更新为运行中尚未提交时，不代表其他请求已经看到运行中；竞争更新会受数据库锁协调。一个请求成功提交后，另一个请求的原状态条件不再成立，因此不能继续初始化。若前一个请求回滚，后一个请求可能成功，仍须重新完成本次全部校验。

这是条件更新方式，不显式使用 `SELECT ... FOR UPDATE`，但 InnoDB 的 UPDATE 内部仍会加锁。Redis 锁减少并发进入，条件更新保护启动资格，事务保证多项写入原子性；这些职责不能全归因于 Redis 锁。任一写入或恢复校验失败，都应结束整个事务，不捕获异常后强行提交。

条件更新保护的是同一次状态转换，不是任意历史执行的永久凭证。如果运维在旧启动请求、工作线程或数据库操作尚未结束时把状态改回已暂停，旧请求仍可能干扰后续执行。因此必须先确认所有旧操作已结束，再恢复可启动状态；不能把 Redis 锁到期当作恢复依据。

### 4.3 15 分钟过期时间与主动释放

15 分钟等于 900 秒，作用对象是批次启动 Redis 锁，为本次已选配置，不是测得的耗时上限。正常路径确认数据库提交后立即释放，不等待 15 分钟，也不持锁到整轮迁移结束。进程宕机后，其他请求最长可能等待接近剩余过期时间才能重新竞争锁。

固定过期时间不能证明原请求已结束；线程停顿、数据库锁等待或网络故障都可能使操作超过预期。当前方案不依赖“绝不超过 15 分钟”保证数据库启动互斥，也未约定自动续期。实际客户端的租约、故障切换和释放行为仍需按选定版本验证。

### 4.4 提交失败、提交未知与恢复

- 初始化明确回滚：状态和新任务一起回滚，下次允许按未启动重新初始化。告警后先排查原因，当前设计不自动重试。
- 恢复校验失败：运行中状态更新回滚，保留已有任务和进度；告警并按异常待处理规则阻止反复启动。异常待处理状态如需持久化，应在原事务结束后按批次状态控制规则处理，不能假定回滚事务中的状态写入已保存。
- 提交响应丢失：不能假定回滚，不继续调度；运维核实数据库中的状态、任务清单和旧操作后处理。
- 提交后、解锁或调度前发生异常：运行中状态与任务清单可能已经提交，不能重新初始化或直接重置为未启动。
- Redis 解锁失败：不撤销已提交的数据库事务；按示例停止本次启动并告警，核实后恢复，不因 15 分钟到期就直接重跑。

恢复操作沿用 [暂停与故障恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/017_不停机数据迁移_在线历史迁移_批次状态控制_暂停与故障恢复.md>)。范围规划见 [任务范围划分](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/019_不停机数据迁移_在线历史迁移_任务范围划分.md>)；具体派发见 [线程池调度](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/020_不停机数据迁移_在线历史迁移_线程池调度.md>)。启动事务只保存任务计划，不扫描迁移全部业务数据，不等待 Future。

## 5 已确认规则

- 当前方案使用 Redis 锁保护启动准备，获取失败直接返回；过期时间为 15 分钟，正常事务提交后主动释放，不等待迁移完成。
- 数据库条件更新检查原状态，并检查影响行数；首次初始化、扫描边界保存与批次状态更新在同一事务中完成。
- 批次状态沿用未启动、运行中、已暂停；任务初始状态为待处理，不将批次和任务状态混用。
- 恢复启动沿用已有任务和进度，先完成旧执行结束及故障修复核实；确认提交后才调度。
- 锁获取与过期设置必须原子完成，释放时原子校验持有者；不将 15 分钟视为绝不失锁的保证。
- 代码只展示核心流程，使用匿名内部类，不使用 Lambda。
