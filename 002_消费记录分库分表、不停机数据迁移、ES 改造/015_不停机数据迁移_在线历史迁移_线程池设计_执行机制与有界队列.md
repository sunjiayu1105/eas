**什么是线程池，有什么好处**

线程池把任务提交和线程管理分开：调用方提交任务，由池中的工作线程执行；线程执行完任务后继续获取后续任务，而不是每个任务都新建一个线程。线程默认可以按需创建，并不要求启动时全部建好。这样能减少频繁创建、销毁线程的开销，在已有空闲线程时更快接手任务，还能集中管理并发、排队、拒绝和关闭。例如迁移有约 300 个范围任务，可以让少量线程重复执行，而不是同时启动 300 个线程。但只有合理设置线程数、队列和拒绝策略，才能限制资源占用；线程池本身不保证任务不丢失或数据线程安全。

**选择 ThreadPoolExecutor**

本题建议使用 Java 8 的 `ThreadPoolExecutor`，因为它能明确指定核心线程数、最大线程数、有界队列、线程工厂和拒绝策略。迁移任务需要限制并发、避免无限排队，并在任务无法提交时保留任务，所以不直接采用 `Executors` 的默认工厂配置。

**常用线程池**

`newFixedThreadPool` 适合固定并发，但默认无界队列；`newSingleThreadExecutor` 保证单线程顺序执行；`newCachedThreadPool` 按需创建线程，适合短任务，不能直接作为数据库迁移的并发上限；`newScheduledThreadPool` 用于延迟或周期任务；`ForkJoinPool` 适合可拆分的计算任务。前四项是 `Executors` 工厂方法，`ForkJoinPool` 是实现类；Java 8 也可用 `newWorkStealingPool` 创建工作窃取池。

**构造参数与示例取值**

这里选用七参数构造函数，需要核心线程数、最大线程数、空闲超时、时间单位、工作队列、线程工厂和拒绝策略。示例设置核心数和最大数都为 2，限制单进程最多执行两个范围任务；队列容量为 2，为两个工作线程暂存下一轮任务描述，限制积压；2 不是最优容量结论；空闲时间为 0 毫秒，因为不创建非核心线程，且默认不开启核心线程超时；使用自定义线程工厂便于命名和监控；使用 `AbortPolicy` 显式拒绝，调度方保留任务后再提交。2 个线程、2 个队列位置和 0 毫秒都是示例，实际值需压测。

**工作流程**

线程池运行时，工作线程数小于核心数就优先新建线程执行任务；达到核心数后先尝试入队，队列满后才尝试扩容到最大线程数，仍无法接收则执行拒绝策略。判断的是当前工作线程数，不是忙碌线程数。工作线程执行完当前任务后继续从队列取任务。线程池已关闭时不再接收新任务；成功入队后也会复查状态，处理与关闭并发发生的情况。

**如何确定线程池大小**

先区分任务是在做 CPU 计算还是等待 I/O。CPU 密集型从可用 CPU 核数附近试起；I/O 密集型可结合等待时间与计算时间估算候选并发，但不能机械套用两倍核数。迁移还受数据库连接预算、数据库承载能力和在线业务延迟约束，因此先用核心数和最大数均为 2 的示例基线，再在资源允许时对照 4 个线程。结合吞吐、连接等待和业务指标决定是否增加，生产取值仍需压测，多实例还要控制总并发。

**批间等待不是线程空闲超时**

每批完成并保存进度后休眠 100 毫秒属于任务内部限流，仍占用工作线程；`keepAliveTime` 默认只控制超出核心数的空闲线程。详见[详细方案](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/015_不停机数据迁移_在线历史迁移_线程池设计_执行机制与有界队列.md:39>)。

## 2 详细方案

### 2.1 线程池的定义、好处与实现类选择

**线程池是什么**

线程池是复用和管理一组工作线程的任务执行机制。调用方通过 `execute(Runnable)` 或 `submit(...)` 提交任务，工作线程执行任务并在完成后获取下一个任务。`submit` 返回 `Future`，可用于观察完成结果；获取结果和处理异常仍是调用方的责任。线程池并不等于提前创建好所有线程，也不是无限容纳任务的容器。

**使用线程池的好处**

- 复用线程，减少重复创建、销毁线程的开销。例如连续提交大量短任务时，已有工作线程可以反复执行它们。
- 减少启动等待：已有空闲线程可以直接接手任务；若任务已经排队，响应时间仍取决于前面任务的耗时，不能保证提交后立即执行。
- 集中限制资源：例如本篇配置最多两个工作线程、两个排队位置，避免每个范围任务各自启动线程；无界队列或过大的线程上限仍可能耗尽资源。
- 集中管理生命周期和执行状态：可以统一关闭线程池，观察活动线程数、排队数和完成任务数；监控采集、异常处理和任务恢复仍需要业务接入，不能由这些统计数证明数据迁移成功。

线程池不替代锁、幂等、事务或持久化机制。上述优势属于执行层管理，不意味着共享数据自动线程安全，也不意味着进程退出后队列中的任务能够恢复。

**为什么选择这个实现类**

Java 8 的 `ThreadPoolExecutor` 是可配置的线程池实现。迁移场景需要同时控制执行线程、等待任务数量和拒绝后的任务状态，因此直接构造它，避免把关键参数隐藏在工厂方法的默认值里。`Executors` 提供的工厂方法可以快速创建线程池，但例如 `newFixedThreadPool` 使用无界队列，任务持续提交时可能积压大量任务；这与本任务的有界排队要求不一致。

### 2.2 常用线程池与适用场景

共同点是复用工作线程执行任务；主要差别在于并发规模、排队方式和调度时机。`ExecutorService` 是任务提交与生命周期管理接口，`ThreadPoolExecutor` 和 `ForkJoinPool` 是实现类，`Executors` 是创建执行器的工厂类。

**固定线程池：** `Executors.newFixedThreadPool(n)` 创建固定数量的工作线程，适合并发度稳定的任务；Java 8 中底层为核心数和最大数均为 n 的 `ThreadPoolExecutor`，默认使用未指定容量的 `LinkedBlockingQueue`，容量为 `Integer.MAX_VALUE`，通常称为无界队列，不能满足本迁移的小容量排队要求。

**单线程执行器：** `Executors.newSingleThreadExecutor()` 使用一个工作线程和同样的无界队列，任务串行执行；多个调用方并发提交时不能据此推断业务先后。适合需要串行处理的任务，但不能替代多实例的全局并发控制。其包装器限制重新配置，与可调整的固定池有区别。

**缓存线程池：** `Executors.newCachedThreadPool()` 底层核心数为 0、最大数为 `Integer.MAX_VALUE`，采用不存储任务的 `SynchronousQueue` 直接交接，空闲线程超过 60 秒被回收。这是 Java 8 工厂配置，不是项目参数。它适合提交规模受控的短任务；数据库变慢时仍可能继续创建大量线程，因此不采用它控制本迁移并发。

**定时线程池：** `Executors.newScheduledThreadPool(n)` 底层是 `ScheduledThreadPoolExecutor`，核心线程数为 n，使用无界延迟队列；设置很大的最大线程数不会获得普通有界池那样的扩容效果。适合延迟或周期任务，例如定时触发扫描。它能直接执行任务；若将耗时迁移交给独立工作池，仍需分别限制工作池并发与排队。

**单线程定时执行器：** `Executors.newSingleThreadScheduledExecutor()` 使用一个工作线程执行延迟或周期任务，并通过包装器限制重新配置。适合需要串行调度的任务；长时间运行的任务可能推迟其他任务的执行，不能保证准点启动。

**ForkJoinPool：** Java 8 的 `ForkJoinPool` 通过工作窃取让空闲线程获取其他线程的任务，适合可拆分的计算任务。`Executors.newWorkStealingPool(p)` 设置目标并行度 p；无参方法默认使用可用处理器数，目标并行度不等同于数据库访问的严格上限。阻塞 JDBC 也不能假定会自动得到有效补偿，因此本方案不以它控制迁移并发。

上述工厂方法和实现类服务于不同任务模型，并非一律不能使用。本方案直接构造 `ThreadPoolExecutor`，是为了显式满足并发与有界排队需求。来源：[Executors Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Executors.html)、[ForkJoinPool Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ForkJoinPool.html)。

### 2.3 ThreadPoolExecutor 构造参数及示例取值

构造函数的参数依次是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory` 和 `handler`。

| 参数 | 作用 | 本文示例与原因 |
| --- | --- | --- |
| `corePoolSize` | 核心线程数；线程数不足时优先创建，默认按需创建且不因空闲超时退出 | 2：同时处理两个范围任务；只是单进程示例 |
| `maximumPoolSize` | 核心线程忙且队列满后允许达到的最大线程数 | 2：与核心数相同，把并发上限固定为 2，避免队列满后扩容 |
| `keepAliveTime` | 非核心空闲线程被回收前的等待时间 | 0 毫秒：当前核心数等于最大数，没有非核心线程；不是批间等待 |
| `unit` | 空闲时间的单位 | `TimeUnit.MILLISECONDS`，使 0 毫秒表达明确 |
| `workQueue` | 暂存尚未执行的任务 | `ArrayBlockingQueue<>(2)`：只保存两个任务描述，形成有界排队 |
| `threadFactory` | 创建线程并设置名称、优先级等属性 | 示例可用自定义工厂命名迁移线程，便于日志和监控；不能改变并发上限 |
| `handler` | 饱和或关闭等导致无法接收任务时的处理策略 | `AbortPolicy` 抛出拒绝异常，调度方保留任务并稍后重试，避免静默丢失 |

两个线程和两个排队位置限制的是当前进程；多实例总并发仍由 019 的跨实例调度规则控制。队列只放范围任务描述，不能预读整个范围数据；每批 500—1000 条和 100 毫秒批间等待是参考或示例值，分别由性能调优和限流文档维护。

~~~java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public final class MigrationPoolExample {
    public static ThreadPoolExecutor createPool() {
        int workers = 2;       // 示例值，实际并发须压测
        int queueCapacity = 2; // 暂存任务描述，不保存整个范围的数据
        AtomicInteger sequence = new AtomicInteger();
        ThreadFactory defaults = Executors.defaultThreadFactory();
        ThreadFactory factory = task -> {
            Thread thread = defaults.newThread(task);
            thread.setName("migration-worker-" + sequence.incrementAndGet());
            return thread; // 保留默认的非守护线程和普通优先级
        };
        return new ThreadPoolExecutor(
            workers, workers, 0L, TimeUnit.MILLISECONDS,
            new ArrayBlockingQueue<Runnable>(queueCapacity),
            factory,
            new ThreadPoolExecutor.AbortPolicy()
        );
    }
}
~~~

**为什么固定为两个线程**

核心数和最大数相等，使队列满时不会再扩容，从而将该池的同时执行数固定在 2 以内。2 沿用当前迁移方案的演示基线，不是由约 300 个任务计算出来的最优值。例如数据库负载上升时，排队任务不能靠新增线程继续冲击数据库；正式取值需要结合连接预算和压测，方法由 [013 性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_性能调优.md>) 维护。

**为什么队列也是两个位置**

示例让两个执行中的任务之外，再暂存下一轮两个任务描述，既允许少量调度缓冲，又让积压尽早反馈给调度方。容量 2 只是解释这组运行与排队关系，不代表队列必须等于线程数，也不保证最优吞吐。`ArrayBlockingQueue` 是固定容量数组队列；显式指定容量的 `LinkedBlockingQueue` 也可以实现有界排队。构造时指定容量并不意味着提交方会自动阻塞等待：普通 `execute` 尝试非阻塞入队，满后按扩容与拒绝规则处理。

**为什么空闲时间为零**

本例最大数等于核心数，且未调用 `allowCoreThreadTimeOut(true)`，没有非核心线程需要按空闲时间回收，因此 0 毫秒不会导致核心线程立即退出。毫秒只是时间单位；改用其他单位表示零也没有不同效果。若要允许核心线程超时，必须设置正的空闲时间。本参数不控制任务执行超时或 JDBC 超时。

**为什么命名线程并显式拒绝**

自定义工厂在默认工厂基础上追加递增编号，便于在日志和线程栈中区分工作线程；多个线程使用同一个名字不利于排查。命名不等于已经接入监控，异常结果仍需按 017 的规则观察。默认非守护线程需要应用显式管理关闭，停止协议由 018 维护。

`AbortPolicy` 抛出 `RejectedExecutionException`，使调度方明确知道任务未被接受；单靠抛出异常不会可靠保存任务，必须由调度方保留任务并安排后续提交。示例不采用让提交线程执行任务的策略，以免出现两个工作线程之外的执行者。完整策略比较和状态处理见 [016 拒绝策略与任务保留](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_线程池设计_拒绝策略与任务保留.md>)。

代码仅创建线程池，不包含调度、任务持久化、异常上报和关闭流程；生产参数尚未确认。此前使用本机 JDK 8u151 编译通过，本轮未修改代码，未运行迁移任务，也未验证数据库负载或关闭恢复效果。

### 2.4 ThreadPoolExecutor 的完整工作流程

以下描述 Java 8 普通任务提交的执行路径。核心线程默认按需创建，构造线程池并不等于已经启动两个线程。示例中核心数与最大数相同，因此不会创建超出两个工作线程的非核心线程。

**任务接收与执行顺序**

1. 检查当前工作线程数；少于 `corePoolSize` 时，尝试新建线程并直接执行本次任务，即使已有线程空闲也可能继续创建核心线程。创建失败时还会继续尝试后续接收路径，不能把“少于核心数”理解为必然创建成功。
2. 未通过上一步接收时，在线程池仍运行的前提下尝试非阻塞入队。普通 `execute` 不会因为有界队列已满而自动阻塞等待空位。
3. 入队成功后复查状态：若线程池已关闭且能移除该任务，就执行拒绝策略；若任务仍应执行但当前没有工作线程，则尝试补建工作线程。
4. 无法入队时，尝试在最大线程数约束内创建线程直接执行任务；若状态或容量等条件不允许，则调用拒绝处理器。已关闭的线程池拒绝新提交的任务，未必先走完扩容过程。
5. 工作线程执行任务，随后循环获取队列任务。默认情况下，超出核心数的空闲工作线程按 `keepAliveTime` 超时退出；核心线程默认持续等待，允许核心线程超时后则按相应规则退出。核心与非核心是数量管理概念，不是给具体线程永久贴标签。

默认拒绝策略是 `AbortPolicy`；本文仍显式传入以突出任务保留责任。`shutdown()` 停止接收新任务，但允许已接收任务继续处理；`shutdownNow()` 尝试中断正在执行的任务并返回尚未执行的排队任务，不保证任务一定立即停止。具体停机和恢复协议由 018 维护。

**容易混淆的配置关系**

采用无界队列时，达到核心数后通常一直入队，单纯调大 `maximumPoolSize` 不能解决积压。采用 `SynchronousQueue` 时没有任务存储空间，无法直接交接便会尝试创建线程，所以必须特别关注线程数上限。提交顺序也不等于执行或完成顺序：队列满后新建的线程可以直接执行新任务，先前排队的任务可能稍后才执行。

来源：[ThreadPoolExecutor Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html) 的核心/最大线程数、排队、空闲回收和拒绝策略说明。

### 2.5 示例：运行数与排队数分开

以下假设线程创建成功、线程池保持运行，且 A、B 在提交 C、D、E 时尚未结束。

1. A、B 分别由两个工作线程执行。

2. C、D 的任务描述进入队列，不提前读取整个主键范围。

3. E 再提交时触发 `AbortPolicy`。两个运行任务不计入队列容量，调度方必须保留 E 的状态。

每个范围任务平均约 100 万条有效记录，执行时按每批 500—1000 条参考目标读取，不能一次加载整个范围。100 毫秒批间休眠须由任务内部另行执行，线程空闲超时不承担这个限流职责。

### 2.6 如何设置线程池大小

**先看任务类型，再估算候选值**

线程池大小通常指工作线程数量；对可伸缩池必须同时说明核心数和最大数，队列容量另算。`Runtime.getRuntime().availableProcessors()` 可作为 JVM 看到的可用处理器数起点；还要结合部署 CPU 配额及同进程其他工作负载核实实际可用算力，不能直接把宿主机核数全部分给迁移。

**CPU 密集型：** 主要耗时在计算，过多线程会增加上下文切换。可从分配给任务的 CPU 核数附近开始压测；常见的 N 或 N+1 只是候选经验值。例如假设可独占 4 个核，可分别测试核心数和最大数均为 4、均为 5 的固定池，不代表 5 一定更快。

**I/O 密集型：** 工作线程经常等待网络或磁盘，可以适当增加线程来覆盖等待。粗略候选公式为 `线程数 ≈ N × U × (1 + W/C)`，N 是实际可用核数，U 是目标 CPU 利用率（0 到 1），W 是单个任务的平均等待时间，C 是同一任务的平均 CPU 计算时间；W、C 使用相同单位且 C 必须大于 0。公式假设任务特征相对稳定、等待期间其他任务可运行，只是估算，不是 JDK 的自动配置规则，也不能描述下游饱和后不断增长的等待。

例如假设 N=4、U=0.75、W=30 毫秒、C=10 毫秒，估算为 12 个线程，可作为核心数和最大数均为 12 的固定池候选，再接受下游容量约束。数字仅演示计算，不能当成本项目配置；“I/O 密集型固定取 2N”没有普遍成立的依据。

**迁移场景必须叠加数据库预算**

数据库迁移包含 JDBC 等待，但数据库连接数、CPU、磁盘、锁竞争和在线业务预留往往比应用 CPU 更早成为瓶颈。增加线程可能只增加连接等待，无法增加吞吐。应分别统计源库和各目标库可分配给迁移的连接预算、单任务最大同时持有连接数以及多实例总并发，不能假设一个线程始终只持有一个连接。

举例：假设某一连接池扣除在线业务和安全余量后，可分配给迁移 8 个连接，每个任务在该池最多同时持有 2 个连接，则单从这个连接池约束看，同时运行的迁移任务不能超过 `floor(8/2)=4`。这只是连接预算上限，不代表数据库能承受 4 个任务；其他连接池、数据库负载或多实例共享预算可能要求更低并发。上述 8、2、4 均为解释预算的假设值。

**把候选值落实为验证步骤**

当前示例仍保留 `corePoolSize=maximumPoolSize=2`、队列容量 2。在数据库与连接预算允许时，可以对照核心数和最大数均为 4 的候选组，保持其他变量一致，观察吞吐、任务耗时、队列等待、连接等待、数据库负载以及在线业务延迟和错误率。达到业务验收阈值前就应停止加并发；吞吐没有明显提升或业务指标恶化时退回较低配置。具体阈值尚未确认。

批间休眠虽然增加工作线程的等待时间，却是主动限流措施，不能机械代入公式后增加线程把限流效果抵消。长时间运行的范围任务也不能按约 300 个任务总数直接设置线程数。若采用核心数小于最大数的伸缩池，还必须同时评估队列容量：它决定何时触发扩容，不能只调整最大线程数。

本节应用户要求补充通用面试回答和预算示例；项目容量实验、最终参数及指标验收仍由 [013 性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_性能调优.md>) 统一维护。估算式是基于 CPU 计算占比的容量近似分析，不是 Java API 的性能保证；本文没有实测 W/C 或生产容量数据。
