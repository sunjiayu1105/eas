## 2 详细方案

### 2.1 为什么选择 ThreadPoolExecutor

线程池把任务提交和工作线程管理分开。工作线程执行完一个范围任务后，可以继续取得下一个任务，避免为约 300 个范围任务各创建一个线程。

Java 8 的 `ThreadPoolExecutor` 可以显式配置核心线程数、最大线程数、有界队列、线程工厂和拒绝策略。迁移需要限制并发、限制排队长度，并在任务无法提交时保留任务，因此不直接使用 `Executors.newFixedThreadPool` 的默认无界队列。

线程池只负责执行层的并发和生命周期管理，不能代替进度持久化、幂等、事务或多实例任务领取。

### 2.2 常用线程池的取舍

共同点是复用工作线程执行任务；差别在于线程数量、排队方式和调度时机。

**固定线程池：** `newFixedThreadPool(n)` 固定线程数，但默认使用无界 `LinkedBlockingQueue`，不适合本迁移的有界排队要求。

**单线程执行器：** `newSingleThreadExecutor()` 串行执行，适合必须单线程处理的任务，但不能替代多实例的全局并发控制。

**缓存线程池：** `newCachedThreadPool()` 可能持续创建线程，数据库变慢时不适合作为迁移并发上限。

**定时线程池：** `newScheduledThreadPool(n)` 适合延迟或周期触发；耗时迁移仍应交给独立工作池。

**ForkJoinPool：** 适合可拆分的计算任务；阻塞 JDBC 场景不能把目标并行度当作数据库访问上限。

因此本方案直接构造 `ThreadPoolExecutor`。来源：[Executors Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Executors.html) 和 [ForkJoinPool Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ForkJoinPool.html)。

### 2.3 构造参数与示例取值

构造函数参数依次是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、时间单位、工作队列、线程工厂和拒绝策略。

| 参数 | 作用 | 示例值及状态 |
| --- | --- | --- |
| `corePoolSize` | 核心线程数 | 2，同时处理两个范围任务；示例值 |
| `maximumPoolSize` | 最大线程数 | 2，与核心数相同，固定单进程并发；示例值 |
| `keepAliveTime` | 非核心线程空闲回收时间 | 0 毫秒；当前没有非核心线程；示例值 |
| `workQueue` | 暂存未执行任务 | `ArrayBlockingQueue<>(2)`，只存任务描述；示例值 |
| `threadFactory` | 创建并命名线程 | 自定义名称便于日志排查；设计建议 |
| `handler` | 线程池无法接收任务时的处理 | `AbortPolicy` 显式拒绝；设计建议 |

两个线程和两个排队位置只限制当前进程。多实例总并发由 [019 多实例任务领取与全局并发](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/019_不停机数据迁移_在线历史迁移_多实例任务领取与全局并发.md>) 处理；线程数和数据库承载能力由 013 通过压测确定。

队列只保存范围、进度位置等任务描述，不能预读整个范围的数据。每批 500—1000 条和 100 毫秒批间等待属于限流或性能文档的参考值，不由本篇确定。

```java
int workers = 2;       // 示例值，实际取值需压测
int queueCapacity = 2; // 只保存任务描述
ThreadFactory factory = Executors.defaultThreadFactory();

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    workers,
    workers,
    0L,
    TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<Runnable>(queueCapacity),
    factory,
    new ThreadPoolExecutor.AbortPolicy()
);
```

代码只说明线程池构造方式，不包含调度、进度持久化、异常上报和关闭流程。

### 2.4 任务提交和执行顺序

1. 当前工作线程数少于 `corePoolSize` 时，线程池尝试创建工作线程直接执行任务。
2. 达到核心线程数后，`execute` 尝试把任务描述放入有界队列；队列满时不会自动等待。
3. 入队成功后，任务等待工作线程取出执行；提交成功不等于任务完成。
4. 队列已满时，线程池尝试在 `maximumPoolSize` 范围内创建线程；本例核心数等于最大数，因此不会扩容。
5. 仍无法接收任务时执行 `AbortPolicy`，由调度方捕获拒绝异常并保留任务。
6. 工作线程执行完成后继续从队列取任务，任务内部按批读取、写入、核实结果并保存进度。

线程池关闭后不再接收新任务；`shutdown()` 允许已接收任务继续执行，`shutdownNow()` 只尝试中断并返回尚未执行的任务。安全停止和结果确认由 [018 安全停止与降低并发](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/018_不停机数据迁移_在线历史迁移_线程池设计_安全停止与降低并发.md>) 展开。

### 2.5 示例：运行任务、排队任务和被拒任务

假设线程池有 2 个工作线程、队列容量为 2，且 A、B 尚未结束：

1. A、B 分别由两个工作线程执行。
2. C、D 的任务描述进入队列，尚未读取整段数据。
3. E 提交时队列已满，触发 `AbortPolicy`。
4. 调度方把 E 保留为待调度状态，等容量恢复后重新提交。
5. A 或 B 完成并取走下一个任务后，队列出现空位；重新提交仍需捕获并发关闭造成的拒绝。

每个范围任务平均约 100 万条有效记录，具体单批范围和批间等待由限流、性能调优文档维护。提交次数、队列空闲和活动线程数都不能单独证明迁移完成；完成状态还要结合批次结果和进度记录判断。
