# 017_不停机数据迁移_在线历史迁移_线程池_执行机制

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。具体实现和运行效果尚未验证。

## 1 问题

线程池如何提交、排队、拒绝和执行迁移任务？

## 2 面试口述精炼版本

口述内容字符数：226

**任务只在执行时读取数据**

调度方提交互不重叠的范围任务，队列只保存范围和进度描述。线程数达到核心数后先入有界队列，队列满再按最大线程数和拒绝策略处理。

**拒绝和异常不能丢失**

拒绝任务由调度方保留并重新提交，不能记为完成。execute 的异常要记录，submit 返回 Future，可通过 get 获取结果和异常；数据库超时或结果未知时不推进进度。

**停止要有边界**

先停止派发，再让任务在批次边界保存结果并退出；shutdownNow 只是中断请求，不能证明数据库操作已经结束。

## 3 详细方案

### 3.1 任务提交和执行顺序

1. 当前工作线程数少于核心线程数时，线程池尝试创建工作线程直接执行任务。
2. 达到核心线程数后，`execute` 尝试把任务描述放入有界队列；队列满时不会自动等待。
3. 入队成功后仍会复查关闭状态：若已关闭且能移除任务则拒绝；若没有工作线程则尝试补建线程。被接收不等于迁移完成。
4. 队列已满时，线程池尝试在最大线程数范围内创建线程；本方案示例核心数等于最大数，因此不会扩容。
5. 仍无法接收任务时执行拒绝策略，由调度方捕获异常并保留任务。
6. 工作线程完成当前任务后继续从队列取任务，任务内部按批读取、写入、核实结果并保存进度。

线程池类型选择依据见 [019 线程池类型选择](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/019_不停机数据迁移_在线历史迁移_线程池设计_线程池类型选择.md>)；拒绝后的任务状态见 [021 拒绝策略与任务保留](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/021_不停机数据迁移_在线历史迁移_线程池设计_执行机制.md:52>)。

执行路径依据：[ThreadPoolExecutor Java 8 API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)。本次为静态文档核对，未运行线程池或迁移任务。

### 3.2 示例：运行、排队和被拒任务

假设核心数和最大数均为 2、队列容量为 2，使用 AbortPolicy，且 A、B 尚未结束：

1. A、B 分别由两个工作线程执行。
2. C、D 的任务描述进入队列，尚未读取整段数据。
3. E 提交时队列已满，触发拒绝策略。
4. 调度方把 E 保留为待调度状态，等容量恢复后重新提交。
5. A 或 B 完成并取走下一个任务后，队列出现空位；重新提交仍需捕获线程池关闭等变化或其他提交者抢占空位造成的拒绝。

每个范围任务按平均约 100 万条有效记录规划。任务内部按批处理，500—1000 条为参考调参范围，批间等待 100 毫秒为设计示例，具体取值待压测。活动线程数、队列空闲和提交次数都不能单独证明迁移完成。

### 3.3 拒绝必须反馈到任务状态

建议采用 AbortPolicy，捕获 RejectedExecutionException。未接收任务不能标记完成，也不能永久停留在“处理中”。持久化任务定义和进度提供恢复依据，内存 Runnable 队列不能代替可靠存储；具体存储方案尚未确定。

可在完成通知到达后再次尝试提交；检查剩余容量与提交之间状态可能变化，因此仍需捕获拒绝异常。线程池关闭时停止提交，不能无限重试。

### 3.4 策略取舍

**共同目标**

拒绝策略决定无法接收任务时如何处理，可靠保存仍由调度方负责。

**AbortPolicy：**显式抛出异常，便于调度方按任务状态处理。

**CallerRunsPolicy：**线程池未关闭时可能直接在提交线程执行任务，例如两个工作线程再加一个提交线程形成三个执行者；线程池关闭时不会执行被拒任务。

**静默丢弃策略：**提交方可能不知道任务未执行，不适合作为本设计的默认策略。

### 3.5 两种提交方式都要记录失败

本篇沿用核心数和最大数均为 2 的固定线程池示例；线程数不改变异常与结果的确认要求，实际配置待压测。

execute 中未捕获的运行时异常会使任务异常退出，需要在任务边界记录任务编号、范围与原因，不能只依赖控制台输出。

ThreadPoolExecutor 的 submit 将任务包装为 FutureTask，执行异常保存在 Future 中。为保留并发，不应每提交一个任务就立即阻塞等待 get；可统一收集 Future，或用 CompletionService 按完成顺序处理结果。Future.get 抛出 ExecutionException 时检查原因并记录失败；调用 get 的线程被中断是另一种情况，不能混为任务执行失败。任务内部吞掉异常后，Future 正常返回也不能证明业务成功。

### 3.6 示例：Future 已结束但执行失败

1. 调度方 submit 提交 A，提交返回正常。

2. A 的数据库操作抛出异常，Future 保存异常。

3. 调度方观察执行结果，记录失败，保留恢复位置并上报。

4. 不能只看提交次数或 Future.isDone；isDone 同时包含正常、异常和取消等结束状态。

### 3.7 超时不直接等于回滚

超时可能发生在发送前、执行中或提交响应返回时。具体异常与事务结果需核实。未知结果时不推进进度，按恢复机制重新判断。工作线程应报告失败或结果未确认，不能把吞掉异常后的正常返回当作范围成功。JDBC 超时与在途操作收尾见 [021 执行机制：安全停止](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/021_不停机数据迁移_在线历史迁移_线程池设计_执行机制.md:92>)；恢复位置见 [023 断点续跑](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/023_不停机数据迁移_在线历史迁移_断点续跑.md>)，重试分类、次数和退避参数由 [024 重试幂等](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/024_不停机数据迁移_在线历史迁移_重试幂等.md>) 维护。

### 3.8 停止接收与停止执行分开

先停止派发，再设置线程间可见的停止标志，例如 volatile 或 AtomicBoolean。任务开始和下一批开始前检查标志；当前批次成功则保存进度后退出，失败或结果未知则保留原进度，不强行等到“成功”才允许退出。

shutdown 后排队任务仍可能执行，因此被取出的任务也需检查停止信号。shutdownNow 尝试中断运行任务并返回未开始任务；这些任务仍需保留可恢复状态。

### 3.9 示例：两个线程降为一个

1. 停止派发，通知原任务在批次边界退出。

2. 核实已确认进度，保留未开始与未完成范围。

3. 确认旧线程池终止，核实无遗留在途写入或未决提交结果。

4. 用 1 个线程恢复，2→1 只是交接示例，不是既定配置。

只停止派发不会立即降低已有并发；仅退出一个任务，空闲线程仍可能领取排队任务。此方案采用暂停后恢复，不声称已实现在线无停顿调节。

### 3.10 超时后的边界

中断不保证 JDBC 请求停止；线程池终止也不能单独证明远端没有未决事务。等待超过预期时需核实数据库结果并告警，不能立即启动重叠执行者。恢复前核实最后持久化位置与范围状态，不能因工作线程方法结束就认为在途操作已收尾。实际等待上限、JDBC 超时和停止协议仍待确认，不填无依据的生产值。
