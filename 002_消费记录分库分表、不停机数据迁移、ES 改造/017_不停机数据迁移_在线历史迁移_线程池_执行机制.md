# 017_不停机数据迁移_在线历史迁移_线程池_执行机制

问题：线程池如何提交、排队、拒绝和执行迁移任务？

以下内容按照当前项目 AGENTS.md 项目级规则为准，使用 Java 8。本文为设计分析，示例未运行验证。

## 1 面试口述精炼版本

口述内容字符数：278

**任务只在执行时读取数据**

调度方提交互不重叠的范围任务，队列只保存范围和进度描述。线程数达到核心数后先入有界队列，队列满再按最大线程数和拒绝策略处理。

**拒绝和异常不能丢失**

拒绝任务由调度方保留并重新提交，不能记为完成。execute 的异常要记录，submit 要通过 Future.get 检查；数据库超时或结果未知时不推进进度。

**停止要有边界**

先停止派发，再让任务在批次边界保存结果并退出；shutdownNow 只是中断请求，不能证明数据库操作已经结束。

## 2 详细方案

### 2.1 提交顺序

工作线程不足时直接执行；达到核心线程数后进入有界队列；队列满时尝试扩展到最大线程数；仍无法接收则触发拒绝策略。提交成功只代表线程池接收任务，不代表迁移成功。

### 2.2 拒绝与异常

建议显式使用 AbortPolicy，捕获 RejectedExecutionException 后把范围保留为待调度。不能使用静默丢弃策略。submit 返回的 Future 必须调用 get 检查 ExecutionException；任务内部吞掉异常时，Future 正常返回也不能证明数据库成功。

### 2.3 安全停止

停止派发后，任务在开始和批次边界检查停止信号。当前批次成功则保存进度后退出；失败或结果未知保留原进度。恢复前核实最后进度和在途数据库操作，不能只看线程已退出。

### 2.4 示例

1. 两个工作线程正在执行 A、B，队列容量为 2，C、D 排队。

2. E 提交时触发拒绝，调度方保留 E。

3. A 完成并取走 C 后，调度方再次提交 E；仍需捕获关闭或竞争造成的再次拒绝。

4. 若数据库超时，E 不记为完成，恢复时按断点和幂等规则核实。

## 3 已确认规则

- 拒绝、异常、停止和结果未知必须反馈给调度方。
- 队列只保存任务描述，不能代替进度存储。
- 具体停止协议和异常核实尚未验证。
