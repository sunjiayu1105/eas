## 1 问题

如何只用数据库行锁和状态防止批次重复启动，并保证初始化完整提交？

## 2 高级 Java 面试核心考点

- 行锁与持久化状态：短事务内串行检查，提交后由状态阻止重复启动。
- 事务原子性：边界、完整清单和运行中状态一起提交。
- 故障窗口：明确回滚、提交未知和提交后宕机分别处理。

## 4 详细方案

### 4.1 启动检查

启动接口采用数据库行锁和批次状态控制，不使用 Redis 锁。这里要区分两种启动场景：首次启动时，状态检查、任务初始化和批次状态改为运行中必须放在同一事务中；暂停后恢复时，任务清单已经存在，只需在事务中锁定批次、检查状态并原子地改为运行中，不重新初始化任务。行锁可直接配合这两种事务边界；选择依据与 Redis 锁的协调边界见 [为什么选择数据库行锁](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/015_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_为什么选择数据库行锁.md>)。批次信息表中的控制记录必须事先存在，所有启动入口都通过主键锁定同一条记录；记录不存在时拒绝启动，不能继续生成任务。使用 `SELECT ... FOR UPDATE` 在事务内锁定记录，串行完成状态检查与变更；锁定读取、其他查询受到的影响和锁的释放时机，见 [SELECT FOR UPDATE 如何加锁与释放锁](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/016_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_SELECT_FOR_UPDATE如何加锁与释放锁.md>)。拿到锁后读取并检查最新批次状态；只允许未启动或已暂停进入初始化或恢复流程。处于运行中、暂停中、已完成或异常待处理时直接结束启动流程，不提交任务。

1. 对允许启动的批次，核实上一次迁移是否已经安全结束；无法确认之前的线程和数据库操作已停止时，进入异常待处理，不启动新实例。人工核实在启动前完成，不能持有数据库行锁等待运维排查。
2. 检查失败任务、结果未知和任务表中的处理中任务。发现未修复失败或未核实结果时进入异常待处理，阻止启动。服务器宕机可能留下处理中状态，不能直接把它当作可执行任务；先由运维确认上一次迁移的线程、进程、事务和数据库操作已经停止，并核实未知写入。

批次状态与按钮见 [批次状态与操作控制](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/012_不停机数据迁移_在线历史迁移_批次状态控制.md>)。恢复核实流程见 [暂停与故障恢复](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/017_不停机数据迁移_在线历史迁移_批次状态控制_暂停与故障恢复.md>)，本节只检查其结果及是否允许启动。

### 4.2 初始化事务与故障窗口

**初始化与状态转换必须一起提交**

批次初始状态为“未启动”，任务初始状态称“待处理”，不混用两个层级。任务数量由 ID 跨度计算，清单只写范围等信息，可以考虑在一个短事务内完成以下操作；事务容量、锁等待和实际耗时仍需验证。

1. 开启数据库事务，按批次主键执行 SELECT ... FOR UPDATE，锁定已有的批次记录并检查状态。首次启动时，锁定查询、状态检查与任务初始化必须处于同一事务，不能检查后先释放锁、再另开事务初始化；恢复启动不再初始化任务，只需在同一事务中完成状态检查和状态更新。
2. 批次状态为未启动时，将整个批次的扫描上下界写入批次信息表，将完整任务清单写入任务表。各任务保存自己的扫描范围，状态为待处理、确认进度为 NULL，并核对范围和计划数量。
3. 在同一事务中将批次信息表中的批次状态改为运行中，然后提交并释放行锁。
4. 确认提交成功后，才查询任务并向线程池提交。行锁只覆盖启动事务，不持有到迁移完成；事务中不执行数据迁移，也不等待 Future。

批次信息表中的状态、扫描上下界与任务表中的完整任务清单必须在同一数据库事务中保存，使用支持事务的存储引擎。任务表需有唯一约束防止重复写入，任务 ID 或范围唯一键必须稳定，不能每次生成新 ID 就认为能够防重。范围计算如需昂贵扫描，应在事务外规划，并在事务中核对并保存同一份边界，避免长期占用控制记录锁。

由此保证：批次正常离开未启动状态时，完整任务清单已可靠保存。初始化明确回滚时，状态仍为未启动，下次可重新初始化；事务已提交但进程在提交线程池前宕机时，清单完整、状态为运行中，须确认上一次迁移的线程和数据库操作已结束后恢复，不能再次初始化。提交响应丢失时先查询核实事务结果，不直接重试初始化，也不贸然启动线程池。

例如计划 300 个任务（教学示例），插入第 100 个时失败：事务回滚，不能留下部分清单却显示运行中。如果约束被人工修数或旧实现破坏，应停止启动并核对清单，不能仅凭状态跳过检查。首次初始化失败且已确认回滚时，不应将批次永久改成代表初始化完成的状态；告警通过日志报告。

再次启动已暂停的批次时，在同一启动互斥保护下，仅将批次状态原子改为运行中，复用原任务清单和各任务进度。检查与状态转换不能被其他启动请求穿插；未确认状态转换成功，不得提交任务。

**释放行锁后仍能防止重复启动**

例如请求 A 锁定批次记录时，请求 B 等待。A 将批次改为运行中并提交后，B 才能获得行锁；B 读取到运行中就退出，不再提交任务。行锁保证检查和状态变更不会并发交错，提交后的运行中状态阻止后续请求重复启动。只有安全收尾后才允许将批次恢复为可启动状态。

本方案使用支持事务与行锁的 InnoDB 表，锁定读取、初始化和状态更新必须使用同一数据库事务与连接，不能在自动提交模式下单独执行锁定查询。锁等待超时或发生死锁时，启动流程回滚整个事务并返回失败；不能绕过锁继续提交任务。具体锁等待及事务超时配置待验证。

### 4.4 核心代码：事务提交后再提交任务

以下使用 Spring JDBC 的 `JdbcTemplate` 和 `TransactionTemplate` 展示核心控制流程，不依赖 MyBatis 或 JPA，也不表示项目已采用 Spring JDBC。示例需引入与 Spring Boot 2.7.18 配套的 JDBC 依赖；批次表和任务表都使用 InnoDB，并通过同一 DataSource 参与同一个本地事务；事务内的查询和写入必须使用同一连接。表名、状态枚举字符串及批次主键 `1` 均为教学示意。

代码分成两段：`tx.execute` 内完成加锁、检查、初始化或恢复以及更新状态；它正常返回后，才调用调度器。启动入口禁止加入外层事务，避免事务模板返回时外层事务尚未提交，就提前执行迁移。运维已经核实上次执行结束、修复未知结果，才允许将批次恢复为已暂停；代码不能仅凭任务状态代替人工核实。

```java
import java.util.List;
import java.util.Objects;
import javax.sql.DataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.transaction.support.TransactionSynchronizationManager;
import org.springframework.transaction.support.TransactionTemplate;

public final class MigrationStarter {
    private static final long BATCH_ID = 1L; // 所有入口使用同一控制记录。
    private static final long ID_SPAN = 1_000_000L; // 已确认的 ID 跨度，不是行数。
    private final JdbcTemplate jdbc;
    private final TransactionTemplate tx;
    private final Dispatcher dispatcher;
    private final int maxTasks; // 初始化任务数上限，由资源预算配置，不是生产固定值。

    public MigrationStarter(DataSource dataSource, Dispatcher dispatcher,
                            int maxTasks) {
        if (maxTasks <= 0) throw new IllegalArgumentException("maxTasks 必须为正数");
        this.jdbc = new JdbcTemplate(dataSource);
        this.tx = new TransactionTemplate(
                new DataSourceTransactionManager(dataSource));
        this.dispatcher = Objects.requireNonNull(dispatcher, "dispatcher 不能为空");
        this.maxTasks = maxTasks;
    }

    public void start() {
        // 本入口不加 @Transactional，也不允许事务方法间接调用它。
        if (TransactionSynchronizationManager.isActualTransactionActive()) {
            throw new IllegalStateException("启动入口不能处于外层事务中");
        }
        Boolean ready = tx.execute(transaction -> {
            List<String> states = jdbc.query(
                    "SELECT status FROM migration_batch WHERE id = ? FOR UPDATE",
                    (rs, rowNum) -> rs.getString(1), BATCH_ID);
            if (states.size() != 1) {
                throw new IllegalStateException("批次控制记录必须预先存在");
            }
            String state = states.get(0);
            if ("NOT_STARTED".equals(state)) {
                initializeTasks();
            } else if ("PAUSED".equals(state)) {
                // 不再查询旧表边界、不重新插入任务、不重置进度。
                if (!hasResumableTasks()) {
                    if (jdbc.update("UPDATE migration_batch SET status = 'NEEDS_ATTENTION' "
                            + "WHERE id = ? AND status = 'PAUSED'", BATCH_ID) != 1) {
                        throw new IllegalStateException("异常状态保存失败");
                    }
                    return false; // 正常提交异常状态；不能抛异常把这次更新回滚掉。
                }
            } else {
                throw new IllegalStateException("当前批次状态不允许启动：" + state);
            }
            int changed = jdbc.update(
                    "UPDATE migration_batch SET status = 'RUNNING' "
                            + "WHERE id = ? AND status = ?", BATCH_ID, state);
            if (changed != 1) throw new IllegalStateException("批次状态更新失败");
            return true;
        }); // 回调异常时回滚；正常返回才表示这次事务提交已被确认。

        // 提交失败或响应未知会抛异常，不会执行到这里；不能捕获后强行继续。
        if (!Boolean.TRUE.equals(ready)) {
            throw new IllegalStateException("批次已转为异常待处理，需告警并人工核实");
        }
        dispatcher.dispatchCommittedBatch(BATCH_ID);
    }

    private void initializeTasks() {
        Long existing = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task", Long.class);
        if (existing == null || existing != 0L) {
            throw new IllegalStateException("未启动批次不应存在残留任务，先核实");
        }
        Long[] bounds = jdbc.queryForObject(
                "SELECT MIN(id), MAX(id) FROM old_consume_record",
                (rs, rowNum) -> new Long[] {
                        rs.getObject(1, Long.class), rs.getObject(2, Long.class) });
        if (bounds == null || bounds[0] == null || bounds[1] == null) {
            throw new IllegalStateException("旧表为空，零任务规则待确认，不生成虚假任务");
        }
        long minId = bounds[0], maxId = bounds[1];
        // 本示例只支持能装入 Java long 的 ID；超出表示范围时拒绝，不截断。
        long distance = Math.subtractExact(maxId, minId);
        if (distance < 0) throw new IllegalStateException("扫描范围非法");
        long planned = distance / ID_SPAN + 1;
        if (planned > maxTasks) throw new IllegalStateException("任务数超过配置上限");
        if (jdbc.update("UPDATE migration_batch SET min_id = ?, max_id = ? WHERE id = ?",
                minId, maxId, BATCH_ID) != 1) {
            throw new IllegalStateException("扫描边界保存失败");
        }
        long inserted = 0;
        for (long startId = minId; ; ) {
            long endId = Math.addExact(startId,
                    Math.min(ID_SPAN - 1, Math.subtractExact(maxId, startId)));
            // 教学映射：用范围起点作为稳定 task_id，主键约束防止重复插入。
            int n = jdbc.update("INSERT INTO migration_task "
                            + "(task_id, start_id, end_id, current_id, status, failure_reason) "
                            + "VALUES (?, ?, ?, NULL, 'PENDING', NULL)",
                    startId, startId, endId);
            if (n != 1) throw new IllegalStateException("任务保存失败");
            inserted++;
            if (endId == maxId) break;
            startId = Math.addExact(endId, 1);
        }
        if (inserted != planned) throw new IllegalStateException("任务清单不完整");
    }

    private boolean hasResumableTasks() {
        Long total = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task", Long.class);
        Long invalid = jdbc.queryForObject("SELECT COUNT(*) FROM migration_task "
                + "WHERE status IS NULL OR status NOT IN ('PENDING', 'PAUSED', 'SUCCESS')",
                Long.class);
        return total != null && total > 0 && total <= maxTasks
                && invalid != null && invalid == 0;
    }

    public interface Dispatcher {
        void dispatchCommittedBatch(long batchId);
    }
}
```

**事务内失败与提交结果未知**

`NOT_STARTED`、`RUNNING`、`PAUSED` 分别表示未启动、运行中、已暂停；`NEEDS_ATTENTION` 表示异常待处理。任务状态 `PENDING`、`PAUSED`、`SUCCESS` 表示待处理、已暂停、成功。初始化中的任意写入失败、算术溢出或状态校验失败，异常向外传播，使本次事务回滚；不能捕获异常后返回正常结果。提交阶段发生连接或响应异常时，结果可能未知，调用方应告警并核实数据库，不得假定已经回滚后自动重试。

例如初始化第三个范围失败，已插入的前两个范围和批次扫描边界一起回滚，批次尚未执行运行中状态更新，仍保持未启动；下一次启动不会沿用半份任务清单。具体回滚行为仍需用真实数据库验证。为了突出事务边界，示例逐条插入任务；实际初始化耗时、任务数上限和是否改用 JDBC 批量写入需要验证。MIN/MAX 查询假设可由索引高效完成；否则按 4.2 的边界规划要求调整，不能长期占用控制记录锁。

**调度器必须承担的交接职责**

`Dispatcher` 是尚待实现的业务接口，不能用空实现后声称迁移已完成。其实现沿用线程池调度专题：提交前复查批次状态与停止信号，只查询待处理、已暂停任务；按原状态更新为处理中后才扫描。线程池核心数、最大数均为按数据库预算压测确定的 `N`，队列及提交上限遵循该专题，不在此重复创建另一套线程池。

事务提交后可能立即收到暂停请求，因此仅在 `dispatchCommittedBatch` 入口查询一次运行中还不够，提交循环、任务入口和分页边界也要检查停止信号。提交被拒或部分提交失败时，调度器负责立即停止新处理、告警、保留已接收的 Future 并组织安全收尾；不能将异常直接丢给启动调用方后放任已运行任务继续。调度器随后按完整任务表汇总状态，不能直接把批次改回未启动或已暂停。

**示例的实现边界**

任务表仅保存这次迁移的任务，不混入其他迁移历史，不新增批次 ID。示例的恢复校验发现空清单及失败、处理中等非法状态时，先提交异常待处理状态，再拒绝启动，但不能仅靠记录条数证明范围完整；还需依靠初始化事务、稳定唯一约束和禁止随意修改清单。人工修数后必须按保存的范围核实完整性与未知结果，确认安全后才能恢复。

示例没有实现 Controller、告警、调度器和人工恢复流程，也没有读取生产配置。它展示的是可落地的事务与 JDBC 调用骨架，不是完整迁移服务；实际 DataSource、事务管理器接线、超时配置以及驱动对 ID 类型的映射需在实现时验证。Spring 事务接口查阅入口：[TransactionTemplate](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/transaction/support/TransactionTemplate.html)、[DataSourceTransactionManager](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/jdbc/datasource/DataSourceTransactionManager.html)；已核对 TransactionTemplate 官方 API 中回调运行时异常触发回滚并向外传播的说明，并依据 [Spring Boot 2.7.18 BOM](https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-dependencies/2.7.18/spring-boot-dependencies-2.7.18.pom) 确认其管理的 Spring Framework 版本为 5.3.31。本次使用该依赖与 Java 8 编译示例通过；这不证明项目已引入相同依赖或事务接线已生效，实际依赖树、数据库运行及故障行为仍待验证。


## 5 已确认规则

- 在详细方案中补充启动互斥与初始化事务的核心代码，并明确示例和待验证边界。
- 所有启动入口锁定同一条预先存在的批次记录，不使用 Redis 锁。
- 批次边界、完整任务清单和运行中状态在同一数据库事务中保存。
- 恢复启动不重新初始化，提交确认后才提交线程池。
- 恢复前确认上一次线程和数据库操作已结束，人工核实不占用启动行锁。
