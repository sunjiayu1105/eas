## 2 问题

后台处理一条更新消息时，新表 UPDATE 影响 0 行，怎样判断这条消息能否标记完成？

### 2.1 考点

1. 说明为什么只知道影响 0 行，还分不出目标缺行和版本条件未命中。
2. 说明目标存在时怎样比较业务版本和字段，判断这条更新是否已生效或已被更新版本覆盖。
3. 说明更新先于历史搬运到达、目标仍缺行时，补写前需要核实哪些来源数据和保留条件。

### 2.2 答题范围

接在 6.4 的后台处理流程之后，从一次已返回的更新结果开始。对照正确分片上的同一笔流水，说明证据不足时为什么应保留待处理状态。业务更新消息缺行后的具体补写方式待核实。6.2 处理写入响应丢失，7.3.1 处理历史快照与删除交错。

### 2.3 候选理由

同一个返回值可能对应不同的业务状态。误标完成可能漏掉更新，盲目补写又可能恢复已清理的流水。

## 3 面试口述版本

口述内容字符数：229

后台执行带版本条件的更新，收到 0 行时，先保留这条消息。按商户号定位新表分片，再按流水的业务主键重读目标。目标已存在，版本相同且业务字段一致，可以确认这次变更已经生效。更高版本已生效，也可以结束这条旧更新。同版本字段不同，要记录冲突；目标版本仍低，则要继续查明为什么没写进去。

如果目标缺行，可能是更新消息先于历史搬运到达。先查当前主写的旧表，核对这笔流水是否仍存在、是否在保留期内，以及能否取得完整字段和有效版本。证据不足时保留待处理状态。实际采用哪种补写方式仍待核实；补写后也要核对新表结果，才能标记完成。

## 4 详细方案

例如，更新消息携带版本 3，目标表里已经是版本 4。只允许较旧目标版本被更新的条件会挡住版本 3。若目标根本没有这笔流水，同一条更新也匹配不到记录。这两种情况的返回值都可能是 0，但第二种情况仍缺少目标已同步的证据。

MySQL 的客户端计数可能返回实际改变的行数，也可能按匹配行数返回。核实项目连接选项和具体 SQL 有助于解释返回值；业务完成条件仍要看正确分片上的记录。若补写前后发生并发写入，要重新核对目标版本，防止迟到的旧消息盖掉较新数据。超时后的查证见[写入响应丢失后的重试](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_业务双写_失败重试.md:1>)。
