# 041_MySQL到ES同步_为什么采集新库日志并通过消息队列写入ES

## 1 说明

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 2 问题

为什么从新库采集变更，再经消息队列写 ES？这种方案给后台查询带来哪些代价？

## 3 高级 Java 面试核心考点

**答题范围** 比较由各写入口直接更新 ES 和统一采集新库日志时，分别怎样覆盖历史搬运、处理 ES 暂时不可用以及发现漏写。说明引入消息队列后需要管理积压、重投和重复消费。项目采用 Canal 与 RocketMQ，同类产品的实测对比及当时采购或运维选型依据待核实。

**入选理由** 主问题 13 要求沿已有链路定位延迟。这道追问考查如何在交易可用性、写入口覆盖和查询时效之间选择同步方式，以及团队为此承担哪些恢复工作。基于项目拟题。[同步链路](<./036_MySQL到ES同步.md:19>)、[消息发布与位点提交](<./039_MySQL到ES同步_消息发布与位点提交.md:19>)

## 4 面试口述版本

口述内容字符数：189

业务双写和历史搬运都会修改新库。如果让每个入口直接更新 ES，就要逐个处理数据库已提交、ES 写入却失败的情况。项目在双写上线时开启 Canal，从两个新库各自的日志起点采集已提交的变更，送到 RocketMQ，由消费服务写 ES。ES 暂时不可用时，新库仍可提交，消息会积压，后台列表也会滞后。恢复后要观察积压是否下降，按记录版本处理重投，再用新表与 ES 校验发现漏写。消息保存期限和源库日志保留时间都限制了可恢复的范围。

## 5 详细方案

从采集位置、队列积压、ES 单行写入结果和搜索刷新逐段排查。同类产品的实测对比及当时的采购或运维依据仍待核实。
