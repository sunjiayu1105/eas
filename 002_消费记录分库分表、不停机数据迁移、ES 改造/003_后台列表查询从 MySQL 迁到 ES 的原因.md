# 003_后台列表查询从 MySQL 迁到 ES 的原因

## 1 说明

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 2 问题

后台跨商户查交易列表，为什么选择 ES？哪些查询仍需读交易库？

## 3 高级 Java 面试核心考点

根据查询条件能否定位分片、业务能接受多久的数据延迟，说明哪些读请求适合 ES，以及维护查询副本需要付出的同步和校验成本。

**入选理由** 本题考查如何根据查询负载和数据时效选择读路径。即使库表拆分方案已经确定，后台列表是否适合迁到 ES，仍需单独判断。

**项目依据** 基于项目拟题。[跨商户查询和读路径选择](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/003_后台列表查询从 MySQL 迁到 ES 的原因.md:31>)

## 4 面试口述版本

口述内容字符数：180

**跨商户查列表** 交易能按商户号定位到一个分片，后台列表却要跨商户筛选、排序和分页。把列表放到 ES 查询，可以省去交易库跨片查询和归并结果的开销。

**查询条件多** 客服和运营组合筛选的方式不同，为每种组合都在交易表上建索引，会增加存储和写入成本。

**隔离查询负载** 列表查询放到 ES 后，交易库可以优先处理交易请求。代价是需要同步和校验查询副本。允许短暂延迟的列表读 ES，写完就要查到最新结果的请求读当前主写库。

## 5 详细方案

运营和客服需要跨商户筛选并连续翻页。列表先取得当页交易，再批量补齐展示字段。

### 5.1 单表和单实例的规模压力

分库分表解决的是数据、索引、读写和维护任务集中在单表或单实例的问题。它不会减少数据总量，也不能仅凭表数量保证性能提升；实际收益取决于数据分布、查询范围、索引设计、资源规格和维护窗口。容量基准、保留周期和具体拓扑属于分库分表设计，详见[007_分库分表](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/007_分库分表.md:1>)。

### 5.2 跨分片查询的额外成本

分片键用于确定数据所在的库表。查询条件无法提供可用的分片定位信息时，系统需要向多个分片发起请求，再合并各分片的结果。全局排序、分页和总数统计通常需要额外的归并处理，深分页和大范围查询会进一步放大请求、传输和合并成本。并行访问可以减少部分等待，但不能消除多分片访问带来的资源消耗；实际耗时仍需结合数据量、索引和并发验证。

### 5.3 多条件查询与索引取舍

联合索引的效果受字段顺序、过滤条件、范围查询和排序要求影响。后台查询条件组合灵活，一个索引难以覆盖所有组合。增加合适的索引可以改善对应查询，但会增加存储、缓存和写入维护成本。因此，ES 适合作为后台列表的检索副本，承担灵活过滤、排序和分页；MySQL 继续作为交易权威数据源。

### 5.4 列表查询与交易写入隔离

复杂列表查询可能扫描较多数据、执行排序和跨分片归并，与实时交易写入共享数据库资源时会产生争用。将列表查询交给 ES 可以把这类查询流量从交易数据库中分离出来，但会增加同步链路、数据一致性保障和运维成本，不能直接等同于查询一定更快。

### 5.5 同步延迟的业务边界

ES 的 `refresh_interval` 为 3 秒，表示新写入数据等待刷新后才具备可搜索性。端到端可见延迟还包括 Canal 采集、RocketMQ 传输和消费、ES 写入等环节，因此不能把 3 秒直接当成列表可查上限。当前已确认业务可以接受正常链路下的几秒级延迟；具体秒数上限、达标比例和异常情况下的提示方式仍需通过验收规则明确。

## 6 已确认规则

- 面试口述中的改造原因，每个原因单独一个段落，并用一个简短、具体的加粗小标题概括该原因。
- 列表查询迁移到 ES 的原因包括跨分片查询成本、多条件组合下的索引取舍，以及列表查询与交易写入的资源争用。
- ES 刷新间隔为 3 秒；该数值不代表端到端同步延迟，也不代表业务容忍上限。
- 后台列表业务可以接受同步链路无积压、无重试且处理及时情况下预期的几秒级延迟；实际延迟仍需验证。
- MySQL 仍是交易权威数据源，单笔详情和最终交易状态以 MySQL 为准。
