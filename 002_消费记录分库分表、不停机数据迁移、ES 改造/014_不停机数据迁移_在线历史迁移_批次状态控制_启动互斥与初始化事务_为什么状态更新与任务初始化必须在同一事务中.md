## 2 问题

为什么首次启动时，批次状态更新、扫描边界保存和任务初始化必须放在同一个数据库事务中？

## 3 高级 Java 面试核心考点

- 事务原子性：批次状态、扫描边界与任务清单一起提交或回滚。
- 失败窗口：分别提交为何会留下状态与任务准备情况不一致的结果。
- 生效条件：相关写入参与同一 InnoDB 事务，失败时确保整个事务回滚。
- 保证边界：事务原子性不替代启动互斥、清单完整性校验及提交后的调度恢复。

### 4.1 先看为什么会再次进入初始化流程

首次启动时，应用会根据批次状态判断是否需要初始化任务：批次为“未启动”时，才进入首次初始化流程。

假如将任务初始化和批次状态更新分开提交，先初始化任务并提交，随后将批次状态改为“运行中”时失败，就会出现任务已经保存，但批次仍是“未启动”的情况。下次启动请求读取到“未启动”，就会再次进入初始化分支；如果没有额外校验，就可能重复创建同一批次的任务。

详见：[分别提交会留下什么问题（第 56 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_为什么状态更新与任务初始化必须在同一事务中.md:56>)。

### 4.2 用同一事务保证状态与任务一起提交

因此，应用要在同一个数据库事务中保存扫描上下界、初始化完整任务清单，并将批次状态改为“运行中”。全部成功后一起提交；中途失败时完整回滚。这样，提交成功后，后续请求会因为批次已是“运行中”而退出；完整回滚后，本次任务写入也已撤销，下次可以重新初始化。确认事务提交成功后，才调度迁移任务。

详见：[事务应怎样组织（第 68 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/014_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_为什么状态更新与任务初始化必须在同一事务中.md:68>)。

### 4.3 检查已有任务和唯一约束各自能做什么

初始化前检查任务表，可以发现这个批次是否已经有任务；唯一约束可以阻止相同任务再次写入。但它们都不能解决“任务已经保存，批次状态却仍是未启动”的问题。因此，任务初始化和批次状态更新仍需放在同一个事务中，保证一起成功，或一起回滚。

上述效果以相关写入真正参与同一 InnoDB 事务、失败时完整回滚为前提，不能只凭一条 SQL 报错就认定整个事务已经回滚。任务清单是否覆盖完整扫描范围，仍需应用校验；并发启动由 Redis 启动锁和数据库条件更新控制。提交结果未知时先核实，不能直接重新初始化。实际事务配置、失败回滚和故障恢复尚未验证。

## 5 详细方案

### 5.1 为什么状态与任务清单不能分别保存

批次状态决定下一次启动是否需要初始化任务清单；批次内任务清单决定哪些范围会被迁移。首次初始化时，应用必须在同一事务中将扫描上下界写入批次表、将完整任务清单写入任务表，并将批次状态改为运行中，才能使批次状态与批次内任务的实际准备情况一致。任务初始状态为待处理，与批次未启动状态属于不同层级。

这里的“一起成功”指事务提交后的持久化结果，不要求事务内部某一条 SQL 执行后，其他 SQL 就已经完成。仅从原子性看，事务内可以先插入任务再更新状态，但不能把中间结果单独提交；当前 013 实现方案先条件更新取得启动资格，再初始化任务，具体顺序见 5.3。后续任务处理必须等提交成功得到确认之后再开始。事务只保证参与其中的写入一起提交或回滚，不会自动判断任务是否覆盖了完整扫描范围；清单完整性仍需应用校验。

依据：[MySQL 8.0 COMMIT 与 ROLLBACK](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/commit.html)，说明提交使当前事务的更改持久化，回滚撤销当前事务的更改。

### 5.2 分别提交会留下什么问题

**失败后的持久化结果**

下面比较相同目标：保存一份完整的批次内任务清单，同时把批次改为运行中。区别在于失败时能否统一撤销。

**分别提交：** 假设批次状态已经单独提交为运行中，计划生成 300 个批次内任务，却在插入 100 个后失败。即使任务插入事务回滚，已提交的批次运行中状态也不会一起撤销；如果任务分多次提交，还可能留下部分批次内任务。下一次启动读到运行中就拒绝，无法按正常首次初始化流程补齐。

**同一事务：** 批次状态更新和 300 个批次内任务插入都尚未提交时，第 100 个任务之后失败，应用完整回滚该事务。该事务已插入的批次内任务，以及已执行的批次扫描边界和状态修改一起撤销，不会留下“批次运行中但批次内任务清单不完整”的已提交结果。

反过来，先独立提交完整的批次内任务，再更新批次状态也不能解决问题：若批次状态更新失败，数据库仍显示未启动，下次会再次进入首次启动分支。当前 013 的残留任务校验会拒绝继续初始化；若缺少这项校验和唯一约束，则可能重复创建任务。拦住重复初始化只能避免继续写错，不能自动修复批次状态与任务清单不一致。

### 5.3 事务应怎样组织

1. 按当前 013 实现方案先获取 Redis 启动锁；进入数据库事务后检查已有批次状态，以原状态作为条件更新为运行中，影响行数为 1 才继续。未取得启动资格时结束，不初始化任务，并按 013 的退出流程释放自己仍持有的启动锁。
2. 首次启动时，在同一事务中保存批次扫描上下界和完整任务清单，各任务初始状态为待处理。这些写入与上一步运行中状态更新都暂不提交。
3. 检查任务清单是否覆盖完整扫描范围、写入是否成功。任一步失败或校验不通过，明确回滚整个事务，不吞掉异常后提交。
4. 全部检查通过后，提交上述写入。确认提交成功后，释放启动锁，再调度任务；失败路径也应按 013 释放自己仍持有的锁，但不能继续调度。不在初始化事务内执行历史数据迁移。

批次表和任务表应使用 InnoDB，批次状态、批次扫描边界和批次内任务清单的写入必须参与同一数据库事务和连接。不能让任务插入使用自动提交、独立事务或异步线程，否则外层回滚无法统一撤销这些已提交写入。Spring 事务是否真正生效、异常是否触发完整回滚，都要验证，不能只凭方法有事务注解判断。

完整核心实现见 [启动互斥与初始化事务实现方案（第 1 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_实现方案.md:1>)；本篇专门解释事务边界，不复制另一份初始化代码。已暂停批次恢复时沿用原任务清单和进度，不重新初始化任务清单。

### 5.4 回滚与提交结果未知要分开处理

仅一条 SQL 失败，不代表数据库已经回滚整个事务。例如锁等待超时默认只回滚当前语句；`innodb_rollback_on_timeout=OFF` 为默认设置，设为 `ON` 时，锁等待超时才会自动回滚整个事务。这是 MySQL 的行为说明，不代表项目已经核实该配置，也不要求为本方案修改服务端配置。应用不能只根据 SQL 报错就继续执行或提交，而应确保整个初始化事务已回滚。确认完整回滚后，才可按原未启动状态重新初始化该批次的任务清单。

如果 COMMIT 的响应丢失，数据库可能已经提交，不能因为客户端异常就认定状态和任务均已撤销。此时应停止本次启动、核实持久化结果，再按既有人工恢复规则处理。事务已提交但进程在调度前宕机，也会留下运行中状态和完整任务清单；这属于调度与恢复问题，不是事务原子性失效。

事务原子性解决的是本次多项写入一起提交或回滚。当前 013 方案中，Redis 锁减少同时进入启动流程的请求，数据库条件更新以原状态匹配及影响行数保护同一次启动资格。仅靠原子性不能防止多个请求分别提交成功；本篇不展开锁实现，也不改变当前选型。同目录不带“实现方案”后缀的 013 已标明为历史行锁方案，仅供对比。

依据：[MySQL 8.0 COMMIT 与 ROLLBACK](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/commit.html) 及 [InnoDB Error Handling](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-error-handling.html)。2026-11-18 前次复核已在线查阅上述官方页面，核对提交使更改持久化、回滚撤销当前事务更改，以及锁等待超时默认仅回滚当前语句的规则。前者支持 5.1—5.3 的事务边界，后者支持本节的完整回滚要求；未执行数据库或故障实验。

### 5.5 为什么检查已有任务和唯一约束不能代替事务

当前 013 方案要求初始化前查询任务表，发现同一批次已有任务时拒绝继续初始化，交由人工核实。这个检查可以阻止应用在已有任务的情况下再次生成任务，却不会把批次状态自动改为运行中。

唯一约束由数据库检查：同一任务再次写入时，如果违反唯一键，就拒绝该次写入。这里要求同一任务对应稳定的任务 ID 或批次内范围唯一键；如果每次生成新的任务 ID，且没有约束同一批次的任务范围，就不能仅凭主键唯一认为已经防止重复初始化。具体唯一键定义仍待确认。

因此，任务表检查负责发现已有任务，唯一约束负责拦截重复记录，事务负责将任务初始化、扫描边界保存和批次状态更新一起提交或回滚。前两项不能自动修复分别提交留下的不一致结果，也不能代替事务的原子性。相关方案依据见 [013 实现方案的辅助方法职责（第 95 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_实现方案.md:95>)；上述机制的实际配置与运行效果仍待验证。
