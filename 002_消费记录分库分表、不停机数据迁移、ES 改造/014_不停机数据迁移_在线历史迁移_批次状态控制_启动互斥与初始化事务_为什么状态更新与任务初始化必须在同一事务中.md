## 1 问题

为什么批次状态更新与批次内任务初始化必须放在同一个数据库事务中？

## 2 高级 Java 面试核心考点

- 用事务原子性保证批次状态和批次内任务清单一致。
- 分析分别提交时的失败窗口，区分单条语句失败与整个事务回滚。
- 区分事务原子性、启动互斥及提交结果未知。

## 3 面试口述精炼版本

口述内容字符数：719

首次启动时，批次扫描上下界、完整任务清单和“运行中”状态必须在同一个数据库事务中提交。事务原子性就是这些写入要么全部提交，要么全部回滚，避免批次状态与任务准备情况不一致。

**先看批次状态如何决定启动行为**

批次为“未启动”时，需要初始化任务清单；“已暂停”时，复用已有任务和进度；其他状态拒绝启动。因此，批次状态不能先于或落后于任务清单单独提交。

详见：[状态与任务清单的关系（第 53 行）](#41-为什么状态与任务清单不能分别保存)。

**分开提交，两种顺序都有失败窗口**

两种顺序都要保存完整任务清单，并把批次改为运行中；但分开提交时，后一步失败都无法撤销前一步已经提交的结果。

**先提交批次状态：** 例如计划生成 300 个任务，状态已提交为运行中，任务插入却失败。即使任务插入全部回滚，批次状态也不会撤销，下一次启动仍会被运行中状态拦住。

**先提交任务清单：** 如果任务已经提交，状态更新却失败，批次仍是未启动。下一次启动可能再次初始化同一批次的任务清单。唯一约束能拦住重复记录，但不能自动修复批次状态。

详见：[分别提交与同一事务的失败对比（第 59 行）](#42-分别提交会留下什么问题)。

**同一事务失败时，要完整回滚**

在同一个事务中保存扫描边界、完整任务清单和运行中状态，任一步失败就回滚整个事务。例如插入 100 个任务后失败，回滚会撤销这 100 个任务以及本事务已写入的边界和状态。确认完整回滚后，下次才能重新初始化；确认提交成功后，才调度迁移任务。

详见：[事务组织与生效条件（第 69 行）](#43-事务应怎样组织)。

**事务原子性不等于启动互斥**

当前方案由 Redis 启动锁和数据库条件更新控制启动竞争，事务负责多项写入一起提交或回滚。一条 SQL 报错不代表整个事务已回滚，应用需要确保完整回滚；提交响应丢失时，结果尚不确定，应先核实，不能直接重新初始化。

详见：[完整回滚与提交结果未知（第 80 行）](#44-回滚与提交结果未知要分开处理)。

## 4 详细方案

### 4.1 为什么状态与任务清单不能分别保存

批次状态决定下一次启动是否需要初始化任务清单；批次内任务清单决定哪些范围会被迁移。首次初始化必须同时保存批次表中的扫描上下界、任务表中的完整任务清单和批次的运行中状态，才能使批次状态与批次内任务的实际准备情况一致。任务初始状态为待处理，与批次未启动状态属于不同层级。

这里的“一起成功”指事务提交后的持久化结果，不要求事务内部某一条 SQL 执行后，其他 SQL 就已经完成。事务内可以先插入任务再更新状态，但不能把中间结果单独提交。后续任务处理必须等提交成功得到确认之后再开始。

### 4.2 分别提交会留下什么问题

下面比较相同目标：保存一份完整的批次内任务清单，同时把批次改为运行中。区别在于失败时能否统一撤销。

**分别提交：** 假设批次状态已经单独提交为运行中，计划生成 300 个批次内任务，却在插入 100 个后失败。即使任务插入事务回滚，已提交的批次运行中状态也不会一起撤销；如果任务分多次提交，还可能留下部分批次内任务。下一次启动读到运行中就拒绝，无法按正常首次初始化流程补齐。

**同一事务：** 批次状态更新和 300 个批次内任务插入都尚未提交时，第 100 个任务之后失败，应用完整回滚该事务。该事务已插入的批次内任务，以及已执行的批次扫描边界和状态修改一起撤销，不会留下“批次运行中但批次内任务清单不完整”的已提交结果。

反过来，先独立提交完整的批次内任务，再更新批次状态也不能解决问题：若批次状态更新失败，数据库仍显示未启动，下次可能再次为同一批次初始化任务清单；唯一约束可以拦住重复任务记录，却不能自动修复批次状态与任务清单不一致。

### 4.3 事务应怎样组织

1. 按当前 013 实现方案先获取 Redis 启动锁；进入数据库事务后检查已有批次状态，以原状态作为条件更新为运行中，影响行数为 1 才继续。未取得启动资格时结束，不初始化任务。
2. 首次启动时，在同一事务中保存批次扫描上下界和完整任务清单，与上一步运行中状态一起提交；各任务初始状态为待处理。
3. 任一步失败或清单校验不通过，明确回滚整个事务，不吞掉异常后提交。
4. 只有提交成功得到确认，才按 013 的释放启动锁、调度任务流程继续；不在初始化事务内执行历史数据迁移。

批次表和任务表应使用 InnoDB，批次状态、批次扫描边界和批次内任务清单的写入必须参与同一数据库事务和连接。不能让任务插入使用自动提交、独立事务或异步线程，否则外层回滚无法统一撤销这些已提交写入。Spring 事务是否真正生效、异常是否触发完整回滚，都要验证，不能只凭方法有事务注解判断。

完整核心实现见 [启动互斥与初始化事务实现方案（第 1 行）](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次状态控制_启动互斥与初始化事务_实现方案.md:1>)；本篇专门解释事务边界，不复制另一份初始化代码。已暂停批次恢复时沿用原任务清单和进度，不重新初始化任务清单。

### 4.4 回滚与提交结果未知要分开处理

仅一条 SQL 失败，不代表数据库已经回滚整个事务。例如锁等待超时默认只回滚当前语句，启用 `innodb_rollback_on_timeout` 后才会自动回滚整个事务。应用不能只根据 SQL 报错就继续执行或提交，而应确保整个初始化事务已回滚。确认完整回滚后，才可按原未启动状态重新初始化该批次的任务清单。

如果 COMMIT 的响应丢失，数据库可能已经提交，不能因为客户端异常就认定状态和任务均已撤销。此时应停止本次启动、核实持久化结果，再按既有人工恢复规则处理。事务已提交但进程在调度前宕机，也会留下运行中状态和完整任务清单；这属于调度与恢复问题，不是事务原子性失效。

事务原子性解决的是本次多项写入一起提交或回滚。当前 013 方案中，Redis 锁减少同时进入启动流程的请求，数据库条件更新以原状态匹配及影响行数保护同一次启动资格。仅靠原子性不能防止多个请求分别提交成功；本篇不展开锁实现，也不改变当前选型。

依据：[MySQL 8.0 COMMIT 与 ROLLBACK](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/commit.html) 及 [InnoDB Error Handling](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-error-handling.html)。2026-11-16 前次复核已在线查阅上述官方页面，核对提交使更改持久化、回滚撤销当前事务更改，以及锁等待超时默认仅回滚当前语句的规则。前者支持 4.1—4.3 的事务边界，后者支持本节的完整回滚要求；未执行数据库或故障实验。
