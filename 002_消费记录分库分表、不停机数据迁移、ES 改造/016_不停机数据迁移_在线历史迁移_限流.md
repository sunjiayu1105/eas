# 016_不停机数据迁移_在线历史迁移_限流

## 1 问题

如何控制历史迁移的任务范围、并发数量和请求频率？

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。具体实现和运行效果尚未验证。

## 2 面试口述精炼版本

口述内容字符数：182

**先划分不重叠范围**

旧表约有 3 亿条、主键递增数据，可按每个任务平均约 100 万条规划约 300 个任务。任务范围互不重叠，再在任务内部按批次读取。任务总数、并发数和单批大小是三个参数。

**限制并发和频率**

例如固定 2 个工作线程，每个任务处理完一批并保存进度后等待 100 毫秒，再读取下一批。观察数据库负载和业务延迟，压力过大就减少并发或延长等待。2 和 100 毫秒只是示例，实际值需压测。

## 3 详细方案

### 3.1 先结合总量划分任务范围

**项目规模与划分原则**

当前旧表保留最近 5 年、约 3 亿条数据，主键递增。这是用户确认的业务背景，不是本次查询数据库得到的统计结果。

建议先按主键跨度划分互不重叠、完整覆盖本次迁移范围的任务区间，再结合已有的数据分布信息估算工作量。主键递增不等于完全连续，不能把主键跨度直接当成记录数；但也不必为了让各任务大小完全相同，先对每个范围执行精确 COUNT。允许任务数据量有差异，发现某个范围明显过大时，可在尚未执行的范围中进一步拆分，保持覆盖完整且不重叠。

**已确认的规模规划：约 300 个任务**

项目按每个任务平均约 100 万条有效记录规划，约 3 亿条数据对应约 300 个任务。这是已确认的规模规划，不要求每个任务恰好 100 万条，也不代表实际任务数必须等于 300。记录数不能直接换算为主键跨度，具体边界需结合实际分布确定；并发数仍需通过压测确定。

一个任务可以包含很多批次。任务范围决定“负责哪部分数据”，单批规模决定“每次处理多少数据”，并发数决定“同时运行多少任务”，三者不能混为一个参数。

### 3.2 任务内部再分批

迁移按旧表主键范围拆分批次。参考文章_04 第 3 节建议从 500—1000 的批次参数开始测试；本文沿用每批 500—1000 条的参考目标，只能作为调参起点，不能直接视为项目固定配置。具体调参方法与事务大小的取舍由性能调优分文档维护。

文章示例按起止主键划定区间，而不是按实际返回条数分页；主键有空洞或记录已删除时，区间内记录会少于预期。例如区间 [1001, 1500] 的宽度是 500，但只剩 420 条记录时，本批实际读取 420 条。边界不得漏掉主键；项目采用何种区间生成和分页方式仍待确认。来源：[参考文章_04：区间计算与读取（第 273 行）](</D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:273>)。

任务范围划分后，由调度器控制哪些任务可以运行；任务内部在批次之间等待。两层控制配合，才能同时限制并发数量和访问频率。

批次大小和并发数如何选择、如何利用索引及控制事务大小，统一见[013 批次性能调优](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/013_不停机数据迁移_在线历史迁移_批次性能调优.md>)。本文保留限流执行机制，不重复展开性能取舍。

### 3.3 并发度如何控制

例如用核心数和最大数均为 2 的固定线程池执行互不重叠的范围任务，限制同时访问数据库的任务数；一个任务内部仍按批次顺序处理。2 个线程只是示例，实际配置待压测；线程数不等于约 300 个任务的总数，也不能直接由总记录数确定。

线程池、队列容量、拒绝处理、任务失败和安全停止的建议集中在 [017 线程池设计](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/017_不停机数据迁移_在线历史迁移_线程池设计.md>)。参考文章_04 仅提出多任务处理不同范围及按负载调整并发，没有给出这些 Java 实现。

### 3.4 批间等待如何控制

每个任务完成本批写入并保存进度后，等待配置的时长，再读取下一批。这会降低单个任务连续访问数据库的频率。并发任务数限制“同时有多少任务在跑”，批间等待限制“每个任务跑得多快”。

参考文章只写了“每批之间短暂休眠”的注释，没有实际等待语句或具体时长；不能把该示例视为已实现限流。项目需要补充等待和中断处理，等待时长通过压测确定。批间等待需要提供可调整的配置；具体阈值与调参验证由性能调优分文档维护，不假定已有自动调节能力。此方式不能保证精确固定的每秒写入条数。

**示例：任务分开跑，每个任务分批等**

以下范围和等待时长仅用于解释机制，不是项目配置。

1. 任务 A 负责主键 1—1000000，任务 B 负责 1000001—2000000，两者没有重叠。

2. 假设每批主键跨度为 500，A 先处理 1—500，B 先处理 1000001—1000500；实际条数可能因空洞而减少。

3. 各自确认本批结果并保存进度后，等待 100 毫秒再读下一批。两个任务可以同时运行，但每个任务都不会连续不停地发请求。

4. 数据库压力偏高时，可减少同时运行的任务数，或延长批间等待；如何安全让任务退出，由线程池分文档展开。

来源：[参考文章_04：批间休眠](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:301>)、[并发度控制](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:320>)。

### 3.5 合计限制所有执行者

示例中两个实例各有 2 个线程，总并发可达 4；如作业目标为 2，就需限制各实例合计并发。静态分配或统一调度要结合部署选择，本文不指定已采用实现。

### 3.6 示例：执行者失去响应

1. A 领取范围 R 开始写入。

2. A 失去响应，不能仅凭超时认定其已停止数据库写入。

3. 若把 R 立即交给 B，A 恢复后继续执行，就可能出现双重执行。

4. 接管需判断或隔离旧执行者，并保护任务归属与进度。

原子领取决定谁获得任务，故障恢复决定未完成任务如何继续，旧执行者隔离决定接管后谁仍有权写入或更新进度。若选租约或分布式锁，也需处理过期后旧执行者仍运行的问题；它们不是项目已选定组件。

现有文档未确认单实例还是多实例，不补造调度平台、任务表、锁组件或租约时长。部署方式确定后再验证领取、接管与总并发。

来源边界：[参考文章_04 第 320 行](<D:/000/sources/eas/002_消费记录分库分表、不停机数据迁移、ES 改造/ref_不停机数据迁移_参考文章_04.md:320>)只提出按范围并行及按数据库负载调节，没有给出本篇 Java 调度与恢复实现。本篇属于跨实例调度的设计分析；单机 Java API 不提供原子领取、旧执行者隔离或故障接管保证，具体实现与部署仍待确认。

## 4 已确认规则

- 不同任务处理互不重叠的主键范围。
- 约 3 亿条数据按每任务平均约 100 万条规划约 300 个任务。
- 区分任务总数、并发数量和单批大小。
- 任务并发和批间等待都必须给出具体数值或范围，并标明示例或待压测状态。
