1．以核心开发者的身份， 参与该项目的性能优化 、技术选型 、技术难点攻关， 以及核心代码的开发工作。

2． “账户管理 ”模块， 通过属性类别 + 查询频繁度 + 占用空间大小作为衡量标准， 对 “账户信息 ”表进行多范围垂直分表， 解决 MySQL 在复杂业务场景下的批量查询瓶颈问题。

3．“消费业务 ”模块， 通过 ShardingSphere-JDBC 框架， 以商户 ID Hash 的方式对 “消费记录 ”表进行分库分表，并通过雪花算法生成分布式 ID， 以及通过基因法将商户 ID 和主键 ID 进行关联映射， 解决 MySQL海量数据下的存储和业务维度查询问题。

4．“消费业务 ”模块， 通过 Elasticsearch 搜索引擎代替 MySQL， 解决 “消费记录 ” 的多维复杂查询和全文检索关键字场景的性能瓶颈问题， 并通过其 search_after 机制来优化深翻页场景的性能瓶颈， 以及通过天凌晨定时对索引进行 force_merge 操作， 设置合理的 translog 和 refresh_interval 机制等方式 ，将后台多条组合复杂查询场景下的平均接口 RT 优化为原来的 30%。

5．“消费业务 ”模块， 调研并引入 Elasticsearch 集群冷热分离策略， 将不常用的 “消费记录 ”冷数据存储到 HDD 磁盘中， 并通过索引全生命周期管理的方式进行自行维护， 将 Elasticsearch 硬件成本降低 20%， 兼顾系统性能和研发效率。

6．“对账清算 ”模块， 通过 XXL-JOB 分片广播 + CompletableFuture 线程并行化方式进行 “海量商户消费数据对账处理 ”， 并通过支持断点自动续跑 、多维度小范围重跑修正的方式， 解决当出现问题只能全量重导致时间消耗过长的痛点， 将该场景下的全年核对及时性从 99.3%提升至 100%。

7．“统计分析 ”模块， 以空间换时间的思想， 通过 Redis 存储过往不可变的历史数据 + 增量数据实时计算的方式，取代原来的全量数据实时计算的方式， 将该业务场景下的平均 RT 优化至原来的 1/7。

8．系统持续巡检优化，通过发现、定位并解决 OOM、数据库死锁、索引失效等问题，提升系统的稳定性和健壮性，同时将处理流程沉淀为标准化排查预案，使团队整体问题排查效率提升约 80%。
