# 3.4.1.5 批次失败后如何确认、重试和恢复？

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 文档维护与已确认规则

- 本文与 005、007、008 保持一致：Canal-to-MQ 投递组件必须在 RocketMQ 发送成功后才确认 Canal 批次；RocketMQ 消费服务逐项检查 ES Bulk 结果，可重试项不确认，终止项进入持久化死信后是否确认由项目策略决定。重试次数、退避、死信保留期和暂停方式尚未确认，不能把参考文章参数写成项目配置。
- 恢复验收按 008 的已确认范围执行：分别检查两个 destination 的 Server 接管、投递组件重连、RocketMQ 积压追赶、ES 增删改、历史索引定位与重复消费。位点连续性、可重试失败、死信确认和 404 分支分别核验。以上是待执行要求，参考来源和未执行边界见 008。

## 面试口述精炼版本

**逐项检查再确认**：Canal-to-MQ 投递组件按批次获取 Canal 消息，多个行变更可以封装为 RocketMQ 事件；RocketMQ 消费服务再把事件组成 ES `_bulk`。一个 Canal 批次可能拆成多个消息或 ES 子批次，必须逐项检查结果并分别处理。RocketMQ 发送未成功时不能确认 Canal 批次，ES 处理未按规则完成时不能确认 RocketMQ 消息，已成功的 Bulk 项也不会自动回滚。

**有限尝试后暂停任务**：当前只确认要区分网络超时、429、5xx、映射错误、索引不存在和定位缺失，分别设置重试、告警或死信策略。具体次数、退避和达到阈值后的暂停动作仍待联调；404 不能一概当作成功。

**保留日志供恢复**：未确认批次可能重放，稳定 `_id` 不能单独保证幂等，还要维持同一记录的事件顺序并命中原具体索引。日志不足以证明位点连续时暂停推进；不能取最新位点跳过缺口。Canal ack、RocketMQ ack 和 ES 写入结果属于不同层次，不能混为一个恢复位置。

**按验收项恢复**：故障演练要分别检查 `db0`、`db1` 的 Server 接管和投递组件重连，核对位点、binlog 连续性、RocketMQ 积压和 ES 实际结果；还要覆盖 rollover 后历史 UPDATE、DELETE、定位缺失、Bulk 部分失败和死信恢复。上述为待执行要求，不是已完成测试。

## 详细方案

**分清 Canal 批次与 ES 操作数**

MySQL binlog 按序产生事件，Canal Server 按序解析。以 Canal TCP 客户端 `getWithoutAck(batchSize)` 为例，一次调用返回一个 `Message`（批次容器），其中包含若干 `Entry`；一个行变更 `Entry` 还能包含多行 `RowData`。因此 `batchSize` 不等于 ES 文档数。当前投递组件的 batchSize、ES 操作数与 Bulk 请求规模分别评估，不把旧 Adapter 的 canal.tcp.batch.size 配置键套成自定义服务参数。

**检查全部子批次后确认**

Canal-to-MQ 投递组件可以把一个 Canal 批次拆成多条 RocketMQ 事件；ES 消费服务再按容量组成一个或多个 `_bulk` 请求。Bulk 可能部分成功，HTTP 整体成功不代表每项成功。可重试项保持未完成并重试；同时出现可重试与终止失败时，必须保存全部终止项后再决定重试，不能提前 return 漏掉终止项；只有所有需要处理的项都成功，或已按明确死信策略完成，才能确认 RocketMQ 消息。不能把固定等待时间当成搜索可见或同步追平的证明。

上述“失败不确认”是项目要求，不是默认端到端保证。RocketMQ Spring 2.3.0 的 ORDERLY 监听方法正常返回表示成功，异常才进入暂停重试；不能异步提交 ES 任务后立即返回，也不能用普通 return 表示不确认。008 的示例保留原消费单元重试，不同时异步补发；终止项持久化与 Broker 内置 DLQ 分开处理，耗尽前须防止同键后续事件越过失败。client 5.2.0 的 API 已静态核对，重试次数、确认政策、Broker 和 ES 运行行为仍待联调。

**分清确认返回、持久化和消费回退**

客户端 ack 方法返回、Server 处理确认并更新消费游标、消费进度完成持久化，是不同阶段。SimpleCanalConnector.ack() 写出确认报文，该方法没有等待 Server 确认响应；因此方法返回不能证明 Server 已处理或位点已持久化。Server 的 ack 根据批次更新游标并确认事件存储进度，持久化仍受 007 所述元数据管理与周期刷新机制约束。ES 写入成功而消费确认未可靠保存时，故障恢复仍可能重复处理。

原生 SimpleCanalConnector 的 rollbackOnConnect 默认 true，普通连接及 ZooKeeper 活动回调中均有连接后的 rollback 路径；rollbackOnDisConnect 默认 false，不能描述为每次断开都会主动回退。Server 的 rollback 清理消费批次状态并回退事件存储读取状态，不会撤销已经写入 ES 的数据。带 batchId 的实现仍调用事件存储的 rollback，源码保留精确回退到指定 batchId 的 TODO，不能将其描述为可任意选择历史批次进行精确回放。上述是默认代码路径，实际发行包、订阅状态及恢复结果仍须验证。

**修改支持来源：** [Canal 1.1.7 SimpleCanalConnector.java](https://github.com/alibaba/canal/blob/canal-1.1.7/client/src/main/java/com/alibaba/otter/canal/client/impl/SimpleCanalConnector.java)的连接回退开关、connect、processActiveEnter、ack 和 rollback，以及 [CanalServerWithEmbedded.java](https://github.com/alibaba/canal/blob/canal-1.1.7/server/src/main/java/com/alibaba/otter/canal/server/embedded/CanalServerWithEmbedded.java)的 ack 与两种 rollback 实现。以上是源码静态核对，不是实际恢复演练结果。

恢复需结合 Server 持久化进度、源日志完整性及 ES 结果核验；不改变现有日志缺口处置规则，也不将初始 GTID 回退待定事项改为自动恢复方案。

**重放时保持顺序和原索引**

未确认批次重放可能再次写入。稳定 `_id` 只能避免同一具体索引中出现第二篇同 ID 文档，不能单独保证重放幂等；同一 `consumeId` 的事件顺序、操作类型与目标具体索引也须正确。首次 INSERT 的路由须可靠预留，重放沿用原物理索引；DELETE 后保留来源顺序与删除标记，搜索未命中不能单独证明不存在。重复写入、删除、版本控制、故障恢复和确认语义须按最终消费端联调，不能宣称已实现 exactly-once（每个事件恰好处理一次）；[009_ES 文档如何写入与检索.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/009_ES 文档如何写入与检索.md:6>)另有边界。

**按最慢链路保留日志并处理缺口**

新库 binlog 保留期与空间须覆盖历史导入、首次同步、故障追赶和两项校验中最长的读取需要；旧库也须覆盖旧表与新表校验。查询切换前连续 2 周无差异不等于 binlog 保留时长，一条链路追平也不能清理其他链路仍需的日志。无法证明恢复位点之后的日志连续时，暂停推进并复核缺口，不能从最新位置重启。校验链路各自的恢复规则见[014_旧表与新表增量校验.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/014_旧表与新表增量校验.md:6>)和[015_新表与 ES 增量校验.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/015_新表与 ES 增量校验.md:6>)。
