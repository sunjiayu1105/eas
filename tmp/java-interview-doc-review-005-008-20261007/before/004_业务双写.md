# 3.3 业务双写

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 3.3.1 保留双写期间的业务写入

## 面试口述精炼版本

**双写期间以旧表为成功依据**：只需要保证旧表写入成功；新表写入失败产生的差异，由自动校验任务发现并交独立流程处理。

**先写旧表并确认提交**：双写期间，业务请求先写旧表。旧表提交失败，请求失败并结束；确认旧表提交成功后，才继续尝试写新表。

**再尝试新表写入**：应用沿用 ShardingSphere-JDBC 分片链路写新表。旧表提交成功后，即使新表写入失败，接口仍按成功处理；两次写入不构成原子事务。

**发现差异后独立修复**：旧表与新表的自动校验收集两端变更、比较当前数据；发现差异后，交给独立流程修复。

## 详细方案

**保持同一业务身份和分片规则**

双写覆盖新增、修改、撤销、退货和物理删除。同一笔交易以不变的交易流水号 `serialNo` 关联新旧表，`merchantNo` 在交易生命周期内固定。ShardingSphere-JDBC 是应用侧分片组件，按配置的商户号规则将新表 SQL 路由到对应库表。恢复业务后的增量必须继续走这条正式写入链路，才能验证实际路由、主键生成和写入结果；历史迁移与校验不替换它。

**执行顺序：先旧表，后新表**

应用先写旧表并确认旧表事务已经提交，再尝试写新表。两次写入不构成一个原子事务，因此旧表已经提交后，新表失败不能回滚旧表，也不能覆盖旧表已经提交的数据。

| 写入情况 | 处理规则 |
|---|---|
| 旧表提交失败 | 请求失败并结束，不继续调用新表写入；未提交事务不产生对应的已提交变更 |
| 旧表提交成功、新表提交成功 | 接口返回成功；新表的已提交变更产生行日志，供 Canal 异步同步 ES |
| 旧表提交成功、新表写入失败 | 接口仍按旧表已提交返回成功；应用可运行时尽量记录失败信息，差异由校验发现并交独立流程修复 |

**新表提交后异步同步 ES**

新表已提交的新增、修改和物理删除通过 ROW 格式 binlog（按行记录变更）交给 Canal，之后异步写入 ES。接口返回成功不表示 ES 已写入或已可搜索；ES 文档的 `_id` 使用 `consumeId`，具体见[008_Canal 同步 MySQL binlog 到 ES（自定义 ES 消费服务处理逻辑）.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/008_Canal 同步 MySQL binlog 到 ES（自定义 ES 消费服务处理逻辑）.md:1>)和[010_批次失败与同步恢复.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/010_批次失败与同步恢复.md:6>)。

**按两端变更触发校验**

旧表与新表增量校验任务从历史验收后的基线监听两端变更。任意一端产生变更，就按 `serialNo` 保存检查任务，稍后重读两端当前状态并比较；发现差异后交独立流程修复，修复完成后再复核。详细的变更收集和差异处理见[014_旧表与新表增量校验.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/014_旧表与新表增量校验.md:6>)和[013_增量校验总览与差异处理.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/013_增量校验总览与差异处理.md:6>)。应用可运行时尽量记录新表写入失败，但校验不能依赖这条记录；新库宕机或应用异常时，失败记录也可能无法写入。若两端都没有已提交变更，校验收不到事件，业务操作是否应成功仍需业务回查或对账判断。

**重试和幂等边界仍待核实**

同一业务请求重试时，不能重复产生业务效果。接口按旧表已提交返回成功，不等于调用方一定收到响应；响应丢失仍可能触发重试。现有材料尚未提供请求身份识别、同一业务的 `consumeId` 复用、并发版本控制和独立修复实现，这些内容仍需结合实际代码确认。本节描述已确认的双写规则，不宣称代码已经编译或运行验证。


## 3.3.2 关闭旧表写入后的业务行为

## 面试口述精炼版本

**满足收尾条件再改单写**：全部旧表业务和查询依赖切换完成，两项校验持续运行并覆盖应检查范围、连续 2 周没有发现差异后，才停止旧表与新表校验并关闭旧表写入。

**以新表提交判断结果**：此后请求直接使用原有 ShardingSphere-JDBC 新表写入链路，以新表事务提交结果判断接口成功或失败；新表到 ES 的同步及新表与 ES 校验继续运行。

## 详细方案

**完成最终切换后停止旧表写入**

具体门禁见[018_ES 验收与查询切换.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/018_ES 验收与查询切换.md:6>)。全部旧表依赖切换完成后，继续双写并运行两项校验；任务持续运行、覆盖应检查范围且连续 2 周无差异，才停止过渡性的旧表与新表校验、关闭旧表写入和旧表查询回退。旧链路代码和开关保留，不等于旧表仍可作为当前查询回退目标。

**新表提交决定接口结果**

请求不再等待旧表先提交，直接沿用 ShardingSphere-JDBC 新表写入链路。新表提交成功则按成功处理，提交失败则按失败处理。

**切换后保留同步校验**

新表 binlog 继续由 Canal 异步同步到 ES，新表与 ES 校验任务长期运行；旧表与新表校验已停止。新表提交成功仍不表示 ES 同步或搜索可见已经完成。

本节涉及的 Canal 职责和异步边界见[024_Canal 是什么？.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/024_Canal 是什么？.md:6>)；完整同步链路见[005_Canal 同步 MySQL binlog 到 ES（总链路）.md](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/005_Canal 同步 MySQL binlog 到 ES（总链路）.md:1>)。
