## 文档维护与已确认规则

- 本文保留掘金文章的原始 Adapter 方案，用来和当前 006、007、008 的已确认方案对照。当前 005–008 已采用 `Canal Server（TCP）→ Canal-to-MQ 投递组件 → RocketMQ → 自定义 ES 消费服务`，Canal Adapter 不再是主写入组件；因此本文中“当前 008 使用 Adapter”的旧表述均按历史对照理解，不能作为当前链路事实。不得将文章未明确、架构图尚未核验的 Adapter 进程数量和故障转移方式补写为已确认事实。

## 一、文章方案概览

文章以单机示例演示 Canal 将 MySQL 增量同步到 Elasticsearch，主要包括：JDK 8、MySQL 8.0.26、Elasticsearch 7.17.11、Canal 1.1.7-alpha-2；MySQL 开启 binlog 并使用 ROW；Canal Server 配置 Instance、起始位点和过滤规则；Canal Adapter 通过 TCP 订阅并用 `conf/es7` 映射文件写入 ES；通过 ETL REST 接口手动全量同步；通过 REST 接口查看任务和开关同步；记录了 `_index`、`_id` 下划线属性解析问题及源码打包替换方案。

文章中的 IP、账号、表名、命令和配置均是演示环境示例，不能视为当前项目生产配置或已验证结论。

## 二、原文方案详细整理（保持文章原方案）

### 1. 数据链路

文章链路为：MySQL 8.0.26 → binlog → Canal Server 1.1.7-alpha-2 → Canal Adapter → Elasticsearch 7.17.11。Server 读取并解析 binlog，Adapter 通过 TCP 订阅后按映射写入 ES。

### 2. MySQL binlog 与起点

文章示例设置 `binlog-format=ROW`、`server_id=1`，并在 Instance 配置中使用 `canal.instance.gtidon=false`，同时预留 journal、position、timestamp 和 gtid 起始属性。

### 3. Server 与实例关系

文章使用一个 `example` Instance 连接一个 MySQL 实例，过滤规则示例为全库匹配；配置完成后通过日志确认 Server 启动。

### 4. Adapter 映射

文章使用 `dataSourceKey: defaultDS`、`destination: example`、`groupId: g1`，在 `esMapping` 中配置 `index`、`id`、显式 SQL、`etlCondition` 和 `commitBatch`。文章强调 SQL 不使用 `select *`，单表也要设置别名。

### 5. 全量与增量边界

文章提供 `/destinations`、同步开关、ETL 和 count REST 接口；如果要重新做全量同步，文章建议删除 `conf/example/meta.dat` 后再次启动或执行同步。

## 三、与 006 文档的对照

### 3.1 相同点

- 都以 MySQL binlog 作为 Canal 增量同步的输入，并使用 ROW 行级事件。
- 都关注 binlog 是否开启、复制账号、起始位置和过滤规则。
- 都把 MySQL、Canal Server 和 ES 写入端分成不同职责，认为 MySQL 的已提交变更要先进入 binlog，Server 再交给下游消费者。掘金文章使用 Adapter；当前 005–008 通过 RocketMQ 交给自定义 ES 消费服务。
- 都要求同步起点、日志保留和恢复过程能够被核对，不能把示例配置直接当作已验证生产事实。

### 3.2 不同点

## 四、与 007 文档的对照

### 4.1 相同点

- 都描述 Canal Server 从 MySQL binlog 读取并解析 INSERT、UPDATE、DELETE 等变更。
- 都认为 Server 负责消息读取和交接，不能把 ES 文档转换职责放到 MySQL。掘金文章由 Adapter 处理下游映射，当前 007/008 分别由 Canal-to-MQ 投递组件和自定义 ES 消费服务承担。
- 都涉及 Instance、MySQL 地址、复制账号、过滤规则、起始位点和启动日志。
- 都承认连接中断或处理失败可能需要重新读取或恢复，运行结果必须通过日志和实际联调确认。

### 4.2 不同点

#### Canal Server 部署方案是否与 007 一致

不一致。文章只演示单个 Canal Server、单个 `example` Instance 的启动、日志查看和 Adapter 连接，没有形成 Server 主备集群；007 采用 ZooKeeper 协调的 Canal Server 主备高可用，同一 destination 同一时间只允许一个节点工作，并为两个 MySQL 实例配置 `db0`、`db1` 两个 destination。两者都使用 Canal Server 读取 MySQL binlog，但文章没有覆盖 ZooKeeper 主备、故障接管、双 destination、位点恢复和积压追赶。因此，文章的 Server 部署只能作为单机示例，不能视为 007 的高可用部署方案。

对照：[007_Canal 同步 MySQL binlog 到 ES（Canal Server 处理逻辑）](<D:/000/sources/eas/002_消费记录分库分表、双写与ES 改造（15）/007_Canal 同步 MySQL binlog 到 ES（Canal Server 处理逻辑）.md:1>)

| 对照点 | 掘金文章原方案 | 007 文档方案 | 结论 |
| --- | --- | --- | --- |
| 版本 | Canal 1.1.7-alpha-2 | Alibaba Canal Server 1.1.7 | 版本不同，不能直接等同 |
| Instance | 单个 example | db0、db1 两个 destination | 拓扑冲突 |
| GTID | gtidon=false 示例，起始属性可留空 | 每个 instance 独立初始 GTID，优先恢复已持久化确认位点 | 起点和恢复策略冲突 |
| 高可用 | 主要演示单机启动 | ZooKeeper 主备，同一 destination 只能一个节点工作 | 文章未覆盖高可用 |
| 消息确认 | 未展开 Server 与 Adapter 的确认和重投递 | 确认后推进位点，失败或未确认时重新投递 | 文章信息不完整 |
| 异常事件 | 未详细处理 DDL、TRUNCATE、未知事件 | 告警、暂停或人工处理，不能静默跳过 | 文章信息不完整 |
| 全量重跑 | 删除 meta.dat 后重新同步 | 正常重启优先使用已保存确认位点 | 恢复方式冲突 |

总体上，两者都采用“Server 读取 MySQL binlog，再向下游消费者提供消息”的方向；但在版本、实例数量、GTID、ZooKeeper 主备、位点确认和异常边界上存在冲突或缺失。本文保留文章原方案，不把 007 的项目规则写回原文方案。

## 五、与 008 文档的对照

### 5.1 相同点

- 都需要订阅 Canal 消息，并通过 destination 或 Instance 选择对应同步任务；掘金文章使用 Canal Adapter，当前 008 使用 RocketMQ 消费服务。
- 都需要明确数据字段、ES 索引和文档主键，把 MySQL 行数据转换为 ES 文档；当前 008 还要维护 rollover 后的物理索引定位。
- 都支持 INSERT、UPDATE、DELETE 语义，并关注稳定业务主键、失败重试和重复投递下的幂等性。
- 掘金文章使用 es7 适配器和 REST/TCP 等 Adapter 配置项，当前 008 的 RocketMQ、索引定位、Bulk 逐项处理和死信规则属于自定义实现，具体 API 仍需验证。

### 5.2 不同点

#### 文章 Adapter 方案是否与当前 008 一致

不一致。掘金文章只部署并启动一个 Adapter，连接单个 `example` Instance、一个 `defaultDS` 数据源和一个 `es7` 外部适配器，主要验证单机同步。当前 008 已改为 RocketMQ 事件契约、自定义 ES 消费服务、物理索引定位、Bulk 逐项处理、重试和死信；它不再采用文章中的 `ds0`、`ds1` 映射文件作为主写入方案。两者都需要稳定业务主键和明确的事件顺序，但掘金文章没有覆盖当前 rollover 后历史 UPDATE、DELETE 的定位问题。

## 六、原文方案的完整执行顺序

1. 安装文章指定版本的 JDK、MySQL、Elasticsearch 和 Canal 发行包。
2. 在 MySQL 中开启 binlog，设置 ROW 和 server_id，并通过 show variables 检查。
3. 解压 Elasticsearch，配置集群名、节点名、数据目录、日志目录、监听地址和端口，处理 Linux 用户及内核参数后启动。
4. 解压 canal-deployer，编辑 example/instance.properties，填写 MySQL 地址、账号、gtidon、起始位点和过滤规则。
5. 编辑 canal_local.properties，填写注册 IP、Admin 地址、端口和账号，启动 Canal Server 并查看日志。
6. 初始化 canal_manager 数据库，编辑 Adapter 的 bootstrap.yml 和 application.yml，配置 TCP、批量大小、重试、数据源和 es7 外部适配器。
7. 创建 ES 索引和 Mapping，删除默认 es7 映射文件并编写 user.yml。
8. 启动 Adapter，通过 destinations、syncSwitch、etl 和 count 接口检查任务、开关、全量同步和数量。
9. 向 MySQL user 表新增数据，在 ES 中查询验证；需要重新全量时按文章建议删除 meta.dat。

## 七、三组对照的共同总览

### 1. 总体数据链路一致

四份方案都采用 MySQL binlog 作为增量来源，经过 Canal Server 读取和解析，再交给下游写入端同步到 Elasticsearch。掘金文章使用 Canal Adapter；当前 005–008 通过 RocketMQ 和自定义 ES 消费服务完成后续处理。共同目标都是把 MySQL 的新增、修改、删除变化同步到 ES，供搜索或查询使用。

### 2. 都依赖 MySQL binlog 和 ROW 事件

文章和 006、007 都要求 MySQL 开启 binlog，并以 ROW 方式记录行变化。这样 Canal Server 能识别库表、事件类型和行数据，而不是只依赖原始 SQL 文本。

### 3. 都区分 Server 与下游写入职责

文章、007 和 008 都把 Canal Server 定位为 binlog 读取、解析和消息提供组件。掘金文章由 Canal Adapter 订阅、执行映射和写入 ES；当前 007 说明 Server 的 TCP 批次及独立 Canal-to-MQ 投递组件，008 负责 MQ 消费、索引定位和 ES 写入。006 也明确了 MySQL、Canal Server 和下游写入端的职责分层。

### 4. 都需要 Instance、destination 和映射配置协同

文章使用 `example` Instance、`destination: example` 和 `dataSourceKey: defaultDS`；007、008 使用 `db0`、`db1` 及对应 destination。虽然名称和数量不同，但共同点是 Server 的任务名称、消息中的 destination、事件字段和下游路由必须正确对应。当前 008 不再以 Adapter 映射文件和回查数据源作为主写入配置。

### 5. 都使用显式字段映射把 MySQL 数据转换为 ES 文档

文章通过 SQL 显式选择字段并设置 `_id`；008 通过事件字段、索引定位和文档 ID 生成 ES 操作；006、007 也都要求 binlog 行事件包含下游组装 ES 文档所需的数据。四份方案都不把 `select *` 或未知字段当作稳定映射方案。

### 6. 都以稳定主键关联 ES 文档

文章用表主键映射 ES 文档 ID，008 使用业务稳定标识作为 `_id`，006 和 007 的恢复与重投递设计也要求消费端能够识别同一业务记录。共同目标是让重复投递或重试不会无边界地产生重复文档。

### 7. 都包含启动、日志和同步验证步骤

文章通过启动脚本、日志、REST 接口和插入测试数据验证链路；006、007、008 虽然更强调恢复边界和待确认项，也都要求通过实际发行包、配置核对、日志和联调验证运行结果，而不是只凭配置文件宣称成功。

### 8. 都承认配置和版本必须与实际发行包核对

文章记录了版本兼容和 `_index`、`_id` 解析问题；006、007、008 也都把未核对的配置键、位点、映射和运行行为标记为待确认。共同点是不能把示例配置、网络文章或伪代码当作已经验证的生产事实。

## 八、最终结论与验证边界

1. 本文保留掘金文章的原始方案、版本、单实例示例、gtidon=false 和 meta.dat 重置方式。
2. 文章与 006、007、008 在“binlog → Canal Server → 下游写入端 → ES”、ROW 事件、职责分层、稳定主键和实际联调验证方面存在共同点；下游写入端的实现不同。
3. 与 006 的冲突集中在版本、拓扑、GTID 起点、日志条件和恢复策略。
4. 与 007 的冲突集中在版本、Instance 数量、GTID/位点恢复、ZooKeeper 主备、确认语义和异常边界。
5. 与 008 的冲突集中在映射字段、bulk 结果处理、ack 时机、拓扑和重放边界。
6. 本次只完成原文静态整理与文档对照，未连接 MySQL、Canal、ZooKeeper 或 ES，未验证文章配置键、REST 接口、meta.dat 行为和高可用切换结果。
