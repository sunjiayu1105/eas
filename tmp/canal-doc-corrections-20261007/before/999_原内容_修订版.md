### ES
于是，我们才使用了行业内的通用做法，通过ES去做这件事情， 因为ES是通过倒排索引 + 正排索引机制去实现的。

#### 正排索引（ Forward Index）
正排索引（ Forward Index） 的实现方式为， 通过文档ID去查找整个文档内容， 适用于全部文档遍历或根据某个文档ID查找内容的场景。

#### 倒排索引（ Inverted Index）
而倒排索引（ Inverted Index） 的实现方式 ，则是通过文档中的关键词去查找文档ID列表， 这也就是其非常适用于全文检索的原因。

很多同学都认为ES是通过倒排索引来实现的查询检索， 其实这种说法并不全面， 而且倒排索引的结构也并非这么简单。

（1） 当用户搜索“database” 关键字的时候， 会先通过以树结构（ Burst-Trie） 存储在内存中的Term Index中的 “d” ，查找到Term Dictionary中的“database”。

打个比方， 该步骤很像我们在上大学时候背的英语四六级字典， 根据字母的顺序ABC在目录中查找到对应的单词。

（3） 再通过为3的文档ID ，从ES的正排索引中查找到对应的数据信息“MySQL is a relational database” ，并返回最终结果。

这个步骤就像我们最后翻到字典中某个页数，找到了对于该单词的详细解释， 包括：音标 、中文 、例句等。

#### MySQL InnoDB的联合索引
##### 修改前

<mark>
由于MySQL InnoDB的联合索引 ，很大程度上是要遵循最左前缀原则的,这就意味着在多维复杂查询的某些场景中， 你需要通过（ a,b,c） ,（ a,c,b） ,（ b,a,c） ,（ b,c,a） ,（ c,a,b） ,（ c,b,a） 这种排列组合创建联合索引的方式，保证用户的查询操作可以完全命中索引。

那上述业务场景中有20多个查询项的情况下， 通过最左前缀原则 、排列组合创建联合索引的方式一定是覆盖不全，况且都不在一个数据库表中， 这是更加不可控的。
</mark>

##### 修改后

<mark>
由于MySQL InnoDB的联合索引很大程度上遵循最左前缀原则，不同查询条件组合往往需要设计不同的联合索引。查询组合越多，联合索引数量和维护成本越高，为所有排列组合建索引成本过大，实际只选择高频组合建立索引。
</mark>

#### MySQL 8的Skip Scan Range Access Method
Btw： 之所以在上文中用到了“很大程度上 ”， 是因为MySQL 8引入了Skip Scan Range Access Method， 它在一定条件下可以不遵守最左前缀原则，利用了范围扫描来替代了全表扫描的发生。

其实现原理为： MySQL隐式的构造了前缀查询条件 ，使一条查询就变成了多次查询 ，执行计划type = range。适用于最左条件区分度较低的情况，否则生成SQL过多，与全表扫描相比并无优势。

## search_after
深度分页是一个经典的问题 ︰ 比如说在数据分片存储的情况下如何获取前1000个文档?

我们获取从990~1000的文档时，会在每个分片上都先获取1000个文档，然后再由Coordinating Node聚合所有分片的结果后再排序选取前1000个文档， 页数越深（ 即from值越大），处理文档就需要越多， 占用内存越多，耗时越长。

为了尽量避免深度分页 ，es通过index.max_result_window限定最多到10000条数据 。如果分页的深度过大， ES会直接拒绝这个检索请求 。这种限制也是可以理解的，从检索的功能来说，本身也应该更关注匹配度高的结果项，深度分页的结果往往属于相关度较低的匹配结果，对于这类数据来说，也不应该太过于关注。

Search After使用简单且可以避免深度分页的性能问题，提供实时的下一页文档获取功能，缺点是不能使用from参数， 即不能指定页数， 只能向下翻页 。第一步为正常的搜索，但要指定sort值，并保证值唯一 ，第二步为使用上一步最后一个文档的sort值进行查询Search_After的API。

### Search_After如何避免深度分页
那么Search_After是如何避免深度分页带来的性能问题呢？

答案是Search_After通过唯一排序值定位将每次要处理的文档数都控制在size内 。我们回忆一下使用from/size时的分页， 比如说要查询第5000-5010的所有文档， 由于ES并不知道第5000个文档在哪里 ，那么就必须从所有分片上面各自查询5010个文档再合并后排序输出。

而使用Search_After则通过唯一排序值解决了这个问题，使得其在查询的过程中，每个分片可以根据唯一排序值定位到文档后，取出数量和size相同的文档即可， 这样就避免了由于分页过深而带来的性能消耗问题。

## force_merge操作
在 Elasticsearch 中， Lucene 索引被分为多个段（segments） 以提高查询性能 。每个段都是一个完整的

Lucene 索引， 包含一部分数据 。当一个文档被添加到索引中时， 它会被添加到一个新的段中 。这些新的段需要合并到更大的段中， 以便更快地执行搜索操作。

当 Elasticsearch 需要执行搜索时， 它必须在所有分片的所有段上执行查询 。如果分片中包含大量小段，则需要执行的查询次数将非常多，增加磁盘 I/O 操作次数，从而导致搜索性能下降 。如果使用 forceMerge 将这些小段合并为更大的段，则查询次数将减少，并且查询性能将得到显著提高。

forceMerge 是 Elasticsearch 提供的一个 API ，可以将多个段合并成一个更大的段 。这个过程可以通过减少段数来提高性能。

## Translog
即使通过每秒刷新（ refresh） 实现了近实时搜索，我们仍然需要经常进行完整提交来确保能从失败中恢复 。但在两次提交之间发生变化的文档怎么办？我们也不希望丢失掉这些数据。

ES增加了一个translog ，或者叫事务日志，在每一次对ES进行操作时均进行了日志记录 。通过translog ，整个流程如下：

### 流程
（1） 一个文档被索引之后，就会被添加到内存缓冲区，并且追加到了translog

（2）分片每秒被刷新（ refresh） 一次： 内存缓冲区被清空，但是translog不会清空；在内存缓冲区的文档被写入到一个新的段中（ 文件系统缓存）；这个段被打开，使其可被搜索。

（3） 这个进程继续工作，更多的文档被添加到内存缓冲区和追加到事务日志

（4）每隔30分钟，或translog 大于512M ，或执行Integer.MAX_VALUE次操作后：所有在内存缓冲区的文档都被写入一个新的段；

缓冲区被清空；

一个提交点被写入硬盘（ 里面标识着这个 commit point 对应的所有 segment file ，用于数据恢复）；

文件系统缓存中的段通过fsync被刷新（flush）；

老的translog被删除，一个新的translog被创建；

### 相关参数：
index.translog.durability：默认request ，每次写请求完成之后执行fsync ，async可选。

index.translog.sync_interval：默认5秒，前提是async

index.translog.flush_threshold_size：默认512m ，事务日志最大容量，超过即flush

index.translog.flush_threshold_ops：默认Integer.MAX_VALUE ，执行多少次操作后执行一次flush

index.translog.flush_threshold_period：默认30分钟，flush间隔

index.translog.disable_flush：禁用translog flush ，默认为false 。尽管默认情况下事务日志刷新是可用的，但对它临时性地禁用能带来其他方面的便利。

### 已设置参数
我们将index.translog.durability设置为了async， index.translog.sync_interval为10秒钟。

## refresh_interval
在ES中， 写入和打开一个新段的轻量的过程叫做refresh ，默认情况下每个分片会每秒自动刷新一次 。这就是为什么我们说ES是近实时搜索 。文档的变化并不是立即对搜索可见 ，但会在一秒之内变为可见 。

<font style="color:#333333;">refresh_interval 越小 ，产生的段越多，搜索反而会越慢；反过来说，加大 refresh_interval ，会相对提升搜索性能 。我们将refresh_interval 设置为3秒钟。</font>

## 2. 业务背景、数据规模与查询目标

### 2.1 业务背景

APP 消费是 E账通提供的电子账户收单能力，并不限定客户只能在银行自己的手机 APP 中消费。商户或合作平台发起订单后，E账通完成客户、订单、金额、限额和风控校验，再调用核心、统一支付或直销通等系统完成资金处理。

```text
商户或合作平台
  -> 前置网关/开放平台
  -> E账通
  -> 核心/统一支付/直销通等支付处理系统
  -> 原链路返回交易结果
```

正常情况下，交易结果实时返回交易发起方；结果未知时，通过已有单笔回查和异常回查机制更新最终状态。人寿电商、华为公交充值等业务均属于商户或合作平台接入 E账通完成消费的场景。

本查询功能供银行内部业务运营、客服和交易排障人员使用，不直接提供给商户或消费者。其目标是在指定时间范围内跨商户查询多笔交易，进行运营核查和异常分析，而不是替代商户侧单笔订单回查。

### 2.2 数据规模与查询问题

`FM_VACOMSUME_DETAIL` 按 `merchantNo` 使用 ShardingSphere-JDBC 分为 2 个数据库，每库 16 张物理表，共 32 个分片。日均新增约 20 万条，5 年累计约 3.65 亿条。

未提供 `merchantNo` 时，直接查询 MySQL 需要访问全部 32 个分片，并在中间件侧完成结果归并、排序和分页。时间条件只能减少各分片的候选数据，不能减少需要访问的分片数量，因此 MySQL 不适合作为跨商户运营列表的主要查询链路。

### 2.3 查询目标

| 查询类型 | 核心条件 | 主要用途 |
| --- | --- | --- |
| 异常排查 | 时间、交易类型、状态、渠道、支付方式、金额、错误码 | 跨商户筛选失败或未知交易，判断异常是否集中在某个时间段、渠道或支付方式；按金额优先排查资金影响较大的交易；按错误码集中查看具有相同失败原因的记录，为系统故障、渠道故障和支付链路异常定位提供依据 |
| 客户及账户核查 | 时间、身份证号、电子账户号 | 根据身份证号查询同一客户跨电子账户的消费、撤销和退货记录，或查询指定电子账户的完整交易历史；结合支付方式、交易状态、绑定卡和消费过渡户信息，协助处理客户投诉、账务疑问、重复扣款及撤销退货核查 |
| 商户及订单定位 | 时间、商户号、商户订单号、交易流水号 | 查询指定商户在一段时间内的交易记录，核对消费、撤销和退货处理情况；通过商户订单号或交易流水号定位具体记录，并关联应用日志、下游调用信息和对账流水进行问题排查 |

上述类型不是互斥场景。实际查询时可以在必填时间范围内组合多个条件，逐步缩小待核查交易范围。

`channelCode` 表示接入来源，`merchantNo` 表示交易归属商户，业务上保证其唯一。一个渠道可以对应多个商户，一个商户也可以通过多个渠道发起交易。

## 3. 总体架构与选型依据

### 3.1 数据分工

| 数据源 | 职责 |
| --- | --- |
| `FM_VACOMSUME_DETAIL` | 保存权威交易明细，承接实时交易写入和最终状态更新 |
| ES 消费交易索引 | 承担列表过滤、排序和游标分页 |
| 商户、客户主数据 | 补充当前商户名称、客户姓名和手机号 |

```text
内部列表查询
  -> 列表查询服务
       -> ES 查询交易记录
       -> 批量查询商户、客户主数据
       -> 应用层组装并返回

单笔详情及最终状态确认
  -> 根据交易标识回查 MySQL
```

MySQL 始终是权威数据源，ES 仅用于列表查询。单笔详情及最终交易状态以 MySQL 为准，具体详情接口不在本文展开。

### 3.2 列表查询链路

交易列表始终查询 ES，`merchantNo` 仅作为可选过滤条件，不触发 MySQL 列表查询。

ES 返回当前页交易记录后，应用按商户标识和客户标识分别去重，再批量查询 MySQL 主数据并完成页面字段组装。该方式避免逐条查询主数据造成 N+1 问题，同时保证页面展示当前有效的商户名称、客户姓名和手机号。

### 3.3 选用 ES 的原因

| 查询问题 | 方案价值 |
| --- | --- |
| 无商户条件时需要广播查询 32 个 MySQL 分片 | ES 在统一索引中完成跨商户过滤，避免交易库全分片归并 |
| 时间、状态、渠道、支付方式、金额等条件灵活组合 | 使用精确、多值和范围条件组合过滤，减少交易库组合索引压力 |
| 内部运营查询可能影响实时交易 | ES 承担列表检索，将运营查询压力与交易写入隔离 |
| 跨分片排序和深分页成本较高 | 在统一索引中稳定排序，并使用 `search_after` 连续分页 |

该设计以列表查询的非实时性换取跨商户检索能力和交易库隔离。涉及资金确认或最终状态判断时，仍以 MySQL 结果为准。

### 4.1 接口定义

接口用于银行内部 APP 消费交易列表查询。接口路径和 `code`、`message` 等通用响应包装最终以项目规范为准。

### 4.3 校验、排序与分页

- 时间范围采用 `[tradeTimeStart, tradeTimeEnd)`，按系统统一时区解析并精确到秒；
- `tradeTimeStart` 必须早于 `tradeTimeEnd`；
- 查询跨度暂定最多 7 天，最终上限以 ES 压测结果为准；
- 多类条件按 AND 组合，同类数组元素按 OR 匹配；
- 金额上下限均包含且必须非负，同时传入时最小值不得大于最大值；
- `tradeStatuses` 只接受 `90`、`99`、`33`；
- `productTypes` 只接受 `0`、`02`、`15`、`17`、`18`。

查询结果固定按以下顺序排序：

```text
tradeTime DESC, consumeId DESC
```

`tradeTime` 是主排序字段，`consumeId` 用于相同交易时间下的稳定排序，避免记录重复或遗漏。

列表采用 `search_after` 连续分页。服务端将当前页最后一条记录的排序位置编码为不透明的 `nextCursor`，前端下一页查询时原样回传。

接口不支持直接跳页，也不返回精确 `total`。`pageSize` 默认 20、最大 100，以控制 ES 读取、主数据补充、网络传输和页面渲染成本，并避免列表接口被用作批量导出接口。

### 4.5 核心数据设计

当前 `FM_VACOMSUME_DETAIL` 各分片表的 DDL 尚待核对。下表记录逻辑字段设计，具体物理列名、类型、长度、约束和索引以后续 DDL 为准。

| 字段或字段组 | ES 用途 | 为什么需要 |
| --- | --- | --- |
| `consumeId` | `_id`、`keyword`、第二排序字段 | 全局唯一定位交易，并保证相同交易时间下排序稳定 |
| `merchantNo` | `keyword` 精确过滤 | 标识交易归属商户，并为后续 MySQL 回查提供分片路由 |
| `idCardNo`、`electronicAccountNo` | `keyword` 精确过滤 | 支持按客户或电子账户查询交易历史 |
| `businessOrderNo`、`tradeNo` | `keyword` 精确过滤 | 关联商户订单、应用日志、下游调用和对账流水 |
| `tradeTime` | `date` 范围过滤和主排序 | 限定查询时间并按交易时间倒序展示 |
| `tradeType`、`tradeStatus`、`productType`、`channelCode` | `keyword` 多值过滤 | 支持按交易类型、状态、支付方式和接入渠道排查问题 |
| `tradeAmount` | `long` 范围过滤 | 展示交易金额并支持大额交易筛选 |
| `errorCode` | `keyword` 精确过滤 | 集中查询具有相同错误原因的异常交易 |
| `bindingCardNo`、`transitAccountNo`、`feeAmount`、`tradeRemark` | 仅保存在 `_source` | 用于列表展示和业务核查，不承担检索条件 |
| `dataVersion` | 不参与业务查询 | 为后续 ES 同步方案提供幂等和版本控制能力 |

#### 4.5.1 `consumeId`

```text
consumeId = snowflakeId + 两位 shardIndex
shardIndex = 根据 merchantNo 计算得到
```

`consumeId` 全局唯一。拼接结果可能超过 Java `Long` 或 MySQL `BIGINT` 范围，因此 MySQL 和接口均按字符串处理；ES 同时将其作为 `_id` 和相同交易时间下的排序兜底字段。

#### 4.5.2 金额边界

- 金额单位均为分，消费、撤销和退货金额使用非负数，资金方向由 `tradeType` 表示；
- 消费、撤销和退货记录的 `tradeAmount` 分别表示本次消费、撤销和实际退货金额；
- `feeAmount` 是交易成功时确定的商户手续费，由商户承担；
- 消费记录表只保留 `tradeAmount` 和 `feeAmount`，不再保留客户支付拆分或优惠金额字段；
- 消费记录表不保存 `merchantSettlementAmount`，T+1 清算时计算，并在独立清算明细中保存本批次金额快照；
- 当前接口不查询、也不返回 `collectionAmt` 和 `scoreAmount`；
- 正常 T+1 清算金额为 `tradeAmount - feeAmount`；发生清算前撤销时，先扣除已撤销金额及对应手续费。

#### 4.5.3 技术主键与业务唯一标识设计

通用数据表设计中，实体表通常同时保留技术主键和业务唯一标识，但两者职责分离：

| 字段类型 | 主要职责 | 使用范围 |
| --- | --- | --- |
| `id` | 数据库内部唯一标识、主键、内部关联和索引 | 通常不对外暴露 |
| `<entity>No` | 在业务和跨系统场景下稳定识别实体 | 接口、消息、日志和业务查询 |

推荐的逻辑结构：

```sql
CREATE TABLE business_entity (
    id BIGINT NOT NULL PRIMARY KEY,
    entity_no VARCHAR(64) NOT NULL,
    ...,
    UNIQUE KEY uk_entity_no (entity_no)
);
```

设计规则：

- `id` 只承担数据库内部技术职责，不作为对外或跨系统的业务身份标识；
- `<entity>No` 必须全局唯一、永久不复用，并原则上不可修改；
- 接口、消息和对外查询使用业务编号，数据库内部关联可使用 `id`；
- 数据迁移、数据重建或分库分表时必须保留业务编号，即使 `id` 重新生成，也不能改变业务身份；
- 以业务编号作为分片依据时，应保证全局唯一，并设计稳定的路由规则；
- 如果业务编号允许修改，应维护编号历史，或另设不可变的业务主键，不能直接把可变编号作为永久身份；
- 纯中间关系表、日志表等没有独立业务身份的表，不强制增加业务编号。

本方案中，`consumeId` 是消费记录的技术唯一标识，`merchantNo` 是商户的业务唯一标识。`merchantNo` 由业务保证全局唯一且不重复使用，作为商户查询条件、跨系统关联字段和分片路由依据；数据迁移时必须保持其值不变。

### 4.6 客户侧账号与资金流转

#### 4.6.1 账户字段边界

| 字段 | 保存到消费记录 | 写入 ES | 查询条件 | 列表返回 |
| --- | --- | --- | --- | --- |
| `electronicAccountNo` | 必存 | 原值保存，建立 `keyword` 索引 | 是 | 固定脱敏 |
| `bindingCardNo` | 按本笔实际使用情况保存 | 原值保存，不建索引 | 否 | 固定脱敏 |
| `transitAccountNo` | 必存 | 原值保存，不建索引 | 否 | 固定脱敏 |
| `collectionAdvanceAccountNo` | 否 | 否 | 否 | 否 |
| 商户对公结算账户 | 否 | 否 | 否 | 否 |

所有 APP 消费在业务准入前必须已经开通电子账户，因此每笔记录都保存 `electronicAccountNo`。`payeeAccountNo` 不再使用，统一由 `transitAccountNo` 表示本笔交易实际进入的消费过渡户。

#### 4.6.2 支付方式与资金流转

`UPOP` 表示银联在线支付或银行卡代收通道。

| 支付编码 | 支付方式 | 客户侧账号 | 资金流转 |
| --- | --- | --- | --- |
| `0` | 余额支付 | 电子账户 | 电子账户 -> 消费过渡户 `2611-0001` |
| `02` | UPOP 卡代收消费 | 电子账户、绑定卡 | 绑定卡 -> 代收垫资户 -> 电子账户 -> 消费过渡户 |
| `15` | 绑定卡支付 | 电子账户、绑定卡 | 绑定卡 -> 消费过渡户 `2611-0001` |
| `17` | 余额 + UPOP 卡代收组合支付 | 电子账户、绑定卡 | 卡代收部分：绑定卡 -> 代收垫资户 -> 电子账户 -> 消费过渡户；余额部分：电子账户 -> 消费过渡户 |
| `18` | UPOP 代扣 | 电子账户、绑定卡 | 绑定卡 -> 代收垫资户 -> 消费过渡户 `2611-0001`，资金不经过电子账户 |

`productType=0` 时 `bindingCardNo` 为空；其他支付方式按实际使用情况保存绑定卡。`productType=15` 或 `18` 的资金即使不经过电子账户，交易记录仍保存客户的电子账户号。

#### 4.6.3 手续费与 T+1 清算口径

以下金额示例使用“元”，实际落库和接口传输单位为“分”。手续费由商户承担，在消费成功时确定并记录在 `feeAmount` 中。手续费收入账户和退货过渡户是资金流转中的逻辑账户，具体会计科目以清算系统最终配置为准。

消费记录表只保留以下两个金额事实：

```text
tradeAmount = 客户实际支付金额
feeAmount   = 交易成功时确定的商户手续费
```

消费记录表不保存 `merchantSettlementAmount`。T+1 清算时，根据原消费金额、已发生的清算前撤销金额及对应手续费计算本批次清算结果，并在独立清算明细中保存 `settlementAmount`、`settlementFeeAmount`、清算批次号、状态和时间等快照信息。

#### 4.6.4 清算前全额撤销

原消费记录：

```text
tradeAmount = 100.00 元
feeAmount   = 2.00 元
```

消费成功后：

```text
客户原支付账户 -> 消费过渡户：100.00 元
```

全额撤销：

```text
消费过渡户 -> 客户原支付账户：100.00 元
```

撤销记录：

```text
tradeAmount = 100.00 元
feeAmount   = 2.00 元
```

```text
剩余交易金额 = 100.00 - 100.00 = 0.00 元
剩余手续费   = 2.00 - 2.00 = 0.00 元
应清算给商户 = 0.00 - 0.00 = 0.00 元
```

商户和手续费收入账户均未收到清算款，T+1 不再为该消费生成清算金额。

#### 4.6.5 清算前部分撤销

原消费记录仍为 `tradeAmount = 100.00` 元、`feeAmount = 2.00` 元，本次部分撤销 30.00 元。

```text
本次撤销手续费 = 2.00 × 30.00 ÷ 100.00 = 0.60 元
```

资金流转及撤销记录：

```text
消费过渡户 -> 客户原支付账户：30.00 元

撤销.tradeAmount = 30.00 元
撤销.feeAmount   = 0.60 元
```

T+1 剩余清算金额：

```text
剩余交易金额 = 100.00 - 30.00 = 70.00 元
剩余手续费   = 2.00 - 0.60 = 1.40 元
应清算给商户 = 70.00 - 1.40 = 68.60 元
```

```text
消费过渡户 -> 商户对公户：68.60 元
消费过渡户 -> 手续费收入账户：1.40 元
```

如果多次部分撤销最终耗尽原消费金额，最后一次撤销退回全部剩余手续费，以消除分次计算产生的舍入尾差。

#### 4.6.6 清算后全额退货

原消费金额为 100.00 元、手续费为 2.00 元，T+1 已完成：

```text
消费过渡户 -> 商户对公户：98.00 元
消费过渡户 -> 手续费收入账户：2.00 元
```

全额退货时：

```text
商户对公户     -> 退货过渡户：98.00 元
手续费收入账户 -> 退货过渡户：2.00 元
退货过渡户     -> 客户原支付账户：100.00 元
```

退货记录：

```text
tradeAmount = 100.00 元
feeAmount   = 2.00 元
```

商户退回此前收到的净清算金额，手续费收入账户退回已收手续费，客户收回原支付金额 100.00 元。

#### 4.6.7 清算后部分退货

原消费金额为 100.00 元、手续费为 2.00 元，T+1 已向商户清算 98.00 元、向手续费收入账户清算 2.00 元。本次部分退货 30.00 元：

```text
本次退货手续费 = 2.00 × 30.00 ÷ 100.00 = 0.60 元
```

资金流转及退货记录：

```text
商户对公户     -> 退货过渡户：29.40 元
手续费收入账户 -> 退货过渡户：0.60 元
退货过渡户     -> 客户原支付账户：30.00 元

退货.tradeAmount = 30.00 元
退货.feeAmount   = 0.60 元
```

```text
剩余可退交易金额 = 100.00 - 30.00 = 70.00 元
剩余可退手续费   = 2.00 - 0.60 = 1.40 元
```

最后一笔部分退货退完剩余金额时，退回全部剩余手续费，确保累计退货手续费等于原始手续费。

### 4.7 安全规则与接口边界

身份证号、电子账户号、绑定卡号、消费过渡户账号和手机号按照系统统一规则固定脱敏，应用日志不得记录这些字段的明文。

ES 内按原值保存 `idCardNo`、`electronicAccountNo`、`bindingCardNo` 和 `transitAccountNo`。其中只有 `idCardNo` 和 `electronicAccountNo` 建立查询索引；本文不展开 ES 字段加密、访问控制和审计方案。

接口明确不返回：

- `customerId`；
- `tradeStatusName`、`errorMessage`；
- `collectionAdvanceAccountNo`、`payeeAccountNo`、商户对公结算账户；
- `businessDate`、`currency`、`collectionAmt`、`scoreAmount`；
- 精确 `total`、`dataAsOf`、`queriedAt`。

本接口仅承担内部交易列表查询，不提供批量导出和直接跳页能力。

单笔详情、最终状态确认、批量消费及退货、闪付、二维码支付、快捷支付等其他模式不在本接口范围内。单笔详情和最终状态需要回查 MySQL，并由后续接口方案展开。

# 接口功能描述

以下内容仅描述接口的业务用途和业务边界，不展开数据实现方案。:codex-annotation{index="1"}

## 接口定位

**接口名称**：APP 消费电商交易明细列表查询

**建议接口**：`POST /internal/consume-records/search`

该接口面向银行内部业务运营、客服及交易排障人员，在指定交易时间范围内查询 APP 消费产生的多笔交易明细，覆盖消费、撤销和退货记录。接口通过组合多个业务条件，帮助工作人员快速缩小核查范围、定位目标交易并开展后续处理。

## 主要业务场景

### 异常交易排查

工作人员可以按交易时间、交易类型、交易状态、接入渠道、支付方式、金额区间和错误码等条件，筛选失败、异常或结果未知的交易。

通过对筛选结果进行对比，可以判断异常是否集中发生在某个时间段、接入渠道或支付方式上；也可以优先查看金额较大的交易，评估潜在资金影响。结合交易流水号和错误码，还可以进一步关联应用日志、下游调用记录及对账信息，定位问题发生的业务环节。

### 客户及电子账户核查

工作人员可以根据身份证号或电子账户号，查询指定客户或账户在一段时间内的消费、撤销和退货记录。

通过核对交易时间、交易金额、支付方式、交易状态及绑定卡等信息，可以协助处理客户投诉、账务疑问、重复扣款、扣款结果未知，以及撤销或退货是否成功等问题。

### 商户及订单定位

工作人员可以根据商户号查询指定商户的交易记录，也可以通过商户订单号或交易流水号快速定位具体交易。

定位后，可以核对该笔交易的消费、撤销和退货处理情况，并结合应用日志、支付链路和对账信息开展问题排查。

### 组合核查

上述场景可以组合使用。例如，先限定商户和交易时间，再按照交易状态、支付方式或错误码继续筛选，逐步缩小待核查的交易范围。

## 功能边界

本接口承担 APP 消费交易的多笔列表查询，不替代单笔交易详情查询和最终交易状态确认。

# 为什么要引入 ES

引入 ES 不是为了替换 MySQL，而是为了解决消费记录分库分表后，跨分片、多条件列表查询的性能和复杂度问题。

## 分库分表带来的影响

分库分表前，消费记录、客户和商户信息可以通过单库一条 SQL 完成关联、排序和分页。

分库分表后，原来的单库多表 JOIN 不再适合按原方式直接使用。系统需要先查询消费记录，再根据当前页的标识批量查询 **MySQL 客户信息表和 MySQL 商户信息表**，最后由应用层组装结果。

但是，在查询消费记录阶段，不带 `merchantNo` 的跨商户查询需要访问全部 32 个分片。带有 `ORDER BY` 时，各分片先过滤并按排序条件返回有序结果，再由 ShardingSphere-JDBC 做全局有序归并并完成分页，导致查询链路和资源开销增加，深分页时问题更加明显。

## MySQL 的查询瓶颈

消费记录列表涉及时间、交易状态、渠道、支付方式、金额、错误码等多维组合条件。MySQL 联合索引受最左前缀原则影响，难以覆盖所有条件组合；如果为各种组合建立索引，索引数量和维护成本都会增加。

## ES 的作用

因此，引入 ES 建立统一的消费交易索引，由 ES 完成跨商户过滤、排序和分页，并使用 `search_after` 降低深分页开销。同时，ES 承担运营和客服的查询流量，降低复杂列表查询对 MySQL 实时交易写入的影响。

ES 是消费记录的查询副本，数据同步可能存在短暂延迟。MySQL 仍是交易权威数据源，单笔详情、资金确认和最终状态判断必须回查 MySQL。
