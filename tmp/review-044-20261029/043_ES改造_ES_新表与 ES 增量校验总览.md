# 043_ES改造_ES_新表与 ES 增量校验总览

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。

## 1 文档目标

本文说明 MySQL 新表与 ES 的增量校验方案。校验程序按 `update_time` 扫描 MySQL 新表中当前仍存在的最新记录，直接读取扫描结果与 ES 对应文档进行比较；发现差异后由程序自动补偿。方案不建立待校验任务表，扫描进度由每张物理表独立维护的复合游标保存。

Binlog、Canal 和 RocketMQ 继续承担 MySQL 到 ES 的正常同步职责，不作为本校验流程的入口。已经从 MySQL 新表删除的记录不会被扫描，也不会进入 ES 比较。

## 2 已确认规则

- 使用 `update_time + consume_id` 复合游标扫描最新变更记录，不按 Binlog 逐条创建校验任务。
- 每轮固定 `scan_end_time = 当前系统时间 - 5 分钟`，只扫描 `update_time <= scan_end_time` 的数据。
- 初次扫描从该物理表最早历史数据开始；后续保留 10 分钟重叠窗口，允许重复扫描。
- 每张物理表独立维护扫描进度；当前页全部处理成功后才更新游标，失败时保留原游标。
- 不建立待校验任务表，不保存任务领取、任务状态或任务重试记录。
- 只校验 MySQL 新表中当前存在的记录；DELETE 数据已不存在于表中，不进入校验。
- 版本相同且字段一致时校验成功；MySQL 版本高于 ES 时自动补偿；ES 版本高于本轮扫描结果时跳过本轮；版本相同但字段不一致时记录差异并按 MySQL 数据进行同版本补偿。
- 查询失败或补偿失败时不推进当前页游标，下一轮继续处理。

## 3 面试口述精炼版本

**按游标扫描当前数据。** 我们不按 Binlog 的每条历史变更生成校验任务，而是按物理表维护 `update_time + consume_id` 复合游标，分页扫描当前仍存在的记录。每轮把扫描上限固定为当前时间减 5 分钟，给正常 ES 同步留出时间；同时回看 10 分钟重叠窗口，避免晚提交和分页边界造成漏查。

**直接比较并自动补偿。** 扫描到一页记录后，直接读取对应 ES 文档比较版本和业务字段。两端一致就继续处理；MySQL 版本更高就按 MySQL 当前数据自动补偿；ES 高于本轮扫描版本时认为扫描结果可能过时，本轮跳过；相同版本字段不一致时记录差异并允许同版本补偿。当前页全部处理成功后推进游标，失败则保留原游标等待下一轮重试。

## 5 待确认或待验证事项

- 所有写入路径是否可靠维护 `update_time`，并已建立 `(update_time, consume_id)` 索引？
- 5 分钟安全延迟和 10 分钟重叠窗口是否覆盖实际事务提交、同步积压和调度延迟？
- 游标更新与当前页处理是否能在故障恢复后避免漏查和重复副作用？
- MySQL 与 ES 的业务版本读取方式、字段比较规则及 ES 客户端的 `external`、`external_gte` 行为是否已验证？
- Redis 分片锁的 TTL、续期、持有者校验和异常释放是否已确定？
