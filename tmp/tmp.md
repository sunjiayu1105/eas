3 面试口述版本

### 3.1 先说方案和职责边界

**我们采用按更新时间扫描、直接比较、程序补偿的方案。** 增量校验作为正常同步链路之外的兜底流程，定期从 MySQL 新表读取当前仍存在的记录，再查询 ES 中的对应文档，比较业务版本和字段；发现差异后，按版本规则决定补偿、跳过或记录差异。正常情况下，Binlog、Canal 和 RocketMQ 继续负责 MySQL 到 ES 的实时同步。

**我们不采用按 Binlog 每条变更建立校验任务的方案。** 这种方式会把同一条记录的多次历史变更分别转成任务，可能重复检查同一条记录的当前状态，还需要额外设计任务合并、去重、持久化和失败恢复。当前校验目标是核对 MySQL 与 ES 的当前状态，因此直接扫描 MySQL 新表更符合本流程的职责边界。

### 3.2 再说每轮扫描范围

**每轮先固定一个扫描上限。** 扫描开始时计算扫描截止时间（`scan_end_time`），取当前系统时间减 5 分钟，本轮始终使用这个固定值，只扫描 `update_time <= scan_end_time` 的记录。预留这 5 分钟是为了给正常同步链路留出处理时间，避免刚提交、但 ES 还没有来得及写入的数据马上被判定为差异。

**从第二轮开始，每轮从上一轮游标对应的时间往前回看 10 分钟。** 回看是为了覆盖事务晚提交等情况，并用于确定本轮扫描起点。由于本轮扫描截止时间固定，扫描范围已经确定；起点确定后，本轮按复合游标继续分页即可。

### 3.3 然后说明复合游标和分页

**分页使用 `update_time + consume_id` 复合游标。** `update_time` 决定时间范围，`consume_id` 负责处理同一时间下的多条记录，保证排序和分页边界稳定。每张物理表单独保存自己的游标；一页记录全部处理成功后，才把游标推进到该页最后一条。当前页中途失败时，保留该页开始前的游标，让下一轮从原位置重试；此前已经成功的页面不回滚。

### 3.4 最后说明比较和补偿

**读取一页 MySQL 记录后，逐条查询对应的 ES 文档，比较业务版本和字段。** 两边版本相同且字段一致，说明校验通过；MySQL 版本更高，说明 ES 可能落后，按 MySQL 当前数据自动补偿；ES 版本更高，说明本轮扫描结果可能已经过时，本轮跳过，避免旧数据覆盖新数据；版本相同但字段不一致，则记录差异，并按 MySQL 数据执行同版本补偿。查询或补偿失败时不推进受影响页面的游标，下一轮继续处理。

### 3.5 用一句话收束

这套方案的主线是“固定窗口读取当前数据、用复合游标稳定分页、直接比较版本和字段、按结果自动补偿、成功后推进进度”；它依赖 `update_time` 可靠维护、查询排序稳定，以及比较和补偿具备幂等性。
