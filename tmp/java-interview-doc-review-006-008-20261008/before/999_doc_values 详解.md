# doc_values 详解

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准。Elasticsearch 服务端版本为 **7.17.15**。

## 一、`doc_values` 的定义与生命周期

`doc_values` 是 Elasticsearch 在生成 Lucene Segment 时为字段建立的列式磁盘结构。它按字段保存各个文档的值，使查询过程能够根据 Segment 内部文档编号读取字段值。

可以用逻辑模型理解：

```text
倒排索引：字段值 -&gt; 文档编号，用于检索
doc_values：文档编号 -&gt; 字段值，用于排序、聚合和脚本读取
_source：文档编号 -&gt; 原始 JSON，通常用于返回和重建
```

这只是逻辑模型，实际磁盘结构会根据字段类型采用数值编码、字典、序号和压缩等方式，并不一定是普通数组。

文档写入后，字段值会先暂存在内存中的索引缓冲区。索引缓冲区中的数据达到刷写条件时，会生成新的 Lucene Segment；已开启 `doc_values` 的字段会随该 Segment 生成对应的数据结构。

`Refresh` 的作用是打开包含新 Segment 的搜索视图，使这些数据对搜索可见。一次 Refresh 是否产生新的 Segment，取决于当时是否存在已刷写的缓冲数据，不能认为每次 Refresh 都必然生成 Segment。

多个 Segment 后续合并时，Lucene 会生成新的合并后 Segment，并重新整理对应的 `doc_values`。

`Refresh` 和 `Flush` 不是同一个概念：Refresh 主要负责更新搜索可见视图；Flush 涉及 Lucene 提交和 translog generation 管理。

## 二、结合消费记录说明查询过程

项目按以下字段排序：

```json
"sort": [
  { "tradeTime": "desc" },
  { "consumeId": "desc" }
]
```

示例请求：

```json
{
  "size": 2,
  "query": {
    "bool": {
      "filter": [
        { "term": { "tradeStatus": "90" } },
        {
          "range": {
            "tradeTime": {
              "gte": "2026-09-01T00:00:00+08:00",
              "lt": "2026-09-07T00:00:00+08:00"
            }
          }
        }
      ]
    }
  },
  "sort": [
    { "tradeTime": "desc" },
    { "consumeId": "desc" }
  ]
}
```

面试时可以这样回答：

&gt; 请求先到达协调节点，再转发到相关分片。每个分片通常通过 `tradeStatus` 的倒排索引执行精确过滤；`tradeTime` 是 `date` 字段，时间范围过滤通常使用 Lucene 的 BKD 点值索引。  
&gt;
&gt; 对于匹配文档，Elasticsearch 根据文档在 Segment 内部的编号，从 `tradeTime` 和 `consumeId` 的 `doc_values` 中读取排序值。排序时先比较 `tradeTime`，时间相同再比较 `consumeId`。  
&gt;
&gt; 在 `from` 默认为 `0`、`size` 为 `2` 的示例中，逻辑上可以理解为每个分片按照完整排序元组维护一个最多保存两条候选记录的优先队列。新候选只有在排序上能够进入本分片前两名时，才会替换队列中靠后的记录。  
&gt;
&gt; 各分片将本地候选文档及排序值返回给协调节点，协调节点再按照相同规则合并各分片结果，确定全局前两条记录。若请求需要返回原始文档且 `_source` 已开启，Elasticsearch 最后根据选中的文档编号读取 `_source`，返回完整消费记录。

可以概括为：

```text
倒排索引：通常用于精确条件过滤
BKD 点值索引：通常用于日期范围过滤
doc_values：提供排序字段的值
协调节点：合并各分片候选结果
_source：在需要时返回完整原始文档
```

`doc_values` 负责排序字段值的读取，不负责替代倒排索引或 BKD 点值索引完成普通条件过滤。

## 三、`search_after` 的边界比较

上一页最后一条记录的 `sort` 数组必须以实际响应为准。例如，逻辑上可能表示为：

```text
[2026-09-06T10:00:00+08:00, C1004]
```

实际响应中的日期排序值可能是格式化日期，也可能是其他返回形式。下一页必须原样传递上一页响应中的完整数组，不能自行转换日期格式或调整数组顺序。

由于项目的两个字段都是倒序，候选记录位于边界之后的条件是：

```text
candidate.tradeTime &lt; boundary.tradeTime
或者
candidate.tradeTime == boundary.tradeTime
且 candidate.consumeId &lt; boundary.consumeId
```

例如边界为：

```text
[2026-09-06T10:00:00+08:00, C1004]
```

则：

| 候选排序值 | 是否位于边界之后 | 原因 |
|---|---|---|
| `[09:59:00, C9999]` | 是 | 时间更早 |
| `[10:00:00, C1003]` | 是 | 时间相同且编号更小 |
| `[10:00:00, C1004]` | 否 | 与边界完全相同 |
| `[10:00:00, C1005]` | 否 | 编号更大，倒序下排在边界之前 |
| `[10:01:00, C1000]` | 否 | 时间更晚，倒序下排在边界之前 |

“位于边界之后”只表示可以参与下一页的候选竞争，并不表示一定出现在最终响应中。`size` 为 `2` 时，每个分片会在排除边界之前及等于边界的记录后，按照完整排序元组维护边界之后的前两条候选；协调节点再合并各分片候选结果。

`search_after` 不是把多个字段分别独立过滤，而是把排序字段组成一个整体排序元组。它也不是按页码跳转，而是从上一页最后一条记录之后继续读取。

如果使用 `from`，分片候选队列通常需要覆盖 `from + size`；当前示例没有设置 `from`，所以按 `size: 2` 说明。

## 四、排序稳定性与分页一致性

`tradeTime DESC, consumeId DESC` 组成完整排序键。稳定使用 `search_after` 时，排序字段应为单值、不能缺失，并且完整排序组合应尽量唯一。

本项目通过业务设计保证 `consumeId` 全局唯一，因此可以在相同 `tradeTime` 下继续区分顺序。但 Mapping 和 `doc_values` 本身不会自动保证字段值唯一，也不会自动补齐缺失值。如果两条文档的完整排序值完全相同，`search_after` 可能无法稳定区分它们，从而产生重复或遗漏风险。

下一页请求必须保持：

- 查询条件一致；
- 排序字段一致；
- 排序方向一致；
- `search_after` 使用上一页响应中的完整 `sort` 数组。

当前方案不使用 PIT（Point in Time，一种固定搜索视图的机制），因此没有固定跨请求的索引视图。如果翻页期间新增或更新的数据在后续请求中变得可见，结果顺序可能变化，从而出现重复或遗漏；Refresh 本身并不必然导致这种问题。
