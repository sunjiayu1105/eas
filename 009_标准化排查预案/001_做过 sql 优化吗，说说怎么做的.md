# 001_做过 sql 优化吗，说说怎么做的

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准，本文使用 MySQL 8.0.33 的 InnoDB 语义。现有材料提供优化方法，没有具体慢 SQL 的实测记录；以下口述是方法框架，案例为教学示例，不能据此声称已完成某次生产优化或取得特定收益。

## 1 问题

面试被问“做过 SQL 优化吗，说说怎么做的”时，如何讲清定位、分析、修改和验证过程？

## 2 高级 Java 面试核心考点

- 用慢日志、调用频率和耗时区分高成本查询、锁等待与应用侧等待。
- 根据执行计划、数据分布和完整查询条件选择索引及改写方案。
- 保持结果语义、分页顺序和事务原子性，评估索引的写入成本。
- 区分估算计划与真实执行，在可比条件下验证结果和性能。

## 4 详细方案

### 4.1 定位问题并保存优化前基线

收集慢日志或监控中的 SQL、真实参数、调用次数、耗时、返回记录数和影响的业务入口，再关联应用调用链。不能只挑单次最慢的一条；高频查询即使单次不慢，累计资源消耗也可能很大。

先区分数据库扫描计算、锁等待、网络传输和连接池等待。连接池中排队不等于数据库已经执行该 SQL；慢日志也不能独自解释应用端全部耗时。若请求跨分片执行，应先确认分片键、路由数量及实际下发 SQL，再分析单个物理表的计划，不能只优化一条物理 SQL 就声称解决了整体跨分片成本。

同时确认表结构、已有索引、数据分布、排序要求及结果语义。查询是否应使用已有 ES 副本属于业务查询架构问题，须按已确认的路由与一致性要求判断，不能把模糊查询或深分页直接等同于必须改走 ES。

例如接口耗时高，但数据库执行很快、应用连接等待明显，此时继续加索引未必解决主要瓶颈。本文未读取实际慢日志、执行计划或监控，项目优化案例仍待补充。

### 4.2 使用执行计划识别主要成本

SQL 优化不能只靠猜测，应结合慢日志、`EXPLAIN`、必要时的 `EXPLAIN ANALYZE` 以及实际耗时验证。

传统表格形式的 `EXPLAIN` 中，需要重点关注：

- `type`：访问方式，例如 `const`、`ref`、`range`、`ALL`；
- `key`：优化器在该次执行计划中选择使用的索引；
- `key_len`：实际使用的索引长度，可辅助判断联合索引使用情况，但不能作为唯一判断依据；
- `rows`：优化器估算需要检查的记录数；
- `filtered`：经过当前表其他过滤条件后，预计保留的记录百分比；
- `ref`：索引比较值的来源，例如常量、前面关联表的字段或表达式；
- `Extra`：是否出现 `Using temporary`、`Using filesort`、`Using index` 等信息。

例如：

```text
rows = 30000
filtered = 10
```

可以近似理解为当前表过滤后预计有：

```text
30000 × 10% ≈ 3000
```

条记录继续参与后续处理。但这是优化器估算值，不等于实际扫描行数。对于多表连接，还要结合前面表产生的行数以及当前表被访问的次数进行判断。

`key` 表示优化器在该次 `EXPLAIN` 中选择的索引，属于执行计划信息，不等同于已经通过实际运行测得的性能结果。需要结合 `EXPLAIN ANALYZE`、慢日志和实际耗时进一步验证。

`ref = func` 表示索引比较值需要经过函数或表达式计算，可能与函数调用或类型转换有关，但不能仅凭这一项直接断定存在隐式类型转换。

`Extra = Using index` 通常表示查询所需字段可以直接从索引返回，即形成覆盖索引，从而减少回表。

`Using temporary` 和 `Using filesort` 不一定绝对错误。`Using filesort` 表示采用了额外的排序过程，也不一定意味着真的发生了磁盘文件排序。是否需要优化，要结合数据量、排序或分组成本以及实际耗时判断。

MySQL 从 **8.0.18** 开始支持 `EXPLAIN ANALYZE`。在 MySQL 8.0 中，它使用 `TREE` 格式，并且会实际执行查询，提供实际耗时、输出行数和循环次数等信息。因此，生产环境使用前需要评估查询耗时、锁和资源影响。

最终应将执行计划、慢日志、实际耗时、数据分布和业务访问模式结合起来判断，不能只因为出现某一个 `Extra` 值，或者只因为 `type` 不是某个级别，就直接认定 SQL 一定存在问题。

`EXPLAIN ANALYZE` 中的实际行数通常是对应算子输出的行数，不应一律当作底层扫描行数；多次循环时，时间和行数需要结合 `loops` 理解，包含子算子时间的父子节点耗时也不能简单相加。先定位成本高的算子，再用实际参数与数据分布解释原因。

来源：[EXPLAIN Statement](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/explain.html)、[EXPLAIN Output Format](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/explain-output.html)。本次核对了计划字段、估算值及 ANALYZE 的执行信息；未在数据库运行待优化 SQL。

### 4.3 设计合适的索引

设计索引时，应重点分析以下字段：

- `WHERE` 中的过滤字段；
- `JOIN ON` 中的连接字段；
- `ORDER BY` 中的排序字段；
- `GROUP BY` 中的分组字段；
- 高频查询字段及其数据分布。

同时还要考虑：

- 等值条件和 `IN` 条件；
- 范围条件；
- 字段选择性；
- 排序和分组是否能够利用索引；
- 是否能够形成覆盖索引；
- 索引带来的存储、写入和维护成本。

联合索引一般需要结合最左匹配原则设计。常见的设计起点是将等值条件放在前面，再结合范围条件、排序字段和查询字段进行调整，但这不是固定模板。范围条件可能影响后续索引列对排序的利用，低选择性字段在某些场景下也可能不适合作为索引前导列，最终仍要结合数据分布和执行计划验证。

### 4.4 让普通索引更容易用于条件查找

应尽量避免在索引列上使用函数或表达式，例如：

```sql
DATE(trade_time) = :tradeDate
```

在没有函数索引或对应生成列索引的情况下，可以改成左闭右开的时间范围：

```sql
trade_time >= :startTime
AND trade_time < :endTime
```

这样通常更有利于普通 B-Tree 索引进行范围查找，也能避免时间边界问题。

还要注意隐式类型转换。例如，字段是字符类型，但参数使用数字类型时，数据库可能对字段进行转换，从而影响索引使用。不过实际影响取决于字段类型、参数类型、数据库版本、字符集和执行计划，不能仅凭 SQL 形式直接下结论。

`LIKE` 查询应尽量避免左模糊：

```sql
LIKE '%abc'
```

这种写法通常不能利用普通 B-Tree 索引做前缀范围定位，但仍可能扫描索引；不能等同于执行计划绝对不会选索引。下面的前缀匹配通常更容易利用索引：

```sql
LIKE 'abc%'
```

实际是否使用索引，还需要结合字段排序规则、索引定义和执行计划判断。

### 4.5 按需减少回表

不要随意使用：

```sql
SELECT *
```

应只查询业务实际需要的字段，并在合适的场景下设计覆盖索引。

以 MySQL InnoDB 为例，二级索引通常包含主键值。当查询需要读取二级索引之外的字段时，数据库通常还需要根据主键访问聚簇索引，这个过程称为回表。

如果查询所需的字段，包括返回、过滤、排序等操作涉及的字段，都能由索引提供，就可能形成覆盖索引，减少回表。但覆盖索引会增加存储空间、写入成本和维护成本，因此应结合查询频率、数据量和实际收益评估。

### 4.6 优化连接与中间结果

连接优化时，应尽量减少连接前的中间结果集。

对于基于索引查找的嵌套循环连接，应重点检查被驱动表连接字段是否有合适的索引。连接顺序和连接算法由优化器决定，不能仅根据 SQL 的书写顺序判断。

“小结果集驱动大表”是常见优化方向，但不是所有连接场景都适用。最终应结合执行计划中的连接顺序、连接算法、访问类型、扫描行数和实际耗时进行验证。

### 4.7 保持 IN、EXISTS 改写的语义

如果右侧是明确的值集合，例如消费类型，可以使用：

```sql
trade_type IN ('消费', '撤销', '退货')
```

如果业务表达的是“是否存在关联记录”，例如商户是否存在异常交易，更适合使用 `EXISTS`。

`EXISTS` 只关心是否存在匹配记录，数据库通常可以在找到匹配记录后停止继续查找，但优化器也可能将其改写为半连接等执行方式，实际仍应以执行计划为准。

反向判断时通常优先考虑 `NOT EXISTS`。原因是 `NOT IN` 存在 `NULL` 陷阱：如果子查询结果包含 `NULL`，比较结果可能变成 `UNKNOWN`，导致记录被过滤。

即使子查询结果不含 `NULL`，如果外层比较字段允许为 `NULL`，`NOT IN` 和使用普通等号关联的 `NOT EXISTS` 也可能返回不同结果。因此，改写前还要确认内外两侧字段的可空性，以及业务是否需要保留外层的 `NULL` 记录。

`IN` 和 `EXISTS` 的性能不能简单绝对比较，最终要结合数据量、索引、数据分布和执行计划判断。

### 4.8 根据业务选择分页方式

小数据集或需要直接跳页时，可以使用稳定排序加 `OFFSET`：

```sql
ORDER BY id ASC
LIMIT :offset, :pageSize
```

这里假设 `id` 唯一，或者排序字段组合能够形成唯一、稳定的顺序。

大数据集按顺序翻页时，更适合使用游标分页。下面的示例假设 `create_time` 和 `id` 不允许为 `NULL`，`id` 具有唯一性，并且查询结果按照升序排列：

```sql
WHERE (create_time, id) > (:lastCreateTime, :lastId)
ORDER BY create_time ASC, id ASC
LIMIT :pageSize
```

如果需要展开写法，可以写成：

```sql
WHERE (
    create_time > :lastCreateTime
    OR (
        create_time = :lastCreateTime
        AND id > :lastId
    )
)
ORDER BY create_time ASC, id ASC
LIMIT :pageSize
```

通常需要结合排序字段评估 `(create_time, id)` 联合索引。使用行构造器比较时，实际索引利用效果仍应通过执行计划验证。如果查询还包含其他过滤条件，索引顺序应根据完整查询条件和执行计划重新设计。

如果使用降序排序，游标比较条件也需要相应调整；如果 `create_time` 允许为 `NULL`，还需要明确处理 `NULL` 的排序语义。

`OFFSET` 分页在偏移量较大时，数据库通常仍需要扫描并跳过前面的记录，因此深分页场景下性能可能下降。

游标分页可以减少深分页扫描，但如果分页期间数据发生新增、删除或排序字段更新，多次查询未必读取同一个数据快照。是否需要一致性快照，还要结合事务隔离级别和业务要求判断。

示例中的 `:参数名` 是参数绑定的示意写法，不是可以直接粘贴到 MySQL 客户端执行的原生参数语法。

### 4.9 控制事务大小而不破坏原子性

大事务可能增加：

- 锁等待；
- Undo Log；
- 回滚成本；
- 事务日志压力；
- 主从复制延迟。

因此，批量操作通常应根据数据量分批处理，并控制单批次耗时、锁持有时间和事务日志大小。

但分批提交会改变事务边界。如果业务要求所有操作在同一个事务中整体提交或回滚，就不得通过分批提交破坏原子性。

只有在业务允许拆分事务、接受中间状态时，才可以考虑分批提交，并按需设计重试、幂等和补偿机制。补偿机制不等同于数据库事务回滚。

### 4.10 教学案例：按商户查询一天的交易

本例假设教学表 `trade_record` 使用 InnoDB，`id` 为主键，`merchant_id` 为整数，`trade_time` 为非空 DATETIME。页面按时间倒序返回 ID、交易时间和金额，允许下一页查询。以下日期、商户 ID 和页大小 50 条均为教学值，不是生产配置；具体字段、查询频率和数据分布尚未确认。

**定位可疑点**

```sql
-- 改写前：对 trade_time 做函数计算，不利于普通时间索引范围查找。
SELECT id, trade_time, amount
FROM trade_record
WHERE merchant_id = 1001
  AND DATE(trade_time) = '2026-01-01'
ORDER BY trade_time DESC, id DESC
LIMIT 50;
```

先检查实际计划，确认是否扫描过多记录或存在高成本排序。若主要耗时来自锁等待，不能仅凭函数条件就认定它是这次慢查询的根因。函数索引或对应生成列索引也可能支持表达式查询，必须先核对现有索引。

**保持语义后改写，并提出候选索引**

```sql
EXPLAIN
SELECT id, trade_time, amount
FROM trade_record
WHERE merchant_id = 1001
  AND trade_time >= '2026-01-01 00:00:00'
  AND trade_time <  '2026-01-02 00:00:00'
ORDER BY trade_time DESC, id DESC
LIMIT 50;

-- 候选索引，仅在测试环境评估，不表示已经上线。
CREATE INDEX idx_merchant_time_id
ON trade_record (merchant_id, trade_time, id);
```

商户等值条件确定前缀，时间条件限定范围，`trade_time, id` 与唯一稳定排序一致；升序索引可能通过反向扫描支持这组同向降序排序，实际计划仍需验证。左闭右开的日期范围包含整天并排除次日，使用 TIMESTAMP 或跨时区查询时还要统一业务日期、连接时区和边界转换。

本例索引不包含 amount，不能声称已经实现覆盖索引；是否把金额加入索引，要比较回表收益与索引宽度、写入成本。InnoDB 二级索引携带主键，实际评估时也应检查现有 `(merchant_id, trade_time)` 是否已能满足条件和顺序，避免机械新增近似重复索引。

**验证结论而不编造结果**

比较改写前后的记录 ID、金额、顺序和日期边界，再观察计划、实际耗时及读取量。预期是改善范围定位和排序利用，但如果查询本来只涉及很少数据，收益可能有限。没有测试数据前，不填写“从几秒降到几毫秒”或“提升百分之多少”。

该例只说明一次可验证的优化思路，不能作为“我在项目中做过”的事实。实际面试经历需要补充对应业务、原 SQL、执行计划、修改理由、验证记录与本人负责的工作。

### 4.11 验证效果并保留回退方式

先核对结果是否等价，再比较性能。检查重复记录、NULL、排序稳定性、时间边界和事务原子性；例如把 NOT IN 改成 NOT EXISTS 后少过滤了一类 NULL 记录，即使速度更快，也不能算等价优化。

性能对照应保持参数、数据规模、统计信息与并发负载可比，区分缓存冷暖，进行多次观测，不能用一次偶然的耗时证明改善。记录实际耗时、扫描或读取量、调用次数、锁等待、CPU/I/O，并观察新增索引对写入和存储的影响。P95 指 95% 请求不超过的耗时，能补充平均值遗漏的尾部延迟；是否采用该指标取决于现有监控口径。

SQL 改写由研发核对业务语义；生产索引变更按既有发布流程与 DBA 协作，评估建索引耗时、资源和锁影响。上线后观察同类参数和负载，异常时回退应用查询或按评估方案处置索引，不把“新增索引”当作没有发布成本的操作。本文未执行任何 DDL 或性能测试。
