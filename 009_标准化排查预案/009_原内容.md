# 功能描述
 系统持续巡检优化，通过发现、定位并解决 OOM、数据库死锁、索引失效、恶意访问请求等问题，提升系统的稳定性和健壮性，同时将处理流程沉淀为标准化排查预案，使团队整体问题排查效率提升约 80%。  

# 相关梳理


# 1 、业务背景与痛点
系统长期运行过程中，会频繁出现各类 “ 隐性故障”—— 比如 OOM（ 内存溢出） 导致服务崩溃 、数据库死锁造成业务卡顿 、索引失效引发查询变慢 、恶意请求攻击拖垮接口等 。这些问题的痛点在于：

1 、排查效率低：新手排查 OOM / 死锁可能要几小时甚至几天，依赖资深工程师经验；

2 、无标准化流程：每次排查都 “凭感觉 、查日志 、试运气 ”， 团队排查效率参差不齐；

3 、稳定性差：故障反复出现，且处理不及时，影响业务可用性。





核心诉求：把 “靠经验排查” 变成 “按标准流程排查” ，提升效率 + 保障系统稳定。



## 2 、技术方案：系统持续巡检 + 问题排查标准化
### 第一步：建立 “持续巡检体系” ，主动发现问题
不再等故障发生后被动处理，而是通过自动化工具 + 人工定期巡检，主动发现潜在问题：

自动化巡检：部署监控工具（ 如 Prometheus 、ELK 、SkyWalking）， 

实时监控：内存指标（JVM 堆内存 / 非堆内存）→ 提前预警 OOM；

数据库指标（锁等待数 、死锁次数 、索引命中率）→ 发现死锁 / 索引失效；

接口访问指标（ 异常 IP 访问频率 、非常规请求参数）→ 识别恶意访问；

人工定期巡检：每周 / 每月对系统核心链路做全量巡检，补充自动化监控的盲区。





### 第二步：梳理 “ 问题定位方法论” ，统一排查路径
针对高频问题（ OOM 、数据库死锁 、索引失效 、恶意请求），总结标准化定位步骤：表格

| 问题类型 | 标准化定位步骤（ 学员可直接套用） |
| --- | --- |
| OOM | 1. 抓取堆转储文件（jmap）；<br/>2. 分析大对象 / 内存泄漏点（ MAT 工具）；<br/>3. 定位代码中未释放的对象 |
| 数据库死锁 | 1. 执行 show engine innodb status 查死锁日志；<br/>2. 定位死锁 SQL；<br/>3. 分析事务隔离级别 / 加锁顺序 |
| 索引失效 | 1. 执行 explain 分析 SQL 执行计划；<br/>2. 检查隐式转换 / 范围查询 / 索引选择性；<br/>3. 验证统计信息是否过期 |






| 恶意访问请求 | 1. 查 Nginx / 网关日志定位异常 IP / 请求特征；<br/>2. 分析请求频率 / 参数规律；<br/>3. 验证是否为爬虫 / 攻击 |
| --- | --- |








### 第三步：输出 “无脑排查预案” ，落地解决方案
将 “定位步骤 + 解决方案 + 验证方法” 整理成标准化 、傻瓜式的排查预案（ 比如文档 / 流程图），核心特点：无技术门槛：新手按步骤操作就能排查，无需资深经验； 闭环落地：每个预案包含 “发现→定位→解决→验证”全流程；

### 第四步：持续优化， 迭代预案
将新出现的问题纳入巡检范围，更新排查预案，形成 “发现问题→沉淀预案→提升效率” 的闭环 。新排查预案，形成 “发现问题→沉淀预案→提升效率” 的闭环。



## 3 、实现效果与价值
系统稳定性提升：主动巡检提前发现并解决 OOM 、死锁等问题，故障发生率下降， 系统健壮性显著提升；

排查效率质的飞跃：团队不再依赖个人经验，按 “无脑预案” 排查问题，整体排查效率提升 80%（ 比如原来排查 OOM 要 4 小时，现在仅需 48 分钟）；

能力标准化：新手快速掌握核心问题排查方法， 团队技术能力拉齐 ，减少对资深工程师的依赖。
