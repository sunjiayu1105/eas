## 1 问题

JOIN 查询慢时，应该从哪些方面优化？

## 2 高级 Java 面试核心考点

- 连接中间结果、连接顺序和算法。
- 索引嵌套循环连接中的被驱动表索引。

## 3 面试口述精炼版本

口述内容字符数：176

**根据连接方式定位成本**

我先看执行计划中的连接顺序、连接算法，以及各步实际处理的行数，判断是否产生了过大的中间结果。对于索引嵌套循环连接，再检查被驱动表的连接字段有没有合适的索引，减少重复查找成本。

“小结果集驱动大表”只是常见思路，不能直接按表总行数或 SQL 书写顺序下结论。需要结合过滤后的结果量和实际计划验证，改写时还要保证连接结果不变。

详见：[详细方案](<D:/000/sources/eas/009_标准化排查预案/004_SQL 优化_如何优化JOIN查询.md:28>)。

## 4 详细方案

### 4.1 优化连接与中间结果

连接优化时，应尽量减少连接前的中间结果集。

对于基于索引查找的嵌套循环连接，应重点检查被驱动表连接字段是否有合适的索引。连接顺序和连接算法由优化器决定，不能仅根据 SQL 的书写顺序判断。

“小结果集驱动大表”是常见优化方向，但不是所有连接场景都适用。最终应结合执行计划中的连接顺序、连接算法、访问类型、扫描行数和实际耗时进行验证。

### 4.2 如何理解重复查找成本

例如过滤后的商户集合逐个查询交易表：采用索引嵌套循环时，交易表商户字段的索引可能减少每次查找的工作量。但是否采用这种算法、过滤后有多少商户，必须看实际计划；不能据此宣称所有 JOIN 都应固定商户表为驱动表。
