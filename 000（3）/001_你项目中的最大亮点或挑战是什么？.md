# <font style="color:rgb(0, 0, 0);">面试回答</font>
<font style="color:rgb(0, 0, 0);">E账通项目里，我认为技术难度比较大的一个点，是消费记录的海量数据治理和查询性能优化。</font>

## <font style="color:rgb(0, 0, 0);">单库单表存在的问题</font>
<font style="color:rgb(0, 0, 0);">因为消费记录既要支持联机交易快速写入，又要支持后台按电子账户账号、身份证号、用户名称、商户名称、订单号、交易时间、交易状态、金额等条件进行复杂查询，后续还要用于交易回查、撤销、退货、对账清算、统计报表、异常回查等。</font>

<font style="color:rgb(0, 0, 0);">如果所有数据都放在 MySQL 单库单表中，随着数据量增长，单表写入、索引维护、复杂查询和深分页都会越来越慢。</font>

## <font style="color:rgb(0, 0, 0);">优化方案</font>
<font style="color:rgb(0, 0, 0);">所以我们把消费记录做成了“交易主库 + 查询副本”两套模型。</font>

<font style="color:rgb(0, 0, 0);">在 MySQL 存储层，我们通过 ShardingSphere-JDBC 对消费明细表做了分库分表，设计成 2 个库，每个库 16 张表，一共 32 个物理分片，分片建为商户 id，因为大多数查询场景都是根据商户维度来进行查询的，分片策略为商户 id hash 取模。另外，也有订单回查这些场景，查询条件只有消费记录 id 的。那我们在设计消费记录主键时，就使用 “雪花算法 + 基因法”，通过雪花算法生成一个全局唯一 snowflakeid 后，再把 shardindex 固定 2 位拼接到 snowflakeid 后面，这样后面根据消费记录 id 回查订单时，也可以精准路由到物理分片。</font>

<font style="color:rgb(0, 0, 0);">在复杂查询层，我们</font><font style="color:rgb(223, 42, 63);">通过 Canal 监听 MySQL Binlog</font><font style="color:rgb(0, 0, 0);">，将消费记录同步到 Elasticsearch。后台消费列表允许秒级延迟，所以由 ES 承接商户、订单、用户、时间、状态、金额区间等多条件组合查询，以及订单号、手机号等模糊检索。</font>

~~<font style="color:rgb(223, 42, 63);">ES 中会同步交易金额、实付金额、优惠金额、手续费、退款金额等字段，金额统一按分存储为 long，避免浮点精度问题。</font>~~

<font style="color:rgb(0, 0, 0);">深分页使用 search_after，避免传统 from + size 随着页码加深而越来越慢；</font>

<font style="color:rgb(0, 0, 0);">ES 历史数据再结合冷热分离和索引生命周期管理，降低长期存储成本。</font>

<font style="color:rgb(0, 0, 0);">核心边界是，MySQL 始终是交易和资金的事实来源，负责交易写入、状态变更、撤销退货、异常回查、对账和清算；ES 只是查询副本，只承担允许短暂延迟的后台复杂查询，不参与资金真实性判断。</font>

## <font style="color:rgb(0, 0, 0);">优化结果</font>
<font style="color:rgb(0, 0, 0);">这个方案最终解决了海量消费记录下写入压力大、后台复杂查询慢、深分页慢和历史数据存储成本高的问题。</font>
