# 007_线程池的拒绝策略有哪几种？

以下内容按照当前项目 `AGENTS.md` 项目级规则中规定的技术栈版本为准，使用 Java 8。本文说明 ThreadPoolExecutor 的内置策略，不代表项目已选用某种策略；配置为教学示例，未执行运行测试。

## 1 问题

线程池的拒绝策略有哪几种，各自如何处理任务？

## 2 面试口述精炼版本

口述内容字符数：244

**触发条件**

线程池无法接收任务时触发拒绝策略，例如线程数和队列达到上限，或线程池已关闭。

**AbortPolicy**

默认策略，抛出 RejectedExecutionException，让调用方感知拒绝。

**CallerRunsPolicy**

未关闭时，由提交任务的调用者线程同步执行，使它暂时无法继续提交任务；关闭后丢弃。

**DiscardPolicy**

直接丢弃当前任务，不抛异常。

**DiscardOldestPolicy**

未关闭时，移除队头任务，再尝试提交当前任务；关闭后丢弃当前任务。队头不一定是最早提交的任务。

## 3 详细方案

### 3.1 拒绝策略何时触发

拒绝策略通过 RejectedExecutionHandler 接口处理线程池无法接收的任务。常见原因是线程池已关闭，或队列不能接收任务且线程池无法再创建工作线程。

不能仅用“队列满且线程忙”判断拒绝：如果线程数还未达到 maximumPoolSize，线程池仍可能创建线程接收任务。以下示例统一采用核心线程数为 1、最大线程数为 1、容量为 1 的 ArrayBlockingQueue；假设线程池正常运行且任务 A 一直未结束，A 正在执行、B 已排队，再提交 C 时才触发策略。所有数量均为教学示例。

### 3.2 AbortPolicy：抛异常，明确反馈拒绝

这是 ThreadPoolExecutor 的默认拒绝策略，会抛出 RejectedExecutionException。在上述示例中，提交 C 的 execute 调用抛异常，C 没有被线程池接收；调用方可以捕获异常并决定返回失败或进行补偿。

抛异常并不等于自动重试，也不等于任务已持久化。如果业务不允许丢任务，需要调用方另行实现可追踪的失败处理，不能仅依靠策略名称判断可靠性。

来源参考：[Java 8 AbortPolicy API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.AbortPolicy.html)。

### 3.3 CallerRunsPolicy：提交任务的线程亲自执行

**调用者是谁**

调用者线程就是执行 pool.execute(task) 的线程，可能是 main 线程、处理请求的线程，也可能是另一个线程池的工作线程。提交的是 Runnable 任务，不是向线程池提交一个新线程。

**为什么提交速度会下降**

在上述示例中，如果线程池未关闭，提交 C 的线程会在 execute 调用过程中同步执行 C；等 C 执行结束或抛出异常后，该调用才返回或抛出。调用者因此不能继续执行后续的提交代码，形成对该提交者的反馈控制。它不是阻塞等待队列腾出位置，也不会额外创建线程执行 C。

若调用者是请求处理线程，请求响应时间可能被拉长。A 仍可能在工作线程执行，C 则在调用者线程执行，因此总任务并发数可能超过 maximumPoolSize；该参数只限制线程池自己的工作线程数。多个提交者还可能分别执行被拒任务，不能把此策略当作严格的全局并发限制。

**关闭后的边界**

线程池已关闭时，该策略不执行任务，而是直接丢弃。下面是其核心处理逻辑，不是完整的独立程序：

```java
public void rejectedExecution(Runnable task, ThreadPoolExecutor pool) {
    if (!pool.isShutdown()) {
        task.run(); // 在当前提交任务的线程中同步执行
    }
}
```

这里的“拒绝策略触发”不等于任务必然不执行。CallerRunsPolicy 就是在未关闭时改由调用者执行；关闭后也不会自动改用 AbortPolicy 抛出拒绝异常。

来源参考：[Java 8 CallerRunsPolicy API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.CallerRunsPolicy.html)。

### 3.4 DiscardPolicy：直接丢弃当前任务

在上述示例中，C 被丢弃，A 和 B 不受这次策略调用影响。策略本身不抛拒绝异常，不记录日志，也不会自动重试；因此 execute 正常返回不代表任务已经执行。

它只适合业务明确允许丢弃的任务，不能未经业务确认就用于必须完成的任务。线程池关闭后触发该策略，同样直接丢弃当前任务。

来源参考：[Java 8 DiscardPolicy API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.DiscardPolicy.html)。

### 3.5 DiscardOldestPolicy：移除队头，再次尝试提交

未关闭时，它先调用队列的 poll 移除队头任务，再调用 execute 尝试提交当前任务。在上述示例中，B 在队头，会被移除，随后重新尝试接收 C；A 是正在执行的任务，不会因此被停止。

“Oldest”不能理解为所有任务中最早提交的那个。对于先进先出队列，队头通常是最早入队的等待任务；对于优先级队列，队头由优先级决定，可能恰好移除了最优先的任务。

再次提交仍要经过接收流程，不能保证一定成功。例如其他提交者可能抢先占用释放的队列位置，进而再次触发策略。不应将它与 SynchronousQueue 直接搭配：该队列不存储任务，在持续饱和、无法交接的情况下，poll 无法腾出等待空间，反复调用 execute 可能导致递归和栈溢出。

线程池已关闭时，不移除队头，也不重新提交，直接丢弃当前任务。

来源参考：[Java 8 DiscardOldestPolicy API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.DiscardOldestPolicy.html)；实现参考：[OpenJDK 8u ThreadPoolExecutor 的内置策略](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/ThreadPoolExecutor.java)。

### 3.6 如何配置，以及 submit 的注意事项

以下片段放在方法中使用，并导入 java.util.concurrent 包中的对应类型。核心线程数和最大线程数均为 1，队列容量为 1，keepAliveTime 为 0 秒；这些是用于说明饱和场景的示例参数，不是生产推荐值。示例未开启核心线程超时。

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        1, 1,
        0L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<Runnable>(1),
        new ThreadPoolExecutor.AbortPolicy()); // 显式指定拒绝策略
// 使用方在不再提交任务后调用 pool.shutdown()，并按需要等待任务结束。
```

可以通过构造器指定策略，也可以调用 setRejectedExecutionHandler 更换策略；生产策略应根据是否允许丢任务、是否允许占用调用者线程等业务约束选择，本文不替项目做选择。

submit 通常先将任务包装为 FutureTask，再交给 execute。如果策略静默丢弃任务，又没有取消该 Future，返回的 Future 可能一直未完成，调用无超时的 get 就可能一直等待。DiscardOldestPolicy 移除的队头任务若是 FutureTask，也不会自动被取消。CallerRunsPolicy 在关闭后丢弃任务时，同样存在此风险。

因此，不能用“submit 返回了 Future”证明任务已执行，也不能把静默丢弃理解成 Future 会自动返回失败。AbortPolicy 则在提交阶段抛出拒绝异常，不会正常返回该次提交的 Future。

来源参考：[Java 8 AbstractExecutorService API：submit](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/AbstractExecutorService.html)、[Java 8 Future API](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)。
