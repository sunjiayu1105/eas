## 4 详细方案

### MySQL：SELECT ... FOR UPDATE 与快照读

#### 1. SELECT ... FOR UPDATE 是什么？

`SELECT ... FOR UPDATE` 是 InnoDB 中的**锁定读**，也叫**当前读**。

它通常放在事务里使用，作用是：

查询最新数据的同时，对相关记录加排他锁，防止其他事务同时修改这些数据。

示例：

```
START TRANSACTION;

SELECT *
FROM account
WHERE id = 1
FOR UPDATE;

UPDATE account
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

意思是：先锁住 `id = 1` 这行数据，在当前事务提交或回滚之前，其他事务不能修改这行数据。

---

#### 2. 为什么要放在事务里？

如果没有显式开启事务，并且 `autocommit = 1`，每条 SQL 都是一个独立事务。

```
SELECT *
FROM user
WHERE id = 1
FOR UPDATE;
```

这条 SQL 执行完就自动提交，锁也马上释放，对后续业务逻辑基本没有保护意义。

所以实际使用时一般这样写：

```
START TRANSACTION;

SELECT *
FROM user
WHERE id = 1
FOR UPDATE;

-- 根据查询结果执行业务修改

COMMIT;
```

---

#### 3. FOR UPDATE 锁的是什么？

`FOR UPDATE` 锁的不是字段，而是**索引记录或索引范围**。

常见锁类型有三种：

|   |   |
|---|---|
|锁类型|含义|
|记录锁|锁住已经存在的索引记录|
|间隙锁|锁住两个索引值之间的空隙|
|Next-Key Lock|记录锁 + 间隙锁|

锁一般在事务 `COMMIT` 或 `ROLLBACK` 后释放。

---

#### 4. FOR UPDATE 的锁范围怎么判断？

锁范围主要看三个因素：

索引、查询条件、执行计划。

最核心的判断逻辑是：

如果是**唯一索引等值查询，并且命中具体记录**，通常只锁一行；
如果不是这种情况，InnoDB 可能会锁扫描到的索引范围；
如果没有合适索引，就可能扫描聚簇索引，锁住大量记录，效果接近锁表。

---

#### 5. 唯一索引等值查询：通常只锁一行

```
SELECT *
FROM user
WHERE id = 1
FOR UPDATE;
```

如果 `id` 是主键，并且 `id = 1` 这条记录存在，通常只锁这一行。

面试说法：

如果使用主键或唯一索引做等值查询，并且命中具体记录，`FOR UPDATE` 通常只锁命中的那一行，锁范围比较小。

补充：

如果唯一索引等值查询没有命中记录，在 RR 隔离级别下，可能会锁住对应的索引间隙，防止其他事务插入这条记录。

例如：

```
SELECT *
FROM user
WHERE id = 10
FOR UPDATE;
```

如果 `id = 10` 不存在，InnoDB 可能会锁住 `10` 应该插入的位置附近的间隙，防止其他事务插入 `id = 10`。

---

#### 6. 什么时候会锁一段索引范围？

这里建议这样记：

只要不是“唯一索引等值命中一行”这种最小锁范围，其他情况都可能扩大锁范围。
如果执行计划走了某个索引，就可能锁住这个索引上扫描到的范围。

### 情况一：普通索引范围查询

```
SELECT *
FROM user
WHERE age BETWEEN 18 AND 25
FOR UPDATE;
```

如果 `age` 有普通索引，MySQL 可能走 `age` 索引范围扫描。

这时锁的是：

`age` 索引上 `18 ~ 25` 这一段范围。

---

### 情况二：普通索引等值查询

```
SELECT *
FROM user
WHERE age = 18
FOR UPDATE;
```

如果 `age` 是普通索引，因为普通索引允许重复值，所以即使是等值查询，也不一定只锁一行。

它可能锁住：

`age = 18` 的多条记录，以及相关索引间隙。

所以普通索引等值查询，也可能比主键等值查询锁得更多。

---

### 情况三：唯一索引或主键的范围查询

```
SELECT *
FROM user
WHERE id BETWEEN 10 AND 20
FOR UPDATE;
```

即使 `id` 是主键，只要是范围查询，也可能锁住：

`id` 索引上 `10 ~ 20` 这一段范围。

所以不能简单说：

主键查询就一定只锁一行。

要看是不是**等值查询**，以及是否**命中具体记录**。

---

#### 7. 什么是 Next-Key Lock？

`Next-Key Lock = 记录锁 + 间隙锁`。

比如 `age` 索引顺序是：

```
10 -> 18 -> 20 -> 25 -> 30
```

执行：

```
SELECT *
FROM user
WHERE age BETWEEN 18 AND 25
FOR UPDATE;
```

在默认 `REPEATABLE READ` 隔离级别下，可能锁住：

```
(10,18]、(18,20]、(20,25]
```

其中：

|   |   |
|---|---|
|部分|含义|
|18、20、25|已有记录|
|(10,18)、(18,20)、(20,25)|索引间隙|

这样做的目的是防止其他事务插入 `19、22、24` 这类新数据，从而避免幻读。

需要注意：

`next-key lock` 的粒度是“当前记录 + 前面的间隙”，所以有些不完全满足查询条件的间隙，也可能被顺带锁住。

---

#### 8. 没有合适索引时锁什么？

例如：

```
SELECT *
FROM user
WHERE age BETWEEN 18 AND 25
FOR UPDATE;
```

如果 `age` 没有索引，那么它锁的不是 `age` 的 `18 ~ 25` 范围。

因为没有 `age` 索引，MySQL 不能按照 `age` 快速定位数据，只能走全表扫描。InnoDB 表本身是按照聚簇索引组织的，一般就是主键索引。

所以实际情况是：

MySQL 扫描聚簇索引，并对扫描到的大量聚簇索引记录加锁。

严格来说，这不是直接加表锁，不等于：

```
LOCK TABLE user WRITE;
```

但因为扫描范围很大，大量记录都可能被锁住，所以效果接近锁表。

面试说法：

如果查询条件没有命中合适索引，`FOR UPDATE` 可能导致全表扫描。InnoDB 会扫描聚簇索引，并对扫描到的大量记录加锁。很多不满足条件的行也可能被锁住，所以效果接近锁表，但严格来说不是直接加表级锁。

---

#### 9. 其他事务会不会被阻塞？

事务 A：

```
START TRANSACTION;

SELECT *
FROM user
WHERE id = 1
FOR UPDATE;
```

事务 A 锁住了 `id = 1` 这行。

事务 B 修改同一行，会被阻塞：

```
UPDATE user
SET name = 'Jack'
WHERE id = 1;
```

事务 B 也执行 `FOR UPDATE`，也会被阻塞：

```
SELECT *
FROM user
WHERE id = 1
FOR UPDATE;
```

但是普通 `SELECT` 一般不会被阻塞：

```
SELECT *
FROM user
WHERE id = 1;
```

因为普通查询通常是 MVCC 快照读，不需要等待 `FOR UPDATE` 的锁释放。

---

### 快照读和 FOR UPDATE 的区别

#### 1. 什么是快照读？

快照读就是普通 `SELECT`：

```
SELECT *
FROM user
WHERE id = 1;
```

它一般不加锁，而是通过 MVCC 读取一个一致性视图。

这里建议不要只说“读取历史版本”，更严谨的说法是：

快照读读取的是某个时间点的一致性数据版本。

不同隔离级别下略有区别：

|   |   |
|---|---|
|隔离级别|快照生成时机|
|READ COMMITTED|每次普通 SELECT 都生成一个新快照|
|REPEATABLE READ|一个事务中第一次普通 SELECT 生成快照，后续普通 SELECT 复用这个快照|

所以在默认 `REPEATABLE READ` 下，同一个事务里的多次普通 `SELECT`，看到的数据通常是一致的。

---

#### 2. 快照读适合什么场景？

快照读适合只读场景：

|   |   |
|---|---|
|场景|示例|
|普通查询展示|商品详情、用户信息|
|列表页查询|订单列表、商品列表|
|报表统计|COUNT、SUM、后台统计|
|实时一致性要求不高|用户中心、后台页面|

特点是：

不加锁，并发高，性能好。

但它不能保证查完之后，数据不会被别人修改。

---

#### 3. 什么场景用 FOR UPDATE？

`SELECT ... FOR UPDATE` 适合这种场景：

先查数据，再根据查询结果做修改，并且必须防止其他事务同时修改。

典型场景：

|   |   |
|---|---|
|场景|作用|
|扣库存|防止超卖|
|账户扣款|防止余额扣错|
|抢优惠券|防止重复领取|
|抢座位、抢名额|防止多人抢到同一个资源|
|订单状态流转|防止重复支付、重复发货、重复取消|
|任务队列抢任务|防止多个消费者处理同一个任务|

例如扣库存：

```
START TRANSACTION;

SELECT stock
FROM product
WHERE id = 100
FOR UPDATE;

-- 判断 stock > 0 后再扣库存

UPDATE product
SET stock = stock - 1
WHERE id = 100;

COMMIT;
```

如果不用 `FOR UPDATE`，两个事务可能同时查到库存还有 `1`，然后都下单成功，最后导致超卖。

---

#### 4. 快照读和 FOR UPDATE 对比

|   |   |   |
|---|---|---|
|对比项|快照读|SELECT ... FOR UPDATE|
|SQL|普通 SELECT|SELECT ... FOR UPDATE|
|读类型|快照读 / 一致性非锁定读|当前读 / 锁定读|
|是否加锁|一般不加锁|加排他锁|
|是否阻塞修改|不阻塞|会阻塞其他事务修改同一批数据|
|读取数据|一致性视图中的数据版本|当前最新可见数据|
|适合场景|查询、展示、统计|查完要改、并发抢资源|
|性能影响|较小|较大|
|是否需要事务|不一定|放在事务里才有意义|
