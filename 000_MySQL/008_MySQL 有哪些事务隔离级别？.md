**先区分三种读取问题**

脏读是读到其他事务未提交的数据；不可重复读是同一事务重复读取同一记录，受到其他事务已提交修改的影响；幻读是重复执行同一条件查询，匹配的记录集合发生变化，不只看行数。

详见：[脏读、不可重复读和幻读（第 40 行）](<D:/000/sources/eas/000_MySQL/008_MySQL 有哪些事务隔离级别？.md:40>)。

**四种级别逐步加强隔离**

MySQL InnoDB 支持读未提交、读已提交、可重复读和串行化。按 SQL 标准对这三类问题的要求，读未提交都可能出现；读已提交避免脏读；可重复读再避免不可重复读，但标准仍允许幻读；串行化要求结果等价于事务按某种顺序串行执行，避免这三类问题，并不要求所有事务实际排队。

详见：[四种隔离级别的保证（第 56 行）](<D:/000/sources/eas/000_MySQL/008_MySQL 有哪些事务隔离级别？.md:56>)。

**再补充 InnoDB 的实现边界**

InnoDB 默认可重复读。读已提交每次普通一致性读建立新快照，可重复读通常复用第一次一致性读的快照，通过 MVCC，也就是多版本并发控制，决定哪些版本可见；事务自身写入仍然可见。可重复读下，范围锁定读取通过记录锁和间隙锁保护范围；它读取当前记录状态，不沿用普通查询的旧快照。串行化在显式事务中会把普通 SELECT 转为共享锁定读，锁范围依赖索引和条件，可能增加等待与死锁，性能要结合负载判断。

详见：[InnoDB 如何实现 RC、RR，以及如何理解幻读（第 80 行）](<D:/000/sources/eas/000_MySQL/008_MySQL 有哪些事务隔离级别？.md:80>)、[串行化怎样加锁，代价是什么（第 104 行）](<D:/000/sources/eas/000_MySQL/008_MySQL 有哪些事务隔离级别？.md:104>)。

## 4 详细方案

### 4.1 脏读、不可重复读和幻读

**脏读：读到了其他事务尚未提交的数据**

A 把余额从 100 改为 200，尚未提交；B 读到 200，就已经构成脏读。A 后续回滚只是说明风险，不是判定脏读的必要条件。

**不可重复读：同一记录受到已提交修改的影响**

A 第一次读取账户余额为 100；B 把余额改为 200 并提交；A 在同一事务再次读取，看到 200。其他事务删除记录后，A 再次读不到原记录，也属于需要讨论的重复读取变化，不能只把它限定为 UPDATE。

**幻读：相同条件匹配的记录集合发生变化**

A 查询所有 `age >= 18` 的用户；B 插入一个满足条件的用户并提交；A 再查时出现新记录，这是典型幻读。删除满足条件的记录，或更新条件字段使记录进入、离开查询范围，也可能改变匹配集合。即使新增一条、删除另一条后总数不变，集合仍可能已经变化，因此不能只用行数是否改变判断。

上述都是教学示例，数字用于说明现象。判断时要保持同一事务、相同查询条件，并区分其他事务的影响与当前事务自己的写入。

### 4.2 四种隔离级别的保证

以下按同一主题分别说明各级别。它们都规定并发事务之间允许看到什么，区别在于隔离保证强度；SQL 标准规定最低要求，数据库实现可以提供更强的保护。“可能出现”不是每次必然发生。

**读未提交（READ UNCOMMITTED）：**

允许普通读取看到其他事务未提交的修改，因此脏读、不可重复读和幻读都可能发生。隔离要求低不等于所有操作都无锁；写入仍需遵守 InnoDB 的并发控制。

**读已提交（READ COMMITTED，简称 RC）：**

对其他事务的数据，只读取已提交且在当前一致性读快照中可见的版本，避免脏读。每次一致性读建立新快照，两次查询之间若有其他事务提交，就可能读到不同结果，因此仍可能发生不可重复读和幻读。

**可重复读（REPEATABLE READ，简称 RR）：**

按 SQL 标准避免脏读、不可重复读，但不要求排除幻读。InnoDB 默认使用 RR，并通过一致性读快照和范围锁提供额外保护，具体边界见 4.3；“默认”不等于所有实例和会话当前都使用该级别。

**串行化（SERIALIZABLE）：**

要求并发事务的结果等价于它们按某种顺序串行执行，可避免上述三类读取问题。数据库可以让不冲突的工作并发进行，不是把所有事务放进同一条队列。InnoDB 的实现与代价见 4.4。

这三类读取现象不是业务正确性的全部。隔离级别不能代替完整的事务边界、约束和更新条件；例如两个请求都先在事务外读余额，再分别写回自己计算的值，不能仅凭数据库默认 RR 就认定不会覆盖更新。

来源：[MySQL 8.0 Transaction Isolation Levels](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-transaction-isolation-levels.html) 列出四种级别、InnoDB 默认值及各级别的读取和加锁机制。此前整理已核对该页面；不据此认定项目生产配置已确认。

### 4.3 InnoDB 如何实现 RC、RR，以及如何理解幻读

**普通一致性读使用快照**

在 RC、RR 下，普通非锁定 SELECT 通常采用一致性读，即按照快照判断可见版本。InnoDB 的 MVCC 利用记录的事务信息、undo 历史版本和 ReadView 实现可见性判断；ReadView 可以理解为判断某个事务版本是否可见的依据，不是把整张表复制一份。

RC 每次一致性读使用新的快照；RR 通常由事务内第一次一致性读建立快照，后续一致性读复用。普通 `BEGIN` 不等于立即固定快照；RR 下使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 可以显式在开始时建立一致性快照。不能把“第一次一致性读”简化成任意一条 SELECT，因为锁定读取不走相同的快照规则。

例如 A 在 RR 下第一次普通查询看到 10 条满足条件的记录；B 插入一条匹配记录并提交；如果 A 自己没有改变这些记录，之后仍用同一快照执行相同普通查询，就不会因 B 的提交多看到这一条。这里是新记录对该快照不可见，不是阻止了 B 插入。

**锁定读取与写入不沿用旧快照**

`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE` 属于锁定读取；UPDATE、DELETE 也需要根据当前记录状态判断和处理。它们不直接沿用先前普通查询的旧快照，遇到冲突锁可能等待，取得锁后应根据实际记录重新判断。当前事务自己的修改也能被自己读取，不能把“读取当前状态”概括成永远只读其他事务已提交的数据。

RR 下的范围锁定读取通常使用 Next-Key Lock（临键锁），即索引记录锁与其前方间隙锁的组合，阻止其他事务向受保护间隙插入记录。例如事务 A 对有索引的年龄范围执行锁定读取，在锁尚未释放时，B 向该受保护范围插入新记录会受到限制。实际范围取决于索引与扫描路径；唯一索引等值命中已有记录时，通常只需要记录锁，不能说所有当前读都使用间隙锁。

**不把两种读取拼成一个保证**

A 先普通查询建立快照，此时并没有因此锁住对应间隙；B 随后插入并提交；A 再改用 FOR UPDATE，就可能看到旧快照中没有的记录。这不是“范围锁已建立后仍允许别人插入”，而是两次查询采用了不同读取方式，前一次没有建立该范围的锁。

此外，当前事务自己的写入仍然可见。官方文档说明，事务更新先前快照中不可见的记录后，后续一致性读可能看见自己更新后的版本。因此“RR 下任何两次查询结果都一样”和“MVCC 加临键锁就能无条件消除所有业务中的结果变化”都不准确。

来源：[Consistent Nonlocking Reads](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-consistent-read.html) 说明 RC/RR 快照时机、自身写入可见及一致性读与写操作的边界；[Phantom Rows](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-next-key-locking.html) 说明临键锁对范围插入的保护。此前整理已核对相关官方说明，未实测上述场景。锁的具体使用与释放示例见 [SELECT FOR UPDATE 如何加锁与释放锁](<D:/000/sources/eas/000_MySQL/010_SELECT_FOR_UPDATE如何加锁与释放锁.md>)。

### 4.4 串行化怎样加锁，代价是什么

在 InnoDB 的 SERIALIZABLE 下，关闭自动提交或显式开启事务后，普通 SELECT 会被隐式转换为 `SELECT ... FOR SHARE`，对访问的记录及必要范围加共享锁。共享锁不是表级共享锁的同义词，实际锁范围仍依赖索引、条件及执行计划。

自动提交开启、且普通 SELECT 自成一个只读事务时，可以使用非锁定一致性读，不一定等待其他事务的写锁。因此必须交代事务模式，不能说串行化下“每条 SELECT 都加表锁”。

更严格的保护可能增加冲突等待、锁持有时间和死锁概率。例如两个事务都共享锁定同一记录，随后都尝试更新，可能因锁升级发生死锁，需要应用处理失败事务。实际吞吐量和延迟取决于读写比例、访问范围、事务长短和索引，不能直接断言串行化在任何负载下都是性能最差。

来源：Transaction Isolation Levels 的 SERIALIZABLE 小节明确区分自动提交下的单条只读查询与显式事务内的普通查询。此前整理已核对该条件；实际锁竞争和性能未经测试。

### 4.5 双会话示例：比较 RC 与 RR 的普通读取

教学前提：`account` 是 InnoDB 表，`id` 为主键，`id = 1` 的余额初始为 100。A 自己不修改数据，没有其他并发请求；数值只用于说明可见性。

会话 A 先执行：

```sql
-- 本设置仅用于下一次事务；另一轮对照时改成 READ COMMITTED。
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT balance FROM account WHERE id = 1; -- 第一次一致性读，预期为 100。
```

保持 A 的事务未结束，会话 B 执行：

```sql
START TRANSACTION;
UPDATE account SET balance = 200 WHERE id = 1;
COMMIT;
```

B 提交后，会话 A 执行：

```sql
SELECT balance FROM account WHERE id = 1;
COMMIT;
```

RR 下，A 第二次普通查询预期仍为 100；另起一轮 RC 对照前，先结束所有示例事务，将余额恢复为 100 并提交，再按相同顺序执行，第二次查询预期为 200。这展示 RC 更新快照与 RR 复用快照的区别，不涉及 A 自身写入或混用锁定读取。

以上是预期行为，不是本次测试结果；没有在数据库执行。实验应在独立测试数据上进行，不能把这组 SQL 直接用于真实账户。
