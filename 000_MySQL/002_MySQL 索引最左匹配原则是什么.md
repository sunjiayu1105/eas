# 002_MySQL 索引最左匹配原则是什么

以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准。本文讨论 MySQL 8.0.33 InnoDB 联合索引；示例用于解释机制，未执行数据库实验。

## 1 问题

MySQL 联合索引的最左匹配原则是什么，范围条件和中间缺列会怎样影响索引定位？

## 2 高级 Java 面试核心考点

- 联合索引的字段定义顺序与 B+Tree 排序。
- 等值、范围和中间缺列对索引范围定位的影响。
- 区分索引定位、过滤、索引条件下推和覆盖索引。

## 3 面试口述精炼版本

口述内容字符数：214

**先看索引定义顺序**

联合索引 `(a,b,c)` 是按 `a`、再按 `b`、最后按 `c` 排序的一棵 B+Tree。查询条件要从最左列开始连续匹配；`a`、`a,b`、`a,b,c` 可以形成连续前缀，WHERE 条件的书写顺序不影响优化器识别，但索引定义顺序不能随意交换。

**等值继续，范围截断**

等值条件可以继续向右匹配；遇到范围条件后，后面的列通常不能继续缩小索引扫描范围，但可能用于过滤、索引条件下推或覆盖索引。中间缺少列时，后面的列也不能继续做最左连续定位，最终要以执行计划确认。

详见：[联合索引的查询规则](<D:/000/sources/eas/000_MySQL/002_MySQL 索引最左匹配原则是什么.md:203>)。

## 4 详细方案

有误，不是完全错，而是**说得太绝对**。正确理解应该是：

**联合索引不是“a、b、c 三个独立索引”，而是一棵按照** `(a, b, c)` **这个顺序排好序的 B+Tree。**
MySQL 能不能高效使用它，核心看查询条件能不能从索引最左边开始，形成一段连续可定位的范围。

---

#### 一、原说法需要修正的地方

#### 1. “索引字段可以任意顺序”这句话不严谨

如果建立的是：

```
index idx_abc(a, b, c)
```

那么索引内部顺序就是：

```
先按 a 排序
a 相同，再按 b 排序
a、b 都相同，再按 c 排序
```

所以：

```
where a = 1 and b = 1
```

和

```
where b = 1 and a = 1
```

这两个 SQL **写法顺序不同，但效果一样**，MySQL 优化器能识别出来它们都可以用 `(a, b)`。

但是这不等于“索引字段可以任意顺序”。

错误理解是：

```
idx_abc(a,b,c) 可以随便当成 idx_bca(b,c,a) 用
```

这是不对的。

正确说法：

**WHERE 条件的书写顺序不重要，联合索引的字段定义顺序才重要。**

---

#### 2. “建立 abc 索引就相当于建立了 a、ab、abc 索引”基本对，但要补充

建立：

```
index idx_abc(a, b, c)
```

可以近似理解为同时支持：

```
a
a, b
a, b, c
```

但不等于支持：

```
b
c
b, c
a, c
```

因为 `(a,b,c)` 这棵 B+Tree 不是按 `b` 开头排的，也不是按 `c` 开头排的。

面试可以这样说：

联合索引 `(a,b,c)` 的可用前缀是 `(a)`、`(a,b)`、`(a,b,c)`。
如果跳过最左列 `a`，通常就不能利用这个联合索引做高效定位。

---

#### 3. `where b = 1 and c = 1` 说“没用索引”太绝对

对于：

```
where b = 1 and c = 1
```

在索引 `(a,b,c)` 中，确实**不能按照最左匹配原则高效定位**。

因为索引是先按 `a` 分组的：

```
a=1 下面有 b,c
a=2 下面有 b,c
a=3 下面有 b,c
```

你只查 `b=1 and c=1`，但是没有 `a`，MySQL 不知道应该从哪个 `a` 分组开始找。

所以常规情况下，它不能像查 `a=1` 那样快速定位。

但不能绝对说“完全没用索引”，因为有几种特殊情况：

```
1. 可能做全表扫描
2. 可能做全索引扫描
3. 如果是覆盖索引，可能扫描索引比扫描表更便宜
4. MySQL 8.0 某些情况下可能使用 skip scan
```

面试里建议说：

`where b = 1 and c = 1` 不满足最左匹配，通常不能利用 `(a,b,c)` 做高效的索引范围定位。优化器可能会选择全表扫描、全索引扫描，或者在特殊版本和场景下使用 skip scan，但这不是常规依赖点。

---

#### 4. `where a = 1 and c = 1` 不是完全不用 `c`

对于：

```
where a = 1 and c = 1
```

联合索引 `(a,b,c)` 中，MySQL 可以先用 `a=1` 定位到一段范围。

但是因为中间缺了 `b`，所以 `c=1` 不能继续帮 MySQL 缩小扫描范围。

也就是说：

```
a 可以用于索引定位
c 通常不能用于缩小索引扫描范围
c 可能作为过滤条件使用
```

如果开启了 Index Condition Pushdown，`c=1` 可能在索引层过滤掉一部分数据，减少回表次数。

所以更准确地说：

`where a = 1 and c = 1` 可以用到索引的 `a` 部分进行定位，`c` 不能继续参与最左连续匹配，但可能用于索引条件下推或过滤。

---

#### 5. 范围查询后面的字段不能继续用于“范围定位”

例如：

```
where a = 1 and b > 10 and c = 1
```

联合索引是 `(a,b,c)`。

MySQL 可以用：

```
a = 1
b > 10
```

定位一段索引范围。

但是 `c = 1` 通常不能继续缩小这段范围，因为 `b > 10` 已经是一个范围了。

原因是索引排序是：

```
先 a
再 b
再 c
```

当 `b` 是范围时，`b` 后面有很多不同的值：

```
(a=1, b=11, c=1)
(a=1, b=11, c=2)
(a=1, b=12, c=1)
(a=1, b=12, c=2)
(a=1, b=13, c=1)
...
```

`c=1` 分散在很多不同的 `b` 分组里，不是一段连续区间，所以不能直接用来确定扫描起点和终点。

面试说法：

联合索引中，等值条件可以继续向右匹配；遇到范围条件后，后面的字段一般不能再用于缩小索引扫描范围，但可能用于过滤或索引条件下推。

---

#### 二、联合索引的核心口诀

建议面试这样记：

```
联合索引看顺序，
最左字段不能丢；
等值匹配可继续，
范围查询会截断；
中间断了后面废，
WHERE 顺序不影响。
```

更完整一点：

```
1. 联合索引本质是一棵按多个字段排序的 B+Tree。
2. 索引列的定义顺序很重要。
3. WHERE 条件的书写顺序不重要。
4. 必须从最左列开始连续匹配。
5. 等值查询可以一直往右匹配。
6. 遇到范围查询后，后面的列通常不能继续用于索引范围定位。
7. 中间缺列，后面的列不能继续用于最左匹配。
8. 后面的列虽然不能用于定位，但可能用于过滤、索引条件下推、覆盖索引。
```

---

#### 三、用 `(a,b,c)` 联合索引举例

假设有索引：

```
index idx_abc(a, b, c)
```

#### 1. 可以完整使用 `(a,b,c)`

```
select * from t where a = 1 and b = 1 and c = 1;
```

能用：

```
a, b, c
```

因为从最左边开始，连续命中。

---

#### 2. 可以使用 `(a,b)`

```
select * from t where a = 1 and b = 1;
```

能用：

```
a, b
```

---

#### 3. WHERE 顺序不影响使用索引

```
select * from t where b = 1 and a = 1;
```

也能用：

```
a, b
```

因为优化器能识别 `a=1 and b=1`。

注意：这是 **WHERE 条件书写顺序不重要**，不是索引字段顺序不重要。

---

#### 4. 可以使用 `a`

```
select * from t where a = 1;
```

能用：

```
a
```

---

#### 5. 不能高效使用 `(a,b,c)` 做定位

```
select * from t where b = 1 and c = 1;
```

因为缺了最左列 `a`。

常规理解：

```
不能走最左匹配
```

更严谨说：

```
不能利用 idx_abc 做高效范围定位，优化器可能选择全表扫描、全索引扫描或特殊情况下 skip scan。
```

---

#### 6. 只能用 `a` 做定位，`c` 用来过滤

```
select * from t where a = 1 and c = 1;
```

能用：

```
a
```

不能连续用：

```
a, c
```

因为中间缺了 `b`。

---

#### 7. 范围查询后，后面的字段通常不能继续用于范围定位

```
select * from t where a = 1 and b > 10 and c = 1;
```

能用来定位的是：

```
a, b
```

`c=1` 通常不能继续缩小扫描范围，只能在扫描过程中做过滤。

---

#### 四、联合索引在 B+Tree 中是怎么排的？

联合索引 `(a,b,c)` 可以理解成一本电话簿。

电话簿如果按：

```
省份、城市、姓名
```

排序，那么你查：

```
省份 = 广东
城市 = 深圳
姓名 = 张三
```

非常快。

但是你只查：

```
城市 = 深圳
姓名 = 张三
```

就不快，因为电话簿不是按城市开头排序的。

---

对于数据库来说，联合索引 `(a,b,c)` 在叶子节点大概是这样排的：

```
(a, b, c, id)

(1, 1, 1, 10)
(1, 1, 2, 11)
(1, 1, 3, 12)
(1, 2, 1, 13)
(1, 2, 2, 14)
(1, 3, 1, 15)
(2, 1, 1, 16)
(2, 1, 2, 17)
(2, 2, 1, 18)
(3, 1, 1, 19)
```

排序规则是：

```
先看 a
a 相同再看 b
b 相同再看 c
c 相同再看主键 id
```

画成分组就是：

```
idx_abc(a,b,c)

a=1
 ├── b=1
 │    ├── c=1
 │    ├── c=2
 │    └── c=3
 ├── b=2
 │    ├── c=1
 │    └── c=2
 └── b=3
      └── c=1

a=2
 ├── b=1
 │    ├── c=1
 │    └── c=2
 └── b=2
      └── c=1

a=3
 └── b=1
      └── c=1
```

#### 五、详细描述：联合索引查询过程

以这个 SQL 为例：

```
select * from t
where a = 1 and b = 2 and c = 1;
```

索引是：

```
idx_abc(a, b, c)
```

#### 第一步：从根节点开始找

B+Tree 不是从第一条数据开始扫，而是从根节点开始判断。

```
                根节点
          ┌───────┼───────┐
        a<1     a=1范围     a>1
                  │
              中间节点
          ┌───────┼───────┐
        b<2     b=2范围     b>2
                  │
              叶子节点
```

MySQL 会根据 `(a,b,c)` 的排序规则，快速定位到第一个满足条件的位置。

---

#### 第二步：定位到叶子节点的起始位置

目标是找：

```
(a=1, b=2, c=1)
```

叶子节点中数据类似：

```
...
(1,1,1,id=10)
(1,1,2,id=11)
(1,2,1,id=13)  ← 找到起点
(1,2,2,id=14)
(1,3,1,id=15)
...
```

MySQL 找到第一个：

```
(1,2,1)
```

的位置。

---

#### 第三步：沿着叶子节点向后扫描

B+Tree 的叶子节点之间是有顺序链表的。

```
叶子节点1             叶子节点2             叶子节点3
┌──────────┐        ┌──────────┐        ┌──────────┐
│(1,1,1)   │  --->  │(1,2,1)   │  --->  │(1,3,1)   │
│(1,1,2)   │        │(1,2,2)   │        │(2,1,1)   │
└──────────┘        └──────────┘        └──────────┘
```

找到起点后，MySQL 会继续向后扫描，直到不满足条件。

例如查询：

```
where a = 1 and b = 2 and c = 1
```

扫描过程：

```
(1,2,1,id=13)  满足
(1,2,1,id=20)  满足
(1,2,2,id=14)  不满足，停止或跳出当前范围
```

如果条件非常精确，扫描范围就很小。

---

#### 六、不同 SQL 的扫描过程图解

#### 情况 1：`where a = 1`

```
select * from t where a = 1;
```

索引扫描范围：

```
(1,1,1)
(1,1,2)
(1,2,1)
(1,2,2)
(1,3,1)
```

图示：

```
a=1 这一整段都会被扫描

a=1
 ├── b=1
 │    ├── c=1
 │    └── c=2
 ├── b=2
 │    ├── c=1
 │    └── c=2
 └── b=3
      └── c=1
```

能用索引定位到：

```
a=1 的起点
```

然后顺序扫描到：

```
a 不等于 1 为止
```

---

#### 情况 2：`where a = 1 and b = 2`

```
select * from t where a = 1 and b = 2;
```

索引扫描范围：

```
(1,2,1)
(1,2,2)
```

图示：

```
a=1
 └── b=2
      ├── c=1
      └── c=2
```

比只查 `a=1` 扫描范围更小。

---

#### 情况 3：`where a = 1 and b = 2 and c = 1`

```
select * from t where a = 1 and b = 2 and c = 1;
```

索引扫描范围：

```
(1,2,1)
```

图示：

```
a=1
 └── b=2
      └── c=1
```

这是最理想的情况，三个字段都连续匹配。

---

#### 情况 4：`where a = 1 and c = 1`

```
select * from t where a = 1 and c = 1;
```

因为中间缺了 `b`，MySQL 只能先定位：

```
a=1
```

然后在 `a=1` 这一大段里面过滤 `c=1`。

扫描过程：

```
(1,1,1)  满足 c=1
(1,1,2)  不满足
(1,2,1)  满足 c=1
(1,2,2)  不满足
(1,3,1)  满足 c=1
```

图示：

```
a=1 这一整段先被定位出来

a=1
 ├── b=1
 │    ├── c=1  √
 │    └── c=2  ×
 ├── b=2
 │    ├── c=1  √
 │    └── c=2  ×
 └── b=3
      └── c=1  √
```

所以它不是直接定位到所有 `c=1`，而是：

```
先找 a=1 的范围，再在里面过滤 c=1
```

---

#### 情况 5：`where b = 1 and c = 1`

```
select * from t where b = 1 and c = 1;
```

缺少最左列 `a`。

在索引中，`b=1 and c=1` 是分散的：

```
a=1
 └── b=1
      └── c=1  √

a=2
 └── b=1
      └── c=1  √

a=3
 └── b=1
      └── c=1  √
```

它们不是一段连续区域，中间隔着很多其他数据：

```
(1,1,1)  √
(1,1,2)
(1,2,1)
(1,2,2)
(2,1,1)  √
(2,1,2)
(2,2,1)
(3,1,1)  √
```

所以 MySQL 不能像查 `a=1` 那样快速定位。

常规面试回答：

因为没有最左列 `a`，`b` 和 `c` 在整棵索引里不是全局有序的，无法形成连续扫描范围，所以不能高效利用 `(a,b,c)`。

---

#### 情况 6：`where a = 1 and b > 10 and c = 1`

```
select * from t
where a = 1 and b > 10 and c = 1;
```

能用：

```
a = 1
b > 10
```

但 `c = 1` 不能继续缩小范围。

扫描范围大概是：

```
a=1
 ├── b=11
 │    ├── c=1  √
 │    └── c=2  ×
 ├── b=12
 │    ├── c=1  √
 │    └── c=3  ×
 ├── b=13
 │    ├── c=1  √
 │    └── c=4  ×
```

原因是 `b > 10` 是一段范围，不是一个固定值。

只要 `b` 变成范围，后面的 `c` 就会分散在多个 `b` 分组中。

面试说法：

`a=1` 是等值，可以继续匹配；`b>10` 是范围，可以用于索引范围扫描；`c=1` 位于范围字段之后，通常不能继续用于缩小扫描范围，只能作为过滤条件。

---

#### 七、`used_key_parts` 怎么理解？

你截图里的 JSON：

```
"key": "idx_test",
"used_key_parts": [
  "a",
  "b"
]
```

意思是：

```
MySQL 这次选择了 idx_test 这个索引；
并且用于索引访问的字段部分是 a、b。
```

如果：

```
used_key_parts: ["a", "b"]
```

说明这次索引主要利用到了联合索引的前两列。

但注意，不能只看 `used_key_parts`，还要结合：

```
key
key_len
type
rows
filtered
Extra
attached_condition
index_condition
```

尤其是 `Extra` 里如果出现：

```
Using index condition
```

说明可能发生了索引条件下推，也就是某些不能用于定位的条件，仍然可以在索引层过滤。

## 5 已确认规则

- 本文按 MySQL 8.0.33 InnoDB 联合索引语义整理，示例与运行验证分开。
- 不把“不能高效定位”绝对化为“完全不会使用索引”。

## 6 待确认或待验证事项

- 实际索引定义、数据分布和执行计划。
- skip scan、索引条件下推等优化在目标版本和数据上的实际选择。

## 7 异议与分析

最左匹配原则约束的是索引范围定位，不等于后续列绝对不会参与过滤，也不等于缺少最左列时绝对不会选用该索引。
