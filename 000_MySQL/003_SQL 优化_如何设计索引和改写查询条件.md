## 4 详细方案

### 4.1 设计合适的索引

设计索引时，应重点分析以下字段：

- `WHERE` 中的过滤字段；
- `JOIN ON` 中的连接字段；
- `ORDER BY` 中的排序字段；
- `GROUP BY` 中的分组字段；
- 高频查询字段及其数据分布。

同时还要考虑：

- 等值条件和 `IN` 条件；
- 范围条件；
- 字段选择性；
- 排序和分组是否能够利用索引；
- 是否能够形成覆盖索引；
- 索引带来的存储、写入和维护成本。

联合索引一般需要结合最左匹配原则设计。常见的设计起点是将等值条件放在前面，再结合范围条件、排序字段和查询字段进行调整，但这不是固定模板。范围条件可能影响后续索引列对排序的利用，低选择性字段在某些场景下也可能不适合作为索引前导列，最终仍要结合数据分布和执行计划验证。

### 4.2 让普通索引更容易用于条件查找

应尽量避免在索引列上使用函数或表达式，例如：

```sql
DATE(trade_time) = :tradeDate
```

在没有函数索引或对应生成列索引的情况下，可以改成左闭右开的时间范围：

```sql
trade_time >= :startTime
AND trade_time < :endTime
```

这样通常更有利于普通 B-Tree 索引进行范围查找，也能避免时间边界问题。

还要注意隐式类型转换。例如，字段是字符类型，但参数使用数字类型时，数据库可能对字段进行转换，从而影响索引使用。不过实际影响取决于字段类型、参数类型、数据库版本、字符集和执行计划，不能仅凭 SQL 形式直接下结论。

`LIKE` 查询应尽量避免左模糊：

```sql
LIKE '%abc'
```

这种写法通常不能利用普通 B-Tree 索引做前缀范围定位，但仍可能扫描索引；不能等同于执行计划绝对不会选索引。下面的前缀匹配通常更容易利用索引：

```sql
LIKE 'abc%'
```

实际是否使用索引，还需要结合字段排序规则、索引定义和执行计划判断。

示例中的 `:参数名` 表示应用绑定参数，不是 MySQL 客户端可直接执行的参数语法。

### 4.3 按需减少回表

不要随意使用：

```sql
SELECT *
```

应只查询业务实际需要的字段，并在合适的场景下设计覆盖索引。

以 MySQL InnoDB 为例，二级索引通常包含主键值。当查询需要读取二级索引之外的字段时，数据库通常还需要根据主键访问聚簇索引，这个过程称为回表。

如果查询所需的字段，包括返回、过滤、排序等操作涉及的字段，都能由索引提供，就可能形成覆盖索引，减少回表。但覆盖索引会增加存储空间、写入成本和维护成本，因此应结合查询频率、数据量和实际收益评估。

### 4.4 教学案例：按商户查询一天的交易

本例假设教学表 `trade_record` 使用 InnoDB，`id` 为主键，`merchant_id` 为整数，`trade_time` 为非空 DATETIME。页面按时间倒序返回 ID、交易时间和金额，允许下一页查询。以下日期、商户 ID 和页大小 50 条均为教学值，不是生产配置；具体字段、查询频率和数据分布尚未确认。

**定位可疑点**

```sql
-- 改写前：对 trade_time 做函数计算，不利于普通时间索引范围查找。
SELECT id, trade_time, amount
FROM trade_record
WHERE merchant_id = 1001
  AND DATE(trade_time) = '2026-01-01'
ORDER BY trade_time DESC, id DESC
LIMIT 50;
```

先检查实际计划，确认是否扫描过多记录或存在高成本排序。若主要耗时来自锁等待，不能仅凭函数条件就认定它是这次慢查询的根因。函数索引或对应生成列索引也可能支持表达式查询，必须先核对现有索引。

**保持语义后改写，并提出候选索引**

```sql
EXPLAIN
SELECT id, trade_time, amount
FROM trade_record
WHERE merchant_id = 1001
  AND trade_time >= '2026-01-01 00:00:00'
  AND trade_time <  '2026-01-02 00:00:00'
ORDER BY trade_time DESC, id DESC
LIMIT 50;

-- 候选索引，仅在测试环境评估，不表示已经上线。
CREATE INDEX idx_merchant_time_id
ON trade_record (merchant_id, trade_time, id);
```

商户等值条件确定前缀，时间条件限定范围，`trade_time, id` 与唯一稳定排序一致；升序索引可能通过反向扫描支持这组同向降序排序，实际计划仍需验证。左闭右开的日期范围包含整天并排除次日，使用 TIMESTAMP 或跨时区查询时还要统一业务日期、连接时区和边界转换。

本例索引不包含 amount，不能声称已经实现覆盖索引；是否把金额加入索引，要比较回表收益与索引宽度、写入成本。InnoDB 二级索引携带主键，实际评估时也应检查现有 `(merchant_id, trade_time)` 是否已能满足条件和顺序，避免机械新增近似重复索引。

**验证结论而不编造结果**

比较改写前后的记录 ID、金额、顺序和日期边界，再观察计划、实际耗时及读取量。预期是改善范围定位和排序利用，但如果查询本来只涉及很少数据，收益可能有限。没有测试数据前，不填写“从几秒降到几毫秒”或“提升百分之多少”。

该例只说明一次可验证的优化思路，不能作为“我在项目中做过”的事实。实际面试经历需要补充对应业务、原 SQL、执行计划、修改理由、验证记录与本人负责的工作。
