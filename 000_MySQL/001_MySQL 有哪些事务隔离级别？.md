你这份说法**大方向是对的**，但有两个面试里很容易被追问的点需要修正：  
第一，**“REPEATABLE READ 一定允许幻读”这句话对 MySQL InnoDB 不够准确**；第二，**“SERIALIZABLE 每次读都需要获得表级共享锁”说法过于绝对**。下面给你整理成一版更准确、更适合面试输出的版本。

---

## 一、先给结论：哪里有误？

主要有两处需要修正。

### 1. “MySQL InnoDB 的可重复读还存在幻读”不严谨

这句话如果按 **SQL 标准** 来说，是对的：

SQL 标准中，REPEATABLE READ 解决脏读、不可重复读，但没有要求必须解决幻读。

但是在 **MySQL InnoDB** 中，情况更特殊：

MySQL InnoDB 在 REPEATABLE READ 级别下，通过 **MVCC + Next-Key Lock**，在很多场景下可以避免幻读。

所以不能简单说：

MySQL InnoDB 的 REPEATABLE READ 一定允许幻读。

更准确的说法是：

**SQL 标准下，REPEATABLE READ 仍可能出现幻读；但 MySQL InnoDB 的 REPEATABLE READ 通过 MVCC 和 Next-Key Lock，在普通快照读和加锁读场景下基本解决了幻读问题。**

---

### 2. “SERIALIZABLE 每次读都需要获得表级共享锁”不准确

这句话也太绝对了。

在 MySQL InnoDB 中，SERIALIZABLE 隔离级别下，普通 `SELECT` 会被当成加锁读来处理，类似加共享锁。

但它不一定每次都是**表级共享锁**。

更准确地说：

**SERIALIZABLE 会让读写之间更严格地互斥，普通查询也可能加锁，锁的粒度可能是行锁、间隙锁、Next-Key Lock；如果索引没用好，锁范围可能扩大，甚至接近锁表效果。**

所以面试时不要说死“每次都是表锁”，可以说：

**SERIALIZABLE 最严格，会让事务串行执行效果更强，读写互相阻塞更多，性能最差。**

---

## 二、三个问题先搞懂：脏读、不可重复读、幻读

理解隔离级别前，先把这三个并发问题记住。

### 1. 脏读：读到了别人还没提交的数据

事务 A 修改了数据，但还没提交。

事务 B 读到了事务 A 修改后的数据。

如果事务 A 后来回滚了，那么事务 B 刚才读到的就是“脏数据”。

```
事务 A：把余额 100 改成 200，但未提交
事务 B：读到余额 200
事务 A：回滚，余额恢复 100
```

事务 B 读到的 200 就是脏数据。

一句话：

**脏读 = 读到了别人未提交的数据。**

---

### 2. 不可重复读：同一行数据，两次读结果不一样

事务 A 在同一个事务里，两次读取同一行数据。

中间事务 B 修改了这行数据并提交。

事务 A 第二次读到的结果变了。

```
事务 A：第一次读 id = 1，余额 = 100
事务 B：把 id = 1 的余额改成 200，并提交
事务 A：第二次读 id = 1，余额 = 200
```

一句话：

**不可重复读 = 同一事务内，同一行数据前后读到的值不一样。**

重点是：**针对 update 修改已有数据。**

---

### 3. 幻读：同一个范围，两次查出来的行数不一样

事务 A 查询一个范围。

中间事务 B 插入了满足条件的新数据并提交。

事务 A 再查同一个范围，发现多了一些“幻影行”。

```
事务 A：查询 age > 18 的用户，有 10 条
事务 B：插入一个 age = 20 的用户，并提交
事务 A：再次查询 age > 18 的用户，变成 11 条
```

一句话：

**幻读 = 同一事务内，同一个范围查询，前后查到的记录数量不一样。**

重点是：**针对 insert 新增满足条件的记录。**

---

## 三、MySQL 四种隔离级别通俗解释

MySQL 支持四种事务隔离级别。

### 1. READ UNCOMMITTED：读未提交

这是隔离性最弱的级别。

特点：

**别人还没提交的数据，我也能读到。**

所以它可能出现：

- 脏读；
- 不可重复读；
- 幻读。

这个级别基本很少在生产使用，因为太不安全。

面试记忆：

**读未提交：最低级别，什么问题都可能发生。**

---

### 2. READ COMMITTED：读已提交

特点：

**只能读到别人已经提交的数据。**

所以它可以避免：

- 脏读。

但仍然可能出现：

- 不可重复读；
- 幻读。

原因是：在一个事务里，每次查询都会读取当前已经提交的最新数据。

例如：

```
事务 A 第一次读余额 = 100
事务 B 修改余额为 200 并提交
事务 A 第二次读余额 = 200
```

所以 READ COMMITTED 解决了脏读，但没有解决不可重复读。

补充：

Oracle、PostgreSQL 等很多数据库默认是 READ COMMITTED。

面试记忆：

**读已提交：只能读提交后的数据，所以没有脏读，但同一事务内多次读可能变。**

---

### 3. REPEATABLE READ：可重复读

这是 **MySQL InnoDB 的默认隔离级别**。

特点：

**同一个事务内，多次普通 SELECT 看到的数据结果是一致的。**

它可以避免：

- 脏读；
- 不可重复读。

原因是 MySQL InnoDB 使用了 **MVCC**。

在 REPEATABLE READ 下，同一个事务中的普通查询通常基于同一个快照读取数据。

也就是说：

```
事务开始后第一次查询看到什么版本，
后续普通查询基本还是看这个版本。
```

所以即使其他事务提交了修改，当前事务普通查询也不一定能看到。

面试记忆：

**可重复读：同一个事务里，多次读同一批数据，结果保持一致。MySQL InnoDB 默认就是这个级别。**

---

### 4. SERIALIZABLE：串行化

这是隔离性最强的级别。

特点：

**事务之间尽量像排队一样串行执行。**

它可以避免：

- 脏读；
- 不可重复读；
- 幻读。

但代价是：

- 并发性能差；
- 读写之间更容易互相阻塞；
- 实际生产中很少作为默认隔离级别。

注意，不要简单说它“每次读都是表级共享锁”。

更准确的说法是：

**在 MySQL InnoDB 中，SERIALIZABLE 会让普通 SELECT 也变成类似加锁读，锁范围取决于查询条件和索引，可能是行锁、间隙锁或 Next-Key Lock；如果索引不合理，锁范围会变大。**

面试记忆：

**串行化：最安全，但并发最差。**

## 五、MySQL InnoDB 下的幻读要怎么说？

这是面试高频追问点。

### 1. 普通 SELECT：快照读

普通查询：

```
SELECT * FROM user WHERE age > 18;
```

这种是**快照读**。

在 MySQL InnoDB 的 REPEATABLE READ 下，普通 SELECT 会基于 MVCC 读取事务快照。

所以同一个事务里，多次普通 SELECT 看到的结果通常是一致的。

例如：

```
事务 A 第一次查询 age > 18，有 10 条
事务 B 插入一条 age = 20 的记录并提交
事务 A 再次普通 SELECT age > 18，还是看到 10 条
```

所以对于普通快照读来说：

**MySQL InnoDB 的 REPEATABLE READ 基本不会出现幻读。**

---

### 2. 加锁读：当前读

下面这些属于**当前读**：

```
SELECT * FROM user WHERE age > 18 FOR UPDATE;

SELECT * FROM user WHERE age > 18 LOCK IN SHARE MODE;

UPDATE user SET name = 'Tom' WHERE age > 18;

DELETE FROM user WHERE age > 18;
```

当前读读取的是最新数据，并且会加锁。

在 REPEATABLE READ 下，InnoDB 会使用：

- Record Lock：记录锁；
- Gap Lock：间隙锁；
- Next-Key Lock：临键锁，记录锁 + 间隙锁。

这些锁可以防止其他事务在查询范围内插入新记录。

例如：

```
SELECT * FROM user WHERE age BETWEEN 10 AND 20 FOR UPDATE;
```

这个查询会锁住符合条件的记录以及相关间隙，防止其他事务插入 `age = 15` 这样的数据。

所以：

**MySQL InnoDB 的 REPEATABLE READ 对加锁读也通过 Next-Key Lock 防止幻读。**

---

### 3. 面试最稳妥说法

不要简单说：

REPEATABLE READ 会出现幻读。

也不要绝对说：

REPEATABLE READ 完全不会有幻读。

更好的表达是：

**按照 SQL 标准，REPEATABLE READ 解决了不可重复读，但仍可能出现幻读；但 MySQL InnoDB 的实现更强，在默认 REPEATABLE READ 下，通过 MVCC 解决普通快照读的一致性问题，通过 Next-Key Lock 解决当前读的幻读问题，所以在大多数场景下可以避免幻读。**

这句话很稳。

---

## 六、MVCC、ReadView、Next-Key Lock 简单理解

面试中不一定要展开很深，但最好知道它们分别负责什么。

### 1. MVCC：多版本并发控制

MVCC 可以理解为：

**同一行数据保存多个版本，事务读数据时，不一定读最新版本，而是读自己应该看到的版本。**

好处是：

- 读不用阻塞写；
- 写不用阻塞普通读；
- 提高并发性能。

在 MySQL InnoDB 中，MVCC 主要依赖：

- undo log；
- ReadView；
- 事务版本号。

---

### 2. ReadView：决定当前事务能看到哪些版本

ReadView 可以理解为：

**事务读数据时的一张可见性名单。**

它决定：

```
哪些事务提交的数据我能看见；
哪些事务未提交或太新的数据我看不见。
```

READ COMMITTED 和 REPEATABLE READ 的区别就在这里。

|   |   |   |
|---|---|---|
|**隔离级别**|**ReadView 创建时机**|**效果**|
|READ COMMITTED|每次 SELECT 都生成新的 ReadView|每次都能看到最新已提交数据|
|REPEATABLE READ|事务内第一次 SELECT 生成 ReadView，后续复用|同一事务内多次读结果一致|

所以：

**RC 是每次读一个新快照，RR 是一个事务基本用同一个快照。**

---

### 3. Next-Key Lock：解决范围插入问题

Next-Key Lock 可以理解为：

**锁住已有记录，同时锁住记录之间的间隙，防止别人往这个范围里插入新数据。**

它主要解决幻读问题。

例如表里有数据：

```
age = 10
age = 20
age = 30
```

查询：

```
SELECT * FROM user WHERE age BETWEEN 10 AND 20 FOR UPDATE;
```

InnoDB 不只锁住 `age = 10` 和 `age = 20`，还可能锁住它们之间的范围，防止别人插入：

```
age = 15
```

这就是防止幻读的关键。

---

## 七、原内容修正版

可以把原来的说法修正成下面这样：

### MySQL 支持四种隔离级别

#### 1. READ UNCOMMITTED：读未提交

允许读取其他事务尚未提交的数据，因此可能发生脏读、不可重复读和幻读。

#### 2. READ COMMITTED：读已提交

只能读取其他事务已经提交的数据，因此可以避免脏读。

但在同一个事务中，多次查询可能读到其他事务已经提交的新结果，所以仍可能出现不可重复读和幻读。

Oracle、PostgreSQL 等很多数据库默认是这个隔离级别。

#### 3. REPEATABLE READ：可重复读

同一个事务内，多次普通查询看到的数据结果保持一致，可以避免脏读和不可重复读。

这是 MySQL InnoDB 的默认隔离级别。

按 SQL 标准来说，REPEATABLE READ 仍可能出现幻读。

但 MySQL InnoDB 的实现更强：普通 SELECT 通过 MVCC 快照读保证一致性；加锁读通过 Next-Key Lock 防止范围内插入新记录。因此在 MySQL InnoDB 中，REPEATABLE READ 在大多数场景下可以避免幻读。

#### 4. SERIALIZABLE：串行化

最高隔离级别，事务之间尽量串行执行，可以避免脏读、不可重复读和幻读。

但并发能力最差，读写之间更容易互相阻塞。

在 MySQL InnoDB 中，SERIALIZABLE 下普通 SELECT 也会变成类似加锁读，锁的范围与查询条件和索引有关，不一定都是表级锁。

## 八、面试推荐回答版

可以直接这样回答：

MySQL 支持四种事务隔离级别：**READ UNCOMMITTED（读未提交）**、**READ COMMITTED（读已提交）**、**REPEATABLE READ（可重复读）**和 **SERIALIZABLE（串行化）**。

在理解隔离级别之前，先要知道它们主要是为了解决三个并发问题：**脏读、不可重复读和幻读**。

**脏读**指的是一个事务读到了另一个事务还没有提交的数据。比如事务 A 修改了一条数据但还没提交，事务 B 此时读到了这个修改后的值，如果事务 A 最后回滚了，那么事务 B 之前读到的就是脏数据。

**不可重复读**指的是在同一个事务中，两次读取同一行数据，结果不一样。通常是因为中间有其他事务修改了这行数据并提交了。它的重点是针对已有数据的 **update 修改**。

**幻读**指的是在同一个事务中，两次执行相同的范围查询，查出来的记录数量不一样。通常是因为中间有其他事务插入了满足条件的新数据并提交了。它的重点是针对范围内的 **insert 新增记录**。

然后对应到 MySQL 的四种隔离级别：

**读未提交**隔离性最弱，允许读取其他事务还没有提交的数据，所以脏读、不可重复读和幻读都可能发生。

**读已提交**只能读取其他事务已经提交的数据，所以可以避免脏读。但因为同一个事务中每次查询都可能读到其他事务新提交的数据，所以仍然可能出现不可重复读和幻读。很多数据库，比如 Oracle，默认就是这个级别。

**可重复读**可以保证同一个事务内多次读取同一数据结果一致，所以可以避免脏读和不可重复读。它是 MySQL InnoDB 的默认隔离级别。按照 SQL 标准来说，可重复读仍然可能出现幻读；但 MySQL InnoDB 的实现更强，通过 MVCC 保证普通快照读的一致性，通过 Next-Key Lock 防止当前读时范围内插入新记录，所以在大多数场景下可以避免幻读。

**串行化**是最高隔离级别，事务之间尽量像排队一样串行执行，可以避免脏读、不可重复读和幻读。但它的并发性能最差，读写之间更容易互相阻塞，生产环境中一般较少作为默认隔离级别。

所以面试里可以总结为：  
**读未提交什么问题都可能有；读已提交解决脏读；可重复读解决脏读和不可重复读；串行化三个问题都能解决。需要注意的是，SQL 标准下 REPEATABLE READ 仍可能出现幻读，但 MySQL InnoDB 在默认 REPEATABLE READ 下通过 MVCC 和 Next-Key Lock 对幻读做了额外处理。**

## 九、最终精简记忆版

面试可以背这一版：

**读未提交：什么都挡不住，脏读、不可重复读、幻读都可能发生。**

**读已提交：挡住脏读，但挡不住不可重复读和幻读。**

**可重复读：挡住脏读和不可重复读，是 MySQL InnoDB 默认级别。SQL 标准下仍可能有幻读，但 InnoDB 通过 MVCC 和 Next-Key Lock 基本解决幻读。**

**串行化：三个问题都能挡住，但并发性能最差。**

再压缩成口诀：

**未提交，问题全有；已提交，没脏读；可重复，防变更；串行化，全都防。**  
**标准 RR 可能幻读，InnoDB RR 基本防幻读。**
