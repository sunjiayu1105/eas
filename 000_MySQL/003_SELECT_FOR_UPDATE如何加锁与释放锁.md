**查询时加锁，事务内完成检查和更新**

SELECT ... FOR UPDATE 是锁定读取。在 InnoDB 中，它读取当前数据并申请排他锁，防止其他事务同时修改被保护的记录。按主键等值查到已有记录时，主要对这条索引记录加锁；如果是范围查询或非唯一索引查询，锁范围还取决于隔离级别和实际扫描的索引，可能连记录之间的间隙也一起保护。

详见：[如何加锁，锁住哪些数据（第 39 行）](<D:/000/sources/eas/000_MySQL/003_SELECT_FOR_UPDATE如何加锁与释放锁.md:39>)。

**冲突操作等待，普通快照查询通常不等待**

其他事务更新、删除同一记录，或申请与它冲突的锁，默认需要等待。在读已提交、可重复读隔离级别下，普通非锁定查询通常通过 MVCC，也就是多版本并发控制，读取可见版本，不必等待这把记录锁释放。

详见：[其他事务会受到什么影响（第 56 行）](<D:/000/sources/eas/000_MySQL/003_SELECT_FOR_UPDATE如何加锁与释放锁.md:56>)。

**提交或回滚后释放，不是查询返回就释放**

查询、检查和更新必须放在同一事务、同一连接里，锁通常随事务提交或完整回滚释放。自动提交下单独执行一条锁定查询，不能保护后面的更新。连接异常时要等数据库识别断连并完成事务处理，不能认为应用超时就已经释放锁；锁等待超时也不等于整个事务已经回滚。

详见：[什么时候释放锁，异常时如何处理（第 66 行）](<D:/000/sources/eas/000_MySQL/003_SELECT_FOR_UPDATE如何加锁与释放锁.md:66>)。

## 4 详细方案

### 4.1 如何加锁，锁住哪些数据

`FOR UPDATE` 表示锁定读取，不会直接修改业务数据。InnoDB 根据执行计划扫描索引，在读取过程中申请排他锁；排他锁用于阻止其他事务取得冲突的锁。若目标记录已有不兼容的锁，当前查询默认等待。它读取当前记录，而不是沿用先前普通查询的快照；等待其他事务结束后，应根据这次锁定读取的结果重新判断。

InnoDB 的行锁实际加在索引记录上，锁范围与查询条件、使用的索引和隔离级别有关：

- **主键或完整唯一索引等值命中已有记录**：通常只需要对命中的索引记录加记录锁，不需要锁住前面的间隙。使用唯一二级索引时，还可能锁定对应的聚簇索引记录，不能把“一条业务记录”理解为只产生一个锁对象。
- **范围查询或非唯一索引查询**：可重复读下通常会使用临键锁，即记录锁与记录前间隙锁的组合。间隙锁保护索引值之间的空隙，主要限制其他事务在该间隙插入；因此锁的影响可能超过结果集中的记录。
- **读已提交隔离级别**：普通搜索和索引扫描通常不使用间隙锁，但外键检查、重复键检查仍有例外；扫描到但不符合条件的记录锁可能提前释放。不能把可重复读的锁范围直接套用过来。
- **没有合适索引或查询不到记录**：无合适索引可能扩大扫描与加锁范围；查询不到记录，在可重复读下仍可能锁住相关间隙。返回零行不代表没有加锁。

例如按主键查询已有账户 `id = 1`，与按余额范围查询一组账户，保护的索引范围可能不同。不能只看 WHERE 条件或返回行数判断锁范围，应结合索引定义、隔离级别、执行计划和实际锁信息验证。

InnoDB 还会取得表级意向排他锁，表示事务准备对表内记录加排他锁，以协调表级与行级加锁；这不等于独占整张表，也不代表所有读写都被阻塞。

依据：[Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[InnoDB Locking](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html)、[Locks Set by Different SQL Statements](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。官方内容本次未联网核验，具体 SQL 的锁范围尚待实验验证。

### 4.2 其他事务会受到什么影响

事务 A 持有某条记录的排他锁时，事务 B 对该记录执行 `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE`，或申请冲突的共享锁，默认需要等待 A 释放锁。等待过程中可能发生超时或死锁，不能保证 B 一定成功获得锁。

读已提交和可重复读下，普通非锁定 SELECT 通常通过 MVCC 读取可见版本，可以在 A 尚未提交时返回符合其可见性规则的数据；它不会因此读到 A 未提交的修改。这只说明能够读取，不表示查询结果已被保护，不能据此直接执行依赖该结果的业务操作。可串行化隔离级别下，普通查询的加锁行为还与事务模式有关，不能笼统套用“不等待”的结论。

`NOWAIT` 可以让行锁冲突立即报错，`SKIP LOCKED` 可以跳过被锁的记录；二者改变冲突处理方式，不改变事务结束后释放锁的基本原则。跳过的记录不等于不存在，因此不能用 `SKIP LOCKED` 的空结果证明全部任务处理完成。本例使用默认等待方式，不使用这两个选项。

依据：[Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html) 和 Locking Reads 中的冲突处理说明；本次未实际观察并发会话行为。

### 4.3 什么时候释放锁，异常时如何处理

需要保护后续更新的锁定读取，应通过 `START TRANSACTION` 开启事务，或由应用事务管理器管理。查询、应用侧检查和更新必须使用同一连接参与同一事务；查询返回时，事务仍未结束，锁仍可继续保护后续操作。

- **正常提交**：`COMMIT` 结束事务并释放事务持有的锁。
- **主动回滚**：完整的 `ROLLBACK` 撤销本次未提交修改并释放锁；回滚耗时较长时，不能把发出回滚请求当作回滚已完成。回滚到保存点也不等于整个事务结束。
- **自动提交**：默认自动提交模式下，单独执行一条锁定查询无法将保护延续到之后另一条语句。应先显式开启事务，或使用正确生效的应用事务，不能查询结束后再单独开启更新事务。
- **锁等待超时**：InnoDB 默认通常只回滚当前等待超时的语句，不自动回滚整个事务，之前取得的锁可能仍在。应用决定放弃本次业务处理时，应明确回滚整个事务；实际行为还需核对 `innodb_rollback_on_timeout` 配置。
- **死锁**：InnoDB 检测到死锁后，会选择一个事务回滚。应用仍须处理异常并确认本次事务已结束，不能捕获异常后继续按旧查询结果处理。
- **连接断开或进程宕机**：数据库确认连接终止后，会回滚该连接上未提交的事务并释放锁；网络故障可能延迟断连检测。应用请求超时、线程中断或收到连接异常，都不能单独证明数据库已经结束事务。

提交响应丢失时，事务可能已经提交。此时应核实实际结果，再决定恢复方式，不能因为客户端报错就假定未提交并重复执行业务。锁等待、事务和数据库请求超时是不同层次的限制，具体生产取值待确认。

上述说明针对本次业务要保护的锁，不能推广成“所有扫描过的记录锁只能在提交时释放”；读已提交下，不匹配记录的锁可能在判断条件后提前释放。

依据：[InnoDB Error Handling](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html) 和 InnoDB 事务、锁定读取规则；连接异常及未知提交的实际恢复行为尚待验证。

### 4.4 核心 SQL：先锁住余额，再扣减

前提：教学表 `account` 使用 InnoDB，`id` 为主键，账户 `id = 1` 已存在；金额使用适当的精确数值类型。示例扣减 `100` 个金额单位，仅用于解释机制，不代表生产参数。以下注释中的分支由应用执行，不能跳过检查后连续执行所有 SQL。

```sql
START TRANSACTION;

SELECT balance
FROM account
WHERE id = 1
FOR UPDATE;

-- 应用检查：记录不存在或余额不足 100 时，ROLLBACK 并返回。
-- 只有记录存在且余额充足，才执行后续更新。
UPDATE account
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;

-- 应用检查影响行数必须为 1；否则 ROLLBACK 并返回失败。
COMMIT;
```

如果 A 锁定后余额为 150，B 此时也执行相同锁定查询，B 默认等待。A 扣减 100 并提交后释放锁，B 获得锁后读取到余额 50，应拒绝扣减并结束事务。这里保护的是“读取、检查、更新”的整体过程，避免两个请求都按旧余额作出判断；例中金额仅用于说明并发结果。

`AND balance >= 100` 是额外的业务条件校验；当前流程主要由前面的行锁保护，不能仅因 UPDATE 带条件就把整套方案称为乐观锁。对于只需按余额条件扣减的简单场景，直接执行条件 UPDATE 并检查影响行数也能原子判断和更新，不必机械地先查询加锁；但它不能替代复杂业务的其他检查，也不是 InnoDB 内部完全不加锁。

不要持锁执行远程调用或等待用户输入。仅锁住完成当前事务所必需的记录，并在业务检查失败时及时结束事务。示例没有展示建表、驱动接线或完整业务重试，尚未执行，不作为已实现能力或生产正确性的证明。
