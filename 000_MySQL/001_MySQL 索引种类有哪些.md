# 001_MySQL 索引种类有哪些

以下内容按照当前项目 AGENTS.md 项目级规则中规定的技术栈版本为准。本文讨论 MySQL 8.0.33 InnoDB；示例用于解释机制，未执行数据库实验。

## 1 问题

MySQL 索引有哪些分类，InnoDB 的索引结构和使用边界是什么？

## 2 高级 Java 面试核心考点

- 按功能、字段数量、数据结构和 InnoDB 存储方式区分索引。
- 理解聚簇索引、二级索引、回表和覆盖索引。
- 根据查询与写入特点判断是否适合建索引。

## 3 面试口述精炼版本

口述内容字符数：235

**按维度分类**

MySQL 索引不能只按一种方式分类：按功能有普通、唯一、主键、全文和空间索引；按字段数量有单列和联合索引；按结构有 B+Tree、Hash、FullText 和 R-Tree；InnoDB 还要区分聚簇索引和二级索引。

**理解 InnoDB 索引**

InnoDB 主键通常是聚簇索引，叶子节点保存整行；其他索引一般是二级索引，叶子节点保存索引列和主键，查完整行可能需要回表。查询字段都能由索引提供时，可能形成覆盖索引。联合索引要遵循最左前缀，索引也不是越多越好，因为会增加空间和写入维护成本。

详见：[索引分类和结构](<D:/000/sources/eas/000_MySQL/001_MySQL 索引种类有哪些.md:39>)。

## 4 详细方案

#### 一、InnoDB 是什么？

**InnoDB 是 MySQL 的一种存储引擎。**

通俗理解：

MySQL 是数据库系统，InnoDB 是 MySQL 里真正负责存数据、建索引、加锁、支持事务、保证数据安全的底层引擎。

MySQL 可以简单分成两层：

|   |   |
|---|---|
|层级|作用|
|MySQL Server 层|负责 SQL 解析、权限校验、查询优化、生成执行计划|
|存储引擎层|负责数据存储、索引组织、事务、锁、MVCC、崩溃恢复|

比如执行：

```
SELECT * FROM user WHERE id = 1;
```

大致过程是：

1. MySQL Server 层解析 SQL；
2. 优化器生成执行计划；
3. InnoDB 根据索引和数据页查数据；
4. 返回结果。

所以，**InnoDB 不是数据库本身，而是 MySQL 的存储引擎之一**。

---

#### 二、InnoDB 的核心特点

InnoDB 是现在 MySQL 中最常用的默认存储引擎，主要特点有：

|   |   |
|---|---|
|特点|说明|
|支持事务|支持 `BEGIN`、`COMMIT`、`ROLLBACK`，满足 ACID|
|支持行级锁|尽量只锁住操作的行，而不是整张表，并发性能更好|
|支持 MVCC|多版本并发控制，让普通读和写尽量不互相阻塞|
|支持外键|可以维护表与表之间的数据一致性|
|支持崩溃恢复|通过 redo log、undo log 等机制保证异常恢复|
|索引主要使用 B+Tree|普通索引、唯一索引、主键索引、联合索引底层一般都是 B+Tree|

一句话：

InnoDB 负责 MySQL 底层的数据存储、索引、事务、锁、MVCC 和崩溃恢复。

---

### 三、MySQL 索引怎么分类？

MySQL 索引不能只从一个角度分类，否则容易混乱。

比较规范的说法是从四个角度分类：

|   |   |
|---|---|
|分类角度|常见类型|
|按功能 / 约束|普通索引、唯一索引、主键索引、全文索引、空间索引|
|按字段数量|单列索引、联合索引|
|按数据结构|B+Tree、Hash、FullText、R-Tree|
|按 InnoDB 存储方式|聚簇索引、二级索引|

面试中不要只说：

MySQL 索引分为普通索引、唯一索引、主键索引、联合索引、全文索引。

这样说虽然常见，但分类维度混了。更好的说法是：

MySQL 索引可以按功能、字段数量、数据结构、InnoDB 存储方式来分类。

---

### 四、按功能 / 约束分类

#### 1. 普通索引

普通索引是最基础的索引，只负责**加快查询速度**，不要求唯一，也不限制是否为空。

```
CREATE INDEX idx_name ON user(name);
```

可以理解为：给字段建了一个“目录”，查数据时不用全表扫描。

---

#### 2. 唯一索引

唯一索引要求索引列的值不能重复。

```
CREATE UNIQUE INDEX idx_email ON user(email);
```

注意：

在 MySQL 中，唯一索引列可以为 `NULL`，并且通常允许多个 `NULL`，因为 `NULL` 表示未知，不认为两个 `NULL` 相等。

---

#### 3. 主键索引

主键索引是一种特殊的唯一索引。

特点是：

1. 唯一；
2. 非空；
3. 一张表只能有一个主键；
4. 主键可以由多个字段组成，也就是联合主键。

```
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50)
);
```

在 **InnoDB** 中，主键索引通常就是聚簇索引。

---

#### 4. 全文索引

全文索引用于文本关键词搜索，比如文章标题、文章正文搜索。

```
MATCH(title, content) AGAINST('mysql index');
```

它不是普通的 `=` 查询，也不是简单的 `LIKE '%xxx%'`，而是专门用于全文检索。

---

#### 5. 空间索引

空间索引用于地理空间数据，比如经纬度、地图坐标、GIS 场景。

普通后端面试中了解即可，不是最高频重点。

---

### 五、按字段数量分类

#### 1. 单列索引

单列索引就是只给一个字段建索引。

```
CREATE INDEX idx_age ON user(age);
```

---

#### 2. 联合索引

联合索引也叫复合索引，是多个字段组成一个索引。

```
CREATE INDEX idx_name_age_city ON user(name, age, city);
```

联合索引最重要的是：**最左前缀原则**。

比如有联合索引：

```
(name, age, city)
```

一般可以用到索引的写法有：

```
WHERE name = 'Tom';

WHERE name = 'Tom' AND age = 18;

WHERE name = 'Tom' AND age = 18 AND city = 'Beijing';
```

但如果直接查：

```
WHERE age = 18;
```

通常不能很好地利用这个联合索引，因为跳过了最左边的 `name`。

一句话记忆：

联合索引不是建了多个字段，每个字段都能随便用，而是要从最左边开始连续使用。

---

### 六、按数据结构分类

#### 1. B+Tree 索引

B+Tree 是 InnoDB 中最常见、最核心的索引结构。

在 InnoDB 中，常见的：

```
PRIMARY KEY
UNIQUE KEY
INDEX
KEY
联合索引
```

底层一般都是 **B+Tree**。

需要注意：

MySQL 官方文档有时写 B-Tree，但面试和数据库原理中，InnoDB 索引通常按 B+Tree 来理解。

---

#### 2. Hash 索引

Hash 索引适合等值查询：

```
WHERE id = 1;
```

但不适合范围查询和排序：

```
WHERE age > 18;

ORDER BY age;
```

因为 Hash 是根据哈希值定位数据，不适合顺序扫描。

在 MySQL 中，MEMORY 存储引擎支持 Hash 索引。
InnoDB 中有**自适应 Hash 索引**，但这是 InnoDB 内部自动优化的，不是开发人员手动创建的普通索引。

---

#### 3. FullText 索引

FullText 索引用于全文检索，底层可以理解为类似**倒排索引**的思想。

适合文章、标题、内容这类文本搜索。

---

#### 4. R-Tree 空间索引

R-Tree 主要用于空间数据索引，比如地图、坐标、地理位置。

普通业务面试中知道它和空间索引有关即可。

---

### 七、按 InnoDB 存储方式分类

这是 MySQL 面试高频重点。

#### 1. 聚簇索引

聚簇索引可以理解为：

索引的叶子节点直接存放完整的行数据。

在 InnoDB 中，一张表一定有一个聚簇索引。

选择规则是：

1. 如果有主键，就用主键作为聚簇索引；
2. 如果没有主键，就选择第一个非空唯一索引；
3. 如果还没有，InnoDB 会生成一个隐藏的聚簇索引。

所以更准确的说法是：

在 InnoDB 中，主键索引通常就是聚簇索引。

不要直接说：

MySQL 默认主键就是聚簇索引。

因为这是 **InnoDB 的特性**，不是所有 MySQL 存储引擎都这样。

---

#### 2. 二级索引

二级索引也叫辅助索引、非聚簇索引。

在 InnoDB 中，除了聚簇索引之外，其他索引一般都是二级索引。

二级索引的叶子节点存的是：

索引列 + 主键值

比如有表：

```
user(id, name, age)
```

其中 `id` 是主键，`age` 建了普通索引。

执行：

```
SELECT * FROM user WHERE age = 18;
```

大概过程是：

1. 先通过 `age` 的二级索引找到对应的主键 `id`；
2. 再通过主键 `id` 去聚簇索引里查完整行数据。

第二步就叫 **回表**。

---

#### 3. 覆盖索引

如果查询字段都在索引里，不需要回表，这种情况叫**覆盖索引**。

比如有联合索引：

```
(name, age)
```

执行：

```
SELECT name, age FROM user WHERE name = 'Tom';
```

因为 `name` 和 `age` 都在索引里，可以直接从索引中拿到结果，不需要回表。

一句话记忆：

二级索引查整行可能要回表；如果查询字段都在索引里，就叫覆盖索引，可以避免回表。

---

### 八、索引的数据结构由谁决定？

索引的数据结构主要由**存储引擎和索引类型**决定，不是开发人员随便指定的。

开发人员主要决定：

1. 给哪些字段建索引；
2. 建普通索引、唯一索引、主键索引、联合索引、全文索引还是空间索引。

至于底层到底是 B+Tree、Hash、倒排索引还是 R-Tree，主要由存储引擎实现。

在 InnoDB 中大致是：

|   |   |
|---|---|
|索引类型|常见底层结构|
|主键索引|B+Tree，通常也是聚簇索引|
|普通索引|B+Tree，二级索引|
|唯一索引|B+Tree，除主键外一般是二级索引|
|联合索引|B+Tree|
|全文索引|类似倒排索引|
|空间索引|R-Tree 相关|
|Hash 索引|InnoDB 主要是自适应 Hash，不是手动创建的普通索引|

虽然 MySQL 语法上可以写：

```
CREATE INDEX idx_name USING BTREE ON user(name);
```

某些存储引擎中也可以写：

```
CREATE INDEX idx_name USING HASH ON user(name);
```

但是否真正支持，要看具体存储引擎。

在 InnoDB 中，普通业务索引主要还是 B+Tree，不是开发人员想用 Hash 就能用 Hash。

一句话：

开发人员决定索引建在哪些字段上、建什么逻辑类型；存储引擎决定底层主要用什么数据结构。

---

### 九、什么时候适合建索引？

一般适合建索引的字段有：

1. 经常出现在 `WHERE` 条件中的字段；
2. 经常用于 `JOIN` 连接的字段；
3. 经常用于 `ORDER BY`、`GROUP BY` 的字段；
4. 区分度高的字段，比如手机号、邮箱、用户 ID；
5. 外键字段通常也适合建索引。

例如：

```
WHERE phone = '138xxxx';

WHERE user_id = 1001;

ORDER BY create_time;
```

这些字段都可能适合建索引。

---

### 十、哪些字段不适合建索引？

一般不太适合建索引的字段有：

1. 表数据量很小的字段；
2. 区分度很低的字段，比如性别、是否删除；
3. 经常被更新的字段；
4. 很长的文本字段，除非使用前缀索引或全文索引；
5. 查询时经常返回大量数据的字段。

因为索引不是越多越好。

索引的优点是提高查询速度，但缺点也很明显：

1. 占用磁盘空间；
2. 降低 `INSERT`、`UPDATE`、`DELETE` 的性能；
3. 数据变化时，索引也需要维护。

所以建索引要结合：

查询频率、数据量、区分度、写入频率。
